Du nom de domaine au processus Node.js

1.1 Les couches et le trajet d’une requête

Un échange Web traverse plusieurs responsabilités distinctes :

  1. Application : le navigateur ou le client construit une requête HTTP.
  2. DNS : le nom est résolu en une ou plusieurs adresses IP, en tenant compte des caches et des règles DNS applicables.
  3. Routage IP : les paquets sont acheminés vers la machine cible.
  4. Transport : TCP établit un flux fiable et ordonné ; HTTP/3 utilise QUIC au-dessus d’UDP.
  5. Sécurité de transport : pour HTTPS, TLS négocie des paramètres cryptographiques et permet de vérifier l’identité présentée par le serveur.
  6. HTTP : le serveur interprète méthode, cible, en-têtes et corps, puis renvoie statut, en-têtes et éventuellement corps.
  7. Application métier : Node.js applique la logique, appelle éventuellement une base ou un service distant et construit la réponse.

Le chemin réel peut inclure un proxy d’entreprise, un CDN, un répartiteur de charge, un pare-feu ou un reverse proxy. Le serveur HTTP Node.js n’est donc pas nécessairement le premier composant rencontré sur la machine d’hébergement.

Une erreur 404 est une réponse HTTP reçue ; ECONNREFUSED signale généralement que la connexion a été refusée ; ENOTFOUND ou EAI_AGAIN concerne la résolution de nom ; une erreur de certificat concerne TLS. Ces erreurs ne se corrigent pas au même endroit.

1.2 IP, ports, sockets et écoute Node.js

Une adresse IP permet l’acheminement. Un port identifie un point d’extrémité de transport. Le couple adresse/port local d’un serveur doit être compatible avec le client et la configuration réseau. Le port 443 est conventionnel pour HTTPS, mais un numéro de port ne garantit pas le protocole réellement servi.

127.0.0.1 et ::1 désignent la boucle locale IPv4 et IPv6. Un service lié à 127.0.0.1 n’est normalement accessible que depuis la machine elle-même. Un service lié à 0.0.0.0 écoute sur toutes les interfaces IPv4 disponibles : cette configuration ne doit pas être choisie sans comprendre l’exposition réseau et les règles de pare-feu.

Exemple minimal en TypeScript, à compiler avant exécution selon la configuration du projet :

import { createServer } from "node:http";

const server = createServer((_request, response) => {
  response.writeHead(200, { "content-type": "text/plain; charset=utf-8" });
  response.end("Serveur Node.js disponible\n");
});

server.listen(3000, "127.0.0.1", () => {
  console.log("Écoute sur http://127.0.0.1:3000");
});

Cet exemple n’implémente ni routage, ni validation d’entrée, ni arrêt gracieux : il sert uniquement à illustrer l’écoute HTTP. Il ne constitue pas une base de production.

1.3 DNS : résolution, TTL et diagnostic

DNS associe un nom à des enregistrements : A (IPv4), AAAA (IPv6), CNAME (alias), MX (messagerie), TXT (texte et vérifications diverses). Un résolveur peut répondre depuis son cache jusqu’à l’expiration du TTL. Après une modification DNS, la propagation apparente dépend des caches, des TTL et de la configuration des résolveurs ; ce n’est pas nécessairement une réplication instantanée mondiale.

Commandes de diagnostic (selon le système, dig peut nécessiter l’installation d’un paquet système) :

dig example.com A
dig example.com AAAA
nslookup example.com

Ne concluez pas à une panne HTTP lorsque la résolution du nom échoue. Testez d’abord la résolution, puis la connexion, puis TLS et enfin la réponse applicative.

Exercice 1 — Localiser la panne

Un navigateur affiche « site inaccessible ». dig api.example.test A renvoie une erreur de résolution ; aucune connexion TCP n’est tentée vers l’adresse attendue.

Question : quelle couche vérifier en premier et pourquoi ?

Corrigé : vérifier la résolution DNS (nom, zone, résolveur, configuration locale et cache). Sans adresse cible résolue, le diagnostic d’une réponse HTTP n’est pas pertinent. Si le DNS est ensuite correct, poursuivre vers la connexion TCP, TLS puis HTTP.

Quiz du module 1

Un port 443 garantit-il que le serveur parle HTTPS ? Non. Le port est une convention ; c’est la négociation TLS et le protocole réellement servi qui déterminent l’échange.
