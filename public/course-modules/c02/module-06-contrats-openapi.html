Contrats OpenAPI

6.1 Pourquoi un contrat explicite ?

OpenAPI décrit les chemins, méthodes, paramètres, corps, réponses, schémas, mécanismes de sécurité et métadonnées d’une API HTTP. Il permet de générer une documentation interactive et, selon l’outillage, des clients, des stubs et des contrôles de contrat. Le document ne prouve pas que le serveur respecte réellement le contrat : des tests doivent comparer l’implémentation et la spécification.

Choisir et documenter la version OpenAPI employée. La spécification OpenAPI 3.1 s’appuie sur une compatibilité étroite avec le modèle de schéma JSON ; les outils ne prennent pas nécessairement en charge toutes les fonctionnalités de manière identique. Épingler les versions d’outils et vérifier les écarts dans la CI.

6.2 Extrait minimal

openapi: 3.1.1
info:
  title: Tasks API
  version: 1.0.0
paths:
  /tasks:
    post:
      operationId: createTask
      summary: Créer une tâche
      requestBody:
        required: true
        content:
          application/json:
            schema:
              type: object
              additionalProperties: false
              required: [title]
              properties:
                title:
                  type: string
                  minLength: 1
                  maxLength: 120
      responses:
        '201':
          description: Tâche créée
        '400':
          description: Corps invalide
        '500':
          description: Erreur inattendue

L’extrait illustre la forme du contrat et ne décrit pas toutes les réponses utiles : il faudrait documenter les schémas des réponses, les erreurs, les en-têtes, l’authentification, les limites et les éventuelles réponses 409/413. La version info.version identifie la version publiée du contrat, mais ne définit pas à elle seule la stratégie de versionnement des URLs.

6.3 Éviter la dérive

Une seule source de vérité réduit les divergences : schémas runtime partagés, génération du document depuis le code, ou contrat OpenAPI utilisé pour générer des types et valider l’implémentation. Chacune de ces stratégies a des compromis. Éviter de maintenir manuellement trois schémas identiques (TypeScript, validateur runtime, OpenAPI) sans mécanisme de cohérence.

Exercice 6 — Contrat sans réponse

Une opération POST /tasks documente seulement 200, mais l’implémentation renvoie 201 et un corps contenant l’identifiant.

Corrigé : mettre le contrat et l’implémentation en accord. Si la création est la sémantique retenue, documenter 201, le schéma du corps et les en-têtes pertinents, puis ajouter un test de contrat. Ne pas supposer que la documentation interactive détectera automatiquement cet écart.

Quiz 6

OpenAPI valide-t-il automatiquement les requêtes en production ? Non. Il décrit un contrat ; il faut une intégration de validation ou des contrôles côté serveur et des tests pour faire respecter ce contrat.
