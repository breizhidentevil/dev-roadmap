Doubles de test : mock, stub, fake et spy

4.1 Quatre notions distinctes

  • Stub : renvoie une valeur contrôlée ou simule une réponse pour un scénario.
  • Mock : permet aussi d’attendre des interactions précises, par exemple l’envoi d’un message.
  • Fake : implémentation simplifiée mais fonctionnelle, par exemple un dépôt en mémoire.
  • Spy : observe les appels d’une vraie fonction ou d’un objet sans nécessairement remplacer son comportement.

Les termes varient parfois selon les équipes ; l’important est de préciser le rôle du double.

4.2 Exemple : isoler un service

type Reservation = { id: string; status: "pending" | "confirmed" };

interface ReservationRepository {
  findById(id: string): Promise<Reservation | null>;
  save(reservation: Reservation): Promise<void>;
}

interface NotificationGateway {
  sendConfirmation(reservationId: string): Promise<void>;
}

export class ReservationService {
  constructor(
    private readonly repository: ReservationRepository,
    private readonly notifications: NotificationGateway,
  ) {}

  async confirm(id: string): Promise<void> {
    const reservation = await this.repository.findById(id);
    if (!reservation) throw new Error("RESERVATION_NOT_FOUND");
    if (reservation.status !== "pending") throw new Error("INVALID_STATE");

    const confirmed = { ...reservation, status: "confirmed" as const };
    await this.repository.save(confirmed);
    await this.notifications.sendConfirmation(id);
  }
}

Le service dépend d’interfaces explicites. Le test peut injecter un fake de dépôt et un mock de notification. Le design rend les effets de bord visibles, sans imposer une bibliothèque de mocks.

Attention : ce service illustre une séquence métier simple, pas une garantie transactionnelle. Si l’envoi de notification échoue après l’écriture, la réservation est déjà confirmée. En production, envisager une outbox transactionnelle ou un processus de reprise plutôt que d’imaginer qu’un mock prouve la fiabilité distribuée.

4.3 Exemple de test isolé

import { beforeEach, expect, it, vi } from "vitest";

const repository = {
  findById: vi.fn(),
  save: vi.fn(),
};
const notifications = {
  sendConfirmation: vi.fn(),
};

beforeEach(() => {
  vi.resetAllMocks();
});

it("enregistre la confirmation puis notifie", async () => {
  repository.findById.mockResolvedValue({ id: "r-17", status: "pending" });
  repository.save.mockResolvedValue(undefined);
  notifications.sendConfirmation.mockResolvedValue(undefined);

  const service = new ReservationService(repository, notifications);
  await service.confirm("r-17");

  expect(repository.save).toHaveBeenCalledWith({
    id: "r-17",
    status: "confirmed",
  });
  expect(notifications.sendConfirmation).toHaveBeenCalledWith("r-17");
});

it("ne notifie pas si la réservation est absente", async () => {
  repository.findById.mockResolvedValue(null);

  const service = new ReservationService(repository, notifications);
  await expect(service.confirm("missing")).rejects.toThrow("RESERVATION_NOT_FOUND");
  expect(repository.save).not.toHaveBeenCalled();
  expect(notifications.sendConfirmation).not.toHaveBeenCalled();
});

Dans un vrai projet TypeScript strict, déclarer les types des mocks ou employer vi.mocked selon la structure des modules afin d’éviter des types trop permissifs. L’extrait privilégie la lisibilité conceptuelle.

4.4 Quand ne pas mocker ?

Ne pas mocker la base pour prouver une contrainte SQL, une transaction ou une isolation concurrente. Ne pas mocker le routeur pour prétendre tester le contrat HTTP. Un double ne peut prouver que son propre comportement et le code qui l’appelle, pas la compatibilité réelle avec l’infrastructure.

Un mock trop détaillé peut transformer le test en miroir de l’implémentation. Une modification interne fait alors échouer la suite sans changement métier. Mockez les frontières instables ou coûteuses, mais gardez des tests d’intégration ciblés.

Exercice 4

Choisir le double adapté :

  1. Forcer une passerelle de paiement à répondre « refusée ».
  2. Vérifier qu’un événement est publié une seule fois.
  3. Tester un algorithme de recherche sans serveur de base.
  4. Vérifier une contrainte UNIQUE PostgreSQL.

Correction expliquée : 1) stub ; 2) mock/spy sur le port de publication ; 3) fake de dépôt si le but est le service, mais tester l’algorithme directement si possible ; 4) vraie base PostgreSQL, pas un mock.

Quiz 4

Pourquoi un fake en mémoire ne suffit-il pas pour tester une contrainte SQL ?

Réponse : il ne reproduit pas nécessairement le moteur SQL, les transactions, les verrous, les contraintes ou l’isolation. Il peut être utile pour tester une logique applicative, mais pas pour prouver le comportement du SGBD.
