Fixtures, déterminisme et couverture

9.1 Fixtures et données de test

Une fixture est un état de départ contrôlé. Elle doit être petite, explicite et adaptée au scénario. Éviter les usines de données si complexes qu’elles masquent les propriétés importantes. Les données peuvent être générées, mais la graine et les contraintes doivent être maîtrisées pour permettre de reproduire un échec.

Chaque test doit pouvoir être exécuté seul et dans un ordre différent. Un test qui passe seulement après un autre dépend d’un état caché.

9.2 Maîtriser l’horloge, l’aléatoire et l’environnement

  • Injecter une horloge ou utiliser les faux timers du runner pour les règles dépendantes du temps.
  • Contrôler la génération d’identifiants lorsque leur valeur influe sur l’assertion.
  • Ne pas dépendre d’un fuseau horaire implicite : utiliser des dates ISO et UTC lorsque cela correspond au contrat.
  • Fixer la locale, les variables d’environnement et la configuration pertinentes.
  • Ne pas appeler de services externes réels dans les tests unitaires.
  • Toujours restaurer les mocks, timers et variables modifiées.

Un test déterministe n’est pas un test qui ignore les pannes : les erreurs doivent être simulées intentionnellement, et les tests d’intégration doivent échouer clairement si leur infrastructure requise n’est pas disponible.

9.3 Couverture de code

Les métriques habituelles incluent :

  • lignes : lignes exécutées ;
  • instructions : instructions exécutées ;
  • branches : chemins conditionnels observés ;
  • fonctions : fonctions appelées.

La couverture aide à identifier des zones non exercées. Elle ne mesure pas directement la pertinence des assertions, la qualité des scénarios, la conformité aux besoins ou la robustesse concurrente.

Un objectif global de 80 % peut être un repère d’équipe, pas une preuve de qualité. Un module de calcul critique peut nécessiter une couverture de branches plus élevée ; une configuration générée ou un adaptateur trivial peut avoir un autre objectif. Éviter de modifier les seuils seulement pour faire passer la CI.

9.4 Mutation testing et qualité des assertions

Le mutation testing introduit volontairement de petites erreurs (par exemple inverser > en >=) et observe si les tests les détectent. Si une mutation plausible survit, les assertions ou les scénarios sont peut-être trop faibles. Cette technique complète la couverture, sans remplacer la revue du modèle métier.

9.5 Définir une porte de qualité reproductible

Un pipeline raisonnable peut exécuter, dans cet ordre :

  1. formatage et lint ;
  2. vérification TypeScript ;
  3. tests unitaires rapides ;
  4. tests d’intégration avec dépendances isolées ;
  5. tests de contrat ;
  6. couverture et contrôle de seuil ;
  7. tests end-to-end ciblés.

Les étapes exactes dépendent des scripts du dépôt. Un résultat local n’est pas reproductible si les versions, les variables d’environnement, les migrations ou les services requis ne sont pas documentés.

Exercice 9

Une suite affiche 98 % de couverture, mais ne teste pas les erreurs SQL, l’accès interdit ni la concurrence. Peut-on conclure que le backend est fiable ?

Correction expliquée : non. La couverture élevée décrit l’exécution des lignes/branches mesurées, pas les propriétés non testées. Ajouter des scénarios correspondant aux risques : panne de dépendance, accès croisé, rollback et opérations concurrentes.

Quiz 9

Quel est le meilleur usage d’un rapport de couverture ?

A. Remplacer la revue de code.
B. Identifier les zones non exécutées et guider l’ajout de tests pertinents.
C. Déclarer l’absence de bugs dès qu’un seuil est atteint.

Réponse : B. La couverture est un outil de diagnostic et de priorisation, pas une garantie de correction.
