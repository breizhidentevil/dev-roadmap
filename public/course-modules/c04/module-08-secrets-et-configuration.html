Secrets et configuration

8.1 Séparer code et secrets

Ne jamais committer les mots de passe de base, clés privées, tokens de fournisseur, secrets OAuth ou clés de chiffrement. Les variables d’environnement sont un moyen de configuration, pas automatiquement un coffre-fort : leur exposition dépend des processus, outils de déploiement, dumps et journaux.

En production, préférer un gestionnaire de secrets ou un mécanisme de plateforme adapté, avec contrôle d’accès, audit et rotation. Injecter les secrets au démarrage ou à l’exécution selon la plateforme, limiter leur durée et leur portée, et éviter de les copier dans les fichiers de configuration du frontend.

8.2 Valider la configuration au démarrage

Traiter la configuration comme une entrée non fiable : valider présence, format et valeurs autorisées. Échouer tôt si une clé obligatoire manque, sans imprimer sa valeur.

type Config = {
  port: number;
  sessionSecret: string;
};

export function loadConfig(env: NodeJS.ProcessEnv): Config {
  const rawPort = env.PORT ?? "3000";
  const port = Number(rawPort);

  if (!Number.isInteger(port) || port < 1 || port > 65535) {
    throw new Error("PORT must be an integer between 1 and 65535");
  }

  const sessionSecret = env.SESSION_SECRET;
  if (!sessionSecret || sessionSecret.length < 32) {
    throw new Error("SESSION_SECRET is missing or too short");
  }

  return { port, sessionSecret };
}

La longueur minimale est ici une règle illustrative, pas un standard universel de génération de secret. Un secret doit être produit par un générateur cryptographiquement sûr et respecter les recommandations du mécanisme utilisé. Ne pas utiliser une phrase prévisible ou un mot de passe humain comme clé de session.

8.3 Rotation et moindre privilège

Définir la rotation et le remplacement d’urgence des secrets. Vérifier les effets d’une rotation sur les sessions et les tokens actifs. Un compte de base de données applicatif ne devrait pas être superutilisateur ; accorder seulement les opérations nécessaires au runtime. Séparer les secrets de développement, test, préproduction et production.

Exercice 8

Un token d’API apparaît dans un commit Git public. Le supprimer dans le commit suivant suffit-il ?

Correction expliquée : non. Le secret doit être considéré compromis : le révoquer ou le faire tourner immédiatement, examiner les usages, supprimer les copies lorsque possible et rechercher d’autres expositions. Réécrire l’historique peut réduire la propagation mais ne remplace jamais la révocation.

Quiz 8

Une variable d’environnement est-elle toujours un stockage sûr de secrets ?

Réponse : non. Elle évite certains secrets codés en dur mais peut être exposée via les processus, diagnostics, outils de déploiement ou logs. Il faut considérer les propriétés de la plateforme et limiter l’accès.
