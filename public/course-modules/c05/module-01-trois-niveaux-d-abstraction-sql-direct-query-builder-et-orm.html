1. Trois niveaux d'abstraction : SQL direct, query builder et ORM

SQL direct

Le développeur écrit le SQL et contrôle explicitement les jointures, les projections, les clauses de verrouillage et les opérations. C'est adapté aux requêtes complexes, aux besoins de performance mesurés et aux équipes qui maîtrisent le modèle relationnel. Le coût est la gestion des conversions de types, de la composition des requêtes et de la correspondance entre résultats et types TypeScript.

import { Pool } from "pg";

const pool = new Pool({ connectionString: process.env.DATABASE_URL });

interface UserRow {
  id: string;
  email: string;
  created_at: Date;
}

export async function findUserByEmail(email: string): Promise<UserRow | undefined> {
  const result = await pool.query<UserRow>(
    `SELECT id, email, created_at FROM users WHERE email = $1`,
    [email],
  );
  return result.rows[0];
}

Le paramètre $1 protège la valeur contre l'interprétation comme fragment SQL. Le type générique UserRow est une déclaration de l'application : il ne valide pas à lui seul les données renvoyées par le serveur et ne remplace pas les contraintes de la base.

Query builder

Un query builder compose une requête par API TypeScript, tout en exposant généralement les concepts SQL. Il peut améliorer la réutilisation et le typage, mais la requête finale doit toujours être inspectée. Un builder ne rend pas automatiquement sûre une interpolation de SQL brut.

ORM

Un ORM représente tables et relations par des modèles ou schémas de code et automatise une partie des opérations de lecture/écriture. Il peut réduire le code répétitif et offrir des types dérivés du schéma. Il peut aussi masquer le coût des requêtes, produire des chargements inattendus et rendre les opérations SQL spécifiques moins évidentes.

Règle de décision : choisir l'abstraction la plus simple qui couvre les besoins démontrés. Une application peut combiner ORM pour les opérations courantes et SQL explicite pour quelques requêtes spécialisées, à condition d'encadrer cette frontière.
