7. Relations, N+1, chargement et pagination

Le problème N+1 apparaît lorsqu'une requête charge une collection puis exécute une requête supplémentaire pour chaque élément. Le code peut sembler simple tout en multipliant le nombre d'allers-retours.

Approches possibles :

  • jointure SQL lorsque les relations et la cardinalité sont maîtrisées ;
  • chargement groupé (batch) des entités associées ;
  • chargement explicite par besoin fonctionnel ;
  • eager loading d'un ORM, à surveiller car plusieurs collections jointes peuvent multiplier les lignes retournées.

Pour toute requête importante, examiner le SQL généré, le nombre de requêtes, les lignes transférées et le plan d'exécution. Utiliser EXPLAIN et, dans un environnement contrôlé, EXPLAIN (ANALYZE, BUFFERS) ; ANALYZE exécute effectivement la requête.

Pagination par offset : simple pour les petites listes, mais le coût augmente parfois avec les offsets élevés et les insertions concurrentes peuvent déplacer les pages. Pour de grandes listes, préférer souvent une pagination par curseur fondée sur un ordre stable et unique :

SELECT id, created_at, title
FROM posts
WHERE (created_at, id) < ($1, $2)
ORDER BY created_at DESC, id DESC
LIMIT $3;

L'index doit correspondre au filtre et à l'ordre de la requête. Le curseur doit être validé, borné et lié au bon filtre/ordre ; ne pas exposer des données sensibles dans un curseur non protégé.
