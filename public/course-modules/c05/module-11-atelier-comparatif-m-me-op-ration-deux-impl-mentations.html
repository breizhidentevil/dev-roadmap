11. Atelier comparatif : même opération, deux implémentations

Implémenter une opération de lecture paginée des publications d'un auteur :

  1. une version avec SQL paramétré via node-postgres ;
  2. une version avec Drizzle ORM ;
  3. des tests d'intégration couvrant pagination, auteur inconnu, paramètres invalides et ordre stable.

Pour chaque version, fournir : SQL final ou généré, nombre de requêtes, plan d'exécution, contraintes attendues, cas d'erreur et compromis de maintenance. Les deux versions doivent partager les mêmes critères de correction.

Exercices corrigés

Exercice 1 — Identifier la garantie

Question : une interface déclare age: number. Est-ce suffisant pour garantir que la base ne contiendra jamais un âge négatif ?

Correction : non. TypeScript ne s'exécute pas comme validation des données entrantes. Valider à la frontière applicative et ajouter une contrainte SQL CHECK (age >= 0) si l'invariant s'applique aux données stockées.

Exercice 2 — Corriger une injection

Question : corriger SELECT * FROM users WHERE email = '${email}'.

Correction : utiliser pool.query("SELECT id, email FROM users WHERE email = $1", [email]). Pour un nom de colonne dynamique, utiliser une liste blanche ; un paramètre ne peut pas remplacer un identifiant SQL.

Exercice 3 — Transaction

Question : pourquoi ne faut-il pas appeler pool.query("BEGIN"), puis deux fois pool.query(...), puis pool.query("COMMIT") en supposant que toutes les requêtes utilisent la même connexion ?

Correction : chaque appel au pool peut emprunter une connexion différente. Acquérir un client, effectuer toutes les instructions transactionnelles sur ce client, puis le libérer dans finally.

Exercice 4 — N+1

Question : une page affiche 40 auteurs et le code lance une requête de livres par auteur. Quel est le problème et une solution ?

Correction : le nombre de requêtes croît avec le nombre d'auteurs (1 + 40 dans cet exemple). Charger les livres par lots avec une requête filtrée sur les identifiants, ou faire une jointure et regrouper les résultats, après mesure et vérification de la cardinalité.

Exercice 5 — Retour arrière

Question : une migration supprime une colonne contenant des données. Un script down qui recrée une colonne vide restaure-t-il l'état précédent ?

Correction : non. La structure revient, mais pas les données perdues. Une restauration nécessite une sauvegarde valide ou une migration corrective alimentée par une source conservée.

Exercice 6 — Pagination

Question : pourquoi ORDER BY created_at DESC LIMIT 20 n'est-il pas un ordre totalement stable si plusieurs lignes partagent le même timestamp ?

Correction : les lignes à timestamp égal peuvent apparaître dans un ordre différent. Ajouter un critère unique, par exemple ORDER BY created_at DESC, id DESC, et inclure ces deux valeurs dans le curseur.

Exercice 7 — Pool

Question : que doit-on garantir après const client = await pool.connect() ?

Correction : libérer le client dans un bloc finally, même en cas d'exception. Pour une transaction, exécuter ROLLBACK lorsque nécessaire, sans perdre l'erreur initiale.

Exercice 8 — ORM

Question : un ORM est-il une garantie que chaque page ne déclenche qu'une requête SQL ?

Correction : non. Les stratégies de chargement peuvent générer plusieurs requêtes, des N+1 ou des jointures volumineuses. Inspecter le SQL, compter les requêtes et tester les cas représentatifs.

Exercice 9 — Test de cohérence

Question : les tests unitaires passent mais la migration a oublié une contrainte UNIQUE. Quelle catégorie de test aurait dû détecter le problème ?

Correction : un test d'intégration appliquant les migrations sur une base isolée puis tentant deux insertions conflictuelles. Un mock du dépôt ne vérifie pas le schéma réel.

Quiz avec explications

  1. Les types TypeScript valident-ils les données à l'exécution ? Non : ils guident la compilation ; il faut valider les entrées non fiables.
  2. Un paramètre SQL peut-il remplacer ORDER BY ${column} ? Non : les paramètres portent sur les valeurs. Les identifiants dynamiques doivent provenir d'une liste contrôlée ou d'une API sûre.
  3. Toutes les requêtes transactionnelles doivent-elles partager un client ? Oui, avec node-postgres ; sinon elles peuvent être exécutées sur des connexions différentes.
  4. Une transaction sérialisable ne peut-elle jamais échouer ? Faux : PostgreSQL peut annuler une transaction pour préserver la sérialisabilité ; la reprise doit être bornée et sûre.
  5. Une migration inverse restaure-t-elle toujours les données ? Non : les changements destructifs peuvent être irréversibles sans sauvegarde ou copie des données.
  6. Un ORM élimine-t-il N+1 ? Non : il peut aider, mais la stratégie de chargement doit être contrôlée.
  7. Pourquoi ajouter une clé secondaire unique à l'ordre paginé ? Pour stabiliser l'ordre lorsque la colonne principale comporte des égalités.
  8. Pourquoi libérer le client dans finally ? Pour éviter de perdre des connexions du pool en cas de succès comme d'échec.
  9. Les tests unitaires prouvent-ils que les migrations s'appliquent ? Non : il faut une validation sur une vraie base de test.

Projet intégrateur

Construire la couche de données d'une API de publications et de comptes avec TypeScript et PostgreSQL. Comparer SQL direct et Drizzle sur une opération représentative.

Fonctionnalités minimales

  • schéma versionné avec clés primaires, clés étrangères, contraintes NOT NULL, UNIQUE et CHECK pertinentes ;
  • dépôt typé et service métier séparés sans abstraction superflue ;
  • paramètres SQL sûrs pour toutes les valeurs ;
  • transaction pour une opération multi-écriture avec gestion des échecs ;
  • pagination stable et bornée ;
  • migrations testées depuis une base vide ;
  • tests d'intégration pour contraintes, erreurs, pagination et concurrence pertinente ;
  • note d'analyse du SQL produit et de ses plans d'exécution.

Critères d'acceptation

  • Aucune valeur utilisateur n'est concaténée dans le SQL.
  • Les invariants essentiels sont protégés par la base, pas uniquement par TypeScript.
  • Les clients acquis au pool sont toujours libérés.
  • Les écritures qui doivent être atomiques sont transactionnelles.
  • Les erreurs de contrainte et de concurrence sont gérées sans divulguer de détails internes au client HTTP.
  • La pagination a un ordre stable, une limite maximale et des paramètres validés.
  • Le nombre de requêtes et le SQL généré sont documentés pour le cas étudié.
  • Les migrations et tests d'intégration sont reproductibles sur une base isolée.
  • Les limites de reprise et de retour arrière sont explicitées.

Limites de ce support

Les exemples sont pédagogiques et ne constituent pas une implémentation complète prête pour la production. Les extraits Drizzle ne sont pas compilés ici et le projet source ne déclare pas Drizzle ni pg comme dépendances applicatives. Avant usage réel, fixer les versions, vérifier les types du pilote, exécuter les migrations et tests sur PostgreSQL et mesurer les requêtes sur des données représentatives.
