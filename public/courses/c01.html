C01 — HTTP, réseaux et Web appliqués à Node.js

  • Version pédagogique : 1.0
  • Date : 14 octobre 2026
  • Statut : rédigé ; exemples non validés par exécution intégrale
  • Niveau : intermédiaire, après JavaScript moderne, TypeScript et bases Node.js
  • Durée indicative : 8 à 12 heures, projet compris
  • Environnement de référence : Node.js 22 LTS ou version LTS ultérieure compatible ; TypeScript 5.9 ; terminal avec curl ; navigateur avec DevTools

Objectifs et prérequis

À l’issue du cours, l’apprenant sait reconstituer le trajet d’une requête depuis le client jusqu’au processus Node.js, lire une requête et une réponse HTTP, distinguer panne DNS, refus TCP, erreur TLS, réponse HTTP en erreur et timeout, expliquer le rôle des cookies, du cache et de CORS, puis collecter des éléments de diagnostic reproductibles.

Prérequis : fonctions, promesses et async/await en JavaScript, types TypeScript, modules Node.js, ligne de commande et notions de base sur les processus. Les cours HTML, JavaScript et Node.js existants restent les références pour leurs concepts respectifs ; ce document les applique aux échanges réseau plutôt que de les recopier.

Plan

  1. Modèle client-serveur, DNS, ports et cycle d’une requête.
  2. HTTP : méthodes, statuts, en-têtes, corps et négociation de contenu.
  3. Cookies, cache HTTP, CORS et requêtes préflight.
  4. TLS, certificats, reverse proxy et terminaison HTTPS.
  5. Timeouts, erreurs réseau, connexions persistantes et limites.
  6. Diagnostic avec curl, DevTools et journaux Node.js.

Module 1 — Du nom de domaine au processus Node.js

1.1 Les couches et le trajet d’une requête

Un échange Web traverse plusieurs responsabilités distinctes :

  1. Application : le navigateur ou le client construit une requête HTTP.
  2. DNS : le nom est résolu en une ou plusieurs adresses IP, en tenant compte des caches et des règles DNS applicables.
  3. Routage IP : les paquets sont acheminés vers la machine cible.
  4. Transport : TCP établit un flux fiable et ordonné ; HTTP/3 utilise QUIC au-dessus d’UDP.
  5. Sécurité de transport : pour HTTPS, TLS négocie des paramètres cryptographiques et permet de vérifier l’identité présentée par le serveur.
  6. HTTP : le serveur interprète méthode, cible, en-têtes et corps, puis renvoie statut, en-têtes et éventuellement corps.
  7. Application métier : Node.js applique la logique, appelle éventuellement une base ou un service distant et construit la réponse.

Le chemin réel peut inclure un proxy d’entreprise, un CDN, un répartiteur de charge, un pare-feu ou un reverse proxy. Le serveur HTTP Node.js n’est donc pas nécessairement le premier composant rencontré sur la machine d’hébergement.

Une erreur 404 est une réponse HTTP reçue ; ECONNREFUSED signale généralement que la connexion a été refusée ; ENOTFOUND ou EAI_AGAIN concerne la résolution de nom ; une erreur de certificat concerne TLS. Ces erreurs ne se corrigent pas au même endroit.

1.2 IP, ports, sockets et écoute Node.js

Une adresse IP permet l’acheminement. Un port identifie un point d’extrémité de transport. Le couple adresse/port local d’un serveur doit être compatible avec le client et la configuration réseau. Le port 443 est conventionnel pour HTTPS, mais un numéro de port ne garantit pas le protocole réellement servi.

127.0.0.1 et ::1 désignent la boucle locale IPv4 et IPv6. Un service lié à 127.0.0.1 n’est normalement accessible que depuis la machine elle-même. Un service lié à 0.0.0.0 écoute sur toutes les interfaces IPv4 disponibles : cette configuration ne doit pas être choisie sans comprendre l’exposition réseau et les règles de pare-feu.

Exemple minimal en TypeScript, à compiler avant exécution selon la configuration du projet :

import { createServer } from "node:http";

const server = createServer((_request, response) => {
  response.writeHead(200, { "content-type": "text/plain; charset=utf-8" });
  response.end("Serveur Node.js disponible\n");
});

server.listen(3000, "127.0.0.1", () => {
  console.log("Écoute sur http://127.0.0.1:3000");
});

Cet exemple n’implémente ni routage, ni validation d’entrée, ni arrêt gracieux : il sert uniquement à illustrer l’écoute HTTP. Il ne constitue pas une base de production.

1.3 DNS : résolution, TTL et diagnostic

DNS associe un nom à des enregistrements : A (IPv4), AAAA (IPv6), CNAME (alias), MX (messagerie), TXT (texte et vérifications diverses). Un résolveur peut répondre depuis son cache jusqu’à l’expiration du TTL. Après une modification DNS, la propagation apparente dépend des caches, des TTL et de la configuration des résolveurs ; ce n’est pas nécessairement une réplication instantanée mondiale.

Commandes de diagnostic (selon le système, dig peut nécessiter l’installation d’un paquet système) :

dig example.com A
dig example.com AAAA
nslookup example.com

Ne concluez pas à une panne HTTP lorsque la résolution du nom échoue. Testez d’abord la résolution, puis la connexion, puis TLS et enfin la réponse applicative.

Exercice 1 — Localiser la panne

Un navigateur affiche « site inaccessible ». dig api.example.test A renvoie une erreur de résolution ; aucune connexion TCP n’est tentée vers l’adresse attendue.

Question : quelle couche vérifier en premier et pourquoi ?

Corrigé : vérifier la résolution DNS (nom, zone, résolveur, configuration locale et cache). Sans adresse cible résolue, le diagnostic d’une réponse HTTP n’est pas pertinent. Si le DNS est ensuite correct, poursuivre vers la connexion TCP, TLS puis HTTP.

Quiz du module 1

Un port 443 garantit-il que le serveur parle HTTPS ? Non. Le port est une convention ; c’est la négociation TLS et le protocole réellement servi qui déterminent l’échange.

Module 2 — Lire et concevoir un échange HTTP

2.1 Anatomie des messages

Une requête HTTP/1.1 typique comprend une ligne de requête, des en-têtes, une ligne vide et, si nécessaire, un corps :

GET /api/products/42 HTTP/1.1
Host: localhost:3000
Accept: application/json

La réponse correspondante pourrait être :

HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8
Cache-Control: no-store

{"id":42,"name":"Clavier"}

HTTP/2 et HTTP/3 n’utilisent pas cette représentation textuelle sur le réseau, mais conservent la sémantique des méthodes, champs d’en-tête et statuts. Les outils d’inspection peuvent afficher une représentation adaptée au protocole.

Le corps n’est pas toujours présent. Content-Type décrit le format du corps envoyé ; Accept exprime les types de réponse que le client sait traiter. La négociation peut aussi utiliser Accept-Language ou Accept-Encoding. Le serveur doit éviter d’annoncer un type de contenu qui ne correspond pas au corps réel.

2.2 Méthodes, sûreté et idempotence

  • GET récupère une représentation ; il est conçu comme une méthode sûre et idempotente.
  • HEAD correspond à GET sans corps de réponse.
  • POST soumet une représentation ou déclenche un traitement ; il n’est pas idempotent par définition.
  • PUT remplace généralement la représentation ciblée et est idempotent du point de vue sémantique.
  • PATCH applique une modification partielle ; son idempotence dépend de l’opération définie.
  • DELETE demande la suppression de la ressource ciblée ; la méthode est idempotente sémantiquement, même si les réponses successives peuvent différer.

Idempotent ne signifie pas « la réponse est toujours identique » et ne garantit pas qu’un client peut répéter aveuglément n’importe quelle opération. Si le client perd la connexion après l’envoi, il peut ignorer si le serveur a effectué l’action. Les opérations de paiement, réservation ou création nécessitent un contrat applicatif clair, parfois une clé d’idempotence persistée côté serveur.

2.3 Statuts et contrat de réponse

  • 2xx : traitement réussi (200, 201, 204).
  • 3xx : redirection ou autre mécanisme de redirection (301, 302, 304).
  • 4xx : problème associé à la requête ou au contexte client (400, 401, 403, 404, 409, 415, 422, 429).
  • 5xx : échec de traitement côté serveur ou intermédiaire (500, 502, 503, 504).

401 signifie que l’authentification est absente ou invalide ; 403 signifie que l’accès est refusé. 502 indique qu’une passerelle a reçu une réponse invalide d’un serveur amont ; 504 qu’elle n’a pas reçu à temps la réponse attendue. Le choix précis dépend du contrat API : ne réutilisez pas les statuts comme des codes métier arbitraires.

Exercice 2 — Choisir une réponse

Pour chaque cas, proposez un statut et justifiez-le : (a) un produit a été créé ; (b) le client a envoyé du JSON mal formé ; (c) une réservation entre en conflit avec un créneau déjà pris ; (d) un service amont n’a pas répondu dans le délai du proxy.

Corrigé indicatif : (a) 201 Created, éventuellement avec Location ; (b) 400 Bad Request ; (c) 409 Conflict ; (d) 504 Gateway Timeout. Le contrat précis peut ajouter un corps d’erreur stable et un identifiant de corrélation.

Quiz du module 2

Pourquoi Content-Type n’est-il pas interchangeable avec Accept ? Content-Type décrit le contenu envoyé ; Accept exprime les formats que le client souhaite recevoir.

Module 3 — Cookies, cache HTTP et CORS

3.1 Cookies et sécurité navigateur

Un serveur peut envoyer un cookie avec Set-Cookie. Le navigateur le renvoie ensuite selon son domaine, son chemin, son expiration et ses règles de contexte. Les attributs importants comprennent :

  • HttpOnly : empêche l’accès au cookie depuis les API JavaScript du navigateur ; il ne bloque pas l’envoi automatique du cookie.
  • Secure : limite son envoi aux connexions sécurisées, sous réserve des règles particulières des environnements locaux.
  • SameSite=Lax|Strict|None : contrôle certains envois intersites. SameSite=None exige Secure dans les navigateurs modernes.
  • Path, Domain, Max-Age et Expires : contrôlent portée et durée de vie.

HttpOnly réduit certains risques de vol via JavaScript, mais ne supprime pas le risque CSRF lorsqu’un navigateur joint automatiquement une session à une requête. La stratégie de session doit aussi prendre en compte CSRF, l’autorisation et la rotation/invalidation de session.

3.2 Cache HTTP

Le cache peut se trouver dans le navigateur, un proxy, un CDN ou un autre intermédiaire. La politique doit tenir compte de la fraîcheur, de la sensibilité des données et de la possibilité de revalidation.

  • Cache-Control: no-store demande de ne pas stocker la réponse.
  • Cache-Control: no-cache permet le stockage, mais exige une revalidation avant réutilisation.
  • max-age=60 autorise une fraîcheur de 60 secondes dans les conditions prévues par la directive.
  • ETag permet de comparer une représentation ; If-None-Match permet une revalidation. Une réponse 304 Not Modified ne transporte pas une nouvelle représentation complète.
  • Vary: Accept-Encoding indique que la représentation varie selon cet en-tête de requête.

Ne mettez pas en cache publiquement des réponses personnalisées ou confidentielles sans analyse stricte des clés de cache et des directives. Une mauvaise configuration peut exposer les données d’un utilisateur à un autre.

3.3 CORS et préflight

CORS est une politique appliquée par les navigateurs pour contrôler si un script d’une origine peut lire une réponse provenant d’une autre origine. Une origine est le triplet schéma + hôte + port. CORS n’est ni une authentification ni un pare-feu serveur : un client non navigateur peut appeler directement l’API, et l’API doit toujours appliquer ses contrôles d’accès.

Une requête interorigine peut déclencher une préflight OPTIONS, notamment selon la méthode et les en-têtes utilisés. Le serveur répond alors avec des champs comme Access-Control-Allow-Origin, Access-Control-Allow-Methods et Access-Control-Allow-Headers. Si des cookies ou d’autres identifiants sont utilisés avec credentials: "include", le serveur doit autoriser explicitement l’origine ; Access-Control-Allow-Origin: * n’est pas valide avec les credentials. Il faut également traiter Vary: Origin lorsque la valeur autorisée est sélectionnée dynamiquement.

Exemple de client :

const response = await fetch("https://api.example.test/profile", {
  credentials: "include",
  headers: { Accept: "application/json" },
});

if (!response.ok) {
  throw new Error(`HTTP ${response.status}`);
}

Ce code suppose que le serveur a correctement configuré CORS et que la politique de session est adaptée. fetch rejette la promesse pour certaines erreurs réseau ou de politique navigateur, mais une réponse HTTP 404 ou 500 ne fait pas automatiquement rejeter la promesse : il faut examiner response.ok ou response.status.

Exercice 3 — Diagnostiquer CORS

Une requête depuis https://front.example.test échoue dans le navigateur. La console signale que l’en-tête Access-Control-Allow-Origin manque. L’API renvoie 200 quand elle est appelée directement avec curl.

Corrigé : curl confirme que l’API répond, mais n’applique pas la politique de lecture CORS du navigateur. Vérifier la réponse de la préflight OPTIONS si elle existe, l’origine exacte (schéma, hôte, port), les méthodes/en-têtes autorisés et la configuration des credentials. Ne pas « corriger » en ouvrant toutes les origines sans nécessité et ne pas traiter CORS comme un contrôle d’accès.

Quiz du module 3

CORS protège-t-il l’API contre un client malveillant hors navigateur ? Non. CORS encadre principalement la lecture de réponses par des scripts de navigateur ; l’API doit authentifier et autoriser chaque opération elle-même.

Module 4 — TLS, certificats et reverse proxy

4.1 Ce que HTTPS garantit

HTTPS encapsule HTTP dans TLS. TLS vise notamment la confidentialité et l’intégrité des échanges, ainsi que l’authentification du serveur au moyen de la validation de son certificat. Le client vérifie la chaîne de confiance, la validité temporelle et la correspondance du nom d’hôte avec les identités du certificat. Un certificat valide ne prouve pas que l’application est sûre, que l’utilisateur est autorisé ou que le serveur ne contient pas de vulnérabilité.

Le navigateur résout le nom, établit le transport, négocie TLS puis échange HTTP de façon protégée. Les détails varient selon HTTP/1.1, HTTP/2 ou HTTP/3 et les capacités négociées. Une erreur de certificat doit être traitée comme un problème de confiance ou de configuration, pas contournée pour « faire fonctionner » une application de production.

4.2 Reverse proxy et terminaison TLS

En production, TLS peut se terminer sur un reverse proxy ou un load balancer. Celui-ci transmet ensuite la requête à Node.js, parfois sur un réseau interne. Le proxy peut ajouter Forwarded ou des en-têtes X-Forwarded-* décrivant le protocole, l’hôte ou l’adresse du client d’origine.

Ces champs ne sont fiables que si la requête provient d’un proxy de confiance et que la topologie est correctement configurée. Si l’application accepte ces en-têtes d’un client quelconque, elle peut construire des URL, journaux ou décisions de sécurité à partir de valeurs falsifiées. Configurez explicitement les proxys de confiance dans le framework choisi et n’inférez pas la sécurité d’une requête uniquement depuis un en-tête contrôlé par le client.

4.3 Vérifications pratiques

curl -v https://example.com/
curl -I https://example.com/

-v affiche des détails de connexion utiles au diagnostic ; -I demande les en-têtes via une requête HEAD si le serveur la prend en charge. N’ajoutez pas -k / --insecure comme correction : cette option désactive la vérification du certificat et peut masquer le défaut réel.

Exercice 4 — Certificat invalide

Un client reçoit une erreur indiquant que le certificat ne correspond pas au nom demandé. La chaîne semble par ailleurs émise par une autorité de confiance.

Corrigé : vérifier le nom d’hôte demandé, les SAN du certificat présenté, le certificat réellement servi par le proxy/load balancer, le SNI et le routage vers le bon virtual host. Une chaîne de confiance valide ne compense pas une identité de serveur incorrecte.

Quiz du module 4

Le TLS qui se termine au reverse proxy rend-il automatiquement le lien proxy → Node.js sûr ? Non. Ce tronçon doit être protégé et contrôlé selon le modèle de menace, et l’application doit faire confiance uniquement aux proxys prévus.

Module 5 — Timeouts, erreurs réseau et connexions persistantes

5.1 Pourquoi un délai maximal est nécessaire

Une opération réseau peut rester en attente : résolution DNS, établissement de connexion, négociation TLS, attente des en-têtes ou lecture du corps. Les timeouts doivent être cohérents avec le budget de latence de l’application. Un timeout côté client n’annule pas nécessairement le traitement déjà commencé côté serveur ; le serveur peut avoir réalisé l’action métier alors que le client a abandonné l’attente.

Avec Node.js 22+, AbortSignal.timeout() peut borner une opération fetch. Le code suivant vérifie le statut, la durée et les erreurs, mais le délai couvre l’opération Fetch selon les règles de l’API et ne remplace pas les timeouts des autres couches :

const startedAt = performance.now();

try {
  const response = await fetch("https://example.com/api/status", {
    signal: AbortSignal.timeout(3_000),
    headers: { Accept: "application/json" },
  });

  if (!response.ok) {
    throw new Error(`Réponse HTTP ${response.status}`);
  }

  const body: unknown = await response.json();
  console.log({ status: response.status, elapsedMs: performance.now() - startedAt, body });
} catch (error: unknown) {
  if (error instanceof Error) {
    console.error({ message: error.message, elapsedMs: performance.now() - startedAt });
  } else {
    console.error("Échec réseau inconnu");
  }
}

Dans une vraie application, ne journalisez pas aveuglément le corps : il peut contenir des données personnelles, des secrets ou un volume excessif. Les erreurs doivent être classées avec prudence : fetch et les systèmes d’exploitation ne donnent pas toujours une distinction portable entre DNS, connexion, TLS et timeout.

5.2 Keep-alive, pooling et limites

Les connexions persistantes évitent de recréer une connexion pour chaque échange, ce qui peut réduire la latence et la charge. La réutilisation est gérée par le protocole et le client HTTP. Il faut cependant définir des limites adaptées : nombre de sockets, durée d’inactivité, concurrence, taille des réponses et temps maximal de traitement.

Une saturation peut provenir d’un trop grand nombre de requêtes simultanées, d’un pool trop petit, d’un service amont lent ou d’un travail synchrone qui bloque la boucle d’événements. Augmenter les timeouts sans diagnostiquer la cause peut augmenter le nombre de requêtes en attente et aggraver la saturation.

5.3 Reprises et incertitude après coupure

Ne répétez pas automatiquement une opération non idempotente parce qu’un timeout a eu lieu. La requête a pu être traitée avant la coupure de connexion. Pour les écritures métier, concevez une stratégie de reprise explicite : clé d’idempotence, identifiant d’opération, vérification de l’état côté serveur, délais avec backoff et limite de tentatives. Les retries ne doivent pas multiplier une panne ni ignorer les statuts qui ne sont pas transitoires.

Exercice 5 — Un timeout après POST

Un client envoie POST /reservations, attend 3 secondes puis abandonne. Il n’a reçu aucune réponse. Peut-il réenvoyer immédiatement la même requête ?

Corrigé : pas sans connaître le contrat de l’API. Le serveur a peut-être créé la réservation avant la coupure. Il faut une clé d’idempotence ou un mécanisme de consultation de l’état, puis une stratégie de reprise bornée. Le timeout du client n’est pas une preuve d’échec métier.

Quiz du module 5

Un timeout prouve-t-il que le serveur n’a pas exécuté l’opération ? Non. Il prouve que le client n’a pas obtenu le résultat attendu dans le délai fixé.

Module 6 — Diagnostic reproductible

6.1 Une séquence de diagnostic

Procédez par couches et conservez les observations :

  1. Nom : le nom est-il résolu ? Comparer dig/nslookup et la configuration DNS.
  2. Transport : la cible et le port sont-ils joignables ? Distinguer refus, absence de route et filtrage.
  3. TLS : certificat, nom, chaîne et négociation sont-ils valides ?
  4. HTTP : quel statut, quels en-têtes et quelle durée ? Une réponse 4xx ou 5xx confirme que la couche HTTP a répondu.
  5. Application : identifier la route, l’exception, le service amont et l’identifiant de corrélation sans exposer les secrets.
  6. Navigateur : examiner Network, Console, la requête OPTIONS, les cookies, le cache et les en-têtes.

6.2 curl et DevTools

Commandes utiles :

# Afficher les détails de connexion et les en-têtes
curl -v https://example.com/api/status

# N'afficher que les en-têtes de réponse
curl -I https://example.com/

# Mesurer quelques phases de la requête
curl -sS -o /dev/null \
  -w 'dns=%{time_namelookup}s connect=%{time_connect}s tls=%{time_appconnect}s first_byte=%{time_starttransfer}s total=%{time_total}s status=%{http_code}\n' \
  https://example.com/

Les métriques affichées dépendent du build de curl et du protocole utilisé ; elles constituent des indices, pas une preuve isolée de la cause. Dans DevTools → Network, examinez URL, méthode, statut, timing, request/response headers, cookies, initiateur et éventuelle préflight. Masquez les jetons et cookies avant de partager une capture.

6.3 Journalisation côté Node.js

Les logs doivent permettre de corréler les étapes sans enregistrer des secrets. Préférez des champs structurés tels que méthode, chemin normalisé, statut, durée, identifiant de requête et résultat technique. Évitez le corps complet, les cookies, les en-têtes d’authentification et les paramètres d’URL sensibles.

Exemple illustratif d’un journal structuré, à adapter au serveur réellement utilisé :

type RequestSummary = {
  method: string;
  route: string; // modèle de route, pas URL brute avec données sensibles
  statusCode: number;
  durationMs: number;
  requestId: string;
};

function logRequest(summary: RequestSummary): void {
  console.log(JSON.stringify({ event: "http.request.completed", ...summary }));
}

Ce helper ne collecte pas lui-même les données et ne génère pas d’identifiant ; il montre seulement la forme des événements à émettre. L’intégration dépend du serveur HTTP et du middleware de corrélation retenus.

Exercice 6 — Établir une hypothèse testable

curl -v https://api.example.test/health montre une connexion TLS établie puis HTTP/1.1 503 Service Unavailable. Quelle conclusion est justifiée, et quelles vérifications suivent ?

Corrigé : DNS, transport, TLS et HTTP ont suffisamment fonctionné pour recevoir une réponse HTTP. 503 indique que le serveur ou l’intermédiaire déclare le service temporairement indisponible ; cela ne permet pas d’identifier seul la cause. Vérifier les en-têtes de réponse, les logs avec l’identifiant de requête, l’état du service amont, les limites de capacité et les éventuels déploiements en cours.

Quiz du module 6

Quel est l’avantage d’un diagnostic par couches ? Il transforme « le site ne marche pas » en hypothèses localisées, testables et reproductibles, au lieu de modifier plusieurs composants au hasard.

Projet intégrateur — Laboratoire de diagnostic HTTP

Mission

Créer un petit service HTTP local et un client TypeScript qui collecte des informations de diagnostic. Le projet sert à démontrer la compréhension du cycle requête-réponse ; il ne doit pas être exposé publiquement ni présenté comme un serveur de production.

Périmètre fonctionnel

  1. Démarrer un serveur Node.js sur 127.0.0.1:3000.
  2. Implémenter GET /health avec 200 et une réponse JSON stable.
  3. Implémenter GET /status/503 pour simuler une indisponibilité et GET /status/404 pour simuler une route absente.
  4. Ajouter Content-Type, une politique de cache explicite et un identifiant de requête non sensible.
  5. Créer un client fetch avec timeout, mesure de durée et traitement explicite des statuts non 2xx.
  6. Documenter les commandes curl pour distinguer succès, erreur HTTP et erreur de connexion.
  7. Ajouter une note de diagnostic CORS expliquant la différence entre curl et un navigateur, sans exposer le service sur le réseau.
  8. Écrire un tableau d’incidents simulés : symptôme, couche probable, commande de vérification, résultat attendu, conclusion.

Critères d’acceptation

  • Les routes et statuts correspondent exactement à la spécification.
  • Le client distingue une réponse HTTP en erreur d’un échec de transport.
  • Le timeout est borné et son résultat est documenté.
  • Les logs incluent statut et durée sans cookies, secrets ni corps arbitraire.
  • Les tests ou commandes manuelles couvrent au moins 200, 404, 503 et un port sans serveur.
  • Le diagnostic explique pourquoi un timeout n’implique pas nécessairement l’échec de l’opération.
  • Les résultats exécutés sont consignés séparément des contrôles statiques.
  • Le service reste lié à la boucle locale et n’est pas présenté comme prêt pour la production.

Limites et statut de validation

Le cours est rédigé et relu statiquement. Les exemples sont des supports pédagogiques, pas des garanties de fonctionnement dans tous les environnements. Ils n’ont pas été exécutés intégralement pendant cette passe ; aucune validation TLS réelle, capture DevTools, test réseau, test de charge, test applicatif, typecheck ni build n’est déclaré réussi. Les exercices disposent de corrigés indicatifs et le projet final possède des critères d’acceptation vérifiables.
