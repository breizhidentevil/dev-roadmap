Conception d’API HTTP avec Node.js et TypeScript

  • Version pédagogique : 1.0
  • Date : 14 octobre 2026
  • Statut : rédigé ; exemples non validés par exécution intégrale
  • Niveau : intermédiaire
  • Durée indicative : 12 à 16 heures, projet compris
  • Environnement de référence : Node.js 22 LTS ou LTS ultérieure compatible ; TypeScript 5.9 ; modules ES ; exemples de serveur basés sur Express 5. Le choix de framework est pédagogique et ne rend pas Express obligatoire dans les autres cours.

Objectifs et prérequis

À l’issue du cours, l’apprenant sait organiser une API en couches, distinguer le typage TypeScript de la validation à l’exécution, définir un contrat HTTP stable, normaliser les erreurs, concevoir pagination et filtres bornés, documenter les opérations avec OpenAPI, faire évoluer un contrat sans casser inutilement les clients et définir une stratégie d’idempotence.

Prérequis : C01, JavaScript asynchrone, types TypeScript, modules Node.js, bases SQL et HTTP. Les détails du protocole, des méthodes et des statuts sont étudiés dans C01 ; ce cours les applique à la conception d’une API et évite de refaire un cours réseau.

Plan

  1. Choisir le niveau d’abstraction HTTP.
  2. Séparer routes, contrôleurs, services et dépôts.
  3. Valider les entrées à l’exécution.
  4. Normaliser les erreurs et la journalisation.
  5. Concevoir pagination, filtres, tri et recherche.
  6. Décrire les contrats avec OpenAPI.
  7. Faire évoluer et versionner une API.
  8. Définir l’idempotence et les clés de requête.

Module 1 — Choisir le niveau d’abstraction HTTP

1.1 Node.js natif ou framework ?

Le module node:http expose directement les primitives HTTP : serveur, requête, réponse, en-têtes et flux. Il convient aux démonstrations, aux petits services et aux cas où l’équipe veut contrôler explicitement le traitement. En contrepartie, le routage, la validation, la composition des middlewares et la convention de gestion des erreurs restent à concevoir.

Un framework ajoute des conventions et des abstractions. Express privilégie une chaîne de middlewares et un routage simple ; Fastify met notamment l’accent sur les schémas de validation/sérialisation et les performances ; NestJS apporte une architecture plus prescriptive. Aucun choix ne remplace la compréhension du protocole ni ne garantit à lui seul la sécurité.

Critères de choix : taille et durée de vie du service, compétences de l’équipe, exigences de validation et de documentation, intégrations existantes, modèle de plugins, stratégie de tests et coût de migration. Éviter de mélanger plusieurs frameworks dans un même service sans raison opérationnelle.

1.2 Exemple minimal avec Express 5

import express from "express";

const app = express();
app.disable("x-powered-by");
app.use(express.json({ limit: "100kb" }));

app.get("/health", (_req, res) => {
  res.status(200).json({ status: "ok" });
});

app.listen(3000, "127.0.0.1", () => {
  console.log("API disponible sur http://127.0.0.1:3000");
});

Le parseur JSON est limité en taille pour éviter d’accepter sans borne des corps arbitraires. Cet exemple reste incomplet pour la production : configuration validée, arrêt gracieux, journalisation, contrôle de disponibilité des dépendances et gestion d’erreurs sont traités ailleurs. Le typage exact dépend aussi des paquets de types installés dans le projet.

Exercice 1 — Choix d’architecture

Une API interne expose quatre routes, doit être déployée dans un conteneur et sera maintenue plusieurs années par une équipe de trois développeurs. L’équipe connaît déjà Express.

Corrigé : Express est un choix raisonnable pour limiter le coût d’apprentissage. Documenter les raisons, fixer les versions majeures, définir les conventions de validation/erreurs et conserver une séparation des responsabilités. Il n’est pas nécessaire d’adopter NestJS uniquement pour donner une apparence architecturée au projet.

Quiz 1

Un framework dispense-t-il de valider les entrées à l’exécution ? Non. Le framework peut fournir des outils, mais les données reçues restent non fiables et leur validation dépend du contrat et de la configuration effective.

Module 2 — Routes, contrôleurs, services et dépôts

2.1 Les responsabilités

  • Route : associe une méthode et un chemin à une chaîne de traitement ; peut appliquer authentification et validation.
  • Contrôleur : traduit le protocole HTTP vers une commande métier et transforme le résultat en réponse HTTP. Il ne devrait pas porter les règles métier complexes.
  • Service : applique les règles métier, les invariants et les décisions de transaction.
  • Dépôt (repository) : encapsule les opérations de persistance et leurs détails techniques.
  • Schéma/DTO : décrit les données qui peuvent entrer ou sortir de l’API ; un DTO public n’est pas automatiquement le modèle de base de données.

Ces noms ne sont pas une obligation. Le but est de créer des frontières testables, pas de multiplier les fichiers pour chaque ligne de code. Pour une API petite, route et contrôleur peuvent rester ensemble tant que les responsabilités sont claires.

2.2 Flux typique

HTTP request
  -> middleware de corrélation / parsing limité
  -> route et contrôles transverses
  -> validation runtime
  -> contrôleur
  -> service métier
  -> dépôt / transaction
  -> DTO de réponse
  -> sérialisation HTTP

Les contrôles d’authentification et d’autorisation doivent être placés avant toute lecture ou modification protégée. L’autorisation porte sur la ressource réelle, pas seulement sur le fait que l’utilisateur est connecté. Les règles d’ordre exact dépendent du framework ; elles doivent être testées.

2.3 Exemple de service indépendant du framework

export type Task = {
  id: string;
  title: string;
  completed: boolean;
};

export interface TaskRepository {
  findById(id: string): Promise<Task | null>;
}

export class TaskNotFoundError extends Error {
  constructor() {
    super("Task not found");
    this.name = "TaskNotFoundError";
  }
}

export class TaskService {
  constructor(private readonly tasks: TaskRepository) {}

  async getById(id: string): Promise<Task> {
    const task = await this.tasks.findById(id);
    if (!task) throw new TaskNotFoundError();
    return task;
  }
}

L’interface permet de tester la règle de service sans démarrer une base de données. Le dépôt réel doit tout de même être testé avec le moteur et les requêtes réellement utilisés. Un mock ne démontre ni l’exactitude SQL, ni les contraintes, ni la concurrence.

Exercice 2 — Placer la règle métier

Une tâche terminée ne peut plus être modifiée. Où placer cette règle ?

Corrigé : dans le service métier ou dans une entité/domaine partagé par les cas d’usage, et si nécessaire la renforcer en base par des contraintes ou une stratégie transactionnelle. Le contrôleur peut traduire l’erreur en réponse HTTP, mais ne doit pas être l’unique lieu où la règle est appliquée.

Quiz 2

Le dépôt doit-il renvoyer directement un objet Response Express ? Non. Il doit exposer une abstraction de données, sans dépendre de l’objet HTTP du framework.

Module 3 — Validation runtime et frontière de confiance

3.1 TypeScript ne valide pas les requêtes

Les annotations et interfaces TypeScript sont supprimées à la compilation. Une déclaration const body = req.body as CreateTaskInput n’inspecte pas le contenu reçu. Le corps peut être absent, mal formé, incomplet, trop grand ou contenir des propriétés inattendues. Il faut analyser la donnée à l’exécution puis construire une valeur interne à partir du résultat validé.

Décider explicitement si les champs inconnus sont rejetés, ignorés ou supprimés. Pour les commandes sensibles, le rejet strict évite qu’un client pense avoir modifié un champ que le serveur ignore, ou qu’un champ inattendu atteigne la persistance. Les identifiants, tailles, formats, plages numériques et règles de normalisation doivent être spécifiés.

3.2 Garde de type sans bibliothèque

type CreateTaskInput = { title: string };

function parseCreateTaskInput(value: unknown): CreateTaskInput {
  if (typeof value !== "object" || value === null || Array.isArray(value)) {
    throw new InputValidationError("Body must be an object");
  }

  const record = value as Record<string, unknown>;
  const keys = Object.keys(record);
  if (keys.some((key) => key !== "title")) {
    throw new InputValidationError("Unexpected property");
  }

  if (typeof record.title !== "string") {
    throw new InputValidationError("title must be a string");
  }

  const title = record.title.trim();
  if (title.length < 1 || title.length > 120) {
    throw new InputValidationError("title must contain 1 to 120 characters");
  }

  return { title };
}

export class InputValidationError extends Error {
  constructor(message: string) {
    super(message);
    this.name = "InputValidationError";
  }
}

Ce garde est volontairement simple et ne remplace pas une bibliothèque de schémas lorsque les contrats deviennent nombreux. Une bibliothèque comme Zod peut inférer un type depuis un schéma, mais le projet doit choisir une version, définir la politique des clés inconnues et éviter de dupliquer manuellement la même règle à plusieurs endroits.

3.3 Validation par emplacement

Valider séparément : paramètres de chemin, query string, en-têtes applicatifs et corps. Les query strings sont des chaînes ou des listes de chaînes ; ?limit=10 ne fournit pas directement un nombre validé. Vérifier aussi les paramètres répétés, les valeurs vides et les limites. Ne jamais concaténer des entrées utilisateur dans une requête SQL : utiliser des paramètres liés.

Exercice 3 — Assertion ou validation ?

const input = req.body as { role: "user" | "admin" };

Corrigé : il s’agit uniquement d’une assertion statique. Elle ne prouve pas que role existe ou vaut l’une des chaînes autorisées. Le serveur doit vérifier la valeur à l’exécution, puis produire un objet validé.

Quiz 3

Un type number empêche-t-il une chaîne malveillante d’arriver depuis JSON ? Non. Le type ne s’exécute pas sur le payload. La validation doit être faite au point d’entrée.

Module 4 — Erreurs HTTP prévisibles

4.1 Une enveloppe stable

Une API devrait présenter un format d’erreur documenté, sans exposer pile d’appel, requête SQL, secret, jeton ou détail interne. Exemple d’enveloppe :

{
  "error": {
    "code": "VALIDATION_FAILED",
    "message": "La requête est invalide.",
    "requestId": "req_01J..."
  }
}

Le requestId doit être créé ou validé selon une politique documentée et propagé aux journaux. Ne faites pas confiance à un identifiant fourni par un client comme preuve d’identité. Les détails de validation peuvent être renvoyés sous forme de chemins et de codes stables, en évitant de refléter des valeurs sensibles.

4.2 Correspondance indicative des statuts

Situation Statut souvent adapté Remarque
Requête mal formée ou validation échouée 400 Préciser le contrat dans le corps d’erreur
Authentification absente/invalide 401 Les schémas HTTP d’authentification exigent généralement WWW-Authenticate
Utilisateur authentifié mais non autorisé 403 404 peut être choisi pour ne pas révéler l’existence d’une ressource, selon une politique cohérente
Ressource absente 404 Ne pas confondre absence et erreur interne
Conflit avec l’état courant 409 Par exemple conflit de version ou contrainte métier
Contenu non acceptable selon les en-têtes 406 À utiliser lorsque la négociation est réellement appliquée
Corps trop volumineux 413 Définir une limite côté parseur/proxy
Erreur inattendue 500 Message générique côté client, détails expurgés dans les logs
Service temporairement indisponible 503 Retry-After peut être pertinent si une reprise est raisonnable

Ces correspondances sont des conventions de conception, pas un remplacement de la sémantique HTTP. Les clients doivent se baser sur les codes stables et les statuts, pas analyser les messages libres.

4.3 Middleware Express d’erreur

import type { ErrorRequestHandler } from "express";

export const errorHandler: ErrorRequestHandler = (err, req, res, _next) => {
  if (res.headersSent) return;

  if (err instanceof InputValidationError) {
    res.status(400).json({
      error: { code: "VALIDATION_FAILED", message: err.message, requestId: req.requestId },
    });
    return;
  }

  // Journaliser err avec requestId dans le logger de l'application,
  // en supprimant secrets, cookies, jetons et données personnelles.
  res.status(500).json({
    error: {
      code: "INTERNAL_ERROR",
      message: "Une erreur interne est survenue.",
      requestId: req.requestId,
    },
  });
};

req.requestId est illustratif : il faut déclarer l’extension de type et installer le middleware qui le crée avant les routes. Dans Express 5, les rejets de promesses retournés par les handlers sont transmis au middleware d’erreur ; pour les versions précédentes ou les wrappers spécifiques, vérifier les conventions de la version utilisée. Les erreurs de parsing du corps doivent aussi être traduites en statuts appropriés. Un gestionnaire final ne remplace pas des limites de corps ni une validation.

Exercice 4 — Éviter une fuite

Un endpoint renvoie 500 et le message complet de l’exception SQL au client. Donnez deux corrections.

Corrigé : renvoyer un message générique et un code d’erreur stable avec identifiant de requête ; consigner le détail côté serveur avec accès contrôlé et secrets/données personnelles expurgés. Ajouter un test qui vérifie que la réponse publique ne contient ni stack trace ni requête SQL.

Quiz 4

Faut-il renvoyer 200 avec { "success": false } pour toutes les erreurs ? Non. Les statuts HTTP sont une partie du contrat et permettent aux clients, proxies et outils de traitement de comprendre la nature du résultat.

Module 5 — Pagination, filtres, tri et recherche

5.1 Limiter le coût des requêtes

Ne renvoyez pas un ensemble de résultats non borné. Définissez une taille par défaut, une limite maximale, les champs filtrables et triables, ainsi que les règles de validation. Ne construisez jamais un fragment ORDER BY à partir d’une chaîne libre : associez les noms de tri acceptés à une liste blanche de colonnes.

La pagination par offset est facile à comprendre mais peut devenir coûteuse sur de grands offsets et produire des doublons/omissions si l’ordre change entre deux pages. La pagination par curseur utilise un ordre stable, avec un dernier élément de référence. Le tri doit être déterministe, par exemple created_at DESC, id DESC, et le curseur doit encoder ou référencer tous les éléments nécessaires à la continuité. Un curseur opaque n’est pas une autorisation : chaque requête doit encore vérifier l’identité et les droits d’accès.

5.2 Parser des paramètres bornés

function parseLimit(raw: unknown, defaultValue = 20, maximum = 100): number {
  if (raw === undefined) return defaultValue;
  if (typeof raw !== "string" || !/^[1-9]\d*$/.test(raw)) {
    throw new InputValidationError("limit must be a positive integer");
  }
  const value = Number(raw);
  if (!Number.isSafeInteger(value) || value > maximum) {
    throw new InputValidationError(`limit must be between 1 and ${maximum}`);
  }
  return value;
}

Cette validation refuse 0, les nombres négatifs, les décimaux, les notations exponentielles, les chaînes vides et les valeurs supérieures à la limite. Adapter la règle si l’API choisit explicitement une autre grammaire. Vérifier aussi la présence de paramètres dupliqués, car certains parseurs produisent un tableau lorsqu’un paramètre apparaît plusieurs fois.

Exemple de contrat de réponse :

{
  "data": [{ "id": "tsk_123", "title": "Lire la documentation" }],
  "page": { "limit": 20, "nextCursor": "opaque-cursor-or-null" }
}

N’exposez pas le curseur comme une garantie de sécurité. Il doit être validé, borné en taille, et éventuellement signé si l’intégrité du contenu encodé est importante. La requête SQL sous-jacente doit toujours employer des paramètres liés.

Exercice 5 — Conception de pagination

Une liste de 500 000 événements est triée par date décroissante. Les événements peuvent être insérés pendant que l’utilisateur navigue.

Corrigé : préférer une pagination par curseur basée sur un ordre total et stable, par exemple date + identifiant unique. Définir le comportement des événements insérés entre les pages et vérifier que le prédicat de continuation correspond exactement à l’ordre. L’offset peut rester acceptable pour de petits ensembles ou un besoin d’accès direct à une page précise.

Quiz 5

Le paramètre sort=createdAt;DROP... peut-il être injecté directement dans SQL ? Non. Utiliser une liste blanche de champs et de directions, puis construire la requête à partir des options validées ; lier les valeurs avec des paramètres SQL.

Module 6 — Contrats OpenAPI

6.1 Pourquoi un contrat explicite ?

OpenAPI décrit les chemins, méthodes, paramètres, corps, réponses, schémas, mécanismes de sécurité et métadonnées d’une API HTTP. Il permet de générer une documentation interactive et, selon l’outillage, des clients, des stubs et des contrôles de contrat. Le document ne prouve pas que le serveur respecte réellement le contrat : des tests doivent comparer l’implémentation et la spécification.

Choisir et documenter la version OpenAPI employée. La spécification OpenAPI 3.1 s’appuie sur une compatibilité étroite avec le modèle de schéma JSON ; les outils ne prennent pas nécessairement en charge toutes les fonctionnalités de manière identique. Épingler les versions d’outils et vérifier les écarts dans la CI.

6.2 Extrait minimal

openapi: 3.1.1
info:
  title: Tasks API
  version: 1.0.0
paths:
  /tasks:
    post:
      operationId: createTask
      summary: Créer une tâche
      requestBody:
        required: true
        content:
          application/json:
            schema:
              type: object
              additionalProperties: false
              required: [title]
              properties:
                title:
                  type: string
                  minLength: 1
                  maxLength: 120
      responses:
        '201':
          description: Tâche créée
        '400':
          description: Corps invalide
        '500':
          description: Erreur inattendue

L’extrait illustre la forme du contrat et ne décrit pas toutes les réponses utiles : il faudrait documenter les schémas des réponses, les erreurs, les en-têtes, l’authentification, les limites et les éventuelles réponses 409/413. La version info.version identifie la version publiée du contrat, mais ne définit pas à elle seule la stratégie de versionnement des URLs.

6.3 Éviter la dérive

Une seule source de vérité réduit les divergences : schémas runtime partagés, génération du document depuis le code, ou contrat OpenAPI utilisé pour générer des types et valider l’implémentation. Chacune de ces stratégies a des compromis. Éviter de maintenir manuellement trois schémas identiques (TypeScript, validateur runtime, OpenAPI) sans mécanisme de cohérence.

Exercice 6 — Contrat sans réponse

Une opération POST /tasks documente seulement 200, mais l’implémentation renvoie 201 et un corps contenant l’identifiant.

Corrigé : mettre le contrat et l’implémentation en accord. Si la création est la sémantique retenue, documenter 201, le schéma du corps et les en-têtes pertinents, puis ajouter un test de contrat. Ne pas supposer que la documentation interactive détectera automatiquement cet écart.

Quiz 6

OpenAPI valide-t-il automatiquement les requêtes en production ? Non. Il décrit un contrat ; il faut une intégration de validation ou des contrôles côté serveur et des tests pour faire respecter ce contrat.

Module 7 — Versionnement et compatibilité

7.1 Faire évoluer un contrat

Une modification est compatible si les clients existants peuvent continuer à fonctionner selon le contrat promis. Renommer un champ, changer son type, supprimer une route, rendre obligatoire un champ auparavant facultatif ou changer la signification d’un statut peut casser des clients. Ajouter un champ facultatif est souvent compatible, mais pas pour tous les clients stricts ou générateurs de code.

Avant une évolution : identifier les consommateurs, mesurer l’usage lorsque c’est possible, publier une politique de dépréciation, documenter la date de retrait, proposer une période de transition et vérifier les usages avant suppression. Une version dans le chemin (/v1) rend le routage explicite ; une version dans un en-tête ou un type média a d’autres avantages et coûts. La cohérence de politique importe davantage que la forme choisie isolément.

7.2 Règles de compatibilité

  • Ne pas réutiliser un nom de champ avec une nouvelle sémantique.
  • Ajouter les champs de réponse avec une politique claire sur les clients stricts.
  • Ne pas rendre obligatoire une propriété d’entrée sans transition ou nouvelle version.
  • Documenter la dépréciation, les dates et les solutions de remplacement.
  • Tester les contrats consommés par les clients importants.
  • Traiter une migration de base et une migration d’API comme deux changements liés mais distincts.

Exercice 7 — Champ obligatoire

Une API v1 accepte { "title": "x" }. L’équipe veut désormais exiger projectId.

Corrigé : rendre le champ obligatoire immédiatement peut casser les clients existants. Choisir une transition (champ facultatif avec comportement défini, annonce et métriques d’usage) ou publier une nouvelle version si la rupture est nécessaire. Ne pas accepter silencieusement des données qui ne permettent pas de respecter les invariants métier.

Quiz 7

Une version v2 dans l’URL garantit-elle la compatibilité ? Non. Elle rend le choix de version visible, mais chaque version doit avoir un contrat et une politique de support précis.

Module 8 — Idempotence et clés de requête

8.1 Idempotence HTTP et idempotence métier

Une méthode HTTP idempotente produit le même effet demandé lorsqu’une requête identique est répétée, même si les réponses peuvent différer. Cela ne signifie pas que toutes les méthodes POST sont non idempotentes, ni qu’une clé d’idempotence transforme automatiquement une opération en opération sûre. L’idempotence doit être définie dans le contrat métier.

Les clés d’idempotence sont utiles quand le client ne sait pas si une création a réussi après un timeout. Le serveur doit définir la portée de la clé (utilisateur, route/opération, durée), le comportement d’une même clé avec un corps différent, le traitement des requêtes concurrentes, le stockage du résultat et l’expiration. Une simple Map en mémoire ne suffit pas pour plusieurs processus, un redémarrage ou plusieurs instances.

8.2 Modèle de registre durable

Un registre peut contenir :

  • identité du client ou du compte appelant ;
  • opération et clé d’idempotence ;
  • empreinte canonique de la requête ;
  • état (in_progress, completed, éventuellement failed_retryable) ;
  • résultat métier ou référence vers la ressource créée ;
  • horodatages et politique d’expiration.

Une contrainte d’unicité en base protège contre deux requêtes concurrentes utilisant la même clé. Pour un effet entièrement local à une base, l’enregistrement de la clé et l’effet métier doivent être coordonnés dans une transaction. Pour un effet externe (paiement, e-mail, service tiers), une transaction SQL ne peut pas rendre l’effet distant atomique : employer un mécanisme de déduplication côté fournisseur, une outbox ou un processus de réconciliation selon le besoin.

8.3 Pseudocode du contrat

1. Valider authentification, autorisation, clé et corps.
2. Calculer une empreinte stable de la requête validée.
3. Tenter de réserver (appelant, opération, clé) dans le stockage durable.
4. Si la clé existe avec une autre empreinte : répondre par un conflit documenté.
5. Si l’opération est terminée : retourner le résultat enregistré.
6. Si une opération identique est en cours : attendre ou répondre selon le contrat.
7. Exécuter l’effet métier avec la stratégie transactionnelle prévue.
8. Enregistrer le résultat final et le rendre disponible aux répétitions.

Ce pseudocode n’est pas une implémentation prête à copier. La gestion des crashs entre réservation et effet, la durée des verrous, les états récupérables, la cohérence avec les transactions et la rétention doivent être spécifiées et testées.

Exercice 8 — Timeout après création

Le client envoie POST /reservations avec la clé abc, perd la connexion et réessaie avec la même clé et le même corps.

Corrigé : le serveur doit retrouver la réservation/résultat déjà créé ou déterminer l’état de l’opération et ne pas créer un doublon. La clé doit être liée à l’identité et à l’opération, protégée par une contrainte durable et associée à l’empreinte du corps. Si la même clé est réutilisée avec un corps différent, retourner un conflit selon le contrat.

Quiz 8

Un UUID aléatoire dans un en-tête suffit-il à garantir l’idempotence ? Non. Il faut le stockage, l’unicité, les règles de concurrence, l’association à la requête et la restitution du résultat.

Projet intégrateur — API de gestion de tâches

Objectif

Construire une API TypeScript documentée et maintenable autour des tâches. Le projet doit pouvoir être réalisé avec Express 5 et un dépôt de données interchangeable ; PostgreSQL peut être ajouté selon le cours de persistance, mais ce cours ne réécrit pas son contenu.

Contrat minimal proposé

Méthode Route Succès Usage
GET /health 200 Vérification simple du processus
GET /v1/tasks?limit=20 200 Liste paginée et bornée
POST /v1/tasks 201 Créer une tâche validée
GET /v1/tasks/{id} 200 Lire une tâche
PATCH /v1/tasks/{id} 200 Modifier les champs autorisés
DELETE /v1/tasks/{id} 204 Supprimer une tâche selon le contrat

Le contrat réel doit définir les réponses 400, 401/403 si une authentification est ajoutée, 404, 409, 413 et 500 selon les opérations et le comportement du service. Ne pas ajouter un mécanisme d’authentification fictif : si le projet est public ou non authentifié, l’indiquer explicitement et traiter cette limite dans la conception.

Livrables obligatoires

  1. Sources TypeScript organisées par responsabilité, sans dépendance du service métier au framework HTTP.
  2. Schémas de validation runtime pour paramètres, query et corps.
  3. Format d’erreur stable et journalisation corrélée, sans secrets.
  4. Pagination bornée avec tri autorisé et ordre stable.
  5. Document OpenAPI cohérent avec les réponses implémentées.
  6. Politique écrite de versionnement et de compatibilité.
  7. Si une opération de création est susceptible d’être rejouée, contrat d’idempotence explicite ; ne pas prétendre que le support existe sans registre durable.
  8. Tests unitaires du service, tests HTTP des statuts/erreurs et test de contrat.
  9. README : versions, commandes, variables, architecture, limites et instructions de validation.

Critères d’acceptation

  • Les entrées externes sont validées à l’exécution ; aucune assertion as SomeInput ne sert de substitut à une validation.
  • Les tailles de corps et de page sont bornées.
  • Les erreurs inattendues n’exposent pas de détails internes.
  • Les statuts et schémas correspondent au document OpenAPI.
  • Le tri et les filtres reposent sur une liste blanche.
  • Les accès aux données utilisent des paramètres liés.
  • Les répétitions d’opérations ont un comportement documenté ; l’idempotence durable est testée si elle est implémentée.
  • Les tests échouent sur une régression de contrat importante.
  • Les limites non testées sont explicitement consignées.
