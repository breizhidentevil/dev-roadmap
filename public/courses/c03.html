Tests backend et qualité logicielle

  • Version pédagogique : 1.0
  • Date : 14 octobre 2026
  • Statut : rédigé ; exemples à exécuter dans l’environnement du projet avant adoption
  • Niveau : intermédiaire
  • Durée indicative : 14 à 18 heures, projet compris
  • Environnement de référence : TypeScript strict, modules ES, Vitest pour les exemples unitaires et @testcontainers/postgresql pour les tests nécessitant PostgreSQL. Le test runner natif node:test est également présenté comme alternative intégrée à Node.js.

Objectifs et prérequis

À l’issue du cours, l’apprenant sait concevoir une stratégie de test proportionnée au risque, isoler la logique métier, choisir entre test unitaire et test d’intégration, employer les doubles de test sans masquer les défauts, valider les contrats HTTP, vérifier les refus d’accès et les erreurs, tester les transactions et la concurrence, rendre les tests reproductibles et interpréter une couverture sans la confondre avec la qualité.

Prérequis : C01 et C02, TypeScript, fonctions asynchrones, API HTTP, SQL et transactions. Le cours n’impose pas de framework applicatif précis. Les exemples Vitest sont des exemples pédagogiques ; ils ne sont pas déclarés exécutés dans ce dépôt.

Module 1 — Stratégie de test et pyramide adaptée au risque

1.1 Tester un comportement, pas une ligne

Un test utile décrit une propriété observable du système : « une réservation ne peut pas être confirmée si le créneau est déjà pris ». Un test fragile décrit plutôt une organisation interne : « la méthode privée checkSlot est appelée avant save ». Si l’implémentation change sans changer le comportement attendu, le second test devient un coût de maintenance.

La question centrale est : quelle régression ce test empêcherait-il de réintroduire ? Si la réponse est vague, le test peut être redondant ou trop lié à l’implémentation.

Un test comporte trois étapes lisibles :

  • Arrange : préparer les données et les dépendances.
  • Act : exécuter l’action.
  • Assert : vérifier le résultat observable et, si nécessaire, les effets secondaires.

Un test ne doit pas seulement passer dans le cas nominal. Il doit aussi couvrir les décisions métier importantes : limites, refus, absence de données, conflits, échecs de dépendances et reprises.

1.2 Les niveaux de test

Niveau Ce qu’il vérifie Dépendances Coût typique
Unitaire Une règle ou une fonction isolée Aucune infrastructure réelle Faible
Intégration Plusieurs composants qui collaborent Base, filesystem ou service réel isolé Moyen
Contrat La conformité entre producteurs et consommateurs Schéma ou contrat partagé Faible à moyen
End-to-end Le parcours complet vu par un client Application et infrastructure assemblées Élevé

La pyramide est un repère, pas une loi mathématique. Un backend avec une logique transactionnelle importante doit investir dans des tests d’intégration ; un service à forte surface HTTP doit vérifier ses contrats. Le nombre de tests par niveau dépend du risque et du coût de diagnostic.

1.3 Construire une matrice de risque

Pour chaque exigence, noter :

  • la gravité si elle échoue ;
  • la probabilité d’une régression ;
  • la difficulté à la détecter en production ;
  • le niveau de test qui prouve réellement la propriété.

Exemple :

Exigence Risque Test prioritaire
Une entrée vide est refusée Moyen Unitaire + contrat HTTP
Un utilisateur ne lit pas la réservation d’un autre Élevé Intégration HTTP avec deux identités
Un transfert ne crée pas d’argent Critique Intégration transactionnelle + concurrence
Un message d’erreur contient le bon texte exact Faible Tester plutôt le code et la structure stable

1.4 Quand arrêter d’ajouter des tests ?

Ajouter un test lorsque sa valeur de détection dépasse son coût d’écriture et de maintenance. Éviter les tests qui répètent la même assertion sur des implémentations différentes sans couvrir de risque distinct. En revanche, un cas de sécurité ou de concurrence ne doit pas être écarté uniquement parce qu’il est plus difficile à tester.

À retenir : une suite utile couvre les comportements critiques, se lance de façon reproductible et fournit un diagnostic exploitable lorsqu’elle échoue.

Exercice 1

Pour une API de réservation, classer ces exigences par niveau de test : format d’un identifiant, refus d’une date passée, conflit entre deux réservations simultanées, absence de fuite d’une réservation privée, forme du document OpenAPI.

Correction expliquée :

  • Format d’identifiant : test unitaire du validateur et test de contrat HTTP.
  • Date passée : test unitaire de la règle métier, avec horloge maîtrisée.
  • Deux réservations simultanées : intégration sur la vraie base et contrainte transactionnelle.
  • Réservation privée : test d’intégration HTTP avec deux utilisateurs distincts.
  • OpenAPI : test de contrat ou validation automatisée du document généré. Un seul niveau ne suffit pas nécessairement : le test unitaire explique la règle, tandis que l’intégration prouve que les composants l’appliquent ensemble.

Quiz 1

Pourquoi une couverture de 100 % ne prouve-t-elle pas l’absence de bugs ?

A. Parce que les tests ne peuvent pas exécuter du TypeScript.
B. Parce que les lignes exécutées peuvent être vérifiées avec des assertions faibles ou incorrectes.
C. Parce que les tests unitaires sont toujours inutiles.

Réponse : B. La couverture indique quelles parties du code ont été exécutées selon une métrique donnée. Elle ne prouve ni que les entrées sont pertinentes, ni que les assertions détectent les erreurs, ni que la concurrence et l’infrastructure sont correctement testées.

Module 2 — Tests unitaires et conception testable

2.1 Extraire la logique métier des effets de bord

Une fonction pure renvoie le même résultat pour les mêmes entrées et n’altère pas d’état externe. Elle est généralement facile à tester. Les appels réseau, l’horloge, les identifiants aléatoires, les fichiers et la base de données sont des effets de bord ; les placer derrière des dépendances explicites facilite leur contrôle.

Exemple de règle métier :

export type ReservationInput = {
  startsAt: Date;
  now: Date;
  durationMinutes: number;
};

export function validateReservation(input: ReservationInput): string[] {
  const errors: string[] = [];

  if (!Number.isFinite(input.startsAt.getTime())) {
    errors.push("startsAt must be a valid date");
  } else if (input.startsAt.getTime() <= input.now.getTime()) {
    errors.push("startsAt must be in the future");
  }

  if (!Number.isInteger(input.durationMinutes) ||
      input.durationMinutes < 15 ||
      input.durationMinutes > 240) {
    errors.push("durationMinutes must be between 15 and 240");
  }

  return errors;
}

Le code reçoit now au lieu d’appeler new Date() à l’intérieur. Le test peut ainsi vérifier une limite exacte sans dépendre de l’heure réelle.

import { describe, expect, it } from "vitest";
import { validateReservation } from "./reservation-validation.js";

describe("validateReservation", () => {
  const now = new Date("2030-04-01T10:00:00.000Z");

  it("accepte une réservation future de durée autorisée", () => {
    expect(validateReservation({
      startsAt: new Date("2030-04-01T11:00:00.000Z"),
      now,
      durationMinutes: 60,
    })).toEqual([]);
  });

  it("refuse une date égale à maintenant", () => {
    expect(validateReservation({
      startsAt: now,
      now,
      durationMinutes: 60,
    })).toContain("startsAt must be in the future");
  });

  it("refuse une durée hors limites", () => {
    expect(validateReservation({
      startsAt: new Date("2030-04-01T11:00:00.000Z"),
      now,
      durationMinutes: 10,
    })).toContain("durationMinutes must be between 15 and 240");
  });
});

Les extensions .js dans les imports sont courantes dans des projets TypeScript compilés en modules ES, mais la configuration exacte dépend du tsconfig et du runner. Adapter l’import au projet réel plutôt que de copier mécaniquement l’exemple.

2.2 Tester les frontières et les invariants

Pour une règle qui accepte les valeurs entre min et max, tester au minimum :

  • min - 1 ;
  • min ;
  • une valeur représentative au milieu ;
  • max ;
  • max + 1 ;
  • les types incorrects, les valeurs manquantes et les valeurs non finies si elles sont possibles à l’entrée.

Un invariant est une propriété qui doit rester vraie quel que soit le chemin d’exécution : un montant ne devient pas négatif, une réservation confirmée possède un créneau, une réponse publique ne contient jamais un hash de mot de passe.

Ne pas multiplier artificiellement les cas si une table de cas apporte une meilleure lisibilité :

it.each([
  { duration: 14, valid: false },
  { duration: 15, valid: true },
  { duration: 60, valid: true },
  { duration: 240, valid: true },
  { duration: 241, valid: false },
])("duration=$duration valid=$valid", ({ duration, valid }) => {
  const errors = validateReservation({
    startsAt: new Date("2030-04-01T11:00:00.000Z"),
    now: new Date("2030-04-01T10:00:00.000Z"),
    durationMinutes: duration,
  });
  expect(errors.length === 0).toBe(valid);
});

2.3 Ne pas tester uniquement les détails

Éviter d’asserter qu’une fonction privée est appelée trois fois ou que l’implémentation emploie une boucle spécifique. Vérifier le résultat métier et les interactions qui font partie du contrat : par exemple, qu’un e-mail n’est pas envoyé si l’écriture en base échoue.

Exercice 2

Écrire des tests pour une fonction qui accepte une quantité entière entre 1 et 20. Couvrir les limites, les valeurs hors plage et les valeurs non entières.

Correction expliquée : tester 0, 1, 20, 21, 1.5, NaN et une valeur absente si le type d’entrée externe permet cette absence. Les cas 1 et 20 prouvent que les bornes sont inclusives ; 0 et 21 prouvent le rejet au-delà des bornes ; 1.5 vérifie l’intégralité ; NaN empêche une comparaison numérique naïve de passer involontairement.

Quiz 2

Pourquoi injecter une horloge ou un générateur d’identifiants ?

A. Pour rendre toutes les dépendances fictives en production.
B. Pour rendre le résultat contrôlable et les tests déterministes.
C. Pour supprimer le besoin de tests d’intégration.

Réponse : B. Les dépendances variables doivent être contrôlées en test. Les tests d’intégration restent nécessaires pour vérifier que les composants fonctionnent avec les vraies dépendances.

Module 3 — Choisir un runner et écrire des assertions utiles

3.1 Runner natif ou bibliothèque spécialisée

Node.js fournit node:test et node:assert/strict, sans dépendance de test tierce. Vitest offre une expérience familière aux projets TypeScript modernes, des mocks, des snapshots et des rapports de couverture. Le choix dépend des conventions du dépôt, du système de modules, de la configuration TypeScript et des besoins de l’équipe.

Ne pas introduire un deuxième runner uniquement pour suivre une préférence personnelle. Une équipe qui possède déjà Vitest devrait d’abord utiliser son infrastructure existante ; un petit package Node.js peut préférer le runner natif.

Exemple avec le runner natif, en JavaScript ESM :

import test from "node:test";
import assert from "node:assert/strict";

test("une fonction additionne deux valeurs", () => {
  assert.equal(2 + 3, 5);
});

Exemple Vitest :

import { expect, it } from "vitest";

it("additionne deux valeurs", () => {
  expect(2 + 3).toBe(5);
});

Ces extraits illustrent les API ; leur exécution dépend de la configuration et des scripts du projet.

3.2 Une assertion doit pouvoir échouer

Cette assertion ne prouve presque rien :

expect(result).toBeDefined();

Si le contrat exige un identifiant, une date ISO et un statut, tester ces propriétés :

expect(result).toMatchObject({
  status: "confirmed",
  id: expect.any(String),
  startsAt: expect.any(String),
});
expect(Number.isNaN(Date.parse(result.startsAt))).toBe(false);

Éviter les snapshots géants et opaques. Un snapshot peut être utile pour un format stable et lisible, mais une modification massive du snapshot ne doit pas être acceptée sans comprendre ce qui a changé.

3.3 Tester les erreurs avec précision

Un test d’erreur doit vérifier :

  • que l’opération échoue ;
  • que l’erreur correspond au contrat attendu ;
  • qu’aucun effet secondaire interdit n’a eu lieu.
await expect(service.confirm("missing-id"))
  .rejects.toMatchObject({ code: "RESERVATION_NOT_FOUND" });
expect(repository.save).not.toHaveBeenCalled();

Ne pas comparer le texte complet d’une erreur technique si ce texte n’est pas un contrat public. Préférer un code métier stable, un statut HTTP ou une structure documentée.

3.4 Asynchronisme et nettoyage

Toujours await les promesses dont le résultat est testé. Une promesse oubliée peut laisser un test passer avant le rejet, ou créer une erreur non attribuée au bon cas. Fermer les serveurs, connexions, streams et conteneurs même si une assertion échoue.

Utiliser les hooks du runner (afterEach, afterAll, ou leurs équivalents) et les blocs try/finally lorsqu’une ressource doit impérativement être libérée.

Exercice 3

Un test appelle une fonction asynchrone sans await, puis vérifie un compteur avant que l’opération ne soit terminée. Expliquer le risque et corriger le test.

Correction expliquée : le test peut terminer avant la résolution ou le rejet de la promesse. Attendre l’opération (await action()) puis vérifier l’état final ; si le contrat est le rejet, employer l’assertion asynchrone appropriée du runner.

Quiz 3

Quelle assertion est la plus utile pour un contrat métier ?

A. Vérifier seulement que le résultat n’est pas undefined.
B. Vérifier le code d’erreur stable et l’absence d’effet secondaire interdit.
C. Vérifier le nom d’une variable locale.

Réponse : B. Elle décrit un comportement visible et protège contre une régression significative.

Module 4 — Doubles de test : mock, stub, fake et spy

4.1 Quatre notions distinctes

  • Stub : renvoie une valeur contrôlée ou simule une réponse pour un scénario.
  • Mock : permet aussi d’attendre des interactions précises, par exemple l’envoi d’un message.
  • Fake : implémentation simplifiée mais fonctionnelle, par exemple un dépôt en mémoire.
  • Spy : observe les appels d’une vraie fonction ou d’un objet sans nécessairement remplacer son comportement.

Les termes varient parfois selon les équipes ; l’important est de préciser le rôle du double.

4.2 Exemple : isoler un service

type Reservation = { id: string; status: "pending" | "confirmed" };

interface ReservationRepository {
  findById(id: string): Promise<Reservation | null>;
  save(reservation: Reservation): Promise<void>;
}

interface NotificationGateway {
  sendConfirmation(reservationId: string): Promise<void>;
}

export class ReservationService {
  constructor(
    private readonly repository: ReservationRepository,
    private readonly notifications: NotificationGateway,
  ) {}

  async confirm(id: string): Promise<void> {
    const reservation = await this.repository.findById(id);
    if (!reservation) throw new Error("RESERVATION_NOT_FOUND");
    if (reservation.status !== "pending") throw new Error("INVALID_STATE");

    const confirmed = { ...reservation, status: "confirmed" as const };
    await this.repository.save(confirmed);
    await this.notifications.sendConfirmation(id);
  }
}

Le service dépend d’interfaces explicites. Le test peut injecter un fake de dépôt et un mock de notification. Le design rend les effets de bord visibles, sans imposer une bibliothèque de mocks.

Attention : ce service illustre une séquence métier simple, pas une garantie transactionnelle. Si l’envoi de notification échoue après l’écriture, la réservation est déjà confirmée. En production, envisager une outbox transactionnelle ou un processus de reprise plutôt que d’imaginer qu’un mock prouve la fiabilité distribuée.

4.3 Exemple de test isolé

import { beforeEach, expect, it, vi } from "vitest";

const repository = {
  findById: vi.fn(),
  save: vi.fn(),
};
const notifications = {
  sendConfirmation: vi.fn(),
};

beforeEach(() => {
  vi.resetAllMocks();
});

it("enregistre la confirmation puis notifie", async () => {
  repository.findById.mockResolvedValue({ id: "r-17", status: "pending" });
  repository.save.mockResolvedValue(undefined);
  notifications.sendConfirmation.mockResolvedValue(undefined);

  const service = new ReservationService(repository, notifications);
  await service.confirm("r-17");

  expect(repository.save).toHaveBeenCalledWith({
    id: "r-17",
    status: "confirmed",
  });
  expect(notifications.sendConfirmation).toHaveBeenCalledWith("r-17");
});

it("ne notifie pas si la réservation est absente", async () => {
  repository.findById.mockResolvedValue(null);

  const service = new ReservationService(repository, notifications);
  await expect(service.confirm("missing")).rejects.toThrow("RESERVATION_NOT_FOUND");
  expect(repository.save).not.toHaveBeenCalled();
  expect(notifications.sendConfirmation).not.toHaveBeenCalled();
});

Dans un vrai projet TypeScript strict, déclarer les types des mocks ou employer vi.mocked selon la structure des modules afin d’éviter des types trop permissifs. L’extrait privilégie la lisibilité conceptuelle.

4.4 Quand ne pas mocker ?

Ne pas mocker la base pour prouver une contrainte SQL, une transaction ou une isolation concurrente. Ne pas mocker le routeur pour prétendre tester le contrat HTTP. Un double ne peut prouver que son propre comportement et le code qui l’appelle, pas la compatibilité réelle avec l’infrastructure.

Un mock trop détaillé peut transformer le test en miroir de l’implémentation. Une modification interne fait alors échouer la suite sans changement métier. Mockez les frontières instables ou coûteuses, mais gardez des tests d’intégration ciblés.

Exercice 4

Choisir le double adapté :

  1. Forcer une passerelle de paiement à répondre « refusée ».
  2. Vérifier qu’un événement est publié une seule fois.
  3. Tester un algorithme de recherche sans serveur de base.
  4. Vérifier une contrainte UNIQUE PostgreSQL.

Correction expliquée : 1) stub ; 2) mock/spy sur le port de publication ; 3) fake de dépôt si le but est le service, mais tester l’algorithme directement si possible ; 4) vraie base PostgreSQL, pas un mock.

Quiz 4

Pourquoi un fake en mémoire ne suffit-il pas pour tester une contrainte SQL ?

Réponse : il ne reproduit pas nécessairement le moteur SQL, les transactions, les verrous, les contraintes ou l’isolation. Il peut être utile pour tester une logique applicative, mais pas pour prouver le comportement du SGBD.

Module 5 — Tests d’intégration avec PostgreSQL réel

5.1 Ce que l’intégration doit prouver

Un test d’intégration vérifie que plusieurs composants fonctionnent ensemble : service, dépôt, pilote SQL, migrations, contraintes et transactions. Pour une fonctionnalité critique, utiliser un PostgreSQL réel isolé plutôt qu’une simulation qui ne partage pas les mêmes règles.

Testcontainers permet de démarrer un conteneur PostgreSQL pour les tests, à condition que l’environnement dispose d’un moteur de conteneurs et des images nécessaires. Cette option n’est pas adaptée à tous les environnements CI ; une base de test dédiée peut être utilisée si son isolation et son nettoyage sont garantis.

5.2 Exemple de principe avec Testcontainers

L’exemple suivant est un squelette à adapter aux versions des bibliothèques et aux conventions du projet :

import { afterAll, beforeAll, describe, expect, it } from "vitest";
import { PostgreSqlContainer, type StartedPostgreSqlContainer } from "@testcontainers/postgresql";
import { Pool } from "pg";

describe("repository PostgreSQL", () => {
  let container: StartedPostgreSqlContainer;
  let pool: Pool;

  beforeAll(async () => {
    container = await new PostgreSqlContainer("postgres:16-alpine").start();
    pool = new Pool({ connectionString: container.getConnectionUri() });

    await pool.query(`
      CREATE TABLE reservations (
        id text PRIMARY KEY,
        status text NOT NULL CHECK (status IN ('pending', 'confirmed'))
      )
    `);
  }, 60_000);

  afterAll(async () => {
    await pool?.end();
    await container?.stop();
  });

  it("refuse un statut invalide au niveau de la base", async () => {
    await expect(
      pool.query("INSERT INTO reservations (id, status) VALUES ($1, $2)", ["r-1", "unknown"]),
    ).rejects.toMatchObject({ code: "23514" });
  });
});

Le code illustre le principe, mais doit être validé avec la version exacte de Testcontainers, du pilote pg, du runner et de TypeScript. Pour un dépôt réel, exécuter les migrations applicatives plutôt que de recréer une structure divergente dans le test. Ajouter une stratégie d’isolation par test : transaction dédiée lorsque cela convient, schéma temporaire ou base fraîche.

5.3 Transactions et rollback

Le test doit vérifier l’état final de la base, pas seulement que ROLLBACK a été appelé sur un mock. Pour un transfert de fonds, par exemple :

  • initialiser deux comptes ;
  • démarrer le transfert ;
  • provoquer une erreur après le débit mais avant le crédit ;
  • vérifier que le débit n’est pas durable ;
  • confirmer qu’aucun compte n’a un solde incohérent.

Il faut provoquer un échec réaliste au bon point du processus. Un test où le service échoue avant toute écriture ne prouve pas le rollback d’une transaction ayant déjà modifié des lignes.

5.4 Nettoyage et isolation

Les tests ne doivent pas dépendre de l’ordre d’exécution. Un test ne doit pas réutiliser implicitement des lignes créées par un autre. Les options usuelles sont :

  • base éphémère par suite ;
  • schéma dédié et nettoyage explicite ;
  • transaction par test si le code testé partage bien la même connexion/transaction ;
  • jeux de données identifiés par un préfixe unique.

Attention : ouvrir une transaction dans le test ne garantit pas que le code testé participe à cette transaction. Si le dépôt ouvre sa propre connexion, le rollback du test ne nettoiera pas ses écritures.

Exercice 5

Concevoir un test qui prouve qu’un transfert échoue sans perdre d’argent lorsqu’une écriture de crédit échoue.

Correction expliquée : créer les comptes en base réelle, capturer les soldes initiaux, injecter une panne contrôlée après le débit et avant le commit, puis relire les deux soldes via une nouvelle transaction/connexion après l’échec. L’égalité des soldes finaux aux soldes initiaux est l’assertion clé. Le test doit vérifier le chemin de transaction réellement utilisé par l’application.

Quiz 5

Quelle preuve est la plus forte pour un rollback SQL ?

A. Vérifier que le mock client.query a reçu le texte ROLLBACK.
B. Relire les données dans la base après l’échec et vérifier qu’aucune écriture partielle n’est durable.
C. Vérifier que la fonction retourne false.

Réponse : B. Le comportement durable observé dans la base est la propriété à protéger. Les assertions d’interaction peuvent compléter le test mais ne le remplacent pas.

Module 6 — Tests de contrat HTTP et OpenAPI

6.1 Tester les frontières publiques

Un test de contrat vérifie qu’un producteur respecte la forme et les règles promises à ses consommateurs. Pour une API, les contrats incluent notamment :

  • méthodes et chemins ;
  • paramètres et corps acceptés ;
  • schémas de réponses ;
  • statuts HTTP ;
  • structure des erreurs ;
  • règles de pagination ;
  • authentification et en-têtes pertinents.

Une interface TypeScript ne valide pas automatiquement un JSON reçu sur le réseau. Les données HTTP doivent être validées à l’exécution et la réponse doit respecter le schéma publié.

6.2 Test HTTP sans dépendre du texte de l’interface

Exemple conceptuel avec une fonction createTestApp() fournie par le projet :

it("retourne 400 si la durée est invalide", async () => {
  const response = await request(createTestApp())
    .post("/reservations")
    .send({ startsAt: "2030-04-01T11:00:00.000Z", durationMinutes: 10 });

  expect(response.status).toBe(400);
  expect(response.body).toMatchObject({
    error: { code: "VALIDATION_ERROR" },
  });
});

request représente ici une bibliothèque de test HTTP telle que Supertest. L’extrait ne fixe pas le choix de bibliothèque ; le projet doit adopter celle qui correspond à son serveur et à ses conventions.

Ne pas seulement tester la fonction de validation : vérifier aussi que la route appelle bien cette validation et transforme le rejet en réponse HTTP correcte.

6.3 OpenAPI : cohérence, pas décoration

OpenAPI décrit les opérations, les paramètres, les corps, les réponses et les mécanismes de sécurité. Il peut être utilisé pour générer des clients ou vérifier des requêtes/réponses. Un document présent dans le dépôt n’est pas une garantie de conformité si personne ne vérifie sa cohérence avec l’application.

Pratiques utiles :

  1. conserver le document OpenAPI dans le dépôt ou le générer de manière reproductible ;
  2. valider la syntaxe et la structure dans la CI ;
  3. tester les réponses réelles contre les schémas documentés ;
  4. traiter les changements incompatibles comme des modifications de contrat ;
  5. inclure les erreurs et les réponses d’authentification dans le contrat.

Exercice 6

L’API documente 201 lors de la création, mais renvoie 200 et un corps différent. Proposer une stratégie de correction.

Correction expliquée : déterminer le contrat intentionnel, puis aligner le code et la spécification. Si des clients utilisent déjà le comportement réel, mesurer le risque de rupture avant de modifier la réponse. Ajouter un test de contrat empêchant la divergence future, et documenter la décision de compatibilité.

Quiz 6

Que prouve la validation du fichier OpenAPI seule ?

Réponse : elle peut prouver que le document est structurellement valide selon le validateur utilisé, mais pas que l’application réelle renvoie les réponses décrites. Des tests contre l’application restent nécessaires.

Module 7 — Erreurs, autorisations et limites

7.1 Les cas négatifs sont des comportements de première classe

Une suite robuste vérifie les refus aussi explicitement que les réussites :

  • JSON mal formé ;
  • champs manquants ou types incorrects ;
  • identifiant inexistant ;
  • ressource existante mais appartenant à un autre utilisateur ;
  • absence d’authentification ;
  • authentification valide mais rôle insuffisant ;
  • pagination excessive ;
  • dépendance en panne ou délai dépassé ;
  • conflit de version ou état métier incompatible.

Le cas « utilisateur A tente de lire la ressource de B » est différent du cas « ressource inexistante ». Selon la politique de sécurité, l’API peut renvoyer 404 dans les deux cas pour éviter de révéler l’existence de ressources privées. Le test doit refléter la politique décidée et documentée.

7.2 Tester les permissions avec plusieurs identités

Un test d’autorisation doit créer au moins deux identités distinctes et une ressource possédée par l’une d’elles. Vérifier que l’autre ne peut ni lire, ni modifier, ni supprimer la ressource en changeant simplement son identifiant.

Ne pas mocker la fonction d’autorisation dans le test censé prouver qu’une route applique cette autorisation. Le test d’intégration doit traverser la route, le middleware et le service concernés.

7.3 Erreurs publiques et erreurs internes

Une réponse publique peut exposer un code stable et un message compréhensible. Elle ne doit pas révéler les secrets, les chaînes de connexion, les traces de pile, les requêtes SQL ou des détails personnels non nécessaires. Les journaux internes doivent être structurés et contenir un identifiant de corrélation, sans enregistrer de mots de passe, jetons ou données sensibles.

Tester à la fois :

  • le statut et la structure de l’erreur ;
  • l’absence de champs internes interdits ;
  • l’absence d’effet secondaire ;
  • la journalisation attendue, si elle est un contrat opérationnel important.

7.4 Limites et bornes

Pour une pagination limitée à 100 éléments, tester les valeurs 0, 1, 100, 101, un entier négatif, une chaîne et une valeur gigantesque. Pour les tailles de corps, délais et tentatives, choisir des tests ciblés qui vérifient les limites de sécurité et la réponse observable.

Exercice 7

Un utilisateur authentifié modifie /api/orders/123 en /api/orders/124. La seconde commande appartient à un autre utilisateur. Écrire les assertions essentielles.

Correction expliquée : la réponse doit respecter la politique de confidentialité choisie (souvent 404 ou 403), ne contenir aucune donnée de la commande 124, ne modifier aucun état et ne déclencher aucune action externe. Créer explicitement les deux utilisateurs et leurs commandes dans l’environnement de test.

Quiz 7

Pourquoi un test de permission doit-il utiliser deux identités réelles dans le scénario ?

Réponse : sans deux propriétaires distincts, le test ne prouve pas que le contrôle d’accès à la ressource est appliqué. Une simple vérification qu’un utilisateur authentifié peut accéder à sa propre ressource ne détecte pas une faille IDOR/BOLA.

Module 8 — Transactions, concurrence et idempotence

8.1 Les tests séquentiels ne prouvent pas la sûreté concurrente

Deux requêtes peuvent lire le même état puis tenter de le modifier. Un test séquentiel peut passer alors que deux requêtes concurrentes créent un doublon ou perdent une mise à jour. Les garanties doivent être portées par la base (contraintes, verrous, isolation) et par le protocole applicatif, puis testées sous concurrence.

Exemples de propriétés à protéger :

  • un créneau n’est réservé qu’une fois ;
  • un solde ne devient jamais négatif ;
  • une clé d’idempotence ne produit pas deux opérations durables ;
  • deux mises à jour de la même version ne s’écrasent pas silencieusement.

8.2 Tester une contrainte d’unicité concurrente

Pour une réservation unique par créneau, une contrainte SQL est plus fiable qu’un simple « vérifier puis insérer » côté application. Le test lance deux opérations indépendantes vers la base et vérifie qu’une seule réservation gagne.

const results = await Promise.allSettled([
  reserveSlot({ slotId: "slot-42", userId: "user-a" }),
  reserveSlot({ slotId: "slot-42", userId: "user-b" }),
]);

expect(results.filter((r) => r.status === "fulfilled")).toHaveLength(1);
expect(results.filter((r) => r.status === "rejected")).toHaveLength(1);

const rows = await pool.query(
  "SELECT slot_id FROM reservations WHERE slot_id = $1",
  ["slot-42"],
);
expect(rows.rowCount).toBe(1);

Le code est un squelette : le schéma, les erreurs attendues et les fonctions doivent être adaptés au dépôt. Les deux opérations doivent utiliser des connexions indépendantes pour créer une véritable concurrence.

8.3 Vérifier le rollback et les erreurs de transaction

Tester le scénario d’échec après une première écriture et avant le commit. Après le rejet, vérifier l’état durable avec une lecture indépendante. Vérifier également que la connexion est remise dans un état réutilisable et que les erreurs secondaires pendant le rollback ne masquent pas l’erreur initiale sans être journalisées.

Les tests de concurrence peuvent être sensibles au timing. Éviter de compter sur un setTimeout arbitraire pour provoquer une course ; utiliser des barrières explicites dans les doubles lorsque l’on teste l’orchestration, et la base réelle pour tester les contraintes et l’isolation.

8.4 Idempotence et répétition

Une requête répétée peut survenir après un timeout : le client ne sait pas si la première opération a été appliquée. Pour une opération non naturellement idempotente, le serveur doit définir comment la clé d’idempotence est enregistrée, comment les requêtes concurrentes avec la même clé sont arbitrées et quelle réponse est rejouée.

Tests minimaux :

  1. même clé et même payload répétés : une seule opération durable ;
  2. même clé avec payload différent : conflit explicite ;
  3. deux requêtes simultanées avec la même clé : pas de double effet ;
  4. échec avant commit : possibilité de reprise conforme au contrat ;
  5. effet externe : outbox ou mécanisme de déduplication vérifié séparément.

Exercice 8

Deux requêtes utilisent la même clé d’idempotence au même moment. Quelles propriétés tester ?

Correction expliquée : une seule opération métier durable, une réponse cohérente pour les deux clients, aucun double effet externe et un résultat déterministe en cas de payload différent. Un test unitaire avec mock ne prouve pas l’arbitrage concurrent dans PostgreSQL ; il faut une intégration avec des connexions indépendantes.

Quiz 8

Pourquoi un Promise.all() de deux appels ne suffit-il pas toujours à prouver une course réelle ?

Réponse : les opérations peuvent être sérialisées par le code ou le pool, ou ne pas se chevaucher au point critique. Le test doit vérifier l’architecture de connexion et l’état final, et provoquer la concurrence de façon contrôlée lorsque c’est nécessaire.

Module 9 — Fixtures, déterminisme et couverture

9.1 Fixtures et données de test

Une fixture est un état de départ contrôlé. Elle doit être petite, explicite et adaptée au scénario. Éviter les usines de données si complexes qu’elles masquent les propriétés importantes. Les données peuvent être générées, mais la graine et les contraintes doivent être maîtrisées pour permettre de reproduire un échec.

Chaque test doit pouvoir être exécuté seul et dans un ordre différent. Un test qui passe seulement après un autre dépend d’un état caché.

9.2 Maîtriser l’horloge, l’aléatoire et l’environnement

  • Injecter une horloge ou utiliser les faux timers du runner pour les règles dépendantes du temps.
  • Contrôler la génération d’identifiants lorsque leur valeur influe sur l’assertion.
  • Ne pas dépendre d’un fuseau horaire implicite : utiliser des dates ISO et UTC lorsque cela correspond au contrat.
  • Fixer la locale, les variables d’environnement et la configuration pertinentes.
  • Ne pas appeler de services externes réels dans les tests unitaires.
  • Toujours restaurer les mocks, timers et variables modifiées.

Un test déterministe n’est pas un test qui ignore les pannes : les erreurs doivent être simulées intentionnellement, et les tests d’intégration doivent échouer clairement si leur infrastructure requise n’est pas disponible.

9.3 Couverture de code

Les métriques habituelles incluent :

  • lignes : lignes exécutées ;
  • instructions : instructions exécutées ;
  • branches : chemins conditionnels observés ;
  • fonctions : fonctions appelées.

La couverture aide à identifier des zones non exercées. Elle ne mesure pas directement la pertinence des assertions, la qualité des scénarios, la conformité aux besoins ou la robustesse concurrente.

Un objectif global de 80 % peut être un repère d’équipe, pas une preuve de qualité. Un module de calcul critique peut nécessiter une couverture de branches plus élevée ; une configuration générée ou un adaptateur trivial peut avoir un autre objectif. Éviter de modifier les seuils seulement pour faire passer la CI.

9.4 Mutation testing et qualité des assertions

Le mutation testing introduit volontairement de petites erreurs (par exemple inverser > en >=) et observe si les tests les détectent. Si une mutation plausible survit, les assertions ou les scénarios sont peut-être trop faibles. Cette technique complète la couverture, sans remplacer la revue du modèle métier.

9.5 Définir une porte de qualité reproductible

Un pipeline raisonnable peut exécuter, dans cet ordre :

  1. formatage et lint ;
  2. vérification TypeScript ;
  3. tests unitaires rapides ;
  4. tests d’intégration avec dépendances isolées ;
  5. tests de contrat ;
  6. couverture et contrôle de seuil ;
  7. tests end-to-end ciblés.

Les étapes exactes dépendent des scripts du dépôt. Un résultat local n’est pas reproductible si les versions, les variables d’environnement, les migrations ou les services requis ne sont pas documentés.

Exercice 9

Une suite affiche 98 % de couverture, mais ne teste pas les erreurs SQL, l’accès interdit ni la concurrence. Peut-on conclure que le backend est fiable ?

Correction expliquée : non. La couverture élevée décrit l’exécution des lignes/branches mesurées, pas les propriétés non testées. Ajouter des scénarios correspondant aux risques : panne de dépendance, accès croisé, rollback et opérations concurrentes.

Quiz 9

Quel est le meilleur usage d’un rapport de couverture ?

A. Remplacer la revue de code.
B. Identifier les zones non exécutées et guider l’ajout de tests pertinents.
C. Déclarer l’absence de bugs dès qu’un seuil est atteint.

Réponse : B. La couverture est un outil de diagnostic et de priorisation, pas une garantie de correction.

Projet intégrateur — Suite de tests pour une API de réservation

Contexte

L’API expose la création et la confirmation de réservations. Une réservation possède un propriétaire, un créneau, un statut et une durée. PostgreSQL est le stockage de référence.

Travaux demandés

  1. Définir une matrice de risques et associer chaque exigence à un test.
  2. Écrire des tests unitaires des validations, limites et transitions d’état.
  3. Tester les routes HTTP : succès, validation invalide, ressource absente et erreur de dépendance.
  4. Vérifier qu’un utilisateur ne peut pas lire ou modifier la réservation d’un autre.
  5. Exécuter des tests d’intégration contre PostgreSQL et appliquer les migrations.
  6. Simuler une erreur au milieu d’une transaction et vérifier l’absence d’écriture partielle.
  7. Lancer deux réservations concurrentes pour un même créneau et prouver qu’une seule réussit.
  8. Tester l’idempotence d’une requête répétée.
  9. Mesurer la couverture, examiner les zones non testées et justifier les exceptions.
  10. Documenter les commandes, variables d’environnement, dépendances et procédure de nettoyage.

Critères d’acceptation

  • Chaque test décrit un comportement et contient des assertions qui échoueraient si ce comportement régressait.
  • Les tests unitaires ne nécessitent pas d’infrastructure externe.
  • Les tests d’intégration utilisent une base PostgreSQL isolée et les migrations réelles du projet.
  • L’échec d’une opération transactionnelle ne laisse pas d’écriture partielle durable.
  • Deux demandes concurrentes ne peuvent pas réserver le même créneau.
  • Les tests d’autorisation utilisent deux propriétaires distincts et n’exposent pas les données privées.
  • La suite peut être lancée à partir d’instructions documentées et ne dépend pas de l’ordre d’exécution.
  • Les limites connues sont documentées ; aucun test non exécuté n’est présenté comme réussi.

Synthèse opérationnelle

Avant d’ajouter un test, formuler la régression qu’il doit détecter. Utiliser les tests unitaires pour la logique isolée, l’intégration pour les interactions réelles, les tests de contrat pour les frontières publiques et les tests end-to-end pour quelques parcours essentiels. Les mocks accélèrent les tests mais ne remplacent pas une vraie base lorsqu’il s’agit de transactions ou de concurrence. Une suite de qualité est déterministe, isolée, reproductible et transparente sur ses limites.
