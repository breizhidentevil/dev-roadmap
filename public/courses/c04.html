Objectifs

À l’issue du cours, l’apprenant doit pouvoir modéliser les menaces d’une API, choisir une stratégie d’authentification adaptée, stocker des mots de passe sans les conserver en clair, sécuriser les sessions navigateur, distinguer OAuth 2.0 d’OpenID Connect, appliquer des permissions au niveau de chaque ressource, protéger les secrets et limiter les abus. La sécurité est une propriété de l’architecture, des contrôles d’accès, des opérations de déploiement et des tests ; elle ne se résume pas à ajouter un JWT.

Module 1 — Modèle de menace et principes de sécurité

1.1 Partir des actifs et des frontières de confiance

Avant de choisir une bibliothèque, inventorier ce qu’il faut protéger : comptes, données personnelles, commandes, rôles, clés d’API, sessions, journaux et disponibilité du service. Identifier les acteurs et les frontières de confiance : navigateur, API publique, service interne, fournisseur d’identité, base de données, file de messages et opérateur.

Pour chaque actif, répondre à quatre questions :

  • Qui peut le lire, le modifier ou le supprimer ?
  • Quel abus est réaliste ?
  • Quel contrôle réduit le risque ?
  • Quel test démontre que ce contrôle fonctionne ?

Un modèle de menace est une hypothèse documentée et révisable, pas une certification. Utiliser des catégories comme usurpation d’identité, altération, répudiation, divulgation, déni de service et élévation de privilèges. Pour les API, examiner notamment les contrôles d’accès objet et fonctionnel, l’authentification, la consommation de ressources, la mauvaise configuration et les flux métier sensibles.

1.2 Défense en profondeur et moindre privilège

Ne pas faire dépendre la sécurité d’un seul contrôle. Une API peut valider un jeton correctement et rester vulnérable si elle ne vérifie pas que l’utilisateur peut lire la ressource demandée. Une base peut être correctement protégée par mot de passe tout en exposant des secrets dans les journaux.

Appliquer :

  • moindre privilège : chaque identité n’obtient que les permissions nécessaires ;
  • refus par défaut : une permission non explicitement accordée est refusée ;
  • validation à la frontière : ne pas faire confiance aux types TypeScript pour valider les données réseau ;
  • séparation des responsabilités : authentification, autorisation et logique métier ont des rôles distincts ;
  • journalisation sans secrets : enregistrer les événements utiles sans stocker les jetons ni les mots de passe ;
  • tests négatifs : vérifier les refus, pas uniquement les succès.

Exercice 1

Pour une API de commandes, identifier quatre actifs, deux acteurs et trois menaces.

Correction expliquée : actifs possibles : données de commande, adresse de livraison, compte utilisateur et clé de paiement. Acteurs : propriétaire du compte et attaquant authentifié avec un compte ordinaire. Menaces : lecture de la commande d’autrui en modifiant son identifiant, élévation de privilèges via un champ role envoyé par le client, et brute force sur la connexion. Associer à chaque menace un contrôle vérifiable : autorisation objet, rôle défini côté serveur et limitation des tentatives.

Quiz 1

Un JWT valide suffit-il à autoriser la lecture d’une commande ?

Réponse : non. Il peut prouver une identité ou transporter des claims signés, mais le serveur doit aussi vérifier l’autorisation d’accès à cette commande et la validité du contexte.

Module 2 — Mots de passe, inscription et réinitialisation

2.1 Ne jamais stocker un mot de passe en clair

Stocker un hash produit par un algorithme spécialisé pour les mots de passe, conçu pour être coûteux. Argon2id est un choix courant lorsque l’environnement le permet ; scrypt est une autre option reconnue. Utiliser une bibliothèque maintenue et ses paramètres recommandés à la date du déploiement. Ne pas employer SHA-256 seul, MD5, SHA-1 ou un chiffrement réversible pour stocker des mots de passe.

Le hash doit inclure un sel unique, normalement géré par la bibliothèque. Le sel n’est pas un secret ; il empêche notamment que deux mots de passe identiques produisent le même hash. Un pepper partagé peut compléter le mécanisme dans certains modèles, mais il doit être stocké séparément du hash et sa rotation doit être conçue à l’avance.

Exemple conceptuel avec une bibliothèque Argon2 maintenue :

import argon2 from "argon2";

export async function hashPassword(password: string): Promise<string> {
  return argon2.hash(password, {
    type: argon2.argon2id,
  });
}

export async function verifyPassword(
  storedHash: string,
  candidate: string,
): Promise<boolean> {
  return argon2.verify(storedHash, candidate);
}

Ce code suppose que la dépendance est correctement installée, configurée et maintenue. Les paramètres de coût doivent être évalués sur le matériel de production ; ne pas copier une configuration sans mesure. Limiter la taille d’entrée pour réduire les risques d’épuisement des ressources.

2.2 Inscription et connexion

Valider le format des entrées, mais éviter les réponses qui révèlent inutilement l’existence d’un compte. Les réponses « adresse inconnue » et « mot de passe incorrect » peuvent faciliter l’énumération des comptes ; adopter des messages publics cohérents et une politique de limitation des tentatives.

Après comparaison du mot de passe :

  • créer une session ou émettre un jeton selon l’architecture ;
  • renouveler l’identifiant de session après authentification et changement de privilège ;
  • ne jamais enregistrer le mot de passe ou son contenu dans les logs ;
  • ne jamais accepter le rôle ou l’état de vérification fourni par le client comme source d’autorité.

2.3 Réinitialisation de mot de passe

Créer un jeton de réinitialisation cryptographiquement aléatoire, à durée courte, à usage unique, lié à un compte et stocké sous forme de hash lorsque cela est possible. Envoyer le lien sur un canal de confiance. Invalider le jeton après usage et empêcher sa réutilisation concurrente. Éviter de changer automatiquement l’adresse e-mail au cours du processus.

La réponse initiale doit rester neutre (« si un compte correspond, des instructions seront envoyées »). Limiter le débit, éviter de placer des jetons dans les logs, et envisager la révocation des sessions existantes après réinitialisation. Le processus de vérification d’adresse e-mail suit des principes analogues : token aléatoire, expiration, usage unique et vérification côté serveur.

Exercice 2

Pourquoi une fonction de hash généraliste rapide est-elle inadaptée aux mots de passe ?

Correction expliquée : si la base fuit, un attaquant peut tester un grand nombre de candidats rapidement. Les fonctions spécialisées sont volontairement plus coûteuses et rendent les attaques hors ligne plus chères. Le sel empêche la réutilisation directe de tables précalculées, mais ne remplace pas le coût du hash.

Quiz 2

Le sel d’un hash de mot de passe doit-il rester secret ?

Réponse : non. Le sel est généralement enregistré avec le hash. C’est le mot de passe qui doit rester secret ; la résistance repose sur un algorithme spécialisé et des paramètres adaptés.

Module 3 — Sessions, cookies et CSRF

3.1 Les cookies de session

Pour une application navigateur classique, une session serveur peut être plus simple à révoquer qu’un jeton autonome. Le cookie ne doit contenir qu’un identifiant opaque et aléatoire ; les données d’autorisation et l’état de session sont conservés côté serveur ou dans un stockage adapté.

Exemple d’attributs à adapter au domaine et au déploiement :

Set-Cookie: __Host-session=<opaque-value>; Path=/; Secure; HttpOnly; SameSite=Lax
  • Secure : le navigateur n’envoie le cookie que sur HTTPS.
  • HttpOnly : le JavaScript côté page ne peut pas lire le cookie via document.cookie.
  • SameSite : contrôle certains envois intersites ; Lax est un compromis courant, pas une protection universelle.
  • Path=/ et l’absence de Domain sont requis par le préfixe __Host-.
  • Max-Age ou Expires définit la durée de vie côté navigateur ; la session côté serveur doit aussi expirer.

Le nom et les attributs doivent correspondre à l’environnement. En développement local, HTTPS et les règles de cookies peuvent différer ; ne pas affaiblir silencieusement la configuration de production pour résoudre un problème local.

3.2 Rotation et révocation

Renouveler l’identifiant de session après connexion, élévation de privilège ou événement sensible afin de prévenir la fixation de session. À la déconnexion, invalider la session côté serveur et expirer le cookie. Une suppression du cookie côté navigateur seule ne révoque pas nécessairement une session encore valide côté serveur.

Prévoir :

  • expiration après inactivité ;
  • durée maximale absolue ;
  • révocation après changement de mot de passe ou suspicion de compromission ;
  • limitation du nombre de sessions si nécessaire ;
  • stockage serveur adapté à plusieurs instances.

3.3 CSRF

Une attaque CSRF tente de faire exécuter au navigateur authentifié une action non désirée. Les cookies étant envoyés automatiquement, une application qui s’appuie sur des cookies doit analyser ce risque.

Mesures possibles selon l’architecture :

  • cookies SameSite adaptés ;
  • jeton CSRF lié à la session et vérifié côté serveur ;
  • validation de Origin ou Referer selon le contexte ;
  • ne pas utiliser GET pour modifier un état ;
  • éviter les points d’entrée qui acceptent des types de contenu inattendus.

SameSite réduit certaines attaques mais ne remplace pas une analyse complète, notamment avec des sous-domaines, des flux OAuth ou des intégrations particulières. CORS n’est pas un mécanisme de prévention CSRF général : il contrôle principalement l’accès des scripts à certaines réponses, pas l’ensemble des requêtes que le navigateur peut envoyer.

Exercice 3

Un utilisateur se déconnecte, mais son ancien cookie est rejoué. Quel contrôle doit rendre ce rejeu inefficace ?

Correction expliquée : la session doit être invalidée côté serveur, puis le cookie expiré côté client. Si le serveur accepte encore l’identifiant, effacer le cookie ne suffit pas.

Quiz 3

HttpOnly empêche-t-il toutes les conséquences d’une faille XSS ?

Réponse : non. Il réduit la possibilité de lire le cookie via JavaScript, mais un script injecté peut encore effectuer des actions au nom de l’utilisateur ou lire les données accessibles dans la page.

Module 4 — JWT : validation, expiration et rotation

4.1 Ce qu’un JWT apporte — et ce qu’il n’apporte pas

Un JWT signé permet au destinataire de vérifier l’intégrité et l’origine du contenu selon une clé et un algorithme attendus. Un JWT signé n’est généralement pas chiffré : son payload peut être lisible par quiconque possède le token. Ne jamais y placer un mot de passe, un secret ou des données personnelles non nécessaires.

Les claims usuels incluent iss (émetteur), aud (destinataire), sub (sujet), exp (expiration), nbf (pas avant) et parfois iat ou jti. Leur sens doit être défini par le contrat. Le serveur doit vérifier les claims attendus, pas simplement décoder le payload.

4.2 Validation obligatoire

Lors de la vérification d’un JWT :

  1. choisir côté serveur une liste d’algorithmes acceptés ; ne pas laisser le token décider seul ;
  2. vérifier la signature avec la bonne clé ;
  3. vérifier iss et aud lorsque le protocole les exige ;
  4. vérifier exp et nbf, avec une tolérance d’horloge limitée et documentée ;
  5. valider le type de token et les claims nécessaires ;
  6. refuser les tokens mal formés ou inattendus ;
  7. appliquer l’autorisation à chaque ressource après authentification.

Ne jamais considérer jwt.decode() ou une simple lecture du payload comme une vérification. Employer une bibliothèque maintenue, suivre sa documentation et limiter les algorithmes et clés autorisés.

4.3 Durée de vie et révocation

Les access tokens doivent avoir une durée de vie limitée selon le risque. Un refresh token est plus sensible : le stocker et le transmettre de manière appropriée, le faire tourner à chaque usage lorsque le protocole le prévoit, détecter la réutilisation d’un ancien refresh token et révoquer la famille ou la session en cas de compromission.

Un JWT autonome n’est pas facilement révocable sans état côté serveur. Selon le besoin, employer des access tokens courts, un registre de révocation, une version de session ou un fournisseur d’identité. Éviter d’ajouter des rôles à longue durée de vie qui restent valides après la révocation d’un privilège.

4.4 Ne pas choisir JWT par réflexe

JWT n’est pas automatiquement plus sûr ou plus évolutif qu’une session. Pour une application web monolithique, une session opaque stockée côté serveur peut simplifier la révocation. Les tokens sont utiles dans certains échanges entre services et dans les architectures OAuth/OIDC, mais augmentent la complexité de gestion des clés, de l’expiration et de la révocation.

Exercice 4

Un backend décode un JWT et lit role: "admin" sans vérifier la signature. Identifier le défaut et la correction.

Correction expliquée : le client peut fabriquer un payload. Le serveur doit vérifier la signature avec les clés et algorithmes attendus, vérifier les claims requis, puis déterminer les permissions selon une source d’autorité fiable. Un rôle fourni par le client n’est jamais une preuve d’autorisation.

Quiz 4

Un JWT signé cache-t-il son payload ?

Réponse : non, pas dans le cas habituel d’un JWT signé (JWS). La signature protège l’intégrité, pas la confidentialité. Ne pas y placer de secrets.

Module 5 — OAuth 2.0 et OpenID Connect

5.1 Deux protocoles aux objectifs distincts

OAuth 2.0 est un cadre d’autorisation déléguée : il permet à un client d’obtenir un accès limité à une ressource. OpenID Connect (OIDC) ajoute une couche d’authentification standardisée au-dessus d’OAuth 2.0 et fournit notamment un ID Token.

Ne pas utiliser un access token comme preuve d’identité sans respecter le protocole prévu. Un access token est destiné à une API ; un ID Token est destiné au client OIDC et ses claims doivent être validés selon les règles OIDC.

5.2 Authorization Code et PKCE

Pour une application interactive moderne, le flux Authorization Code avec PKCE est généralement privilégié. Le client crée un code_verifier imprévisible, en dérive un code_challenge, puis le fournisseur d’identité vérifie le code au moment de l’échange. PKCE réduit le risque qu’un code d’autorisation intercepté soit échangé par un autre acteur.

Mesures essentielles :

  • valider exactement le paramètre state pour lier la réponse au démarrage de l’authentification ;
  • utiliser nonce lorsque requis par le flux OIDC et vérifier sa valeur ;
  • enregistrer des URI de redirection exactes, sans joker dangereux ;
  • valider la signature et les claims de l’ID Token ;
  • gérer expiration, erreurs, révocation et déconnexion ;
  • ne pas intégrer un client secret dans une application publique distribuée au navigateur ou à un mobile.

Le protocole et le choix du client doivent être alignés sur les recommandations actuelles du fournisseur et les spécifications en vigueur. Éviter les anciens flux qui transmettent directement des tokens dans l’URL de redirection.

5.3 Comptes liés et identité externe

Ne pas lier automatiquement un compte existant à un compte externe sur la seule base d’une adresse e-mail reçue. Vérifier les garanties du fournisseur et l’état de vérification de l’adresse, puis définir un processus explicite de liaison et de déliaison. Le couple émetteur/sujet (iss, sub) est généralement plus adapté comme identifiant stable OIDC qu’une adresse e-mail mutable.

Exercice 5

Une application confond access token et ID Token. Quel est le risque ?

Correction expliquée : les deux tokens ont des destinataires et des usages distincts. Le serveur doit valider un access token selon les règles de l’API ; le client doit valider l’ID Token selon OIDC. Intervertir leurs usages peut conduire à accepter un token destiné à un autre composant ou à mal interpréter les claims.

Quiz 5

Que fait PKCE ?

Réponse : il lie l’échange du code d’autorisation au client qui a initié le flux, en exigeant la preuve du code_verifier. Il ne remplace pas state, la validation des tokens ou les URI de redirection exactes.

Module 6 — Authentification, RBAC et autorisation par ressource

6.1 Trois questions différentes

  • Authentification : quelle identité est présentée et comment sa preuve est-elle vérifiée ?
  • Autorisation : cette identité peut-elle réaliser cette action sur cette ressource dans ce contexte ?
  • Logique métier : l’action est-elle valide selon l’état et les règles du domaine ?

Une authentification réussie ne signifie pas que l’utilisateur peut accéder à toutes les données. Un rôle admin ne doit pas être attribué par le client, et un utilisateur ayant un rôle autorisé peut encore être soumis à des contraintes de propriété, d’organisation ou d’état.

6.2 RBAC et permissions

Le RBAC associe des permissions à des rôles, puis des rôles à des utilisateurs. Il est utile lorsque les responsabilités sont relativement stables. Pour des règles dépendant de l’objet, du propriétaire, de l’organisation ou du contexte, compléter le RBAC par une vérification par ressource ou par des politiques d’autorisation explicites.

Exemple de politique lisible :

type Principal = {
  userId: string;
  roles: string[];
  organizationId: string;
};

type DocumentRecord = {
  id: string;
  ownerId: string;
  organizationId: string;
  visibility: "private" | "organization";
};

export function canReadDocument(
  principal: Principal,
  document: DocumentRecord,
): boolean {
  if (principal.roles.includes("platform-admin")) return true;
  if (document.ownerId === principal.userId) return true;
  return document.visibility === "organization" &&
    document.organizationId === principal.organizationId;
}

Cette fonction illustre une politique métier, pas une architecture complète. Les règles de rôle administrateur doivent être justifiées et auditées ; dans certains systèmes, même les administrateurs n’ont pas un accès implicite à tous les contenus. Tester chaque branche et les combinaisons limites.

6.3 Appliquer l’autorisation à chaque requête

Ne pas vérifier les permissions uniquement dans l’interface. Le serveur doit contrôler l’accès à chaque opération, y compris lecture, modification, suppression, export, téléchargement et actions en arrière-plan. Éviter les routes qui autorisent une action parce que l’utilisateur connaît un identifiant.

Lorsque c’est possible, appliquer la portée d’accès dans la requête de données, par exemple en sélectionnant la ressource par identifiant et propriétaire. Cela réduit le risque qu’une vérification séparée soit oubliée, mais ne dispense pas de gérer correctement les rôles et les règles plus complexes.

Exercice 6

Un utilisateur peut modifier son profil mais envoie {"role":"admin"} dans la requête. Comment prévenir l’escalade de privilèges ?

Correction expliquée : définir un schéma d’entrée qui n’accepte que les champs modifiables par l’utilisateur ; ne pas réutiliser directement l’objet de requête pour mettre à jour le modèle complet ; gérer les changements de rôle dans une opération distincte, autorisée et auditée côté serveur.

Quiz 6

Une route protégée par authentification est-elle forcément protégée contre l’accès non autorisé aux objets ?

Réponse : non. Elle doit aussi vérifier que le principal peut agir sur la ressource demandée. C’est une cause fréquente de vulnérabilités BOLA/IDOR.

Module 7 — IDOR/BOLA et tests de contrôle d’accès

7.1 Le danger des identifiants manipulables

IDOR (Insecure Direct Object Reference) et BOLA (Broken Object Level Authorization) désignent des problèmes où une application n’applique pas correctement les permissions sur une ressource identifiée par l’utilisateur. L’identifiant peut être séquentiel, UUID ou autre : un identifiant difficile à deviner ne remplace pas l’autorisation.

Une route comme GET /api/invoices/:id doit vérifier la permission sur la facture correspondante. Il faut faire de même pour les exports, fichiers, messages, rapports, jobs asynchrones et opérations administratives.

7.2 Tester deux propriétaires

Pour chaque type de ressource :

  1. créer l’utilisateur A et l’utilisateur B ;
  2. créer une ressource appartenant à A ;
  3. appeler la route avec l’identité de B et l’identifiant de la ressource de A ;
  4. vérifier le statut et l’absence de données sensibles ;
  5. vérifier qu’aucune mutation ou action externe n’a eu lieu ;
  6. répéter pour lecture, mise à jour, suppression et actions secondaires pertinentes.

Selon la politique de confidentialité, l’API peut renvoyer 403 Forbidden ou 404 Not Found. Choisir un comportement cohérent et documenté ; le test ne doit pas imposer une réponse qui divulgue l’existence d’une ressource privée.

7.3 Exemple de test d’intégration

it("n'expose pas la facture d'un autre utilisateur", async () => {
  const owner = await fixtures.user();
  const other = await fixtures.user();
  const invoice = await fixtures.invoice({ ownerId: owner.id });

  const response = await request(app)
    .get(`/api/invoices/${invoice.id}`)
    .set("Authorization", `Bearer ${other.accessToken}`);

  expect([403, 404]).toContain(response.status);
  expect(response.body).not.toHaveProperty("total");
});

Le code est un patron illustratif : les fixtures, l’application de test et le mécanisme d’authentification doivent être ceux du projet. Le test doit exercer le véritable middleware et la véritable règle d’autorisation ; mocker le contrôle d’accès invaliderait la preuve recherchée.

Exercice 7

Créer trois tests négatifs pour une API de documents.

Correction expliquée : utilisateur B lit le document privé de A ; B modifie son contenu ; B télécharge une pièce jointe de A. Pour chaque cas, vérifier le refus, l’absence de fuite du contenu et l’absence de modification ou de téléchargement effectif.

Quiz 7

Pourquoi un UUID ne corrige-t-il pas BOLA ?

Réponse : un UUID peut réduire la facilité de découverte, mais un identifiant obtenu par fuite, partage ou autre route reste exploitable si le serveur n’applique pas les permissions.

Module 8 — Secrets et configuration

8.1 Séparer code et secrets

Ne jamais committer les mots de passe de base, clés privées, tokens de fournisseur, secrets OAuth ou clés de chiffrement. Les variables d’environnement sont un moyen de configuration, pas automatiquement un coffre-fort : leur exposition dépend des processus, outils de déploiement, dumps et journaux.

En production, préférer un gestionnaire de secrets ou un mécanisme de plateforme adapté, avec contrôle d’accès, audit et rotation. Injecter les secrets au démarrage ou à l’exécution selon la plateforme, limiter leur durée et leur portée, et éviter de les copier dans les fichiers de configuration du frontend.

8.2 Valider la configuration au démarrage

Traiter la configuration comme une entrée non fiable : valider présence, format et valeurs autorisées. Échouer tôt si une clé obligatoire manque, sans imprimer sa valeur.

type Config = {
  port: number;
  sessionSecret: string;
};

export function loadConfig(env: NodeJS.ProcessEnv): Config {
  const rawPort = env.PORT ?? "3000";
  const port = Number(rawPort);

  if (!Number.isInteger(port) || port < 1 || port > 65535) {
    throw new Error("PORT must be an integer between 1 and 65535");
  }

  const sessionSecret = env.SESSION_SECRET;
  if (!sessionSecret || sessionSecret.length < 32) {
    throw new Error("SESSION_SECRET is missing or too short");
  }

  return { port, sessionSecret };
}

La longueur minimale est ici une règle illustrative, pas un standard universel de génération de secret. Un secret doit être produit par un générateur cryptographiquement sûr et respecter les recommandations du mécanisme utilisé. Ne pas utiliser une phrase prévisible ou un mot de passe humain comme clé de session.

8.3 Rotation et moindre privilège

Définir la rotation et le remplacement d’urgence des secrets. Vérifier les effets d’une rotation sur les sessions et les tokens actifs. Un compte de base de données applicatif ne devrait pas être superutilisateur ; accorder seulement les opérations nécessaires au runtime. Séparer les secrets de développement, test, préproduction et production.

Exercice 8

Un token d’API apparaît dans un commit Git public. Le supprimer dans le commit suivant suffit-il ?

Correction expliquée : non. Le secret doit être considéré compromis : le révoquer ou le faire tourner immédiatement, examiner les usages, supprimer les copies lorsque possible et rechercher d’autres expositions. Réécrire l’historique peut réduire la propagation mais ne remplace jamais la révocation.

Quiz 8

Une variable d’environnement est-elle toujours un stockage sûr de secrets ?

Réponse : non. Elle évite certains secrets codés en dur mais peut être exposée via les processus, diagnostics, outils de déploiement ou logs. Il faut considérer les propriétés de la plateforme et limiter l’accès.

Module 9 — Limitation d’abus et défense en profondeur

9.1 Rate limiting adapté au risque

Limiter les tentatives sur les points sensibles : connexion, réinitialisation, vérification de code, envoi d’e-mail, recherche coûteuse, export et endpoints publics. Une limite uniquement par adresse IP peut pénaliser des utilisateurs derrière un NAT et être contournée par des réseaux distribués. Combiner plusieurs dimensions selon le risque : compte, IP, session, appareil, clé d’API et coût de l’opération.

En production multi-instance, un compteur uniquement en mémoire ne donne pas une limite globale fiable. Utiliser un stockage partagé adapté, prévoir la panne du système de limitation et documenter le comportement de secours.

9.2 Éviter les protections qui deviennent des vulnérabilités

  • Appliquer des limites de taille de corps et de pagination.
  • Fixer des timeouts aux appels réseau et opérations coûteuses.
  • Contrôler la concurrence et les files de tâches.
  • Utiliser des messages d’erreur qui n’exposent pas les détails internes.
  • Vérifier les origines et les politiques CORS sans les confondre avec l’autorisation.
  • Protéger contre les injections avec des requêtes paramétrées et des validations adaptées.
  • Éviter les redirections ouvertes et les URI de redirection permissives.
  • Ne pas faire confiance à X-Forwarded-For ou autres en-têtes de proxy sauf derrière des proxys explicitement approuvés.

9.3 Journalisation utile

Journaliser les événements de sécurité pertinents : échecs d’authentification, changement de rôle, rotation de secrets, révocation de session et refus anormaux. Ajouter un identifiant de corrélation et limiter les données personnelles. Ne jamais journaliser mot de passe, cookie de session, access token ou refresh token. Protéger également l’accès aux journaux et leur durée de conservation.

Exercice 9

Pourquoi un rate limiter en mémoire est-il insuffisant derrière quatre instances de l’API ?

Correction expliquée : chaque instance maintient un compteur distinct ; un attaquant peut répartir les requêtes entre instances et dépasser la limite totale. Un stockage partagé ou une stratégie distribuée est nécessaire pour appliquer une limite globale cohérente.

Quiz 9

CORS est-il un mécanisme d’autorisation côté serveur ?

Réponse : non. CORS est une politique appliquée par les navigateurs sur certaines interactions cross-origin. L’API doit toujours authentifier et autoriser chaque requête selon ses propres règles.

Module 10 — Dépendances, incidents et procédure de réponse

10.1 Sécurité de la chaîne logicielle

Utiliser des dépendances maintenues, des versions maîtrisées et un lockfile. Examiner les alertes de vulnérabilité, l’origine des paquets et les scripts d’installation. Un audit automatique peut produire des faux positifs ou ne pas détecter une vulnérabilité exploitable dans le contexte : évaluer la gravité, l’exposition et les mitigations, puis documenter les décisions.

Limiter les permissions des pipelines CI et des tokens de publication. Ne pas exposer les secrets de production aux jobs exécutant du code non fiable. Séparer les tâches de vérification des tâches de déploiement.

10.2 Réponse à incident

Préparer un processus avant l’incident :

  1. détecter et confirmer le signal ;
  2. contenir l’exposition (révoquer une clé, désactiver une route ou isoler un composant) ;
  3. préserver les preuves utiles sans copier de secrets ;
  4. mesurer le périmètre et l’impact ;
  5. corriger la cause et vérifier les contrôles ;
  6. restaurer le service de façon contrôlée ;
  7. documenter les actions et prévenir la récurrence.

Ne pas supprimer les journaux pertinents au moment où un incident est détecté. Prévoir qui peut révoquer un secret et comment redéployer en urgence. Les obligations de notification dépendent du contexte juridique et des données concernées ; consulter les responsables compétents.

10.3 Checklist avant livraison

  • Aucun secret ni jeton dans le code, l’historique récent ou les logs.
  • Hachage de mot de passe spécialisé, paramètres évalués.
  • Sessions renouvelées après authentification et invalidées à la déconnexion.
  • Cookies et CSRF adaptés au modèle d’authentification.
  • JWT vérifiés avec algorithmes, émetteur, audience et dates attendus.
  • Flux OAuth/OIDC aligné sur les spécifications et le fournisseur.
  • Permissions vérifiées côté serveur et au niveau de chaque ressource.
  • Tests négatifs avec plusieurs identités.
  • Limites de débit, de taille et de temps configurées.
  • Journaux sans secrets, avec accès contrôlé.
  • Dépendances et pipeline CI examinés.
  • Procédure de rotation et de réponse à incident documentée.

Projet intégrateur — Sécuriser une API multi-utilisateur

Contexte

Une API TypeScript gère des documents privés, leurs propriétaires, des équipes et des sessions. Elle expose les opérations de connexion, de déconnexion, de réinitialisation de mot de passe, de lecture et de modification de documents.

Travaux demandés

  1. Écrire un modèle de menace avec actifs, acteurs, scénarios d’abus et contrôles.
  2. Mettre en place le stockage de mots de passe par une bibliothèque maintenue et documenter les paramètres.
  3. Concevoir une session ou une architecture de tokens, justifier le choix et décrire révocation et expiration.
  4. Protéger les routes et vérifier les permissions sur chaque document.
  5. Valider toutes les entrées et interdire l’assignation de rôle par un utilisateur ordinaire.
  6. Ajouter une limitation des tentatives de connexion et de réinitialisation.
  7. Écrire des tests d’intégration avec deux propriétaires distincts, incluant lecture, modification et téléchargement.
  8. Vérifier qu’aucun secret n’apparaît dans les logs ou réponses publiques.
  9. Documenter la configuration, la rotation des secrets et les procédures de révocation.
  10. Produire une checklist de livraison et les limites connues.

Critères d’acceptation

  • Les mots de passe ne sont jamais stockés en clair ni journalisés.
  • Les jetons et cookies sont vérifiés et expirent selon un contrat explicite.
  • La déconnexion ou la révocation rend la session inutilisable selon le modèle choisi.
  • Un utilisateur ne peut accéder aux ressources privées d’un autre en modifiant un identifiant.
  • Les rôles et permissions sont déterminés côté serveur.
  • Les tests vérifient les refus et l’absence de fuite ou de mutation.
  • Les limites d’abus fonctionnent de manière cohérente dans l’architecture déployée.
  • Les secrets sont séparés du code et une procédure de rotation est documentée.
  • Les tests, validations et limites sont décrits honnêtement ; aucun contrôle non exécuté n’est déclaré réussi.

Synthèse opérationnelle

Authentifier une identité ne suffit pas : chaque opération doit être autorisée sur la ressource concernée. Stocker les mots de passe avec un algorithme spécialisé, choisir entre session et token selon les besoins réels, vérifier strictement les JWT et les flux OIDC, contrôler les secrets et limiter les abus. La preuve la plus importante pour une API multi-utilisateur est un ensemble de tests négatifs qui démontrent qu’une identité ne peut ni lire ni modifier les données d’une autre.
