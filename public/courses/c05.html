C05 — Accès aux données et ORM en TypeScript

Parcours : spécialisation TypeScript / Node.js · Niveau : intermédiaire à avancé · Durée indicative : 12 à 18 heures
Prérequis : TypeScript, API HTTP, SQL relationnel, bases de PostgreSQL et notions de tests backend.

Objectifs pédagogiques

À la fin du cours, l'apprenant doit pouvoir :

  • distinguer SQL direct, query builder et ORM, et justifier un choix technique selon le contexte ;
  • relier types TypeScript, schéma applicatif et contraintes réellement garanties par PostgreSQL ;
  • écrire des requêtes paramétrées et repérer les limites des paramètres SQL ;
  • gérer transactions, erreurs, concurrence et pools de connexions ;
  • organiser les migrations en production sans supposer qu'un retour arrière est toujours automatique ;
  • diagnostiquer les requêtes N+1, choisir une stratégie de chargement et paginer de manière stable ;
  • tester l'intégration avec une vraie base isolée et expliquer le SQL effectivement envoyé.

1. Trois niveaux d'abstraction : SQL direct, query builder et ORM

SQL direct

Le développeur écrit le SQL et contrôle explicitement les jointures, les projections, les clauses de verrouillage et les opérations. C'est adapté aux requêtes complexes, aux besoins de performance mesurés et aux équipes qui maîtrisent le modèle relationnel. Le coût est la gestion des conversions de types, de la composition des requêtes et de la correspondance entre résultats et types TypeScript.

import { Pool } from "pg";

const pool = new Pool({ connectionString: process.env.DATABASE_URL });

interface UserRow {
  id: string;
  email: string;
  created_at: Date;
}

export async function findUserByEmail(email: string): Promise<UserRow | undefined> {
  const result = await pool.query<UserRow>(
    `SELECT id, email, created_at FROM users WHERE email = $1`,
    [email],
  );
  return result.rows[0];
}

Le paramètre $1 protège la valeur contre l'interprétation comme fragment SQL. Le type générique UserRow est une déclaration de l'application : il ne valide pas à lui seul les données renvoyées par le serveur et ne remplace pas les contraintes de la base.

Query builder

Un query builder compose une requête par API TypeScript, tout en exposant généralement les concepts SQL. Il peut améliorer la réutilisation et le typage, mais la requête finale doit toujours être inspectée. Un builder ne rend pas automatiquement sûre une interpolation de SQL brut.

ORM

Un ORM représente tables et relations par des modèles ou schémas de code et automatise une partie des opérations de lecture/écriture. Il peut réduire le code répétitif et offrir des types dérivés du schéma. Il peut aussi masquer le coût des requêtes, produire des chargements inattendus et rendre les opérations SQL spécifiques moins évidentes.

Règle de décision : choisir l'abstraction la plus simple qui couvre les besoins démontrés. Une application peut combiner ORM pour les opérations courantes et SQL explicite pour quelques requêtes spécialisées, à condition d'encadrer cette frontière.

2. Outil de référence du cours : Drizzle ORM

Pour les exemples ORM de ce cours, Drizzle est retenu comme outil de référence pédagogique : sa démarche « SQL-first » conserve une proximité visible avec les tables et les requêtes. Ce choix ne signifie pas qu'il est déjà installé dans le dépôt ou qu'il convient à tous les projets. Prisma reste une option pertinente lorsque l'équipe préfère un modèle de données et un workflow centrés sur son schéma et ses outils générés.

Avant adoption réelle, vérifier les versions compatibles, les pilotes, la stratégie de migrations, les capacités de transaction, le support de PostgreSQL, les exigences d'exploitation et les pratiques de l'équipe. Ne pas installer de dépendance ni migrer un projet existant sans décision explicite.

Exemple schématique Drizzle pour PostgreSQL :

import { pgTable, uuid, varchar, timestamp } from "drizzle-orm/pg-core";

export const users = pgTable("users", {
  id: uuid("id").defaultRandom().primaryKey(),
  email: varchar("email", { length: 320 }).notNull().unique(),
  createdAt: timestamp("created_at", { withTimezone: true }).defaultNow().notNull(),
});

Le schéma décrit les colonnes et contraintes gérées par l'outil. Il faut encore vérifier la migration produite et l'état réel de la base. Une colonne TypeScript string ne garantit pas que la valeur reçue d'une requête HTTP soit un e-mail valide.

3. Modèle, types et contraintes : qui garantit quoi ?

Distinguer trois niveaux :

  1. Validation d'entrée : contrôle les données non fiables à la frontière HTTP (présence, format, longueur, règles métier).
  2. Types TypeScript : détectent certaines incohérences au développement ; ils disparaissent à l'exécution.
  3. Contraintes SQL : garantissent l'intégrité au niveau de la base, y compris lorsque plusieurs processus ou outils écrivent simultanément.

Exemple PostgreSQL :

CREATE TABLE accounts (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  email text NOT NULL UNIQUE,
  balance_cents bigint NOT NULL CHECK (balance_cents >= 0),
  created_at timestamptz NOT NULL DEFAULT now()
);

Utiliser NOT NULL, UNIQUE, CHECK, clés étrangères et contraintes adaptées. Les validations applicatives améliorent les messages d'erreur ; elles ne remplacent pas les contraintes. Attention aux types SQL dont la représentation JavaScript n'est pas exacte pour toutes les valeurs : les entiers 64 bits et les décimaux doivent être traités explicitement.

4. Requêtes paramétrées et SQL dynamique

Ne jamais concaténer une valeur utilisateur dans une requête SQL :

// À proscrire : injection SQL possible.
const sql = `SELECT * FROM users WHERE email = '${email}'`;

Préférer les paramètres du pilote :

const result = await pool.query(
  "SELECT id, email FROM users WHERE email = $1",
  [email],
);

Les paramètres représentent des valeurs, pas des noms de table, colonnes, mots-clés ou directions de tri. Pour une colonne de tri dynamique, sélectionner dans une liste fermée :

const sortColumns = {
  newest: "created_at",
  email: "email",
} as const;

type SortKey = keyof typeof sortColumns;

function getSortColumn(input: string): string {
  if (Object.hasOwn(sortColumns, input)) {
    return sortColumns[input as SortKey];
  }
  return sortColumns.newest;
}

Insérer ensuite uniquement la valeur issue de cette liste contrôlée dans la partie structurelle de la requête ; toutes les données restent paramétrées. Pour SQL brut fourni à un ORM, utiliser son API de requête préparée ou de fragments sûrs et lire sa documentation précise. « Utiliser un ORM » n'est pas une preuve suffisante d'absence d'injection.

5. Transactions, isolation et verrouillage

Une transaction regroupe des opérations qui doivent réussir ou échouer ensemble. Avec node-postgres, toutes les instructions d'une transaction doivent utiliser le même client, pas des appels indépendants au pool.

import type { Pool, PoolClient } from "pg";

export async function transfer(
  pool: Pool,
  fromId: string,
  toId: string,
  amount: number,
): Promise<void> {
  if (!Number.isSafeInteger(amount) || amount <= 0) {
    throw new Error("amount must be a positive safe integer");
  }

  const client: PoolClient = await pool.connect();
  try {
    await client.query("BEGIN");
    const debit = await client.query(
      `UPDATE accounts
       SET balance_cents = balance_cents - $1
       WHERE id = $2 AND balance_cents >= $1
       RETURNING id`,
      [amount, fromId],
    );
    if (debit.rowCount !== 1) throw new Error("Insufficient funds or account missing");

    const credit = await client.query(
      "UPDATE accounts SET balance_cents = balance_cents + $1 WHERE id = $2 RETURNING id",
      [amount, toId],
    );
    if (credit.rowCount !== 1) throw new Error("Destination account missing");
    await client.query("COMMIT");
  } catch (error) {
    try { await client.query("ROLLBACK"); } catch { /* préserver l'erreur initiale */ }
    throw error;
  } finally {
    client.release();
  }
}

Cet extrait illustre la structure, mais ne suffit pas à rendre un transfert complet en production : il faut notamment valider l'existence et la différence des comptes, définir les règles de devise, gérer les deadlocks et les erreurs de sérialisation, prévoir l'idempotence au niveau métier et tester les écritures concurrentes. En production, ne pas relancer aveuglément une opération dont l'issue est incertaine après une coupure réseau.

  • READ COMMITTED : chaque instruction voit un nouvel instantané ; deux lectures dans une transaction peuvent donc différer.
  • REPEATABLE READ : cohérence de l'instantané transactionnel, avec des conflits possibles.
  • SERIALIZABLE : vise l'équivalence à une exécution séquentielle, mais peut annuler une transaction ; l'application doit prévoir une reprise bornée et sûre.
  • Verrouillage (SELECT ... FOR UPDATE) : utile pour certaines règles concurrentes, mais peut créer attente et deadlock. Toujours définir un ordre de prise de verrous et des délais adaptés.

Ne pas augmenter l'isolation par réflexe : identifier d'abord l'invariant métier et le mécanisme nécessaire.

6. Migrations versionnées et déploiements

Une migration est un changement explicite, versionné et relu du schéma de données. Elle doit être reproductible, ordonnée et testée sur une base représentative.

Séquence recommandée

  1. Créer une migration dans le dépôt et relire le SQL généré.
  2. L'appliquer à une base temporaire vide, puis à une copie représentative des données si possible.
  3. Vérifier contraintes, index, durée, verrouillage et compatibilité avec l'application en production.
  4. Déployer selon une stratégie compatible avec les versions applicatives en circulation.
  5. Vérifier les métriques et conserver une procédure de récupération testée.

Pour les changements risqués, utiliser expand/contract : ajouter d'abord la nouvelle structure compatible, déployer le code qui peut utiliser les deux formes, migrer les données, puis retirer l'ancienne structure dans un déploiement ultérieur. Ajouter une colonne NOT NULL ou construire un index sur une grande table peut nécessiter une stratégie spécifique.

Un « down migration » ne rend pas toujours une opération réversible : une suppression ou une transformation avec perte peut détruire l'information. Préférer souvent une migration corrective en avant, avec sauvegarde et restauration éprouvées. Une sauvegarde non testée n'est pas une stratégie de reprise validée.

7. Relations, N+1, chargement et pagination

Le problème N+1 apparaît lorsqu'une requête charge une collection puis exécute une requête supplémentaire pour chaque élément. Le code peut sembler simple tout en multipliant le nombre d'allers-retours.

Approches possibles :

  • jointure SQL lorsque les relations et la cardinalité sont maîtrisées ;
  • chargement groupé (batch) des entités associées ;
  • chargement explicite par besoin fonctionnel ;
  • eager loading d'un ORM, à surveiller car plusieurs collections jointes peuvent multiplier les lignes retournées.

Pour toute requête importante, examiner le SQL généré, le nombre de requêtes, les lignes transférées et le plan d'exécution. Utiliser EXPLAIN et, dans un environnement contrôlé, EXPLAIN (ANALYZE, BUFFERS) ; ANALYZE exécute effectivement la requête.

Pagination par offset : simple pour les petites listes, mais le coût augmente parfois avec les offsets élevés et les insertions concurrentes peuvent déplacer les pages. Pour de grandes listes, préférer souvent une pagination par curseur fondée sur un ordre stable et unique :

SELECT id, created_at, title
FROM posts
WHERE (created_at, id) < ($1, $2)
ORDER BY created_at DESC, id DESC
LIMIT $3;

L'index doit correspondre au filtre et à l'ordre de la requête. Le curseur doit être validé, borné et lié au bon filtre/ordre ; ne pas exposer des données sensibles dans un curseur non protégé.

8. Pool de connexions et erreurs

Un pool réutilise des connexions coûteuses à établir. Il faut définir et mesurer : taille maximale, temps d'attente, délais de requête, durée de vie des connexions et comportement en arrêt du processus. Une taille excessive par instance peut dépasser la capacité du serveur lorsque plusieurs réplicas démarrent.

  • Toujours libérer un client acquis avec pool.connect() dans finally.
  • Fermer le pool proprement lors de l'arrêt contrôlé du processus.
  • Fixer des délais adaptés et surveiller le nombre de connexions actives, l'attente, les timeouts et les erreurs.
  • Ne pas exposer les chaînes de connexion, paramètres sensibles ou requêtes contenant des secrets dans les journaux.
  • Classer les erreurs : validation métier, contrainte d'intégrité, timeout, connexion perdue, deadlock ou échec de sérialisation. Ne pas renvoyer les messages SQL bruts aux clients HTTP.
  • Ne relancer que les erreurs transitoires identifiées, avec un nombre de tentatives limité, temporisation et garantie d'idempotence.

Un pool applicatif et un pooler externe comme PgBouncer répondent à des besoins distincts ; les modes de pooling peuvent imposer des contraintes sur les sessions et les instructions préparées. Vérifier la configuration utilisée plutôt que supposer qu'elle est transparente.

9. Dépôts typés et frontières d'architecture

Le dépôt encapsule l'accès aux données, sans devenir une couche de magie. Il doit exprimer des opérations utiles au domaine, pas nécessairement reproduire chaque méthode CRUD générique.

export interface UserSummary {
  id: string;
  email: string;
}

export interface UserRepository {
  findByEmail(email: string): Promise<UserSummary | null>;
}

export class PgUserRepository implements UserRepository {
  constructor(private readonly pool: Pool) {}

  async findByEmail(email: string): Promise<UserSummary | null> {
    const result = await this.pool.query<UserSummary>(
      "SELECT id, email FROM users WHERE email = $1",
      [email],
    );
    return result.rows[0] ?? null;
  }
}

Le service métier dépend de l'interface lorsque cette séparation facilite réellement les tests, le domaine ou le remplacement d'adaptateur. Éviter une interface par classe sans bénéfice concret. Les erreurs doivent être converties à une frontière connue ; une couche ne doit pas masquer les causes utiles au diagnostic.

Attention : les interfaces TypeScript sont effacées à l'exécution. Un type de retour ne valide ni une réponse externe, ni une ligne issue d'une base compromise ou d'une migration inattendue.

10. Tests d'intégration et cohérence schéma/code

Les tests unitaires peuvent tester les règles métier avec un dépôt simulé, mais ils ne prouvent pas que SQL, contraintes, migrations, transactions ou types du pilote fonctionnent ensemble.

Une suite d'intégration utile :

  • démarre une base isolée de la même famille/version que la cible ;
  • applique toutes les migrations depuis un état vide ;
  • insère des données représentatives et vérifie les contraintes ;
  • teste les chemins de succès et d'échec d'une transaction ;
  • provoque des accès concurrents sur les invariants critiques ;
  • vérifie la pagination, les filtres et les limites de taille ;
  • détruit ou réinitialise l'environnement de test sans toucher aux données réelles.

Ne pas utiliser une base de production pour les tests. Ne pas affirmer qu'une suite a réussi si elle n'a pas été exécutée. Les tests peuvent nécessiter Docker ou un service PostgreSQL disponible ; ces prérequis doivent être explicites.

11. Atelier comparatif : même opération, deux implémentations

Implémenter une opération de lecture paginée des publications d'un auteur :

  1. une version avec SQL paramétré via node-postgres ;
  2. une version avec Drizzle ORM ;
  3. des tests d'intégration couvrant pagination, auteur inconnu, paramètres invalides et ordre stable.

Pour chaque version, fournir : SQL final ou généré, nombre de requêtes, plan d'exécution, contraintes attendues, cas d'erreur et compromis de maintenance. Les deux versions doivent partager les mêmes critères de correction.

Exercices corrigés

Exercice 1 — Identifier la garantie

Question : une interface déclare age: number. Est-ce suffisant pour garantir que la base ne contiendra jamais un âge négatif ?

Correction : non. TypeScript ne s'exécute pas comme validation des données entrantes. Valider à la frontière applicative et ajouter une contrainte SQL CHECK (age >= 0) si l'invariant s'applique aux données stockées.

Exercice 2 — Corriger une injection

Question : corriger SELECT * FROM users WHERE email = '${email}'.

Correction : utiliser pool.query("SELECT id, email FROM users WHERE email = $1", [email]). Pour un nom de colonne dynamique, utiliser une liste blanche ; un paramètre ne peut pas remplacer un identifiant SQL.

Exercice 3 — Transaction

Question : pourquoi ne faut-il pas appeler pool.query("BEGIN"), puis deux fois pool.query(...), puis pool.query("COMMIT") en supposant que toutes les requêtes utilisent la même connexion ?

Correction : chaque appel au pool peut emprunter une connexion différente. Acquérir un client, effectuer toutes les instructions transactionnelles sur ce client, puis le libérer dans finally.

Exercice 4 — N+1

Question : une page affiche 40 auteurs et le code lance une requête de livres par auteur. Quel est le problème et une solution ?

Correction : le nombre de requêtes croît avec le nombre d'auteurs (1 + 40 dans cet exemple). Charger les livres par lots avec une requête filtrée sur les identifiants, ou faire une jointure et regrouper les résultats, après mesure et vérification de la cardinalité.

Exercice 5 — Retour arrière

Question : une migration supprime une colonne contenant des données. Un script down qui recrée une colonne vide restaure-t-il l'état précédent ?

Correction : non. La structure revient, mais pas les données perdues. Une restauration nécessite une sauvegarde valide ou une migration corrective alimentée par une source conservée.

Exercice 6 — Pagination

Question : pourquoi ORDER BY created_at DESC LIMIT 20 n'est-il pas un ordre totalement stable si plusieurs lignes partagent le même timestamp ?

Correction : les lignes à timestamp égal peuvent apparaître dans un ordre différent. Ajouter un critère unique, par exemple ORDER BY created_at DESC, id DESC, et inclure ces deux valeurs dans le curseur.

Exercice 7 — Pool

Question : que doit-on garantir après const client = await pool.connect() ?

Correction : libérer le client dans un bloc finally, même en cas d'exception. Pour une transaction, exécuter ROLLBACK lorsque nécessaire, sans perdre l'erreur initiale.

Exercice 8 — ORM

Question : un ORM est-il une garantie que chaque page ne déclenche qu'une requête SQL ?

Correction : non. Les stratégies de chargement peuvent générer plusieurs requêtes, des N+1 ou des jointures volumineuses. Inspecter le SQL, compter les requêtes et tester les cas représentatifs.

Exercice 9 — Test de cohérence

Question : les tests unitaires passent mais la migration a oublié une contrainte UNIQUE. Quelle catégorie de test aurait dû détecter le problème ?

Correction : un test d'intégration appliquant les migrations sur une base isolée puis tentant deux insertions conflictuelles. Un mock du dépôt ne vérifie pas le schéma réel.

Quiz avec explications

  1. Les types TypeScript valident-ils les données à l'exécution ? Non : ils guident la compilation ; il faut valider les entrées non fiables.
  2. Un paramètre SQL peut-il remplacer ORDER BY ${column} ? Non : les paramètres portent sur les valeurs. Les identifiants dynamiques doivent provenir d'une liste contrôlée ou d'une API sûre.
  3. Toutes les requêtes transactionnelles doivent-elles partager un client ? Oui, avec node-postgres ; sinon elles peuvent être exécutées sur des connexions différentes.
  4. Une transaction sérialisable ne peut-elle jamais échouer ? Faux : PostgreSQL peut annuler une transaction pour préserver la sérialisabilité ; la reprise doit être bornée et sûre.
  5. Une migration inverse restaure-t-elle toujours les données ? Non : les changements destructifs peuvent être irréversibles sans sauvegarde ou copie des données.
  6. Un ORM élimine-t-il N+1 ? Non : il peut aider, mais la stratégie de chargement doit être contrôlée.
  7. Pourquoi ajouter une clé secondaire unique à l'ordre paginé ? Pour stabiliser l'ordre lorsque la colonne principale comporte des égalités.
  8. Pourquoi libérer le client dans finally ? Pour éviter de perdre des connexions du pool en cas de succès comme d'échec.
  9. Les tests unitaires prouvent-ils que les migrations s'appliquent ? Non : il faut une validation sur une vraie base de test.

Projet intégrateur

Construire la couche de données d'une API de publications et de comptes avec TypeScript et PostgreSQL. Comparer SQL direct et Drizzle sur une opération représentative.

Fonctionnalités minimales

  • schéma versionné avec clés primaires, clés étrangères, contraintes NOT NULL, UNIQUE et CHECK pertinentes ;
  • dépôt typé et service métier séparés sans abstraction superflue ;
  • paramètres SQL sûrs pour toutes les valeurs ;
  • transaction pour une opération multi-écriture avec gestion des échecs ;
  • pagination stable et bornée ;
  • migrations testées depuis une base vide ;
  • tests d'intégration pour contraintes, erreurs, pagination et concurrence pertinente ;
  • note d'analyse du SQL produit et de ses plans d'exécution.

Critères d'acceptation

  • Aucune valeur utilisateur n'est concaténée dans le SQL.
  • Les invariants essentiels sont protégés par la base, pas uniquement par TypeScript.
  • Les clients acquis au pool sont toujours libérés.
  • Les écritures qui doivent être atomiques sont transactionnelles.
  • Les erreurs de contrainte et de concurrence sont gérées sans divulguer de détails internes au client HTTP.
  • La pagination a un ordre stable, une limite maximale et des paramètres validés.
  • Le nombre de requêtes et le SQL généré sont documentés pour le cas étudié.
  • Les migrations et tests d'intégration sont reproductibles sur une base isolée.
  • Les limites de reprise et de retour arrière sont explicitées.
