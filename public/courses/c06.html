Architecture backend TypeScript

Parcours : spécialisation TypeScript / Node.js · Niveau : intermédiaire à avancé · Durée indicative : 14 à 20 heures
Prérequis : C01 HTTP et réseaux, C02 API HTTP, C03 tests backend, C04 sécurité web, C05 accès aux données ; modules ES et TypeScript strict.

Objectifs pédagogiques

À la fin du cours, l'apprenant doit pouvoir :

  • structurer un monolithe modulaire par domaines et responsabilités, sans créer de couches mécaniques inutiles ;
  • distinguer domaine métier, cas d'utilisation, adaptateurs HTTP et persistance ;
  • orienter les dépendances vers les règles métier et injecter les ports nécessaires ;
  • placer la validation et la traduction des erreurs aux frontières adaptées ;
  • charger une configuration typée et échouer tôt lorsqu'elle est invalide ;
  • gérer correctement les transactions traversant plusieurs opérations métier ;
  • tester les règles métier sans serveur HTTP ni base réelle, puis tester les adaptateurs séparément ;
  • documenter les décisions structurantes avec des ADR courtes.

Module 1 — Architecture : gérer les responsabilités

1.1 L'architecture sert les changements attendus

L'architecture décrit les frontières, les responsabilités, les dépendances et les décisions difficiles à inverser. Elle ne se mesure pas au nombre de dossiers, d'interfaces ou de frameworks. Une petite API peut être correctement structurée sans microservices, bus d'événements ni conteneur d'injection sophistiqué.

Une décision d'architecture devrait répondre à un risque ou à un coût concret : règles métier difficiles à tester, dépendance à un fournisseur qui change, accès aux données dispersé, transactions incohérentes ou responsabilités mêlées dans les contrôleurs.

1.2 Couplage et cohésion

  • Cohésion : les éléments d'un module contribuent à une responsabilité liée.
  • Couplage : le degré de connaissance qu'un module possède des détails d'un autre.
  • Frontière : contrat explicite par lequel deux parties collaborent.

Le but n'est pas de supprimer toute dépendance, mais de rendre les dépendances utiles, explicites et stables. Un module métier peut dépendre d'une interface de dépôt ; il ne devrait pas devoir importer Express ou le client PostgreSQL pour appliquer une règle métier.

Exemple

// Domaine : aucune dépendance au transport HTTP.
export type OrderStatus = "draft" | "confirmed";

export interface Order {
  readonly id: string;
  readonly totalCents: number;
  readonly status: OrderStatus;
}

export function confirmOrder(order: Order): Order {
  if (order.status !== "draft") {
    throw new Error("ORDER_NOT_CONFIRMABLE");
  }
  if (!Number.isSafeInteger(order.totalCents) || order.totalCents <= 0) {
    throw new Error("ORDER_TOTAL_INVALID");
  }
  return { ...order, status: "confirmed" };
}

Le code illustre une règle pure. Dans une application complète, on préférera souvent des erreurs métier dédiées plutôt que des chaînes génériques ; l'exemple garde le domaine minimal pour montrer la frontière.

Exercice 1. Une route Express vérifie le stock, calcule le total, écrit trois tables et construit la réponse HTTP. Identifiez quatre responsabilités distinctes.

Corrigé. Le contrôleur traduit HTTP et valide la forme de la requête ; le cas d'utilisation orchestre l'opération ; le domaine porte les invariants et calculs métier ; les ports/adaptateurs d'infrastructure lisent et écrivent les données. La transaction est définie autour de l'unité métier cohérente, pas au gré des appels HTTP.

Module 2 — Monolithe modulaire et frontières de domaine

2.1 Commencer par les capacités métier

Un monolithe modulaire est une application déployée comme une unité, organisée en modules aux responsabilités et contrats explicites. Il évite le coût réseau et opérationnel des microservices tout en permettant de limiter le couplage interne.

Découper selon les capacités métier — par exemple orders, catalog, accounts — est souvent plus robuste que de placer toute l'application dans des dossiers globaux controllers, services, repositories. Le découpage par couches reste possible à l'intérieur de chaque module ; la frontière de domaine reste visible au premier niveau.

src/
  modules/
    orders/
      domain/
      application/
      infrastructure/
      http/
    catalog/
      domain/
      application/
      infrastructure/
      http/
  shared/
    errors/
    observability/
  app.ts
  main.ts

Cette structure est une proposition pédagogique, pas une obligation à recopier. Un module petit peut réunir certains fichiers si les responsabilités restent compréhensibles. shared doit contenir du code réellement transversal, pas un dépotoir de fonctions difficiles à attribuer.

2.2 Protéger les frontières

Le module orders ne devrait pas modifier directement les tables internes de catalog. Il appelle un contrat public ou reçoit les données nécessaires par un cas d'utilisation explicite. Éviter les imports profonds qui contournent l'API d'un module.

Une frontière n'exige pas systématiquement un package npm séparé. Dans un dépôt simple, les règles d'import, l'organisation des dossiers et des tests d'architecture légers peuvent suffire.

Exercice 2. Deux équipes modifient régulièrement le même fichier common.ts, qui contient validation de commandes, formatage de dates et accès SQL. Proposez une première action de découpage.

Corrigé. Relever les consommateurs et responsabilités, puis déplacer chaque comportement vers le module qui en possède la règle. Garder dans shared uniquement les abstractions véritablement communes. Ne pas créer trois packages ou services déployables avant d'avoir un besoin démontré.

Module 3 — Architecture en couches et architecture hexagonale

3.1 Les couches

  • Domaine : règles et invariants métier indépendants des détails techniques.
  • Application : cas d'utilisation, orchestration et politiques de transaction.
  • Adaptateurs entrants : HTTP, tâche planifiée ou message ; ils traduisent l'entrée vers un cas d'utilisation.
  • Adaptateurs sortants : base de données, service externe, système de fichiers ; ils implémentent les contrats nécessaires.
  • Composition : point où les implémentations concrètes sont assemblées.

L'architecture hexagonale (ports et adaptateurs) met l'accent sur la séparation entre le cœur applicatif et ses interactions. Les couches sont un moyen de matérialiser cette séparation, pas une obligation de multiplier les fichiers.

3.2 Direction des dépendances

Les détails techniques dépendent des contrats dont le cœur a besoin, plutôt que le cœur ne dépende de tous les détails. Le domaine n'importe pas Express, pg, Drizzle ou un SDK externe. Le contrôleur peut dépendre d'un cas d'utilisation ; l'adaptateur PostgreSQL peut implémenter un port défini côté application.

export interface OrderRepository {
  findById(id: string): Promise<Order | undefined>;
  save(order: Order): Promise<void>;
}

export interface TransactionRunner {
  run<T>(work: (repositories: { orders: OrderRepository }) => Promise<T>): Promise<T>;
}

Le contrat ci-dessus est schématique : dans une implémentation réelle, il faut garantir que le dépôt fourni dans work utilise la même transaction que les autres écritures. Exposer un simple transaction() sans clarifier la portée de ses dépôts peut donner une fausse impression de cohérence.

Exercice 3. Un fichier de domaine importe Request depuis Express pour accéder à req.user. Quelle est la violation et comment la corriger ?

Corrigé. Le domaine dépend du transport et de son modèle de requête. L'adaptateur HTTP extrait l'identité authentifiée, puis transmet au cas d'utilisation un contexte applicatif explicite (par exemple actorId) après les contrôles de validation et d'autorisation requis.

Module 4 — Ports, adaptateurs et injection de dépendances

4.1 Injection sans conteneur

L'injection de dépendances consiste à fournir une collaboration depuis l'extérieur au lieu de la construire à l'intérieur du module. Elle peut se faire par paramètres de fonction, constructeur ou fabrique. Un conteneur automatique n'est pas nécessaire pour quelques dépendances.

export interface Clock {
  now(): Date;
}

export interface OrderStore {
  save(order: Order): Promise<void>;
}

export function createPlaceOrder(deps: {
  store: OrderStore;
  clock: Clock;
}) {
  return async (input: { id: string; totalCents: number }): Promise<Order> => {
    if (!Number.isSafeInteger(input.totalCents) || input.totalCents <= 0) {
      throw new Error("ORDER_TOTAL_INVALID");
    }
    const order: Order = {
      id: input.id,
      totalCents: input.totalCents,
      status: "draft",
    };
    // Le temps est injecté pour être contrôlable en test, même si cette
    // version minimale ne stocke pas encore createdAt.
    deps.clock.now();
    await deps.store.save(order);
    return order;
  };
}

Les ports doivent représenter des besoins métier ou applicatifs utiles, pas recopier toutes les méthodes d'un fournisseur. Une interface par classe concrète, sans variation ou besoin de substitution, ajoute parfois plus de maintenance que de valeur.

4.2 Composition à la racine

Le point de composition crée les adaptateurs concrets puis injecte les dépendances. Le code métier n'a pas besoin de savoir si OrderStore est implémenté par PostgreSQL, un fake en test ou un service externe.

// Pseudocode d'assemblage : les constructeurs concrets dépendent
// de bibliothèques et de variables d'environnement propres au projet.
const store = createPostgresOrderStore(pool);
const clock = { now: () => new Date() };
const placeOrder = createPlaceOrder({ store, clock });
const app = createHttpApp({ placeOrder });

Exercice 4. Faut-il injecter Array.map derrière une interface pour tester une transformation simple ?

Corrigé. Non. Une dépendance stable et intrinsèque au langage ne justifie pas une abstraction. Injecter une horloge, un générateur d'identifiants, un stockage ou un fournisseur externe peut en revanche améliorer le contrôle et l'isolation.

Module 5 — Domaine, cas d'utilisation et validation

5.1 TypeScript ne valide pas les entrées à l'exécution

Une annotation comme input: CreateOrderInput n'empêche pas un client HTTP d'envoyer un objet invalide. Les données externes sont unknown jusqu'à validation. Le contrôleur ou un adaptateur valide leur forme ; le domaine protège les invariants qui doivent rester vrais quelle que soit la provenance de l'appel.

Il faut distinguer :

  1. Validation de forme : JSON, champs requis, types primitifs, longueurs et formats.
  2. Règle métier : transition d'état autorisée, montant positif, quantité disponible.
  3. Contrainte de persistance : unicité, clé étrangère, NOT NULL, transaction.
  4. Autorisation : l'acteur a-t-il le droit d'effectuer cette action sur cette ressource ?

Ces contrôles sont complémentaires. La validation HTTP ne remplace pas une contrainte unique en base, et un type TypeScript ne remplace ni la validation ni l'autorisation.

5.2 Cas d'utilisation explicite

Un cas d'utilisation orchestre une action qui a un sens pour le métier : confirmer une commande, inscrire un utilisateur, rembourser un paiement. Il reçoit des données déjà décodées, appelle le domaine et les ports requis, puis renvoie un résultat applicatif. Il ne devrait pas construire une réponse Response HTTP.

type ConfirmOrderResult =
  | { ok: true; order: Order }
  | { ok: false; reason: "NOT_FOUND" | "INVALID_STATE" };

export async function confirmOrderUseCase(
  id: string,
  repository: OrderRepository,
): Promise<ConfirmOrderResult> {
  const order = await repository.findById(id);
  if (!order) return { ok: false, reason: "NOT_FOUND" };
  if (order.status !== "draft") return { ok: false, reason: "INVALID_STATE" };
  const confirmed = { ...order, status: "confirmed" as const };
  await repository.save(confirmed);
  return { ok: true, order: confirmed };
}

Cette version simplifiée illustre la séparation ; si plusieurs lectures/écritures doivent être atomiques, le cas d'utilisation doit utiliser un contrat transactionnel adapté et gérer la concurrence. Vérifier uniquement l'état lu en mémoire ne prévient pas deux confirmations simultanées.

Exercice 5. Une requête fournit quantity: -2. Où placer les contrôles ?

Corrigé. Le schéma d'entrée rejette une valeur de forme ou de plage invalide ; le domaine ou le cas d'utilisation protège également l'invariant métier pour les autres voies d'entrée ; la base conserve les contraintes persistantes adaptées, par exemple CHECK (quantity > 0). L'autorisation est vérifiée séparément.

Module 6 — Erreurs aux frontières et configuration typée

6.1 Erreurs internes et erreurs publiques

Le domaine peut émettre des erreurs métier identifiables ou retourner une union de résultats. L'adaptateur HTTP traduit les résultats en statuts et formats de réponse. Une erreur de base de données ne doit pas être renvoyée telle quelle au client : elle peut révéler le schéma, les requêtes ou des données sensibles.

Définir une correspondance cohérente, par exemple : entrée invalide → 400 ou 422 selon le contrat ; ressource absente → 404 ; absence d'autorisation → 403 ou 404 selon la politique de divulgation ; conflit métier → 409 ; erreur inattendue → 500 avec identifiant de corrélation. Le choix doit rester cohérent avec l'API documentée.

type PublicError = {
  status: number;
  code: string;
  message: string;
};

function toPublicError(error: unknown): PublicError {
  if (error instanceof Error && error.message === "ORDER_NOT_FOUND") {
    return { status: 404, code: "ORDER_NOT_FOUND", message: "Commande introuvable." };
  }
  return { status: 500, code: "INTERNAL_ERROR", message: "Une erreur inattendue est survenue." };
}

En production, préférer des classes d'erreurs ou codes discriminés plutôt que comparer des messages ; ne jamais exposer stack trace, secrets, SQL ou corps sensibles dans la réponse. Journaliser les détails utiles avec une politique de masquage et un identifiant de corrélation.

6.2 Configuration au démarrage

Lire les variables d'environnement une fois à la frontière, vérifier leur présence et leur format, puis transmettre un objet de configuration validé. Éviter de lire process.env partout dans le domaine et de convertir silencieusement une valeur absente en chaîne vide.

interface AppConfig {
  port: number;
  databaseUrl: string;
  nodeEnv: "development" | "test" | "production";
}

export function loadConfig(env: NodeJS.ProcessEnv): AppConfig {
  const port = Number(env.PORT ?? "3000");
  const databaseUrl = env.DATABASE_URL;
  const nodeEnv = env.NODE_ENV ?? "development";

  if (!Number.isInteger(port) || port < 1 || port > 65535) {
    throw new Error("Invalid PORT configuration");
  }
  if (!databaseUrl) throw new Error("DATABASE_URL is required");
  if (nodeEnv !== "development" && nodeEnv !== "test" && nodeEnv !== "production") {
    throw new Error("Invalid NODE_ENV configuration");
  }
  return { port, databaseUrl, nodeEnv };
}

Ce type utilise NodeJS.ProcessEnv, qui suppose les types Node.js présents dans le projet d'exemple. Le dépôt pédagogique ne reçoit aucune dépendance supplémentaire pour ce cours. Ne pas journaliser la chaîne de connexion complète.

Exercice 6. L'application démarre même si DATABASE_URL manque et échoue au premier appel utilisateur. Quelle amélioration appliquer ?

Corrigé. Valider la configuration avant d'ouvrir le serveur et échouer avec un message d'exploitation explicite, sans secret. Le démarrage ne doit être déclaré prêt qu'après les contrôles requis, par exemple une connexion initiale si la stratégie opérationnelle l'impose.

Module 7 — Transactions et cohérence métier

7.1 La transaction suit l'unité métier

Si confirmer une commande exige de réserver du stock et d'enregistrer un événement local, l'ensemble doit être cohérent. Une transaction courte peut encapsuler les écritures liées. Le cas d'utilisation exprime la frontière métier ; l'adaptateur de persistance garantit qu'elles partagent la même connexion et la même transaction.

Ne pas ouvrir une transaction dans un middleware HTTP sans rapport avec le cas d'utilisation. Ne pas laisser une transaction ouverte pendant un appel réseau lent. Pour une opération distribuée entre PostgreSQL et un fournisseur de paiement, une transaction SQL ne rend pas les deux systèmes atomiques : utiliser un workflow explicite, idempotence, états intermédiaires, compensation ou outbox selon les besoins.

7.2 Concurrence

Deux requêtes peuvent lire simultanément un stock de 1 puis tenter de réserver chacune une unité. La logique « lire puis décrémenter » n'est pas suffisante si elle n'est pas protégée. Selon le modèle, utiliser une mise à jour conditionnelle atomique, des verrous, des contraintes ou un niveau d'isolation adapté, puis traiter les conflits et les tentatives répétées.

UPDATE inventory
SET quantity = quantity - $1
WHERE sku = $2 AND quantity >= $1
RETURNING quantity;

Le code applicatif doit vérifier si une ligne a été retournée et interpréter l'absence comme un échec de réservation selon le contrat métier. Le contrôle de quantity > 0 doit aussi être assuré par la validation et/ou une contrainte adaptée. Le SQL ne doit pas être assemblé par concaténation de données utilisateur.

Exercice 7. Une confirmation écrit la commande puis appelle un prestataire de paiement dans une transaction SQL maintenue ouverte pendant 20 secondes. Quel est le problème et quelle approche proposer ?

Corrigé. La transaction longue retient verrous et connexions et peut augmenter les conflits. Séparer l'orchestration de paiement de la transaction locale, utiliser une clé d'idempotence côté prestataire, des états métier explicites et un mécanisme de reprise/compensation. Ne pas prétendre qu'une transaction SQL couvre le service externe.

Module 8 — Tests, observabilité et fiabilité

8.1 Tester chaque frontière au niveau utile

  • Domaine : tests unitaires rapides sur les invariants et transitions.
  • Application : tests avec ports contrôlés pour vérifier l'orchestration, les refus et les scénarios d'erreur.
  • Adaptateur HTTP : tests de contrat sur statuts, schémas et traduction d'erreurs.
  • Persistance : tests d'intégration sur le moteur réel, notamment transactions, contraintes et concurrence.
  • Système : quelques tests bout en bout sur les parcours critiques.

Les fakes doivent préserver les propriétés utiles du contrat ; ils ne simulent pas fidèlement toutes les contraintes de PostgreSQL. Les tests unitaires ne prouvent donc pas la correction des transactions ou des migrations.

8.2 Observabilité aux frontières

Utiliser des journaux structurés, des métriques et des traces adaptés au service. Propager un identifiant de corrélation sans le confondre avec une identité authentifiée. Ne pas journaliser mots de passe, jetons, cookies, données personnelles inutiles ou chaînes de connexion. Les erreurs doivent indiquer le contexte opérationnel utile sans exposer les détails internes au client.

Exercice 8. Un test unitaire avec un dépôt fake passe, mais une contrainte d'unicité échoue en production. Pourquoi ?

Corrigé. Le fake ne reproduisait pas la contrainte réelle, ni éventuellement la concurrence. Ajouter un test d'intégration sur PostgreSQL et traiter explicitement le conflit d'unicité ; ne pas faire du fake une preuve de comportement du moteur.

Module 9 — Découpage proportionné, anti-patterns et ADR

9.1 Quand créer un module ou un service ?

Créer une frontière quand elle réduit un coût réel : règle métier cohérente, équipe responsable, dépendance variable, politique de sécurité distincte, besoin de test ou rythme d'évolution différent. Ne pas extraire un service distant seulement parce qu'un dossier devient volumineux. Les microservices introduisent réseau, pannes partielles, déploiements coordonnés, observabilité distribuée et cohérence éventuelle.

Signaux d'architecture à revoir :

  • contrôleurs contenant règles métier et SQL ;
  • dépendances circulaires entre domaines ;
  • shared contenant des règles métier de tous les domaines ;
  • interfaces créées sans besoin de substitution ni frontière claire ;
  • services génériques avec de nombreux paramètres booléens ;
  • exceptions techniques traduites en succès silencieux ;
  • transactions et autorisations dispersées dans plusieurs couches.

9.2 ADR — Architecture Decision Record

Une ADR est une note courte qui conserve le contexte et la raison d'une décision. Modèle recommandé :

# ADR-0001 — Organiser l'API en monolithe modulaire

- Statut : accepté
- Date : AAAA-MM-JJ

## Contexte
Quel problème et quelles contraintes motivent la décision ?

## Décision
Quelle option est retenue, avec quel périmètre ?

## Alternatives considérées
Quelles options réalistes ont été comparées et pourquoi écartées ?

## Conséquences
Quels bénéfices, coûts, risques et conditions de réévaluation ?

Une ADR n'est ni un document marketing ni une garantie que le choix sera éternel. Si le contexte change, une nouvelle ADR peut remplacer l'ancienne tout en gardant l'historique.

Exercice 9. Une équipe souhaite passer en microservices parce que son monolithe a 30 modules et que le déploiement est encore manuel. Que doit-elle analyser avant de décider ?

Corrigé. Identifier le problème réel : frontières mal définies, équipes en conflit, besoin de déploiements indépendants, charge différenciée, contraintes de sécurité ou limites techniques. Vérifier d'abord les modules, le pipeline et la propriété du code. Le nombre de modules seul ne justifie pas des services distribués ; documenter les options et coûts dans une ADR.

Module 10 — Projet intégrateur

Sujet

Transformer une API de commandes simple en monolithe modulaire TypeScript. Le domaine comporte au minimum commandes et catalogue. L'application doit créer et confirmer une commande, vérifier la disponibilité, persister les données et exposer une API HTTP. Les règles métier ne doivent pas dépendre directement du framework HTTP ou du fournisseur de base de données.

Livrables attendus

  1. Arborescence organisée par domaines et responsabilités, avec frontières documentées.
  2. Domaine avec types et invariants testés.
  3. Cas d'utilisation injectant des ports explicites.
  4. Adaptateurs HTTP et persistance distincts du domaine.
  5. Configuration validée au démarrage, sans secret dans les journaux.
  6. Stratégie transactionnelle et traitement explicite de la concurrence.
  7. Tests unitaires, tests d'adaptateur et tests d'intégration adaptés au risque.
  8. Au moins une ADR décrivant la structure retenue et une alternative écartée.
  9. README précisant les commandes réellement vérifiées et les limites de validation.

Critères d'acceptation

  • Les règles métier sont testables sans serveur HTTP ni base réelle.
  • Le domaine n'importe pas le framework HTTP, le pilote SQL ou l'ORM.
  • Les contrôleurs traduisent le protocole et délèguent les décisions métier.
  • Les frontières de module sont compréhensibles et aucun cycle injustifié n'est introduit.
  • Les entrées externes sont validées à l'exécution ; les invariants critiques sont aussi protégés au niveau métier et persistance.
  • Les erreurs publiques ne divulguent ni stack trace ni détails internes sensibles.
  • Les variables requises sont validées avant que le service soit déclaré prêt.
  • Les opérations multi-écritures ont une stratégie transactionnelle explicite ; les effets externes ont une stratégie de reprise/idempotence.
  • Les tests couvrent au minimum succès, refus métier, absence de ressource, erreur de dépendance et cas de concurrence pertinent.
  • Les décisions structurantes et les compromis sont documentés.

Quiz de validation — 9 questions expliquées

  1. Quelle est la première raison de séparer le domaine du contrôleur HTTP ?
    Réponse : protéger les règles métier des détails du transport et permettre leur test sans serveur. Explication : la séparation améliore aussi la réutilisation, mais le bénéfice principal est une dépendance moins fragile.
  2. Un monolithe modulaire doit-il être déployé en plusieurs unités ?
    Réponse : non. Explication : ses modules partagent un processus et un déploiement ; leur frontière est logique et technique, pas nécessairement réseau.
  3. Dans quel sens orienter les dépendances en architecture hexagonale ?
    Réponse : les détails implémentent les ports dont le cœur a besoin. Explication : le cœur n'importe pas les SDK ou frameworks d'infrastructure.
  4. Faut-il créer une interface pour chaque classe ?
    Réponse : non. Explication : un port se justifie par une frontière, un besoin de substitution ou un contrat utile, pas par une règle de comptage.
  5. Une annotation TypeScript valide-t-elle un JSON reçu par HTTP ?
    Réponse : non. Explication : les types sont effacés à l'exécution ; une validation runtime reste nécessaire.
  6. Où traduire une erreur interne en statut HTTP ?
    Réponse : à la frontière HTTP. Explication : le domaine conserve une signification métier et ne doit pas dépendre des statuts du protocole.
  7. Une transaction SQL peut-elle rendre atomique un appel à un prestataire de paiement ?
    Réponse : non. Explication : le système externe n'appartient pas à la transaction locale ; il faut concevoir idempotence, reprise et compensation.
  8. Un test avec un dépôt fake prouve-t-il le comportement des contraintes PostgreSQL ?
    Réponse : non. Explication : les contraintes, verrous et niveaux d'isolation nécessitent des tests d'intégration sur le moteur réel.
  9. Le nombre de modules suffit-il à justifier des microservices ?
    Réponse : non. Explication : il faut un besoin démontré d'indépendance de déploiement, de propriété, de mise à l'échelle ou d'isolation qui compense le coût distribué.
