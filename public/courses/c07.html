Cache et Redis avec Node.js

Niveau : intermédiaire à avancé · Durée indicative : 8 à 12 heures
Prérequis : TypeScript, Node.js asynchrone, HTTP, API et bases de données relationnelles.

Objectifs pédagogiques

  • Expliquer quand un cache réduit réellement la latence ou la charge.
  • Choisir entre cache HTTP, cache local et cache partagé.

  • Implémenter une lecture cache-aside avec Redis et TypeScript.
  • Gérer expiration, invalidation, erreurs, concurrence et protection contre les avalanches de requêtes.
  • Mesurer le taux de succès, la latence et le coût mémoire avant d’optimiser.

Module 1 — Le cache comme compromis

1.1 Pourquoi mettre en cache ?

Un cache conserve temporairement une représentation d’une donnée afin d’éviter de refaire un calcul ou un accès coûteux. Il peut réduire la latence, les lectures SQL, la consommation d’une API externe et le coût d’un calcul. Il introduit en échange une copie supplémentaire, une politique d’expiration, un risque de donnée périmée et des besoins de supervision.

Mettre en cache n’est pas une optimisation automatique. Si une opération est déjà rapide, si la donnée change constamment ou si son invalidation est difficile, le cache peut augmenter la complexité sans gain mesurable. Mesurer le comportement avant et après est indispensable.

1.2 Fraîcheur et cohérence

Le TTL (time to live) borne la durée de conservation d’une entrée. Un TTL court limite la durée de péremption mais augmente les lectures en source. Un TTL long améliore souvent le taux de succès mais peut exposer des valeurs obsolètes plus longtemps. Le TTL n’est pas une garantie absolue de fraîcheur : une suppression, une panne ou une éviction peut faire disparaître l’entrée plus tôt.

Il faut définir explicitement le niveau de fraîcheur acceptable : quelques secondes pour un catalogue public peuvent être acceptables ; un solde bancaire ou un droit d’accès ne doit pas être décidé à partir d’une copie périmée.

Exercice 1

Classez ces données selon leur aptitude au cache : liste publique de catégories, profil privé, stock d’un produit, résultat d’un calcul statistique quotidien.

Corrigé

Les catégories publiques et les statistiques quotidiennes se prêtent généralement bien au cache, avec un TTL ou une invalidation adaptés. Un profil privé nécessite une clé isolée par utilisateur et une politique stricte de confidentialité. Le stock est volatil : il peut être mis en cache pour l’affichage indicatif, mais la disponibilité doit être revalidée dans la transaction qui confirme la commande.

Module 2 — Choisir le niveau de cache

NiveauAvantagesLimites
Cache HTTP navigateur/CDNRéduit le trafic jusqu’au serveur ; efficace pour les ressources publiques.Contrôle par directives HTTP ; inadapté aux réponses privées mal configurées.
Mémoire du processus Node.jsTrès rapide, simple pour une petite donnée locale.Chaque instance possède ses propres valeurs ; mémoire limitée ; perte au redémarrage.
Redis partagéAccès partagé entre instances, TTL natif, structures de données et opérations atomiques.Ajoute réseau, coût opérationnel, disponibilité et capacité à superviser.

Un cache n’est pas une source de vérité durable. Si Redis devient indisponible, le système doit appliquer une stratégie décidée à l’avance : continuer sans cache si la source le permet, ou refuser certaines opérations si la sécurité ou la cohérence l’exige.

Exercice 2

Une API fonctionne sur quatre instances Node.js. Pourquoi un simple Map global n’est-il pas un cache partagé ?

Corrigé

Chaque processus détient son propre tas mémoire. Les écritures d’une instance ne sont pas visibles des autres, les redémarrages effacent les entrées et les données peuvent diverger. Un stockage partagé comme Redis permet de mutualiser les entrées, au prix d’un appel réseau et d’une dépendance opérationnelle supplémentaire.

Module 3 — Clés, TTL et représentation

3.1 Une clé décrit toutes les dimensions pertinentes

La clé doit intégrer les paramètres qui modifient la réponse : identifiant, langue, devise, version de représentation ou périmètre d’accès. Elle doit être déterministe, bornée et dépourvue de secrets. Ne construisez pas une clé à partir d’une chaîne fournie sans limite par un client : cela facilite la pollution du cache et peut produire des clés gigantesques.

catalog:v2:product:482:locale:fr-FR

La version v2 permet de séparer les représentations après un changement de format. Les valeurs d’identifiants doivent être validées avant la création de la clé.

3.2 Sérialisation

JSON convient aux objets simples, mais il faut traiter les valeurs absentes, les dates, les grands entiers, les changements de schéma et les erreurs de parsing. Les données récupérées d’un cache restent des données externes : elles doivent être validées au niveau nécessaire, surtout si plusieurs versions du service partagent Redis.

Exercice 3

Proposez une clé pour le prix affiché d’un produit, variant selon le pays et la devise.

Corrigé

Par exemple catalog:v1:price:product-482:country-FR:currency-EUR, après validation et normalisation des valeurs. Si le prix dépend aussi du segment client ou d’une promotion personnalisée, cette dimension doit être prise en compte ou cette réponse ne doit pas être partagée entre clients.

Module 4 — Cache-aside avec TypeScript et Redis

Dans le modèle cache-aside, le service consulte d’abord le cache. En cas d’absence, il lit la source de vérité, place le résultat dans le cache avec un TTL puis le retourne. La source reste responsable de l’exactitude métier.

Exemple avec le client redis officiel pour Node.js. L’installation et la configuration du service Redis dépendent de l’environnement ; l’extrait présente la logique applicative.

import { createClient } from 'redis';

type Product = {
  id: string;
  name: string;
  priceCents: number;
};

const redis = createClient({ url: process.env.REDIS_URL });
redis.on('error', (error: Error) => {
  // À connecter au système de journalisation de l’application.
  console.error('Redis error', error.message);
});
await redis.connect();

async function getProductFromDatabase(id: string): Promise {
  // Remplacer par le dépôt SQL réel et ses requêtes paramétrées.
  return productRepository.findById(id);
}

export async function getProduct(id: string): Promise {
  if (!/^[a-zA-Z0-9_-]{1,64}$/.test(id)) {
    throw new Error('Identifiant de produit invalide');
  }
  const key = `catalog:v1:product:${id}`;
  try {
    const cached = await redis.get(key);
    if (cached !== null) return JSON.parse(cached) as Product;
  } catch {
    // Une panne du cache ne doit pas forcément rendre la lecture impossible.
    // La politique de repli doit être adaptée au niveau de criticité.
  }

  const product = await getProductFromDatabase(id);
  if (product !== null) {
    try {
      await redis.set(key, JSON.stringify(product), { EX: 60 });
    } catch {
      // La source de vérité a répondu : ne pas perdre le résultat à cause du cache.
    }
  }
  return product;
}

Points à renforcer en production : valider le schéma après parsing, éviter de masquer toutes les erreurs indistinctement, ajouter des métriques, limiter la durée d’attente du cache, définir un comportement pour les pannes de base et vérifier que les données mises en cache sont partageables. L’exemple suppose l’existence d’un dépôt productRepository.

Exercice 4

Pourquoi ne faut-il pas mettre automatiquement en cache un résultat null pour une durée longue ?

Corrigé

Une ressource absente peut être créée juste après la lecture. Un cache négatif peut alors retarder sa visibilité. Le cache négatif est utile contre des recherches répétées de ressources inexistantes, mais son TTL doit être court et sa suppression prévue lors de la création.

Module 5 — Invalidation et cohérence

5.1 Invalider après une écriture

Une stratégie simple consiste à écrire dans la base, puis à supprimer la clé correspondante. Supprimer avant la transaction peut laisser une lecture concurrente recharger l’ancienne valeur. Supprimer après validation réduit ce risque, sans l’éliminer totalement : une lecture peut avoir commencé avant l’écriture et replacer ensuite une ancienne valeur dans le cache.

async function renameProduct(id: string, name: string): Promise {
  await productRepository.rename(id, name); // La base reste la source de vérité.
  try {
    await redis.del(`catalog:v1:product:${id}`);
  } catch (error) {
    // Journaliser et surveiller : le TTL borne la durée de l’éventuelle valeur périmée.
    logger.warn({ error, productId: id }, 'Cache invalidation failed');
  }
}

Pour les opérations critiques, une simple invalidation best-effort peut être insuffisante. Un outbox transactionnel, un événement durable, une version de donnée ou une lecture sans cache peuvent être nécessaires. L’architecture dépend de la tolérance métier à l’incohérence.

5.2 Éviter les données privées croisées

Une clé partagée ne doit jamais retourner à un utilisateur la réponse personnalisée d’un autre. Les réponses contenant des droits, des informations personnelles ou des prix individualisés exigent une séparation des clés et une politique HTTP appropriée, ou doivent être exclues du cache partagé. Ne considérez pas le cache comme un mécanisme d’autorisation.

Exercice 5

Après une mise à jour, la suppression de la clé Redis échoue. Quelles mesures prendre ?

Corrigé

Retourner le résultat de la transaction confirmée si la mutation a réussi, journaliser l’échec sans exposer de données sensibles, produire une métrique/alerte, et s’appuyer sur un TTL court ou un mécanisme durable de réinvalidation. Pour une donnée où la fraîcheur est critique, ne pas servir une valeur potentiellement périmée.

Module 6 — Concurrence et stampede

Un cache stampede survient lorsqu’une entrée expire et que de nombreuses requêtes déclenchent simultanément le même calcul ou la même requête SQL. Le cache réduit alors peu la charge précisément au moment où la source est sollicitée en masse.

  • Expiration aléatoire : ajouter un léger jitter au TTL pour répartir les expirations.
  • Single-flight local : partager une promesse en cours au sein d’un processus.
  • Verrou distribué : utile dans certains cas, mais exige TTL de verrou, propriétaire unique et traitement de l’expiration ; ne pas improviser un verrou fragile.
  • Stale-while-revalidate : servir temporairement une valeur ancienne acceptable pendant qu’un rafraîchissement est lancé.
  • Limitation de concurrence : plafonner les lectures simultanées vers la source.

Un mécanisme single-flight local peut réduire les doublons dans une instance, mais ne coordonne pas les autres instances. Il faut aussi nettoyer les promesses terminées ou rejetées pour éviter de conserver des erreurs en mémoire.

Exercice 6

Quelle mesure est la plus adaptée à un catalogue public dont une version périmée de quelques secondes est acceptable ?

Corrigé

Un TTL avec jitter et une stratégie stale-while-revalidate peuvent lisser les pics. La décision doit être accompagnée de mesures sur la charge SQL, la fraîcheur réelle et la latence. Cette stratégie ne convient pas automatiquement à des permissions ou à des transactions financières.

Module 7 — Sécurité et exploitation

  • Protéger Redis par réseau privé, authentification, ACL et chiffrement lorsque le contexte l’exige ; ne pas l’exposer publiquement.
  • Ne pas placer de jetons d’accès, mots de passe ou données personnelles dans les clés et journaux.
  • Limiter la mémoire et choisir une politique d’éviction cohérente avec l’usage ; distinguer cache éphémère et données que l’on ne peut pas perdre.
  • Configurer timeouts, reconnexion avec backoff et limites de concurrence sans créer une tempête de reconnexions.
  • Suivre latence p50/p95/p99, taux de succès, évictions, erreurs, mémoire et charge de la source.
  • Définir une stratégie de repli : indisponibilité du cache, indisponibilité de la base et surcharge ne sont pas le même incident.

Le taux de succès se calcule par hits / (hits + misses), en excluant les erreurs de mesure ou en les reportant séparément. Un taux élevé n’est pas une preuve de qualité si les entrées sont obsolètes ou si la latence globale n’a pas diminué.

Exercice 7

Une panne Redis entraîne une hausse massive des requêtes SQL. Quel mécanisme protège le mieux la source ?

Corrigé

Combiner une limite de concurrence vers la base, des timeouts, éventuellement un circuit breaker et une dégradation contrôlée. Une stratégie de repli qui envoie sans limite chaque requête directement vers SQL peut transformer une panne de cache en panne générale.

Module 8 — Tests et projet intégrateur

8.1 Stratégie de tests

  • Tester la logique de décision indépendamment de Redis.
  • Tester les cas hit, miss, valeur absente, erreur de parsing, expiration et indisponibilité.
  • Vérifier qu’une écriture invalide la bonne clé, et seulement les clés concernées.
  • Tester l’isolation des clés entre utilisateurs, langues, devises et versions.
  • Utiliser un Redis réel ou éphémère pour les tests d’intégration portant sur les TTL, commandes atomiques et comportements spécifiques au serveur.
  • Mesurer avec une charge représentative plutôt que d’affirmer un gain sur la seule base d’un microbenchmark.

Projet intégrateur : cache de catalogue

Construisez une couche de lecture pour un catalogue de produits avec PostgreSQL comme source de vérité et Redis comme cache facultatif. Le service doit offrir une lecture cache-aside, une invalidation après modification, une stratégie de repli et des métriques de base.

Critères de réussite

  1. Les clés sont déterministes, validées, versionnées et isolent les variantes de représentation.
  2. Les requêtes SQL restent paramétrées ; le cache ne remplace pas les contraintes de la base.
  3. Un TTL est explicite et justifié pour chaque catégorie de données.
  4. Les erreurs Redis sont observables et le repli protège la base d’une surcharge.
  5. Les données privées ne peuvent pas être servies à un autre utilisateur.
  6. Les scénarios hit, miss, expiration, invalidation et panne sont couverts par des tests.
  7. Les métriques démontrent l’effet sur la latence et la charge.
  8. La procédure d’exploitation décrit mémoire, disponibilité, sauvegarde si nécessaire et comportement en cas d’indisponibilité.

Quiz de révision

1. Redis doit-il devenir la source de vérité des produits ?

Non, pas dans cette architecture. PostgreSQL conserve les contraintes et la durabilité ; Redis accélère certaines lectures et ses entrées peuvent disparaître.

2. Un TTL de 60 secondes garantit-il que la donnée a moins de 60 secondes ?

Non. Le TTL borne la durée de conservation de l’entrée depuis son écriture, mais une invalidation ratée, une lecture concurrente ou une écriture mal ordonnée peuvent remettre une valeur ancienne en cache.

3. Pourquoi intégrer la langue dans une clé de cache ?

Parce qu’une réponse française et une réponse anglaise sont deux représentations distinctes. Omettre cette dimension peut retourner une réponse incorrecte.

4. Faut-il ignorer toute erreur Redis ?

Non. La politique dépend du caractère facultatif du cache. Il faut distinguer erreur de lecture, erreur d’écriture et indisponibilité, puis mesurer et appliquer un repli borné.

5. Que protège une limitation de concurrence SQL pendant une panne du cache ?

Elle limite le nombre d’opérations simultanées qui atteignent la base et réduit le risque d’effondrement en cascade.

6. Pourquoi ne pas mettre en cache une décision d’autorisation sans stratégie d’invalidation ?

Une permission révoquée pourrait rester utilisable jusqu’à expiration. Les décisions de sécurité doivent reposer sur une source et une fraîcheur compatibles avec le risque métier.
