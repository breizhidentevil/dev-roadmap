11. Conception et intégration des API

Gestion cohérente des erreurs d’API

Normaliser les erreurs et produire des réponses prévisibles.

Tutoriel complet · Niveau intermédiaireDurée indicative : 2 h

Objectifs d’apprentissage

  • Différencier erreur de validation, absence de ressource, authentification, autorisation et panne serveur.
  • Choisir des codes HTTP cohérents et une structure d’erreur stable.
  • Centraliser le traitement des exceptions sans exposer d’informations sensibles.
  • Documenter et tester le contrat d’erreur d’une API.

1. Pourquoi normaliser les erreurs ?

Un client d’API doit savoir distinguer une requête invalide, une session expirée, une ressource absente et une panne temporaire. Si chaque endpoint invente son format, le client doit multiplier les cas particuliers et risque de traiter incorrectement une erreur.

Une réponse d’erreur robuste possède trois couches : un code HTTP qui décrit la catégorie générale, un corps structuré qui apporte un code métier stable et un message compréhensible, puis éventuellement des détails de validation ou un identifiant de corrélation pour le support.

2. Choisir le code HTTP

CodeUsage courantAttention
400Requête mal formée ou paramètres invalides au niveau syntaxiqueDécrire précisément la correction attendue.
401Authentification absente ou invalideCe code ne signifie pas « pas autorisé » au sens des permissions.
403Identité connue mais action interditeNe pas divulguer inutilement des détails sur les ressources protégées.
404Ressource absente ou volontairement masquéeUne API peut choisir de masquer l’existence d’une ressource sensible.
409Conflit avec l’état actuel, par exemple une contrainte métierExpliquer ce qui entre en conflit et comment résoudre le conflit.
422Contenu syntaxiquement compris mais sémantiquement invalide, si ce choix fait partie du contratNe pas mélanger arbitrairement 400 et 422.
429Limite de débit atteinteFournir si possible une indication de temporisation, par exemple Retry-After.
500Erreur inattendue côté serveurNe jamais renvoyer stack trace, secrets ou requêtes internes au client.
503Service temporairement indisponiblePeut être accompagné d’une indication de reprise.

Le choix exact doit être cohérent avec les standards HTTP et le contrat public. Évitez d’utiliser 200 pour une erreur métier : le client et les outils de supervision interpréteraient la requête comme un succès HTTP.

3. Définir un format stable

Exemple de contrat simple, inspiré des formats d’erreur structurés courants :

{
  "error": {
    "code": "VALIDATION_FAILED",
    "message": "Certains champs sont invalides.",
    "details": [
      { "field": "email", "code": "INVALID_FORMAT" }
    ],
    "requestId": "req_7f3a"
  }
}

Les propriétés ont des rôles différents :

  • code : identifiant stable que le client peut traiter par programmation ; ne le changez pas pour une simple reformulation du texte.
  • message : résumé destiné à être compris par un humain. Pour une interface multilingue, le client peut traduire à partir du code.
  • details : détails limités et structurés, utiles notamment pour la validation.
  • requestId : identifiant qui permet de retrouver les journaux internes sans exposer ces journaux.

Ne renvoyez pas d’objet d’exception brut. Il peut contenir un chemin de fichier, une requête SQL, des données utilisateur ou des secrets.

4. Centraliser le traitement avec Express

Les routes traitent les erreurs métier attendues et transmettent les erreurs inattendues au gestionnaire central. L’identifiant de requête est créé une fois, propagé dans la réponse et utilisé pour retrouver les traces internes.

import express, { type Request, type Response, type NextFunction } from "express";
import { randomUUID } from "node:crypto";

const app = express();

// Créer l’identifiant avant les parseurs : leurs erreurs seront corrélables.
app.use((req: Request, res: Response, next: NextFunction) => {
  res.locals.requestId = randomUUID();
  res.setHeader("X-Request-Id", res.locals.requestId);
  next();
});
app.use(express.json());

app.get("/users/:id", async (req: Request, res: Response, next: NextFunction) => {
  try {
    const user = await findUser(req.params.id);
    if (!user) {
      res.status(404).json({
        error: {
          code: "USER_NOT_FOUND",
          message: "Utilisateur introuvable.",
          requestId: res.locals.requestId
        }
      });
      return;
    }
    res.json({ data: user });
  } catch (error) {
    next(error);
  }
});

app.use((error: unknown, req: Request, res: Response, next: NextFunction) => {
  if (res.headersSent) return next(error);

  const requestId = String(res.locals.requestId ?? "unknown");
  const parserErrorType =
    typeof error === "object" && error !== null && "type" in error
      ? error.type
      : undefined;

  // Les types ci-dessous sont ceux du body-parser utilisé par Express.
  if (parserErrorType === "entity.parse.failed") {
    res.status(400).json({
      error: {
        code: "INVALID_JSON",
        message: "Le corps JSON est invalide.",
        requestId
      }
    });
    return;
  }
  if (parserErrorType === "entity.too.large") {
    res.status(413).json({
      error: {
        code: "PAYLOAD_TOO_LARGE",
        message: "Le corps de la requête est trop volumineux.",
        requestId
      }
    });
    return;
  }

  // logger est un logger structuré, protégé et configuré pour expurger
  // secrets et données personnelles ; ne pas sérialiser l’objet brut.
  logger.error({
    requestId,
    errorName: error instanceof Error ? error.name : "UnknownError",
    method: req.method
  }, "API request failed");

  res.status(500).json({
    error: {
      code: "INTERNAL_ERROR",
      message: "Une erreur inattendue est survenue.",
      requestId
    }
  });
});

findUser et logger représentent des composants applicatifs à fournir. Le middleware de corrélation précède express.json() afin qu’une erreur de parsing possède aussi un identifiant de requête. Le gestionnaire distingue le JSON mal formé (400) et le corps trop volumineux (413) des défaillances inattendues (500) ; il s’appuie ici sur les types d’erreur documentés par le parseur Express et ne fait pas confiance à un statut arbitraire porté par toute exception. Le journal interne doit permettre un diagnostic sans renvoyer l’exception au client ; si la stack est conservée, elle doit rester dans un système d’observabilité à accès contrôlé et avec expurgation. Le gestionnaire doit respecter le comportement du framework lorsque les en-têtes ont déjà été envoyés. Les erreurs attendues (validation, conflit, autorisation) doivent être converties en réponses contractuelles avant d’arriver à ce gestionnaire d’erreurs inattendues.

5. Erreurs de validation

Validez les données à l’entrée du système et distinguez au moins :

  • JSON mal formé ou paramètres impossibles à interpréter ;
  • champs obligatoires absents ;
  • format incorrect ;
  • valeurs hors limites ;
  • violation d’une règle métier ;
  • conflit avec une donnée déjà existante.

Une erreur de validation peut contenir plusieurs détails, mais elle ne doit pas révéler les règles internes au-delà de ce qui est nécessaire. Le client ne doit pas avoir à analyser une phrase libre pour identifier le champ en erreur.

6. Réessais, idempotence et observabilité

Les clients ne doivent pas réessayer toutes les erreurs. Une requête mal formée ne deviendra pas valide en étant répétée. Une erreur temporaire de service peut justifier un nouvel essai avec délai exponentiel et aléa, mais les opérations non idempotentes peuvent créer des doublons si le client ne sait pas si la première tentative a été appliquée.

Associez les erreurs à des métriques et journaux structurés : code HTTP, code applicatif, route, durée, identifiant de requête et résultat. Évitez les données personnelles dans les logs. Une hausse des 5xx ou des 429 doit pouvoir être détectée sans consulter manuellement chaque ligne.

7. Tests du contrat d’erreur

  • Chaque erreur attendue renvoie le code HTTP prévu.
  • Le JSON suit le schéma et contient le code applicatif stable.
  • Les erreurs inattendues renvoient une réponse générique en production.
  • Les détails de validation sont déterministes et n’exposent pas de données sensibles.
  • Les clients peuvent distinguer une erreur réessayable d’une erreur définitive lorsque le contrat le prévoit.
  • Les changements du format d’erreur sont couverts par des tests de contrat.

Contrôles négatifs à inclure

  • Une erreur métier ne doit pas être renvoyée en HTTP 200 avec un champ success: false.
  • Ne convertis pas toutes les exceptions en 400 : distingue les erreurs client des défaillances serveur.
  • Ne journalise pas le corps complet des requêtes par défaut ; masque les champs sensibles et les identifiants qui ne sont pas nécessaires au diagnostic.
  • Vérifie que le même requestId apparaît dans l’en-tête, le corps d’erreur et les journaux associés.

8. Exercice

Concevez les réponses d’erreur pour une API de gestion de tâches : tâche absente, utilisateur non connecté, action interdite, titre vide, titre déjà utilisé, limite de débit dépassée et panne de base de données. Pour chaque cas, définissez code HTTP, code applicatif, message, détails éventuels et comportement du client.

Critères de réussite

Le format est identique d’un endpoint à l’autre, le code applicatif est stable, les erreurs attendues sont distinguées des pannes inattendues et aucune stack trace n’est envoyée au client.
