8. Architecture et conception logicielle

API évolutives et rétrocompatibles

Faire évoluer les contrats sans perturber les consommateurs existants.

Tutoriel complet · Niveau intermédiaireDurée indicative : 2 h

Objectifs d’apprentissage

  • Définir compatibilité ascendante et descendante dans le contexte d’une API.
  • Identifier les modifications compatibles et celles qui cassent un client.
  • Faire évoluer un contrat sans obliger tous les consommateurs à migrer immédiatement.
  • Planifier versionnage, dépréciation, tests de contrat et retrait d’une version.

1. Le contrat d’une API

Une API n’est pas seulement une collection de routes : c’est un contrat consommé par des applications qui peuvent être déployées à un rythme différent du serveur. Le contrat comprend les chemins, méthodes HTTP, paramètres, schémas de requête et de réponse, codes de statut, règles d’authentification, limites et comportements observables.

Une modification est risquée si un client existant cesse de fonctionner ou interprète différemment une réponse. La difficulté est particulièrement forte pour les API publiques, les applications mobiles et les intégrations tierces dont on ne maîtrise pas le calendrier de mise à jour.

Repère de vocabulaire : pour éviter l’ambiguïté de « rétrocompatible », raisonne sur les deux côtés du contrat. Un nouveau serveur est compatible avec les anciens clients si ceux-ci continuent à fonctionner. Un nouveau client reste compatible avec l’ancien serveur s’il n’utilise que les capacités déjà disponibles. Une même modification peut donc être sûre dans un sens et risquée dans l’autre.

ÉvolutionAncien client / nouveau serveurNouveau client / ancien serveur
Ajouter un champ facultatif à une réponseGénéralement compatible si le client tolère les champs inconnus.Compatible seulement si le nouveau client sait gérer l’absence du champ sur l’ancien serveur.
Ajouter un champ facultatif à une requêteLe serveur doit continuer à accepter les requêtes qui ne le transmettent pas.Le nouveau client ne peut l’envoyer qu’après vérification de la capacité du serveur.
Supprimer ou renommer un champRupture probable si l’ancien client l’utilise.Rupture probable si le nouveau client attend le nouveau nom sur un ancien serveur.

Cette analyse doit couvrir les réponses de succès et d’erreur, les codes HTTP, la nullabilité, les valeurs d’énumération et les règles d’authentification. La compatibilité ne se déduit pas uniquement de la validité du JSON.

2. Compatibilité : ce qui casse un client

ChangementRisqueApproche prudente
Supprimer un champ de réponseÉlevéDéprécier d’abord, mesurer l’usage, puis retirer après délai annoncé.
Renommer un champÉlevéAjouter le nouveau champ, maintenir l’ancien temporairement et documenter la migration.
Rendre obligatoire un champ auparavant facultatifÉlevéIntroduire une nouvelle règle de façon progressive et explicite.
Ajouter un champ facultatif à une réponseSouvent faibleLes clients doivent tolérer les propriétés inconnues.
Ajouter une nouvelle routeFaible pour les clients existantsDocumenter et sécuriser la nouvelle capacité.
Ajouter une valeur à un enumPotentiellement élevéLes clients doivent prévoir une valeur inconnue, ou le contrat doit traiter l’évolution explicitement.
Changer le sens d’un champ sans le renommerTrès élevéNe pas modifier silencieusement la sémantique ; introduire une nouvelle représentation.

« Ajouter un champ » n’est pas toujours sans risque : un client strict qui rejette les propriétés inconnues peut casser. De même, une valeur d’énumération nouvelle peut faire échouer un client qui suppose que la liste est exhaustive. Il faut considérer le comportement réel des consommateurs et le contrat publié.

3. Concevoir des réponses extensibles

Les clients devraient lire les champs dont ils ont besoin et ignorer les propriétés qu’ils ne connaissent pas, sauf si le contrat impose une validation stricte. Les objets de réponse peuvent évoluer par ajouts facultatifs, à condition que ces ajouts ne changent pas le sens des champs existants.

// Réponse initiale
{
  "id": "task_123",
  "title": "Réviser TypeScript"
}

// Évolution généralement compatible
{
  "id": "task_123",
  "title": "Réviser TypeScript",
  "priority": "high"
}

Un consommateur qui utilise seulement id et title continue à fonctionner. Le nouveau champ doit être documenté, sa nullabilité doit être claire et les clients doivent savoir comment traiter les valeurs inconnues.

4. Versionner avec discernement

Il existe plusieurs stratégies : version dans le chemin (/v1/tasks), dans un en-tête, ou dans un mécanisme de négociation de contenu. Aucune n’est universellement supérieure. Le chemin est visible et simple à diagnostiquer ; un en-tête évite de multiplier les chemins, mais peut être moins évident à explorer manuellement.

Ne créez pas une nouvelle version pour chaque petit ajout compatible. Réservez le changement majeur à une évolution réellement incompatible. Documentez la politique de support, les dates de fin de vie et les différences entre versions.

Dans une migration, faites coexister les versions lorsque c’est nécessaire, mesurez l’utilisation de l’ancienne version et fournissez une procédure de migration. Les versions doivent être testées séparément et leur sécurité doit rester équivalente.

5. Déprécier et retirer une capacité

  1. Identifiez les consommateurs et les usages réels à partir de métriques et de journaux respectueux de la vie privée.
  2. Annoncez la dépréciation, le motif, la solution de remplacement et les dates importantes.
  3. Ajoutez la nouvelle capacité avant de retirer l’ancienne, lorsque c’est possible.
  4. Fournissez un guide de migration et des exemples de requêtes avant/après.
  5. Surveillez les erreurs et le trafic sur l’ancienne route pendant la transition.
  6. Retirez seulement lorsque la politique annoncée et les contraintes opérationnelles le permettent.

La dépréciation est une période de transition, pas un simple changement de documentation. Une API peut exposer des métadonnées ou des en-têtes de dépréciation, mais la communication humaine et le suivi des consommateurs restent essentiels.

6. OpenAPI et tests de contrat

Maintenez une spécification OpenAPI qui décrit les routes, paramètres, schémas, réponses et mécanismes de sécurité. Elle permet de générer de la documentation et certains clients, et de repérer des incohérences entre l’implémentation et le contrat.

Ajoutez des tests de contrat : vérifiez les schémas de réponse, les codes HTTP et les comportements attendus. Pour une API consommée par plusieurs services, les tests basés sur les usages réels des consommateurs peuvent détecter une rupture que les tests unitaires du serveur ne voient pas.

  • Vérifiez la compatibilité de la spécification à chaque pull request.
  • Testez les clients contre les nouvelles réponses, y compris avec des champs supplémentaires et des valeurs inconnues.
  • Documentez les changements incompatibles et les migrations.

7. Erreurs fréquentes

  • Considérer tout ajout comme automatiquement compatible.
  • Changer le sens d’un champ sans modifier le contrat.
  • Supprimer une propriété parce qu’elle paraît inutilisée sans mesurer les usages externes.
  • Multiplier les versions majeures au lieu de faire évoluer prudemment les contrats.
  • Oublier les clients mobiles, les intégrations partenaires et les tâches planifiées.
  • Ne pas définir de calendrier de dépréciation ni de stratégie de migration.

8. Exercice

Une API renvoie actuellement { "id": 7, "name": "Ada" }. Le produit demande de remplacer name par displayName, d’ajouter un champ facultatif avatarUrl et d’interdire désormais les noms vides. Proposez un plan qui distingue les changements compatibles et incompatibles, définit une transition et liste les tests nécessaires.

Critères de réussite

Votre proposition maintient un temps de migration réaliste, décrit la nouvelle spécification, permet de mesurer les usages de l’ancien champ et n’introduit pas silencieusement de changement de comportement.

Atelier de validation : prouver la rétrocompatibilité

Une modification est compatible si les clients existants continuent à fonctionner selon le contrat observable. Une réponse qui reste valide en JSON peut malgré tout casser un client si un champ change de type, si l’ordre métier change ou si une erreur devient un succès.

Exemple : ajouter une propriété

// Réponse existante
{ "id": "cmd_123", "status": "confirmed" }
// Réponse enrichie : généralement additive
{ "id": "cmd_123", "status": "confirmed", "trackingUrl": null }

Avant d’ajouter un champ, vérifiez si les clients tolèrent les propriétés inconnues et si null a une sémantique définie. Renommer status, changer sa casse, modifier le sens d’une valeur ou rendre obligatoire un champ de requête est potentiellement incompatible. Les clients générés peuvent avoir des contraintes différentes des clients permissifs.

Plan de livraison

  1. Définissez le contrat courant et les comportements effectivement consommés.
  2. Ajoutez des tests de contrat pour clients représentatifs et cas d’erreur.
  3. Livrez d’abord une évolution additive ; mesurez l’usage de l’ancien champ sans journaliser de données sensibles.
  4. Publiez une date de dépréciation, une procédure de migration et une période de coexistence.
  5. Retirez l’ancien comportement uniquement après les preuves d’adoption et le respect de la politique annoncée.

Pièges et exercice

  • Une nouvelle valeur d’énumération peut casser un client qui traite les valeurs comme exhaustives.
  • Changer le code HTTP ou la forme des erreurs peut être une rupture même si le schéma de succès ne change pas.
  • Une version d’URL n’exonère pas de documenter le contrat ni de corriger les ambiguïtés.

Exercice : proposez l’ajout d’un statut partially_refunded. Listez les clients, les risques d’énumération, les changements OpenAPI, les tests contractuels, la télémétrie et le plan de retour arrière.

Critères de réussite : compatibilité analysée côté requête, réponse et erreurs ; migration documentée ; test de contrat reproductible ; suppression conditionnée à des preuves d’usage.
