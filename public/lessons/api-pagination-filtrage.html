11. Conception et intégration des API

Pagination, tri et filtrage

Concevoir des endpoints efficaces pour parcourir des collections.

Tutoriel complet · Niveau intermédiaireDurée indicative : 2 h

Objectifs d’apprentissage

  • Concevoir des paramètres de pagination, de tri et de filtrage cohérents.
  • Comparer pagination par offset et pagination par curseur.
  • Valider et borner les paramètres pour protéger la base et l’API.
  • Documenter les métadonnées de navigation et tester les cas limites.

1. Pourquoi paginer ?

Une collection peut contenir des milliers ou des millions de ressources. Renvoyer toute la collection augmente la latence, la consommation mémoire et le trafic réseau, et peut faire peser une charge excessive sur la base de données. La pagination limite le nombre de résultats renvoyés dans une réponse et permet au client de parcourir la collection progressivement.

Le tri rend l’ordre des résultats explicite. Le filtrage réduit la collection à un sous-ensemble pertinent. Ces trois fonctionnalités doivent être conçues ensemble : un tri stable est essentiel pour éviter les doublons ou les omissions lorsque le client passe d’une page à l’autre.

2. Définir un contrat lisible

Exemple de requête :

GET /api/tasks?status=open&sort=-createdAt&limit=20&offset=40
  • status=open : filtre sur un champ autorisé.
  • sort=-createdAt : tri décroissant, si cette convention est documentée.
  • limit=20 : taille de page demandée.
  • offset=40 : nombre d’éléments ignorés avant la page.

La réponse peut exposer les données et les métadonnées :

{
  "data": [
    { "id": "task_41", "title": "Tester les endpoints" }
  ],
  "page": {
    "limit": 20,
    "offset": 40,
    "hasMore": true
  }
}

Il faut préciser si le total est exact, approximatif ou absent. Calculer un total exact peut être coûteux sur une très grande collection ; ne l’ajoutez pas par défaut si le produit n’en a pas besoin.

3. Offset ou curseur ?

Pagination par offset

L’offset est facile à comprendre et permet de sauter directement à une position. Il devient souvent coûteux sur de grands offsets, car le moteur doit parcourir ou ignorer de nombreuses lignes. Si la collection change entre deux requêtes, des éléments peuvent se déplacer et être répétés ou omis.

Pagination par curseur

Le serveur fournit un curseur opaque représentant la position de reprise, souvent fondée sur une clé de tri stable. Le client le renvoie pour demander la page suivante. Cette approche est généralement plus adaptée aux flux volumineux et aux collections qui changent fréquemment, mais ne permet pas toujours de sauter arbitrairement à la page numéro 50.

GET /api/tasks?limit=20
→ { "data": [...], "nextCursor": "opaque-token" }

GET /api/tasks?limit=20&cursor=opaque-token

Traitez le curseur comme une valeur opaque : le client ne doit pas en fabriquer ni en modifier le contenu. Le serveur doit valider son format, son contexte et, si nécessaire, sa signature ou son expiration. Lier le curseur aux filtres, au tri et au périmètre d’accès évite de le réutiliser dans un autre contexte ; il ne remplace jamais l’autorisation côté serveur.

Exemple PostgreSQL pour la page suivante, avec un tri décroissant sur deux colonnes non nulles et un curseur contenant les valeurs de la dernière ligne reçue :

SELECT id, created_at, title
FROM tasks
WHERE owner_id = $1
  AND (created_at, id) < ($2, $3)
ORDER BY created_at DESC, id DESC
LIMIT $4;

Les paramètres sont liés par le pilote SQL ; owner_id vient de l’identité authentifiée, pas d’une valeur libre fournie par le client. Cet exemple suppose que created_at et id sont non nuls. Si le tri autorise des valeurs nulles ou des directions différentes, la condition de reprise doit refléter exactement cet ordre. La première page utilise une requête distincte sans condition de curseur.

4. Assurer un tri stable

Un tri sur un champ non unique ne suffit pas toujours. Si plusieurs tâches ont la même date de création, ajoutez un second critère déterministe, par exemple l’identifiant :

ORDER BY created_at DESC, id DESC

Ce tri fournit un ordre total tant que la clé de départ est unique. Pour une pagination par curseur, le curseur doit contenir ou référencer les valeurs nécessaires à la reprise dans cet ordre. Le serveur doit aussi documenter comment les valeurs nulles et les égalités sont traitées.

5. Valider les paramètres

  • Définissez une taille par défaut et un maximum strict pour limit.
  • Refusez les valeurs négatives, non numériques ou excessives plutôt que de les laisser produire des requêtes coûteuses.
  • Utilisez une liste blanche pour les champs de tri et de filtrage autorisés.
  • Paramétrez les valeurs SQL et ne concaténez jamais directement un texte fourni par le client dans une requête.
  • Définissez clairement les opérateurs de filtrage autorisés et leurs règles de combinaison.
  • Décidez si un paramètre inconnu est rejeté ou ignoré, puis documentez cette règle.

Les valeurs de tri sont souvent des noms de colonnes, qui ne peuvent pas être traités comme de simples paramètres de valeur SQL. Associez donc les noms externes à une liste de colonnes autorisées.

6. Cohérence entre pages

Un jeu de résultats paginé n’est pas forcément un instantané immuable. Si de nouveaux éléments arrivent pendant que le client parcourt les pages, l’ensemble peut changer. Selon le besoin, vous pouvez utiliser une pagination par curseur, une borne temporelle, un instantané transactionnel ou simplement documenter que les résultats reflètent l’état courant.

Les paramètres de tri et de filtre doivent rester identiques entre les pages. Si une API utilise un lien de continuation, le client devrait suivre le lien fourni sans en reconstruire lui-même les paramètres lorsque le contrat indique qu’il est opaque.

7. Tests essentiels

  • Collection vide, une page exacte et une dernière page incomplète.
  • Limite absente, égale à zéro, négative, non numérique et supérieure au maximum.
  • Valeur de tri inconnue et ordre déterministe en cas d’égalité.
  • Curseur invalide, expiré ou provenant d’un autre filtre.
  • Éléments ajoutés ou supprimés entre deux requêtes.
  • Vérification que le filtrage se fait côté serveur avant la pagination.
  • Mesure de la performance sur des volumes réalistes et des index appropriés.

8. Exercice

Concevez GET /api/products avec filtres de catégorie et de prix, tri par prix ou date, et pagination. Définissez les paramètres, leurs limites, la forme de la réponse et le comportement en cas de paramètre invalide. Comparez ensuite offset et curseur pour un catalogue de plusieurs millions de produits.

Critères de réussite

Le contrat est documenté, le tri est stable, les paramètres sont bornés et sécurisés, et le client peut détecter la fin de la collection sans supposer un nombre fixe de pages.

Atelier approfondi — Concevoir un endpoint de collection prévisible

Objectifs opérationnels

  • Expliquer les garanties et les limites du mécanisme présenté.
  • Choisir une stratégie adaptée à un cas réaliste et justifier ses compromis.
  • Vérifier le comportement avec des tests reproductibles plutôt que par intuition.

Explications et exemple guidé

Une API de collection doit définir un ordre stable, des limites et le comportement des paramètres invalides. Sans tri déterministe, des éléments peuvent être répétés ou omis entre deux pages lorsque plusieurs lignes partagent la même valeur de tri.

GET /api/orders?status=paid&sort=createdAt&direction=desc&limit=20&cursor=eyJpZCI6...

Validez les paramètres à l’entrée : limite entière bornée, champ de tri dans une liste autorisée, direction parmi asc/desc et filtres documentés. N’insérez jamais directement un nom de colonne fourni par le client dans une requête SQL.

const allowedSort = new Set(['createdAt', 'totalCents']);
const parsedLimit = rawLimit === undefined ? 20 : Number(rawLimit);
if (!Number.isInteger(parsedLimit) || parsedLimit < 1 || parsedLimit > 100) {
  throw new Error('Invalid limit');
}
const limit = parsedLimit;
if (!allowedSort.has(sort)) throw new Error('Unsupported sort field');
if (!['asc', 'desc'].includes(direction)) throw new Error('Invalid direction');

La pagination par offset est simple pour les petites collections, mais les grands offsets peuvent coûter cher et les insertions concurrentes déplacent les pages. Une pagination par curseur s’appuie sur un ordre stable, généralement complété par une clé unique.

Pièges et limites

  • Piège : accepter une limite illimitée et permettre une réponse trop volumineuse.
  • Piège : trier uniquement par une colonne non unique.
  • Piège : mélanger filtres, tri et pagination sans documenter si le total est exact ou estimé.
  • Piège : faire croire qu’un curseur opaque est une autorisation d’accès ; les permissions restent vérifiées à chaque requête.

Exercice

Définissez le contrat d’un endpoint de produits avec filtre de catégorie, tri par prix ou date et pagination par curseur. Décrivez les réponses aux paramètres invalides et écrivez des tests pour les valeurs limites et les éléments partageant le même prix.

Critères de réussite

  • Les paramètres, valeurs par défaut et limites sont documentés.
  • L’ordre de tri est déterministe et inclut un départage unique.
  • Les paramètres sont validés et les requêtes restent paramétrées.
  • Les tests couvrent page vide, dernière page, limite maximale et données concurrentes.
