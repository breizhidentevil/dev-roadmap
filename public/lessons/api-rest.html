3. Backend

Conception d’API REST

Concevoir un contrat HTTP centré sur les ressources, avec des méthodes sémantiques, des réponses prévisibles, une validation explicite et des tests de compatibilité.

Tutoriel complet · Niveau débutant à intermédiaireDurée indicative : 3 h

Objectifs d’apprentissage

  • Comprendre les contraintes fondamentales du style architectural REST.
  • Modéliser une API autour de ressources et de représentations.
  • Choisir des chemins, méthodes HTTP, codes de réponse et formats cohérents.
  • Documenter, sécuriser et tester une API REST.

Fil conducteur

La conception suit cet ordre : identifier les ressources, définir les opérations et leurs effets, choisir les statuts et représentations, fixer les règles de validation/autorisation, puis documenter et tester le contrat.

1. REST : un style architectural, pas une syntaxe d’URL

REST signifie Representational State Transfer. C’est un style architectural défini autour de contraintes, dont la séparation client-serveur, l’absence d’état de session applicatif obligatoire entre les requêtes, la possibilité de mise en cache, une interface uniforme et une architecture en couches. Une API qui utilise HTTP et des URL propres n’implémente pas nécessairement toutes les contraintes REST.

Dans la pratique courante, « API REST » désigne souvent une API HTTP qui expose des ressources, utilise les méthodes HTTP selon leur sémantique et renvoie des représentations structurées, souvent en JSON. Comprendre la différence évite de présenter REST comme un simple modèle de nommage.

2. Modéliser les ressources

Commencez par les objets métier que le client doit consulter ou modifier : utilisateurs, tâches, commandes, produits. Utilisez des noms de ressources plutôt que des verbes d’action dans chaque chemin.

GET    /api/tasks          # lister les tâches
POST   /api/tasks          # créer une tâche
GET    /api/tasks/42       # lire la tâche 42
PUT    /api/tasks/42       # remplacer sa représentation
PATCH  /api/tasks/42       # modifier certains champs
DELETE /api/tasks/42       # supprimer la tâche 42

Une ressource est identifiée par une URI. Le JSON renvoyé est une représentation de son état, pas la ressource elle-même. Une route comme /api/tasks/42/complete peut être acceptable pour une action métier qui ne se modélise pas naturellement comme une modification de ressource, mais il vaut mieux ne pas inventer systématiquement un verbe pour chaque opération.

3. Utiliser les méthodes HTTP selon leur sémantique

MéthodeIntentionPropriété importante
GETLire une représentationNe doit pas déclencher de modification métier.
POSTCréer une ressource ou soumettre une opérationPas idempotent par défaut.
PUTRemplacer l’état de la ressource cibleIdempotent si le serveur respecte la sémantique.
PATCHAppliquer une modification partielleL’idempotence dépend de l’opération et du format choisi.
DELETESupprimer la ressource cibleIdempotent au sens de l’effet attendu, même si les réponses peuvent varier.

Une méthode est idempotente si répéter la même requête a le même effet intentionnel sur le serveur que la lancer une fois. Cela ne signifie pas que la réponse HTTP doit être identique à chaque appel. Cette distinction est importante pour les réessais réseau.

4. Concevoir les réponses

Définissez des conventions homogènes pour les réponses de succès, les erreurs, la pagination, les dates et les champs facultatifs. Par exemple :

{
  "data": {
    "id": "task_42",
    "title": "Lire la documentation HTTP",
    "status": "open",
    "createdAt": "2026-10-10T10:30:00Z"
  }
}

Le wrapper data est un choix de conception, pas une obligation universelle. L’essentiel est de prendre une décision documentée et de la garder cohérente. Les dates doivent avoir un format et un fuseau explicites ; les champs facultatifs et la nullabilité doivent être spécifiés.

Choisissez des codes HTTP adaptés : 200 pour une lecture ou modification réussie avec représentation, 201 pour une création, 204 lorsque le succès ne renvoie pas de corps, 400 ou 422 pour une requête invalide selon le contrat, 401 pour l’authentification, 403 pour une action interdite, 404 pour une ressource absente et 5xx pour les erreurs serveur.

5. Statelessness et cache

Chaque requête doit contenir les informations nécessaires à son traitement ; le serveur ne doit pas dépendre d’un état de conversation implicite conservé entre deux requêtes. Cela ne signifie pas que l’application ne possède aucune donnée persistante : les ressources et données métier peuvent évidemment être stockées en base.

HTTP permet de définir les conditions de mise en cache avec des en-têtes comme Cache-Control, ETag et Last-Modified. Le cache peut réduire la latence et la charge, mais il doit être configuré avec prudence pour les données privées. Un cache partagé ne doit pas divulguer une réponse personnalisée à un autre utilisateur.

6. Valider, autoriser et sécuriser chaque requête

Ne faites jamais confiance au client. Validez la structure et les valeurs des paramètres, vérifiez l’identité de l’appelant et autorisez l’action sur la ressource précise. Le fait qu’un utilisateur soit connecté ne signifie pas qu’il peut lire ou modifier toutes les ressources.

  • Validez le corps JSON et les paramètres de chemin et de requête.
  • Utilisez des requêtes SQL paramétrées et des listes blanches pour les champs dynamiques.
  • Appliquez l’autorisation côté serveur à chaque opération sensible.
  • Limitez la taille des corps, la fréquence des requêtes et les volumes retournés.
  • Ne renvoyez jamais de secrets ou de stack traces dans les réponses.
  • Journalisez les événements utiles sans enregistrer de jetons ni de données sensibles.

7. Documenter le contrat avec OpenAPI

OpenAPI décrit les chemins, opérations, paramètres, schémas, réponses et mécanismes de sécurité d’une API HTTP. Une spécification exploitable réduit les ambiguïtés, facilite la génération de documentation et de clients, et permet de contrôler les changements du contrat.

Pour chaque opération, documentez au minimum : l’objectif, les paramètres, le corps accepté, les réponses possibles, les erreurs, les permissions nécessaires, les règles de pagination et les exemples. Évitez une documentation qui ne décrit que les réponses de succès.

8. Exemple d’endpoint Express

app.get("/api/tasks/:id", requireAuthenticatedUser, async (req, res, next) => {
  try {
    if (!isValidTaskId(req.params.id)) {
      res.status(400).json({
        error: { code: "INVALID_TASK_ID", message: "Identifiant invalide." }
      });
      return;
    }

    const task = await taskRepository.findById(req.params.id);
    if (!task || !canReadTask(req.user, task)) {
      // Politique choisie ici : ne pas révéler l’existence d’une tâche inaccessible.
      res.status(404).json({
        error: { code: "TASK_NOT_FOUND", message: "Tâche introuvable." }
      });
      return;
    }

    res.status(200).json({ data: task });
  } catch (error) {
    next(error);
  }
});

Les helpers requireAuthenticatedUser, isValidTaskId et canReadTask sont propres à l’application et doivent être implémentés et testés. La règle 404 pour une ressource inaccessible vise à masquer son existence ; un contrat peut choisir 403 s’il assume cette divulgation, mais le choix doit être cohérent. Le middleware central doit transformer les erreurs inattendues en réponse 5xx générique sans exposer la stack trace.

9. Tests et erreurs de conception fréquentes

  • Vérifiez les codes de statut, schémas JSON et en-têtes.
  • Testez un appel non authentifié (401), un identifiant invalide (400), une ressource absente et une ressource appartenant à un autre utilisateur (404 ou 403 selon le contrat).
  • Vérifiez qu’un utilisateur ne peut pas lire ou modifier une ressource en changeant simplement son identifiant dans l’URL.
  • Testez les réessais et les effets de bord pour les opérations importantes.
  • Testez la pagination, le tri et le comportement du cache si présents.
  • Évitez les chemins inconsistants, les verbes HTTP mal utilisés, les erreurs non documentées et les réponses qui changent de forme sans raison.

10. Exercice pratique

Concevez une API REST pour gérer des tâches. Écrivez les opérations de liste, lecture, création, modification partielle et suppression. Pour chacune, définissez la méthode, l’URI, les paramètres, le corps, les codes de succès, les erreurs possibles et les permissions.

Critères de réussite

Les méthodes HTTP ont une sémantique cohérente, les routes représentent des ressources, les réponses sont documentées, la validation et l’autorisation sont côté serveur et le contrat est testable.
