23. Spécialisations avancées

Applications temps réel

Approfondir la diffusion d’événements et la synchronisation des clients.

Tutoriel complet · Niveau intermédiaireDurée indicative : 2 h

Objectifs

  • Choisir entre polling, Server-Sent Events et WebSocket.
  • Concevoir la reconnexion, la gestion des erreurs et l’autorisation.
  • Comprendre les limites des connexions longues en production.

1. Définir le besoin temps réel

Une interface est dite temps réel lorsqu’elle doit refléter rapidement un événement externe : notification, tableau de bord, chat, suivi de traitement ou collaboration. Le besoin réel est rarement une latence nulle. Définissez plutôt un objectif mesurable : par exemple, 95 % des mises à jour visibles en moins d’une seconde, avec un comportement acceptable en cas de perte réseau.

Évaluez la fréquence des événements, le nombre de clients connectés, le sens du flux, la tolérance aux retards et le besoin de conserver les événements manqués. Un indicateur qui change toutes les minutes n’a pas les mêmes besoins qu’un jeu multijoueur.

2. Comparer les stratégies

ApprocheAdaptée lorsque…Limites
PollingLe client interroge périodiquement une API simple.Requêtes inutiles et délai lié à l’intervalle.
Long pollingLe serveur répond quand un événement arrive ou qu’un délai expire.Plus de complexité de gestion des requêtes en attente.
Server-Sent Events (SSE)Le serveur pousse un flux d’événements unidirectionnel vers le navigateur.Le client envoie ses commandes par HTTP séparément.
WebSocketLes deux côtés doivent envoyer fréquemment des messages.Protocole et cycle de vie plus complexes à exploiter.

Choisissez la solution la plus simple qui respecte les exigences. Une connexion persistante n’est pas automatiquement meilleure : elle augmente le travail d’observabilité, de montée en charge, de déploiement et de gestion des clients inactifs.

3. Exemple SSE côté navigateur

const events = new EventSource("/api/events");

events.addEventListener("task-updated", (event) => {
  const update = JSON.parse(event.data);
  renderTaskUpdate(update);
});

events.onerror = () => {
  showConnectionStatus("Connexion interrompue, reconnexion en cours");
};

// À la fin de vie de l'écran :
events.close();

SSE utilise une réponse HTTP avec le type de contenu text/event-stream. Le serveur sépare les messages par une ligne vide. Prévoyez des commentaires périodiques ou des événements de maintien de connexion si l’infrastructure coupe les connexions silencieuses. Vérifiez aussi les limites de connexions du navigateur et du proxy.

Le navigateur sait généralement retenter une connexion SSE. Cela ne garantit pas que chaque événement sera reçu : si la reprise exacte est nécessaire, le serveur doit attribuer des identifiants d’événement et implémenter une stratégie de reprise compatible avec la durée de conservation.

4. Exemple WebSocket

const socket = new WebSocket("wss://example.test/ws");

socket.addEventListener("open", () => {
  socket.send(JSON.stringify({ type: "subscribe", channel: "tasks" }));
});

socket.addEventListener("message", (event) => {
  const message = JSON.parse(event.data);
  if (message.type === "task-updated") renderTaskUpdate(message.payload);
});

socket.addEventListener("close", () => showConnectionStatus("Déconnecté"));

Dans une application réelle, validez chaque message reçu : taille maximale, type connu, schéma, autorisation et limites de fréquence. Ne faites jamais confiance au nom du canal fourni par le client. Le serveur doit vérifier que l’utilisateur peut s’abonner à ce canal et accéder aux données qu’il transporte.

5. Reconnexion, doublons et ordre

Le réseau peut tomber pendant un échange. Une reconnexion ne dit pas si le dernier message a été appliqué. Pour les événements importants, ajoutez un identifiant unique, une version ou un curseur. Le client peut ignorer les doublons et détecter un trou dans la séquence. Pour les opérations de commande, utilisez une clé d’idempotence ou une commande dont l’application répétée est sans danger.

  • Appliquez un délai exponentiel avec aléa pour éviter que tous les clients se reconnectent en même temps.
  • Limitez le nombre de tentatives ou adaptez-les à la durée de vie de l’écran.
  • Affichez l’état de connexion sans bloquer toute l’interface.
  • Rechargez un instantané après une longue déconnexion si le flux ne peut pas rejouer tous les événements.
  • Ne supposez pas que l’ordre est global entre plusieurs serveurs ou canaux.

6. Architecture de production

Les connexions longues consomment des ressources. Mesurez les connexions actives, la durée, les erreurs, les messages par seconde, la latence et les reconnexions. Configurez les délais du reverse proxy et de l’équilibreur de charge. Lorsqu’une application tourne sur plusieurs instances, un mécanisme de diffusion partagé peut être nécessaire pour que les événements publiés sur une instance atteignent les clients connectés aux autres.

Pour les événements métier importants, ne dépendez pas uniquement d’une diffusion en mémoire. Envisagez une file ou un journal d’événements durable, une stratégie de rétention et une procédure de rattrapage. Documentez ce qui se passe lorsqu’un client est hors ligne.

7. Sécurité

  • Utilisez TLS, donc wss:// pour WebSocket sur un site sécurisé.
  • Vérifiez l’origine du navigateur au moment de l’établissement de la connexion.
  • Authentifiez la connexion et réévaluez les autorisations quand elles peuvent changer.
  • Ne placez pas de jetons secrets dans les URL, où ils risquent d’apparaître dans les journaux.
  • Limitez taille, fréquence et nombre de connexions par utilisateur.
  • Validez les messages et encodez correctement les données affichées.

8. Tests et exercice

Testez la perte réseau, les reconnexions répétées, les messages mal formés, les permissions révoquées, les doublons, les événements hors ordre et les clients lents. Simulez un grand nombre de connexions plutôt que de vous limiter à deux navigateurs.

Exercice : concevez un tableau de suivi de tâches qui affiche les changements en moins de deux secondes. Justifiez SSE, WebSocket ou polling, définissez le format d’événement, la reconnexion, l’autorisation et les métriques opérationnelles.

Critères de réussite

  • Le choix du transport découle du besoin et du sens du flux.
  • Les messages sont validés et autorisés côté serveur.
  • Les reconnexions et les événements manqués ont une stratégie définie.
  • La solution est observable et testée en conditions de panne.

169 — Atelier de clôture : applications temps réel

Objectif : Choisis un transport temps réel et conçois reconnexion, authentification, ordre des messages et retour à l’état cohérent.

Modèle mental et méthode

WebSocket fournit un canal bidirectionnel ; Server-Sent Events diffuse des événements serveur vers client ; le polling est parfois suffisant et plus simple. Le transport ne remplace ni la persistance ni la gestion des états manquants. Utilise des identifiants de séquence ou curseurs pour reprendre après une coupure.

Exemple guidé

Exemple : à la reconnexion, le client envoie le dernier curseur reçu ; le serveur rejoue les événements disponibles puis fournit un snapshot si la fenêtre de rétention est dépassée.

Pièges à éviter

Pièges : supposer une connexion permanente, ne pas limiter le débit, oublier l’expiration des jetons, ou ne pas réconcilier les messages manqués.

Exercice de synthèse

Exercice : choisis entre polling, SSE et WebSocket pour un tableau de bord, un chat et une progression de tâche ; justifie le choix et la stratégie de reconnexion.

Critères de réussite

Réussite : transport justifié, authentification contrôlée, débit borné, reconnexion et resynchronisation testées.
