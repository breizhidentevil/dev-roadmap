23. Spécialisations avancées

Architecture événementielle

Découpler des composants par événements et messages.

Tutoriel complet · Niveau intermédiaire à avancéDurée indicative : 3 h

Objectifs

  • Différencier événement, commande et message.
  • Découpler producteurs et consommateurs sans perdre le contrôle des flux.
  • Comprendre livraison, idempotence, ordre et cohérence éventuelle.

1. Les concepts fondamentaux

Une commande demande qu’une action soit exécutée (« créer une commande »). Un événement annonce un fait déjà survenu (« commande créée »). Un message est le terme générique qui transporte une information entre composants. Cette distinction aide à définir les responsabilités : le producteur d’un événement affirme un fait et les consommateurs décident de leurs réactions.

Dans une architecture événementielle, les composants communiquent en publiant des événements sur un canal, un courtier ou un journal. Les consommateurs peuvent être ajoutés sans modifier directement le producteur, ce qui favorise le découplage. Le découplage n’est toutefois pas gratuit : le parcours d’exécution devient indirect, et il faut gérer la livraison, les erreurs et l’observabilité.

2. Flux direct, courtier et journal

Un appel HTTP direct convient quand l’appelant doit connaître immédiatement le résultat. Une file de messages répartit généralement les tâches entre consommateurs, tandis qu’un mécanisme de publication/abonnement permet à plusieurs groupes d’intérêt de recevoir le même événement. Un journal durable conserve un historique ordonné selon certaines partitions et permet parfois de relire les événements.

ModèleAvantageCoût
Appel synchroneFlux simple et réponse immédiateCouplage temporel et propagation des pannes
File de travailAbsorption des pics et repriseGestion des retries et files d’échec
Pub/subPlusieurs consommateurs indépendantsContrats d’événements et cohérence à coordonner

3. Concevoir un événement

Un événement utile est stable, versionné et autonome autant que nécessaire. Il contient un type, un identifiant, une date, une version de schéma, l’identifiant de corrélation et les données métier indispensables. Évitez d’y inclure secrets, données personnelles inutiles ou objets internes complets.

{
  "eventId": "evt_01J...",
  "type": "order.created",
  "schemaVersion": 1,
  "occurredAt": "2026-10-10T10:30:00Z",
  "correlationId": "checkout_42",
  "data": {
    "orderId": "ord_123",
    "customerId": "cus_456",
    "totalMinorUnits": 2599,
    "currency": "EUR"
  }
}

Les montants en unités monétaires mineures évitent les erreurs classiques de virgule flottante. Les consommateurs doivent gérer les champs inconnus selon le contrat et ne pas supposer que l’événement contient toutes les données de la ressource courante.

4. Livraison et idempotence

Une livraison « au moins une fois » peut produire des doublons : le consommateur effectue son travail mais tombe avant d’accuser réception. Une livraison « au plus une fois » peut perdre un message. Une garantie « exactement une fois » est souvent limitée à un périmètre technique précis et ne garantit pas automatiquement l’effet unique sur une base externe ou une API tierce.

La défense courante est un consommateur idempotent. Il enregistre l’identifiant d’événement traité et l’effet métier dans une transaction lorsque c’est possible. Une contrainte d’unicité peut empêcher le traitement double. Pour les appels externes, utilisez les mécanismes d’idempotence proposés par le service ou une table d’état dédiée.

BEGIN;
INSERT INTO processed_events(event_id)
VALUES ('evt_123')
ON CONFLICT DO NOTHING
RETURNING event_id;
-- Le code applicatif vérifie si une ligne a été retournée.
-- Aucune ligne : événement déjà traité ; ne pas refaire l'effet.
-- Une ligne : appliquer l'effet métier local dans cette transaction.
COMMIT;
-- Accuser réception du message seulement après le commit.

La contrainte unique sur event_id arbitre les consommateurs concurrents. L’enregistrement de déduplication et l’effet métier local doivent être dans la même transaction : sinon, un arrêt entre les deux peut perdre l’effet ou le répéter. Si le traitement doit appeler un service externe, la transaction SQL ne peut pas rendre cet appel atomique ; utilise alors une clé d’idempotence côté service externe ou une seconde outbox.

5. Transaction outbox

Un problème classique survient quand le service écrit une commande en base puis publie un événement. Si la base valide mais que le courtier est indisponible, l’état métier change sans événement. La transaction outbox consiste à écrire l’état métier et une ligne d’outbox dans la même transaction ; un processus distinct publie ensuite cette ligne et la marque comme traitée.

CREATE TABLE outbox (
  event_id UUID PRIMARY KEY,
  aggregate_id TEXT NOT NULL,
  event_type TEXT NOT NULL,
  payload JSONB NOT NULL,
  occurred_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  published_at TIMESTAMPTZ
);

BEGIN;
-- INSERT/UPDATE de la commande métier ici.
INSERT INTO outbox (event_id, aggregate_id, event_type, payload)
VALUES ('00000000-0000-4000-8000-000000000123', 'ord_123',
        'order.confirmed', '{"orderId":"ord_123"}'::jsonb);
COMMIT;

Le relais lit les lignes non publiées, envoie l’événement au courtier puis renseigne published_at après l’accusé de réception. Si le courtier a accepté le message mais que le relais s’arrête avant la mise à jour SQL, il peut le republier : c’est attendu, et le consommateur doit rester idempotent. L’outbox rend atomiques l’écriture métier et l’intention de publier, pas la livraison de bout en bout.

6. Ordre, retries et files d’échec

L’ordre global est coûteux et rarement garanti dans un système distribué. Si l’ordre compte, définissez la clé de partition ou la séquence métier concernée. Les retries doivent distinguer erreurs temporaires et erreurs permanentes, appliquer un délai progressif et avoir une limite. Après épuisement, placez le message dans une file d’échec consultable avec une procédure de reprise.

  • Définissez un délai maximal de traitement et une politique de retry.
  • Rendez visibles les messages en attente et les plus anciens.
  • Prévoyez le rejeu contrôlé et documentez ses effets.
  • Ne laissez pas une erreur poison bloquer indéfiniment toute une partition.

7. Observabilité et sécurité

Propager un identifiant de corrélation entre API, producteur, courtier et consommateur permet de reconstruire un parcours. Mesurez le débit, la latence de bout en bout, la taille des files, les erreurs, les retries et l’âge du message le plus ancien. Un service qui accepte les messages mais ne les traite plus doit déclencher une alerte.

Authentifiez les producteurs et consommateurs, limitez leurs droits aux canaux nécessaires, chiffrez les flux et protégez les données en transit et au repos. Les messages doivent être validés et traités comme des entrées non fiables, même lorsqu’ils viennent d’un système interne.

8. Exercice

Une commande validée doit déclencher un e-mail, une mise à jour analytique et une réservation de stock. Dessinez les événements, les responsabilités des consommateurs, la stratégie outbox, les garanties de livraison, la déduplication, les retries et les alertes. Déterminez ce qui doit être synchrone pour informer l’utilisateur et ce qui peut être asynchrone.

Critères de réussite

  • Commande et événement sont distingués.
  • Les doublons et erreurs temporaires sont gérés.
  • Le modèle de cohérence est documenté.
  • Le flux peut être observé, rejoué et dépanné.

168 — Atelier de clôture : architecture événementielle

Objectif : Détermine quand un événement métier est utile et comment garantir sa publication et son traitement.

Modèle mental et méthode

Un événement décrit un fait passé et stable (« commande confirmée »), tandis qu’une commande demande une action. Prévois version du schéma, identifiant unique, clé de partition, politique de rétention, idempotence des consommateurs et gestion des messages invalides. Le pattern outbox évite de valider la base sans publier l’événement correspondant.

Exemple guidé

Exemple : la transaction écrit la commande et un enregistrement outbox ; un relais publie ensuite l’événement. Le consommateur mémorise l’identifiant traité pour ignorer un doublon.

Pièges à éviter

Pièges : publier avant le commit, supposer l’ordre global, changer un schéma sans compatibilité, ignorer les files de quarantaine et le rejeu.

Exercice de synthèse

Exercice : dessine un flux commande confirmée vers facturation et notification ; indique garanties, doublons, évolution du schéma et procédure de rejeu.

Critères de réussite

Réussite : commande et événement distingués, publication fiable, consommateurs idempotents, erreurs et observabilité prévues.
