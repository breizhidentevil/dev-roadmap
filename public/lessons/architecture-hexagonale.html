17. Architecture backend approfondie

Architecture hexagonale

Isoler le domaine métier des frameworks et des systèmes externes.

Tutoriel complet · Niveau intermédiaireDurée indicative : 2 h 30

Objectifs d’apprentissage

À la fin de cette leçon, tu dois pouvoir séparer les règles métier des détails techniques et montrer cette séparation par le sens des dépendances et par les tests.

  • Définir un port à partir d’un besoin du cas d’usage, puis un adaptateur qui le réalise.
  • Faire dépendre le cœur d’un contrat plutôt que d’un framework, d’un ORM ou d’un fournisseur externe.
  • Assembler les implémentations au point de composition et tester le cas d’usage avec un faux adaptateur.
  • Reconnaître quand le coût des interfaces et des couches dépasse leur bénéfice.

Prérequis : fonctions, classes, interfaces TypeScript et tests unitaires.

1. Le problème du couplage

Quand une règle métier dépend directement d’Express, d’un ORM ou du SDK d’un prestataire, une modification technique se propage jusque dans le domaine. Les tests doivent alors souvent démarrer une base ou simuler des objets complexes. L’architecture hexagonale (ports et adaptateurs) inverse cette dépendance : le cœur décrit ce dont il a besoin, et l’infrastructure fournit une implémentation.

Le « centre » n’est pas obligatoirement une classe ou un dossier particulier. Il comprend les règles métier et les cas d’usage qui orchestrent un scénario. L’objectif est de protéger les décisions métier qui doivent rester stables malgré le changement de framework, de transport ou de stockage.

Exemple : le cas d’usage « renommer une tâche » doit vérifier que la tâche existe et appliquer les règles du domaine. Il ne devrait pas connaître la requête SQL, le code HTTP ni la manière dont le contrôleur désérialise le JSON.

2. Ports et adaptateurs

Un port est un contrat exprimé du point de vue du cœur applicatif. Un adaptateur traduit ce contrat vers une technologie concrète : PostgreSQL, HTTP, un fichier, une file de messages ou un dépôt en mémoire pour les tests.

export class Task {
  constructor(public readonly id: string, private title: string) {}

  rename(nextTitle: string): void {
    const normalized = nextTitle.trim();
    if (normalized.length === 0) throw new Error("TITLE_REQUIRED");
    this.title = normalized;
  }
  getTitle(): string { return this.title; }
}

export interface TaskRepository {
  findById(id: string): Promise<Task | null>;
  save(task: Task): Promise<void>;
}

export class RenameTask {
  constructor(private readonly tasks: TaskRepository) {}

  async execute(id: string, title: string): Promise<void> {
    const task = await this.tasks.findById(id);
    if (!task) throw new Error("TASK_NOT_FOUND");
    task.rename(title);
    await this.tasks.save(task);
  }
}

Le type de retour explicite rend le contrat lisible : l’absence de tâche est représentée par null, et save signale sa fin sans inventer une valeur métier. Le domaine porte la validation du titre ; le cas d’usage orchestre le chargement et la sauvegarde. Dans une application réelle, préfère des erreurs métier typées si l’appelant doit les distinguer sans comparer des chaînes.

Le port n’est pas nécessairement un dépôt générique CRUD. Il doit exposer les opérations utiles au cas d’usage, avec le niveau d’abstraction approprié.

3. Direction des dépendances

Le contrôleur HTTP peut appeler le cas d’usage ; le cas d’usage utilise le port ; l’adaptateur SQL implémente ce port. À la compilation, le code du cœur ne doit pas importer l’adaptateur SQL. À l’exécution, l’objet concret est injecté au cas d’usage.

                    Port dépôt
                         ▲

Le flux d’exécution et le graphe d’imports ne sont donc pas identiques : l’appel aboutit dans l’adaptateur, mais la dépendance de code reste orientée vers l’interface définie côté application. Une interface TypeScript disparaît à l’exécution ; elle ne crée pas de conteneur magique. Le point de composition doit construire l’adaptateur concret et le transmettre explicitement.

Une vérification pratique consiste à rechercher les imports de frameworks et de pilotes dans les dossiers domain et application. Si le domaine importe un modèle ORM, une classe Express ou une variable d’environnement, la frontière est probablement traversée.

4. Organiser les fichiers

src/
  domain/Task.ts
  application/RenameTask.ts
  application/ports/TaskRepository.ts
  adapters/http/tasksController.ts
  adapters/persistence/PostgresTaskRepository.ts
  composition/createApplication.ts

Cette arborescence est illustrative, pas une norme. Les frontières sont d’abord des règles de dépendance et de responsabilité, pas des dossiers imposés. Un petit projet peut regrouper plusieurs éléments tant que les dépendances restent claires. À l’inverse, une arborescence très découpée ne garantit rien si les cas d’usage importent directement les classes d’infrastructure.

Le point de composition est l’endroit où les détails sont réunis : il crée le dépôt PostgreSQL, le transmet à RenameTask, puis donne le cas d’usage au contrôleur. Il est normal que ce point connaisse les deux côtés ; il doit rester étroit et sans règles métier.

5. Tester sans infrastructure

Un test unitaire du cas d’usage peut utiliser un dépôt en mémoire qui implémente le même port. Il vérifie le comportement métier rapidement, sans serveur ni base réelle.

class InMemoryTaskRepository implements TaskRepository {
  private readonly items = new Map<string, Task>();
  async findById(id: string): Promise<Task | null> {
    return this.items.get(id) ?? null;
  }
  async save(task: Task): Promise<void> {
    this.items.set(task.id, task);
  }
}

Ce double est adapté à un test du cas d’usage, mais il ne prouve pas que l’adaptateur PostgreSQL construit la bonne requête ni que le mapping des colonnes fonctionne. Complète la suite avec des tests d’intégration pour l’adaptateur et un test du câblage réel. N’utilise pas uniquement des mocks : ils peuvent reproduire les hypothèses du test au lieu du comportement du système.

Les tests doivent couvrir au moins la tâche absente, le titre vide, la sauvegarde réussie et l’erreur de persistance. Décide aussi si une erreur technique doit remonter, être traduite ou être réessayée ; cette décision fait partie du contrat du cas d’usage.

6. Composition et cycle de vie

Le point de composition crée les implémentations concrètes et les injecte. Pour un service stateless, une instance partagée peut être appropriée ; pour un objet contenant l’identité ou l’état d’une requête, un singleton global peut provoquer une fuite de données entre utilisateurs. La durée de vie doit correspondre à celle des ressources et des données.

const repository = new PostgresTaskRepository(pool);
const renameTask = new RenameTask(repository);
const controller = new TasksController(renameTask);

Ce pseudo-exemple montre l’assemblage, pas toutes les signatures d’un serveur. Un conteneur d’injection est utile lorsque le graphe devient grand et que les cycles de vie doivent être gérés, mais il n’est pas requis pour appliquer l’inversion des dépendances. L’injection par constructeur suffit souvent et rend les dépendances visibles.

7. Coûts, limites et pièges

  • Créer une interface par classe sans besoin réel de substitution ou de contrat stable.
  • Faire remonter des types ORM ou HTTP jusqu’au domaine.
  • Placer les règles dans les contrôleurs, puis appeler cela « architecture hexagonale » parce qu’il existe plusieurs dossiers.
  • Dupliquer les mêmes validations dans toutes les couches sans décider quelle couche possède la règle.
  • Tester uniquement avec des doubles et ne jamais vérifier l’adaptateur réel.
  • Confondre ports/adaptateurs et microservices : l’architecture hexagonale peut parfaitement rester dans un monolithe.

Elle est utile quand le domaine contient des règles significatives, que les systèmes externes varient ou que les tests rapides ont de la valeur. Pour un CRUD simple et temporaire, une structure plus directe peut être plus économique. La mesure de réussite est la facilité à changer ou tester une dépendance sans modifier les règles métier, pas le nombre de couches créées.

8. Exercice pratique

Construis le cas d’usage « terminer une tâche ». Le domaine refuse une transition invalide ; le cas d’usage charge et sauvegarde la tâche ; l’adaptateur HTTP traduit l’entrée et la réponse ; un dépôt en mémoire permet de tester sans serveur ni base.

  1. Écris le port du dépôt dans la couche application.
  2. Implémente un adaptateur en mémoire puis un adaptateur de persistance réel.
  3. Teste la tâche absente, la transition interdite et le succès sans infrastructure.
  4. Ajoute un test d’intégration qui vérifie le mapping et le câblage de l’adaptateur réel.
  5. Trace les imports et démontre que domaine/application n’importent ni le framework HTTP ni l’ORM.

Critères de réussite de l’exercice

  • Le domaine n’importe aucun framework ou adaptateur.
  • Le cas d’usage dépend d’un port et non d’une classe concrète de persistance.
  • Les tests unitaires s’exécutent sans infrastructure et vérifient les cas d’échec.
  • Un test d’intégration couvre l’adaptateur réel.
  • Le point de composition est le seul endroit qui assemble les détails concrets.
