8. Architecture et conception logicielle

Architecture modulaire

Découper le système en modules cohérents et à responsabilités claires.

Tutoriel complet · Niveau intermédiaireDurée indicative : 2 h

Objectifs

  • Découper un système en modules cohérents.
  • Définir des interfaces publiques et limiter les dépendances.
  • Détecter les cycles et tester les frontières architecturales.

1. Pourquoi modulariser ?

La modularité réduit le nombre de concepts qu’un développeur doit comprendre simultanément. Un bon module regroupe des responsabilités qui changent ensemble et expose une interface publique limitée. Un mauvais découpage disperse une règle métier dans de nombreux dossiers ou crée des dépendances croisées.

Le découpage doit suivre la cohésion fonctionnelle et les changements probables, pas uniquement les types de fichiers. Un dossier « controllers » ou « services » est une organisation technique ; un module « facturation » ou « catalogue » représente une capacité métier et peut regrouper ses propres routes, règles et accès aux données.

2. Cohésion, couplage et frontières

La cohésion mesure à quel point les éléments d’un module servent un même objectif. Le couplage décrit la dépendance entre modules. Recherchez une forte cohésion interne et des dépendances explicites, limitées et stables.

src/
  modules/
    tasks/
      public.ts
      taskService.ts
      taskRepository.ts
      taskRoutes.ts
    users/
      public.ts
      userService.ts
      userRepository.ts

Un module devrait consommer l’API publique d’un autre module plutôt que d’importer ses fichiers internes. L’import direct de détails internes crée une dépendance cachée qui rend les changements plus risqués.

3. Contrats publics

Exposez uniquement ce dont les autres modules ont besoin. Les types internes, requêtes SQL et structures de persistance doivent rester privés si les consommateurs n’en ont pas besoin. Une interface publique trop large devient un engagement de compatibilité.

// modules/tasks/public.ts
export type TaskSummary = {
  id: string;
  title: string;
  status: "open" | "done";
};

export async function getTaskSummary(id: string): Promise<TaskSummary | null> {
  // délégation à l'implémentation interne
  return taskService.getSummary(id);
}

Cet exemple est schématique : les imports et l’initialisation sont omis. Dans un projet réel, évitez d’exposer des fonctions qui contournent les règles d’autorisation ou les invariants métier.

4. Dépendances et cycles

Un cycle A → B → C → A rend l’initialisation, les tests et la compréhension plus difficiles. Si deux modules se connaissent trop intimement, cherchez à déplacer un contrat partagé dans une couche neutre, à inverser une dépendance ou à revoir la frontière métier. Un dossier « shared » géant n’est pas une solution durable : il devient vite une dépendance universelle.

  • Définissez des règles d’import explicites.
  • Utilisez un outil d’analyse de dépendances si le dépôt est assez grand.
  • Ajoutez une vérification automatique qui interdit certains imports.
  • Évitez les imports profonds vers des fichiers internes d’un autre module.

5. Modularité dans un monolithe et dans des packages

Un monolithe modulaire peut fournir des frontières solides sans introduire les coûts du réseau. Des packages distincts deviennent pertinents lorsqu’un module doit être publié, versionné ou déployé indépendamment. Ne transformez pas automatiquement chaque module en microservice : les appels réseau, la sécurité, la supervision et les transactions distribuées ajoutent un coût important.

Pour un package npm, définissez les points d’entrée publics, les types exportés, les dépendances de production et une politique de versionnage. N’exposez pas accidentellement toute l’arborescence interne via des chemins d’import non documentés.

6. Refactoriser progressivement

  1. Cartographiez les dépendances et repérez les zones qui changent ensemble.
  2. Choisissez une capacité métier limitée.
  3. Définissez son contrat public avant de déplacer les fichiers.
  4. Déplacez l’implémentation en conservant les tests de comportement.
  5. Remplacez les imports internes par le contrat public.
  6. Ajoutez des règles automatisées pour empêcher la régression.

Effectuez des changements petits et vérifiables. Une refonte massive qui déplace simultanément des centaines de fichiers rend difficile l’identification de la cause d’une régression.

7. Exercice

Dans une application de gestion de tâches, séparez les modules utilisateurs, tâches et notifications. Définissez ce que chacun expose, ce qu’il garde privé et comment les notifications sont déclenchées sans importer les détails internes du module tâches.

Critères de réussite

  • Chaque module a une responsabilité claire.
  • Les imports intermodules passent par des contrats explicites.
  • Aucun cycle de dépendance n’est nécessaire.
  • Le découpage n’ajoute pas une complexité disproportionnée.

Atelier de validation : éprouver une frontière de module

Une frontière utile protège une règle métier et limite les raisons de modifier plusieurs modules ensemble. Elle ne se mesure pas au nombre de dossiers, mais à la stabilité des contrats et à la facilité d’évolution indépendante.

Exemple : commandes et notifications

Le module Commandes décide si une commande est confirmée et émet un événement métier CommandeConfirmee. Le module Notifications traduit cet événement en courriel. Commandes ne doit pas importer le client SMTP, le modèle de courriel ni les détails internes de Notifications.

type CommandeConfirmee = { commandeId: string; clientId: string; date: string };
interface EvenementsMetier {
  publier(event: CommandeConfirmee): Promise<void>;
}

Ce contrat est un exemple de forme, pas une obligation d’utiliser un bus d’événements. Dans un petit monolithe, un appel d’interface local peut être plus simple. Si la publication et l’écriture de commande doivent être atomiques, étudiez une outbox transactionnelle plutôt que de supposer que deux opérations indépendantes réussiront ensemble.

Test de la frontière

  1. Énumérez les dépendances publiques autorisées pour chaque module.
  2. Recherchez les imports profonds qui contournent l’API publique.
  3. Vérifiez les cycles dans le graphe des dépendances.
  4. Testez le contrat public sans connaître l’implémentation interne.
  5. Mesurez le coût de coordination d’un changement réel avant de déplacer du code.

Pièges et exercice

  • Un module par classe produit souvent de la fragmentation sans autonomie.
  • Un type partagé trop générique peut devenir une dépendance centrale instable.
  • Une frontière de package n’isole pas à elle seule les données ou les transactions.

Exercice : dessinez les modules Utilisateurs, Commandes et Notifications ; marquez les imports actuels et proposez une API publique minimale. Décrivez un test qui échoue si un import interne est ajouté.

Critères de réussite : responsabilités explicites, dépendances orientées, absence de cycle, contrat testable et justification du coût du découpage.
