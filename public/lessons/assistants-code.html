22. Intelligence artificielle appliquée au développement

Assistants de code

Utiliser l’IA pour explorer, générer et expliquer du code avec discernement.

Tutoriel complet · Niveau intermédiaireDurée indicative : 1 h 30

Objectifs pédagogiques

  • Formuler une demande précise et contextualisée à un assistant de code.
  • Vérifier le code proposé par rapport aux exigences, aux tests et à la sécurité.
  • Utiliser l’IA pour apprendre, explorer et refactoriser sans lui confier aveuglément la décision.

1. Ce qu’un assistant de code fait — et ne fait pas

Un assistant peut expliquer une fonction, proposer une implémentation, générer des tests, suggérer un refactoring ou aider à comprendre une erreur. Il prédit une réponse à partir du contexte fourni et de ses connaissances : il ne garantit ni la compilation, ni l’exactitude, ni la compatibilité avec la version exacte de vos dépendances.

Il peut inventer une API, ignorer une contrainte implicite, produire un test qui confirme son propre bug ou recommander une solution obsolète. Traitez toute proposition comme un changement de code écrit par un contributeur qu’il faut relire.

2. Construire une bonne demande

Une demande utile précise le contexte, le résultat attendu, les contraintes, ce qui est hors périmètre et la façon de vérifier le résultat. Fournissez un extrait minimal reproductible plutôt qu’un dépôt entier si quelques fichiers suffisent.

Contexte : API Node.js avec TypeScript.
Objectif : valider le corps d’une requête de création de tâche.
Contraintes :
- ne pas modifier le contrat HTTP existant ;
- distinguer erreur de validation et erreur interne ;
- ne pas ajouter de dépendance ;
- conserver les fonctions pures testables.
Livrable : proposition, tests unitaires et limites connues.
Ne modifie pas les autres fichiers.

3. Travailler par petites boucles

Évitez de demander une fonctionnalité complète en une seule instruction. Décomposez le travail : comprendre le code existant, proposer un plan, implémenter un changement limité, lancer les tests, inspecter le diff, puis traiter les erreurs. Cette approche rend les causes des régressions plus faciles à isoler.

  1. Énoncez le comportement attendu et les critères d’acceptation.
  2. Demandez une explication ou un plan avant une modification importante.
  3. Examinez le diff et supprimez tout changement hors sujet.
  4. Lancez formatage, lint, tests et build.
  5. Relisez manuellement les cas limites et les chemins de sécurité.

4. Vérifier au lieu de croire

La validation doit être indépendante de la réponse de l’assistant. Un test généré par le même assistant est utile, mais ne constitue pas à lui seul une preuve : ajoutez des cas tirés des exigences, des erreurs possibles et des limites d’entrée.

  • Compilez avec les options strictes du projet.
  • Exécutez les tests pertinents et, si possible, la suite complète.
  • Contrôlez les dépendances ajoutées, leurs versions et leurs licences.
  • Examinez les accès aux fichiers, au réseau, aux secrets et à la base.
  • Vérifiez les hypothèses factuelles dans la documentation officielle.

5. Confidentialité et responsabilité

Ne transmettez pas de mots de passe, clés API, données personnelles, code propriétaire ou données clients à un service sans autorisation explicite et compréhension de ses conditions. Utilisez des exemples anonymisés et des variables factices. Les règles de votre employeur ou de votre projet priment sur la commodité de l’outil.

Le développeur reste responsable du code fusionné : l’assistant ne connaît pas nécessairement les exigences métier, les contraintes de production ni les conséquences d’une faille.

6. Exercice

Demandez à un assistant de proposer une fonction TypeScript qui valide un identifiant de tâche et cinq tests. Comparez ensuite le résultat avec vos propres critères : chaîne vide, espaces, type incorrect, longueur excessive et valeur valide. Corrigez les oublis et notez les hypothèses que la demande initiale ne précisait pas.

Critères de réussite

  • La demande inclut contexte, contraintes et résultat attendu.
  • Le diff est limité et compréhensible.
  • Les tests ont été exécutés et complétés indépendamment.
  • Aucun secret ni donnée sensible n’a été exposé.

162 — Atelier de clôture : assistants de code

Objectif : Utilise un assistant de code comme outil de proposition, jamais comme source d’autorité.

Modèle mental et méthode

Fournis un contexte minimal mais suffisant : objectif, contraintes, versions, conventions, exemples d’entrée/sortie et critères d’acceptation. Demande une modification limitée, lisible et testable. Examine le diff avant de l’intégrer.

Exemple guidé

Exemple de flux : reproduire le bug, demander une hypothèse et un test ciblé, appliquer le changement dans une branche, lancer tests et analyse statique, puis relire les effets secondaires.

Pièges à éviter

Pièges : partager des secrets, accepter des dépendances sans examen, générer un gros refactoring non demandé, confondre code plausible et code correct.

Exercice de synthèse

Exercice : demande une fonction de validation avec tests, puis vérifie les cas limites et compare le résultat à une implémentation de référence.

Critères de réussite

Réussite : contexte maîtrisé, changements petits, tests indépendants, revue humaine et traçabilité.
