3. Backend

Authentification et autorisation

Distinguer identité, permissions et contrôle d’accès.

Tutoriel détailléLot 12 · 2026

Objectifs d’apprentissage

  • Distinguer identification, authentification et autorisation.
  • Appliquer le moindre privilège et le refus par défaut.
  • Protéger identifiants, sessions et accès aux ressources.
  • Tester les accès autorisés et interdits.

1. Trois questions distinctes

Identification : quel compte est revendiqué ? Authentification : quelle preuve vérifie cette revendication ? Autorisation : cette identité peut-elle effectuer cette action sur cette ressource dans ce contexte ? Être connecté ne donne pas automatiquement accès à toutes les fonctions.

Un utilisateur peut consulter ses commandes sans pouvoir lire celles d’un autre compte. Cette vérification doit être faite côté serveur à chaque opération pertinente, pas seulement dans l’interface.

2. Authentifier sans inventer sa cryptographie

Privilégie les mécanismes éprouvés du framework ou d’un fournisseur d’identité. Pour les mots de passe, stocke un hash adapté avec sel et paramètres de coût appropriés, jamais le texte en clair. Prévois limitation des tentatives, récupération sécurisée et MFA selon le risque.

Ne construis pas l’identité à partir d’un champ contrôlé par le client comme userId, isAdmin ou role. Les messages d’échec ne doivent pas faciliter inutilement l’énumération des comptes.

3. Autoriser chaque action

Une vérification globale « utilisateur connecté » ne remplace pas les contrôles de permission sur chaque ressource. Les règles peuvent dépendre du rôle, de la propriété, de l’état métier, du tenant ou du contexte.

Charge la ressource et applique une politique explicite avant de renvoyer les données ou de modifier l’état. Selon le besoin, filtre aussi les requêtes de base de données par propriétaire ou tenant pour limiter les erreurs d’accès.

4. Modèles de permissions

RBAC associe des permissions à des rôles. ABAC évalue aussi les attributs du sujet, de la ressource et du contexte. Une application simple peut commencer par une politique explicite et testable ; la complexité doit suivre les besoins réels.

Applique le moindre privilège et le refus par défaut : une route nouvellement ajoutée ne doit pas être accessible simplement parce qu’aucune règle n’a été écrite. Journalise les refus utiles sans stocker de secrets.

5. Sessions, cookies et jetons

Les sessions serveur facilitent la révocation centralisée, mais nécessitent un stockage accessible aux instances. Les cookies doivent être configurés selon le contexte, notamment avec HttpOnly, Secure et SameSite.

Les jetons signés peuvent être adaptés à certains systèmes, mais ne sont pas nécessairement chiffrés et peuvent être volés. Définis expiration, audience, rotation, révocation et stockage. Le choix doit découler des exigences, pas d’une règle « JWT partout ».

6. Étude de cas : empêcher l’accès à une ressource d’un autre compte

Un utilisateur connecté appelle GET /api/invoices/123. Le fait que sa session soit valide prouve son identité, pas son droit de lire la facture 123. Une faille fréquente consiste à vérifier seulement le rôle général « utilisateur connecté » puis à faire confiance à l’identifiant fourni dans l’URL.

async function getInvoice(request, reply) {
  const actor = request.auth; // établi par un mécanisme serveur fiable
  const invoice = await invoices.findById(request.params.id);
  if (!invoice) return reply.code(404).send({ error: "NOT_FOUND" });

  const allowed = await policy.canReadInvoice(actor, invoice);
  if (!allowed) return reply.code(404).send({ error: "NOT_FOUND" });
  return reply.send(toPublicInvoice(invoice));
}

Le code illustre une frontière de sécurité, pas une politique universelle. Selon les besoins, il peut être préférable de répondre 403 pour une ressource connue et interdite, ou 404 pour réduire la divulgation de son existence. Le choix doit rester cohérent et ne remplace pas la vérification d’autorisation. La fonction toPublicInvoice limite aussi les champs exposés : autoriser la lecture d’une facture ne signifie pas exposer tous les champs internes.

Règles à appliquer

  • Refus par défaut : une action est interdite tant qu’une règle explicite ne l’autorise pas.
  • Moindre privilège : donner uniquement les actions nécessaires, sur les ressources nécessaires.
  • Contrôle côté serveur : masquer un bouton dans l’interface améliore l’expérience, mais n’empêche pas un appel direct.
  • Réévaluer le contexte : propriété, organisation, statut de la ressource et permissions peuvent changer entre deux requêtes.
  • Journaliser avec discernement : enregistrer l’action refusée et un identifiant de corrélation, sans recopier les secrets ou le contenu sensible.

Les rôles (RBAC) sont pratiques pour des fonctions globales ; les règles fondées sur les attributs ou la relation avec la ressource sont souvent nécessaires pour « propriétaire », « membre de l’équipe » ou « document partagé ». Les combiner est possible, mais une politique trop dispersée devient difficile à tester.

Matrice de tests minimale : propriétaire autorisé, autre utilisateur refusé, administrateur selon la règle, ressource inexistante, session absente, permission révoquée et identifiant mal formé. Teste chaque action sensible, pas seulement la page d’accueil.

Critère de réussite : un appel direct avec l’identifiant d’un autre utilisateur est refusé par le serveur, et les tests prouvent à la fois les accès attendus et les accès interdits.

Erreurs fréquentes

  • Confondre authentification et autorisation.
  • Faire confiance à un rôle transmis par le navigateur.
  • Contrôler la route mais pas la ressource.
  • Oublier récupération et révocation de compte.
  • Inscrire des tokens dans les logs ou URL.

Exercice guidé

Pour une application de documents partagés, définis les droits de lecture, création, modification et suppression pour propriétaire, collaborateur et administrateur. Ajoute un test où un utilisateur devine l’identifiant d’un document appartenant à un autre compte.

Critères de réussite

identité établie côté serveur ; chaque ressource contrôlée ; moindre privilège et refus par défaut ; cycle de vie des sessions prévu ; tests négatifs inter-comptes.
