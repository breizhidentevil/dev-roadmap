5. Sécurité applicative

Autorisations côté serveur

Vérifier les permissions sur chaque opération sensible.

Tutoriel complet · Niveau intermédiaireDurée indicative : 1 h 45

Objectifs pédagogiques

  • Identifier les risques d’accès horizontal et vertical.
  • Mettre en place des contrôles d’accès côté serveur, y compris au niveau des objets.
  • Écrire des tests négatifs qui détectent les contournements d’autorisation.

1. Le serveur est la frontière de confiance

Le client contrôle son propre environnement : il peut modifier le HTML, appeler directement une API, changer les paramètres et rejouer des requêtes. Toute décision de sécurité doit donc être prise ou vérifiée par le serveur. Le frontend peut améliorer l’expérience en masquant les actions indisponibles, mais ce n’est pas un mécanisme de sécurité.

2. Accès horizontal et vertical

Un accès horizontal permet à un utilisateur d’atteindre les données d’un autre utilisateur de niveau similaire, par exemple en remplaçant /api/orders/123 par /api/orders/124. Un accès vertical permet d’exécuter une action réservée à un niveau de privilège supérieur, comme appeler directement une route d’administration.

Ces deux familles doivent figurer dans les scénarios de test. Les identifiants difficiles à deviner ne remplacent pas le contrôle d’accès : un UUID n’est pas une autorisation.

3. Politique explicite et centralisée

Définis des permissions métier nommées, par exemple project:read, project:update ou user:manage. Associe-les à des rôles si cela simplifie l’administration, puis applique les contraintes liées à la ressource : propriétaire, organisation, état de l’objet ou délégation temporaire.

function canEditProject(user, project) {
  if (!user) return false;
  if (user.permissions.includes("project:edit:any")) return true;
  return project.organizationId === user.organizationId
      && project.ownerId === user.id;
}

Cette fonction illustre une règle simple. En production, normalise le contexte d’identité après authentification et traite explicitement les privilèges administratifs, les délégations et les limites entre organisations. Garde la règle dans une politique réutilisable et testée, plutôt que de la recopier dans chaque contrôleur.

4. Appliquer le contrôle sans fuite de données

Filtre les données dans la requête au périmètre autorisé, au lieu de charger toutes les lignes puis de filtrer dans le navigateur. Le contexte de session et l’organisation doivent provenir de l’authentification vérifiée côté serveur, jamais d’un identifiant d’organisation fourni librement par le client.

const project = await db.project.findFirst({
  where: {
    id: projectId,
    organizationId: session.organizationId
  }
});

if (!project || !canEditProject(session.user, project)) {
  // Ce parcours choisit 404 pour ne pas révéler l’existence
  // d’une ressource inaccessible.
  throw new NotFoundError();
}

Adapte le code à l’ORM utilisé. Le filtrage par organisation et la politique de permission sont deux contrôles distincts : le premier borne le périmètre, la seconde vérifie le rôle, la propriété et l’action demandée. Pour une ressource visible mais une action interdite, une réponse 403 peut être appropriée ; choisis une règle cohérente et évite de divulguer involontairement l’existence d’objets privés.

5. Tests et audit

Construis une matrice de tests négatifs, pas seulement un test du chemin autorisé. Les réponses attendues ci-dessous sont des exemples : fixe le contrat exact de ton API et conserve-le dans les tests.

ScénarioRésultat attenduRisque couvert
Sans authentification401Accès anonyme
Utilisateur autorisé sur sa ressource2xxChemin positif
Autre propriétaire ou autre organisation404 si l’existence doit rester privéeIDOR et fuite d’existence
Rôle sans permission d’administration403 ou 404 selon la politique documentéeÉlévation verticale
Permission retirée pendant une sessionRefus après la fenêtre de révocation prévuePrivilèges obsolètes

Journalise les refus significatifs et les changements de permissions sans enregistrer de secrets. Les logs doivent permettre de comprendre l’action et la ressource concernées tout en minimisant les données personnelles. Les tests de séparation entre organisations doivent utiliser des comptes et données distincts.

6. Exercice

Sur une API de projets, écris une matrice d’accès pour lecteur, éditeur et administrateur. Implémente un endpoint de lecture qui ne retourne que les projets accessibles à l’utilisateur courant. Ajoute un test où l’utilisateur A remplace l’identifiant de son projet par celui de l’utilisateur B, puis un test d’appel direct à une route d’administration avec un rôle insuffisant. Vérifie le statut, le corps et l’absence de données privées dans la réponse de refus.

Critères de réussite

  • Aucune décision de sécurité ne dépend uniquement du frontend.
  • Les contrôles couvrent le rôle et la relation avec la ressource.
  • Les données d’une autre organisation ne sont jamais retournées.
  • Les tests couvrent les refus, les cas limites et les accès privilégiés.
