15. Méthodes de travail en équipe

Stratégie Git et résolution de conflits

Collaborer avec des branches et résoudre les conflits proprement.

Tutoriel complet · Niveau intermédiaireDurée indicative : 1 h 30

Objectifs pédagogiques

  • Choisir une stratégie de branches proportionnée au projet.
  • Résoudre un conflit en comprenant les deux changements concurrents.
  • Sécuriser l’intégration avec une revue, des tests et un historique lisible.

1. Une branche est un pointeur, pas une copie isolée

Git représente les versions sous forme de commits reliés entre eux. Une branche est un nom mobile qui pointe vers un commit. Créer une branche permet d’isoler une ligne de travail sans dupliquer tout le dépôt. Un conflit apparaît lorsque Git ne peut pas déterminer automatiquement comment combiner deux modifications, pas simplement parce que deux développeurs ont touché au même fichier.

2. Choisir un flux de travail

Pour une petite équipe, une branche principale toujours intégrable, des branches courtes et des pull requests fréquentes suffisent souvent. Les branches longues divergent et rendent les intégrations plus difficiles. Les modèles plus complexes avec branches de release ou branches de développement se justifient par des besoins de livraison précis, pas par tradition.

git switch main
git pull --ff-only
git switch -c feature/filtre-taches
# modifier les fichiers, tester
git add src/
git commit -m "feat: ajouter le filtre des tâches"
git push -u origin feature/filtre-taches

Ne commitez pas les fichiers générés, secrets ou modifications sans rapport. Un commit doit représenter une unité compréhensible et vérifiable.

3. Comprendre les marqueurs de conflit

Lors d’un conflit, Git insère généralement des marqueurs comme <<<<<<<, ======= et >>>>>>>. La partie du haut correspond généralement à votre version courante (HEAD) et celle du bas à l’autre version, mais vérifiez toujours le contexte de la commande et de l’outil utilisé.

<<<<<<< HEAD
const pageSize = 20;
=======
const pageSize = 50;
>>>>>>> origin/main

Ne choisissez pas automatiquement le haut ou le bas. Déterminez la règle attendue : faut-il conserver une seule valeur, fusionner deux comportements, ou réécrire la logique ?

4. Résoudre et vérifier

  1. Consultez git status pour identifier les fichiers concernés.
  2. Lisez les deux versions et, si nécessaire, l’historique des commits.
  3. Éditez le fichier pour exprimer le comportement final voulu.
  4. Supprimez tous les marqueurs de conflit.
  5. Exécutez les tests ciblés, puis les contrôles du projet.
  6. Marquez le fichier résolu avec git add et terminez l’opération en cours.
git status
# corriger les fichiers
git diff --check
git diff
npm test
git add src/chemin/fichier.ts
git status

Pour un rebase ou un merge, les commandes de continuation et d’annulation diffèrent. Lisez le message de Git et utilisez git rebase --continue, git merge --continue ou l’annulation appropriée selon l’opération active.

5. Éviter les erreurs dangereuses

Avant une commande destructive, inspectez l’état du dépôt et sauvegardez les modifications non commitées. Évitez de forcer un push sur une branche partagée sans comprendre l’impact. Ne résolvez pas un conflit en supprimant un bloc entier uniquement pour faire disparaître les marqueurs : cela peut éliminer une règle métier ou un correctif de sécurité.

Après résolution, vérifiez le diff complet et le comportement fonctionnel. La disparition des marqueurs ne prouve pas que la fusion est correcte.

6. Exercice

Créez deux branches qui modifient la même constante et un autre fichier avec des modifications compatibles. Fusionnez-les, résolvez le conflit selon une règle explicite, puis vérifiez l’historique et exécutez les tests.

Critères de réussite

  • Les branches restent courtes et leur objectif est clair.
  • La résolution conserve l’intention des deux changements pertinents.
  • Le diff ne contient aucun marqueur ni modification accidentelle.
  • Les tests sont exécutés après la résolution.

Atelier approfondi — seconde passe

Objectifs opérationnels

  • Choisir entre merge et rebase en fonction de la politique du dépôt.
  • Résoudre un conflit en comprenant les deux changements plutôt qu’en choisissant mécaniquement un côté.
  • Vérifier l’état du dépôt et les tests avant de poursuivre une intégration.

Explications et méthode

Une branche est un pointeur mobile vers un commit. Un merge conserve les deux historiques et peut créer un commit de fusion ; un rebase rejoue des commits sur une nouvelle base et réécrit leurs identifiants. Ne rebase pas une branche partagée sans coordination, car les autres clones conservent l’ancien historique.

Un conflit signale que Git ne peut pas décider automatiquement comment combiner des modifications. Les marqueurs indiquent des versions concurrentes, pas une réponse à sélectionner sans contexte. Lis le code environnant et l’intention de chaque commit, puis reconstruis le comportement souhaité.

Avant toute commande de résolution, vérifie git status et protège le travail non commité. Après résolution, inspecte le diff, recherche les marqueurs restants, exécute les tests et confirme que le commit contient uniquement les changements attendus.

Exemple commenté

git status
# Actualiser les références distantes sans modifier le répertoire de travail
git fetch origin
# Choisir une stratégie cohérente avec les règles de l’équipe
git switch feature/recherche
git merge origin/main
# Après résolution manuelle des fichiers conflictuels :
git diff --check
git diff --cached
# Si le merge est devenu trop risqué, avant de le valider :
git merge --abort

Pièges à éviter

  • Résoudre tous les conflits en choisissant « ours » ou « theirs » sans comprendre l’effet métier.
  • Lancer un reset destructif ou un rebase avec du travail non sauvegardé.
  • Oublier qu’une résolution peut être syntaxiquement valide mais supprimer un comportement de l’autre branche.

Exercice d’application

Crée deux branches qui modifient la même fonction de façons différentes. Intègre l’une dans l’autre, résous le conflit en conservant l’intention des deux changements, puis vérifie le diff et exécute les tests. Refais l’exercice avec une stratégie d’intégration différente si le dépôt l’autorise.

Critères de réussite

  • La stratégie choisie respecte les conventions de l’équipe et l’historique partagé.
  • Aucun marqueur de conflit ne subsiste et le comportement final est expliqué.
  • Le dépôt est propre, le diff relu et les tests exécutés après la résolution.
