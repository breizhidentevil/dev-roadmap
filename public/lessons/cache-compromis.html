8. Architecture et conception logicielle

Cache et compromis de performance

Évaluer latence, fraîcheur des données et complexité opérationnelle.

Tutoriel complet · Niveau intermédiaireDurée indicative : 1 h 45

Objectifs pédagogiques

  • Identifier les couches où un cache peut réduire le coût.
  • Choisir une stratégie d’expiration et d’invalidation cohérente.
  • Évaluer les risques de données périmées, de cache stampede et de fuite entre utilisateurs.

1. Pourquoi mettre en cache ?

Un cache conserve temporairement un résultat coûteux afin d’éviter de le recalculer ou de le relire. Il peut réduire la latence, la charge de la base de données et les coûts d’un service distant. Il ajoute toutefois un second endroit où une représentation de la donnée existe : le problème central devient la cohérence entre la source et le cache.

Commencez par mesurer le goulot d’étranglement. Mettre en cache une opération déjà rapide peut ajouter de la complexité sans bénéfice mesurable.

2. Les couches de cache

Le navigateur peut réutiliser des ressources statiques ; un CDN peut servir des réponses proches des utilisateurs ; l’application peut conserver des résultats en mémoire ou dans Redis ; la base de données possède aussi ses propres caches. Chaque couche a une portée, une politique d’expiration et des règles de partage différentes.

Un cache client améliore les chargements répétés. Un cache partagé côté serveur peut réduire la charge pour plusieurs utilisateurs, mais exige une clé correcte et une stratégie stricte pour les données privées.

3. Cache-aside et expiration

Avec le modèle cache-aside, l’application cherche d’abord la valeur dans le cache, lit la source en cas d’absence, puis remplit le cache. Une durée de vie (TTL) borne la durée pendant laquelle une valeur peut rester disponible sans nouvelle lecture.

async function getProduct(id) {
  const key = `product:${id}`;
  const cached = await cache.get(key);
  if (cached !== null) return JSON.parse(cached);

  const product = await repository.findById(id);
  if (!product) return null;

  await cache.set(key, JSON.stringify(product), { EX: 60 });
  return product;
}

Exemple schématique : adaptez l’API du client Redis utilisé. Définissez aussi le traitement des erreurs du cache. Si le cache est un accélérateur non critique, une panne peut parfois entraîner une lecture directe de la source, sous réserve de ne pas la surcharger.

4. Invalidation et cohérence

Quand une donnée change, il faut décider comment le cache est actualisé : suppression de la clé après écriture, mise à jour de la valeur, invalidation par version, ou expiration courte. La stratégie dépend de la tolérance aux données périmées. Une valeur de stock ou de droits d’accès peut nécessiter des garanties plus strictes qu’une image de profil.

  • Écrivez d’abord dans la source de vérité, puis invalidez le cache.
  • Documentez ce qui se passe si l’invalidation échoue.
  • Évitez de supposer que supprimer une clé suffit quand plusieurs clés représentent la même donnée.
  • Ne mettez pas en cache une réponse privée avec une clé qui omet l’identité ou le périmètre d’accès.

5. Cache stampede, limites et observabilité

Lorsqu’une clé populaire expire, de nombreuses requêtes peuvent recalculer simultanément la même valeur. Ce phénomène est appelé cache stampede. Des mécanismes de coalescence des requêtes, un verrou à durée limitée, une expiration avec jitter ou une actualisation en arrière-plan peuvent réduire ce risque. Chaque technique introduit ses propres compromis.

Mesurez le taux de succès du cache, la latence, le nombre de lectures à la source, les erreurs et la mémoire consommée. Un taux de succès élevé n’est pas une fin en soi si les données servies sont incorrectes ou si l’invalidation coûte trop cher.

Approfondissement pratique : décider si un cache vaut son coût

Un cache n’est pas une optimisation gratuite : il échange du calcul, des lectures ou de la latence contre de la mémoire, une politique de fraîcheur et une nouvelle source possible d’incidents. Avant de l’ajouter, formulez une hypothèse mesurable : « cette lecture représente 35 % du temps de réponse et peut être réutilisée pendant 30 secondes ». Sans hypothèse, le cache risque de masquer le vrai goulot.

Mesurer le bénéfice réel

Suivez au minimum le taux de succès (hits / total), la latence des lectures, le coût de calcul ou de requête évité, la taille mémoire et l’âge des valeurs servies. Un taux de succès élevé ne prouve pas à lui seul une amélioration : les requêtes restantes peuvent être très coûteuses, ou l’invalidation peut ralentir les écritures. Comparez les percentiles p50, p95 et p99 avant et après, sur une charge comparable.

// Pseudocode : le cache ne remplace pas la source de vérité
async function getProduct(id) {
  const key = `product:${id}`;
  const cached = await cache.get(key);
  if (cached !== null) return JSON.parse(cached);
  const product = await database.findProduct(id);
  if (!product) return null;
  await cache.set(key, JSON.stringify(product), { ttlSeconds: 60 });
  return product;
}

Ce modèle cache-aside suppose que l’absence de valeur en cache est détectable sans confondre « clé absente » et valeur métier nulle. En production, traitez explicitement les erreurs du cache : selon la criticité, la lecture peut retomber sur la base de données, mais il faut éviter qu’une panne du cache fasse subitement exploser sa charge.

Deux pièges opérationnels

  • Cache stampede : une clé populaire expire et des centaines de requêtes interrogent simultanément la base. Mitigations possibles : verrou court, rafraîchissement anticipé, jitter sur le TTL et limitation de concurrence.
  • Données partagées entre utilisateurs : une clé qui omet le tenant, la langue ou les droits peut servir une réponse à la mauvaise personne. Toute dimension qui modifie le résultat doit être prise en compte dans la clé ou exclue du cache.

Exercice de décision

Sur un endpoint qui lit un catalogue mis à jour toutes les cinq minutes, proposez une clé, un TTL, une stratégie d’invalidation et un comportement en cas d’indisponibilité du cache. Ajoutez un scénario où le résultat doit être immédiatement frais, puis expliquez pourquoi le cache n’est alors pas adapté ou doit être contourné.

Critères de réussite : la proposition nomme la source de vérité, définit une fraîcheur acceptable, évite le mélange de données entre utilisateurs et prévoit au moins une métrique permettant de vérifier le bénéfice.

6. Exercice

Ajoutez un cache de 60 secondes à la lecture d’un catalogue. Lors d’une modification de produit, invalidez la clé correspondante. Testez une lecture répétée, une mise à jour, une clé absente, une panne du cache et deux utilisateurs avec des droits différents.

Critères de réussite

  • La source de vérité reste clairement identifiée.
  • La politique de fraîcheur et d’invalidation est documentée.
  • Les clés ne mélangent pas les périmètres de sécurité.
  • Des métriques permettent de vérifier le bénéfice réel.
