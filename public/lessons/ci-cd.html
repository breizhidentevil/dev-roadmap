7. Environnement, livraison et exploitation

Intégration et déploiement continus

Automatiser les contrôles et livrer des artefacts traçables, en limitant les actions manuelles et les risques de publication.

Tutoriel approfondiCompétence Full Stack

Objectifs et prérequis

L’intégration continue (CI) automatise des contrôles sur les changements : installation reproductible, lint, tests, compilation et parfois analyse de sécurité. La livraison continue prépare un artefact déployable ; le déploiement continu peut publier automatiquement en production lorsque les conditions prévues sont satisfaites. Ces notions sont liées mais ne sont pas synonymes.

  • Comprendre les étapes et conditions d’un pipeline.
  • Rendre les contrôles reproductibles et visibles.
  • Relier l’artefact livré à son commit source.
  • Protéger les secrets et permissions du pipeline.
  • Prévoir vérifications de santé et retour arrière.

1. Définir une chaîne de livraison

Un pipeline courant récupère le commit, installe les dépendances, exécute lint et tests, construit l’application, produit un artefact puis le vérifie et le déploie. Un contrôle obligatoire doit faire échouer clairement le pipeline lorsqu’il échoue.

La CI réduit le délai de détection d’un défaut, mais elle ne garantit pas la qualité si les tests sont faibles ou instables. Commence par les contrôles rapides puis exécute les plus coûteux. Les tests unitaires précèdent souvent les tests d’intégration et end-to-end pour fournir un retour précoce.

2. Exemple GitHub Actions

name: CI
on:
  pull_request:
  push:
    branches: [main]
permissions:
  contents: read
jobs:
  verify:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: npm
      - run: npm ci
      - run: npm run lint
      - run: npm test -- --run
      - run: npm run build

Adapte les commandes au projet et vérifie les versions des actions utilisées. Le script de test peut avoir une syntaxe différente. Épingle les actions selon la politique de sécurité ; un SHA de commit est plus immuable qu’un tag majeur.

Les permissions minimales réduisent l’impact d’une action compromise. N’accorde pas de droits d’écriture si le job ne publie rien. Pour les contributions externes, limite l’accès aux secrets et évite d’exécuter du code non fiable dans un contexte privilégié.

3. Tests fiables et artefacts

Utilise un lockfile, des données de test isolées et un nettoyage explicite des ressources. Évite les dépendances à l’heure locale ou à un service partagé non maîtrisé. Un test intermittent (« flaky ») diminue la confiance ; diagnostique sa cause plutôt que de relancer indéfiniment.

Un artefact peut être une image conteneur, un paquet ou un bundle. Idéalement, construis-le une fois puis promeus le même contenu entre test et production, en faisant varier la configuration plutôt que le binaire. Associe l’artefact au commit source et aux résultats des contrôles. Le tag latest n’identifie pas précisément une version.

4. Déploiement et retour arrière

Un déploiement n’est pas validé simplement parce que la commande de publication a terminé. Vérifie la santé réelle du service : démarrage, endpoint de santé, erreurs, latence et dépendances critiques. Définis les critères qui interrompent la livraison ou déclenchent un rollback.

Une livraison progressive — préproduction, canari ou remplacement graduel — peut réduire l’impact d’un défaut, mais ajoute des mécanismes à maintenir. Pour une petite application, une procédure simple, testée et documentée peut être préférable. Le rollback applicatif ne restaure pas automatiquement le schéma de base de données : les migrations doivent être conçues pour rester compatibles avec les versions concernées.

5. Secrets et permissions

Un pipeline peut lire le code, publier des paquets et déployer en production. Limite ses permissions, protège les branches et sépare validation et déploiement si le risque le justifie. Stocke les secrets dans les mécanismes prévus par la plateforme ; ne les affiche jamais dans les logs.

Lorsque c’est possible, préfère des identifiants temporaires ou une fédération d’identité aux clés statiques de longue durée. Prévois rotation et révocation. Le pipeline lui-même doit être revu comme du code : une action tierce ou un script externe non vérifié peut compromettre la chaîne entière.

6. Protéger la chaîne d’approvisionnement

Le pipeline exécute du code provenant du dépôt et parfois d’actions tierces. Une dépendance ou une action compromise peut donc obtenir les permissions du job. Pour les workflows sensibles, épingle les actions à un SHA de commit complet vérifié, examine les mises à jour et limite les permissions au besoin exact. Un tag comme @v4 est plus lisible dans un exemple, mais ne fournit pas la même immutabilité qu’un SHA.

  • Sur une pull request provenant d’un fork, n’expose aucun secret de déploiement et n’accorde pas de permission d’écriture par défaut.
  • Évite d’exécuter du code non fiable dans un workflow privilégié tel que pull_request_target sans séparation et examen de sécurité explicites.
  • Réserve le déploiement de production à une branche protégée et à un environnement avec permissions distinctes, approbation si nécessaire et identifiants temporaires lorsque la plateforme le permet.
  • Ajoute selon le risque l’analyse des dépendances, le scan de secrets, la provenance de l’artefact et un inventaire des composants (SBOM). Un résultat vert n’est utile que si les contrôles couvrent réellement le risque visé.

Exercice : crée une pull request depuis un fork de test et démontre que le job de validation ne peut ni lire les secrets de production ni publier un déploiement. Vérifie ensuite que l’artefact promu correspond au commit validé, sans le reconstruire silencieusement.

Erreurs fréquentes et compromis

  • Tout lancer sans ordre : sépare les contrôles rapides des plus coûteux.
  • Rebuilder pour chaque environnement : promeus un artefact traçable.
  • Ignorer les tests instables : traite leur cause plutôt que masquer les échecs.
  • Accorder trop de droits : applique le moindre privilège.
  • Publier sans contrôle de santé : vérifie le service après livraison.
  • Penser qu’un rollback annule une migration : traite séparément le schéma et les données.

La vitesse, la couverture de tests et le coût de maintenance sont des compromis. N’enlève pas un contrôle critique uniquement pour gagner quelques secondes.

Concevoir une pipeline qui bloque les livraisons risquées

Chaque étape doit produire un résultat vérifiable et échouer de façon visible : installation déterministe, lint, tests, build, puis publication et déploiement. Une étape ultérieure ne doit pas s’exécuter si un contrôle requis échoue. La pipeline doit utiliser le même lockfile que le développement et ne pas dépendre d’un cache comme source de vérité.

# Exemple de séquence de commandes à automatiser
npm ci
npm run lint
npm test -- --run
npm run build

La syntaxe exacte des commandes de test dépend du projet. Vérifie qu’elles terminent dans l’environnement CI et qu’un test en échec renvoie un code de sortie non nul. Une suite qui imprime « failed » mais renvoie zéro ne protège pas la livraison.

Les secrets de déploiement ne sont nécessaires qu’aux jobs qui en ont besoin. Pour les contributions provenant de forks, évite d’exposer des secrets et limite les permissions du jeton CI. Épingle les actions tierces selon la politique de sécurité du dépôt, et exige une approbation explicite avant la production si le risque le justifie.

Conserve l’identifiant du commit, le résultat des tests et la version de l’artefact. Idéalement, le même artefact validé est promu entre environnements ; reconstruire différemment à chaque étape peut introduire un écart entre ce qui a été testé et ce qui est livré. Définis enfin le signal qui déclenche un rollback et vérifie qu’il est observable.

Exercice guidé

Crée un pipeline qui installe les dépendances, exécute le lint, les tests et la compilation. Introduis volontairement une erreur de lint puis un test en échec ; confirme que chaque cas bloque le pipeline. Corrige ensuite et vérifie le retour au vert.

Exercice autonome et critères de réussite

Ajoute la production d’un artefact versionné et un déploiement vers un environnement de test. Documente permissions, secrets, contrôles de santé et procédure de retour arrière.

  • Les changements sont contrôlés avant fusion.
  • Un échec de lint, test ou build bloque le pipeline.
  • L’artefact est relié à un commit identifiable.
  • Les secrets ne sont pas exposés aux jobs non fiables.
  • La santé du service est vérifiée après livraison.
  • Les limites du rollback des migrations sont documentées.
