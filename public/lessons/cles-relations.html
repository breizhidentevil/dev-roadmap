4. Bases de données et modélisation

Clés primaires et étrangères

Garantir l’identification des lignes et l’intégrité des relations.

Seconde passe pédagogiqueLot 13 · 2026

Objectifs d’apprentissage

  • Définir une clé primaire et une clé étrangère.
  • Choisir entre identifiant technique et clé métier.
  • Comprendre les relations et les règles de suppression.
  • Prévenir les références orphelines et les doublons.

1. Clé primaire : identité stable

Une clé primaire identifie de façon unique chaque ligne d’une table. Elle ne peut pas être nulle et doit rester stable. Une clé peut être composée de plusieurs colonnes, mais une clé simple est souvent plus facile à référencer dans une application.

Un identifiant technique, comme un entier généré ou un UUID, découple l’identité de la ligne des propriétés métier. Une clé métier, comme un code réglementaire, peut être utile si elle est réellement unique et stable. Le choix dépend du domaine ; il n’existe pas de règle unique valable pour toutes les tables.

2. Clé étrangère : garantir la relation

Une clé étrangère garantit qu’une valeur référencée existe (ou vaut NULL si la relation est facultative). Elle protège l’intégrité même si les données sont écrites par plusieurs services, scripts ou tâches concurrentes. La validation côté application améliore le message utilisateur, mais ne remplace pas la contrainte en base.

CREATE TABLE commandes (
  id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  client_id bigint NOT NULL REFERENCES clients(id)
    ON DELETE RESTRICT,
  cree_le timestamptz NOT NULL DEFAULT now()
);

Choisis la politique de suppression en fonction du domaine : RESTRICT/NO ACTION protège les références, CASCADE supprime les dépendances, et SET NULL conserve l’enfant sans parent si le schéma l’autorise. Ces comportements ne sont pas interchangeables ; évalue aussi les suppressions en masse et l’audit.

3. Relations facultatives et cardinalités

Une clé étrangère déclarée NOT NULL rend la relation obligatoire pour chaque ligne. Si une tâche peut ne pas être affectée, la colonne peut accepter NULL. Cela ne signifie pas que la base accepte une valeur non nulle inexistante : les références présentes doivent toujours respecter la contrainte.

Une clé étrangère simple représente souvent un lien plusieurs-vers-un. Pour une relation plusieurs-à-plusieurs, utilise une table d’association avec deux clés étrangères et, généralement, une contrainte unique sur la paire afin d’empêcher les doublons.

4. Suppression et mise à jour

Quand une ligne référencée est supprimée, la base doit appliquer une règle. RESTRICT ou NO ACTION empêchent une suppression qui violerait la relation ; CASCADE supprime aussi les lignes dépendantes ; SET NULL rend la référence nulle lorsque la colonne le permet. Choisis selon la sémantique métier, pas par commodité.

Une suppression en cascade peut être dangereuse si elle efface un historique ou un grand nombre d’éléments inattendus. Pour les données métier importantes, une désactivation logique ou une politique d’archivage peut être plus appropriée.

5. Index et cohérence

La clé primaire crée un index unique dans PostgreSQL. En revanche, une clé étrangère ne crée pas automatiquement un index sur la colonne référençante. Cet index peut accélérer les jointures et surtout éviter qu’une suppression ou modification du parent doive parcourir toute la table enfant. Il n’est pas systématiquement nécessaire : mesure les requêtes et le coût des écritures.

Les contraintes d’unicité composées sont utiles pour les règles telles que « un utilisateur ne peut appartenir qu’une fois à une équipe » :

CREATE TABLE membres_equipe (
  equipe_id bigint NOT NULL REFERENCES equipes(id),
  utilisateur_id bigint NOT NULL REFERENCES utilisateurs(id),
  PRIMARY KEY (equipe_id, utilisateur_id)
);

Vérifie les doublons existants avant d’ajouter une contrainte unique à une table déjà peuplée. Lors d’une migration, planifie le nettoyage des données et le comportement en cas d’échec.

Erreurs fréquentes

  • Utiliser une valeur modifiable comme identifiant sans raison.
  • Oublier les contraintes parce que le code vérifie déjà la relation.
  • Mettre ON DELETE CASCADE partout sans évaluer les conséquences.
  • Confondre clé étrangère et index de performance.
  • Ne pas imposer l’unicité d’une paire dans une table d’association.

Exercice guidé

Crée les tables users, tasks et task_labels. Chaque tâche a un créateur obligatoire, un responsable facultatif et plusieurs étiquettes. Définis les clés primaires, les clés étrangères et la règle qui empêche d’associer deux fois la même étiquette à une tâche. Justifie les choix de suppression.

Critères de réussite

  • Chaque ligne possède une clé primaire unique.
  • Les références impossibles sont rejetées par la base.
  • Les relations obligatoires et facultatives sont distinguées.
  • Les doublons d’association sont empêchés.
  • Les règles de suppression sont justifiées et testées.
