3. Backend

Codes HTTP et idempotence

Choisir les statuts HTTP, exprimer un contrat d’erreur stable et comprendre quand une requête peut être répétée sans produire plusieurs effets métier.

Tutoriel détailléLot 10 · 2026

Objectifs d’apprentissage

  • Comprendre les grandes familles de statuts HTTP.
  • Choisir un statut adapté au résultat de l’opération.
  • Construire des réponses d’erreur cohérentes.
  • Expliquer l’idempotence et les limites des répétitions de requêtes.
  • Éviter d’utiliser les statuts comme des codes métier arbitraires.

Fil conducteur

Choisis d’abord la sémantique du résultat (succès, erreur client, erreur serveur), puis le statut précis. Le corps de réponse complète le statut mais ne doit pas le contredire.

1. Les cinq familles

Les statuts HTTP sont regroupés par premier chiffre : 1xx information, 2xx succès, 3xx redirection, 4xx problème associé à la requête cliente, et 5xx échec côté serveur ou d’une passerelle. Le statut exprime le résultat du protocole ; le corps peut apporter des détails supplémentaires.

Choisis un statut selon la sémantique définie par HTTP et le contrat de ton API. Un statut correct facilite les clients génériques, la supervision, les caches et le diagnostic. N’utilise pas systématiquement 200 pour toutes les situations en plaçant seulement un champ success: false dans le JSON.

2. Les statuts de succès

200 OK indique que la requête a réussi et qu’une représentation peut être renvoyée. 201 Created convient lorsqu’une ressource a été créée ; un en-tête Location peut indiquer sa cible. 202 Accepted signifie qu’une demande a été acceptée pour traitement, sans affirmer que le travail est terminé. 204 No Content indique un succès sans corps de réponse.

Le choix dépend de la méthode et du contrat. Une tâche asynchrone ne devrait pas renvoyer un message laissant croire que le traitement est déjà achevé si seul son lancement a été confirmé.

3. Les erreurs côté client

400 Bad Request couvre notamment une requête mal formée. 401 Unauthorized indique que l’authentification est requise ou invalide ; une réponse 401 doit inclure l’en-tête WWW-Authenticate décrivant le défi d’authentification applicable. 403 Forbidden indique que le serveur refuse la demande ; il ne doit pas être confondu avec l’absence d’authentification. 404 Not Found indique que la ressource cible n’est pas trouvée ou n’est pas exposée. 409 Conflict convient à certains conflits avec l’état courant ; 422 Unprocessable Content est souvent utilisé pour une représentation comprise mais dont le contenu ne peut être traité.

Ne divulgue pas l’existence d’une ressource sensible si le modèle de sécurité impose de la masquer. Le choix entre 400 et 422, par exemple, doit être stable et documenté plutôt que laissé au hasard de chaque contrôleur.

4. Les erreurs serveur et passerelle

500 Internal Server Error désigne une erreur serveur inattendue. 502 Bad Gateway signale une réponse invalide reçue par un serveur jouant le rôle de passerelle, 503 Service Unavailable une indisponibilité temporaire, et 504 Gateway Timeout un délai dépassé auprès d’une dépendance en amont.

Ne transforme pas chaque erreur de dépendance en 500 sans distinguer la situation, mais n’expose pas non plus les détails internes au client. Journalise le contexte technique protégé et renvoie une réponse sûre, avec un identifiant de corrélation si cela aide le support.

5. Un format d’erreur stable

Une API doit documenter la structure de ses erreurs : type, titre, statut, détail sûr et éventuellement erreurs par champ ou identifiant de corrélation. RFC 9457 définit le format « Problem Details for HTTP APIs », utile pour éviter que chaque endpoint invente sa propre structure.

{
      "type": "https://example.test/problems/validation",
      "title": "Données invalides",
      "status": 422,
      "detail": "Un ou plusieurs champs doivent être corrigés."
    }

Exemple illustratif : l’URL de type doit identifier une catégorie de problème documentée. Ne place pas dans le corps des traces de pile, secrets, requêtes SQL ou informations personnelles inutiles. Les clients doivent pouvoir se baser sur le statut et des champs stables, pas sur le texte du message.

6. Idempotence et répétition des requêtes

Une méthode est idempotente lorsque plusieurs requêtes identiques ont le même effet voulu sur l’état du serveur qu’une seule requête ; les réponses HTTP peuvent néanmoins différer. GET et HEAD sont sûres et idempotentes ; PUT et DELETE sont idempotentes, mais pas sûres. POST n’est pas idempotente par défaut.

Après un délai d’attente ou une coupure réseau, le client peut ignorer si le serveur a déjà appliqué l’opération. Ne répète donc pas aveuglément une création ou un paiement non idempotent. Une API peut définir une clé d’idempotence pour ces opérations : elle doit être liée au client et à l’opération, enregistrée de façon durable avec le résultat, et protégée contre deux requêtes concurrentes portant la même clé. Ce mécanisme relève du contrat applicatif ; HTTP ne l’active pas automatiquement.

Teste la répétition après une réponse perdue, deux requêtes simultanées avec la même clé, la réutilisation de la clé avec un contenu différent et la durée de conservation du résultat. Le contrat doit préciser quels statuts et quel résultat sont renvoyés aux répétitions.

Exercice guidé

Définis les réponses HTTP d’une API de tâches : création réussie, requête invalide, absence de session, permission refusée, identifiant inconnu, conflit de modification et indisponibilité temporaire. Ajoute un scénario où le client perd la réponse après une création et doit déterminer si une répétition est sûre. Écris un tableau de contrat et quelques tests vérifiant statuts, en-têtes, répétitions et structure du corps.

Critères de réussite

  • Chaque scénario utilise un statut sémantiquement adapté.
  • 401 inclut un défi WWW-Authenticate et 401/403 sont distingués.
  • Les réponses de succès respectent la méthode et le résultat réel.
  • La stratégie de répétition est explicite pour les opérations non idempotentes.
  • Les erreurs suivent un format documenté.
  • Aucun détail sensible n’est exposé au client.

Erreurs fréquentes

  • Renvoyer 200 pour un échec métier ou technique.
  • Confondre 401 et 403.
  • Utiliser 202 pour une tâche déjà terminée ou sans traitement réellement accepté.
  • Renvoyer des traces de pile ou détails sensibles.
  • Changer de format d’erreur selon les endpoints sans justification.
