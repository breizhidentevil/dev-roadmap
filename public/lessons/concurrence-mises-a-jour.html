Concurrence et mises à jour perdues

Détecter les conflits lorsque plusieurs utilisateurs modifient la même donnée et choisir entre écrasement, contrôle de version, fusion et verrouillage.

1. Objectifs et prérequis

Une mise à jour perdue se produit lorsque deux opérations lisent un même état, le modifient indépendamment et que l’écriture finale efface une partie du travail précédent. Le problème peut apparaître dans une base de données, une API, un éditeur collaboratif ou un formulaire ouvert dans plusieurs onglets. À la fin, vous saurez repérer cette course, ajouter un contrôle de version et choisir une politique de résolution adaptée au sens des données.

2. Exemple d’une mise à jour perdue

Imaginez un compteur qui vaut 10. Deux requêtes lisent cette valeur. La première calcule 11 et écrit 11 ; la seconde, qui avait elle aussi calculé 11 à partir de l’ancienne valeur, écrit 11. Deux incréments ont été demandés mais le compteur n’a augmenté que d’une unité. La difficulté ne vient pas d’une syntaxe incorrecte : chaque requête était cohérente isolément, mais leur interleaving ne l’était pas.

Une autre situation concerne un document. Alice ouvre la version 4 et modifie le titre. Bob ouvre aussi la version 4 et modifie le contenu. Si chaque formulaire renvoie l’intégralité du document sans vérifier sa version, la dernière sauvegarde peut écraser le changement de l’autre personne, même si elle n’a jamais vu ce changement.

3. Éviter la lecture-modification-écriture naïve

Pour un compteur, l’incrément doit généralement être réalisé par une instruction atomique côté base de données plutôt que par une lecture puis une écriture depuis l’application :

UPDATE counters
SET value = value + 1
WHERE id = :id;

Cette instruction évite la course spécifique à l’incrément dans les conditions normales d’un moteur relationnel. Elle ne suffit pas à protéger tous les invariants métier, mais elle illustre une règle générale : quand l’opération peut être exprimée comme une mutation atomique, laissez le système de stockage l’exécuter au lieu de calculer une nouvelle valeur à partir d’une copie périmée.

Pour les documents, il faut souvent détecter que l’état a changé depuis la lecture. Une colonne de version ou un horodatage fiable peut servir de jeton de concurrence. L’écriture n’est acceptée que si la version actuelle correspond à celle que l’utilisateur avait lue.

4. Contrôle optimiste par version

UPDATE articles
SET title = :title,
    body = :body,
    version = version + 1
WHERE id = :id
  AND version = :expectedVersion
RETURNING id, version;

Avec PostgreSQL, RETURNING permet de récupérer la nouvelle version si une ligne a été modifiée. Si aucune ligne n’est retournée, le serveur ne doit pas annoncer un succès : il peut s’agir d’une version périmée ou d’une ressource absente. Le contrat doit choisir s’il renvoie un conflit ou distingue le cas absent par une vérification adaptée, sans introduire une course dans le contrôle de concurrence.

Une version entière est souvent plus claire qu’un timestamp, car les horloges peuvent avoir une précision limitée ou diverger. Les timestamps restent utiles pour l’affichage, mais ils ne sont pas toujours un jeton de concurrence fiable. Le choix doit garantir que chaque modification pertinente change le jeton observé par le client.

5. Utiliser HTTP : ETag et If-Match

Une API HTTP peut exposer un ETag qui identifie la représentation courante. Le client renvoie ensuite If-Match avec la valeur qu’il a lue. Le serveur ne réalise la modification que si la représentation correspond encore à ce jeton. Cela déplace le contrôle de concurrence dans le contrat HTTP, plutôt que de le laisser comme une convention implicite du frontend.

GET /api/articles/42
ETag: "v7"

PATCH /api/articles/42
If-Match: "v7"
Content-Type: application/json

{ "title": "Nouveau titre" }

Si la ressource a changé entre les deux requêtes, le serveur peut répondre 412 Precondition Failed. Une réponse 409 Conflict est également utilisée par certaines API pour signaler un conflit métier, selon le contrat. Il faut documenter le comportement, et surtout effectuer la comparaison et l’écriture de façon atomique côté serveur.

Pour If-Match, utilisez le validateur fort exact reçu dans l’ETag ; un ETag faible préfixé par W/ ne satisfait pas cette précondition. Si votre API exige une précondition et que le client omet If-Match, vous pouvez documenter une réponse 428 Precondition Required. Le test de concurrence essentiel est : deux clients lisent "v7", le premier écrit et obtient "v8", puis le second envoie encore "v7" et reçoit un échec sans écraser la première modification.

6. Que faire lorsqu’un conflit est détecté ?

Détecter le conflit ne résout pas le problème métier. Plusieurs politiques sont possibles :

  • Demander à l’utilisateur de recharger et de réappliquer ses changements.
  • Afficher une comparaison entre la version initiale, la version actuelle et la modification locale.
  • Fusionner automatiquement les champs indépendants si les règles métier le permettent.
  • Utiliser une structure collaborative spécialisée pour des modifications simultanées à grande échelle.

Ne faites pas de fusion automatique sur la seule base du fait que deux changements concernent des champs différents sans comprendre leurs dépendances. Modifier la date de fin d’un contrat peut dépendre de sa date de début ; changer deux champs séparés peut donc enfreindre une règle métier. La fusion doit être fondée sur les invariants du domaine.

7. Mise à jour partielle et sémantique des champs

Une requête qui transmet seulement les champs modifiés réduit le risque d’écraser des champs sans rapport, mais ne supprime pas tous les conflits. Deux utilisateurs peuvent modifier le même champ ; une règle métier peut dépendre de plusieurs champs ; et la sémantique de null, d’un champ absent ou d’une collection remplacée doit être définie.

Un endpoint PATCH ne garantit pas par lui-même la fusion. Si le serveur reçoit un patch puis le combine avec l’état actuel, il peut préserver les changements indépendants, mais doit toujours contrôler les invariants et décider quoi faire lorsque deux mises à jour touchent la même propriété. Un contrôle de version peut être appliqué au document entier ou à une unité plus fine selon les exigences.

8. Verrouillage pessimiste ou optimiste ?

Le verrouillage pessimiste empêche certaines modifications concurrentes pendant une période. Il peut être approprié pour des opérations courtes où le conflit coûterait cher, mais il ajoute des attentes et un risque de deadlock. Le contrôle optimiste laisse les clients travailler librement, puis rejette une sauvegarde périmée. Il convient souvent aux formulaires et documents où les conflits sont rares et où une résolution utilisateur est acceptable.

Pour des systèmes à forte concurrence, mesurez le taux de conflits et le coût des retries. Si chaque mise à jour échoue régulièrement, un verrouillage, une sérialisation ou un autre modèle de données peut être préférable. Si les conflits sont rares, un jeton de version est souvent plus simple et plus scalable.

9. Erreurs fréquentes

  • Faire confiance au fait que le formulaire était à jour au moment de son ouverture.
  • Mettre à jour toute la ligne sans vérifier sa version.
  • Utiliser un timestamp non fiable comme seul jeton de concurrence.
  • Retourner un succès alors que la requête n’a modifié aucune ligne.
  • Fusionner automatiquement des champs sans vérifier les invariants métier.
  • Confondre un code HTTP de conflit avec une stratégie réelle de résolution.

10. Exercice et critères de réussite

Construisez un endpoint de modification d’article avec un numéro de version. Simulez deux clients qui lisent la version 3. Le premier sauvegarde et produit la version 4 ; le second tente de sauvegarder la version 3. Vérifiez que sa requête est rejetée, que la version du premier client est préservée et que l’API fournit assez d’information pour permettre une résolution explicite.

  • Je sais employer une mise à jour atomique quand elle correspond à la règle métier.
  • Je peux implémenter un contrôle de version et détecter une sauvegarde périmée.
  • Je distingue détection du conflit et politique de résolution.
  • Je choisis une stratégie adaptée au coût et à la fréquence des conflits.

Explications et exemple guidé

Une mise à jour perdue survient lorsque deux acteurs lisent la même version d’une donnée, calculent chacun une modification puis enregistrent successivement leurs résultats : la seconde écriture peut effacer la première. Deux approches courantes sont le verrouillage pessimiste et le contrôle optimiste de concurrence.

UPDATE documents
SET body = :newBody, version = version + 1
WHERE id = :id AND version = :expectedVersion;
-- si rowCount = 0 : version périmée, signaler un conflit

Le contrôle optimiste compare une version ou un ETag au moment de l’écriture. HTTP permet notamment If-Match ; un préconditionnement non satisfait se traduit généralement par 412. L’interface doit alors demander de recharger, fusionner ou réappliquer la modification plutôt que répéter automatiquement la même écriture.

Pièges et limites

  • Piège : lire une version puis faire un UPDATE sans condition atomique.
  • Piège : transformer tout conflit en succès silencieux.
  • Piège : confondre un conflit de concurrence avec une panne transitoire réessayable.
  • Piège : fusionner automatiquement du texte ou des données métier sans règle de domaine explicite.

Exercice

Ajoutez un champ de version à une ressource modifiable. Écrivez le contrat HTTP d’une mise à jour conditionnelle et testez deux clients qui enregistrent simultanément une version initiale identique.

Critères de réussite

  • La vérification de version et l’écriture sont atomiques.
  • Une mise à jour périmée déclenche un conflit explicite.
  • Le client sait recharger ou présenter une résolution de conflit.
  • Les tests prouvent qu’aucune modification concurrente n’est silencieusement perdue.
