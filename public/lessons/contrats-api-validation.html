Contrats d’API et validation des réponses

Définir des contrats explicites entre client et serveur, valider les données à l’exécution et gérer les erreurs de manière prévisible.

1. Objectifs et prérequis

Une API est un contrat entre des composants qui peuvent évoluer séparément. Ce contrat précise les opérations disponibles, les entrées, les réponses, les erreurs et les règles de compatibilité. À la fin, vous saurez documenter une route, distinguer les types statiques de la validation réelle, structurer les erreurs et tester les cas valides et invalides. Il faut connaître HTTP, JSON, les fonctions et les types TypeScript.

2. Décrire le contrat avant l’implémentation

Pour chaque endpoint, précisez la méthode HTTP, le chemin, l’authentification attendue, les paramètres, le corps de requête, les statuts de réponse et les effets de bord. Par exemple, POST /reservations doit décrire les champs obligatoires, les limites de longueur, les formats, la règle métier empêchant deux réservations incompatibles et la réponse renvoyée en cas de conflit.

Un contrat ne se limite pas au schéma JSON. Il inclut la sémantique : l’opération est-elle idempotente ? Une requête échouée a-t-elle pu produire un effet partiel ? Quelles erreurs peuvent être corrigées par l’appelant ? Une documentation OpenAPI permet de décrire les opérations et leurs schémas dans un format exploitable par des outils, mais elle doit rester alignée avec le comportement réel.

3. Types TypeScript et validation runtime

Une interface TypeScript n’est pas présente dans le JavaScript produit. Elle ne vérifie donc pas un JSON reçu du réseau. Ce code est dangereux s’il se contente d’affirmer que la réponse a une forme attendue :

const response = await fetch("/api/user");
const user = await response.json() as User;

L’assertion as User ne contrôle pas le contenu. Si le serveur renvoie {}, le compilateur ne le détectera pas. Traitez les données entrantes comme inconnues et vérifiez leur structure avec une fonction dédiée, un schéma partagé ou une bibliothèque de validation.

type User = { id: string; name: string };

function isUser(value: unknown): value is User {
  if (typeof value !== "object" || value === null) return false;
  if (!("id" in value) || !("name" in value)) return false;
  return typeof value.id === "string"
    && typeof value.name === "string";
}

async function fetchUser(): Promise<User> {
  const response = await fetch("/api/user");
  if (!response.ok) throw new Error(`HTTP ${response.status}`);
  const payload: unknown = await response.json();
  if (!isUser(payload)) throw new Error("Réponse utilisateur invalide");
  return payload;
}

Cet exemple montre le principe. En production, prévoyez aussi les erreurs de réseau, le JSON invalide, les délais, l’annulation et la stratégie de présentation des erreurs. Le message d’exception doit être utile au diagnostic sans exposer de données sensibles.

4. Valider les entrées côté serveur

Le serveur doit considérer toute entrée client comme non fiable, même si le frontend utilise TypeScript et un formulaire qui vérifie les champs. Un appel peut venir d’un script, d’un navigateur modifié ou d’un autre client. Validez le type, la longueur, le format, les limites numériques et les règles métier avant de déclencher des effets de bord.

La validation de forme et la validation métier sont distinctes. Une date peut être au bon format mais appartenir au passé ; un identifiant peut être une chaîne valide mais désigner une ressource inaccessible à cet utilisateur. Vérifiez aussi l’autorisation pour chaque ressource. Une validation réussie ne signifie pas que l’opération est autorisée.

5. Statuts HTTP et structure des erreurs

Choisissez un statut qui reflète la situation : 400 pour une requête mal formée ou invalide selon le contrat, 401 lorsque l’authentification manque ou est invalide, 403 lorsque l’accès est interdit, 404 lorsque la ressource n’est pas trouvée, 409 pour un conflit d’état et une famille 5xx pour les erreurs serveur. La convention exacte doit être documentée et appliquée de manière cohérente.

{
  "error": {
    "code": "RESERVATION_CONFLICT",
    "message": "Le créneau n’est plus disponible",
    "requestId": "req-abc123"
  }
}

Le champ code permet au client de réagir de manière stable ; le message est destiné à l’humain et peut être localisé. Le requestId aide à retrouver l’événement dans les journaux. Ne renvoyez pas de stack trace, de requête SQL ou de secrets dans une réponse publique. Journalisez le détail nécessaire côté serveur avec des contrôles d’accès appropriés.

6. Évolution et compatibilité

Modifier une API peut casser des clients qui ne sont pas déployés en même temps que le serveur. Ajouter un champ facultatif est généralement moins risqué que renommer ou supprimer un champ existant, mais cela dépend aussi des générateurs de clients et de la manière dont les schémas sont validés. Supprimer une valeur d’une union d’états peut casser les consommateurs qui la traitent explicitement.

Avant une modification, identifiez les consommateurs, les champs réellement utilisés, la politique de versionnement et la durée de coexistence nécessaire. Une dépréciation progressive peut laisser le temps de migrer. Les tests de contrat automatisés peuvent vérifier que le serveur et les clients respectent les attentes partagées.

7. Tests du contrat

Testez les succès, les erreurs attendues, les valeurs limites, les champs absents, les types incorrects, les autorisations et les changements de schéma. Un test qui vérifie seulement le statut 200 ne prouve pas que la réponse respecte sa forme ni sa sémantique. Ajoutez des tests négatifs et vérifiez qu’aucun effet de bord ne survient lorsqu’une requête est refusée.

Pour les réponses de grande taille, la pagination et les limites doivent faire partie du contrat. Pour les opérations sensibles ou répétées, précisez les règles d’idempotence et les mécanismes de protection contre les doubles soumissions. Les contrats sont plus utiles lorsqu’ils répondent aux questions qui apparaissent en situation réelle, pas seulement au scénario heureux.

8. Erreurs fréquentes

  • Considérer une interface TypeScript comme une validation des données reçues.
  • Valider uniquement dans le frontend et faire confiance au client côté serveur.
  • Utiliser le même statut HTTP pour des erreurs de nature différente sans convention.
  • Renvoyer des détails internes ou des données sensibles dans les erreurs.
  • Modifier un contrat sans identifier ses consommateurs.
  • Tester uniquement le scénario de réussite.

9. Exercice

Définissez le contrat d’un endpoint POST /reservations avec un identifiant de créneau et une date. Écrivez les réponses attendues pour une requête valide, une entrée invalide, un utilisateur non authentifié et un conflit de réservation. Implémentez ou simulez une validation runtime et ajoutez des tests pour un champ absent, une date invalide et une réponse serveur mal formée côté client.

10. Critères de réussite

  • Je peux décrire les entrées, sorties, erreurs et effets de bord d’un endpoint.
  • Je distingue les types TypeScript de la validation à l’exécution.
  • Je valide les entrées côté serveur et vérifie l’autorisation.
  • Je choisis des statuts et des erreurs cohérents et documentés.
  • Je teste les cas limites et pense à la compatibilité lors de l’évolution.

Explications et exemple guidé

Un type TypeScript disparaît à l’exécution : il ne valide ni un JSON reçu d’un client ni une réponse reçue d’un fournisseur. Traitez toute donnée externe comme inconnue, validez-la à la frontière et convertissez-la ensuite vers un modèle interne fiable.

import { z } from 'zod';
const CreateUser = z.object({
  email: z.string().email(),
  displayName: z.string().trim().min(1).max(80)
}).strict();

const parsed = CreateUser.safeParse(request.body);
if (!parsed.success) {
  return response.status(400).json({ code: 'INVALID_REQUEST' });
}
const command = parsed.data; // valeur validée et normalisée

Le contrat doit préciser champs obligatoires, nullabilité, formats, limites, codes HTTP et compatibilité des évolutions. La validation des requêtes et celle des réponses de fournisseurs sont deux frontières différentes. Évitez de renvoyer les détails internes de validation au client si cela expose des informations sensibles.

Pièges et limites

  • Piège : croire qu’une interface TypeScript remplace la validation runtime.
  • Piège : accepter des propriétés inconnues sans stratégie claire de compatibilité.
  • Piège : utiliser le même schéma interne comme réponse publique et exposer des champs privés.
  • Piège : modifier silencieusement des données sans décider si la normalisation fait partie du contrat.

Exercice

Décrivez le contrat d’une création de commande : schéma d’entrée, erreurs de validation, réponse réussie et schéma de réponse. Ajoutez un test où le fournisseur renvoie un JSON malformé ou un champ de type inattendu.

Critères de réussite

  • Les données externes sont validées à l’exécution.
  • Les erreurs ont un format stable sans fuite de détails internes.
  • Le contrat distingue entrée, modèle métier et sortie publique.
  • Les tests couvrent champs manquants, types incorrects, valeurs limites et réponse fournisseur invalide.
