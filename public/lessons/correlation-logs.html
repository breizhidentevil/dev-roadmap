Corrélation des logs

Structurer les journaux et les relier aux requêtes pour accélérer le diagnostic sans exposer d’informations sensibles.

Leçon approfondieThéorie · pratique · validation

Objectifs d’apprentissage

À la fin de cette leçon, tu dois pouvoir expliquer les concepts avec tes propres mots, choisir une approche adaptée à un besoin réel et justifier tes choix à partir de contraintes observables.

  • Définir le vocabulaire essentiel et le problème que la compétence résout.
  • Appliquer les principes dans un exemple pratique et identifier les limites.
  • Vérifier le résultat avec des critères explicites plutôt qu’une impression subjective.

1. À quoi servent les logs corrélés ?

Un journal d’application est une suite d’événements décrivant ce qui s’est produit : démarrage, requête reçue, règle refusée, dépendance indisponible ou tâche terminée. Les logs deviennent difficiles à exploiter lorsque chaque composant écrit un format différent, que les messages sont uniquement du texte libre ou que l’on ne peut pas relier les événements d’une même requête.

La corrélation consiste à ajouter des identifiants partagés afin de retrouver tous les événements pertinents. Un identifiant de requête permet de suivre un traitement à travers plusieurs lignes de log ; un trace ID peut relier ces logs à une trace distribuée. Ce ne sont pas des mécanismes d’autorisation et ils ne doivent pas être considérés comme secrets. Leur but est d’améliorer le diagnostic.

Un bon système de logs répond à des questions opérationnelles : quel composant a échoué, quand, dans quelle opération et avec quelle conséquence ? Il n’a pas besoin de conserver le corps complet de chaque requête. Collecter trop de détails augmente le coût, le bruit et le risque de fuite de données.

2. Préférer des logs structurés

Un message texte comme « erreur lors du paiement » est lisible, mais difficile à filtrer de façon fiable. Un log structuré en JSON sépare les champs : horodatage, niveau, service, environnement, message, request ID, trace ID et code d’erreur. Les champs stables facilitent la recherche et les agrégations.

{
  "timestamp": "2026-10-10T12:00:00Z",
  "level": "error",
  "service": "orders-api",
  "environment": "production",
  "message": "payment_provider_timeout",
  "request_id": "req-example-42",
  "trace_id": "trace-example-7",
  "duration_ms": 1800
}

Ces valeurs sont fictives et illustratives. Choisis une convention de nommage et garde-la stable entre services. Le niveau doit refléter l’action nécessaire : debug pour l’investigation temporaire, info pour les événements normaux significatifs, warn pour une anomalie récupérable et error pour un échec nécessitant une attention. Les niveaux ne remplacent pas un code d’erreur précis.

Les logs doivent être exploitables par une machine et compréhensibles par un humain. Évite les phrases différentes pour chaque code de résultat si un champ normalisé peut porter l’information. N’enregistre pas le même événement à tous les niveaux de la chaîne : un timeout peut être logué comme erreur dans plusieurs couches et produire une alerte en double.

3. Propager l’identifiant de corrélation

À l’entrée d’une requête, le serveur peut générer un identifiant interne ou accepter un identifiant fourni selon une politique contrôlée. Si un identifiant externe est accepté, borne sa longueur et filtre les caractères problématiques afin d’éviter les injections dans les logs. Il ne faut pas laisser une valeur arbitrairement longue ou contrôlée par le client polluer les journaux.

Le contexte doit ensuite suivre le traitement asynchrone et les appels sortants. Dans un service web, cela peut être géré par un middleware et un contexte d’exécution ; dans une file de messages, il faut transmettre les métadonnées pertinentes avec le message. Quand les logs sont liés à une trace OpenTelemetry, les champs de trace peuvent être ajoutés automatiquement par le SDK ou l’intégration de journalisation.

Ne confonds pas un request ID avec un trace ID : le premier identifie généralement une requête à une frontière donnée ; le second peut couvrir un parcours distribué plus large, avec plusieurs services et spans. Définis clairement leur portée. Si une tâche se détache de la requête initiale, garde un lien causal sans prétendre qu’elle s’exécute toujours dans le même cycle HTTP.

4. Choisir quoi journaliser

Journalise les événements qui permettent de comprendre le comportement et d’agir : démarrage, arrêt, changements de configuration significatifs, échecs d’authentification selon la politique de sécurité, erreurs inattendues, échecs de dépendance et résultats importants. Pour une requête HTTP, la méthode, le nom de route, le statut et la durée sont souvent plus utiles que l’URL complète avec tous ses paramètres.

Évite les mots de passe, jetons d’accès, cookies de session, clés API, données de paiement et données personnelles non nécessaires. Les informations sensibles doivent être exclues à la source, pas seulement masquées dans un tableau de bord. Si des données métier sont indispensables au diagnostic, définis une liste autorisée, une justification, une durée de conservation et des droits d’accès.

Les logs peuvent aussi être manipulés par un utilisateur si les valeurs entrantes ne sont pas encodées correctement. Utilise un sérialiseur fiable, protège les sauts de ligne et autres caractères de contrôle selon le format, et limite les champs. La journalisation est une surface d’attaque et un système de données à part entière.

5. Coût, bruit et diagnostic

Une stratégie utile prévoit le volume, la rétention, la rotation, l’indexation et les droits d’accès. Les logs très détaillés sont précieux en développement mais peuvent être trop coûteux en production. Un niveau de debug activé partout peut saturer le stockage et rendre les événements importants difficiles à repérer. Les échantillons et les limites de débit peuvent aider, mais ne doivent pas supprimer les événements de sécurité critiques.

Lors d’un incident, recherche d’abord par trace ID ou request ID, puis examine la séquence temporelle, le service et le code d’erreur. Vérifie le fuseau horaire et la synchronisation des horloges : des horodatages incohérents compliquent l’ordre apparent des événements. Relie les logs aux métriques pour savoir si le cas est isolé ou généralisé.

  • Ne logue pas chaque détail « au cas où ».
  • Ne transforme pas une erreur récupérée en alerte critique sans contexte.
  • Ne laisse pas les clients imposer sans validation l’identifiant de corrélation.
  • Ne compte pas sur les logs pour reconstruire des données métier qui auraient dû être stockées durablement.

6. Exercice pratique

Crée trois logs structurés pour une requête qui échoue : entrée dans l’API, timeout du prestataire, réponse HTTP finale. Fais circuler le même request ID et le même trace ID. Ajoute un code d’erreur, une durée et le nom du service, mais aucun secret. Puis écris deux requêtes de recherche conceptuelles : retrouver un parcours donné et compter les timeouts par service sur quinze minutes.

Critères de réussite

  • Je peux expliquer la différence entre request ID et trace ID.
  • Je produis des logs structurés avec des champs stables.
  • Je propage le contexte aux appels et tâches asynchrones pertinents.
  • Je limite les données sensibles, le bruit et le volume.
  • Je peux retrouver un parcours complet et relier ses logs aux métriques.

Atelier approfondi — corréler les journaux sans les rendre dangereux

Objectifs pédagogiques

  • Distinguer identifiant de requête, trace ID et identifiant métier.
  • Définir un schéma de logs structurés interrogeable.
  • Protéger les secrets et les données personnelles dans les journaux.

Schéma stable

Émettre timestamp, niveau, service, environnement, événement et identifiants de corrélation sous forme structurée.

Propagation

Créer ou accepter un identifiant de corrélation selon une règle documentée; ne pas faire confiance sans validation à une valeur fournie par un client.

Recherche

Une requête de diagnostic doit pouvoir filtrer par trace ID, service, fenêtre temporelle et code d’erreur.

Sécurité

Masquer ou exclure mots de passe, tokens, données bancaires et contenus sensibles. Définir rétention, contrôle d’accès et audit.

Signal utile

Préférer un événement explicite avec champs stables à un message libre ambigu; éviter les identifiants à forte cardinalité comme labels métriques.

Exercice pratique

Proposer un format JSON pour une erreur de commande propagée sur trois services. Fournir une requête de recherche et une règle de masquage des données sensibles.

Critères de réussite

  • Les champs de corrélation sont cohérents de bout en bout.
  • Les logs sont structurés et horodatés.
  • Les secrets et données personnelles sont exclus ou masqués.
  • Une procédure de recherche permet de retrouver une requête.
