5. Sécurité applicative

Configuration de CORS

Contrôler les origines autorisées à lire les réponses du serveur.

Tutoriel approfondiSécurité applicative

Objectifs d’apprentissage

À la fin de cette leçon, tu dois pouvoir expliquer ce qu’est une origine, diagnostiquer une erreur CORS dans le navigateur et configurer une liste d’origines autorisées sans ouvrir inutilement l’API.

  • Distinguer origine et site : schéma, hôte et port composent l’origine.
  • Comprendre les requêtes simples, les pré-vérifications OPTIONS et les en-têtes CORS.
  • Éviter de confondre CORS avec l’authentification ou une protection contre tous les appels malveillants.

1. Le problème que CORS résout

Les navigateurs appliquent la politique de même origine : un script chargé depuis https://app.example ne peut normalement pas lire librement la réponse d’un serveur situé sur une autre origine, par exemple https://api.example. CORS est un mécanisme par lequel le serveur indique au navigateur quelles origines peuvent lire la réponse.

Une origine est le triplet schéma + hôte + port. Ainsi, http://localhost:3000 et http://localhost:5173 sont deux origines différentes. Le chemin ne fait pas partie de l’origine.

Point essentiel : CORS est appliqué par les navigateurs. Il ne remplace ni une vérification de session, ni une autorisation côté serveur, ni une limitation de débit. Un script côté serveur ou un outil en ligne de commande n’est généralement pas bloqué par la politique CORS du navigateur.

2. Comment se déroule l’échange

Pour certaines requêtes, le navigateur envoie directement la requête et vérifie les en-têtes de la réponse. Pour d’autres, notamment certaines méthodes comme PUT, des en-têtes personnalisés ou certains types de contenu, il envoie d’abord une pré-vérification OPTIONS. Le serveur doit alors autoriser l’origine, la méthode et les en-têtes demandés.

Access-Control-Allow-Origin: https://app.example
Access-Control-Allow-Methods: GET, POST, PUT
Access-Control-Allow-Headers: Content-Type, Authorization
Vary: Origin

Vary: Origin doit accompagner toutes les variantes d’une réponse dont les en-têtes CORS dépendent de l’origine, y compris lorsqu’une origine est refusée ou absente ; sinon un cache intermédiaire peut réutiliser une variante construite pour une autre requête. Pour les réponses de pré-vérification OPTIONS, ajoute aussi Access-Control-Request-Method et Access-Control-Request-Headers à Vary, car le résultat dépend de ces valeurs.

3. Configurer une liste explicite

Dans un backend, pars d’une liste d’origines exactes et contrôlées par ton organisation. Exemple conceptuel en Node/Express :

const allowedOrigins = new Set([
  "https://app.example",
  "https://admin.example"
]);
const allowedMethods = new Set(["GET", "POST", "PUT", "DELETE"]);
const allowedHeaders = new Set(["content-type", "authorization"]);

app.use((req, res, next) => {
  const origin = req.get("Origin");
  const originAllowed = Boolean(origin && allowedOrigins.has(origin));

  // Ajouter Vary sur toutes les variantes, y compris les refus, sans écraser
  // d’autres dimensions de cache déjà définies par Express ou un middleware.
  res.vary("Origin");
  if (req.method === "OPTIONS") {
    res.vary("Access-Control-Request-Method");
    res.vary("Access-Control-Request-Headers");
  }

  if (originAllowed) {
    res.setHeader("Access-Control-Allow-Origin", origin);
    res.setHeader("Access-Control-Allow-Methods", [...allowedMethods].join(", "));
    res.setHeader("Access-Control-Allow-Headers", [...allowedHeaders].join(", "));
  }

  const requestedMethod = req.get("Access-Control-Request-Method");
  if (req.method === "OPTIONS" && requestedMethod) {
    const requestedHeaders = (req.get("Access-Control-Request-Headers") || "")
      .split(",")
      .map((header) => header.trim().toLowerCase())
      .filter(Boolean);

    if (!originAllowed || !allowedMethods.has(requestedMethod.toUpperCase()) ||
        !requestedHeaders.every((header) => allowedHeaders.has(header))) {
      return res.sendStatus(403);
    }
    return res.sendStatus(204);
  }

  next();
});

Cet extrait illustre une politique restrictive : une pré-vérification ne reçoit 204 que si l’origine, la méthode demandée et tous les en-têtes demandés sont autorisés ; sinon, elle est refusée. Adapte les ensembles à ton contrat. Le middleware est pédagogique, pas prêt à copier tel quel en production : une bibliothèque CORS maintenue gère mieux les cas particuliers et la fusion des valeurs Vary. Si l’API utilise des cookies, configure aussi explicitement les identifiants et n’utilise jamais le joker pour l’origine.

4. Cookies et identifiants

Si une application doit envoyer des cookies à une API cross-origin, le navigateur et le serveur doivent être configurés pour les requêtes avec identifiants. Le serveur doit répondre avec une origine explicite et Access-Control-Allow-Credentials: true ; la combinaison avec Access-Control-Allow-Origin: * n’est pas autorisée pour les réponses avec identifiants.

Les cookies doivent aussi avoir des attributs appropriés, notamment Secure et généralement HttpOnly pour les cookies de session. CORS ne prévient pas à lui seul les attaques CSRF : il faut une défense adaptée au modèle d’authentification.

Procédure de diagnostic CORS

Diagnostique CORS depuis l’onglet Réseau du navigateur. Vérifie d’abord l’URL de l’API et l’en-tête Origin, puis distingue la requête réelle de la pré-vérification OPTIONS. Une pré-vérification refusée peut empêcher l’envoi de la requête réelle ; une réponse réelle dépourvue des bons en-têtes peut au contraire être envoyée mais rester illisible pour le script.

  1. Comparer l’origine exacte (schéma, hôte, port) avec la liste configurée.
  2. Pour OPTIONS, vérifier la méthode et les en-têtes demandés, ainsi que le code de réponse.
  3. Pour les cookies, vérifier à la fois le mode credentials du client, Access-Control-Allow-Credentials: true et une origine explicite ; le joker * ne convient pas à ce cas.
  4. Confirmer que Vary: Origin est présent sur les variantes autorisées comme refusées ; pour OPTIONS, vérifier aussi les dimensions de pré-vérification et la conservation des autres valeurs Vary.

Ne corrige pas le problème en reflétant aveuglément toute valeur Origin. Le serveur doit continuer à authentifier et autoriser chaque requête, même si CORS autorise le navigateur à lire la réponse.

5. Erreurs fréquentes et diagnostic

  • Autoriser toutes les origines par réflexe : cela expose plus largement les réponses lisibles par des sites tiers.
  • Réfléchir toute valeur de Origin : renvoyer automatiquement l’origine fournie revient à autoriser potentiellement n’importe quel site.
  • Oublier OPTIONS : la pré-vérification peut échouer avant l’appel métier.
  • Traiter CORS comme une permission métier : l’API doit toujours authentifier l’utilisateur et vérifier son droit sur la ressource.
  • Lire seulement le message JavaScript : examine dans l’onglet Réseau la requête, la pré-vérification et les en-têtes de réponse.

Le navigateur masque souvent le corps d’une réponse à JavaScript si CORS échoue ; cela ne signifie pas nécessairement que le serveur n’a pas reçu la requête.

Exercice guidé

Une interface tourne sur http://localhost:5173 et appelle une API sur http://localhost:3000. Autorise uniquement cette origine pour les requêtes de développement, puis vérifie :

  1. un GET simple ;
  2. un POST avec Content-Type: application/json et sa pré-vérification ;
  3. un appel depuis une origine non autorisée ;
  4. une requête qui tente d’accéder à une ressource sans permission métier.

Observe les en-têtes dans les outils développeur du navigateur. N’utilise pas l’absence de message d’erreur comme unique preuve.

Exercice autonome et critères de réussite

Configure CORS pour deux origines de production et une origine de développement activée uniquement en environnement local. Documente les méthodes, en-têtes et besoins éventuels en cookies autorisés.

Réussite :

  • une origine inconnue ne reçoit pas un en-tête d’autorisation valide ;
  • les pré-vérifications nécessaires aboutissent avec les seules méthodes et en-têtes requis ;
  • aucun wildcard incompatible avec les identifiants n’est utilisé ;
  • les contrôles d’authentification et d’autorisation restent actifs indépendamment de CORS ;
  • les scénarios sont vérifiés dans un navigateur et consignés.
