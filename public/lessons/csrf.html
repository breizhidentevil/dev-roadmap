5. Sécurité applicative

Prévention des attaques CSRF

Protéger les opérations authentifiées contre les requêtes forgées déclenchées depuis un autre site.

Tutoriel approfondiBackend et données

Objectifs d’apprentissage

  • Expliquer pourquoi une session par cookie peut être utilisée involontairement par le navigateur.
  • Protéger les opérations qui modifient l’état contre les requêtes forgées.
  • Comprendre le rôle complémentaire des jetons CSRF, de SameSite et de la vérification d’origine.

1. Le mécanisme de la CSRF

Une attaque Cross-Site Request Forgery (CSRF) pousse le navigateur d’un utilisateur authentifié à envoyer une requête vers un site où il possède une session. Si le navigateur joint automatiquement le cookie de session et que le serveur ne vérifie pas l’intention de l’utilisateur, une action peut être exécutée sans consentement explicite.

Le risque concerne surtout les opérations qui modifient l’état : changement d’adresse, création d’un paiement ou modification de paramètres. Les requêtes GET ne doivent pas modifier l’état. Une API qui utilise uniquement un jeton d’accès dans un en-tête explicitement ajouté par le code client présente un profil différent d’une application qui s’appuie automatiquement sur les cookies ; il faut néanmoins analyser l’architecture complète.

2. Jetons CSRF et vérification de l’origine

Pour les applications utilisant une session par cookie, une défense courante consiste à générer un jeton imprévisible lié à la session ou à une requête, puis à exiger sa présence dans un champ de formulaire ou un en-tête personnalisé. Un site tiers ne doit pas pouvoir lire facilement ce jeton à cause de la politique de même origine. Le serveur vérifie le jeton avant d’exécuter l’action.

Vérifie aussi les en-têtes Origin ou, si nécessaire, Referer contre une liste d’origines de confiance. Pour une application à session cookie, conserve de préférence le jeton CSRF recommandé par le framework et utilise le contrôle d’origine comme défense complémentaire. Un contrôle d’origine seul ne doit être retenu qu’avec une politique documentée, une gestion explicite des en-têtes absents et une analyse des clients/proxys légitimes ; ne suppose pas qu’il remplace automatiquement le jeton.

Ne crée pas un jeton CSRF prévisible ni un simple jeton global réutilisé sans lien avec le contexte attendu. Utilise le mécanisme recommandé par le framework plutôt qu’une implémentation cryptographique maison.

3. Cookies SameSite et limites

L’attribut SameSite réduit l’envoi de cookies dans certains contextes intersites. Lax constitue souvent un bon point de départ ; Strict est plus restrictif mais peut gêner certains parcours, et None exige généralement Secure. Les comportements exacts dépendent des navigateurs et du flux d’authentification.

SameSite ne remplace pas systématiquement les jetons CSRF : des scénarios intersites, des sous-domaines ou des changements d’architecture peuvent modifier le risque. Associe les protections à des cookies Secure et HttpOnly lorsque c’est approprié, et n’autorise pas les mutations par GET. Une protection CSRF ne protège pas contre une XSS qui s’exécute déjà dans l’origine de confiance.

Décider si une route est exposée à la CSRF

Classe chaque endpoint selon son effet et la manière dont le navigateur transmet l’authentification. Une opération qui modifie l’état ne doit pas être accessible par GET ; les opérations sensibles devraient aussi exiger une réauthentification ou une confirmation adaptée au risque. Le contrôle CSRF doit être appliqué côté serveur avant la mutation, et non seulement lors de la construction du formulaire.

CORS n’est pas une protection CSRF générale : certaines requêtes peuvent être envoyées même si le script tiers ne peut pas lire la réponse. De même, une XSS sur le site peut contourner une partie des protections CSRF, car le script s’exécute dans l’origine de confiance.

Erreurs fréquentes

  • Penser que CORS suffit à empêcher toutes les requêtes CSRF.
  • Autoriser des mutations via GET.
  • Considérer SameSite comme une protection universelle, indépendamment du contexte.
  • Accepter les requêtes mutantes sans jeton ni contrôle d’origine dans une application à session cookie.
  • Oublier que les requêtes légitimes peuvent venir de plusieurs origines maîtrisées et doivent être configurées explicitement.

Exercice

Une application utilise un cookie de session pour modifier l’adresse e-mail d’un compte. Décris les contrôles à appliquer côté serveur, les attributs du cookie et les tests permettant de vérifier qu’une page tierce ne peut pas déclencher la modification. Explique la différence entre CSRF et XSS.

Critères de réussite

  • La mutation n’est pas déclenchable par une requête GET.
  • Le serveur vérifie un jeton CSRF et/ou une politique d’origine adaptée à l’architecture.
  • SameSite est configuré comme défense complémentaire.
  • Les tests couvrent les jetons manquants ou invalides et les origines non autorisées.
  • La différence entre action forgée depuis un autre site et script exécuté dans l’origine est claire.
