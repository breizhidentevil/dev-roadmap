3. Backend

Cycle requête-réponse d’une application Web

Suivre une requête depuis le navigateur jusqu’à la réponse, en distinguant transport, logique métier, accès aux données et gestion des échecs.

Tutoriel détailléLot 10 · 2026

Objectifs d’apprentissage

  • Décrire les étapes d’une requête Web.
  • Distinguer client, serveur applicatif et base de données.
  • Identifier les points où traiter validation, erreurs et autorisations.
  • Diagnostiquer un échec en suivant le trajet de la requête.

Fil conducteur

Pour chaque requête, identifie successivement qui l’a reçue, quelles validations ont eu lieu, quelle règle métier a été appliquée, quelles dépendances ont été appelées et quelle réponse a été produite.

1. Du navigateur au serveur

Lorsqu’un utilisateur ouvre une page ou déclenche une action, le navigateur prépare une requête HTTP. Elle contient notamment une méthode, une cible, des en-têtes et parfois un corps. La résolution DNS permet de trouver l’adresse du serveur ; une connexion réseau est ensuite établie, généralement protégée par TLS pour HTTPS. Des caches, proxies ou réseaux de distribution peuvent intervenir avant l’application.

La réponse contient un statut HTTP, des en-têtes et éventuellement un corps. Une réponse 200 indique un succès selon la sémantique de la requête, tandis que 404 indique qu’une ressource n’a pas été trouvée. Un statut de succès ne garantit pas à lui seul que le contenu métier est correct.

2. Traitement côté serveur

Le serveur reçoit la requête et la fait passer par une chaîne de traitement : routage, middleware, authentification, autorisation, validation, logique métier et accès aux données. L’ordre compte. Par exemple, une mutation protégée doit vérifier l’identité et les droits avant d’effectuer l’opération sensible.

Requête HTTP
      → routage
      → authentification
      → autorisation
      → validation
      → logique métier
      → base de données
      → réponse HTTP

Cette séquence est illustrative : une application peut ajouter un cache, une file de tâches, un service tiers ou une transaction. Les vérifications de sécurité doivent rester côté serveur, même si l’interface masque déjà les actions interdites.

3. Accès aux données et cohérence

La logique métier transforme une demande utilisateur en opération du domaine : créer une commande, modifier un profil ou rechercher des produits. Elle appelle ensuite un dépôt ou une couche d’accès aux données. Une base relationnelle peut appliquer contraintes et transactions pour protéger la cohérence en cas d’erreur ou d’accès concurrent.

Ne conserve pas une transaction ouverte pendant une longue opération réseau sans nécessité. Définis ce qui doit réussir ou échouer ensemble, et traite explicitement les conflits, les données absentes et les indisponibilités. Pour une opération longue, une tâche asynchrone peut être préférable à une requête HTTP qui reste ouverte.

4. Construire la réponse

Le serveur transforme le résultat en réponse adaptée au contrat de l’API : statut, en-têtes et représentation JSON ou HTML. Les erreurs doivent avoir une structure cohérente, ne pas exposer les traces internes et permettre au client de comprendre quoi faire ensuite. Les détails techniques restent dans les journaux protégés.

Le navigateur interprète la réponse, met à jour l’interface et peut déclencher d’autres requêtes. Un seul clic visible peut donc provoquer plusieurs échanges. Dans les outils de développement, observe méthode, URL, statut, durée, taille et initiateur avant de conclure à un problème frontend ou backend.

5. Diagnostiquer par étapes

Commence par reproduire le problème et noter la requête concernée. Vérifie ensuite si elle part du navigateur, si elle atteint le serveur, à quelle étape elle échoue et si une dépendance est impliquée. Un identifiant de corrélation peut relier les journaux du serveur, les appels aux services et les opérations en base sans journaliser de données sensibles.

Mesure séparément les temps réseau, applicatif et base de données. Un délai global élevé ne prouve pas que le SQL est lent : l’attente peut provenir d’un service tiers, d’un verrou, d’un pool de connexions saturé ou d’un transfert volumineux.

Exercice guidé

Trace une requête de connexion ou de recherche depuis le navigateur jusqu’à une source de données simulée. Pour chaque étape, indique les entrées, les contrôles, les erreurs possibles et les informations à journaliser. Simule un statut 400, un statut 401, une erreur serveur et une dépendance lente.

Critères de réussite

  • Le trajet complet de la requête est documenté.
  • Validation et autorisation sont exécutées côté serveur.
  • Les erreurs sont traduites en statuts cohérents.
  • Les journaux permettent de corréler les étapes sans exposer de secrets.
  • Le diagnostic distingue réseau, application et dépendances.

Erreurs fréquentes

  • Diagnostiquer uniquement à partir du message visible dans l’interface.
  • Confondre statut HTTP réussi et résultat métier correct.
  • Faire confiance à la validation côté navigateur.
  • Exposer une trace de pile ou un secret dans la réponse.
  • Journaliser des mots de passe, jetons ou données personnelles inutiles.

Repère pratique. La base de données est une frontière de fiabilité : une requête peut être lente, échouer ou retourner zéro ligne. Définis les délais d’attente, les limites de résultats et les transactions selon l’invariant métier ; ne transforme pas un délai dépassé en succès supposé.
