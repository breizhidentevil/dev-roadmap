6. Tests, débogage et qualité

Débogage méthodique

Localiser la cause d’un défaut en formulant des hypothèses, en réduisant le problème et en vérifiant chaque résultat.

Tutoriel approfondiQualité et tests

Objectifs et prérequis

Le débogage consiste à expliquer un comportement observé, pas à essayer des changements au hasard jusqu’à ce que l’erreur disparaisse. Tu apprendras à reproduire le défaut, formuler des hypothèses vérifiables, inspecter l’exécution et confirmer la cause avant de modifier le code.

  • Réduire un problème à un cas reproductible.
  • Choisir entre logs, points d’arrêt, inspection réseau et analyse de données.
  • Vérifier la correction avec un test et rechercher les effets secondaires.

1. Décrire le défaut précisément

Commence par distinguer le résultat attendu du résultat observé. Note les étapes, les données utilisées, l’environnement, le navigateur ou la version de runtime, l’heure éventuelle et la fréquence du défaut. « La page ne marche pas » est trop vague ; « après l’envoi du formulaire avec un titre vide, l’interface affiche un succès alors que l’API renvoie 400 » permet de cibler le problème.

Essaie de reproduire le défaut de manière fiable. Réduis ensuite le cas : retire les étapes non nécessaires, remplace les données par un exemple minimal et désactive les dépendances non pertinentes. Un cas minimal facilite la compréhension et devient souvent un excellent test de régression.

2. Formuler des hypothèses testables

À partir des symptômes, énumère quelques causes plausibles, puis cherche une observation qui permet de les départager. Exemple : si une liste est vide, les causes possibles incluent une réponse API vide, un filtre incorrect, une erreur de transformation ou un rendu conditionnel qui masque les éléments.

  1. Vérifier l’onglet Network : la requête part-elle et quel est son statut ?
  2. Inspecter la réponse : les données attendues sont-elles présentes ?
  3. Placer un point d’arrêt après la transformation : la structure a-t-elle changé ?
  4. Inspecter l’état utilisé par le composant : est-il mis à jour ?
  5. Vérifier la condition de rendu et les erreurs de console.

Chaque étape réduit l’espace des causes possibles. Évite de changer simultanément plusieurs éléments : si le résultat change, tu ne sauras pas quelle modification a compté.

3. Utiliser les bons outils

Logs : utiles pour les événements survenus dans un processus ou un environnement distant, à condition d’être structurés et de ne pas exposer de secrets.

Points d’arrêt : suspendent l’exécution pour inspecter variables, pile d’appels et flux de contrôle. Place-les près de la transition où la valeur devient incorrecte, pas uniquement sur la ligne où l’erreur se manifeste.

Onglet Network : permet de vérifier URL, méthode, statut, en-têtes, durée et corps de réponse. Il aide à distinguer un problème frontend d’un problème backend ou réseau.

Stack trace : donne la chaîne d’appels associée à une exception. Lis-la depuis l’origine pertinente, et pas seulement depuis la dernière ligne du message. Une erreur affichée dans une bibliothèque peut être déclenchée par une donnée incorrecte fournie par ton code.

4. Suivre une donnée de bout en bout

Dans une application Full Stack, trace la donnée à travers les frontières : formulaire, validation cliente, requête HTTP, validation serveur, logique métier, base de données, réponse et affichage. Vérifie le format à chaque étape. Une date, par exemple, peut être interprétée dans un fuseau différent ; un nombre peut devenir une chaîne ; un champ optionnel peut être absent plutôt que défini à null.

Utilise un identifiant de corrélation pour relier les logs d’une même requête sans enregistrer des données sensibles. Compare la requête réellement envoyée à celle attendue par l’API et inspecte les paramètres de configuration chargés au démarrage.

5. Confirmer la cause et éviter la récidive

Une correction est crédible quand elle explique le symptôme et que l’on peut montrer pourquoi elle le supprime. Après modification, rejoue le cas minimal, exécute les tests pertinents et vérifie les scénarios voisins. Ajoute un test de régression lorsqu’il est possible d’automatiser le défaut.

Évite les « corrections » qui masquent seulement le symptôme : attraper toutes les exceptions sans les traiter, ajouter une attente arbitraire ou désactiver une validation. Si la cause n’est pas certaine, note ce qui est prouvé et ce qui reste une hypothèse.

6. Transformer une enquête en expérience contrôlée

Avant chaque manipulation, écris la prédiction : « si l’hypothèse H est vraie, l’observation O devrait apparaître ». Choisis ensuite une seule expérience qui peut invalider cette hypothèse. Cette discipline évite de confondre une corrélation avec une cause et permet de revenir sur les étapes déjà réfutées.

Pour les défauts intermittents, consigne la fréquence et les conditions de déclenchement. Ne conclus pas à une résolution après une seule exécution réussie : définis à l’avance un nombre d’essais pertinent ou un test déterministe qui couvre la condition.

Erreurs fréquentes

  • Modifier plusieurs variables à la fois sans mesurer l’effet de chaque changement.
  • Se fier uniquement au message d’erreur sans lire la pile d’appels ou le contexte réseau.
  • Déboguer avec des données réelles sensibles copiées dans un environnement non protégé.
  • Ajouter des logs qui modifient fortement le timing d’un bug concurrent.
  • Corriger le symptôme sans identifier la cause racine.
  • Oublier de supprimer les traces temporaires ou de conserver un test de régression.

Exercice guidé

Prends un bug simulé : une liste ne s’affiche pas alors que la requête API semble réussir. Reproduis-le, inspecte la réponse réseau, vérifie la transformation des données et place un point d’arrêt au moment où l’état est mis à jour. Écris une courte chronologie des observations avant de modifier le code.

Une fois la cause trouvée, corrige-la et ajoute un test adapté. Vérifie le cas nominal et un cas voisin, puis supprime les logs de diagnostic qui ne sont plus nécessaires.

Exercice autonome et critères de réussite

Rédige un rapport de débogage pour un défaut réel ou fictif : étapes de reproduction, attendu, observé, hypothèses, observations, cause, correction et vérification.

Réussite : le défaut est reproductible ou ses conditions sont clairement circonscrites ; les hypothèses sont testées séparément ; les outils sont choisis selon le symptôme ; la cause est distinguée du symptôme ; la correction est couverte par un test ou une vérification reproductible.
