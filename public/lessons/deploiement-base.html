7. Environnement, livraison et exploitation

Déployer application et base de données

Mettre en ligne une application et sa base de données avec une configuration reproductible, des contrôles de santé et une procédure de retour arrière.

Tutoriel approfondiCompétence Full Stack

Objectifs et prérequis

Déployer signifie rendre une version exécutable disponible dans un environnement réel, pas seulement copier des fichiers sur un serveur. Il faut fournir l’artefact, la configuration, les accès aux services, le schéma de données attendu, les règles réseau et les moyens de vérifier que le système fonctionne.

  • Décrire les composants nécessaires à l’application.
  • Séparer le code et la configuration de production.
  • Connecter l’application à une base sans exposer celle-ci inutilement.
  • Appliquer les migrations et vérifier le service après livraison.
  • Préparer une procédure de reprise en cas d’échec.

Prérequis : savoir lancer l’application localement, configurer ses variables d’environnement et lire les logs. Les commandes exactes dépendent de la plateforme ; la méthode de diagnostic reste similaire.

1. Cartographier les composants

Avant de choisir un hébergeur, dessine les éléments indispensables : navigateur, serveur HTTP ou proxy, processus applicatif, base de données, stockage de fichiers, services tiers et système de logs. Pour chaque flèche, précise le protocole, le sens de communication et les identifiants nécessaires.

Une application simple peut être déployée sur une seule machine, mais la base ne devrait pas être exposée publiquement sans nécessité. Dans une plateforme gérée, le fournisseur peut prendre en charge une partie des sauvegardes, correctifs ou certificats ; vérifie exactement ce qui est inclus au lieu de supposer que « géré » signifie « sans maintenance ».

Liste aussi les dépendances au démarrage : la base doit-elle être joignable immédiatement ? L’application peut-elle redémarrer sans perte de données ? Les fichiers téléversés sont-ils stockés dans le conteneur éphémère ou dans un stockage persistant ? Ces questions influencent l’architecture de déploiement.

2. Préparer l’environnement de production

Le code livré devrait être identifiable par un commit ou une version. Construis l’artefact à partir d’un dépôt propre et d’un lockfile, puis déploie cet artefact plutôt que de modifier manuellement des fichiers sur le serveur. La configuration propre à l’environnement doit être injectée au lancement.

NODE_ENV=production
PORT=3000
DATABASE_URL=postgres://app:secret@db.internal:5432/app

Ces valeurs illustrent les noms de variables ; ne place pas de vrais secrets dans un fichier suivi par Git ni dans la documentation. Utilise les mécanismes de secrets de l’hébergeur et limite les personnes ou processus qui peuvent les lire. Une URL de base contient souvent un mot de passe : ne l’affiche pas dans les logs et ne l’inclus pas dans un rapport d’incident.

Valide la configuration au démarrage : variables obligatoires présentes, ports dans une plage valide, URL de base compréhensible et mode de production explicite. Une erreur de configuration doit empêcher le lancement plutôt que provoquer un dysfonctionnement plus tard au milieu d’une requête.

3. Base de données, réseau et migrations

Crée un compte applicatif avec les permissions minimales nécessaires. Le compte utilisé par l’application n’a généralement pas besoin de créer des rôles ou de modifier la configuration globale du serveur. Restreins les connexions à la base aux sources prévues et chiffre les communications lorsque le contexte réseau l’exige.

Les migrations doivent être exécutées dans un ordre défini et de préférence par une étape contrôlée du processus de livraison, pas indépendamment par chaque instance qui démarre. Sur un déploiement avec plusieurs instances, une migration concurrente peut entrer en conflit ou bloquer les requêtes. Prévois un mécanisme qui garantit une exécution unique.

Les changements incompatibles exigent une stratégie en plusieurs étapes : ajouter une colonne facultative, déployer le code qui sait gérer les deux formes, migrer les données, puis retirer l’ancien champ dans une livraison ultérieure. Le retour à l’ancienne version du code ne restaure pas automatiquement les données modifiées ni un schéma supprimé.

4. Lancer et vérifier le service

Un processus qui démarre n’est pas nécessairement opérationnel. Prévois un endpoint de santé qui confirme que l’application répond et, si cela correspond à la définition de disponibilité, un contrôle distinct pour les dépendances critiques. Évite qu’un contrôle de santé très strict provoque des redémarrages en boucle pendant une panne temporaire de la base.

Après livraison, vérifie une séquence courte et reproductible :

  1. Le processus ou conteneur est en cours d’exécution.
  2. Les logs de démarrage ne signalent pas d’erreur de configuration ou de connexion.
  3. L’endpoint de santé répond comme prévu.
  4. Un parcours utilisateur non destructif fonctionne de bout en bout.
  5. Les métriques et logs ne montrent pas d’augmentation anormale des erreurs ou de la latence.

Teste aussi depuis l’extérieur de la machine : un service accessible depuis son propre conteneur peut rester inaccessible via le DNS, le proxy ou le pare-feu. Ne te contente pas de vérifier le processus local.

5. Préparer la reprise

Définis à l’avance comment arrêter le trafic, revenir à une version applicative précédente et restaurer la base si nécessaire. Les trois opérations sont différentes. Un rollback de code peut être rapide ; une restauration de données est plus risquée, peut faire perdre des écritures récentes et nécessite souvent une interruption ou une procédure de bascule.

Avant une livraison risquée, vérifie l’existence d’une sauvegarde récente et la possibilité de la restaurer. Une sauvegarde qui n’a jamais été testée ne prouve pas que le service pourra être récupéré. Documente qui peut décider du retour arrière, quels signaux le déclenchent et comment communiquer l’incident.

Erreurs fréquentes et compromis

  • Modifier directement la production : les changements deviennent difficiles à reproduire et à auditer.
  • Exposer la base sur Internet : limite les interfaces réseau et les sources autorisées.
  • Utiliser un compte administrateur pour l’application : applique le moindre privilège.
  • Exécuter les migrations dans chaque instance : centralise et verrouille cette étape.
  • Confondre démarrage et disponibilité : vérifie les parcours et dépendances réels.
  • Supposer qu’un rollback annule les écritures : traite séparément code, schéma et données.

Un déploiement manuel peut convenir à un prototype, mais doit être documenté et répétable. À mesure que le risque augmente, automatise les étapes vérifiables et conserve une validation humaine pour les actions sensibles.

Procédure de livraison et critères de retour arrière

Avant chaque livraison, consigne la version source, l’artefact, la configuration attendue, les migrations à appliquer, la sauvegarde vérifiée et les contrôles après déploiement. Le plan doit être exécutable par une autre personne sans dépendre de connaissances implicites.

ÉtapePreuve attendueSi elle échoue
PréparationArtefact et commit identifiésNe pas promouvoir une version inconnue
MigrationRésultat journalisé, schéma attenduArrêter le déploiement et diagnostiquer
DémarrageProcessus prêt, configuration valideInspecter logs et connectivité
Smoke testRequête non destructive réussieRetirer la version du trafic si nécessaire
SurveillanceErreurs et latence stablesAppliquer le seuil de rollback défini

La stratégie « expand/contract » réduit les risques des migrations incompatibles : ajouter d’abord une structure compatible avec l’ancien et le nouveau code, déployer le code de transition, migrer les données, puis supprimer l’ancien champ dans une version ultérieure. Ne suppose pas qu’un rollback du code annule une migration ou restaure les données.

Les sauvegardes doivent être testées par une restauration dans un environnement isolé. Note la date, la durée, les étapes manuelles, la cohérence obtenue et les limites de perte de données. Une sauvegarde présente mais impossible à restaurer n’est pas un plan de reprise.

Exercice guidé

Prépare une fiche de déploiement pour une API et PostgreSQL : composants, variables nécessaires, accès réseau, migrations, endpoint de santé et commandes ou actions de contrôle. Remplace tous les secrets par des noms de variables ou des valeurs factices.

Exercice autonome et critères de réussite

Déploie une petite application dans un environnement de test et documente la mise à jour vers une nouvelle version. Simule une configuration invalide et une migration en échec, puis décris les étapes de diagnostic et de reprise.

  • L’artefact déployé est associé à une version identifiable.
  • La configuration et les secrets ne sont pas intégrés au code.
  • La base n’est accessible qu’aux clients autorisés.
  • Les migrations ont un ordre et un responsable d’exécution définis.
  • La santé du service est vérifiée après livraison.
  • La procédure de rollback distingue code, schéma et données.
