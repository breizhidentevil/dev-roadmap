Patterns de conception

Un pattern de conception est un vocabulaire partagé pour décrire une structure de solution récurrente. Il aide à communiquer et à comparer des options, mais ne remplace ni le diagnostic du problème ni une conception simple.

Tutoriel approfondiCompétence Full Stack

Objectifs et prérequis

Les patterns décrivent des compromis connus dans des contextes récurrents. Ils ne sont ni des bibliothèques à installer systématiquement, ni des règles imposant une structure identique à tous les projets.

  • Expliquer ce qu’un pattern apporte et ce qu’il coûte.
  • Reconnaître quelques patterns courants dans du code existant.
  • Choisir une solution à partir du problème plutôt que du nom du pattern.
  • Éviter la sur-ingénierie et tester le comportement attendu.

1. Partir du problème, pas du catalogue

Avant d’appliquer un pattern, décrivez la difficulté en une phrase : « plusieurs fournisseurs doivent être appelés derrière un contrat commun », « l’objet doit être construit avec des règles de validation », ou « une opération doit être notifiée à plusieurs abonnés ». Ensuite, comparez la solution la plus simple à une solution structurée.

Un pattern devient utile lorsqu’il réduit le couplage, rend une variation explicite, clarifie un cycle de vie ou permet de tester une partie isolément. Il devient nuisible lorsqu’il ajoute des classes, des indirections ou un vocabulaire que l’équipe doit apprendre sans bénéfice observable.

Les patterns ont souvent des variantes. Il est plus important de comprendre l’intention et les conséquences que de reproduire exactement un diagramme trouvé dans un livre.

2. Patterns de création

Factory : centralise la sélection ou la construction d’un objet lorsque cette décision est non triviale. Par exemple, un service peut choisir un adaptateur de paiement selon une configuration validée. Pour un simple new Report(), une factory dédiée n’est probablement pas utile.

Builder : construit progressivement un objet complexe, notamment lorsque de nombreux paramètres optionnels doivent être validés ensemble. Attention à ne pas créer un builder pour chaque objet de données simple.

Singleton : vise une instance partagée. Il peut simplifier un accès à une ressource, mais introduit souvent un état global qui complique les tests, la concurrence et l’isolation. Une dépendance injectée avec une durée de vie explicite est souvent plus facile à maîtriser.

Le choix doit rendre les contraintes de construction plus visibles, pas simplement ajouter une couche de code.

3. Patterns structurels

Adapter : traduit l’interface d’une bibliothèque externe vers le contrat attendu par l’application. Exemple : transformer les réponses d’un fournisseur de paiement en types internes stables. L’adaptateur isole les changements du fournisseur, mais il doit traiter explicitement les erreurs, les unités et les différences de sémantique.

Facade : propose une interface simplifiée devant plusieurs composants. Elle est utile pour éviter qu’un appelant connaisse l’ordre de plusieurs opérations. Une façade ne doit pas masquer des effets secondaires importants ni devenir une classe « qui fait tout ».

Decorator : ajoute un comportement autour d’un objet respectant le même contrat, par exemple des métriques ou une mise en cache. Il permet de composer des comportements, mais l’ordre des décorateurs peut changer le résultat. Une mise en cache placée avant ou après une vérification d’autorisation n’a pas les mêmes implications.

4. Patterns comportementaux

Strategy : permet de substituer un algorithme derrière un contrat commun. Plusieurs règles de calcul de frais peuvent ainsi être choisies selon le contexte. Si une simple condition contient deux branches stables, des classes de stratégie peuvent être excessives.

Observer : diffuse un événement à plusieurs abonnés. Il convient lorsque les émetteurs ne doivent pas connaître tous les destinataires, mais exige de traiter l’ordre, les erreurs, les doublons et la durée de vie des abonnements. Dans un système distribué, un événement asynchrone ajoute des problèmes de livraison et de cohérence.

Command : représente une action comme un objet ou un message. Il peut faciliter la mise en file, la journalisation ou l’annulation, mais ne fournit pas automatiquement une transaction ou une garantie de livraison.

State : rend explicites les comportements liés aux états d’un objet. Il est utile quand les transitions deviennent nombreuses et que certaines actions sont interdites dans certains états. Une énumération et une machine à états simple suffisent parfois.

5. Comment décider et refactoriser

  1. Écrivez le besoin et les contraintes observables.
  2. Identifiez ce qui varie : algorithme, fournisseur, construction, notification ou état.
  3. Établissez une solution minimale et ses limites.
  4. Comparez le coût du pattern : nouvelles abstractions, navigation, tests et concepts à transmettre.
  5. Ajoutez des tests comportementaux avant la refactorisation.
  6. Appliquez le pattern progressivement et vérifiez que le code appelant est réellement simplifié.

Ne choisissez pas un pattern parce qu’il apparaît dans une liste d’entretien technique. Le bon choix dépend de la taille du problème, du rythme des changements et de l’équipe qui maintiendra le code.

  • Un nom de pattern ne prouve pas que l’implémentation est bonne.
  • Un diagramme classique n’est pas forcément adapté aux paradigmes fonctionnels ou aux frameworks modernes.
  • Plus d’abstractions ne signifie pas automatiquement plus de testabilité.
  • Un pattern mal documenté peut devenir une convention locale que personne ne comprend.

Exercice guidé

Une application calcule les frais de livraison selon trois modes : standard, express et retrait en magasin. Plus tard, une quatrième règle pourrait être ajoutée. Proposez une première implémentation puis une évolution avec Strategy, sans écrire plus d’abstraction que nécessaire.

  1. À partir de combien de variations une stratégie séparée devient-elle intéressante dans votre cas ? Justifiez.
  2. Où valider qu’un mode de livraison est autorisé pour une commande donnée ?
  3. Comment tester chaque règle sans créer une commande HTTP réelle ?
  4. Si les règles ne changent jamais et restent très courtes, quelle solution plus simple conserveriez-vous ?

Critères de réussite : vous formulez le problème avant de nommer le pattern, décrivez ses bénéfices et coûts, conservez les invariants au bon endroit et savez expliquer pourquoi une solution plus simple pourrait suffire.

Atelier de validation : choisir un pattern à partir des forces en présence

Un pattern est utile quand il nomme une structure qui résout un problème récurrent. Il n’est pas un objectif en soi : comparez le coût de l’abstraction au coût réel des changements qu’elle permet.

Exemple : plusieurs fournisseurs de paiement

interface Paiement {
  debiter(montantCentimes: number, reference: string): Promise<"accepte" | "refuse">;
}
class PaiementSimule implements Paiement {
  async debiter(): Promise<"accepte" | "refuse"> { return "accepte"; }
}
async function finaliser(paiement: Paiement, total: number, id: string) {
  return paiement.debiter(total, id);
}

L’interface et les implémentations peuvent illustrer Strategy/port-adapter si plusieurs fournisseurs doivent réellement être substituables. En production, il faut aussi définir idempotence, délais, erreurs ambiguës et rapprochement : le pattern seul ne résout pas ces propriétés.

Décision guidée

  1. Décrivez le changement concret qui provoque la duplication ou le couplage.
  2. Écrivez les invariants qui doivent rester vrais quelle que soit l’implémentation.
  3. Comparez une solution directe, une fonction passée en paramètre et un objet de stratégie.
  4. Ajoutez un test qui utilise deux implémentations sans modifier le code appelant.
  5. Réévaluez l’abstraction si elle exige plus de configuration qu’elle ne retire de complexité.

Pièges et exercice

  • Un Singleton global complique l’isolation des tests et masque les dépendances.
  • Une Factory n’est pas utile si elle ne fait que renommer un constructeur sans politique de création.
  • Ne choisissez pas un pattern seulement parce qu’il figure dans un catalogue.

Exercice : comparez trois implémentations d’un calcul de frais de livraison. Choisissez un pattern uniquement si les variations le justifient et écrivez un test commun aux implémentations.

Critères de réussite : problème formulé avant le nom du pattern, alternative plus simple évaluée, invariants explicites et tests de substituabilité.
