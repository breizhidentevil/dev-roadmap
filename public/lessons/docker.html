7. Environnement, livraison et exploitation

Docker et conteneurs

Construire une image reproductible et exécuter l’application dans un conteneur avec ses ports, volumes et dépendances.

Tutoriel approfondiCompétence Full Stack

Objectifs et prérequis

Une image est un modèle immuable contenant fichiers et métadonnées ; un conteneur est une instance en cours d’exécution avec processus, réseau, variables et couche inscriptible. Les conteneurs Linux partagent le noyau de l’hôte ou de la machine virtuelle qui héberge Docker ; ils ne sont pas des machines virtuelles complètes.

  • Différencier image, conteneur, registre, volume et réseau.
  • Écrire un Dockerfile et exploiter le cache de construction.
  • Publier un port et conserver des données persistantes.
  • Utiliser Compose pour plusieurs services.
  • Réduire taille et risques de l’image.

1. Image et conteneur

Supprimer un conteneur n’est pas supprimer son image. En revanche, les données écrites uniquement dans la couche éphémère du conteneur peuvent disparaître à sa recréation. Les données importantes doivent être placées dans un volume ou un service externe.

docker pull node:22-alpine
docker image ls
docker ps -a
docker run --rm node:22-alpine node --version

Choisis un tag de version explicite plutôt que latest, qui peut changer. Pour une reproductibilité forte, épingler le digest d’une image permet d’identifier précisément son contenu.

2. Construire un Dockerfile

L’ordre des instructions influence le cache. Les manifestes de dépendances changent souvent moins que le code ; les copier avant le reste permet de réutiliser l’installation lorsque seuls les fichiers source changent.

FROM node:22-alpine
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build
ENV NODE_ENV=production
EXPOSE 3000
CMD ["node", "dist/server.js"]

Adapte le point d’entrée, le script de build et le gestionnaire de paquets au projet. npm ci attend un lockfile cohérent. Cet exemple simple peut encore embarquer les dépendances de développement et les sources ; une construction multi-étape peut créer une image finale plus légère.

EXPOSE 3000 documente le port attendu mais ne le publie pas sur l’hôte. Le mapping s’effectue au lancement ou dans Compose.

3. Lancer et diagnostiquer

docker build -t exemple-api:dev .
docker run --rm -p 3000:3000 --name exemple-api exemple-api:dev
docker logs exemple-api
docker inspect exemple-api
docker exec -it exemple-api sh

Le mapping -p 3000:3000 relie généralement le port 3000 de l’hôte à celui du conteneur. L’application doit écouter sur une interface accessible depuis le réseau du conteneur, souvent 0.0.0.0, et non seulement sur son loopback 127.0.0.1.

Si le conteneur s’arrête, consulte les logs et le code de sortie. Si le navigateur ne se connecte pas, vérifie dans l’ordre : processus vivant, port d’écoute, interface, port publié et pare-feu. Un conteneur démarré n’est pas forcément prêt à servir le trafic.

4. Volumes, réseaux et Compose

Un volume conserve des données hors de la couche éphémère du conteneur. Un bind mount relie un chemin de l’hôte au conteneur : pratique en développement, mais susceptible d’écraser des fichiers du conteneur.

services:
  api:
    build: .
    ports: ["3000:3000"]
    environment:
      DATABASE_URL: postgres://app:example@db:5432/app
    depends_on: [db]
  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_USER: app
      POSTGRES_PASSWORD: example
      POSTGRES_DB: app
    volumes: [pgdata:/var/lib/postgresql/data]
volumes:
  pgdata:

Dans le réseau Compose, le nom de service db est utilisé par l’API pour joindre PostgreSQL. Depuis le navigateur de l’hôte, ce nom n’est pas nécessairement résoluble. Les identifiants ci-dessus sont factices : ne les réutilise pas en production. depends_on ordonne le démarrage, mais ne garantit pas à lui seul que la base accepte les connexions ; prévois un healthcheck et une reconnexion robuste.

5. Reproductibilité et sécurité

Ajoute un .dockerignore pour exclure notamment .git, les dépendances locales, les fichiers de build obsolètes et les secrets. Sinon, le contexte peut être volumineux et des données privées peuvent entrer dans l’image.

Utilise un utilisateur non privilégié lorsque c’est compatible, garde les images de base à jour, évite le mode privilégié et ne place pas de secret dans ARG ou ENV si la valeur peut rester dans les métadonnées ou couches. Les secrets de construction doivent passer par les mécanismes dédiés de BuildKit lorsque nécessaire.

Docker améliore la cohérence d’exécution, mais ne rend pas l’application automatiquement sécurisée, disponible ou sauvegardée. Les mises à jour, journaux, healthchecks et sauvegardes restent à gérer.

Erreurs fréquentes et compromis

  • Confondre image et conteneur : modèle d’un côté, exécution de l’autre.
  • Perdre les données : utilise un volume pour la persistance.
  • Penser qu’EXPOSE publie le port : utilise un mapping explicite.
  • Utiliser localhost entre conteneurs : localhost désigne le conteneur courant.
  • Copier un secret dans l’image : exclus-le du contexte et injecte-le au runtime.
  • Supposer qu’un service est prêt : vérifie sa santé et gère les reconnexions.

Le multi-stage build réduit souvent la taille finale, mais ajoute de la complexité. Commence par une image fonctionnelle, puis mesure et durcis progressivement.

Construire une image exploitable en production

Le but n’est pas seulement d’obtenir un conteneur qui démarre : l’image doit être reproductible, petite autant que raisonnable, non privilégiée et sans secrets. Un fichier .dockerignore empêche notamment d’envoyer inutilement node_modules, .git, les fichiers locaux et les secrets au contexte de construction.

# Exemple de .dockerignore
node_modules
.git
.env
.env.*
coverage
npm-debug.log

Dans un Dockerfile multi-étapes, sépare les dépendances de construction de l’image d’exécution. Copie d’abord les fichiers de verrouillage pour bénéficier du cache, installe les dépendances avec une commande déterministe, puis copie les sources nécessaires. Exécute le processus avec un utilisateur non-root lorsque c’est compatible avec l’application.

docker build -t catalogue:dev .
docker image inspect catalogue:dev
docker run --rm -p 3000:3000 catalogue:dev
docker ps
docker logs --tail 100 NOM_OU_ID

Le port publié relie le port de l’hôte au port du conteneur ; l’application doit souvent écouter sur 0.0.0.0 dans le conteneur, pas uniquement sur 127.0.0.1. Un conteneur qui s’arrête immédiatement doit être diagnostiqué avec son code de sortie et ses logs avant d’ajouter un redémarrage automatique.

Les conteneurs sont remplaçables : ne conserve pas les données métier uniquement dans leur système de fichiers éphémère. Utilise un volume ou un service de stockage adapté et teste explicitement la persistance après recréation du conteneur.

Exercice guidé

Conteneurise une petite API écoutant sur le port 3000, publie le port et vérifie un endpoint de santé. Recrée ensuite le conteneur et observe quels fichiers persistent. Ajoute un fichier .dockerignore.

Exercice autonome et critères de réussite

Ajoute PostgreSQL avec Compose, connecte l’API au service par son nom réseau et conserve les données dans un volume. Documente les commandes de démarrage, arrêt et consultation des logs.

  • L’image se construit depuis un dépôt propre et un lockfile.
  • L’API est accessible via le port publié.
  • La base est jointe par le nom du service, pas localhost.
  • Les données persistent à la recréation du conteneur.
  • Les fichiers secrets sont exclus de l’image.
  • Les logs permettent de diagnostiquer un démarrage en échec.
