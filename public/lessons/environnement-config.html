7. Environnement, livraison et exploitation

Variables d’environnement et configuration

Séparer la configuration du code, valider les paramètres au démarrage et protéger les valeurs sensibles.

Tutoriel approfondiCompétence Full Stack

Objectifs et prérequis

La configuration regroupe les valeurs qui changent selon le contexte : port HTTP, URL de base de données, niveau de logs, timeout ou service tiers. Le code définit le comportement ; la configuration en règle les paramètres. Cela permet de promouvoir le même artefact entre développement, test et production sans modifier le code.

  • Distinguer configuration, valeur par défaut et secret.
  • Valider types et contraintes plutôt que faire confiance aux chaînes brutes.
  • Protéger les secrets dans Git, les logs et le bundle frontend.
  • Créer une configuration distincte pour les tests.

1. Centraliser la lecture

Évite de lire process.env dans tous les modules. Un point de configuration unique permet de vérifier les paramètres au démarrage et d’exposer des valeurs déjà typées au reste de l’application. Les variables d’environnement sont des chaînes : nombres et booléens doivent être parsés explicitement.

function required(name: string): string {
  const value = process.env[name];
  if (!value) throw new Error(`Variable requise absente : ${name}`);
  return value;
}
function positiveInteger(name: string, fallback: number): number {
  const raw = process.env[name];
  if (raw === undefined) return fallback;
  const value = Number(raw);
  if (!Number.isInteger(value) || value <= 0) {
    throw new Error(`${name} doit être un entier positif`);
  }
  return value;
}
export const config = {
  port: positiveInteger("PORT", 3000),
  databaseUrl: required("DATABASE_URL"),
};

Les messages d’erreur indiquent le nom du paramètre, pas sa valeur secrète. Les erreurs de configuration doivent apparaître avant l’acceptation de requêtes, pas au milieu d’une transaction métier.

2. Valeurs par défaut et validation

Un défaut est raisonnable pour un port local ou un niveau de logs ; il peut être dangereux pour une connexion obligatoire ou une option de sécurité. Classe les paramètres : obligatoires, optionnels avec défaut sûr et secrets injectés par un gestionnaire dédié. Documente aussi les unités : TIMEOUT_MS=5000 est moins ambigu qu’un paramètre TIMEOUT=5.

Attention au booléen JavaScript : Boolean("false") vaut true, car toute chaîne non vide est truthy. Parse une liste explicite de valeurs autorisées et rejette le reste. De même, une conversion numérique peut produire NaN : vérifie la plage, l’entier et les limites acceptables.

3. Environnements et fichiers locaux

Les environnements peuvent utiliser des URLs, bases de données et intégrations différentes, mais devraient partager le même code. Un fichier .env.example peut documenter les noms de variables avec des valeurs factices ; le vrai fichier local doit être ignoré par Git.

# .env.example — exemple, pas de secret réel
PORT=3000
DATABASE_URL=postgres://user:password@localhost:5432/app
LOG_LEVEL=debug

Si un secret a déjà été commité, l’ajout au .gitignore ne le retire pas de l’historique : révoque-le et remplace-le. Les tests doivent pointer vers des ressources isolées, jamais accidentellement vers la base de production. Vérifie les paramètres qui sélectionnent une ressource destructive.

4. Backend et frontend

Une variable disponible côté serveur n’est pas nécessairement sûre si elle est injectée dans le JavaScript envoyé au navigateur. Tout ce qui entre dans le bundle frontend est public. Avec Vite, le préfixe VITE_ rend les variables accessibles au code client : il ne transforme pas une clé secrète en donnée protégée.

Une clé nécessaire uniquement au serveur doit rester côté serveur et être utilisée via une API contrôlée. Ne journalise pas l’objet de configuration complet : les chaînes de connexion, jetons et mots de passe peuvent être exposés dans les logs ou systèmes d’observabilité.

5. Valider au démarrage

Un schéma typé explicite les contraintes. Avec une bibliothèque comme Zod, la validation peut vérifier l’environnement avant que l’application commence à servir le trafic.

import { z } from "zod";
const EnvSchema = z.object({
  NODE_ENV: z.enum(["development", "test", "production"]),
  PORT: z.coerce.number().int().min(1).max(65535).default(3000),
  DATABASE_URL: z.string().url(),
});
const parsed = EnvSchema.safeParse(process.env);
if (!parsed.success) {
  throw new Error("Configuration invalide : vérifier les variables d’environnement");
}
export const config = parsed.data;

Le schéma doit refléter le protocole réellement attendu : une URL générique valide n’assure pas que l’hôte ou le protocole convienne. N’ignore pas une variable invalide si l’application ne peut pas fonctionner sans elle.

Erreurs fréquentes et compromis

  • Committer un secret : ignore le fichier local et révoque tout secret déjà exposé.
  • Exposer une clé frontend : toute valeur du bundle doit être considérée comme publique.
  • Convertir implicitement : parse et valide chaque type.
  • Multiplier les sources de vérité : documente clairement la priorité des fichiers, variables et paramètres de plateforme.
  • Défaut permissif en production : fais échouer le démarrage si une configuration critique manque.

Un fichier local est pratique en développement ; en production, un gestionnaire de secrets facilite l’accès, la rotation et l’audit. Le choix dépend de la plateforme, mais le principe de non-exposition est constant.

Contrat de configuration et diagnostic

Une configuration fiable se traite comme une entrée externe : elle doit être documentée, validée et refusée si elle est incohérente. Pour chaque variable, définis son propriétaire, son type, son caractère obligatoire, sa valeur par défaut éventuelle et si elle contient un secret.

VariableRègleÉchec à éviter
PORTEntier dans la plage autoriséeChaîne vide ou port invalide
DATABASE_URLURL requise, protocole et hôte validesDémarrage réussi puis panne à la première requête
LOG_LEVELValeur dans une liste ferméeFaute de frappe silencieusement ignorée
PUBLIC_API_BASEValeur exposable au navigateurInjection d’un secret dans le bundle client

Un défaut acceptable est explicite et sûr ; un secret ou une URL de production ne doit généralement pas recevoir une valeur de secours silencieuse. Valide la configuration une seule fois au démarrage, puis transmets un objet typé aux composants concernés au lieu de relire process.env partout.

const port = Number(process.env.PORT ?? 3000);
if (!Number.isInteger(port) || port < 1 || port > 65535) {
  throw new Error("PORT doit être un entier entre 1 et 65535");
}
if (!process.env.DATABASE_URL) {
  throw new Error("DATABASE_URL est obligatoire");
}

Pour diagnostiquer une différence entre local, CI et production, compare les noms et règles des variables, jamais les valeurs secrètes en clair. Vérifie aussi les règles propres au framework : certaines variables préfixées sont incorporées au JavaScript envoyé au navigateur et deviennent publiques.

Exercice guidé

Centralise PORT, DATABASE_URL et LOG_LEVEL. Définis un défaut seulement pour le port et le niveau de logs. Fais échouer le démarrage si l’URL manque ou si le port est invalide, puis teste plusieurs configurations.

Exercice autonome et critères de réussite

Ajoute un environnement de test séparé, un fichier .env.example sans secrets et une liste documentée des variables. Inspecte le bundle frontend pour vérifier qu’aucune clé privée n’est exposée.

  • La configuration est lue depuis un point central.
  • Types et contraintes sont validés au démarrage.
  • Les paramètres obligatoires manquants produisent une erreur claire.
  • Les secrets ne sont ni commités ni envoyés au navigateur.
  • Développement, tests et production utilisent des configurations distinctes.
