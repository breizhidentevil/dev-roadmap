Environnements de développement, test et production

Séparer les environnements, maîtriser la configuration et promouvoir un même artefact avec des contrôles adaptés à chaque étape.

Leçon approfondieThéorie · pratique · validation

Objectifs d’apprentissage

À la fin de cette leçon, tu dois pouvoir expliquer les concepts avec tes propres mots, choisir une approche adaptée à un besoin réel et justifier tes choix à partir de contraintes observables.

  • Définir le vocabulaire essentiel et le problème que la compétence résout.
  • Appliquer les principes dans un exemple pratique et identifier les limites.
  • Vérifier le résultat avec des critères explicites plutôt qu’une impression subjective.

1. Pourquoi séparer les environnements ?

Un environnement est une combinaison de code, configuration, données, dépendances et permissions dans laquelle l’application s’exécute. Le développement favorise le retour rapide, le test vérifie des comportements dans des conditions contrôlées, et la production sert les utilisateurs réels. Les objectifs sont différents, mais les environnements ne doivent pas diverger au point que les tests ne prédisent plus le comportement du déploiement final.

Le développement local peut utiliser des données synthétiques, des services simulés et des outils de diagnostic. L’environnement de test doit être suffisamment proche de la production pour détecter les incompatibilités, sans exposer de données ou de secrets réels. La production exige des accès limités, une surveillance, des sauvegardes et des procédures de restauration. Il est souvent utile d’ajouter une préproduction pour valider le déploiement et les intégrations dans un environnement représentatif.

La séparation n’est pas seulement une question d’URL ou de fichiers de configuration. Elle concerne aussi les comptes cloud, les bases de données, les clés API, les droits d’écriture, les files de messages et les domaines. Une application de test qui peut écrire dans la base de production représente un risque majeur, même si son interface porte clairement la mention « test ».

2. Externaliser la configuration

Le même code doit pouvoir être lancé avec des paramètres adaptés à chaque environnement. Les URL des services, les niveaux de journalisation et les options fonctionnelles peuvent être configurés hors du code. Les secrets — mots de passe, jetons et clés privées — doivent être fournis par un mécanisme dédié, pas stockés dans Git ou inclus dans une image publique.

# Exemple local, valeurs non sensibles
APP_ENV=development
LOG_LEVEL=debug
API_TIMEOUT_MS=2500

# DATABASE_URL est injectée à l’exécution par le gestionnaire
# de secrets ; ne pas placer sa vraie valeur dans .env.example.

Ce fragment décrit des variables, pas un format universel. Le nommage, la validation et les valeurs par défaut doivent être cohérents. Au démarrage, l’application devrait échouer clairement si une variable obligatoire est absente ou invalide, plutôt que de se connecter silencieusement à une mauvaise base. Évite les valeurs par défaut dangereuses en production. Avant une migration ou une opération destructive, vérifie explicitement l’identité de l’environnement et de la base cible, puis refuse l’opération si elle ne correspond pas à l’environnement attendu.

Une configuration typée ou validée réduit les erreurs de déploiement. Sépare les paramètres non secrets des secrets, limite leur durée de vie lorsque c’est possible et contrôle qui peut les lire. Les secrets de développement ne doivent pas être réutilisés en production, et les journaux ne doivent pas les afficher.

3. Réduire l’écart entre test et production

La parité parfaite est souvent trop coûteuse, mais les différences importantes doivent être identifiées. Des versions différentes de la base, un système de fichiers local qui persiste alors que la production est éphémère, ou des appels externes simulés peuvent masquer des défauts. Utilise des versions proches, automatise la création de l’environnement et documente les écarts qui restent.

Les tests doivent s’exécuter avec un état maîtrisé. Les jeux de données doivent être reproductibles, les tests indépendants autant que possible et le nettoyage explicite. N’utilise pas de données personnelles réelles sans base légitime, protection et autorisation appropriées. Les jeux synthétiques permettent de tester de nombreux cas sans diffuser des informations sensibles.

La préproduction est utile pour vérifier le paquet, les migrations, les variables, les permissions et les dépendances. Elle ne garantit pas à elle seule le succès en production : le volume de trafic, les secrets, les données et certaines intégrations restent différents. Complète les tests par des contrôles après déploiement et une procédure de retour arrière.

4. Promouvoir le même artefact

Un artefact est le résultat construit et identifié d’une version : image de conteneur, paquet ou bundle. Une chaîne fiable le construit une fois, le teste, puis promeut ce même artefact entre les environnements. Recompiler séparément pour chaque environnement peut produire des binaires différents malgré le même commit et rendre l’audit plus difficile.

Le déploiement doit identifier la version exacte, conserver les résultats de tests et séparer les autorisations. Les protections de branche, l’approbation pour la production et les identités de déploiement à privilèges minimaux réduisent le risque. La configuration varie entre environnements, mais l’artefact applicatif doit rester traçable.

Les migrations de base demandent une attention particulière : un nouveau code peut être incompatible avec l’ancien schéma, et un retour arrière de l’application n’annule pas automatiquement une migration destructive. Préfère des migrations compatibles par étapes lorsque les déploiements peuvent coexister : ajouter une colonne, déployer le code compatible, migrer les données, puis supprimer l’ancien champ dans une version ultérieure après vérification.

5. Garde-fous et erreurs fréquentes

  • Confusion de base : affiche clairement l’environnement et vérifie l’URL de connexion avant toute opération destructive.
  • Secrets dans Git : retire-les, révoque-les et renouvelle-les ; supprimer le commit ne suffit pas toujours.
  • Test trop différent : documente les différences et ajoute des tests de préproduction pour les intégrations critiques.
  • Artefacts reconstruits : identifie et promeus le même artefact pour améliorer la traçabilité.
  • Déploiement sans validation : contrôle santé, erreurs, latence et fonctions essentielles après publication.

Les environnements éphémères par branche ou par demande de changement peuvent accélérer la validation, mais leur création et leur destruction doivent être automatisées. Ils doivent posséder des quotas, des règles de nettoyage et des accès limités afin d’éviter l’accumulation de ressources et de données oubliées.

6. Exercice pratique

Définis les environnements local, test, préproduction et production pour une API. Liste les bases, secrets, permissions, jeux de données et contrôles de santé de chacun. Propose un pipeline qui construit un artefact une seule fois, le teste, le déploie en préproduction, puis demande une approbation avant la production. Ajoute une vérification empêchant l’environnement de test d’écrire dans la base de production.

Critères de réussite

  • Je peux expliquer le rôle et les risques de chaque environnement.
  • Je sépare code, configuration et secrets.
  • Je réduis les écarts critiques entre test et production.
  • Je promeus un artefact identifiable et conserve la traçabilité.
  • Je prévois des contrôles après déploiement et une stratégie de restauration.

Atelier approfondi — réduire les écarts entre environnements

Objectifs pédagogiques

  • Séparer configuration et code déployé.
  • Identifier les écarts qui invalident les tests.
  • Gérer secrets, données et permissions par environnement.

Parité utile

Chercher à rapprocher versions runtime, dépendances et services, sans prétendre que les environnements doivent être identiques en taille ou en données.

Configuration

Injecter la configuration à l’exécution; valider les variables requises au démarrage et échouer clairement en cas de valeur invalide.

Secrets

Utiliser un gestionnaire de secrets, des identités distinctes et le moindre privilège; ne pas copier les secrets de production en test.

Données

Privilégier des jeux synthétiques ou anonymisés et définir le cycle de vie des données temporaires.

Promotion

Promouvoir un même artefact construit et identifié; éviter de reconstruire un binaire différent pour chaque environnement.

Exercice pratique

Créer une matrice dev/test/prod pour une application web. Lister les différences autorisées, les secrets, les services dépendants et les contrôles avant promotion.

Critères de réussite

  • Les écarts autorisés sont documentés.
  • Les secrets sont séparés et à privilèges limités.
  • Les données de test sont adaptées et protégées.
  • Le même artefact est promu entre environnements.
