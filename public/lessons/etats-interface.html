14. UX, accessibilité et qualité produit

États de chargement, erreur et vide

Rendre les interfaces fiables et compréhensibles pendant les attentes, les échecs et l’absence de données.

Tutoriel approfondiLecture et mise en pratique

Objectifs d’apprentissage

À la fin de cette leçon, tu sauras modéliser les états d’une interface asynchrone, différencier absence de données et échec technique, éviter les états contradictoires et rendre les mises à jour perceptibles. Tu pourras concevoir un chargement initial, un rafraîchissement, une liste vide, une erreur récupérable et une confirmation de succès.

Prérequis : notions de JavaScript asynchrone, HTTP et composants React. Les principes valent aussi pour Vue, Angular ou une interface sans framework.

1. Pourquoi expliciter les états ?

Une requête réseau n’est ni instantanée ni garantie. Elle peut être lente, échouer, renvoyer zéro résultat ou réussir avec des données partielles. Si l’interface ne distingue pas ces cas, l’utilisateur peut interpréter un écran blanc comme une panne, croire qu’une liste vide signifie qu’il n’a aucun droit ou répéter une action déjà envoyée.

Commence par inventorier les états d’une tâche, pas seulement les écrans habituels. Pour une liste de commandes, on peut distinguer : initialisation, chargement initial, données disponibles, aucun élément, erreur de chargement, actualisation en cours et actualisation échouée avec données précédentes conservées. Pour une sauvegarde, ajoute l’enregistrement en cours, succès confirmé et échec avec possibilité de réessayer.

Chaque état doit avoir une signification unique. Si `loading` et `error` peuvent être vrais en même temps sans règle claire, la structure autorise des combinaisons incohérentes. Une modélisation explicite rend les cas possibles visibles dans le code et facilite les tests.

2. Représenter les états

Pour un petit composant, un état discriminé peut suffire. Au lieu de plusieurs booléens indépendants, utilise une union dont chaque variante contient uniquement les données pertinentes :

type ListState<T> =
  | { status: "loading" }
  | { status: "success"; items: T[] }
  | { status: "error"; message: string };

Ce modèle empêche d’avoir un statut `success` sans liste ou un statut `error` sans information associée. L’état vide n’a pas nécessairement besoin d’une variante technique distincte : une réussite avec `items.length === 0` peut représenter « aucune donnée ». Il faut toutefois que l’interface distingue clairement le résultat vide de l’absence de requête.

Quand l’application doit conserver les anciennes données pendant une actualisation, modélise cette situation explicitement. Par exemple, conserve `items` et ajoute un indicateur `refreshing`, avec un champ d’erreur de rafraîchissement séparé. N’efface pas automatiquement une liste déjà utile parce qu’une nouvelle requête échoue.

Évite de stocker des valeurs qui peuvent être calculées à partir d’autres états. Si `isEmpty` est simplement `status === "success" && items.length === 0`, le conserver séparément crée une source de désynchronisation. Le bon modèle dépend du comportement voulu, mais doit limiter les combinaisons impossibles.

3. Charger des données et gérer les échecs

Avec `fetch`, une réponse HTTP 404 ou 500 ne rejette pas automatiquement la promesse. Il faut vérifier `response.ok`. Il faut également distinguer une erreur réseau, une réponse HTTP non réussie et une réponse dont le contenu n’est pas conforme au contrat attendu. Chaque cas peut nécessiter un message différent, même si le détail technique reste dans les logs.

async function loadOrders(): Promise<Order[]> {
  const response = await fetch("/api/orders");
  if (!response.ok) {
    throw new Error(`Échec HTTP : ${response.status}`);
  }
  return response.json() as Promise<Order[]>;
}

Le type `Order[]` dans cet exemple n’effectue pas une validation à l’exécution : une réponse externe peut être mal formée. Pour des données importantes, valide le JSON avec un schéma ou une fonction dédiée. Ne montre jamais directement à l’utilisateur une trace de pile, un message de base de données ou une réponse interne sensible.

Dans React, une requête déclenchée par un effet doit tenir compte du démontage du composant et du changement de paramètres. Un `AbortController` peut annuler une requête devenue inutile. Sans cela, une réponse ancienne peut remplacer les données d’une recherche plus récente. Les bibliothèques de requêtes apportent cache, déduplication, annulation ou revalidation, mais elles ne dispensent pas de décider quels états présenter.

4. Messages utiles et accessibles

Un indicateur de chargement doit être proportionné à l’attente. Pour une action quasi immédiate, changer le libellé du bouton peut suffire ; pour une page qui prend plusieurs secondes, un squelette ou une progression peut rassurer. Ne montre pas une progression chiffrée si tu ne peux pas l’estimer honnêtement.

Un état vide doit aider à comprendre pourquoi il n’y a rien et, si possible, proposer une prochaine action. « Aucune commande pour le moment » est plus informatif qu’un espace vide. Si les filtres excluent tous les résultats, propose de les réinitialiser. Si la liste est réellement nouvelle, un bouton « Créer une commande » peut être pertinent. Ne confonds pas « aucun résultat » avec « erreur de chargement ».

Un message d’erreur doit indiquer ce qui a échoué, ce qui reste intact et comment reprendre. Pour une sauvegarde, précise si les modifications ont été enregistrées ou non. Si le résultat est incertain parce que la connexion a été coupée après l’envoi, ne prétends pas que l’opération a échoué : le serveur peut l’avoir exécutée. Une vérification de statut ou une clé d’idempotence peut être nécessaire.

Les changements de statut doivent aussi être accessibles. Les lecteurs d’écran ne perçoivent pas forcément un changement visuel. Utilise des régions de statut ou des alertes adaptées, sans annoncer chaque mise à jour répétitive. Place les erreurs de formulaire près des champs et relie-les programmatiquement aux champs concernés.

5. Exemple React : états d’une liste

Le rendu doit traiter toutes les branches et ne pas laisser un chargement infini silencieux :

function OrdersPanel({ state }: { state: ListState<Order> }) {
  if (state.status === "loading") {
    return <p role="status">Chargement des commandes…</p>;
  }

  if (state.status === "error") {
    return (
      <section>
        <p role="alert">Les commandes n’ont pas pu être chargées.</p>
        <button onClick={retry}>Réessayer</button>
      </section>
    );
  }

  if (state.items.length === 0) {
    return <p>Aucune commande pour le moment.</p>;
  }

  return <OrderList items={state.items} />;
}

Cet exemple suppose que `retry` existe dans le contexte du composant et que le statut est maintenu par une couche de données. Il illustre la présentation, pas toute la logique réseau. En production, pense à éviter les doubles soumissions, à désactiver temporairement les actions incompatibles et à préserver la navigation au clavier.

Évite de remplacer toute la page par un écran de chargement à chaque mise à jour. Si les données précédentes sont encore valides, un indicateur discret peut préserver la continuité. Le choix dépend de la criticité : une donnée financière doit clairement indiquer sa fraîcheur, tandis qu’une petite liste de suggestions peut tolérer une actualisation moins visible.

Pièges, limites et compromis

  • Ne traite pas les statuts HTTP d’erreur comme des rejets automatiques de `fetch`.
  • Ne transforme pas une liste vide en erreur et ne présente pas une erreur comme une absence de résultats.
  • Ne suppose pas qu’un timeout prouve que le serveur n’a pas effectué l’opération.
  • Évite les booléens indépendants qui permettent des états contradictoires.
  • Une animation de chargement ne remplace pas un délai, un timeout ou une stratégie de reprise.
  • Les Error Boundaries React concernent principalement les erreurs de rendu qu’elles interceptent ; elles ne capturent pas automatiquement toute erreur asynchrone ou tout gestionnaire d’événement.
  • Une annonce accessible doit être utile et non envahissante ; trop d’annonces rendent l’application pénible.

Exercice

Crée un composant de liste de tâches qui charge les données depuis une fonction simulée. Fais varier le délai et provoque trois situations : réussite avec résultats, réussite sans résultats et erreur. Ajoute un bouton de nouvelle tentative, puis simule une actualisation qui conserve les anciennes données. Vérifie que les messages restent cohérents, que l’utilisateur ne peut pas déclencher plusieurs opérations incompatibles et que les statuts importants sont perceptibles au clavier et avec un lecteur d’écran.

Critères de réussite

  • Les états de chargement, réussite, vide et erreur sont distingués.
  • Une réponse HTTP non réussie est traitée explicitement.
  • Les données externes sont validées lorsqu’elles influencent des opérations importantes.
  • Une erreur explique la reprise possible sans divulguer de détails internes.
  • Une requête obsolète ne remplace pas une réponse plus récente.
  • Les messages de statut sont perceptibles visuellement et par les technologies d’assistance.

Atelier approfondi — seconde passe

Objectifs opérationnels

  • Décrire les états d’une opération asynchrone sans combinaisons contradictoires.
  • Distinguer une liste vide valide d’un échec de chargement et d’une actualisation en cours.
  • Éviter qu’une réponse ancienne remplace le résultat d’une requête plus récente.

Explications et méthode

Une interface de données est une petite machine à états. Au minimum, elle distingue l’état initial, le chargement, le succès avec données, le succès sans résultat et l’échec. Une actualisation peut conserver les données précédentes tout en signalant discrètement qu’une requête est en cours.

Un modèle explicite réduit les états impossibles. Plusieurs booléens indépendants comme isLoading, hasError et isEmpty peuvent devenir vrais simultanément. Une union discriminée ou un reducer permet de décider quels champs existent dans chaque état.

Les requêtes peuvent se terminer dans un ordre différent de leur lancement. Lors d’un changement de filtre, annuler la requête précédente si possible ou ignorer sa réponse évite d’afficher des données périmées. Avec fetch, vérifier response.ok : une réponse HTTP 404 ou 500 ne rejette pas automatiquement la promesse.

Exemple commenté

type ViewState<T> =
  | { status: "loading" }
  | { status: "success"; items: T[] }
  | { status: "error"; message: string };

function messageFor<T>(state: ViewState<T>): string {
  switch (state.status) {
    case "loading": return "Chargement…";
    case "success": return state.items.length === 0
      ? "Aucun résultat pour ces critères."
      : `${state.items.length} résultat(s)`;
    case "error": return state.message;
  }
}

Pièges à éviter

  • Afficher « aucun résultat » avant que la requête ait réussi : l’utilisateur peut croire que ses données ont disparu.
  • Remplacer une liste utile par un écran vide lors d’une actualisation alors qu’un indicateur discret suffirait.
  • Afficher directement le détail brut d’une exception ou supposer qu’une requête HTTP non-2xx est une promesse rejetée.

Exercice d’application

Construis une liste de produits avec chargement initial, résultat vide, résultat non vide, erreur récupérable et actualisation. Change rapidement deux filtres successifs et simule une réponse lente pour vérifier que la première réponse ne remplace pas la seconde.

Critères de réussite

  • Chaque état possède un rendu compréhensible et aucun état contradictoire n’est possible.
  • Le succès vide est différent de l’erreur ; l’erreur propose une action adaptée.
  • Une réponse obsolète est ignorée ou annulée et les messages de statut sont annoncés sans être excessivement bavards.
