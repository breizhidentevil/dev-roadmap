Frontières entre modules

Organiser le code autour de responsabilités explicites et limiter les dépendances qui rendent une application difficile à faire évoluer.

Leçon approfondieThéorie · pratique · validation

Objectifs d’apprentissage

À la fin de cette leçon, tu dois pouvoir définir le propriétaire d’une règle métier, exposer un contrat stable et repérer les dépendances qui rendent un changement local coûteux.

  • Délimiter un module à partir de ses invariants, de son vocabulaire et de ses raisons de changement.
  • Créer une API publique minimale sans exporter les détails internes.
  • Repérer les cycles, les imports transverses et les dépendances vers des couches inappropriées.
  • Choisir entre appel direct et événement en tenant compte de la cohérence et des coûts opérationnels.

Prérequis : imports/exports TypeScript ou JavaScript et notions de tests unitaires.

1. Pourquoi tracer des frontières ?

Un module regroupe du code qui évolue pour une raison cohérente et expose une interface à ses consommateurs. Une frontière de module répond à trois questions : qui possède cette règle, quelles opérations sont autorisées, et quelles connaissances doivent rester cachées ? Sans frontière claire, chaque partie de l’application peut lire ou modifier les détails des autres ; un changement local devient alors une modification globale.

La taille ne suffit pas à définir un bon module. Un fichier unique peut contenir plusieurs responsabilités indépendantes, tandis qu’un ensemble de petits fichiers peut former un seul module cohérent. Il faut regarder les raisons de changement, les invariants, le vocabulaire métier et les dépendances. Par exemple, le module « commandes » peut posséder les règles de transition d’une commande, alors que le module « notifications » sait envoyer un message sans décider si une commande doit être confirmée.

Un module ne doit pas nécessairement correspondre à un microservice. Dans une application monolithique, les frontières internes peuvent déjà être explicites et testables. Les extraire en processus séparés ajoute des coûts de réseau, de déploiement et d’observabilité ; on le fait pour une raison opérationnelle ou organisationnelle, pas simplement pour obtenir davantage de dossiers.

2. Définir une interface publique minimale

Le consommateur doit dépendre du contrat utile, pas de la structure interne. L’API publique peut exposer quelques fonctions, types ou événements. Les helpers, tables ORM et formats de stockage restent privés tant qu’ils ne constituent pas un contrat nécessaire.

// commandes/index.ts : point d'entrée public
export { creerCommande, annulerCommande } from "./service";
export type { Commande, NouvelleCommande } from "./types";

// commandes/service.ts : implémentation interne
export async function creerCommande(
  entree: NouvelleCommande
): Promise<Commande> {
  // Valider les règles métier et coordonner le stockage.
  throw new Error("exemple à implémenter");
}

Le point d’entrée du module agit comme une liste explicite de ce que les autres modules sont autorisés à utiliser. Évite les imports profonds tels que commandes/infrastructure/sql/commande-row : ils lient le consommateur à un détail susceptible de changer. Un export large rend les refactorisations plus coûteuses, car chaque export peut devenir une dépendance implicite.

Ne crée pas automatiquement une interface pour chaque classe. Une abstraction est utile lorsqu’elle protège une règle, permet une substitution réellement nécessaire ou stabilise un contrat. Sinon, elle ajoute une indirection sans bénéfice. Après une modification interne, un test du consommateur doit pouvoir continuer à passer sans changer son code.

3. Contrôler le sens des dépendances

Une frontière n’est réelle que si le code la respecte. Le domaine métier ne devrait pas importer un composant React, un contrôleur HTTP ou un modèle généré par l’ORM. Une couche externe peut appeler le cœur, tandis que le cœur exprime les contrats dont il a besoin sans connaître leur implémentation.

HTTP / CLI  ──>  cas d'usage  ──>  domaine
                    ▲
                    │ contrat défini côté application
             adaptateur SQL implémente le contrat

Le dessin représente le sens des dépendances de code, pas nécessairement le chemin d’exécution. Pour détecter les violations, cherche les imports qui traversent plusieurs domaines, les cycles et les dépendances du domaine vers l’infrastructure. Des règles d’import (ESLint ou un outil de vérification d’architecture) peuvent faire échouer la CI si un module importe une couche interdite.

Face à un cycle A → B → A, ne le résous pas immédiatement en déplaçant tout dans common. Identifie d’abord qui possède la règle. Si les deux modules ont réellement besoin d’un contrat stable, extrais un petit module de contrat ; si l’un appelle l’autre seulement pour une notification, un événement peut être approprié. Les événements apportent toutefois de l’asynchronisme, des doublons et une cohérence éventuellement différée : ils ne remplacent pas automatiquement un appel direct.

4. Exemple de découpage métier

Dans une application de vente, distingue par exemple catalogue, commandes, paiement et notifications. Le catalogue possède les prix publiés ; commandes possède le cycle de vie et les lignes commandées ; paiement traduit le protocole du prestataire en résultats internes ; notifications envoie les messages demandés sans décider si la commande est confirmée.

Écris pour chaque module une phrase de propriété et une liste de données qu’il est seul autorisé à modifier. Par exemple, un autre module peut demander « annuler la commande 501 », mais ne doit pas modifier directement orders.status. Le propriétaire applique les règles de transition, vérifie l’état actuel et émet éventuellement un événement.

Les frontières ne déterminent pas à elles seules les frontières de déploiement. Des modules internes à un monolithe peuvent partager une transaction de base et rester indépendants au niveau du code. Les répartir en services introduit des pannes réseau, des contrats de version, des déploiements coordonnés ou une cohérence différée. Extrais un service lorsqu’un besoin d’autonomie opérationnelle, de mise à l’échelle ou de responsabilité d’équipe justifie ce coût — pas simplement pour créer plus de dossiers.

5. Signaux de mauvaise frontière

  • Une modification métier exige de toucher plusieurs modules sans contrat explicite.
  • Un module lit ou modifie directement les tables privées d’un autre.
  • Des imports circulaires rendent l’ordre d’initialisation fragile.
  • Des noms comme Manager, Helper ou Common masquent l’absence de propriétaire.
  • Un test d’une règle locale doit démarrer toute l’application parce que les dépendances ne sont pas séparées.

Ces signes ne sont pas des règles absolues : le partage d’un type stable peut être sain et certains modules doivent évoluer ensemble. Évalue la fréquence des changements, la cohésion des règles, le coût des tests et le nombre de consommateurs. Trop de petits modules créent aussi de la navigation et des contrats artificiels.

Refactorise par étapes : ajoute d’abord des tests de caractérisation, définis le contrat cible, déplace la responsabilité, remplace les imports directs, puis supprime l’ancien chemin. Chaque étape doit laisser le projet compilable et le comportement observable stable.

6. Exercice pratique

Sur une application de gestion de tâches, propose les modules tasks, users, reminders et persistence. Pour chacun, documente son propriétaire, son API publique, les données qu’il peut modifier et les dépendances interdites.

  1. Dessine le graphe d’imports et identifie tout cycle ou import vers un détail interne.
  2. Expose une fonction completeTask(taskId) qui applique la règle métier sans importer l’ORM.
  3. Écris un test du contrat public qui ne dépend pas du chemin interne des fichiers.
  4. Décide si le rappel doit être un appel direct ou un événement ; justifie le choix selon la tolérance à la latence, aux doublons et aux retards.
  5. Décris un plan de refactorisation qui conserve un état fonctionnel après chaque étape.

Critères de réussite

  • Chaque module possède une responsabilité formulée clairement et un propriétaire de ses invariants.
  • Les consommateurs utilisent l’API publique, pas des chemins internes ou des tables privées.
  • Le graphe d’imports ne comporte pas de cycle non justifié et les règles de dépendance sont vérifiables.
  • Une règle métier peut être testée sans lancer toute l’application.
  • Le choix entre appel direct et événement tient compte des exigences de cohérence et des échecs possibles.
  • La refactorisation est découpée en étapes testables et réversibles.
