5. Sécurité applicative

Gestion des secrets

Sortir les clés et mots de passe du code et des dépôts Git.

Tutoriel approfondiSécurité applicative

Objectifs d’apprentissage

Tu dois pouvoir identifier les secrets d’une application, les injecter dans un environnement sans les intégrer au dépôt, limiter leur accès et réagir correctement à une fuite.

  • Distinguer configuration ordinaire et secret porteur d’accès.
  • Choisir un stockage selon le contexte : développement, CI/CD ou production.
  • Mettre en place rotation, moindre privilège et procédures de réponse à incident.

1. Qu’est-ce qu’un secret ?

Un secret est une valeur dont la divulgation peut permettre un accès ou une action non autorisée : mot de passe de base de données, clé d’API, token de déploiement, clé privée, clé de signature ou credential cloud. Une URL de service ou un nom de fonctionnalité est généralement de la configuration, pas un secret, même si certaines valeurs peuvent révéler des informations internes.

La règle de base est de séparer le code de sa configuration et de ne pas versionner les secrets. Un fichier .env local peut être pratique pour le développement, mais il doit être ignoré par Git et ne doit pas être copié tel quel en production.

2. Fournir les secrets à l’application

En développement, utilise un fichier local non versionné ou un gestionnaire de secrets adapté. En CI/CD, utilise le magasin de secrets de la plateforme et limite les workflows qui peuvent le lire. En production, privilégie si possible un gestionnaire de secrets ou l’identité de service de la plateforme, avec accès accordé au strict nécessaire.

# .gitignore
.env
.env.*
!.env.example

.gitignore empêche surtout l’ajout futur d’un fichier non suivi : il ne retire pas un fichier déjà versionné. Vérifie la règle et l’état du suivi dans un dépôt de démonstration :

git check-ignore -v .env
git ls-files --error-unmatch .env

La première commande doit afficher la règle d’exclusion. La seconde doit échouer si .env n’est pas suivi ; si elle renvoie le chemin, le fichier est déjà dans l’index Git. Dans ce cas, retire-le de l’index avec git rm --cached .env sans confondre cette opération avec l’effacement des anciennes copies. Si une vraie valeur a déjà été commitée ou publiée, révoque-la et remplace-la même après son retrait du dépôt.

Un fichier .env.example peut documenter les noms de variables attendues avec des valeurs fictives :

DATABASE_URL=
PAYMENT_API_KEY=
SESSION_SIGNING_KEY=

Ne mets jamais de vraie valeur dans l’exemple. Les variables d’environnement ne sont pas une protection magique : elles peuvent être exposées par des dumps de processus, des outils de diagnostic ou des logs mal conçus. Leur usage doit s’inscrire dans une politique d’accès plus large.

3. Principe du moindre privilège

Un secret doit permettre uniquement les actions nécessaires au composant qui l’utilise. Une clé de lecture ne devrait pas pouvoir supprimer des données ; un token de CI pour un dépôt ne devrait pas avoir un accès administratif à toute l’organisation. Sépare les secrets entre développement, test et production afin qu’une fuite de test ne donne pas accès à l’environnement réel.

Évite de partager une seule clé entre plusieurs applications : cela complique l’attribution d’un incident et oblige à tout remplacer lorsqu’un seul consommateur est compromis. Lorsque c’est possible, préfère des credentials temporaires et une identité de service à des clés statiques de longue durée.

4. Rotation et réponse à une fuite

  1. Révoquer ou désactiver le secret compromis dès que possible.
  2. Créer et déployer un nouveau secret par un canal contrôlé.
  3. Vérifier que les consommateurs ont migré, puis retirer l’ancien.
  4. Examiner les journaux d’accès et l’étendue possible de l’exposition.
  5. Retirer la valeur des emplacements accessibles, documenter l’incident et corriger la cause.

Supprimer un secret du dernier commit ne suffit pas : il peut rester dans l’historique Git, les forks, les caches, les artefacts CI et les logs. Si un secret a été poussé dans un dépôt, considère-le comme compromis et révoque-le d’abord ; le nettoyage de l’historique vient ensuite, avec coordination des collaborateurs.

5. Détection et prévention

Active le secret scanning lorsqu’il est disponible, ajoute des contrôles avant commit ou dans la CI, et vérifie les journaux et artefacts produits par les pipelines. Ces contrôles réduisent le risque, mais ne garantissent pas qu’aucun secret ne fuit : les formats privés et les valeurs inconnues peuvent échapper aux scanners.

Ne journalise jamais les valeurs de configuration sensibles. Si le débogage nécessite d’inspecter la configuration, affiche uniquement la présence de la variable ou une version masquée. Prévois une procédure documentée qui indique qui peut révoquer, remplacer et valider les secrets critiques.

Traiter une fuite comme un incident

Lorsqu’un secret est exposé, la priorité est de le rendre inutilisable : révoquer ou désactiver l’ancienne valeur, émettre une nouvelle valeur, la distribuer aux seuls consommateurs nécessaires, puis vérifier que l’ancienne ne fonctionne plus. La suppression du fichier ou la réécriture de l’historique Git ne remplace jamais la révocation ; des clones, caches et journaux peuvent déjà contenir la valeur.

  1. Identifier le secret, son propriétaire, les systèmes qui le consomment et ses privilèges.
  2. Révoquer ou faire tourner la valeur selon le mécanisme du fournisseur.
  3. Mettre à jour les environnements et le pipeline de déploiement, puis vérifier les services.
  4. Examiner les journaux d’accès pour rechercher un usage anormal, sans recopier le secret dans le rapport.
  5. Réduire la cause : droits, durée de vie, secret scanning, règles de dépôt et procédure d’astreinte.

Un fichier .env.example doit contenir des noms de variables et des valeurs fictives, jamais des identifiants réels. Vérifie aussi les artefacts de build, les traces CI et les dumps de diagnostic : ils peuvent exposer des variables d’environnement.

Erreurs fréquentes

  • Mettre une clé dans le code en se disant que le dépôt est privé.
  • Committer un fichier .env puis le supprimer dans un commit ultérieur.
  • Réutiliser une même clé dans tous les environnements.
  • Donner aux secrets CI des permissions excessives.
  • Confondre suppression de l’historique et révocation du secret.
  • Afficher des variables sensibles dans les logs de démarrage ou de débogage.

Exercice guidé

Dans un dépôt de démonstration, crée un fichier .env.example, ajoute le fichier local réel à .gitignore, puis adapte l’application pour lire les valeurs depuis la configuration de l’environnement. Vérifie que le fichier réel n’est pas suivi par Git et qu’aucune valeur secrète n’apparaît dans les logs.

Simule ensuite une fuite avec une valeur factice : décris comment la révoquer, la remplacer dans la CI et les environnements, et vérifier que l’ancienne valeur ne fonctionne plus.

Exercice autonome et critères de réussite

Établis un inventaire de secrets pour une application fictive : base de données, service de paiement, signature de session et déploiement. Pour chacun, indique son propriétaire, les consommateurs autorisés, son stockage, sa durée de vie et la procédure de rotation.

Réussite : aucune valeur réelle n’est versionnée ; les environnements sont séparés ; les permissions sont minimales ; les secrets ne sont pas journalisés ; la détection est activée ; une procédure de révocation et de rotation est documentée et testable.
