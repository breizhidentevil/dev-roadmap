Git et gestion de versions

Conserver l’historique du code, organiser les changements et collaborer sans perdre le travail des autres.

Tutoriel détailléLot 8 · 2026

Objectifs d’apprentissage

  • Expliquer le rôle du dépôt, de l’index et du répertoire de travail.
  • Créer des commits cohérents et lisibles.
  • Utiliser branches, fusion et rebase avec discernement.
  • Résoudre un conflit et vérifier le résultat.

1. Comprendre les trois zones

Git est un système de gestion de versions distribué. Le répertoire de travail contient les fichiers modifiés, l’index prépare le prochain commit et le dépôt local conserve l’historique. git status résume leur état ; git diff montre les changements non indexés et git diff --staged ceux qui sont prêts à être validés.

git status
    git diff
    git add src/
    git diff --staged
    git commit -m "Ajoute la validation du formulaire"

Un commit représente un ensemble de changements enregistré dans l’historique. Prépare uniquement les fichiers qui appartiennent à cette modification : cela rend la revue et l’annulation plus faciles.

2. Écrire des commits utiles

Un bon commit correspond à une intention cohérente : correction d’un bug, ajout d’une fonctionnalité ou refactorisation ciblée. Le message doit décrire le changement de façon précise. Évite les commits fourre-tout qui mélangent formatage, dépendances et logique métier sans raison.

Avant de valider, inspecte le diff et vérifie qu’aucun secret, fichier généré inutile ou changement accidentel n’est inclus. Le fichier .gitignore permet d’exclure les fichiers qui ne doivent généralement pas être versionnés, mais il ne retire pas automatiquement un fichier déjà suivi.

3. Branches et intégration

Une branche est un pointeur mobile vers un commit. Elle permet de travailler sur une fonctionnalité sans modifier directement la branche de référence.

git switch -c feat/recherche
    # modifier les fichiers et créer des commits
    git switch main
    git pull --ff-only
    git merge feat/recherche

Adapte les noms de branches et la procédure aux conventions de l’équipe. Une demande de fusion (pull request ou merge request) permet la revue, l’exécution des tests et la discussion avant intégration. Elle complète les tests automatiques, elle ne les remplace pas.

4. Fusion, rebase et conflits

La fusion conserve les relations entre les branches et peut créer un commit de fusion. Le rebase rejoue des commits sur une nouvelle base et réécrit leurs identifiants. Le rebase peut produire un historique linéaire, mais il faut éviter de réécrire une branche partagée sans coordination.

Un conflit signifie que Git ne peut pas décider seul comment combiner certaines modifications. Ouvre les fichiers concernés, interprète les deux versions, édite le résultat final, puis vérifie le diff et lance les tests.

# Si le conflit survient pendant une fusion (merge)
git status
# Éditer les fichiers, puis vérifier la résolution
git add fichier-concerne
git diff --cached
git merge --continue

# Si le conflit survient pendant un rebase : autre séquence
git add fichier-concerne
git diff --cached
git rebase --continue

Ne résous pas mécaniquement un conflit en gardant systématiquement « la nôtre » ou « la leur » : chacune peut contenir un comportement indispensable. Pour abandonner l’opération en cours, git merge --abort ou git rebase --abort correspond à l’opération concernée ; vérifie d’abord l’état du répertoire de travail et sauvegarde les changements non engagés si nécessaire.

5. Annuler sans perdre le travail

Les commandes d’annulation ont des effets différents. git restore fichier peut remplacer des modifications locales ; git revert crée un commit qui inverse un changement déjà enregistré ; git reset déplace la référence courante et peut retirer des commits de la branche. Vérifie toujours le statut et la portée avant d’exécuter une commande destructive.

git log --oneline --graph --decorate -12
    git revert <identifiant-du-commit>
    git reflog

Le reflog aide à retrouver des références récentes dans le dépôt local, mais ce n’est pas une sauvegarde universelle. Pousse régulièrement les branches utiles et conserve les données sensibles hors du dépôt.

Erreurs fréquentes

  • Valider sans relire le diff indexé.
  • Confondre git fetch et l’intégration des changements distants.
  • Réécrire l’historique d’une branche déjà partagée.
  • Résoudre un conflit sans exécuter les tests.
  • Utiliser reset --hard sans avoir sauvegardé le travail.

Analyse approfondie : récupérer sans perdre de travail

Avant une commande destructive, identifie ce qui est dans le répertoire de travail, l’index et les commits. Les noms de commandes ne suffisent pas à prévoir leur effet : leur portée dépend de la cible et des options.

git status --short
git diff
git diff --staged
git log --oneline --decorate -8

Ces commandes constituent un état des lieux avant toute récupération. Si un fichier modifié doit être conservé temporairement, un commit de sauvegarde sur une branche ou un git stash push -u peut être approprié ; vérifie ensuite le contenu récupéré. Le stash n’est pas une sauvegarde durable et les fichiers ignorés ne sont pas inclus par défaut.

Choisir la bonne opération

  • git revert crée un nouveau commit qui annule l’effet d’un commit existant : pratique pour une branche partagée.
  • git reset déplace le pointeur de branche et, selon le mode, modifie aussi l’index ou le répertoire de travail : prudence sur les commits publiés.
  • git restore restaure des fichiers depuis une source choisie ; une restauration peut écraser des modifications locales.
  • git reflog aide à retrouver des positions récentes de références locales, mais n’est pas une garantie d’archivage permanent.

Vérification après intégration

Après une fusion ou un rebase, inspecte git status, le diff par rapport à la branche cible et l’historique. Exécute les tests pertinents : résoudre les marqueurs de conflit ne garantit pas que le comportement métier est correct.

Exercice guidé

Crée un dépôt, ajoute une petite application, puis effectue une fonctionnalité sur une branche dédiée. Crée deux commits distincts, modifie la même ligne sur deux branches et provoque un conflit. Résous-le, inspecte le diff final et lance les tests.

Critères de réussite

  • Les commits sont petits et décrivent une intention cohérente.
  • La branche principale reste stable pendant le développement.
  • Le conflit est résolu en comprenant les deux changements.
  • Les tests passent après intégration.
  • La méthode d’annulation choisie correspond à l’effet voulu.
