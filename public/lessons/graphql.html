GraphQL

Comprendre schémas, queries, mutations, résolution des données et limites d’une API GraphQL.

Leçon approfondieThéorie · pratique · validation

Objectifs d’apprentissage

À la fin de cette leçon, tu dois pouvoir expliquer les concepts avec tes propres mots, choisir une approche adaptée à un contexte réel et justifier tes décisions en fonction des contraintes et des risques.

  • Comprendre les notions essentielles et le problème qu’elles permettent de résoudre.
  • Appliquer une méthode concrète et vérifier son résultat.
  • Identifier les limites, les compromis et les erreurs fréquentes.

1. Le modèle mental de GraphQL

GraphQL est un langage de requête et une spécification pour demander des données à une API. Le client décrit les champs qu’il souhaite recevoir ; le serveur expose un schéma qui définit les types, les champs et les opérations possibles. GraphQL ne remplace pas automatiquement une base de données et n’est pas un moteur qui rend toute requête gratuite : le serveur doit toujours authentifier, autoriser, résoudre et limiter les demandes.

Les opérations principales sont les queries pour lire, les mutations pour demander une modification et, dans certains systèmes, les subscriptions pour recevoir des événements. Le type racine et les champs disponibles sont décrits par le schéma. Le client choisit les champs à sélectionner, mais il ne peut pas inventer un champ absent du contrat.

GraphQL peut réduire le sur- ou sous-chargement de données et facilite les besoins variés de plusieurs interfaces. En contrepartie, le serveur doit gérer la complexité des requêtes, la mise en cache, les permissions au niveau des champs et les performances de résolution. Une API REST bien conçue peut être plus simple pour certains domaines ; le choix dépend des besoins réels.

2. Schéma, types et opérations

type Product {
  id: ID!
  name: String!
  priceCents: Int!
}

type ProductEdge {
  cursor: String!
  node: Product!
}

type PageInfo {
  hasNextPage: Boolean!
  endCursor: String
}

type ProductConnection {
  edges: [ProductEdge!]!
  pageInfo: PageInfo!
}

type Query {
  product(id: ID!): Product
  products(first: Int = 20, after: String): ProductConnection!
}

type Mutation {
  renameProduct(id: ID!, name: String!): Product
}

Le suffixe ! signifie que le champ ou argument ne peut pas être nul dans le contrat. [ProductEdge!]! signifie que la liste elle-même et ses éléments ne sont pas nuls. Ces distinctions sont importantes pour le client : un champ nullable peut représenter une absence normale ou une erreur de résolution selon le contexte et le format de réponse.

Une pagination par curseur peut s’utiliser ainsi :

query ProductPage($first: Int!, $after: String) {
  products(first: $first, after: $after) {
    edges { cursor node { id name priceCents } }
    pageInfo { hasNextPage endCursor }
  }
}

Le client transmet endCursor comme valeur de after à la page suivante et s’arrête lorsque hasNextPage vaut false. Le curseur est un jeton opaque, pas un droit d’accès : le serveur doit refaire les contrôles d’autorisation à chaque page. Pour éviter les doublons ou les omissions pendant que les données changent, le tri doit être stable et comporter un critère de départage unique, par exemple createdAt puis id. Borne aussi first côté serveur.

Une query pourrait être :

query ProductDetails($id: ID!) {
  product(id: $id) {
    id
    name
    priceCents
  }
}

Les variables séparent les valeurs du document de requête. Elles rendent la requête réutilisable et évitent de construire manuellement des fragments de texte à partir des entrées. Le client ne devrait pas assembler une requête par concaténation de chaînes non fiables.

Une mutation exprime une intention de changement. Il faut définir les règles de validation, les erreurs métier, l’autorisation et les effets de bord. Le fait qu’un champ existe dans le schéma ne signifie pas que tous les utilisateurs peuvent l’appeler. L’authentification identifie l’appelant ; l’autorisation décide ce qu’il a le droit de faire sur une ressource précise.

3. Résolveurs et accès aux données

Un résolveur fournit la valeur d’un champ. Il peut lire une base, appeler un service ou calculer un résultat. Un schéma clair ne garantit pas un bon plan d’exécution : si une query récupère 100 commandes et effectue ensuite une requête séparée pour chaque client, le serveur peut produire le problème N+1, soit une requête initiale puis une requête par élément.

Pour réduire ce coût, utilise des jointures adaptées, des chargements groupés ou un mécanisme de batching comme DataLoader. Mesure les requêtes réelles avant d’optimiser, et garde les règles métier dans des services réutilisables plutôt que de dupliquer la logique dans plusieurs résolveurs. Une mutation devrait aussi traiter les transactions nécessaires et définir ce qui se passe en cas d’échec partiel.

Les erreurs doivent être compréhensibles pour le client sans divulguer les détails internes. Évite de retourner une trace de pile, une requête SQL ou des secrets dans les messages d’erreur de production. Distingue les erreurs de validation, les refus d’accès, les ressources absentes et les pannes techniques lorsque cela est utile au contrat.

4. Performance, cache et sécurité

Les clients peuvent imbriquer des champs et créer des requêtes très coûteuses. Fixe des limites de profondeur ou de complexité, des quotas et des délais d’exécution adaptés. Les limites doivent correspondre aux usages réels : une requête légitime peut avoir plusieurs niveaux d’imbrication. Surveille les requêtes lentes et les résolveurs qui accèdent à trop de données.

Le cache est plus subtil que dans de nombreuses API REST, car deux requêtes différentes peuvent viser les mêmes entités avec des sélections différentes. Un cache au niveau du client, un cache de réponse et un cache d’entité ne résolvent pas les mêmes problèmes. Les mutations doivent invalider ou mettre à jour les données concernées, et les réponses personnalisées ne doivent pas être partagées entre utilisateurs sans contrôle.

Applique l’autorisation à chaque chemin sensible, pas uniquement au point d’entrée. Un utilisateur peut demander un champ ou un identifiant qui ne lui appartient pas. Limite également l’introspection selon le contexte de sécurité et les besoins opérationnels ; elle n’est pas à elle seule une faille, mais elle peut exposer la structure de l’API. Valide les entrées, borne la pagination et protège les mutations contre les abus.

5. Quand choisir GraphQL ?

GraphQL est intéressant lorsque plusieurs clients ont des besoins de données différents, lorsque les relations entre entités sont nombreuses ou lorsque le contrat doit évoluer sans créer de nombreux endpoints spécialisés. Il peut être moins adapté si l’application expose surtout des ressources simples, si le cache HTTP standard est central, ou si l’équipe ne peut pas assurer les contrôles de complexité et de permissions nécessaires.

Évite de créer un champ qui renvoie une structure arbitraire sans contrat, de dupliquer les mêmes données dans plusieurs endroits du schéma ou de confondre le schéma public avec la structure interne de la base. Un schéma est une API conçue pour des clients : il doit évoluer de manière compatible, documenter les dépréciations et conserver une sémantique stable.

6. Exercice pratique

Conçois un schéma GraphQL pour des livres et leurs auteurs. Ajoute une query paginée, une query par identifiant et une mutation de renommage. Décris les permissions nécessaires, un risque N+1, une limite de complexité et le comportement lorsqu’un livre n’existe pas. Explique dans quels cas une API REST serait plus simple.

Critères de réussite

  • Je distingue query, mutation, subscription, schéma et résolveur.
  • Je comprends la nullabilité et l’usage des variables.
  • Je sais reconnaître le problème N+1 et envisager le batching.
  • Je prévois permissions, limites de requête, pagination et cache.
  • Je peux justifier le choix de GraphQL face à une API REST.

165 — Atelier de clôture : concevoir et sécuriser une API GraphQL

Objectif : Conçois un schéma GraphQL stable et maîtrise les coûts des requêtes.

Modèle mental et méthode

Le schéma expose des types, champs et opérations. Les resolvers chargent les données ; sans stratégie de regroupement, les relations peuvent créer le problème N+1. Ajoute limites de profondeur/coût, pagination, autorisation au niveau des ressources et gestion des erreurs sans fuite interne.

Exemple guidé

Exemple : une requête listant 100 auteurs et leurs livres ne doit pas déclencher 101 requêtes SQL. Un DataLoader peut regrouper les identifiants dans une requête par lot.

Pièges à éviter

Pièges : croire que masquer un champ dans l’interface constitue une autorisation, exposer des erreurs SQL, autoriser des requêtes imbriquées coûteuses.

Exercice de synthèse

Exercice : définis une API de catalogue avec pagination cursor-based, règles d’accès et stratégie contre N+1.

Critères de réussite

Réussite : schéma cohérent, contrôle d’accès serveur, coûts bornés, pagination et tests documentés.
