2. Frontend

HTML sémantique

Structurer le contenu avec des éléments HTML qui expriment leur rôle, améliorent l’accessibilité et rendent le document plus robuste.

Tutoriel détailléLot 8 · 2026

Objectifs d’apprentissage

  • Choisir les éléments HTML selon le sens du contenu.
  • Construire une hiérarchie de titres logique.
  • Structurer navigation, contenu principal, articles et formulaires.
  • Comprendre les bénéfices et limites de la sémantique native.

1. Le HTML décrit le sens du contenu

HTML n’est pas seulement un moyen de placer des blocs à l’écran. Les éléments indiquent le rôle du contenu : titre, paragraphe, navigation, liste, bouton, formulaire ou article. Le CSS contrôle l’apparence et JavaScript le comportement ; utiliser l’élément approprié donne au navigateur et aux technologies d’assistance des informations déjà standardisées.

Préfère un élément natif à un div générique lorsqu’il correspond réellement à l’intention. Un button possède par exemple un comportement clavier et un rôle accessibles par défaut, contrairement à un div auquel on aurait seulement ajouté une classe.

2. Organiser la page

<header>
      <h1>Catalogue</h1>
      <nav aria-label="Navigation principale">...</nav>
    </header>
    <main>
      <section aria-labelledby="nouveautes">
        <h2 id="nouveautes">Nouveautés</h2>
        <article>
          <h3>Produit récent</h3>
          <p>Description du produit.</p>
        </article>
      </section>
    </main>
    <footer>Informations de contact</footer>

Utilise un seul main visible représentant le contenu dominant de la page. section regroupe un thème, tandis que article représente un contenu autonome qui pourrait être compris séparément. Le choix dépend du sens, pas de la mise en page souhaitée.

3. Hiérarchie des titres

Les titres structurent le document pour tous les lecteurs, y compris ceux qui naviguent par liste de titres. Choisis les niveaux selon la hiérarchie du contenu : un titre principal, puis des sous-parties, puis leurs sous-parties. Ne choisis pas un niveau uniquement parce que sa taille par défaut convient visuellement ; le CSS gère la présentation.

Chaque section titrée doit avoir un titre qui décrit son contenu. Les intitulés vagues comme « Divers » ou « Cliquez ici » sont moins utiles. La hiérarchie n’a pas besoin d’être artificiellement parfaite dans chaque détail, mais elle doit refléter l’organisation réelle de la page.

4. Liens, boutons et formulaires

Un lien mène vers une ressource ou une destination ; un bouton déclenche une action. N’utilise pas un lien sans destination comme bouton, ni un bouton pour naviguer simplement vers une autre page. Les libellés doivent être compréhensibles hors contexte autant que possible.

Associe chaque champ de formulaire à un libellé explicite. Les attributs name, type, required et les contraintes adaptées aident le navigateur, mais la validation côté client ne remplace pas la validation serveur. Les messages d’erreur doivent être liés aux champs concernés et perceptibles par les technologies d’assistance.

<label for="courriel">Adresse e-mail</label>
<input id="courriel" name="courriel" type="email"
       aria-invalid="true" aria-describedby="courriel-erreur">
<p id="courriel-erreur">Saisis une adresse e-mail valide.</p>

Dans cet exemple, aria-describedby relie le champ au texte d’erreur et aria-invalid="true" indique un état réellement invalide. Ne pose cet état qu’après avoir constaté l’erreur ; retire-le ou remets-le à false lorsque le champ redevient valide. Le serveur doit appliquer la même règle métier indépendamment de cet affichage.

5. Accessibilité et validation

Le HTML sémantique est une base importante, mais il ne garantit pas à lui seul une interface accessible. Il faut aussi vérifier le contraste, l’ordre du focus, les libellés, les messages d’erreur et le comportement clavier. N’ajoute pas des rôles ARIA lorsqu’un élément natif exprime déjà le même rôle, et ne change pas le rôle d’un élément sans reproduire les comportements attendus.

Valide le document avec un validateur HTML, puis teste-le au clavier et avec les outils d’accessibilité du navigateur. Les validateurs détectent des erreurs de syntaxe et de structure, mais ne remplacent pas une évaluation d’usage.

Erreurs fréquentes

  • Employer des div pour tous les composants interactifs.
  • Choisir les titres en fonction de leur taille visuelle.
  • Confondre navigation et action.
  • Ajouter des rôles ARIA redondants ou incorrects.
  • Considérer un HTML valide comme une preuve suffisante d’accessibilité.

Analyse approfondie : choisir l’élément selon l’intention

La sémantique dépend du rôle du contenu, pas de son apparence. Un élément <nav> représente un ensemble important de liens de navigation ; un lien <a href> mène vers une destination ; un bouton <button> déclenche une action. Un élément générique stylé pour ressembler à un bouton ne fournit pas automatiquement les interactions clavier attendues.

Exemple : lien ou action ?

<a href="/profil">Consulter mon profil</a>
<button type="button" id="ouvrir-aide">Afficher l’aide</button>

Le premier contrôle change de destination ; le second modifie l’interface. Pour un formulaire, un bouton sans attribut type peut soumettre le formulaire par défaut. Déclare type="button" pour une action qui ne doit pas déclencher la soumission, et type="submit" pour la validation prévue.

Structure des titres et régions

Organise les titres selon la hiérarchie du contenu plutôt qu’en fonction de leur taille visuelle. Utilise CSS pour l’apparence. Les régions <main>, <header>, <footer> et <nav> ont un sens contextuel : plusieurs en-têtes ou pieds de page sont possibles, mais ils ne sont pas tous des régions de repérage selon leur emplacement.

Valide le document, puis parcours-le sans souris. La validation syntaxique repère certaines erreurs, mais elle ne peut pas décider si les éléments choisis représentent correctement l’intention éditoriale.

Exercice guidé

Réécris une page composée uniquement de conteneurs génériques. Utilise les éléments appropriés pour l’en-tête, la navigation, le contenu principal, les sections, les articles, les listes et les actions. Ajoute des titres hiérarchisés et des libellés de formulaire, puis valide le résultat.

Critères de réussite

  • La structure reflète le sens du contenu.
  • Les liens naviguent et les boutons déclenchent des actions.
  • La hiérarchie des titres est compréhensible.
  • Les champs disposent de libellés explicites.
  • Le document est validé puis testé au clavier.
