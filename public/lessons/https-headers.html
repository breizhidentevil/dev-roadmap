5. Sécurité applicative

HTTPS et en-têtes de sécurité

Protéger le transport et renforcer les politiques du navigateur.

Tutoriel approfondiSécurité applicative

Objectifs d’apprentissage

Tu dois pouvoir expliquer ce que garantit HTTPS, choisir quelques en-têtes de sécurité adaptés et vérifier leur présence sur les réponses réelles. Tu dois aussi comprendre qu’un en-tête mal configuré peut casser l’application ou créer un faux sentiment de sécurité.

  • Distinguer chiffrement du transport, identité du serveur et protection côté navigateur.
  • Comprendre HSTS, CSP, nosniff et les politiques de référent.
  • Déployer les changements progressivement et surveiller les effets secondaires.

1. Ce que HTTPS garantit

HTTPS utilise TLS pour protéger la confidentialité et l’intégrité des échanges et authentifier le serveur via son certificat. Il ne corrige pas une autorisation défaillante, une injection SQL ou une XSS. Les données peuvent encore être exposées par l’application, les logs, le navigateur ou un poste compromis.

En production, redirige HTTP vers HTTPS et assure-toi que les ressources, API et liens utilisés par la page ne réintroduisent pas de contenu non sécurisé. Le renouvellement du certificat, la chaîne de confiance et la configuration TLS doivent être surveillés.

2. HSTS : mémoriser l’usage de HTTPS

Strict-Transport-Security indique au navigateur de privilégier HTTPS pour les connexions futures à l’hôte. Exemple :

Strict-Transport-Security: max-age=31536000; includeSubDomains

N’active includeSubDomains que si tous les sous-domaines concernés supportent HTTPS. Le paramètre preload implique un processus externe et des exigences strictes ; ne l’ajoute pas sans vérifier que le domaine est prêt et que l’engagement est voulu. HSTS n’est pris en compte que lorsqu’il est reçu sur une connexion HTTPS valide.

3. CSP : réduire les sources de contenu

La Content Security Policy définit les sources depuis lesquelles le navigateur peut charger des scripts, styles, images et autres ressources. Une politique de départ peut être restrictive :

Content-Security-Policy: default-src 'self'; object-src 'none'; base-uri 'self'; frame-ancestors 'none'

Une application réelle doit compléter cette politique selon ses besoins, notamment pour les scripts, styles, API, polices et intégrations. Évite de copier une liste de domaines trop large ou de compter sur 'unsafe-inline' comme solution durable. Les nonces ou hashes peuvent permettre une politique de scripts plus stricte.

Commence éventuellement par Content-Security-Policy-Report-Only pour observer les violations sans bloquer immédiatement les ressources, puis resserre la politique et passe en mode effectif après validation.

4. En-têtes complémentaires

  • X-Content-Type-Options: nosniff demande au navigateur de respecter le type MIME annoncé plutôt que de tenter certaines interprétations.
  • Referrer-Policy: strict-origin-when-cross-origin limite les informations de provenance envoyées à d’autres origines, tout en conservant un comportement utile dans de nombreux cas.
  • frame-ancestors dans CSP contrôle les sites qui peuvent intégrer la page dans une frame.
  • Permissions-Policy permet de restreindre l’accès à certaines fonctionnalités du navigateur, selon les besoins du produit.

Ne copie pas une liste sans comprendre son effet. Par exemple, interdire toute intégration en frame peut casser un flux légitime d’administration ou d’intégration partenaire.

5. Déploiement et vérification

Les en-têtes doivent être définis à un niveau cohérent : application, reverse proxy ou CDN. Évite les valeurs contradictoires ajoutées par plusieurs couches. Vérifie les réponses HTML, API, erreurs et redirections, pas uniquement la page d’accueil.

Tu peux inspecter les en-têtes avec l’onglet Réseau du navigateur ou une commande GET qui conserve les en-têtes sans afficher le corps :

export APP_URL="https://app.example.test"
curl -sS -D - -o /dev/null "$APP_URL/"

Une requête HEAD (curl -I) peut suivre un chemin différent de GET selon le serveur. Vérifie aussi la chaîne de redirections avec curl -sS -D - -o /dev/null -L "$APP_URL/", puis teste séparément les routes API, les réponses 404/500 et les ressources statiques. Ces commandes inspectent les réponses HTTP ; elles ne prouvent pas à elles seules que le navigateur applique la politique comme prévu.

Matrice de vérification

  • HTTP redirige vers HTTPS sans boucle et sans rétrograder une URL sensible.
  • La réponse HTML principale, une route API, une ressource statique et une page d’erreur portent les en-têtes attendus.
  • La CSP en mode rapport produit des rapports utiles sans exposer de données sensibles ; les violations légitimes sont examinées avant le mode bloquant.
  • HSTS n’est testé qu’après validation du HTTPS sur tous les hôtes inclus ; includeSubDomains et preload ne sont pas ajoutés par défaut.

Déployer les en-têtes sans casser l’application

Les en-têtes de sécurité doivent être testés sur les réponses HTML, les erreurs, les redirections et les sous-domaines concernés. HTTPS protège le transport entre les points terminaux, mais ne rend pas l’application sûre contre les contrôles d’accès défaillants ou les scripts injectés.

Déploie une CSP en mode rapport avant d’appliquer une politique restrictive, analyse les violations puis retire progressivement les exceptions. Évite d’autoriser largement unsafe-inline ou * pour faire disparaître les erreurs. HSTS ne doit être activé qu’après confirmation que le domaine et les sous-domaines visés peuvent fonctionner durablement en HTTPS ; l’option preload a des conséquences de déploiement difficiles à annuler rapidement.

  • Vérifier la chaîne de certificats, le renouvellement et les redirections HTTP vers HTTPS.
  • Contrôler CSP, X-Content-Type-Options et les politiques de cadrage selon l’application.
  • Tester les ressources tierces, les connexions API, les iframes légitimes et les pages d’erreur.
  • Conserver un plan de retour arrière pour les politiques qui bloquent une fonctionnalité.

Erreurs fréquentes

  • Activer HSTS avant que HTTPS soit correctement opérationnel sur les sous-domaines visés.
  • Déployer une CSP copiée telle quelle, qui bloque des scripts nécessaires ou autorise trop de sources.
  • Penser que les en-têtes remplacent l’encodage de sortie, les contrôles d’accès ou les mises à jour.
  • Ne vérifier que le code 200 et oublier les pages d’erreur ou redirections.
  • Ajouter plusieurs valeurs contradictoires depuis le serveur et le proxy.

Exercice guidé

Sur une application de test que tu contrôles, relève les en-têtes existants, puis propose HSTS, CSP, nosniff et une politique de référent. Si tu ajoutes CSP, commence en mode rapport et observe les violations pendant que tu parcours les fonctionnalités principales.

Teste les pages de connexion, les formulaires, les images, les scripts, les appels API et les intégrations externes avant d’appliquer la politique en mode bloquant.

Exercice autonome et critères de réussite

Écris un tableau avec chaque en-tête, la menace ciblée, la valeur choisie, les effets secondaires possibles et le test de validation.

Réussite : HTTPS fonctionne sur tous les hôtes concernés ; HSTS est activé avec un périmètre compris ; la CSP est testée sur les parcours réels ; les en-têtes sont cohérents sur les réponses principales et d’erreur ; aucune politique n’est ajoutée sans justification ; les contrôles applicatifs restent en place.
