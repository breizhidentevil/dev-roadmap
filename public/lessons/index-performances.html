4. Bases de données et modélisation

Index et performances SQL

Comprendre comment un index accélère certaines lectures et ajoute des coûts d’écriture et de stockage.

Seconde passe pédagogiqueBase de données

Objectifs d’apprentissage

  • Expliquer ce qu’un index accélère et ce qu’il coûte.
  • Choisir des index à partir des requêtes réellement exécutées.
  • Lire les bases d’un plan EXPLAIN.

1. Rôle d’un index

Un index est une structure auxiliaire qui aide le moteur à retrouver certaines lignes sans parcourir toute la table. Les index B-tree courants conviennent notamment aux égalités, aux plages de valeurs et à certains tris. Les clés primaires et contraintes UNIQUE créent généralement un index adapté dans les bases relationnelles.

CREATE INDEX idx_commandes_client_date
ON commandes (client_id, cree_le DESC);

SELECT id, cree_le
FROM commandes
WHERE client_id = 42
ORDER BY cree_le DESC
LIMIT 20;

L’index composé permet de filtrer par client puis de parcourir ses commandes récentes. L’ordre des colonnes compte : un index sur (client_id, cree_le) ne remplace pas nécessairement un index sur (cree_le, client_id).

2. Partir des requêtes réelles

Un index n’est pas un accélérateur universel. Il doit correspondre à un filtre, un tri ou une jointure réelle, avec une sélectivité suffisante. Commence par capturer la requête, les paramètres représentatifs, la durée, le nombre de lignes renvoyées et la fréquence d’exécution. Teste aussi des paramètres fréquents et rares : le même plan n’est pas forcément optimal pour les deux.

Pour un index composé, l’ordre des colonnes compte. Dans cet exemple, un index sur (client_id, cree_le) peut aider une recherche filtrée par client_id et triée par cree_le, mais n’est pas équivalent à un index sur (cree_le, client_id). L’ordre des colonnes doit correspondre aux filtres et tris réellement utilisés. Évite d’ajouter un index redondant sans comparer les préfixes et les contraintes déjà présentes.

3. Mesurer avec EXPLAIN

EXPLAIN (ANALYZE, BUFFERS)
SELECT id, cree_le
FROM commandes
WHERE client_id = 42
ORDER BY cree_le DESC
LIMIT 25;

EXPLAIN présente le plan estimé ; EXPLAIN ANALYZE exécute la requête et compare les estimations aux mesures. Inspecte les écarts de cardinalité, les boucles répétées, le tri, les lectures de blocs et le temps total. Un parcours séquentiel peut être le meilleur choix si une grande partie de la table est demandée.

Protocole : mesure avant, crée un seul index candidat, actualise les statistiques si nécessaire, répète les mesures sur des données représentatives, puis contrôle le coût d’écriture et l’espace. Ne teste pas uniquement sur une table minuscule et ne publie pas de chiffres de benchmark sans préciser données, cache et environnement.

Erreurs fréquentes

  • Indexer toutes les colonnes « au cas où ».
  • Ignorer l’ordre des colonnes d’un index composé.
  • Mesurer sur une table minuscule ou une seule exécution.
  • Considérer tout parcours séquentiel comme mauvais.
  • Ne pas comparer les plans avant et après modification.

Exercice

Analyse une requête qui recherche les commandes d’un client et les trie par date. Compare son plan avant et après la création d’un index composé. Note les lignes estimées et réelles, la durée, puis réfléchis au coût supplémentaire sur les insertions.

Critères de réussite

  • L’index répond à une requête identifiée.
  • Les plans sont comparés dans des conditions similaires.
  • Le compromis stockage/écriture est expliqué.
  • Tu acceptes de ne pas conserver l’index si le gain n’est pas démontré.
