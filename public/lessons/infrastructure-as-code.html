Infrastructure as code

L’infrastructure as code (IaC) transforme la configuration des environnements en fichiers révisables et reproductibles. Elle réduit les écarts entre environnements, à condition de maîtriser l’état, les secrets et les changements appliqués.

Tutoriel approfondiCompétence Full Stack

Objectifs et prérequis

Après ce tutoriel, vous devez pouvoir expliquer pourquoi l’infrastructure est décrite dans des fichiers, distinguer configuration déclarative et scripts impératifs, lire un plan de changement et sécuriser l’état d’un outil IaC. Les exemples supposent que vous connaissez déjà les notions de serveur, réseau, base de données et environnement de déploiement.

  • Décrire une infrastructure attendue plutôt que documenter manuellement une machine.
  • Comprendre le cycle initialisation, planification, application et vérification.
  • Réduire les dérives de configuration et les changements non relus.
  • Repérer les risques liés aux secrets, à l’état et aux suppressions.

1. Pourquoi décrire l’infrastructure ?

Une application dépend de ressources qui ne sont pas du code applicatif : réseau, règles de pare-feu, service de calcul, stockage, base de données, comptes de service, DNS et certificats. Si elles sont créées à la main, leur configuration dépend de la mémoire des opérateurs et les environnements finissent par diverger.

L’IaC stocke une description de ces ressources dans des fichiers suivis par Git. Une revue de code permet alors de répondre à des questions concrètes : quelle règle réseau change ? Quelle base sera remplacée ? Le coût risque-t-il d’augmenter ? Le changement est-il réversible ?

La reproductibilité n’est toutefois pas absolue : les API cloud évoluent, les versions de fournisseurs changent, les quotas varient et certaines ressources contiennent un état externe. Il faut donc épingler les versions utiles, documenter les prérequis et tester les changements dans un environnement adapté.

2. Déclaratif ou impératif ?

Un script impératif décrit une suite d’actions : créer un réseau, puis créer un serveur, puis modifier un fichier. Une approche déclarative décrit plutôt le résultat voulu : « un réseau de tel type, un serveur attaché à ce réseau et une règle autorisant tel trafic ». L’outil compare cette description à l’état qu’il observe et calcule les opérations nécessaires.

Le déclaratif rend l’intention plus lisible et permet de détecter une partie des écarts. Il ne dispense pas de comprendre le plan : une modification de type ou de clé peut entraîner le remplacement d’une ressource, et certains changements ne sont pas réversibles.

Choisissez un outil selon le fournisseur, les compétences de l’équipe, la maturité de l’écosystème, les besoins de tests et les contraintes de licence. Évitez de multiplier les outils IaC pour un même périmètre sans raison opérationnelle claire.

3. Cycle de travail sûr

  1. Décrire : créer des fichiers lisibles, des variables explicites et des valeurs par défaut prudentes.
  2. Formater et valider : utiliser les commandes de formatage et de validation de l’outil dans la CI.
  3. Planifier : générer un plan qui présente les créations, modifications et suppressions prévues.
  4. Relire : faire vérifier les changements sensibles, les règles réseau et les remplacements de données.
  5. Appliquer : exécuter le plan validé avec des identités limitées aux droits nécessaires.
  6. Vérifier : contrôler l’état réel, les journaux de déploiement et le fonctionnement applicatif.

Exemple conceptuel de workflow Terraform : terraform fmt -check, terraform validate, puis terraform plan. Ces commandes ne remplacent pas la revue métier du plan. N’appliquez pas automatiquement un changement destructeur simplement parce que la commande réussit.

# Exemple de variable typée
variable "environment" {
  description = "Environnement ciblé"
  type        = string
  validation {
    condition     = contains(["dev", "staging", "prod"], var.environment)
    error_message = "Utiliser dev, staging ou prod."
  }
}

La validation réduit les valeurs accidentelles, mais ne garantit pas à elle seule qu’une configuration de production est sûre.

4. État, modules et environnements

Les outils déclaratifs maintiennent souvent un fichier ou service d’état qui associe les ressources décrites aux ressources réelles. Cet état peut contenir des identifiants sensibles et des attributs confidentiels : il doit être protégé, sauvegardé et accessible uniquement aux personnes ou pipelines autorisés. Pour une équipe, un stockage distant avec verrouillage concurrent est généralement préférable à un fichier local partagé de manière informelle.

Les modules permettent de réutiliser une abstraction, par exemple un service web avec ses règles réseau. Un bon module expose peu de paramètres, valide les entrées et masque les détails répétitifs sans rendre le comportement opaque. Trop de paramètres génériques transforment un module en mini-langage difficile à comprendre.

Séparez les environnements selon le risque et le cycle de vie : les ressources de test ne doivent pas pouvoir être supprimées par erreur lors d’une opération de production. Les espaces de travail ne remplacent pas automatiquement une séparation forte des droits, des comptes ou des états.

5. Secrets, dérive et pièges

  • Secrets dans Git : ne mettez pas de mot de passe ou de jeton dans un fichier versionné. Utilisez un gestionnaire de secrets et limitez leur exposition dans les journaux et les plans.
  • Application aveugle : un plan doit être lu, surtout s’il contient des suppressions, des remplacements ou des changements réseau.
  • Dérive manuelle : une modification dans la console peut créer un écart entre la description et la réalité. Détectez-le et décidez si la source de vérité doit être modifiée ou si la ressource doit être réalignée.
  • Concurrence : deux applications simultanées peuvent se contredire si l’état n’est pas verrouillé.
  • Dépendance implicite : exprimez les dépendances nécessaires dans la configuration plutôt que de compter sur l’ordre accidentel des fichiers.
  • Destruction trop facile : protégez les ressources critiques et préparez des sauvegardes avant toute opération destructive.

L’IaC ne rend pas une infrastructure intrinsèquement sécurisée. Elle rend les changements plus visibles et répétables, y compris les mauvaises décisions.

6. Exemple de revue d’un plan IaC en production

Un plan annonce le remplacement d’une base de données alors que la demande initiale portait seulement sur l’ajout d’une règle réseau. N’applique pas le plan sous prétexte que la validation syntaxique réussit. Identifie la ressource remplacée, la raison du remplacement, les dépendances et l’impact sur les données avant de poursuivre.

  1. Vérifie le workspace, le compte/projet et la région ciblés.
  2. Relis les créations, modifications et destructions, en particulier les ressources avec état.
  3. Confirme que le plan correspond à la version du code qui sera appliquée et qu’il n’est pas périmé.
  4. Contrôle les sauvegardes et le chemin de récupération des ressources critiques.
  5. Fais approuver le changement sensible par une seconde personne, puis applique-le avec une identité à privilèges limités.
  6. Compare l’état réel après application et consigne l’écart éventuel.

L’état IaC peut contenir des métadonnées sensibles, voire des valeurs secrètes selon le fournisseur et la ressource. Stocke-le dans un backend distant avec contrôle d’accès, chiffrement et verrouillage si l’outil le prend en charge. Ne le commite pas dans le dépôt par défaut et ne suppose pas qu’un secret reste masqué parce qu’il est déclaré comme sensible : cette propriété peut limiter l’affichage sans empêcher son stockage dans l’état.

Le drift — différence entre la description versionnée et l’infrastructure réelle — doit être traité explicitement. Détermine si la modification manuelle est légitime : soit elle est réintégrée dans le code, soit elle est annulée par une application contrôlée. Évite qu’une exécution automatique efface sans revue une correction d’urgence.

Exercice guidé

Imaginez une application de démonstration qui nécessite un réseau privé, un serveur web et une base de données non exposée directement à Internet. Écrivez un plan de conception IaC avant de coder : ressources, variables, dépendances, droits et sorties utiles. Puis relisez le plan comme si vous étiez responsable de la production.

  1. Quelles ressources doivent être publiques et lesquelles doivent rester privées ?
  2. Comment différencier développement et production sans copier-coller toute la configuration ?
  3. Où seront stockés l’état et les secrets ? Qui peut les lire ?
  4. Quel contrôle empêcherait la suppression accidentelle de la base ?
  5. Quels tests doivent bloquer une pull request ?

Critères de réussite : vous distinguez l’état déclaré de l’état réel, prévoyez un plan relu avant application, ne versionnez aucun secret, protégez l’état partagé et expliquez comment détecter une dérive.
