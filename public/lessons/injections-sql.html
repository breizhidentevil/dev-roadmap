5. Sécurité applicative

Prévention des injections SQL

Séparer strictement les données du langage SQL et réduire l’impact des erreurs de sécurité.

Tutoriel approfondiBackend et données

Objectifs d’apprentissage

  • Expliquer comment une donnée non fiable peut modifier la structure d’une requête SQL.
  • Utiliser des requêtes paramétrées et distinguer valeurs et identifiants SQL.
  • Réduire l’impact d’une vulnérabilité par les privilèges minimaux et les tests.

1. Comprendre l’injection SQL

Une injection SQL survient lorsque l’application construit une requête en concaténant du texte contrôlé par l’utilisateur. La donnée peut alors être interprétée comme une partie du langage SQL plutôt que comme une simple valeur. Le problème est une confusion entre code et données, pas seulement la présence de caractères inhabituels.

// À éviter : concaténation de l’entrée utilisateur
const sql = "SELECT id FROM users WHERE email = '" + email + "'";

Une entrée conçue pour fermer la chaîne et ajouter une condition peut modifier la logique de la requête. Selon les droits du compte de base, les conséquences peuvent inclure lecture non autorisée, modification ou suppression de données.

2. Paramétrer les valeurs

La défense principale est d’utiliser les paramètres fournis par le pilote ou l’ORM. Le SQL est préparé séparément des valeurs, qui sont transmises comme données.

// Exemple avec node-postgres
const result = await pool.query(
  "SELECT id FROM users WHERE email = $1",
  [email]
);

Ne remplace pas ce mécanisme par un échappement manuel improvisé. Les paramètres servent aux valeurs, pas aux noms de table, de colonne ou aux mots-clés. Pour un tri dynamique, associe une entrée utilisateur à une liste blanche d’identifiants SQL autorisés :

const sortColumns = {
  recent: "created_at",
  name: "display_name"
};
const column = sortColumns[requestedSort] ?? sortColumns.recent;
// La valeur de column provient exclusivement de la liste blanche.
// Les valeurs filtrées restent paramétrées.

Les noms autorisés doivent être choisis par le code, jamais copiés directement depuis une entrée utilisateur.

3. Défense en profondeur

Le compte applicatif de base ne doit posséder que les privilèges nécessaires : éviter un compte administrateur partagé avec l’application. Valide les données pour respecter les règles métier, mais ne considère pas cette validation comme un substitut aux paramètres. Les erreurs SQL détaillées ne doivent pas être exposées aux utilisateurs ; journalise les informations utiles côté serveur sans y écrire des secrets.

Les tests doivent vérifier les chemins de lecture et d’écriture, y compris les filtres, recherches et tris dynamiques. Un ORM n’immunise pas automatiquement le code : les requêtes brutes ou les fragments SQL construits dynamiquement peuvent rester vulnérables.

Diagnostic d’une requête dynamique

La revue doit porter sur chaque fragment de syntaxe construit dynamiquement : filtres, recherche, tri, exports, rapports et requêtes brutes de l’ORM. Une valeur paramétrée reste une donnée ; un identifiant SQL doit provenir d’un choix fermé défini par le serveur.

const sortMap = new Map<string, "created_at" | "display_name">([
  ["recent", "created_at"],
  ["name", "display_name"],
]);

function resolveSortColumn(requestedSort: string) {
  return sortMap.get(requestedSort) ?? "created_at";
}

const sortColumn = resolveSortColumn(requestedSort);
const rows = await pool.query(
  `SELECT id, display_name FROM users WHERE tenant_id = $1 ORDER BY ${sortColumn}`,
  [tenantId]
);

Les valeurs interpolées sont ici exclusivement des constantes du code. Une Map évite aussi de confondre une clé autorisée avec une propriété héritée d’un objet JavaScript. Une assertion TypeScript ne valide jamais une entrée à l’exécution : contrôle d’abord le type de la valeur reçue, puis applique la liste blanche. Les valeurs de filtre restent paramétrées.

Tests de non-régression

expect(resolveSortColumn("recent")).toBe("created_at");
expect(resolveSortColumn("name")).toBe("display_name");
expect(resolveSortColumn("toString")).toBe("created_at");
expect(resolveSortColumn("name DESC; DROP TABLE users")).toBe("created_at");

Ces tests vérifient le choix de colonne, pas toute la sécurité de la requête. Complète-les par des tests d’intégration sur les filtres paramétrés, les recherches, la pagination, les permissions de tenant et les messages d’erreur génériques.

Erreurs fréquentes

  • Échapper manuellement les apostrophes au lieu d’utiliser des paramètres.
  • Concaténer une valeur dans une clause WHERE ou LIKE.
  • Insérer directement un nom de colonne demandé par le client.
  • Penser que la validation de formulaire suffit à sécuriser la requête.
  • Exécuter l’application avec un compte SQL disposant de droits excessifs.

Exercice

Réécris une recherche d’utilisateurs qui filtre par e-mail et autorise un tri par date ou nom. Utilise des paramètres pour les valeurs et une liste blanche pour la colonne de tri. Ajoute une courte stratégie de tests et indique les privilèges nécessaires au compte applicatif.

Critères de réussite

  • Aucune entrée utilisateur n’est concaténée comme valeur SQL.
  • Le tri dynamique ne peut sélectionner qu’une colonne autorisée.
  • Les privilèges du compte applicatif sont limités au nécessaire.
  • Les tests couvrent filtres, tris et requêtes brutes éventuelles.
