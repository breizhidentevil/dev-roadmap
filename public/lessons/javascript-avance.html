Objectifs d’apprentissage

  • Expliquer la portée lexicale et le fonctionnement d’une closure.
  • Manipuler des promesses avec then, catch et finally.
  • Utiliser async/await sans perdre la gestion des erreurs.
  • Différencier tâches synchrones, microtâches et tâches de la boucle d’événements.
  • Choisir entre exécution séquentielle et concurrente.

1. Portée lexicale et closures

La portée lexicale détermine où un nom peut être utilisé à partir de la structure du code. Une closure est une fonction associée à l’environnement lexical dans lequel elle a été créée. Elle peut donc conserver l’accès à des variables même après le retour de la fonction externe.

function creerCompteur() {
      let valeur = 0;
      return function incrementer() {
        valeur += 1;
        return valeur;
      };
    }
    const compteur = creerCompteur();
    console.log(compteur()); // 1
    console.log(compteur()); // 2

La variable valeur n’est pas globale : elle reste accessible via la fonction retournée. Les closures sont utiles pour encapsuler un état, fabriquer des fonctions spécialisées ou conserver des callbacks. Elles peuvent toutefois prolonger la durée de vie d’objets en mémoire si des références inutiles sont conservées.

2. Promesses et propagation des erreurs

function chargerProfil(id) {
      return fetch(`/api/profils/${id}`)
        .then(reponse => {
          if (!reponse.ok) throw new Error(`HTTP ${reponse.status}`);
          return reponse.json();
        });
    }
    
    chargerProfil("u-42")
      .then(profil => afficher(profil))
      .catch(erreur => afficherErreur(erreur))
      .finally(() => masquerIndicateur());

Une promesse représente un résultat futur : en attente, accomplie ou rejetée. Une réponse HTTP 404 ne rejette pas automatiquement la promesse renvoyée par fetch ; il faut vérifier response.ok. Une chaîne de then renvoie une nouvelle promesse, ce qui permet de propager les résultats et les erreurs.

3. async/await

async function chargerProfil(id) {
      const reponse = await fetch(`/api/profils/${id}`);
      if (!reponse.ok) {
        throw new Error(`Échec HTTP ${reponse.status}`);
      }
      return reponse.json();
    }
    
    async function afficherProfil(id) {
      try {
        const profil = await chargerProfil(id);
        afficher(profil);
      } catch (erreur) {
        afficherErreur(erreur);
      }
    }

Une fonction async renvoie toujours une promesse. await suspend la progression de cette fonction jusqu’au règlement de la promesse, sans bloquer à lui seul le thread JavaScript de l’interface. Une exception dans la fonction se traduit par une promesse rejetée. Intercepte les erreurs au niveau où une décision utile peut être prise, sans les avaler silencieusement.

4. Séquentiel ou concurrent ?

async function chargerEnSequence(id) {
      // À choisir si la seconde opération dépend du premier résultat.
      const profil = await chargerProfil(id);
      const commandes = await chargerCommandes(id);
      return { profil, commandes };
    }

    async function chargerEnParallele(id) {
      // À choisir uniquement si les deux appels sont indépendants.
      const [profil, commandes] = await Promise.all([
        chargerProfil(id),
        chargerCommandes(id)
      ]);
      return { profil, commandes };
    }

Ces deux fonctions sont des variantes : appelle celle qui correspond aux dépendances réelles, au lieu d’exécuter les deux exemples successivement. Promise.all rejette dès qu’un membre échoue, mais n’annule pas automatiquement les autres opérations. Si les résultats partiels sont utiles, examine Promise.allSettled. N’exécute pas en parallèle des opérations dépendantes ou susceptibles de saturer un service.

5. La boucle d’événements

console.log("A");
    setTimeout(() => console.log("timer"), 0);
    Promise.resolve().then(() => console.log("microtâche"));
    console.log("B");
    // A, B, microtâche, timer

Le code courant s’exécute jusqu’à la fin de la pile. Les callbacks de promesses sont planifiés comme microtâches, généralement traitées avant les tâches de minuterie suivantes. Un délai de zéro milliseconde ne signifie pas une exécution immédiate. Un calcul synchrone long bloque le thread principal et retarde les interactions, même si des opérations réseau sont asynchrones.

Erreurs fréquentes

  • Oublier return dans une chaîne de promesses et perdre la propagation.
  • Ne pas vérifier response.ok après fetch.
  • Mettre des await en série alors que les opérations sont indépendantes.
  • Lancer une promesse sans gérer son rejet.
  • Confondre asynchronisme et parallélisme : le code JavaScript ne s’exécute pas automatiquement sur plusieurs cœurs.

Exercice

Crée une closure qui limite le nombre d’appels à une fonction. Ensuite, écris une fonction qui charge deux ressources indépendantes en parallèle, vérifie les statuts HTTP et présente un message exploitable en cas d’échec.

Critères de réussite

  • L’état privé n’est pas exposé globalement.
  • Les erreurs sont propagées puis traitées au bon niveau.
  • Les appels indépendants sont concurrents, les dépendances restent séquentielles.
  • L’ordre des logs de l’exemple de boucle d’événements est expliqué.

Approfondissement — comprendre ce que conserve une closure et ce que promet une opération asynchrone

Une closure conserve l’accès à une liaison lexicale, pas nécessairement une photographie de sa valeur au moment où la fonction est créée. Cette différence explique certains bugs de callbacks : plusieurs fonctions peuvent observer la même variable modifiée ultérieurement.

const actions = [];
for (let i = 0; i < 3; i++) {
  actions.push(() => i);
}
console.log(actions.map(action => action())); // [0, 1, 2]

Avec let, chaque itération de cette boucle crée une liaison propre à l’itération. Avec un ancien var, les callbacks partageraient la même variable de fonction et liraient la valeur finale après la boucle. Lorsque tu écris un callback, demande-toi si tu veux lire une valeur future ou conserver une valeur déterminée ; copie-la explicitement si une photographie est nécessaire.

Pour les promesses, distingue aussi l’échec d’une requête réseau de la réponse HTTP d’erreur : fetch rejette en cas d’échec réseau ou d’interruption, mais une réponse 404 ou 500 reste une réponse à inspecter via response.ok. Une chaîne asynchrone doit décider à quel niveau l’erreur peut être traduite en message utilisateur, journalisée ou propagée à l’appelant.

Annuler une opération devenue inutile

async function chargerRecherche(terme, signal) {
  const url = `/api/recherche?q=${encodeURIComponent(terme)}`;
  const reponse = await fetch(url, { signal });
  if (!reponse.ok) throw new Error(`HTTP ${reponse.status}`);
  return reponse.json();
}

async function demonstrerAnnulation() {
  const controleur = new AbortController();
  const promesse = chargerRecherche("clavier", controleur.signal);
  // Une nouvelle saisie peut déclencher cette annulation.
  controleur.abort();
  try {
    await promesse;
  } catch (erreur) {
    if (erreur instanceof DOMException && erreur.name === "AbortError") {
      // Annulation attendue : ne pas l'afficher comme une panne serveur.
    } else {
      throw erreur;
    }
  }
}

L’annulation est utile pour les recherches à chaque frappe, les changements de page ou les composants démontés. Elle ne garantit pas qu’un serveur ayant déjà reçu la requête arrête le travail ; elle permet au client d’interrompre l’attente et le traitement associé. Une annulation attendue doit être distinguée d’une erreur inattendue.

Parallélisme logique et gestion des échecs

Promise.all permet d’attendre plusieurs résultats indépendants, mais la promesse agrégée est rejetée dès qu’un membre échoue. Cela n’annule pas automatiquement les autres opérations. Si chaque résultat doit être examiné même en cas d’échec partiel, Promise.allSettled fournit un statut pour chacune. Choisis selon le contrat fonctionnel : un écran peut accepter des widgets indépendants en échec partiel, alors qu’une validation de paiement doit souvent échouer comme un tout.

Exercice de vérification

Écris une recherche déclenchée par un champ texte. Chaque nouvelle saisie doit annuler la requête précédente, ignorer les erreurs d’annulation attendues et afficher les erreurs réseau ou HTTP utiles. Ajoute ensuite deux appels indépendants : montre le comportement de Promise.all lorsqu’un seul échoue, puis celui de Promise.allSettled.

Critères de réussite

  • Le comportement d’une closure est expliqué en termes de liaison et de portée.
  • Les statuts HTTP sont vérifiés explicitement après fetch.
  • L’annulation attendue n’est pas affichée comme une panne utilisateur.
  • Le choix entre Promise.all et Promise.allSettled est justifié.
  • Les erreurs inattendues ne sont ni avalées ni transformées en succès fictif.
