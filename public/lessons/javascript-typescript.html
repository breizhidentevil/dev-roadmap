1. Fondamentaux de la programmation et du Web

JavaScript puis TypeScript

Passer d’un JavaScript maîtrisé aux types statiques pour sécuriser les données et les contrats d’une application.

Tutoriel détailléLot 5 · 2026

Objectifs d’apprentissage

  • Expliquer la différence entre JavaScript, TypeScript et le contrôle à l’exécution.
  • Choisir entre types primitifs, unions, interfaces, alias et génériques.
  • Réduire les valeurs inconnues avec le narrowing plutôt que masquer les erreurs.
  • Définir une configuration TypeScript stricte et compiler un petit module.

1. JavaScript s’exécute, TypeScript vérifie

JavaScript est le langage exécuté par le navigateur ou Node.js. TypeScript ajoute une analyse statique : le compilateur détecte certaines incohérences avant l’exécution, puis le code est transformé en JavaScript. Les types TypeScript ne valident pas automatiquement les données reçues d’un serveur à l’exécution.

function prixTTC(prixHT: number, taux: number): number {
      return prixHT * (1 + taux);
    }
    const total = prixTTC(20, 0.2); // 24
    // prixTTC("20", 0.2); // erreur de compilation

Une annotation décrit le contrat attendu. Elle ne convertit pas la valeur : une chaîne contenant « 20 » ne devient pas un nombre parce qu’on lui attribue un type.

2. Les types courants

let nom: string = "Ada";
    let tentatives: number = 3;
    let actif: boolean = true;
    let identifiant: string | number = "u-42";
    
    type Utilisateur = {
      id: string;
      nom: string;
      email?: string;
      roles: ("lecteur" | "admin")[];
    };
    
    function saluer(personne: Utilisateur): string {
      return `Bonjour ${personne.nom}`;
    }

Utilise type pour nommer un type, notamment les unions et compositions ; interface convient aussi aux contrats d’objets et peut être étendue. Le choix importe moins que la cohérence de l’équipe. Le suffixe ? signifie qu’une propriété peut être absente : le code doit donc traiter ce cas.

3. Unions et narrowing

function afficherId(id: string | number): string {
      if (typeof id === "number") {
        return id.toFixed(0);
      }
      return id.toUpperCase();
    }

Le narrowing réduit les possibilités à partir d’un test fiable : typeof, vérification de propriété, comparaison d’un discriminant ou fonction de garde. Préfère cette approche à as string, qui demande au compilateur de faire confiance au développeur sans vérifier la réalité de la donnée.

type Resultat =
      | { ok: true; valeur: string }
      | { ok: false; erreur: string };
    
    function presenter(r: Resultat) {
      return r.ok ? r.valeur : r.erreur;
    }

4. Données externes et configuration

Une réponse HTTP, un fichier JSON ou une valeur de stockage local doit être considérée comme non fiable. Le type statique ne remplace pas une validation d’exécution. Commence par unknown, vérifie la structure, puis transforme la valeur en objet métier valide.

function estUtilisateur(v: unknown): v is Utilisateur {
  if (typeof v !== "object" || v === null || Array.isArray(v)) return false;
  const x = v as Record<string, unknown>;
  const rolesValides = Array.isArray(x.roles)
    && x.roles.every(
      (role: unknown) => role === "lecteur" || role === "admin"
    );

  return typeof x.id === "string"
    && typeof x.nom === "string"
    && (x.email === undefined || typeof x.email === "string")
    && rolesValides;
}

Dans un projet, active notamment strict: true dans tsconfig.json. Corrige les erreurs à la source et évite de multiplier any, les assertions forcées et les non-null assertions (!).

5. Erreurs fréquentes et compromis

  • Tout annoter : les types sont souvent inférés ; ajoute-les surtout aux frontières et aux contrats publics.
  • Employer any partout : cela désactive une partie des protections ; préfère unknown et une validation.
  • Confondre compilation et validation : les données d’API peuvent être invalides malgré un type déclaré.
  • Sur-modéliser : un type complexe n’est utile que s’il clarifie les invariants réels.
  • Ignorer la configuration : une compilation non stricte peut laisser passer des valeurs nulles dangereuses.

Exercice guidé

Crée un type Produit avec un identifiant, un nom, un prix et une disponibilité. Écris une fonction qui calcule le prix après remise, en refusant une remise hors de l’intervalle 0–1. Ajoute une union pour représenter un succès ou une erreur et traite chaque branche.

Exercice autonome

Écris une fonction qui reçoit unknown et vérifie qu’il s’agit d’une liste de produits valides. Ne considère aucun champ externe comme fiable avant contrôle.

Critères de réussite

  • Le projet compile en mode strict sans recourir à any pour contourner les erreurs.
  • Les fonctions ont des entrées et sorties cohérentes.
  • Les unions sont réduites avant d’utiliser leurs valeurs.
  • Les données externes sont validées à l’exécution.
  • Les cas limites (valeur absente, type incorrect, remise invalide) sont testés.

Approfondissement — faire coïncider le type annoncé et les données réelles

Une fonction de garde de type (type guard) n’est pas seulement un test pratique : lorsqu’elle retourne true, TypeScript fait confiance à son affirmation. Si elle vérifie uniquement qu’une propriété est un tableau sans contrôler ses éléments, elle peut certifier à tort un objet qui ne respecte pas le type déclaré. Une garde doit donc vérifier chaque invariant nécessaire au code qui consommera la valeur.

const casDeTest: Array<{
  nom: string;
  valeur: unknown;
  attendu: boolean;
}> = [
  { nom: "valide", valeur: { id: "u-1", nom: "Ada", roles: ["admin"] }, attendu: true },
  { nom: "rôle inconnu", valeur: { id: "u-2", nom: "Lin", roles: ["owner"] }, attendu: false },
  { nom: "email numérique", valeur: { id: "u-3", nom: "Sam", email: 42, roles: [] }, attendu: false },
  { nom: "rôle non textuel", valeur: { id: "u-4", nom: "Jo", roles: ["admin", 7] }, attendu: false },
  { nom: "identifiant absent", valeur: { nom: "Noa", roles: ["lecteur"] }, attendu: false },
];

for (const cas of casDeTest) {
  if (estUtilisateur(cas.valeur) !== cas.attendu) {
    throw new Error(`Échec du cas : ${cas.nom}`);
  }
}

JSON.parse ne valide pas le schéma métier : il transforme du texte JSON valide en valeur JavaScript, qui peut être un objet incomplet ou contenir des champs inattendus. La garde de la section précédente vérifie l’identifiant, le nom, l’email optionnel et chaque rôle avant de certifier le type. Pour un modèle plus complexe, une bibliothèque de validation peut réduire le code répétitif, mais ses règles doivent elles aussi être testées. Les cas ci-dessus rendent visibles les entrées qui doivent être acceptées ou refusées.

Il faut également distinguer trois opérations : décrire une valeur avec un type, vérifier statiquement le code et valider une donnée à l’exécution. Une assertion comme valeur as Utilisateur ne réalise que la première opération du point de vue du compilateur ; elle ne transforme ni ne contrôle la valeur.

Procédure de contrôle

  1. Active strict: true dans tsconfig.json.
  2. Traite toute donnée externe comme unknown à la frontière du système.
  3. Valide les propriétés utilisées ensuite, y compris les éléments des tableaux et les valeurs d’union.
  4. Convertis la donnée validée vers un modèle interne si le format externe est différent.
  5. Teste les entrées valides, les propriétés absentes, les types incorrects et les valeurs d’énumération inconnues.

Exercice de vérification

Ajoute une propriété actif: boolean au type, puis écris des tests pour un utilisateur valide, un rôle inconnu, un email numérique, un tableau de rôles contenant un nombre et une propriété obligatoire absente. La garde doit refuser chacun des cas invalides.

Critères de réussite

  • Aucune assertion de type ne remplace la validation des données externes.
  • La garde vérifie les types des éléments internes aux tableaux.
  • Les tests couvrent au moins un cas valide et quatre cas invalides.
  • Les erreurs TypeScript sont corrigées plutôt que masquées par any.
