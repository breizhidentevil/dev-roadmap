6. Tests, débogage et qualité

Lire le code d’autres développeurs

Explorer un dépôt inconnu en remontant des points d’entrée vers les règles métier, les dépendances et les tests.

Tutoriel approfondiCompétence Full Stack

Objectifs et prérequis

Lire du code existant est différent d’écrire du code neuf. Dans un projet réel, le comportement est réparti entre routes, composants, services, modèles, configuration, tests et bibliothèques. L’objectif n’est pas de comprendre tout le dépôt immédiatement, mais de reconstruire une explication fiable du parcours qui mène d’une entrée à un résultat.

  • Repérer les points d’entrée et les commandes de lancement.
  • Suivre une fonctionnalité à travers plusieurs modules.
  • Utiliser les tests et l’historique Git pour confirmer les hypothèses.
  • Documenter les responsabilités et les questions encore ouvertes.

Prérequis : lire le langage principal du projet et comprendre fonctions, imports, HTTP et tests.

1. Commencer par le contexte

Lis d’abord le README, les scripts du gestionnaire de paquets, les fichiers de configuration et l’arborescence. Ces éléments indiquent comment installer, lancer, tester et construire le projet. Vérifie la version du runtime : une documentation récente peut ne pas correspondre à la version utilisée.

pwd
git status --short
git log -5 --oneline
find . -maxdepth 2 -type f | sort | head -100
cat package.json

Adapte les commandes au dépôt et n’affiche pas de fichiers contenant des secrets. Le statut Git révèle aussi les changements locaux à préserver. Identifie les commandes de test, build, lint et développement. Si les tests ne démarrent pas, note ce blocage au lieu de conclure que le code est cassé.

2. Suivre une fonctionnalité de bout en bout

Choisis une fonctionnalité observable et trace son parcours. Une page de liste peut suivre ce chemin : route frontend → composant → appel HTTP → route backend → validation → service métier → requête SQL → réponse JSON → affichage. C’est une hypothèse de départ, pas une architecture universelle.

  1. Repère l’URL, le libellé d’interface ou le message d’erreur.
  2. Recherche ce texte, le nom de la route ou un champ de données.
  3. Examine le point d’entrée et les appels qu’il effectue.
  4. Continue jusqu’à la source de données ou l’effet final.
  5. Remonte le chemin pour comprendre comment le résultat est transformé.

La recherche globale de l’éditeur est souvent plus efficace qu’une lecture séquentielle. Les noms de fonctions, types et événements sont de bons indices. Vérifie où les permissions sont réellement contrôlées : un nom comme getOrder ne garantit aucune autorisation.

async function getOrderPage(id: string) {
  const response = await fetch(`/api/orders/${id}`);
  if (!response.ok) throw new Error(`HTTP ${response.status}`);
  return response.json();
}

Cet extrait montre seulement le client. Pour comprendre le comportement complet, trouve la route serveur, la validation, le service appelé et les tests correspondants.

3. Tests, historique et preuves

Les tests décrivent des comportements attendus, des entrées limites et parfois des décisions métier. Lis le scénario, sa préparation, l’action et les assertions. Un test peut toutefois être incomplet ou préserver un comportement historique incorrect : il constitue une preuve utile, pas une vérité absolue.

git log --oneline -- chemin/vers/fichier
git blame chemin/vers/fichier
git show <identifiant-du-commit>

git blame montre qui a modifié une ligne en dernier, pas qui est responsable d’une décision. Utilise-le pour retrouver le commit et son contexte. Les messages de commit et les revues peuvent expliquer pourquoi une abstraction existe ou quel bug elle prévient.

Distingue le fait observé de l’hypothèse. « La route appelle orderService.findById » est vérifiable ; « le service garantit que la commande appartient à l’utilisateur » doit être confirmé dans le code ou les tests.

4. Construire une carte utile

Note le point d’entrée, les modules importants, les flux de données, les dépendances externes et les tests pertinents. Un schéma de cinq à dix boîtes consacré à une fonctionnalité est souvent plus utile qu’une architecture exhaustive et vite périmée. Mets à jour tes notes lorsque tu confirmes ou réfutes une hypothèse.

La profondeur dépend du risque : une correction de texte demande peu d’exploration ; une modification d’autorisations, de paiements ou de transactions exige d’examiner les échecs, les effets secondaires et les dépendances indirectes.

5. Valider la compréhension avant de proposer une modification

Avant d’éditer, écris une courte description du comportement actuel et cite les preuves : fichier et fonction, test exécuté, requête observée ou commit explicatif. Pour une modification risquée, recherche aussi les appelants, les consommateurs externes, les migrations et les tâches asynchrones. La recherche d’un nom ne suffit pas toujours : un comportement peut être déclenché par une configuration, un décorateur, un middleware ou une inscription d’événement.

AffirmationPreuve attendue
« Cette route exige une authentification »Middleware effectif, test non authentifié et configuration de montage de la route
« Cette fonction est sans effet secondaire »Inspection des appels indirects et des accès aux systèmes externes
« Ce champ peut être supprimé »Recherche des usages, contrats API, données persistées et consommateurs
« Le test couvre cette règle »Assertion qui échouerait si la règle était retirée, idéalement vérifiée par une mutation simple

Lors d’une revue, formule les commentaires en termes de risque observable et de question précise. Distingue un défaut bloquant, une suggestion de lisibilité et une préférence personnelle. Si le contexte manque, demande la raison de la règle plutôt que de supposer qu’elle est inutile.

Pièges et compromis

  • Lire les fichiers dans l’ordre alphabétique : pars d’une fonctionnalité observable.
  • Déduire à partir des noms : vérifie les appels, les types et les tests.
  • Tout lire avant d’agir : fixe une question précise puis élargis l’enquête.
  • Faire confiance aux commentaires seuls : le code et les tests peuvent révéler une documentation obsolète.
  • Modifier trop tôt : reproduis le comportement et localise les tests avant la correction.

Un code étrange peut protéger un invariant peu visible ou être un ancien contournement. Cherche le contexte avant de supprimer une complexité apparente.

Exercice guidé

Dans un dépôt d’exercice, trouve le parcours d’une page de détails : composant ou route d’entrée, appel réseau, traitement backend, source de données et un test lié. Écris le chemin en cinq à huit étapes et note deux hypothèses à confirmer.

Exercice autonome et critères de réussite

Cartographie la création d’une commande : validations, permissions, écritures en base, erreurs et réponse renvoyée. Vérifie une partie de ton schéma en exécutant un test ou en utilisant le débogueur.

  • Le point d’entrée et la commande de test sont identifiés.
  • Le flux de données peut être expliqué dans les deux sens.
  • Les validations et autorisations sont localisées sans supposition fondée sur le nom.
  • Un test pertinent est relié au comportement observé.
  • Faits, hypothèses et questions ouvertes sont séparés.
