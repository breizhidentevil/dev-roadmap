6. Tests, débogage et qualité

Linting et formatage du code

Automatiser les vérifications de style et les règles statiques pour réduire les erreurs évitables et faciliter les revues.

Tutoriel approfondiQualité et tests

Objectifs et prérequis

Le formatage impose une présentation cohérente du code ; le linting détecte des motifs suspects ou des règles de qualité ; le compilateur TypeScript vérifie un ensemble de contraintes de types. Ces outils se complètent, mais aucun ne prouve à lui seul que le programme est correct.

  • Configurer des règles partagées et compréhensibles.
  • Différencier formatage, lint, vérification de types et tests.
  • Automatiser les contrôles localement et dans l’intégration continue.

1. Quatre contrôles différents

  • Formatage : espaces, retours à la ligne, guillemets et mise en forme uniforme. Prettier est conçu pour limiter les débats de style.
  • Linting : détecte des constructions risquées, des variables inutilisées, des dépendances incorrectes dans certains hooks ou des règles propres au projet.
  • Vérification de types : TypeScript contrôle la cohérence statique des types, selon la configuration et les déclarations disponibles.
  • Tests : vérifient le comportement observable à l’exécution.

Un projet peut donc être bien formaté et échouer au lint, compiler sans erreur de type et pourtant contenir un bug métier. La chaîne de qualité doit exécuter chaque contrôle utile sans présenter l’un comme un substitut des autres.

2. Installer et définir des commandes reproductibles

Installe les outils dans le projet et verrouille leurs versions dans le gestionnaire de paquets. Cela évite qu’un développeur et la CI appliquent des règles différentes. Exemple de scripts dans package.json :

{
  "scripts": {
    "format": "prettier --write .",
    "format:check": "prettier --check .",
    "lint": "eslint .",
    "typecheck": "tsc --noEmit",
    "test": "vitest run",
    "check": "npm run format:check && npm run lint && npm run typecheck && npm test"
  }
}

Les commandes exactes dépendent de la structure et des outils du dépôt. Il peut être nécessaire d’exclure les fichiers générés, les répertoires de build et certains fichiers de configuration. N’exclus pas un dossier simplement parce que les contrôles y trouvent des problèmes sans comprendre la raison.

3. Configurer sans multiplier les règles contradictoires

Choisis un formateur principal et un ensemble limité de règles de lint. Les règles de formatage détaillées sont rarement utiles dans ESLint lorsque Prettier s’en charge déjà. Une configuration trop stricte, mal expliquée ou pleine d’exceptions sera contournée plutôt qu’adoptée.

Dans un projet TypeScript, active une configuration adaptée au langage et aux fichiers réellement analysés. Les règles qui nécessitent des informations de type peuvent être plus coûteuses ; réserve-les aux zones où elles apportent une vraie valeur et mesure le temps d’exécution.

Ajoute un fichier EditorConfig pour harmoniser des paramètres simples comme la fin de ligne et l’indentation, si l’équipe utilise des éditeurs différents. Documente les commandes dans le README pour qu’un nouveau contributeur puisse lancer les contrôles sans deviner.

4. Exécuter les contrôles au bon moment

Un flux courant consiste à lancer le formatage à la demande ou à la sauvegarde, puis lint, vérification de types et tests avant la fusion. Un hook Git peut empêcher certains commits mal formatés, mais il ne remplace pas la CI : il peut être contourné et ne garantit pas que le contrôle sera exécuté sur la bonne version du code.

La CI doit reproduire les mêmes commandes avec un environnement verrouillé. Pour un grand monorepo, il est possible de limiter certains contrôles aux fichiers modifiés, mais la vérification finale doit aussi couvrir les interactions entre modules et les configurations globales pertinentes.

5. Gérer les exceptions et la dette

Une désactivation locale de règle peut être légitime si elle est étroite, justifiée et temporaire. Préfère une désactivation sur une ligne à une désactivation globale du fichier ou du projet. Un commentaire peut expliquer pourquoi le code ne peut pas suivre la règle sans perdre une propriété nécessaire.

Lorsqu’un ancien projet adopte le linting, évite de corriger automatiquement des milliers de fichiers sans isoler le changement de comportement. Procède par étapes : établir une base, corriger les règles critiques, automatiser les fichiers modifiés, puis réduire progressivement la dette. Les modifications purement formatées sont plus faciles à relire si elles restent séparées des changements métier.

6. Rendre la qualité reproductible en local et en CI

Les mêmes commandes doivent produire les mêmes résultats sur le poste d’un développeur et dans l’intégration continue. Verrouille les versions dans le fichier de lock, documente le runtime et privilégie les scripts du dépôt plutôt que des commandes globales dont la version peut varier.

{
  "scripts": {
    "lint": "eslint .",
    "format:check": "prettier --check .",
    "format": "prettier --write .",
    "typecheck": "tsc --noEmit",
    "check": "npm run lint && npm run format:check && npm run typecheck"
  }
}

Exemple indicatif à adapter aux outils réellement installés : un projet JavaScript sans TypeScript n’a pas besoin du script typecheck. Dans la CI, exécute le contrôle en lecture seule et fais échouer le pipeline si le dépôt n’est pas conforme ; ne lance pas automatiquement le formatage pour masquer une différence. Un hook pré-commit accélère le retour, mais ne remplace jamais la CI, car il peut être contourné.

Lors de l’introduction d’une règle sur un dépôt ancien, sépare le code modifié du stock historique : fixe une ligne de base, corrige progressivement les fichiers touchés et évite de mêler des milliers de changements de formatage à une modification fonctionnelle.

Erreurs fréquentes

  • Confondre formatage, linting, types et tests.
  • Installer des versions flottantes ou laisser la CI utiliser une configuration différente.
  • Faire exécuter simultanément à ESLint et Prettier des règles contradictoires.
  • Désactiver une règle globalement pour contourner quelques cas difficiles.
  • Ne pas exclure les fichiers générés, ou exclure des dossiers entiers sans justification.
  • Compter uniquement sur les hooks locaux au lieu de contrôler le résultat dans la CI.

Exercice guidé

Sur un petit projet TypeScript, ajoute les scripts format:check, lint, typecheck et test. Introduis volontairement une variable inutilisée, une erreur de type et un formatage incorrect, puis observe quel contrôle détecte chaque problème.

Configure ensuite la CI pour exécuter les mêmes commandes. Vérifie que l’échec d’un contrôle empêche la validation du pipeline et que les consignes sont documentées pour un nouveau contributeur.

Exercice autonome et critères de réussite

Propose une configuration minimale pour un dépôt React et TypeScript, avec exclusions explicites, scripts et étape CI. Explique pourquoi chaque contrôle est présent et quelles limites il conserve.

Réussite : les commandes fonctionnent sur une installation propre ; les versions sont reproductibles ; formatage, lint, types et tests sont distingués ; les fichiers générés sont gérés explicitement ; la CI exécute les contrôles ; les exceptions locales restent rares et justifiées.
