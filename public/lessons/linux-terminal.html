7. Environnement, livraison et exploitation

Linux et ligne de commande

Naviguer dans Linux, inspecter les fichiers et processus, puis diagnostiquer un environnement de développement depuis le terminal.

Tutoriel approfondiCompétence Full Stack

Objectifs et prérequis

Le terminal est une interface textuelle ; le shell, souvent Bash, interprète les commandes et transmet leurs arguments aux programmes. ls est généralement un programme externe, tandis que cd est une commande intégrée : elle doit modifier le répertoire courant du shell lui-même.

  • Comprendre les chemins absolus et relatifs.
  • Créer, lire, déplacer et rechercher des fichiers.
  • Utiliser les redirections et pipelines.
  • Inspecter les processus et les permissions.
  • Consulter l’aide et éviter les opérations destructrices.

1. Chemins et fichiers

Un chemin absolu part de /. Un chemin relatif est interprété depuis le répertoire courant, affiché par pwd. . désigne le répertoire courant, .. son parent et ~ le dossier personnel.

pwd
ls -la
cd ~/projets/mon-app
mkdir -p exercices/terminal
touch exercices/terminal/notes.txt
cp exercices/terminal/notes.txt /tmp/notes-copie.txt
mv /tmp/notes-copie.txt /tmp/notes.txt

ls -la affiche aussi les fichiers cachés comme .git. Avant de supprimer ou déplacer des fichiers, vérifie le répertoire courant et la cible. Les noms contenant des espaces doivent être placés entre guillemets, par exemple "mon dossier".

2. Lire et rechercher

less permet de parcourir un fichier, head et tail affichent ses extrémités, grep recherche un motif et find recherche des fichiers selon des critères.

less README.md
grep -RIn "TODO" src/
find . -type f -name "*.ts"
tail -n 100 logs/app.log
tail -f logs/app.log

tail -f suit les nouvelles lignes ; arrête-le avec Ctrl+C. Les recherches récursives peuvent traverser de grands dossiers : exclue les dépendances et les fichiers de build lorsque nécessaire. Pour une commande inconnue, lis son aide avant de copier des options trouvées ailleurs.

3. Redirections et pipelines

Les processus utilisent notamment une entrée standard (0), une sortie standard (1) et une sortie d’erreur (2). | transmet la sortie d’une commande à l’entrée de la suivante. > remplace un fichier, >> ajoute à la fin et 2> redirige les erreurs.

find src -type f -name "*.ts" | wc -l
npm run build > build.log 2>&1
tail -n 200 build.log | grep -i "error"
echo $?

La dernière commande affiche le code de sortie de la commande précédente : zéro indique généralement le succès, une valeur non nulle un échec. L’ordre des redirections compte, car 2>&1 dirige les erreurs vers la destination actuelle de la sortie standard. Évite d’écraser par accident un fichier utilisé en entrée.

4. Processus et permissions

Un processus est une instance d’un programme en cours d’exécution. ps, pgrep et top aident à l’inspecter. kill envoie un signal à un PID ; commence par identifier précisément le processus.

ps aux | grep node
pgrep -af node
kill -TERM 12345

Le PID est ici un exemple, à remplacer par celui réellement trouvé. TERM demande un arrêt propre ; KILL force l’arrêt sans laisser le programme nettoyer ses ressources et doit rester un dernier recours.

Les permissions distinguent propriétaire, groupe et autres. chmod les modifie et chown change le propriétaire. Évite d’utiliser sudo pour masquer un problème de droits : cela peut créer des fichiers appartenant à root dans ton projet.

5. Sécurité et dépannage

Consulte man nom ou commande --help. Les commandes de suppression, les jokers et les privilèges administrateur exigent une attention particulière. Pour une opération risquée, liste d’abord les cibles et essaie sur un petit échantillon. Ne lance pas aveuglément une chaîne qui télécharge puis exécute un script distant.

  • Chemin incorrect : vérifie pwd et le type de chemin.
  • Permission refusée : inspecte propriétaire et permissions avant sudo.
  • Sortie écrasée : rappelle-toi que > remplace le contenu.
  • Commande apparemment bloquée : vérifie si elle attend une entrée ou suit un flux continu.

Les scripts accélèrent les tâches répétitives, mais amplifient aussi les erreurs. Utilise des chemins explicites et des vérifications lorsque tu automatises.

Diagnostic reproductible : partir du symptôme

Une bonne investigation réduit l’incertitude étape par étape. Avant de modifier quoi que ce soit, note le répertoire courant, la commande exacte, le code de sortie et les premières lignes d’erreur. Reproduis ensuite le problème avec le plus petit nombre de commandes possible.

pwd
command -v node
node --version
printf 'code précédent = %s\n' "$?"
ls -ld ./node_modules
id
printf 'PATH=%s\n' "$PATH"

Exécute printf immédiatement après la commande à diagnostiquer : sinon, son propre code de sortie remplace celui de la commande testée. command -v révèle quel exécutable sera lancé ; c’est utile lorsque plusieurs versions de Node sont installées. Évite de publier la sortie complète d’un environnement sans l’examiner, car elle peut contenir des chemins personnels ou des informations sensibles.

Pour un processus qui écoute sur un port, identifie d’abord le port et le processus avec les outils disponibles sur ta distribution, puis vérifie son journal et sa configuration. Ne tue pas un processus avant d’avoir confirmé son identité et son rôle.

Exercice guidé

Crée un dossier atelier-linux avec deux sous-dossiers et trois fichiers texte. Recherche le mot « erreur », redirige les résultats dans un rapport et affiche ses cinq premières lignes. Vérifie le code de sortie de la recherche.

Exercice autonome et critères de réussite

Dans un projet de test, produis un rapport listant les fichiers TypeScript et les lignes de journal contenant « error », sans modifier les sources.

  • Les chemins et cibles sont compris.
  • Le pipeline ne modifie pas les sources.
  • Les sorties standard et d’erreur sont traitées consciemment.
  • Le code de sortie est interprété correctement.
  • Les privilèges élevés ne sont pas utilisés par réflexe.
