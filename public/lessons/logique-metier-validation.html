3. Backend

Logique métier et validation des données

Séparer la validation de forme, les règles métier et les invariants persistants afin que les données restent valides même en présence de requêtes concurrentes.

Tutoriel détailléLot 10 · 2026

Objectifs d’apprentissage

  • Distinguer validation de format et règle métier.
  • Valider les données à la frontière du système.
  • Préserver les invariants pendant les modifications.
  • Tester les cas limites et les tentatives de contournement.

Fil conducteur

Valider tôt améliore le message d’erreur ; garantir un invariant au niveau métier et de la base protège le système. Ces protections sont complémentaires, pas interchangeables.

1. Trois niveaux de validation

La validation syntaxique vérifie la forme d’une entrée : type, longueur, format ou structure. La validation sémantique vérifie que la valeur a un sens dans le contexte, par exemple une date de fin postérieure à une date de début. La règle métier détermine si l’opération est permise : un stock doit être suffisant, un compte doit être actif ou une commande doit être dans un état compatible.

Ces niveaux peuvent être implémentés à des endroits différents, mais ils doivent former un parcours cohérent. Une chaîne bien formée n’est pas nécessairement autorisée, et une interface qui empêche une action ne suffit pas à protéger le serveur.

2. Valider à la frontière

Les données venant d’une requête HTTP, d’un fichier ou d’un service externe doivent être considérées comme non fiables. Valide leur structure au point d’entrée et convertis-les vers un type interne clair. Rejette les valeurs impossibles avec un message exploitable, sans renvoyer de détails internes.

type CreateAccountInput = {
      email: string;
      displayName: string;
    };
    
    function validateInput(value: unknown): CreateAccountInput {
      // Vérifier le type, les champs requis,
      // les limites et le format avant conversion.
      throw new Error("À implémenter");
    }

Cette fonction est un squelette pédagogique, pas un validateur prêt à l’emploi. Utilise une bibliothèque adaptée ou des contrôles explicites et teste les entrées absentes, mal typées, excessivement longues et inattendues.

3. Les invariants doivent tenir dans le temps

Un invariant est une condition qui doit rester vraie pour les états valides du domaine : une quantité non négative, un identifiant unique ou une transition autorisée entre statuts. La validation ne doit pas être un contrôle isolé que certaines routes peuvent oublier.

Place les règles près de la logique qui les possède et renforce-les avec les garanties de la base de données lorsque c’est possible : contraintes, clés étrangères, unicité et transactions. Les contrôles applicatifs donnent des messages utiles ; les contraintes de stockage protègent aussi contre les accès concurrents et les chemins d’écriture oubliés.

4. Concurrence et opérations métier

Un contrôle peut devenir faux entre la lecture et l’écriture. Par exemple, deux requêtes peuvent lire un stock de 1 et chacune tenter d’acheter la dernière unité. Une vérification préalable seule ne garantit pas l’absence de survente.

Utilise une transaction, une mise à jour conditionnelle, une contrainte ou un verrou adapté au niveau de cohérence requis. Définis aussi comment traiter un conflit : nouvelle tentative contrôlée, réponse de conflit ou demande de confirmation. La stratégie dépend de l’opération et de la base de données.

5. Erreurs et tests métier

Les erreurs de validation doivent être distinguées des erreurs inattendues. Une entrée invalide peut produire une réponse client de type 400 ou 422 selon le contrat ; une absence d’authentification ou de permission relève d’une autre catégorie. Documente la structure d’erreur pour que les clients puissent l’exploiter sans analyser du texte libre.

Teste les limites et les transitions, pas uniquement les exemples habituels : valeur minimale, maximale, champ manquant, doublon, état interdit, accès concurrent et répétition de requête. Les tests métier doivent être indépendants de l’interface afin que toutes les voies d’entrée respectent les mêmes règles.

Exercice guidé

Implémente le cas métier « réserver une place » avec validation des entrées, contrôle des permissions et disponibilité limitée. Écris des tests pour une quantité invalide, une ressource absente, une réservation répétée et deux demandes concurrentes.

Critères de réussite

  • Les données sont validées à l’entrée du système.
  • Les règles métier sont centralisées et testables.
  • Les invariants sont protégés même en cas de concurrence.
  • Les erreurs ont des catégories et réponses cohérentes.
  • Les tests couvrent cas limites et répétitions.

Erreurs fréquentes

  • Considérer une validation frontend comme une protection suffisante.
  • Confondre format valide et opération autorisée.
  • Mettre les règles métier uniquement dans le contrôleur HTTP.
  • Oublier les contraintes de base de données et les courses concurrentes.
  • Retourner des erreurs internes détaillées au client.
