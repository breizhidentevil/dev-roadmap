6. Tests, débogage et qualité

Gestion des erreurs et logs structurés

Concevoir des erreurs exploitables pour le diagnostic sans exposer les détails internes ni les données sensibles.

Tutoriel approfondiQualité et tests

Objectifs et prérequis

Une erreur doit être compréhensible par le client quand une action est attendue de lui, et suffisamment détaillée dans les systèmes internes pour aider au diagnostic. Ces deux besoins ne doivent pas être confondus : une réponse publique ne doit pas révéler une pile d’appels, un nom de table ou une clé de configuration.

  • Définir une forme d’erreur stable pour une API.
  • Distinguer erreur attendue, erreur inattendue et événement à journaliser.
  • Relier les événements avec un identifiant de requête tout en protégeant les secrets.

1. Classer les erreurs

Une erreur de validation (par exemple un champ requis manquant) fait partie des situations attendues et peut être traduite en réponse client précise. Une ressource absente peut devenir un 404. Une absence d’authentification relève généralement de 401, tandis qu’un utilisateur authentifié mais non autorisé relève généralement de 403. Une panne imprévue de base de données doit produire une réponse générique de serveur et un événement interne exploitable.

La classification doit être explicite dans l’application. Évite de déduire le statut HTTP à partir d’un texte libre ou de renvoyer 200 avec un objet contenant error : cela complique les clients, les métriques et les alertes. Consulte aussi la compétence sur les codes HTTP pour les distinctions précises.

2. Définir un contrat d’erreur

Un contrat stable aide les clients à traiter les erreurs sans analyser un message destiné aux humains. RFC 9457 définit un format courant appelé Problem Details :

{
  "type": "https://api.example.test/problems/validation",
  "title": "Les données sont invalides",
  "status": 400,
  "detail": "Un ou plusieurs champs doivent être corrigés.",
  "instance": "/api/tasks",
  "code": "VALIDATION_FAILED",
  "requestId": "req_7f3a"
}

Le domaine et l’identifiant sont illustratifs. N’inclus pas de trace technique, de requête SQL, de token ni de contenu personnel dans detail. Pour les erreurs de validation, ajoute éventuellement une liste de champs en erreur, sans renvoyer des données soumises qui pourraient contenir des secrets. Garde les codes machine stables même si les messages sont traduits.

3. Traiter les exceptions au bon endroit

Une couche proche de la règle métier peut lever une erreur typée ou retourner un résultat explicite. Une frontière HTTP traduit ensuite les erreurs connues en statuts et formats adaptés. Un gestionnaire centralisé évite de répéter le même traitement dans chaque endpoint.

try {
  const task = await taskService.create(input);
  return response.status(201).json(task);
} catch (error) {
  if (error instanceof TaskValidationError) {
    return response.status(400).json({
      code: "INVALID_TASK",
      requestId
    });
  }

  logger.error({
    event: "task_creation_failed",
    requestId,
    errorType: error instanceof Error ? error.name : "UnknownError"
  });

  return response.status(500).json({
    code: "INTERNAL_ERROR",
    requestId
  });
}

Exemple de principe à adapter au framework. Le logger doit être structuré et le détail de l’exception, s’il est journalisé, doit être filtré et réservé aux personnes autorisées. Ne laisse pas une exception inconnue être transformée en message détaillé transmis au client.

4. Journaliser pour enquêter

Un log structuré contient typiquement un horodatage, un niveau, un nom d’événement stable, un identifiant de corrélation et quelques attributs techniques utiles. Par exemple, payment_authorization_failed est plus facile à agréger qu’une phrase différente à chaque exécution.

Utilise les niveaux selon leur finalité : debug pour les investigations ciblées, info pour les événements opérationnels utiles, warn pour une situation anormale mais récupérable, error pour un échec nécessitant une analyse. La convention doit être cohérente et ne pas faire dépendre les alertes d’une simple préférence de vocabulaire.

Ne journalise pas les mots de passe, cookies, jetons d’accès, clés d’API, données bancaires ni les corps de requête complets par défaut. Contrôle également les valeurs utilisateur susceptibles d’injecter des retours à la ligne ou de fausser la lecture des logs.

5. Corrélation, alertes et bruit

Un identifiant de requête permet de relier la réponse HTTP, les logs applicatifs et les appels internes associés. Il doit être généré ou validé par le serveur selon une règle claire ; ne traite pas un identifiant fourni par le client comme une preuve d’identité.

Une alerte doit correspondre à un signal exploitable : taux d’erreurs qui augmente, échecs répétés d’une dépendance ou saturation. Alerter sur chaque erreur individuelle peut provoquer une fatigue d’alerte et masquer les incidents importants. Ajoute du contexte agrégé, des seuils et une procédure de diagnostic. Définis aussi les droits d’accès et la durée de conservation des journaux.

6. Concevoir des événements exploitables et sûrs

Un événement de log doit répondre à une question opérationnelle : quel composant a échoué, pendant quelle opération, avec quel résultat et quelle possibilité de reprise ? Préfère un schéma stable à des phrases libres. Les champs utiles comprennent un horodatage UTC, un niveau, un nom d’événement, un service, un identifiant de corrélation et un code d’erreur contrôlé. N’inclus pas de mot de passe, jeton, cookie, contenu de formulaire ou corps complet d’une requête par défaut.

logger.warn({
  event: "payment_authorization_failed",
  requestId,
  orderId,
  errorCode: "PROVIDER_TIMEOUT",
  retryable: true
}, "Payment authorization failed");

Ce modèle n’est sûr que si les identifiants sont autorisés dans le système de logs et ne révèlent pas de données personnelles. L’exception technique complète peut être réservée à une destination protégée ; l’API publique reçoit un message stable et non sensible. Pour éviter une tempête de logs, regroupe les erreurs répétées, ajoute des limites d’échantillonnage et alerte sur un taux ou une tendance plutôt que sur chaque occurrence.

Contrôles de revue

  • Le niveau correspond-il à l’action attendue (debug, info, warn, error) ?
  • Le message permet-il de distinguer panne, rejet métier et annulation normale ?
  • Un identifiant de corrélation permet-il de suivre la requête sans recopier des secrets ?
  • La rétention, les droits d’accès et la politique de suppression sont-ils définis ?
  • Une alerte est-elle liée à un impact observable et à une action de diagnostic ?

Erreurs fréquentes

  • Renvoyer au client la stack trace ou le message brut d’une exception.
  • Utiliser le texte du message comme code d’erreur contractuel.
  • Enregistrer des tokens, cookies ou corps de requêtes complets.
  • Journaliser toutes les erreurs au niveau error, sans distinction.
  • Créer des alertes sur chaque événement sans agrégation ni seuil.
  • Perdre l’identifiant de corrélation entre middleware, service et tâche asynchrone.

Exercice guidé

Sur une API de tâches, définis les réponses pour trois situations : titre invalide, tâche inexistante et exception inattendue. Crée un format public stable, puis un événement de log distinct pour l’échec inattendu avec un identifiant de requête.

Vérifie que la réponse publique ne contient ni pile d’appels ni détails internes. Vérifie aussi que les logs n’incluent aucun en-tête Authorization ou corps complet de la requête.

Exercice autonome et critères de réussite

Écris une courte convention d’erreurs pour ton backend : catégories, statuts, codes machine, champs publics, champs de logs, niveaux et politique de corrélation.

Réussite : les clients reçoivent un contrat stable ; les erreurs connues sont traduites explicitement ; les exceptions inattendues restent génériques côté client ; les logs structurés permettent l’enquête ; les secrets sont exclus ; les alertes sont exploitables et la rétention est définie.
