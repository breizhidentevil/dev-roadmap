Migrations pendant la livraison

Orchestrer les changements applicatifs et de données de façon sûre.

Leçon approfondieThéorie · pratique · validation

Objectifs d’apprentissage

À la fin de cette leçon, tu dois pouvoir expliquer les concepts avec tes propres mots, choisir une approche adaptée à un contexte réel et justifier tes décisions en fonction des contraintes et des risques.

  • Comprendre les notions essentielles et le problème qu’elles permettent de résoudre.
  • Appliquer une méthode concrète et vérifier son résultat.
  • Identifier les limites, les compromis et les erreurs fréquentes.

1. Pourquoi les migrations sont une partie du déploiement

Une migration transforme le schéma ou les données d’une base : ajout de colonne, nouvel index, changement de contrainte, conversion de données ou suppression d’un ancien champ. Le code applicatif et le schéma évoluent ensemble, mais ils ne sont pas nécessairement mis en production au même instant. Pendant un déploiement progressif, plusieurs versions du code peuvent utiliser la même base. La migration doit donc prendre en compte cette période de coexistence.

Une migration qui fonctionne sur une base de développement minuscule peut bloquer une table de production ou durer plusieurs heures. Il faut examiner le volume, les verrous, les index, la réplication, la charge des écritures et les limites du moteur utilisé. Les détails varient selon le SGBD et sa version : ne suppose pas qu’une opération « en ligne » est sans verrou ni impact.

Chaque changement devrait être traçable et automatisé. Le dépôt contient les migrations ordonnées ; l’outil sait lesquelles ont été appliquées ; le pipeline vérifie le résultat. Modifier manuellement le schéma de production sans consigner l’opération crée une divergence que les environnements et les prochains déploiements ne pourront pas reproduire.

2. La stratégie expand–migrate–contract

Pour un changement incompatible, préfère plusieurs livraisons compatibles. La phase expand ajoute les éléments nécessaires sans supprimer l’ancien fonctionnement. La phase migrate déploie le code compatible et transforme progressivement les données. La phase contract retire l’ancien schéma après confirmation qu’aucune version ni tâche ne l’utilise encore.

Exemple : une application stocke un nom complet dans full_name et doit passer à first_name et last_name. Une migration directe qui supprime immédiatement full_name peut casser l’ancienne version toujours en service. Une approche plus sûre ajoute les nouvelles colonnes, déploie du code qui lit les deux formats et écrit selon une règle contrôlée, remplit les nouvelles colonnes par lots, compare les valeurs, bascule les lectures, puis supprime l’ancien champ dans une livraison ultérieure.

Il faut définir qui est la source de vérité pendant la transition. Écrire dans trois colonnes sans stratégie peut créer des divergences. Le code doit préciser l’ordre des écritures, le comportement en cas d’échec partiel et comment les données seront réparées. Une double écriture n’est pas automatiquement sûre : elle doit être idempotente, observable et temporaire.

3. Les risques opérationnels

Verrous et durée. Ajouter une contrainte ou construire un index peut bloquer les écritures selon le moteur et la commande. Consulte la documentation de la version réelle, estime la durée avec des données représentatives et choisis les options qui réduisent le verrouillage si elles existent.

Backfill volumineux. Mettre à jour des millions de lignes en une seule transaction peut générer beaucoup de journaux, gonfler les tables et perturber la réplication. Traite les données par lots bornés, suis la progression et prévois la reprise après interruption. Le script doit pouvoir être relancé sans doubler les effets.

Contraintes et données historiques. Une nouvelle contrainte NOT NULL ou une unicité peut échouer si les données existantes ne la respectent pas. Mesure d’abord les anomalies, définis une règle de correction et vérifie le résultat avant d’activer la contrainte.

Retour arrière. Le code peut être restauré alors que la migration a déjà changé la structure ou les valeurs. Une migration inverse ne restaure pas toujours l’information supprimée. Pour les opérations destructives, la sauvegarde, la restauration testée ou une correction en avant sont souvent plus réalistes qu’un simple « down migration ».

4. Exemple de plan de livraison

  1. Créer une migration additive et la tester sur une copie représentative de la base.
  2. Mesurer son temps, ses verrous, son volume de journaux et son impact sur la réplication.
  3. Déployer une version du code compatible avec l’ancien et le nouveau schéma.
  4. Exécuter le backfill par lots avec métriques de progression, reprise et contrôle d’intégrité.
  5. Comparer les données, puis basculer les lectures et surveiller les erreurs.
  6. Attendre la disparition des anciennes versions et tâches, puis retirer l’ancien schéma dans une livraison séparée.

Dans le pipeline, sépare autant que possible la validation, l’application de migration et le déploiement du code. Les migrations peuvent demander des droits élevés ; donne-les à une identité dédiée et limitée, plutôt qu’à chaque processus applicatif. Pour les migrations longues, préfère un job contrôlé et observable à une opération cachée au démarrage de chaque instance.

5. Automatisation et contrôle

Le pipeline doit détecter les migrations déjà appliquées, échouer clairement si l’état est incohérent et empêcher deux exécutions concurrentes du même changement. Vérifie les migrations depuis une base vide et depuis une version antérieure réaliste. Le premier scénario vérifie la construction initiale ; le second vérifie l’évolution réelle. Les deux sont nécessaires.

Avant une opération destructive, confirme qu’une sauvegarde existe et qu’une restauration a été testée. Une sauvegarde n’est utile que si elle est récupérable dans le délai attendu. Définis aussi un seuil d’arrêt : durée excessive, hausse de latence, réplication en retard ou taux d’erreur inhabituel.

Ne modifie pas une migration déjà appliquée dans les environnements partagés pour « corriger le fichier » : les bases peuvent avoir exécuté des contenus différents. Crée une nouvelle migration corrective, documente la divergence et réconcilie l’état. Les migrations doivent rester immuables une fois publiées.

Exemple PostgreSQL : backfill borné et reprenable

Exemple illustratif pour convertir price_text en centimes entiers. Vérifie le moteur et sa version sur une base représentative avant la livraison ; une opération additive n’est pas automatiquement sans verrou ni impact.

-- Migration expand séparée du backfill
ALTER TABLE product ADD COLUMN price_cents bigint;

-- Précontrôle : traiter les valeurs non convertibles avant la bascule
SELECT id, price_text
FROM product
WHERE price_text IS NOT NULL
  AND price_text !~ '^[0-9]+([.][0-9]{1,2})?$'
ORDER BY id
LIMIT 100;

-- Exécuter plusieurs fois avec les paramètres positionnels $1 (dernier identifiant) et $2 (taille du lot).
-- Le curseur avance sur les identifiants retournés ; les valeurs invalides
-- sont traitées séparément et ne doivent pas être converties silencieusement.
WITH batch AS (
  SELECT id, round(price_text::numeric * 100)::bigint AS cents
  FROM product
  WHERE id > $1
    AND price_cents IS NULL
    AND price_text ~ '^[0-9]+([.][0-9]{1,2})?$'
  ORDER BY id
  LIMIT $2
)
UPDATE product AS p
SET price_cents = batch.cents
FROM batch
WHERE p.id = batch.id
RETURNING p.id;

Après chaque lot, enregistre le nombre de lignes traitées, le dernier identifiant retourné, la durée et les erreurs. Avant la bascule, compare les lignes convertibles restantes et les écarts entre l’ancien et le nouveau format ; définis une procédure explicite pour les valeurs invalides. Le code applicatif doit garder une règle de double écriture cohérente pendant la coexistence. La suppression de price_text n’intervient que dans une migration ultérieure, après preuve qu’aucune version active ne le lit.

  • Reprise : relancer un lot ne modifie pas une ligne déjà remplie grâce à price_cents IS NULL.
  • Arrêt : interrompre le backfill si la latence, le retard de réplication ou les verrous dépassent les seuils convenus.
  • Validation : tester base vide, données historiques, valeurs invalides et interruption/reprise sur une copie représentative.

6. Exercice pratique

Planifie le passage d’une colonne price_text vers un montant numérique price_cents. Décris les phases expand, migrate et contract ; indique comment traiter les valeurs invalides, comment migrer par lots, comment vérifier la parité entre colonnes et ce qui se passe si le backfill s’arrête à mi-chemin. Ajoute les métriques et le plan de reprise.

Critères de réussite

  • Je comprends pourquoi les versions applicatives peuvent coexister pendant une migration.
  • Je sais appliquer expand–migrate–contract à un changement incompatible.
  • J’anticipe les verrous, les backfills, les contraintes et les données historiques.
  • Je teste les migrations sur une base vide et sur une base existante représentative.
  • Je prévois une reprise observable et une stratégie réaliste de récupération.

Atelier approfondi — livrer une migration compatible

Objectifs pédagogiques

  • Organiser une migration de schéma sans synchroniser tous les déploiements.
  • Gérer backfill, double lecture/écriture et retrait différé.
  • Prévoir surveillance, reprise et conditions d’arrêt.

Expand

Ajouter d’abord une structure compatible avec l’ancienne version; éviter les opérations longues ou bloquantes sur le chemin critique.

Migration progressive

Déployer le code capable de lire l’ancien et le nouveau format, puis effectuer le backfill par lots bornés et reprenables.

Bascule

Vérifier la complétude et la cohérence des données avant de faire du nouveau champ la source de vérité.

Contract

Ne supprimer l’ancien champ qu’après avoir prouvé qu’aucune version active ni tâche différée ne l’utilise.

Exploitation

Mesurer durée, erreurs, verrous et retard; définir des checkpoints, un mécanisme de reprise et une stratégie de réparation.

Exercice pratique

Faire évoluer `customer.name` vers `given_name` et `family_name`. Détailler les étapes de compatibilité, le backfill, la validation et la suppression différée.

Critères de réussite

  • Ancienne et nouvelle versions coexistent sans rupture.
  • Le backfill est borné, observable et reprenable.
  • La bascule dépend d’une vérification de cohérence.
  • Le retrait est retardé jusqu’à preuve d’absence d’usage.
