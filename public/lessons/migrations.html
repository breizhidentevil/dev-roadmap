4. Bases de données et modélisation

Migrations de schéma

Faire évoluer la structure d’une base de manière versionnée, reproductible et sûre.

Seconde passe pédagogiqueBase de données

Objectifs d’apprentissage

  • Expliquer pourquoi le schéma de base doit être versionné.
  • Écrire une migration reproductible et comprendre ses limites de réversibilité.
  • Planifier un changement compatible avec un déploiement progressif.

1. Le schéma comme historique versionné

Une migration décrit une évolution précise de la base : créer une table, ajouter une colonne, introduire une contrainte ou transformer des données. Les migrations sont conservées dans le dépôt et exécutées dans un ordre déterminé. L’outil de migration enregistre généralement celles qui ont été appliquées.

Le schéma local, celui des tests et celui de production doivent pouvoir être rapprochés à partir du même historique. Une modification manuelle en production sans migration crée une dérive difficile à reproduire.

-- Exemple de migration ascendante
ALTER TABLE utilisateurs
ADD COLUMN nom_affiche TEXT;

Une migration doit avoir une intention claire, un ordre stable et des conditions d’exécution connues. Elle doit être testée sur une base représentative, pas uniquement sur une base vide.

2. Changer le schéma sans casser l’application

Un déploiement progressif peut faire coexister l’ancienne et la nouvelle version du code. La stratégie « expand–migrate–contract » réduit le risque : ajouter d’abord une structure compatible, déployer un code qui sait la lire/écrire, remplir les anciennes lignes, vérifier les résultats, puis retirer l’ancien champ lors d’un déploiement ultérieur.

  1. Expand : ajouter la colonne ou la table sans rendre immédiatement l’ancien code invalide.
  2. Migrate : remplir les données par lots si le volume est important, en surveillant verrous, durée et charge.
  3. Switch : basculer les lectures et écritures, puis vérifier métriques et cohérence.
  4. Contract : supprimer l’ancien champ uniquement après confirmation qu’aucun code actif ne l’utilise.

Les détails dépendent du SGBD : certaines opérations prennent des verrous forts ou réécrivent la table. Vérifie le comportement de la version exacte et teste sur un volume proche de la production.

Exemple de contrainte progressive sous PostgreSQL

  1. Ajouter nom_affiche nullable et déployer une version du code qui renseigne le champ pour les nouvelles écritures.
  2. Remplir les anciennes lignes par lots bornés, puis mesurer les valeurs manquantes et vides.
  3. Une fois le backfill terminé, ajouter puis valider la contrainte :
ALTER TABLE utilisateurs
  ADD CONSTRAINT utilisateurs_nom_affiche_valide
  CHECK (nom_affiche IS NOT NULL AND length(btrim(nom_affiche)) > 0)
  NOT VALID;

ALTER TABLE utilisateurs
  VALIDATE CONSTRAINT utilisateurs_nom_affiche_valide;

-- Planifier ensuite SET NOT NULL après vérification du verrouillage
-- et des garanties de la version PostgreSQL utilisée.

Dans PostgreSQL, une contrainte CHECK ... NOT VALID n’inspecte pas immédiatement toutes les lignes existantes, mais elle est appliquée aux nouvelles lignes et aux lignes modifiées ; la validation explicite vérifie ensuite les données déjà présentes. Ajoute cette contrainte après le backfill si des lignes historiques ne la respectent pas encore. Ne suppose pas qu’une opération est sans verrou parce qu’elle est déclarée en ligne.

3. Réversibilité et données

Un rollback de migration ne restaure pas nécessairement les données supprimées ou transformées. Distingue l’inversion du schéma, la compensation métier et la restauration depuis sauvegarde. Avant une transformation destructive, conserve une copie vérifiable, mesure les lignes concernées et définis le point au-delà duquel un retour arrière n’est plus simple.

Une migration doit être reproductible, ordonnée et traçable. Évite de modifier après coup une migration déjà appliquée dans plusieurs environnements : crée une nouvelle migration corrective. En CI, teste une base vide et, si le projet le permet, une mise à niveau depuis un schéma précédent contenant des données réalistes.

Erreurs fréquentes

  • Modifier le schéma à la main sans enregistrer de migration.
  • Ajouter une contrainte incompatible avec les données existantes.
  • Supprimer une colonne avant que toutes les versions de l’application aient cessé de l’utiliser.
  • Supposer qu’une migration descendante restaure les données supprimées.
  • Tester seulement sur une base vide et ignorer la durée des opérations.
  • Utiliser IF NOT EXISTS pour masquer une dérive de schéma sans vérifier la définition réellement présente.
  • Laisser chaque instance applicative lancer les migrations au démarrage sans mécanisme de sérialisation adapté à l’outil.

Exercice

Une table utilisateurs contient des milliers de lignes et doit recevoir un champ obligatoire nom_affiche. Propose un plan de migrations compatible avec un déploiement progressif, incluant le remplissage des anciennes lignes et les contrôles avant d’imposer la contrainte.

Critères de réussite

  • Les étapes n’exigent pas que toutes les instances changent simultanément.
  • Les anciennes lignes sont remplies et vérifiées avant la contrainte.
  • Le plan prévoit surveillance, sauvegarde et gestion d’échec.
  • Les suppressions irréversibles sont différées jusqu’à ce qu’elles soient sûres.
