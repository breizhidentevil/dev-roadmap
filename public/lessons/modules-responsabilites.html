3. Backend

Modules et responsabilités backend

Découper le backend en modules dont les responsabilités sont cohérentes, les interfaces explicites et les dépendances dirigées vers des abstractions stables.

Tutoriel détailléLot 10 · 2026

Objectifs d’apprentissage

  • Regrouper le code par responsabilité métier.
  • Définir des contrats entre modules.
  • Réduire le couplage et éviter les dépendances circulaires.
  • Distinguer modularité interne et déploiement distribué.

Fil conducteur

Un bon module regroupe ce qui change ensemble et cache ses détails internes. Le test décisif est de pouvoir modifier son implémentation sans obliger les consommateurs à changer.

1. Organiser autour des responsabilités

Un module regroupe du code qui évolue pour une raison cohérente : commandes, comptes, facturation ou catalogue. Une organisation purement technique — tous les contrôleurs ensemble, tous les services ailleurs — peut devenir difficile à parcourir lorsque chaque changement métier traverse de nombreux dossiers.

Un découpage par fonctionnalité rapproche les règles, les cas d’usage et les tests qui changent ensemble. Il n’impose pas une architecture unique : une application peut conserver des couches internes tout en regroupant les fichiers par domaine. Le bon découpage facilite la compréhension et limite les modifications collatérales.

2. Définir l’interface publique

Un module devrait exposer les opérations et types dont les autres modules ont réellement besoin, tout en gardant ses détails internes privés. Le contrat public peut être un service applicatif, une fonction, un ensemble de types ou une API HTTP selon le contexte.

catalog/
      index.ts        // interface publique
      catalog.service.ts
      catalog.repository.ts
      catalog.types.ts
      catalog.test.ts

Les noms sont illustratifs. Évite que d’autres modules importent directement les fichiers internes du module : ces chemins deviennent une dépendance implicite qui rend les refactorisations risquées. Attention : un fichier index.ts est une convention de point d’entrée, pas une frontière imposée par TypeScript. Pour faire respecter la règle, ajoute des contrôles adaptés au projet, par exemple des règles de lint sur les imports ou des frontières de packages via exports lorsque le code est publié comme package Node.js.

3. Couplage, cohésion et dépendances

La cohésion mesure si les éléments d’un module servent une même responsabilité ; le couplage décrit la dépendance entre modules. Cherche une cohésion forte et un couplage limité, sans transformer chaque fonction en module indépendant.

Une dépendance circulaire rend l’ordre d’initialisation, les tests et le raisonnement plus difficiles. Pour la casser, clarifie la propriété d’une règle métier, introduis une interface si elle représente une vraie frontière, ou déplace une responsabilité vers le module qui possède les données et invariants concernés. Une interface abstraite n’est pas utile si elle ne réduit aucun couplage réel.

4. Dépendances entre domaines

Un module peut avoir besoin d’une information détenue par un autre. Préfère une interface explicite à l’accès direct à ses tables ou à ses structures internes. Cela permet au module propriétaire de préserver ses règles et de faire évoluer son stockage.

Ne duplique pas la logique métier dans plusieurs modules. Si un concept partagé apparaît, vérifie qu’il possède réellement le même sens dans chaque contexte : deux valeurs portant le même nom peuvent avoir des règles différentes. Les modèles partagés trop vastes finissent souvent par devenir un point de couplage global.

5. Modularité et microservices

Un monolithe modulaire peut être déployé comme une seule application tout en gardant des frontières internes solides. Les microservices ajoutent des frontières réseau, des déploiements indépendants, de la latence, des pannes partielles, de l’observabilité distribuée et des enjeux de cohérence des données.

Commence généralement par des modules internes bien définis. Envisage une extraction en service lorsque des besoins réels le justifient : rythme de déploiement différent, mise à l’échelle distincte, propriété d’équipe ou contraintes d’isolation. Une séparation en processus n’est pas une amélioration automatique de l’architecture.

Exercice guidé

Prends une application de vente en ligne fictive et propose des modules pour catalogue, panier, commandes et comptes. Dessine les dépendances, définis une interface publique par module et identifie les accès qui devraient être interdits. Explique quels critères justifieraient éventuellement une extraction en service séparé.

Critères de réussite

  • Chaque module possède une responsabilité identifiable.
  • Les contrats publics sont limités et documentés.
  • Aucune dépendance circulaire n’est nécessaire.
  • Les invariants métier restent sous le contrôle de leur module propriétaire.
  • Le choix monolithe ou microservices est argumenté par des besoins concrets.

Erreurs fréquentes

  • Créer des modules trop petits sans responsabilité claire.
  • Exposer tous les fichiers internes comme une API publique.
  • Partager directement les tables entre domaines.
  • Introduire des interfaces abstraites sans besoin concret.
  • Confondre découpage du code et découpage en microservices.

Repère pratique. Commence par les cas d’usage et les règles métier, pas par une arborescence de dossiers générique. Un module « commandes » peut posséder les transitions de commande et exposer des opérations métier, tandis que l’accès SQL reste un détail interne.

Repère pratique. Un import circulaire est souvent le symptôme d’une frontière mal placée. Repère qui doit connaître qui, puis déplace le contrat partagé vers un module stable ou inverse la dépendance via une interface ; évite de résoudre chaque cycle par un conteneur global.

Repère pratique. Une frontière de module ne justifie pas à elle seule un service réseau séparé. Un microservice ajoute déploiement, observabilité, sécurité réseau, latence et cohérence distribuée ; extrais-le quand l’autonomie de livraison ou la contrainte opérationnelle compense ce coût.
