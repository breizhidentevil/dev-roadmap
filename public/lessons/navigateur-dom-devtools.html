1. Fondamentaux de la programmation et du Web

Navigateur, DOM et DevTools

Comprendre le chemin entre le HTML reçu et l’interface rendue, puis utiliser les outils du navigateur pour inspecter et diagnostiquer.

Tutoriel détailléLot 8 · 2026

Objectifs d’apprentissage

  • Distinguer HTML source, DOM, styles calculés et pixels affichés.
  • Inspecter les éléments et les règles CSS effectives.
  • Utiliser la console, les outils réseau et les points d’arrêt.
  • Relier un symptôme visuel à une cause probable.

1. Du document à l’affichage

Le navigateur récupère les ressources, analyse le HTML et construit le DOM. Il analyse le CSS pour déterminer les styles, puis calcule la géométrie des éléments et peint le résultat. Ce modèle est simplifié : les étapes peuvent se chevaucher, et le JavaScript peut modifier le DOM ou les styles pendant le chargement.

Le code source HTML n’est pas toujours identique au DOM observé : le navigateur corrige certaines structures, les scripts peuvent ajouter ou retirer des éléments et le serveur peut générer le document dynamiquement. Pour comprendre ce qui est réellement affiché, inspecte le DOM courant plutôt que de te fier uniquement au fichier initial.

2. Inspecter un élément

L’inspecteur permet de sélectionner un élément, de remonter dans ses ancêtres et de voir les règles CSS qui s’appliquent. Les styles calculés montrent les valeurs finales après cascade, héritage et résolution des valeurs. Si une règle ne s’applique pas, vérifie le sélecteur, la spécificité, l’ordre des feuilles et les conditions de media query.

Les modifications faites dans DevTools sont temporaires et ne changent pas directement le fichier source. Utilise-les pour tester une hypothèse, puis reporte le correctif dans le code et vérifie-le après rechargement.

3. Console et débogueur

La console expose les erreurs, avertissements et messages de diagnostic. Le débogueur permet de suspendre l’exécution, inspecter les variables et suivre les appels. Quand une erreur survient, pars de la première erreur pertinente et de sa pile d’appels ; les messages suivants peuvent n’être que des conséquences.

console.debug("état du composant", { actif, chargement });
    console.table(elements);

Les logs doivent répondre à une question de diagnostic et ne doivent pas exposer de jetons, mots de passe ou données personnelles.

4. Réseau et stockage

L’onglet Réseau montre les requêtes, leurs statuts, durées, en-têtes, corps et initiateurs. Il aide à distinguer une erreur de chargement d’une erreur de rendu. Vérifie le cache, les redirections et les réponses API, sans déduire qu’un statut 200 garantit un contenu correct.

Les outils de stockage permettent d’examiner cookies, stockage local, session storage et caches disponibles. Ne copie pas les valeurs sensibles dans un ticket ou une capture partagée. En cas de problème d’authentification, inspecte les attributs des cookies et le contexte de la requête sans divulguer leur valeur.

5. Reproduire les conditions réelles

Teste plusieurs tailles de fenêtre, un réseau lent, le cache activé ou désactivé et les interactions qui déclenchent le bug. Le mode responsive simule la taille de viewport et certaines caractéristiques mobiles, mais ne remplace pas toujours un appareil réel.

Pour une interface lente, enregistre une trace de performance et cherche les tâches longues, recalculs de style ou mises en page coûteuses. Pour un bug visuel, vérifie d’abord l’existence du nœud, puis sa visibilité, sa géométrie et les règles CSS avant de modifier le code.

Erreurs fréquentes

  • Confondre le code source initial et le DOM après exécution.
  • Modifier une règle CSS sans comprendre la cascade.
  • Prendre une réponse HTTP réussie pour une preuve de bon fonctionnement.
  • Ignorer les conditions qui rendent le bug reproductible.
  • Partager des captures contenant des données privées.

Analyse approfondie : formuler et tester une hypothèse

Un bon débogage réduit l’incertitude étape par étape. Commence par écrire le symptôme exact, les étapes pour le reproduire et le résultat attendu. Évite de changer plusieurs variables simultanément : tu ne saurais plus quel changement a résolu le problème.

Exemple de raisonnement

  1. Symptôme : les cartes sont visibles, mais les images manquent.
  2. Hypothèse : la ressource n’est pas chargée, plutôt qu’un problème de mise en page.
  3. Test : filtre les requêtes d’images dans Réseau et inspecte le statut et l’URL.
  4. Conclusion : un 404 oriente vers le chemin ou le déploiement ; un 200 avec image vide conduit à examiner le contenu et les dimensions CSS.

Le cache peut masquer un défaut ou faire croire à une correction. Répète le test avec un rechargement adapté et note si le résultat dépend du cache. Un mode mobile simulé n’émule pas parfaitement le matériel, le navigateur ni les conditions réseau d’un appareil réel.

Breakpoints et inspection ciblée

Pose un point d’arrêt sur la ligne qui modifie l’interface, inspecte les valeurs au moment précis où le résultat diverge, puis remonte la pile d’appels. Retire les points d’arrêt et les journaux temporaires après le diagnostic. N’utilise pas de captures d’écran contenant des cookies, jetons, données personnelles ou paramètres privés d’URL.

Exercice guidé

Sur une page de test, masque volontairement un bouton par CSS, casse une URL de ressource et ajoute une erreur JavaScript. Utilise successivement l’inspecteur, l’onglet Réseau et le débogueur pour identifier chaque cause. Note la preuve observée avant de corriger.

Critères de réussite

  • Chaque défaut est relié à un outil de diagnostic adapté.
  • La cause est démontrée par une observation reproductible.
  • Le correctif persiste après rechargement.
  • Les données sensibles ne sont pas copiées dans les logs.
  • Un contrôle final confirme l’absence de régression visible.
