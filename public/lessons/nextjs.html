2. Frontend

Next.js

Comprendre le routage basé sur les fichiers, les composants serveur et client, le rendu et la récupération de données dans Next.js.

Tutoriel détailléLot 9 · 2026

Objectifs d’apprentissage

  • Expliquer le rôle de l’App Router et des segments de route.
  • Distinguer composants serveur et composants client.
  • Choisir où récupérer les données.
  • Comprendre les compromis du rendu et du cache.

Fil directeur

Next.js ajoute au modèle React des conventions de routage, des capacités de rendu serveur et des mécanismes de récupération et de cache. La première décision consiste à savoir où une opération doit s’exécuter, puis à traiter explicitement les erreurs, les permissions et la fraîcheur des données.

1. Faire correspondre l’arborescence aux URL

Avec l’App Router, les dossiers sous `app` définissent les segments de route. `page.tsx` rend une page, `layout.tsx` partage une structure, `loading.tsx` décrit un état de chargement et `error.tsx` une frontière de gestion d’erreur. Un segment dynamique comme `[id]` représente une ressource, mais ne valide pas l’identifiant.

Dans l’App Router, `error.tsx` doit être un composant client et commencer par la directive `"use client"`. Il reçoit notamment `error` et `reset` ; ce dernier permet de proposer une nouvelle tentative. N’affiche pas directement les détails internes de l’exception au visiteur.

app/
  products/page.tsx
  products/[id]/page.tsx

Prévois explicitement le cas où la ressource n’existe pas et valide les paramètres avant de les utiliser dans des opérations sensibles.

2. Choisir la frontière serveur/client

Les composants serveur sont le choix par défaut dans l’App Router. Ils peuvent accéder aux données côté serveur et éviter d’envoyer au navigateur du JavaScript inutile. Un composant client est nécessaire pour les Hooks d’état, les gestionnaires d’événements et les API du navigateur ; le fichier commence alors par la directive `"use client"`.

Garde cette frontière aussi étroite que possible. Les props transmises doivent être sérialisables selon les règles de React/Next.js. Toute donnée envoyée au client peut être inspectée : ne transmets pas de secrets et ne confonds pas masquage visuel et autorisation.

3. Récupérer et valider les données

Un composant serveur peut effectuer une récupération asynchrone. Vérifie le statut de la réponse, valide sa structure et traite séparément les erreurs et l’absence de résultat. Un type TypeScript seul ne valide pas un JSON à l’exécution.

const response = await fetch(sourceUrl);
if (!response.ok) {
  throw new Error("Impossible de charger les produits");
}
const payload: unknown = await response.json();
// Valider payload avant de le transmettre à l’interface.

L’URL est fournie par la configuration du projet ; ne place pas d’identifiants privés dans le code client.

4. Définir rendu, chargement et cache

Le rendu serveur, l’hydratation client et le streaming peuvent être combinés pour afficher du contenu progressivement. Utilise `loading.tsx` ou des frontières de suspension lorsque le chargement doit être représenté, et prévois une voie claire pour les erreurs.

Le cache peut réduire le travail et la latence, mais il peut aussi servir des données périmées. Les valeurs par défaut et les API de cache changent selon les versions de Next.js : vérifie la documentation de la version installée et définis explicitement les besoins de fraîcheur et d’isolation.

5. Sécuriser et vérifier le déploiement

Contrôle l’autorisation côté serveur pour chaque lecture ou mutation sensible, y compris lorsque l’identifiant vient de l’utilisateur. Le fait qu’un bouton soit caché ne protège pas une route. Vérifie aussi que les réponses en cache ne partagent pas des données propres à un utilisateur entre sessions.

Avant déploiement, teste les routes directes, les identifiants inconnus, les états de chargement et d’erreur, les variables d’environnement, les chemins d’assets et les politiques de cache. Le mode développement ne reproduit pas nécessairement toutes les caractéristiques du build de production.

Erreurs fréquentes et diagnostic

  • Ajouter `use client` à toute l’application par défaut.
  • Supposer qu’un type TypeScript valide le JSON reçu.
  • Confondre absence de résultat et panne inattendue.
  • Supposer que le cache se comporte de la même façon dans toutes les versions.
  • Vérifier les permissions uniquement dans l’interface.

Exercice guidé

Crée une route de liste de produits et une route dynamique de détail. Charge les données dans un composant serveur, valide la réponse, puis ajoute un composant client pour une interaction locale. Gère ressource absente, chargement, erreur et politique de cache ; teste les permissions côté serveur.

Critères de réussite

  • L’arborescence correspond aux URL attendues.
  • Les composants client ne contiennent que les interactions nécessaires.
  • Les données externes sont vérifiées à l’exécution.
  • Les erreurs et ressources absentes ont des comportements distincts.
  • Permissions et cache sont définis et testés côté serveur.
