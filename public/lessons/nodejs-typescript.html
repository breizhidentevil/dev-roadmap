3. Backend

Node.js et TypeScript

Comprendre l’exécution JavaScript côté serveur, structurer les modules et compiler TypeScript avec une configuration reproductible et des frontières d’entrée explicites.

Tutoriel détailléLot 9 · 2026

Objectifs d’apprentissage

  • Distinguer Node.js du navigateur.
  • Comprendre modules, scripts npm et configuration TypeScript.
  • Gérer l’asynchronisme et les erreurs.
  • Valider les données externes et protéger la configuration.

Fil conducteur

Le chemin d’une application serveur est : charger la configuration, initialiser les dépendances, démarrer le processus, traiter les entrées asynchrones, puis arrêter proprement les ressources.

1. Node.js : JavaScript hors du navigateur

Node.js exécute JavaScript en dehors du navigateur et fournit des API pour le système de fichiers, le réseau, les processus et d’autres tâches serveur. Il n’expose pas automatiquement le DOM ou window. Le modèle d’E/S non bloquantes permet de gérer de nombreuses opérations réseau sans créer un thread par requête, mais du calcul synchrone long peut bloquer la boucle d’événements.

console.log("Node", process.version);
    console.log("Répertoire courant", process.cwd());

Choisis une version de Node.js maintenue et cohérente avec les dépendances du projet. Documente la version attendue, par exemple avec un fichier de version et le champ engines si cela convient au workflow. engines décrit une plage compatible mais ne garantit pas, à lui seul, que chaque poste ou chaque pipeline utilise cette version : configure le gestionnaire de versions et vérifie la version dans la CI.

2. Modules et scripts

Node.js prend en charge les modules CommonJS et ECMAScript. Le choix détermine la syntaxe d’importation et certaines règles de résolution ; configure le projet de façon cohérente et suis la documentation de la version de Node utilisée.

// src/math.ts
    export function add(a: number, b: number): number {
      return a + b;
    }

Dans package.json, les scripts nomment les tâches courantes comme développement, compilation et tests. Évite de compter sur une commande disponible uniquement sur ton poste ; déclare les outils du projet comme dépendances de développement et documente les étapes nécessaires.

3. Compiler et configurer TypeScript

TypeScript ajoute un système de types statique à JavaScript et doit être transformé en JavaScript pour l’exécution standard. Le fichier tsconfig.json contrôle notamment les fichiers inclus, la cible JavaScript, les modules et le niveau de vérification.

{
      "compilerOptions": {
        "target": "ES2022",
        "module": "NodeNext",
        "moduleResolution": "NodeNext",
        "strict": true,
        "outDir": "dist",
        "rootDir": "src"
      },
      "include": ["src/**/*.ts"]
    }

La configuration doit correspondre au mode de modules et à la version Node du projet. Les options ci-dessus sont un point de départ, pas une configuration universelle. Une compilation réussie ne garantit pas que les données externes sont valides à l’exécution.

4. Asynchronisme et erreurs

Les opérations de fichiers et de réseau sont souvent asynchrones. Avec async/await, les erreurs doivent être traitées au bon niveau et les ressources libérées lorsque nécessaire. Évite les appels synchrones coûteux dans les chemins de requête d’un serveur.

async function loadConfig() {
      try {
        const value = await readConfig();
        return value;
      } catch (error) {
        throw new Error("Impossible de charger la configuration", { cause: error });
      }
    }

readConfig est ici une fonction illustrative. Ajoute le contexte utile à une erreur sans y inclure de secrets. Une erreur doit être traitée, propagée ou transformée explicitement, pas ignorée silencieusement.

5. Entrées, configuration et sécurité

Les types TypeScript ne valident pas les valeurs reçues par HTTP, les fichiers ou les variables d’environnement. Traite ces valeurs comme inconnues, vérifie leur format et convertis-les en types internes validés avant de les utiliser.

Les secrets et paramètres spécifiques à l’environnement doivent venir d’une configuration protégée plutôt que du code source. Vérifie les variables obligatoires au démarrage et échoue tôt avec un message explicite si une configuration indispensable manque. Ne journalise pas les mots de passe, jetons ou clés.

Exercice guidé

Crée un petit programme Node.js en TypeScript qui lit une configuration, valide ses paramètres, exécute une fonction asynchrone et renvoie un code de sortie cohérent en cas d’erreur. Ajoute des scripts de compilation et de test, puis exécute le programme à partir du JavaScript compilé.

Critères de réussite

  • Le projet possède une configuration TypeScript stricte et documentée.
  • Les modules sont configurés de façon cohérente.
  • Les entrées externes sont validées à l’exécution.
  • Les erreurs utiles sont propagées sans divulguer de secrets.
  • Le build et les tests fonctionnent depuis une installation propre.

Erreurs fréquentes

  • Utiliser des API du navigateur dans un processus Node.js.
  • Mélanger des conventions de modules incompatibles.
  • Supposer que TypeScript valide les données à l’exécution.
  • Bloquer la boucle d’événements avec du calcul synchrone long.
  • Ignorer les erreurs ou écrire des secrets dans les logs.

Repère pratique. Node.js fournit des API serveur et un modèle d’E/S non bloquantes, mais une tâche CPU longue bloque tout de même la boucle d’événements. Déporte les calculs réellement coûteux ou découpe-les ; « asynchrone » ne signifie pas « parallèle ».

Repère pratique. Sépare la vérification des types de la transformation du code : TypeScript n’effectue pas automatiquement une validation des données à l’exécution. Une réponse JSON, une variable d’environnement ou un message de file doit être vérifié comme une donnée inconnue à la frontière.

Repère pratique. Traite les variables d’environnement comme des chaînes potentiellement absentes ou mal formées. Valide-les au démarrage, échoue avec un message exploitable et ne journalise jamais les secrets.
