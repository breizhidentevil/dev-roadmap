4. Bases de données et modélisation

Normalisation et dénormalisation

Réduire les incohérences, puis dénormaliser seulement lorsque le besoin est mesuré.

Seconde passe pédagogiqueBase de données

Objectifs d’apprentissage

  • Identifier les anomalies de mise à jour.
  • Expliquer les formes normales courantes.
  • Choisir entre normalisation et dénormalisation selon un besoin mesuré.

1. Pourquoi normaliser ?

La normalisation organise les données pour qu’un fait soit stocké à un endroit cohérent. Quand la même information est répétée dans plusieurs lignes, sa modification doit être répercutée partout. Cela provoque des anomalies de mise à jour, d’insertion et de suppression.

Par exemple, si chaque commande répète le nom et l’e-mail du client, changer l’e-mail exige de corriger toutes ses commandes. Une table client séparée réduit cette duplication.

CREATE TABLE clients (
  id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  nom TEXT NOT NULL,
  email TEXT NOT NULL UNIQUE
);
CREATE TABLE commandes (
  id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  client_id BIGINT NOT NULL REFERENCES clients(id),
  cree_le TIMESTAMPTZ NOT NULL DEFAULT now()
);

2. Les formes normales

La première forme normale vise des valeurs atomiques dans chaque cellule et des lignes identifiables. La deuxième forme normale concerne les dépendances à une partie seulement d’une clé candidate composée. La troisième forme normale cherche à éliminer les dépendances transitives inappropriées entre attributs non-clés. Ces définitions servent à repérer les anomalies, pas à appliquer mécaniquement une recette sans comprendre les dépendances fonctionnelles.

Exemple : si une table de lignes de commande répète nom_client et que client_id détermine ce nom, une correction de nom doit sinon toucher plusieurs lignes. Déplace les données du client dans une table distincte si elles décrivent bien l’état courant. En revanche, conserve le prix appliqué à une ligne de commande si ce prix représente le prix historique de la vente, et non le prix actuel du catalogue.

Pour chaque duplication, demande-toi : quelle est la source de vérité, quand la valeur peut-elle changer, et quelle règle maintient les copies cohérentes ?

3. Lire une dépendance fonctionnelle avant de décomposer

Supposons une table de lignes de commande dont la clé candidate est (commande_id, produit_id). Si produit_id détermine nom_produit, ce nom dépend seulement d’une partie de la clé composée : le conserver sur chaque ligne crée une dépendance partielle. En revanche, quantite et le prix réellement payé dépendent de la ligne complète. Le prix appliqué doit souvent rester un instantané historique, même si le prix courant du catalogue change.

CREATE TABLE produits (
  id BIGINT PRIMARY KEY,
  nom TEXT NOT NULL
);

CREATE TABLE commandes_lignes (
  commande_id BIGINT NOT NULL REFERENCES commandes(id),
  produit_id BIGINT NOT NULL REFERENCES produits(id),
  quantite INTEGER NOT NULL CHECK (quantite > 0),
  prix_unitaire_applique NUMERIC(12,2) NOT NULL
    CHECK (prix_unitaire_applique >= 0),
  PRIMARY KEY (commande_id, produit_id)
);

Pour la troisième forme normale, examine aussi les dépendances transitives : si departement_id détermine nom_departement, stocker ce nom sur chaque employé le répète sans nécessité. Une table departements séparée devient la source de vérité. Cette décomposition suppose qu’un seul département est associé à chaque identifiant ; les règles réelles doivent être modélisées explicitement.

La clé composée ci-dessus suppose qu’un produit ne peut apparaître qu’une fois par commande. Si le métier autorise plusieurs lignes pour le même produit (par exemple des lots ou des remises distinctes), choisis une clé de ligne dédiée ou une autre contrainte métier au lieu d’imposer cette hypothèse silencieusement.

4. Dénormaliser avec intention

La dénormalisation peut réduire des jointures ou accélérer des lectures fréquentes, mais elle introduit une obligation de synchronisation. Elle se justifie après mesure : requête identifiée, latence cible, volume et coût d’écriture connus. Documente l’autorité de la donnée, le moment où la copie est mise à jour et le comportement si une mise à jour échoue.

Exemples possibles : compteur de commentaires maintenu par transaction, projection de lecture reconstruisible ou instantané de facture. Ce sont des sémantiques différentes. Un compteur recalculable n’a pas les mêmes exigences qu’un montant légal archivé. Prévois une procédure de réconciliation qui compare les valeurs dérivées à leur source.

Erreurs fréquentes

  • Stocker une liste séparée par des virgules dans une colonne.
  • Répéter une information modifiable dans plusieurs tables sans règle de cohérence.
  • Dénormaliser avant d’avoir mesuré un problème réel.
  • Confondre une redondance historique voulue et une duplication accidentelle.

Exercice

Modélise une boutique avec clients, commandes, produits et lignes de commande. Une commande contient plusieurs produits et un produit apparaît dans plusieurs commandes. Propose les tables, clés et contraintes. Décide quelles données doivent être conservées comme instantané historique, par exemple le prix unitaire au moment de l’achat.

Critères de réussite

  • La relation plusieurs-à-plusieurs passe par les lignes de commande.
  • Les données du client et du produit ne sont pas répétées inutilement.
  • Le prix historique est distingué du prix courant.
  • Chaque redondance a une justification et une règle de cohérence.
