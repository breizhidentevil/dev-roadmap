3. Backend

OAuth 2.0 et OpenID Connect

Comprendre la délégation d’autorisation et l’authentification fédérée.

Tutoriel détailléLot 12 · 2026

Objectifs d’apprentissage

  • Distinguer OAuth 2.0 et OpenID Connect.
  • Identifier client, serveur d’autorisation et API.
  • Comprendre Authorization Code avec PKCE, scopes et redirect URI.
  • Valider les retours et protéger les jetons.

1. OAuth et OIDC

OAuth 2.0 est un cadre de délégation d’autorisation : une application obtient un accès limité à une ressource. OpenID Connect ajoute une couche d’identité standardisée au-dessus d’OAuth, notamment un ID Token et des informations sur l’utilisateur.

Un access token sert à accéder à une API selon ses règles ; un ID Token sert au client OIDC à vérifier les informations d’authentification. Ne substitue pas l’un à l’autre et ne traite pas un access token opaque comme un profil utilisateur.

2. Authorization Code avec PKCE

L’utilisateur est redirigé vers le serveur d’autorisation. Le client envoie une URI de retour exacte, les scopes demandés, un état anti-CSRF et les paramètres PKCE. Après authentification, le navigateur revient avec un code que le client échange contre des jetons.

PKCE lie l’échange du code à une preuve créée par le client et protège notamment contre l’interception du code. Utilise des bibliothèques maintenues plutôt que de réimplémenter manuellement le protocole.

3. Scopes, audiences et redirections

Demande uniquement les scopes nécessaires. L’API doit vérifier que le jeton lui est destiné et autorise l’opération ; un scope ne remplace pas les permissions métier sur une ressource précise.

Les URI de redirection doivent être contrôlées strictement : les redirections ouvertes peuvent envoyer des codes vers un domaine hostile. Vérifie state et, en OIDC, nonce lorsque requis. Une redirection réussie n’est pas à elle seule une preuve d’identité.

4. Valider les ID Tokens

Vérifie la signature avec les clés et règles du fournisseur, ainsi que l’émetteur, l’audience, l’expiration et le nonce lorsqu’il a été envoyé. Ne fais pas confiance à un JSON simplement décodé.

Les informations de profil peuvent changer. Pour relier des comptes, évite de fusionner deux identités sur la seule base d’une adresse e-mail non vérifiée.

5. Architecture et cycle de vie

Une application serveur peut créer une session locale après OIDC et conserver les jetons côté serveur. Les applications publiques ne doivent pas embarquer un secret client. Applique les recommandations adaptées au type de client et évite les flux obsolètes.

Prévois expiration, renouvellement, rotation des clés et déconnexion. La déconnexion locale et la déconnexion chez le fournisseur sont distinctes et n’offrent pas nécessairement les mêmes garanties.

6. Étude de cas : connecter un utilisateur via un fournisseur d’identité

Dans un flux Authorization Code avec PKCE, distingue trois parties : le client qui initie la connexion, le serveur d’autorisation qui authentifie l’utilisateur et émet les jetons, et l’API qui protège les ressources. Le navigateur transporte des redirections ; il ne devient pas pour autant un lieu de confiance pour les secrets ou les décisions d’accès.

  1. Le client crée une valeur state imprévisible et un couple PKCE code_verifier/code_challenge, puis conserve l’état de transaction dans un stockage approprié.
  2. Il redirige vers l’endpoint d’autorisation avec une URI de retour préenregistrée exacte, le type de réponse attendu, les scopes minimaux et le challenge PKCE.
  3. Au retour, il compare state à la transaction initiée, consomme cette valeur une seule fois et échange le code avec le vérificateur PKCE via le canal prévu. La requête d’échange réutilise la même URI de redirection que celle enregistrée pour l’autorisation.
  4. Pour OIDC, il valide l’ID Token : signature et algorithme attendu, émetteur exact, audience, expiration et nonce lorsque celui-ci a été envoyé. Si plusieurs audiences sont présentes, il vérifie également azp selon les règles OIDC. Il établit ensuite sa propre session applicative.
  5. Lors d’un appel API, l’API vérifie l’access token selon son format et ses règles (audience, scopes/permissions, expiration). L’ID Token n’est pas un jeton d’accès à l’API.

Le paramètre state lie le retour à la transaction initiée et contribue à la protection contre la falsification de requête ; PKCE protège le code contre son interception et son échange par un autre acteur. Ils ont des fonctions liées mais non interchangeables. Le paramètre nonce lie un ID Token à la demande d’authentification OIDC et aide à prévenir la réutilisation dans un autre contexte.

Erreurs de configuration typiques

  • URI de retour validée par préfixe ou wildcard trop large, permettant une redirection vers un domaine non approuvé.
  • Absence de vérification de state ou de la liaison PKCE.
  • Acceptation d’un ID Token sans vérifier l’audience, l’émetteur ou l’expiration.
  • Demande de scopes excessifs ou confiance dans un scope sans autorisation métier sur la ressource.
  • Stockage ou journalisation des jetons dans un endroit accessible à des scripts ou aux journaux.

Exercice : dessine la séquence navigateur/client/serveur d’autorisation/API, puis injecte un mauvais state, un code réutilisé, une audience incorrecte et une URI de retour non enregistrée. Chaque cas doit être rejeté avant la création d’une session valide ou l’accès à l’API.

Ne journalise ni code d’autorisation, ni access token, ni ID Token, ni code_verifier. En cas de rotation des clés JWKS, actualise les clés depuis le fournisseur configuré et traite une clé inconnue sans suivre une URL de clé fournie librement dans un jeton.

Critère de réussite : tu peux expliquer chaque paramètre du flux, identifier qui valide quel jeton et montrer que le client n’accepte ni retour détourné ni jeton destiné à une autre application.

Erreurs fréquentes

  • Utiliser OAuth comme si cela définissait toute l’authentification utilisateur.
  • Confondre access token et ID Token.
  • Ne pas vérifier issuer, audience ou expiration.
  • Accepter des URI de redirection trop permissives.
  • Intégrer un secret client dans une application publique.

Exercice guidé

Conçois la connexion OIDC d’une application Web : dessine les redirections et échanges, liste les paramètres de sécurité, précise où les jetons sont conservés et décris les validations du retour. Ajoute les cas où state ne correspond pas ou l’audience du token est incorrecte.

Critères de réussite

OAuth et OIDC distingués ; Authorization Code avec PKCE expliqué ; state, nonce et claims validés selon le cas ; jetons destinés au bon client/API ; session, révocation et déconnexion traitées.
