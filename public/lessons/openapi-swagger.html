3. Backend

Documentation OpenAPI/Swagger

Décrire une API avec un contrat OpenAPI exploitable par les humains et les outils, puis intégrer sa validation au cycle de développement.

Tutoriel détailléLot 11 · 2026

Objectifs d’apprentissage

  • Comprendre le rôle d’une spécification OpenAPI.
  • Décrire routes, paramètres, schémas et réponses.
  • Documenter authentification, erreurs et exemples.
  • Valider le contrat automatiquement et le garder aligné avec le code.

Fil conducteur

Documente le contrat observé par le client : méthodes, paramètres, schémas, statuts, erreurs, sécurité et exemples. La spécification doit évoluer avec le code, idéalement via des contrôles automatisés.

1. OpenAPI et Swagger : distinction

OpenAPI est une spécification décrivant une API HTTP dans un format structuré, généralement YAML ou JSON. Swagger désigne notamment des outils capables de visualiser, modifier ou exploiter ce contrat. Le document OpenAPI est la source du contrat ; l’interface graphique n’est qu’une façon de le consulter.

Une spécification précise ce que les clients peuvent envoyer et recevoir. Elle peut alimenter une documentation interactive, générer des clients, vérifier les réponses ou produire des mocks. Elle ne prouve pas à elle seule que l’implémentation respecte le contrat.

2. Structure minimale

openapi: 3.1.0
info:
  title: API des tâches
  version: 1.0.0
paths:
  /tasks:
    get:
      summary: Lister les tâches
      responses:
        "200":
          description: Liste renvoyée
          content:
            application/json:
              schema:
                type: array
                items:
                  $ref: "#/components/schemas/Task"
components:
  schemas:
    Task:
      type: object
      required: [id, title, done]
      properties:
        id: { type: string }
        title: { type: string }
        done: { type: boolean }

Le document décrit le chemin, l’opération, les réponses et le schéma. Dans un vrai contrat, ajoute les paramètres, les réponses d’erreur, les exemples, les règles d’authentification et les contraintes utiles.

3. Décrire précisément les entrées et sorties

Utilise parameters pour les paramètres de chemin, de requête et d’en-tête ; requestBody pour le corps ; et responses pour les résultats possibles. Distingue un champ absent d’un champ nullable : ce sont deux comportements différents. Décris les formats, limites, valeurs autorisées et champs obligatoires lorsque ces règles font partie du contrat.

Documente les réponses d’erreur attendues, par exemple 400, 401, 403, 404 et 500. Des réponses d’erreur absentes de la spécification laissent les clients deviner comment réagir.

4. Réutilisation et sécurité

Déplace les schémas réutilisables dans components/schemas, les mécanismes de sécurité dans components/securitySchemes et les réponses communes dans components/responses. Les références $ref évitent les duplications et réduisent les divergences entre endpoints.

Décris l’authentification sans exposer de secret réel. Une clé API d’exemple doit être fictive. La spécification peut documenter les exigences d’accès, mais les autorisations doivent toujours être appliquées par le serveur.

5. Validation dans le cycle de développement

  1. Versionner la spécification avec le code.
  2. Valider la syntaxe et les règles de style à chaque pull request.
  3. Comparer les changements au contrat précédent pour détecter les ruptures.
  4. Générer ou mettre à jour les clients si le projet le prévoit.
  5. Tester que l’implémentation correspond aux schémas et statuts documentés.

Choisis une approche contract-first si le contrat doit être partagé avant l’implémentation. Une approche code-first peut convenir si le framework génère une spécification fiable. Dans les deux cas, évite que le contrat publié diverge de l’API réellement déployée.

Exercice guidé

Décris une API qui crée une tâche avec un titre obligatoire et renvoie 201. Prévois aussi les erreurs de validation et d’absence d’authentification, un schéma réutilisable pour une tâche et un exemple de réponse. Vérifie le fichier dans un éditeur OpenAPI.

Critères de réussite

  • La spécification est valide et lisible.
  • Les paramètres, corps et réponses sont explicitement décrits.
  • Les erreurs et l’authentification sont documentées.
  • Les schémas réutilisables sont centralisés.
  • Une vérification automatique est prévue en CI.

Erreurs fréquentes

  • Décrire uniquement les réponses de succès.
  • Oublier les contraintes, la nullabilité ou les valeurs d’énumération.
  • Copier le même schéma dans plusieurs endpoints au lieu de le réutiliser.
  • Considérer une page Swagger comme une preuve de conformité.
  • Modifier le code sans régénérer ou valider le contrat.

Utilise `required` pour les propriétés obligatoires et distingue soigneusement propriété absente, valeur `null` et chaîne vide : ces états ne sont pas équivalents.

Repère pratique. Décris les réponses d’erreur autant que le succès, y compris les statuts et le schéma du corps. Un exemple doit respecter le schéma déclaré ; sinon, il donne aux consommateurs un contrat trompeur même si le fichier passe une validation syntaxique.

Repère pratique. Ajoute au minimum une validation de la spécification en CI et, si possible, une vérification de compatibilité entre versions. La validité du YAML ne prouve pas que l’API implémente le contrat : complète-la par des tests de contrat ou des tests d’intégration.
