2. Frontend

Vite, npm/pnpm, ESLint et Prettier

Configurer un environnement frontend reproductible, gérer les dépendances et automatiser les contrôles de qualité du code.

Tutoriel détailléLot 9 · 2026

Objectifs d’apprentissage

  • Comprendre le rôle du serveur de développement et du build.
  • Gérer les dépendances et le fichier de verrouillage.
  • Distinguer linting et formatage.
  • Créer des scripts fiables pour le développement et l’intégration continue.

Fil directeur

Une chaîne frontend fiable doit rendre les mêmes dépendances et contrôles reproductibles sur le poste de développement et en intégration continue. Sépare les outils qui servent à exécuter l’application de ceux qui vérifient la qualité du code.

1. Comprendre le cycle de développement et de build

Vite fournit un serveur de développement et un processus de build. Le serveur accélère le retour pendant le codage ; le build produit des fichiers destinés à être servis en production. `preview` permet d’inspecter localement le résultat compilé, mais ne remplace pas un déploiement réel.

npm create vite@latest mon-app
cd mon-app
npm install
npm run dev
npm run build
npm run preview

Lis `package.json` : les scripts exacts et le dossier de sortie dépendent du modèle de projet et de la configuration.

2. Rendre les dépendances reproductibles

`package.json` décrit les dépendances et les scripts ; le fichier de verrouillage enregistre la résolution concrète des versions. Versionne le lockfile et utilise le gestionnaire choisi par le dépôt. Évite de mélanger `package-lock.json` et `pnpm-lock.yaml`, car cela rend les installations moins prévisibles.

npm ci

`npm ci` réalise une installation propre en CI à partir d’un lockfile cohérent. Pour pnpm, utilise la commande d’installation figée correspondante à la version configurée. Documente la version de Node.js pour réduire les écarts entre machines.

3. Séparer formatage, analyse et tests

Prettier formate le code ; ESLint signale des motifs problématiques et applique des règles d’analyse statique ; les tests vérifient le comportement. Aucun de ces contrôles ne remplace les autres. Configure des scripts avec des objectifs distincts, par exemple `lint`, `format:check`, `test` et `build`.

{
  "scripts": {
    "lint": "eslint .",
    "format:check": "prettier --check .",
    "test": "vitest run",
    "build": "vite build"
  }
}

Adapte les commandes au langage et à la configuration : un dépôt TypeScript/JSX doit être analysé avec les extensions et règles adaptées. L’exemple suppose que Vitest est installé et configuré ; si le projet utilise un autre runner, remplace `vitest run` par sa commande non interactive. En CI, exécute au minimum `npm ci`, `npm run lint`, `npm run format:check`, `npm test` et `npm run build`, en arrêtant le pipeline dès qu’une étape échoue.

4. Automatiser le workflow et protéger les secrets

En CI, commence par une installation propre, puis exécute lint, formatage, tests et build. Une vérification locale ou un hook Git accélère le retour, mais peut être contourné ; la CI doit donc rester l’autorité pour les contrôles requis.

Tout ce qui est intégré au bundle frontend est potentiellement public. Les variables préfixées pour être exposées au navigateur ne doivent jamais contenir de clé privée ou de mot de passe. Après le build, teste les routes directes, les chemins de ressources et les erreurs de console dans des conditions proches de la production.

Erreurs fréquentes et diagnostic

  • Oublier le lockfile ou utiliser un gestionnaire différent de celui du projet.
  • Confondre formatage, lint, tests et build.
  • Ne valider que le serveur de développement.
  • Exposer une clé privée dans une variable client.
  • Compter sur un hook local au lieu de contrôles CI.

Exercice guidé

Crée une application Vite avec scripts séparés pour lint, vérification du format, tests et build. Versionne le lockfile, fixe la version de Node.js et configure une CI qui échoue dès qu’un contrôle échoue. Inspecte le bundle pour vérifier qu’aucun secret n’est exposé.

Critères de réussite

  • Un clone neuf s’installe avec une procédure documentée.
  • Un seul gestionnaire de paquets et son lockfile sont utilisés.
  • Les scripts ont des responsabilités distinctes.
  • La CI exécute les contrôles et le build.
  • Aucun secret serveur n’est livré dans le code client.
