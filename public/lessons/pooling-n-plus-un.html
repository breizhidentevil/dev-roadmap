4. Bases de données et modélisation

Pool de connexions et problème N+1

Maîtriser les connexions à la base et éviter les requêtes répétitives qui dégradent la latence.

Seconde passe pédagogiqueBackend et données

Objectifs d’apprentissage

  • Expliquer le rôle d’un pool de connexions et le coût d’une connexion créée à chaque requête.
  • Reconnaître le problème N+1 et ses effets sur la latence.
  • Choisir entre jointure, chargement groupé et chargement différé selon le cas.

1. Pool de connexions : réutiliser sans saturer

Une connexion consomme des ressources côté client et serveur. Le pool limite le nombre de connexions ouvertes et les réutilise. Dimensionne-le globalement : si 8 instances peuvent ouvrir 15 connexions chacune, la base peut recevoir jusqu’à 120 connexions applicatives, auxquelles s’ajoutent les connexions d’administration et de supervision. Compare ce total à la limite réellement disponible.

const result = await pool.query(
  'SELECT id, email FROM utilisateurs WHERE id = $1',
  [userId]
);

Pour un client emprunté manuellement, utilise un bloc try/finally afin de le restituer même si une instruction échoue. Configure un délai d’attente, surveille les connexions actives/inactives et les files d’attente. Une attente de pool peut être la cause de la latence même si les requêtes SQL sont rapides.

2. Le problème N+1

Le problème N+1 apparaît lorsqu’une requête récupère une liste de N entités, puis exécute une requête supplémentaire pour chaque entité afin de charger une relation. Une page qui affiche 50 articles et leurs auteurs peut ainsi déclencher 1 requête pour les articles puis 50 requêtes pour les auteurs. Même si chaque requête est rapide, les allers-retours réseau et la charge cumulée coûtent cher.

// Schéma de comportement à éviter : une requête par article
const articles = await listArticles();
for (const article of articles) {
  article.auteur = await findUser(article.auteurId);
}

Solutions courantes : une jointure SQL, une requête groupée avec WHERE id IN (...), un chargement anticipé fourni par l’ORM, ou un DataLoader qui regroupe les demandes d’un même lot. Le choix dépend de la cardinalité : une jointure sur plusieurs relations « un-à-plusieurs » peut elle-même multiplier les lignes et rendre le résultat volumineux.

3. Mesurer plutôt que deviner

Mesure au moins : requêtes SQL par requête HTTP, latence totale, temps passé en base, durée d’attente d’une connexion, nombre de connexions actives, lignes et octets transférés. Utilise des identifiants de corrélation sans enregistrer les mots de passe, jetons ou données personnelles sensibles.

Compare trois variantes sur un jeu de données réaliste : boucle N+1, requête groupée avec WHERE id = ANY($1) ou IN, et jointure. Vérifie aussi les doublons produits par la jointure, le comportement lorsque la liste est vide et les limites de taille des lots. Une seule requête géante peut augmenter la mémoire et répéter des colonnes ; quelques requêtes groupées peuvent être plus simples et plus rapides.

Les chargements différés conviennent si une relation est rarement utilisée, mais deviennent coûteux quand ils se déclenchent dans une boucle. Les chargements anticipés sont utiles si les données sont réellement nécessaires à l’écran ; ne charge pas toutes les relations par défaut.

Erreurs fréquentes

  • Créer une nouvelle connexion à chaque opération sans la fermer correctement.
  • Configurer un pool indépendamment du nombre d’instances de l’application.
  • Ignorer une multiplication des requêtes déclenchée par une boucle ou une sérialisation.
  • Remplacer N+1 par une jointure énorme qui duplique les données.
  • Augmenter la taille du pool sans vérifier si la base est déjà saturée.

Exercice

Une route renvoie 40 articles avec le nom de leur auteur. Elle exécute actuellement une requête pour les articles puis une requête par auteur. Propose deux solutions pour réduire les requêtes et décris les métriques à comparer. Explique également comment dimensionner le pool si l’application tourne sur plusieurs instances.

Critères de réussite

  • Tu identifies clairement les requêtes N+1 dans les journaux ou les métriques.
  • Tu proposes un chargement groupé ou une jointure adaptée.
  • Tu compares nombre de requêtes, latence et volume transféré.
  • Tu tiens compte du nombre d’instances et de la limite de connexions de la base.
