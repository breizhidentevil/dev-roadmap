4. Bases de données et modélisation

PostgreSQL

Installer, configurer et utiliser une base relationnelle robuste.

Seconde passe pédagogiqueLot 13 · 2026

Objectifs d’apprentissage

  • Comprendre serveur, base, schéma, table, rôle et connexion.
  • Créer des tables avec des types et contraintes cohérents.
  • Se connecter de façon sûre et gérer les droits.
  • Découvrir transactions, index, sauvegardes et plans d’exécution.

1. Les principaux objets

PostgreSQL est un système de gestion de base de données relationnelle. Une instance de serveur héberge des bases ; une base contient des schémas ; les schémas regroupent notamment tables, vues, fonctions et séquences. Les rôles servent à représenter des utilisateurs ou groupes et à attribuer des privilèges.

En développement, une instance locale peut être suffisante. En production, il faut aussi penser aux mises à jour, sauvegardes, supervision, gestion des secrets, contrôle d’accès, disponibilité et restauration après incident.

2. Définir une table avec des contraintes

CREATE TABLE tasks (
  id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  title text NOT NULL CHECK (length(trim(title)) > 0),
  done boolean NOT NULL DEFAULT false,
  created_at timestamptz NOT NULL DEFAULT now()
);

Choisis les types selon la sémantique : un montant ne devrait pas être un flottant binaire arbitraire, une date avec fuseau doit être représentée en tenant compte du contexte, et une relation devrait être protégée par une clé étrangère lorsque l’intégrité l’exige. Les contraintes en base protègent les données même si plusieurs applications écrivent simultanément.

3. Connexions, rôles et configuration

Utilise un rôle applicatif distinct du rôle administrateur. Accorde seulement les privilèges nécessaires sur les schémas et tables utilisés par l’application. Les secrets de connexion ne doivent pas être commis dans Git ; utilise un mécanisme de configuration et de secrets adapté à l’environnement.

En production, limite les connexions réseau et configure l’authentification selon les recommandations de PostgreSQL et de l’infrastructure. Un mot de passe fort ne compense pas un serveur exposé inutilement à Internet.

4. Transactions et concurrence

Une transaction regroupe des opérations qui doivent réussir ou échouer ensemble. PostgreSQL utilise MVCC pour fournir des vues cohérentes, mais cela ne garantit pas automatiquement toutes les règles métier : deux transactions peuvent lire le même solde avant de tenter un débit. Pour une règle comme « le solde ne devient jamais négatif », combine contrainte, mise à jour conditionnelle ou verrouillage adapté.

BEGIN;
UPDATE accounts
SET balance = balance - 50
WHERE id = 1 AND balance >= 50;
-- Vérifier que la première mise à jour a modifié exactement une ligne.
UPDATE accounts SET balance = balance + 50 WHERE id = 2;
COMMIT;

Ce fragment illustre une partie du transfert, pas une implémentation complète : le code appelant doit vérifier le nombre de lignes affectées et exécuter ROLLBACK si une étape échoue. Garde les transactions courtes et évite d’y attendre un service HTTP ou une interaction utilisateur.

5. Index, diagnostics et sauvegardes

Un index B-tree aide souvent pour l’égalité, les plages et certains tris, mais son utilité dépend de la sélectivité, de la taille de table et de la forme de la requête. Commence par une requête réelle, relève sa latence et son volume, puis examine le plan.

EXPLAIN (ANALYZE, BUFFERS)
SELECT id, title FROM tasks
WHERE owner_id = 42 AND done = false
ORDER BY created_at DESC
LIMIT 20;

EXPLAIN ANALYZE exécute effectivement la requête : sois prudent avec les instructions qui modifient des données. Compare les lignes estimées aux lignes réelles, les accès disque/mémoire et le coût de tri ; ne cherche pas à forcer un index sans preuve. Chaque index ajoute un coût aux écritures et au stockage.

Une sauvegarde n’est vérifiée qu’après une restauration testée. Définis le RPO (perte de données acceptable) et le RTO (temps de reprise), la rétention, la séparation du stockage et la procédure de restauration. Les sauvegardes logiques, physiques et l’archivage WAL répondent à des besoins différents.

Erreurs fréquentes

  • Utiliser le rôle superutilisateur pour l’application.
  • Compter uniquement sur le code applicatif pour l’intégrité des données.
  • Ajouter des index sans examiner les requêtes réelles.
  • Considérer une sauvegarde non testée comme une garantie.
  • Exposer les identifiants de connexion dans le dépôt ou les logs.

Exercice guidé

Crée une table tasks avec identifiant, titre, état et date de création. Ajoute une contrainte empêchant un titre vide, un rôle applicatif avec des droits minimaux, puis écris une requête de liste et inspecte son plan. Rédige enfin une procédure de sauvegarde et de test de restauration.

Critères de réussite

  • Les types et contraintes reflètent le domaine.
  • Les privilèges sont minimaux.
  • Les transactions et erreurs sont comprises.
  • Les performances sont mesurées plutôt que supposées.
  • La sauvegarde inclut un scénario de restauration vérifiable.
