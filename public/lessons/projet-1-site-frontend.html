Projet 1 — Site frontend

Concevoir et livrer un site statique responsive, accessible, utilisable au clavier et documenté, sans framework obligatoire.

1. Contexte et besoin

Vous devez publier un petit site de présentation pour une association, un événement culturel ou une activité fictive. Une personne qui découvre le site doit comprendre l’offre, trouver les informations pratiques et contacter l’organisateur. Le contenu peut être fictif, mais il doit rester cohérent sur toutes les pages.

Utilisateur principal

Une personne consultant le site sur téléphone ou ordinateur, avec ou sans souris. Elle doit pouvoir accéder aux informations essentielles sans compte et sans installer de logiciel.

2. Périmètre fonctionnel

Fonctionnalités obligatoires

  • Une page d’accueil présentant clairement le sujet, avec un titre principal unique et un appel à l’action pertinent.
  • Une page ou section « À propos » présentant l’organisation, l’activité ou l’événement.
  • Une page ou section pratique avec horaires ou dates, lieu ou zone, et moyen de contact fictif clairement identifié.
  • Une navigation cohérente entre les sections/pages, avec l’état de navigation compréhensible et sans lien factice.
  • Une interaction JavaScript utile et non essentielle à la lecture : par exemple un menu mobile ou un filtre sur une liste de contenus.
  • Une page ou section de contact avec des coordonnées de démonstration ; si un formulaire est ajouté, ses erreurs doivent être annoncées et ses limites expliquées.

Hors périmètre

Pas de compte utilisateur, paiement, API distante, base de données, CMS ou collecte réelle de données personnelles. Ces éléments relèvent de projets ultérieurs. Ne pas ajouter une dépendance ou un framework uniquement pour complexifier le projet.

3. Exigences non fonctionnelles

  • Responsive : pas de défilement horizontal à 320 px de largeur, sauf contenu intrinsèquement bidimensionnel justifié ; contenu lisible à 320, 768 et 1280 px.
  • Accessibilité : HTML sémantique, ordre de titres logique, liens et contrôles utilisables au clavier, focus visible, libellés explicites et textes alternatifs pertinents.
  • Performance : images dimensionnées et compressées raisonnablement ; éviter les scripts ou bibliothèques inutiles ; pas d’erreur console bloquante pendant le parcours principal.
  • Compatibilité : vérifier au minimum un navigateur Chromium récent et un second moteur si disponible ; noter précisément les navigateurs réellement testés.
  • Confidentialité : utiliser des données fictives ; ne pas inclure de secret, clé d’API ni donnée personnelle réelle.
  • Maintenabilité : noms de fichiers et classes explicites, styles organisés, JavaScript limité aux comportements nécessaires.

4. Stack et organisation

  • HTML sémantique pour la structure.
  • CSS natif pour la mise en page, les états de focus et les adaptations responsive.
  • JavaScript natif pour une interaction ciblée, avec gestion du cas où l’élément attendu n’existe pas.
  • Git pour conserver des étapes de travail compréhensibles.

Organisation suggérée :

site-frontend/
├── index.html
├── pages/
│   ├── a-propos.html
│   └── informations.html
├── assets/
│   └── images/
├── css/
│   └── styles.css
├── js/
│   └── main.js
└── README.md

Cette structure est une proposition, pas une contrainte absolue. Pour un site d’une seule page, des sections avec ancres peuvent remplacer les pages séparées si la navigation reste claire.

5. Étapes de réalisation

  1. Cadrer le contenu : écrire les besoins, choisir le public, définir les pages/sections et dessiner un wireframe simple.
  2. Construire la structure : créer les fichiers, les titres, les régions sémantiques et la navigation sans mise en forme avancée.
  3. Ajouter le style : définir typographie, espacements, couleurs, états interactifs et points de rupture ; tester d’abord les petits écrans.
  4. Ajouter l’interaction : implémenter une fonctionnalité précise, prévoir le clavier et le cas où JavaScript échoue lorsque c’est possible.
  5. Contrôler le contenu : vérifier les liens, textes alternatifs, libellés, cohérence des informations et absence de faux boutons.
  6. Tester et corriger : suivre la grille d’acceptation ci-dessous, puis résoudre les défauts avant publication.
  7. Livrer : rédiger le README, expliquer comment ouvrir le site et consigner les limites connues.

6. Critères d’acceptation

Le projet est accepté uniquement si chaque point applicable peut être vérifié :

  • Le site s’ouvre depuis le fichier d’entrée documenté et les chemins relatifs fonctionnent après extraction du dossier.
  • Chaque page possède un titre de document pertinent, un seul titre principal visible et une structure de titres compréhensible.
  • Tous les liens internes conduisent à une destination existante ; les liens externes sont identifiés et testés avant livraison.
  • À 320, 768 et 1280 px, les éléments essentiels restent visibles et utilisables sans défilement horizontal accidentel.
  • Le parcours principal fonctionne entièrement au clavier ; le focus est visible et ne se perd pas dans un contrôle masqué.
  • Les images informatives ont un texte alternatif adapté ; les images décoratives n’ajoutent pas de bruit aux lecteurs d’écran.
  • L’interaction JavaScript fonctionne avec les cas normal et vide ; une erreur de saisie, si le formulaire existe, est indiquée en texte.
  • Aucune donnée réelle sensible, aucun secret et aucune dépendance non documentée ne sont livrés.
  • Le README décrit le but du site, la structure, la méthode de lancement et les vérifications effectuées.

7. Plan de tests

Tests manuels fonctionnels

  • Suivre tous les liens et utiliser l’action principale sur chaque page.
  • Tester l’interaction avec souris, clavier et, si disponible, lecteur d’écran.
  • Vérifier le menu ou le filtre sur contenu normal, vide et très long.
  • Redimensionner la fenêtre aux trois largeurs cibles et contrôler l’orientation mobile si l’appareil est disponible.

Contrôles automatisables

  • Validation HTML avec un outil reconnu, si disponible.
  • Vérification des liens locaux par script.
  • Audit automatisé d’accessibilité comme aide au diagnostic, complété par un test clavier manuel.
  • Inspection de la console et de l’onglet réseau dans le navigateur.

Ne noter un contrôle comme réussi qu’après l’avoir réellement exécuté. L’absence d’outil ou de navigateur doit être signalée comme non testée, pas transformée en succès.

8. Sécurité, accessibilité et publication

  • Éviter d’injecter du contenu utilisateur avec `innerHTML` ; privilégier les API DOM adaptées ou échapper correctement les données si un rendu HTML est réellement nécessaire.
  • Ne pas collecter ni transmettre de données personnelles. Si un formulaire de démonstration existe, afficher clairement qu’il n’envoie rien.
  • Respecter la navigation clavier, les contrastes suffisants, les libellés et la réduction des animations lorsque c’est pertinent.
  • Pour la publication, utiliser un hébergement statique HTTPS, vérifier les chemins et ne publier que les fichiers nécessaires.
  • Ajouter un contrôle de liens et un audit d’accessibilité dans une CI simple si le projet le justifie ; ce n’est pas une condition pour commencer.

9. Livrables et définition de terminé

  • Code source complet avec structure stable.
  • README de lancement et de maintenance.
  • Grille d’acceptation cochée avec notes sur les tests réellement exécutés.
  • Liste des limites connues ou points non testés.
  • Historique Git avec des commits décrivant les changements.

Dossier de transfert. En plus du code, conserver une carte des pages et des parcours, les wireframes ou décisions d’interface importantes, l’inventaire des interactions et des champs de formulaire, ainsi que les résultats réellement observés aux largeurs cibles. Signaler les données encore fictives, les comportements simulés et les points d’accessibilité non vérifiés. Ce dossier servira de référence lors de la réutilisation de l’interface dans les projets Full Stack ; il ne suppose pas que le site statique doive devenir l’application métier.

Terminé signifie que les critères d’acceptation sont vérifiés, que les défauts bloquants sont corrigés, que les contrôles non réalisés sont signalés et qu’une autre personne peut ouvrir et comprendre le projet grâce au README. Une simple capture d’écran ou une page qui « semble fonctionner » ne suffit pas.

10. Checklist de validation

Les cases de cette page ne sont pas enregistrées après fermeture. Consigner l’état durablement dans le README ou le suivi du projet.
