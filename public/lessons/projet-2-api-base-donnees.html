Projets pratiques et validation des acquis

Projet 2 — API et base de données

Construire une API HTTP typée, persistante et testée, dont le contrat et les règles de données peuvent être compris et vérifiés indépendamment de l’interface utilisateur.

1. Contexte et objectif

Vous devez fournir le backend d’une petite application de gestion de tâches. Un client peut consulter les tâches, en créer, modifier leurs propriétés et supprimer celles qui ne sont plus utiles. Le serveur valide les entrées, applique les règles métier, interroge PostgreSQL et renvoie des réponses HTTP prévisibles.

Le but pédagogique n’est pas d’empiler des routes : il est de comprendre la frontière entre contrat HTTP, validation, logique applicative et persistance. Le projet doit permettre de démontrer qu’une donnée incorrecte est rejetée, qu’une donnée valide survit au redémarrage du processus et qu’un défaut de base de données ne produit pas une réponse trompeuse.

Prérequis

  • Connaître les bases de JavaScript/TypeScript, les fonctions asynchrones et les modules.
  • Comprendre les méthodes HTTP, les codes de statut, JSON et les notions de table, clé primaire et contrainte SQL.
  • Savoir lancer des tests et lire une erreur de terminal. Les transactions et les index peuvent être appris pendant le projet.

2. Périmètre fonctionnel

Inclus

  • Créer une tâche avec un titre obligatoire, une description facultative, un statut et une date d’échéance facultative.
  • Consulter une tâche par identifiant et lister les tâches avec pagination, tri stable et filtre facultatif par statut.
  • Modifier partiellement une tâche sans écraser les champs omis ; supprimer une tâche existante.
  • Fournir une route de santé simple, une documentation du contrat HTTP et des tests automatisés.
  • Initialiser et faire évoluer le schéma au moyen de migrations versionnées, puis fournir des données de démonstration non sensibles.

Hors périmètre de la première version

  • Comptes utilisateurs, connexion, permissions multi-utilisateurs, pièces jointes, notifications et synchronisation en temps réel.
  • Interface graphique complète, paiement, déploiement multi-région et optimisation prématurée de gros volumes.

La version pédagogique peut fonctionner en local avec des données fictives. Ne pas exposer publiquement une API sans authentification ni contrôles adaptés. Si une mise en ligne publique est ajoutée, l’authentification, les limites de débit, la politique CORS et la gestion des abus deviennent des exigences de conception, pas des options implicites.

3. Contrat HTTP à implémenter

Préfixe commun : /api/v1. Les réponses JSON doivent être documentées et cohérentes. Les exemples ci-dessous définissent le comportement attendu ; ils ne prétendent pas qu’une API est déjà implémentée.

Méthode et routeComportement attenduRéponse nominale
GET /tasksListe triée de façon déterministe par date de création décroissante, puis par identifiant UUID croissant en cas d’égalité ; accepte limit, offset et status.200 avec données et métadonnées de pagination.
POST /tasksValide puis crée une tâche.201, représentation créée et en-tête Location.
GET /tasks/:idRetourne une tâche existante.400 si l’UUID est mal formé, 200 si trouvé, 404 si l’UUID valide est absent.
PATCH /tasks/:idModifie uniquement les champs transmis, après validation.400 si l’UUID est mal formé, 200 avec la tâche actualisée, 404 si l’UUID valide est absent.
DELETE /tasks/:idSupprime une tâche existante.400 si l’UUID est mal formé, 204 sans corps si supprimée, 404 si l’UUID valide est absent.
GET /healthIndique si le processus et la connexion requise à la base sont disponibles.200 si prêt, 503 sinon, sans divulguer de secrets.

Règles de contrat

  • Identifiants UUID générés côté serveur ; ne jamais faire confiance à un identifiant fourni dans le corps de création. Un identifiant de route mal formé renvoie 400 avec un code stable tel que INVALID_ID ; un UUID valide mais absent renvoie 404.
  • title : chaîne non vide après suppression des espaces en bordure, 1 à 120 caractères ; description : chaîne facultative de 0 à 2 000 caractères ou valeur nulle si ce choix est documenté.
  • status : une des valeurs todo, in_progress ou done. La valeur par défaut à la création est todo.
  • dueDate : date au format ISO 8601 ou valeur nulle. Le contrat doit préciser la convention de fuseau horaire si un horodatage est utilisé.
  • limit par défaut à 20 et plafonné à 100 ; offset entier positif ou nul. Une valeur invalide reçoit une erreur de validation, pas une conversion silencieuse.
  • Les erreurs utilisent une enveloppe stable, par exemple {"error":{"code":"VALIDATION_ERROR","message":"...","fields":{}}}. Ne jamais inclure de trace de pile, de requête SQL ni de secret dans une réponse publique.

4. Modèle de données et persistance

Créer une table tasks avec au minimum : id UUID PRIMARY KEY, title VARCHAR(120) NOT NULL, description TEXT, status contraint aux trois valeurs autorisées, due_date DATE, created_at TIMESTAMPTZ NOT NULL et updated_at TIMESTAMPTZ NOT NULL. Définir les valeurs par défaut et les contraintes dans PostgreSQL, pas uniquement dans le code TypeScript.

  • Écrire une migration initiale, une migration de retour arrière si l’outil le permet et un jeu de données de démonstration reproductible.
  • Conserver les dates d’audit en UTC et documenter la conversion en entrée/sortie. Une date d’échéance sans heure peut être stockée en DATE pour éviter d’inventer un fuseau.
  • Utiliser des requêtes paramétrées pour toutes les valeurs utilisateur. Les noms de colonnes et directions de tri ne se paramètrent pas comme les valeurs : les choisir dans une liste blanche.
  • Réutiliser un pool de connexions et fermer proprement les connexions lors de l’arrêt. Une transaction est nécessaire dès qu’une opération doit réussir ou échouer comme un tout sur plusieurs écritures.
  • Ajouter des index pour une requête mesurée ou un besoin clair. Le tri fréquent par created_at peut justifier un index ; un index sur une colonne à peu de valeurs, comme le statut, ne doit pas être ajouté automatiquement sans considérer les requêtes et les volumes.

Ne pas construire une requête SQL en concaténant le titre, le filtre ou l’identifiant reçu. Le typage TypeScript aide à prévenir certaines erreurs de programmation, mais ne remplace ni la validation à l’exécution ni les contraintes SQL : les requêtes HTTP restent des entrées non fiables.

5. Architecture et choix techniques

Stack de référence proposée : Node.js LTS, TypeScript en mode strict, Fastify pour le serveur HTTP, PostgreSQL pour la persistance, le pilote pg pour les requêtes SQL, un outil de migrations versionnées et Vitest pour les tests. Ce choix garde les couches visibles et permet d’apprendre SQL sans masquer toutes les requêtes derrière un ORM. Une autre stack est acceptable si le contrat, les contrôles et les tests restent équivalents.

src/
  app.ts              # création de l'application et des routes
  server.ts           # démarrage et arrêt du processus
  config/             # validation de la configuration
  modules/tasks/
    task.routes.ts    # contrat HTTP
    task.schema.ts    # validation des entrées/sorties

  plugins/            # connexion DB et gestion d'erreurs

tests/
.env.example
README.md

Les routes traduisent HTTP vers les cas d’usage ; le service applique les règles métier ; le dépôt contient les requêtes et transforme les lignes SQL en objets de domaine. Pour une petite application, ces séparations peuvent rester légères : le but n’est pas de créer une classe par fonction, mais d’éviter de mélanger validation, SQL et réponse HTTP dans un unique gestionnaire de route.

Valider les variables d’environnement au démarrage. Fournir un .env.example avec des noms et valeurs factices, jamais le mot de passe réel. Garder la configuration de test distincte de la configuration de développement afin qu’un test ne puisse pas effacer une base personnelle par erreur.

6. Étapes de réalisation

  1. Écrire le contrat : préciser les routes, les formes JSON, les statuts HTTP, la validation, la pagination et le format d’erreur avant de coder.
  2. Initialiser le projet : configurer TypeScript strict, les scripts de développement/test, le lint éventuel et la validation de la configuration.
  3. Créer le schéma : écrire et appliquer les migrations, les contraintes, les données de démonstration et une procédure de remise à zéro réservée à la base de test.
  4. Construire une tranche verticale : implémenter la création d’une tâche de bout en bout, de la requête HTTP à l’écriture SQL puis à la réponse.
  5. Ajouter les autres routes : lecture unitaire, liste paginée, modification partielle et suppression ; centraliser le traitement des erreurs sans masquer leur cause dans les journaux.
  6. Tester les cas limites : données invalides, ressource absente, identifiant mal formé, statut inconnu, pagination extrême, panne DB et tentatives d’injection.
  7. Documenter et livrer : générer ou maintenir une spécification OpenAPI, décrire les commandes, les variables, les migrations et les tests réellement passés.

7. Critères d’acceptation mesurables

  • Les six routes listées dans le contrat répondent avec les statuts et formes JSON documentés, y compris les erreurs attendues.
  • Les cinq opérations CRUD passent par PostgreSQL ; une tâche créée reste consultable après redémarrage du serveur.
  • Une entrée avec titre vide, titre trop long, statut inconnu, pagination négative ou corps JSON invalide est rejetée sans écriture en base.
  • Un identifiant de route mal formé renvoie 400 ; un UUID valide mais absent renvoie 404 pour la lecture, la modification et la suppression. Une suppression réussie renvoie 204 sans corps.
  • La liste respecte le filtre de statut, le plafond de 100 éléments, le tri documenté et les métadonnées de pagination.
  • Les requêtes utilisent des paramètres SQL ; une chaîne contenant des caractères de syntaxe SQL reste une donnée et ne modifie pas la structure de la requête.
  • Les migrations peuvent être appliquées sur une base vide et le jeu de démonstration peut être chargé sans intervention manuelle non documentée.
  • Les tests automatisés couvrent les chemins nominaux, la validation, les ressources absentes et au moins une erreur de persistance ; les tests d’intégration utilisent une base isolée.
  • La documentation OpenAPI correspond aux routes et schémas réellement implémentés ; le README explique l’installation, la configuration et les commandes de vérification.

8. Plan de tests

Tests unitaires

  • Tester la validation des champs, les valeurs par défaut, les règles de mise à jour partielle et la transformation des erreurs.
  • Vérifier les limites de pagination, les statuts permis et la construction sûre des options de tri.

Tests d’intégration

  • Utiliser une base PostgreSQL de test dédiée ; appliquer les migrations avant la suite et nettoyer les données entre tests de manière déterministe.
  • Tester chaque route via le client HTTP de test, puis vérifier l’état persistant en base. Tester au moins une contrainte SQL et un échec de connexion ou d’écriture.
  • Vérifier qu’une réponse d’erreur ne contient ni mot de passe, ni chaîne de connexion, ni trace de pile.

Commandes et preuves de livraison

Documenter les scripts réels du projet, par exemple npm run test, npm run lint et une commande de vérification de types. Ne pas déclarer ces commandes réussies avant leur exécution. Conserver dans le compte rendu le résultat, l’environnement et les contrôles qui n’ont pas pu être effectués.

9. Sécurité, fiabilité et exploitation

  • Valider les entrées à l’exécution et limiter la taille du corps de requête ; ne pas considérer une interface TypeScript comme une barrière de sécurité.
  • Employer des requêtes paramétrées, une liste blanche pour les fragments SQL dynamiques et un compte PostgreSQL aux droits minimaux nécessaires.
  • Ne pas renvoyer les détails internes des erreurs au client. Journaliser un identifiant de requête et un contexte utile sans journaliser secrets ou données personnelles inutiles.
  • Définir les délais d’attente, traiter les connexions indisponibles et fermer le serveur ainsi que le pool DB proprement à l’arrêt.
  • Pour une publication publique, ajouter au minimum authentification/autorisation adaptées, limitation de débit, CORS restrictif, HTTPS, sauvegardes, supervision et procédure de mise à jour des secrets.

10. Livrables et définition de terminé

  • Code source structuré, migrations versionnées et données de démonstration non sensibles.
  • Contrat OpenAPI, exemples de requêtes/réponses et tableau des erreurs HTTP.
  • Tests unitaires et d’intégration reproductibles sur une base dédiée.
  • README avec versions requises, installation, variables d’environnement, démarrage, migrations, tests et dépannage.
  • Liste des limites connues, dont toute mesure de sécurité ou tout test de production non réalisé.

Terminé signifie que les critères d’acceptation sont vérifiés, que le projet peut être lancé à partir d’instructions propres, que les tests se reproduisent sur une base isolée et que les limites sont explicites. Une collection de routes qui renvoie des exemples codés en dur n’est pas une API persistante achevée.
