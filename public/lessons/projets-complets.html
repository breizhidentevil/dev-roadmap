Construire des projets complets

Un projet complet démontre votre capacité à relier interface, API, données, sécurité, tests et déploiement. Sa valeur vient moins du nombre de fonctionnalités que de la cohérence du périmètre et de la qualité du résultat vérifiable.

Objectifs et prérequis

Un projet complet sert à prouver qu’une solution fonctionne au-delà d’un exemple isolé. Il doit répondre à un besoin identifiable, présenter un parcours utilisateur cohérent et expliquer comment l’installer, le tester et le déployer. Il n’est pas nécessaire de construire une plateforme gigantesque : un périmètre limité mais terminé est plus convaincant.

  • Définir un MVP et des critères d’acceptation.
  • Découper le travail en incréments démontrables.
  • Intégrer sécurité, tests et exploitation dès le début.
  • Documenter les décisions et les limites connues.

1. Choisir un problème et un périmètre

Commencez par un utilisateur cible et un problème précis. « Application de gestion » est trop vague ; « permettre à une association de suivre les prêts de matériel et de savoir qui doit rendre chaque objet » décrit un besoin testable.

Écrivez les parcours essentiels avant de choisir une pile technique. Un MVP peut inclure la création d’un objet, son emprunt, son retour et la consultation de l’historique. Les notifications, tableaux de bord avancés et intégrations externes peuvent rester hors périmètre jusqu’à ce que le flux principal soit fiable.

Définissez les critères d’acceptation en termes observables : un utilisateur authentifié peut créer un prêt ; un prêt déjà clôturé ne peut pas être rendu une seconde fois ; une personne non autorisée ne peut pas modifier le prêt d’autrui. Ces critères guident le modèle de données et les tests.

2. Concevoir l’architecture utile

Une application web classique peut comporter une interface, une API, une base de données et un processus de déploiement. Dessinez les flux principaux : quelles données entrent, quelles règles s’appliquent, où elles sont stockées et comment les erreurs reviennent à l’utilisateur. Un schéma d’une page suffit souvent au départ.

Définissez les responsabilités : le navigateur améliore l’expérience et valide certains champs ; le serveur reste responsable de l’autorisation et des invariants métier ; la base impose les contraintes qui doivent survivre à la concurrence, comme l’unicité d’une adresse ou la cohérence d’une relation.

Choisissez la technologie en fonction de vos objectifs d’apprentissage, de la simplicité de déploiement et de votre capacité à la maintenir. N’ajoutez pas un broker de messages, une architecture microservices ou Kubernetes sans exigence qui les justifie.

3. Construire par tranches verticales

Une tranche verticale traverse l’interface, la logique serveur et les données pour livrer un parcours complet. Par exemple, réaliser « créer un élément » de bout en bout avant d’implémenter dix écrans sans backend permet de découvrir tôt les problèmes de contrat et de validation.

  1. Créer le dépôt, le README et les conventions de travail.
  2. Définir le modèle et une première migration de base de données.
  3. Implémenter un cas d’usage complet avec validation serveur.
  4. Relier l’interface et gérer les états de chargement, succès et erreur.
  5. Ajouter des tests automatisés sur la règle métier et le contrat API.
  6. Déployer un environnement de démonstration et vérifier le flux réel.

Gardez les commits lisibles et les changements petits. Les pull requests, même pour un projet personnel, permettent de pratiquer la revue de code et de garder une trace de la raison d’un changement.

4. Qualité, sécurité et livraison

La qualité n’est pas seulement l’absence de bugs visibles. Testez les règles métier en priorité, les frontières avec les systèmes externes ensuite, puis les parcours critiques via des tests end-to-end ciblés. Un grand nombre de tests fragiles ne garantit pas la qualité ; chaque test doit protéger un comportement important.

Traitez les risques de sécurité dès le MVP : autorisation côté serveur, stockage sûr des mots de passe si vous gérez l’authentification, secrets hors du dépôt, dépendances mises à jour, requêtes paramétrées et erreurs publiques non bavardes. N’inventez pas votre propre cryptographie ou protocole de session.

La livraison doit être reproductible : configuration documentée, variables d’environnement listées, migrations explicites, commande de test et procédure de déploiement. Ajoutez au minimum un health check utile, des journaux sans données sensibles et une sauvegarde si les données sont importantes.

5. README et démonstration

Le README est une interface pour les personnes qui évaluent ou reprennent le projet. Il doit expliquer le problème, les fonctionnalités, la pile, les prérequis, l’installation, la configuration, les tests, le déploiement et les limites connues. Des captures d’écran ou une courte démonstration peuvent aider, mais elles ne remplacent pas les instructions reproductibles.

Documentez les choix importants et leurs compromis : pourquoi une base relationnelle, pourquoi cette méthode d’authentification, quelles fonctionnalités ont été reportées. N’affirmez pas qu’un projet est sécurisé ou scalable sans préciser les contrôles réellement mis en place.

  • Ne laissez pas de fichier de configuration contenant des secrets dans le dépôt.
  • Ne décrivez pas des fonctionnalités qui ne fonctionnent pas.
  • Ne présentez pas un déploiement local comme une production robuste.
  • Ne repoussez pas tous les tests et la documentation à la fin.

Approfondissement pratique : prouver qu’un projet est réellement terminé

Un projet complet n’est pas une collection de fonctionnalités isolées : il doit permettre à une autre personne de comprendre le besoin, installer le système, exécuter les tests, observer le comportement et reproduire une démonstration. La définition de « terminé » doit donc inclure le parcours principal, les erreurs attendues, la sécurité minimale, les données de démonstration, la documentation et une livraison reproductible.

Découper par tranches verticales

Construisez d’abord un parcours utilisateur de bout en bout, même réduit : interface, validation côté serveur, persistance, réponse d’erreur et test. Une tranche verticale expose tôt les problèmes d’intégration. À l’inverse, terminer toute l’interface, puis toute l’API, puis la base peut repousser les incompatibilités jusqu’à la fin. Chaque tranche doit produire une preuve visible et testable.

Checklist de livraison

  • Le README décrit le problème, les prérequis, l’installation, la configuration et les commandes de lancement.
  • Les secrets sont fournis par variables d’environnement ou un mécanisme de configuration, jamais commités.
  • Les tests couvrent le parcours critique, les validations et au moins un cas d’échec.
  • Les erreurs sont compréhensibles sans exposer de détails internes sensibles.
  • Une migration ou un script de préparation permet de recréer les données nécessaires.
  • Les limites connues et les décisions techniques importantes sont documentées.
  • La démonstration utilise un scénario déterministe et des données non sensibles.

Exemple de preuve reproductible

# Exemple de séquence à documenter dans le README
npm ci
npm test
npm run build
npm run start

Ces commandes sont illustratives : adaptez-les au gestionnaire de paquets et aux scripts réellement présents dans le projet. N’annoncez pas qu’une commande fonctionne avant de l’avoir exécutée dans un environnement propre. Distinguez ce qui a été testé localement de ce qui a été testé en intégration ou en production.

Exercice de portfolio

Choisissez un projet réalisable en une semaine. Rédigez une définition de fini en dix points maximum, un parcours utilisateur principal, trois scénarios d’erreur et un plan de démonstration de cinq minutes. Demandez à une personne qui ne connaît pas le dépôt de suivre le README sans assistance et notez les étapes ambiguës.

Critères de réussite : une personne externe peut installer et lancer le projet, reproduire le parcours principal, comprendre les choix majeurs et identifier clairement les limites restantes.

Exercice guidé

Construisez une application de suivi de lecture avec livres, statut de lecture et notes personnelles. Limitez la première version à la création d’un livre, au changement de statut et à la consultation de la liste.

  1. Écrivez trois critères d’acceptation et un cas d’erreur.
  2. Définissez les tables ou collections et les règles d’autorisation.
  3. Implémentez une tranche verticale complète avant d’ajouter d’autres écrans.
  4. Choisissez cinq tests qui protègent les comportements les plus importants.
  5. Écrivez les étapes exactes pour lancer le projet depuis un dépôt neuf.

Critères de réussite : un autre développeur peut installer et lancer l’application, les parcours essentiels fonctionnent, les validations et autorisations sont côté serveur, les tests sont exécutables et les limites sont décrites honnêtement.
