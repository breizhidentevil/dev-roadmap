Tutoriel technique

Contrôle d’accès par rôle et par ressource

Concevoir des autorisations explicites, cohérentes et testables avec RBAC, ABAC et des contrôles appliqués côté serveur.

1. Objectifs et prérequis

Un contrôle d’accès détermine qui peut effectuer quelle action sur quelle ressource et dans quel contexte. Une interface qui masque un bouton n’est pas un mécanisme d’autorisation : un utilisateur peut appeler directement l’API. Ce tutoriel présente les modèles RBAC et ABAC, la différence entre authentification et autorisation, la manière d’appliquer les règles côté serveur et les tests qui permettent de détecter les accès excessifs. Il suppose que vous connaissez les bases d’une API web et des utilisateurs authentifiés.

2. Authentification et autorisation

L’authentification répond à la question « qui présente cette identité ? ». L’autorisation répond à « cette identité peut-elle effectuer cette action sur cette ressource maintenant ? ». Une session valide ne donne pas automatiquement accès à toutes les données. Chaque endpoint sensible doit appliquer les règles correspondant à l’action demandée et à la ressource visée.

Un risque fréquent est l’IDOR/BOLA : l’application accepte un identifiant de ressource fourni par le client, puis retourne l’objet sans vérifier que l’utilisateur y a droit. Remplacer `/orders/100` par `/orders/101` ne devrait pas permettre d’accéder à la commande d’un autre compte. Un identifiant difficile à deviner ne remplace pas un contrôle d’autorisation.

3. RBAC : permissions attribuées par rôle

Le contrôle d’accès basé sur les rôles (RBAC) associe des permissions à des rôles, puis attribue ces rôles aux utilisateurs. Par exemple, `support` peut consulter les tickets qui lui sont assignés, `manager` peut consulter ceux de son équipe, et `admin` peut gérer la configuration. Cette approche est lisible lorsque les responsabilités sont relativement stables et correspondent aux fonctions de l’organisation.

Évitez de multiplier les rôles pour exprimer chaque nuance métier. Une collection de rôles comme `admin-france-lundi`, `admin-france-mardi` et `admin-allemagne-lundi` devient rapidement ingérable. Les rôles devraient représenter des responsabilités cohérentes ; les conditions liées à une ressource ou à une situation peuvent être évaluées séparément.

const permissionsByRole = {
  reader: ["document:read"],
  editor: ["document:read", "document:update"],
  admin: ["document:read", "document:update", "user:manage"]
};

function hasPermission(role, permission) {
  return permissionsByRole[role]?.includes(permission) ?? false;
}

Cet exemple illustre une table de permissions, mais ne constitue pas à lui seul une architecture complète. Il faut valider la provenance du rôle, gérer les rôles absents ou inconnus comme un refus, tenir compte de la ressource concernée et appliquer la règle sur chaque opération sensible. Ne laissez pas le client choisir librement son propre rôle dans une requête.

4. ABAC : décisions fondées sur des attributs

Le contrôle d’accès basé sur les attributs (ABAC) évalue des attributs du sujet, de la ressource, de l’action et parfois de l’environnement. Une règle pourrait autoriser un utilisateur à modifier un document si son compte appartient à la même organisation que le document, si le document n’est pas archivé et si l’utilisateur possède la permission d’édition. Cette approche exprime mieux les relations et contraintes contextuelles.

Les attributs doivent provenir de sources fiables. Si le client envoie `organizationId` ou `isAdmin`, il ne faut pas les considérer comme vrais simplement parce qu’ils figurent dans le JSON. Le serveur doit obtenir l’identité depuis une session ou un jeton validé, puis charger les attributs de ressource et les relations nécessaires. Un attribut périmé peut aussi entraîner une autorisation incorrecte.

function canEditDocument(user, document) {
  if (!user || !document || user.active !== true) return false;
  if (user.organizationId == null || document.organizationId == null) return false;
  if (user.organizationId !== document.organizationId) return false;
  if (document.status === "archived") return false;

  // permissions doit provenir du contexte d'autorisation côté serveur.
  const permissions = Array.isArray(user.permissions) ? user.permissions : [];
  return permissions.includes("document:update");
}

Cette fonction rend les conditions explicites, mais les données `user` et `document` doivent avoir été authentifiées et chargées correctement. Il faut aussi décider comment traiter les valeurs absentes, les erreurs de base de données et les états incohérents : le comportement sûr par défaut est de refuser l’accès plutôt que d’autoriser en cas de doute.

5. Appliquer la règle au bon endroit

Les contrôles doivent être proches des opérations protégées, dans une couche serveur commune plutôt que dispersés uniquement dans les composants d’interface. Selon l’architecture, on peut utiliser un middleware, une politique d’autorisation ou un service dédié. Les requêtes à la base peuvent aussi intégrer les contraintes de propriétaire ou d’organisation pour éviter qu’une ressource non autorisée ne soit chargée par erreur.

Il faut distinguer un refus d’autorisation d’une ressource inexistante. Certaines API renvoient 403 lorsqu’une ressource existe mais que l’utilisateur n’y a pas accès ; d’autres utilisent 404 afin de ne pas révéler son existence. Le choix doit être cohérent, documenté et appliqué sans fuite d’information dans le corps de réponse ou les journaux.

6. Principe du moindre privilège

Un compte doit disposer du minimum de droits nécessaire à son travail. Appliquez ce principe aux utilisateurs, aux comptes de service, aux tâches d’arrière-plan et aux accès à la base. Séparez les opérations ordinaires des opérations administratives, et exigez une authentification renforcée pour les actions particulièrement sensibles lorsque le risque le justifie.

Les permissions doivent être retirées lorsque le besoin disparaît. Les comptes inactifs, les accès temporaires et les droits de prestataires doivent avoir un cycle de vie explicite. Les journaux d’audit devraient permettre de savoir qui a modifié les rôles et quand, sans enregistrer inutilement des secrets ou des données sensibles.

7. Tests d’autorisation

Testez les refus autant que les autorisations. Pour chaque action, vérifiez le cas autorisé, le cas sans session, le rôle insuffisant, la ressource appartenant à un autre utilisateur, l’organisation différente et les états particuliers comme un document archivé. Les tests doivent appeler l’API directement, sans dépendre de l’interface, afin de vérifier la vraie frontière de sécurité.

Les tests fondés sur des matrices sont utiles : lignes pour les rôles ou types de sujet, colonnes pour les actions, et résultats attendus. Ajoutez des tests de non-régression lorsqu’un incident révèle une règle manquante. Si les politiques sont complexes, centralisez leur logique et fournissez des explications diagnostiques réservées aux environnements de développement, sans divulguer ces détails au client final.

8. Erreurs fréquentes et compromis

  • Masquer les boutons dans l’interface sans protéger les endpoints.
  • Faire confiance à un identifiant, un rôle ou un attribut transmis par le client.
  • Confondre rôle global et droit sur une ressource précise.
  • Autoriser par défaut lorsque l’utilisateur, la ressource ou la politique est absent.
  • Multiplier les rôles au lieu d’exprimer les conditions métier dans une politique.
  • Tester seulement les accès autorisés, jamais les cas de refus.

RBAC est souvent plus simple à administrer, tandis qu’ABAC peut représenter des conditions plus riches. Les deux peuvent être combinés : les rôles fournissent une permission générale, puis une politique vérifie le propriétaire, l’organisation ou l’état de la ressource. Le coût est la complexité de conception et de test ; documentez les règles avant qu’elles ne deviennent implicites.

9. Exercice et critères de réussite

Concevez les règles d’une application de documents avec trois rôles : lecteur, éditeur et administrateur. Ajoutez la contrainte que les utilisateurs ne peuvent consulter que les documents de leur organisation. Décrivez la décision d’accès pour lire, modifier, supprimer et partager un document. Implémentez des tests couvrant les autorisations et les refus, notamment lorsqu’un utilisateur remplace l’identifiant dans l’URL.

  • Je distingue authentification et autorisation.
  • Je sais expliquer quand RBAC ou ABAC convient mieux.
  • Je vérifie les droits côté serveur sur chaque ressource sensible.
  • Je refuse par défaut si une condition d’autorisation n’est pas établie.
  • Je teste explicitement les accès croisés entre utilisateurs et organisations.

Atelier approfondi — Vérifier l’autorisation sur chaque ressource

Objectifs opérationnels

  • Construire une décision d’autorisation à partir de l’acteur, de l’action et de la ressource.
  • Choisir entre RBAC, ABAC ou une combinaison sans multiplier inutilement les règles.
  • Tester les refus, les frontières de tenant et les changements de privilège.

Explications et exemple guidé

RBAC attribue des permissions à des rôles : par exemple, un rôle « éditeur » peut modifier des documents. ABAC évalue des attributs de l’acteur, de la ressource et du contexte : l’utilisateur appartient-il au bon tenant, est-il propriétaire du document, le document est-il publié, l’action est-elle autorisée dans ce contexte ? Les deux approches peuvent se combiner, mais la décision doit rester compréhensible et testable.

function canReadDocument(user, doc) {
  if (!user || !doc || user.active !== true) return false;
  if (user.id == null || user.tenantId == null || doc.tenantId == null) return false;
  if (user.tenantId !== doc.tenantId) return false;

  const roles = Array.isArray(user.roles) ? user.roles : [];
  return roles.includes("admin") || doc.ownerId === user.id;
}

Cet exemple est volontairement simple : dans une application réelle, les attributs doivent provenir de sources fiables côté serveur, la politique doit couvrir toutes les actions et les règles d’administration doivent être définies séparément. Ne te contente pas de masquer un bouton dans l’interface. L’API doit refaire la vérification au moment de lire ou de modifier la ressource, car un client peut fabriquer une requête directe avec un identifiant différent.

Adopte le refus par défaut : une action n’est autorisée que si une règle explicite l’accorde. Écris des tests négatifs, notamment l’accès d’un utilisateur à la ressource d’un autre tenant, la modification d’un identifiant dans l’URL, la révocation d’un rôle et les actions sur une ressource supprimée ou en brouillon.

Pièges et limites

  • Confondre authentification (« qui est connecté ? ») et autorisation (« peut-il effectuer cette action sur cette ressource ? »).
  • Faire confiance à un rôle, un tenant ou un propriétaire envoyé par le navigateur.
  • Tester uniquement les accès autorisés et oublier les accès interdits.
  • Créer des rôles trop nombreux ou des règles ABAC implicites difficiles à auditer.

Exercice

Définis les permissions d’une application de documents pour lecteur, éditeur et administrateur. Ajoute la contrainte que chaque document appartient à un tenant. Écris une matrice acteur/action/ressource et au moins huit tests couvrant succès, refus, changement de rôle et tentative d’accès inter-tenant.

Critères de réussite

  • Les règles sont évaluées côté serveur à chaque opération sensible.
  • La politique combine rôle et attributs seulement lorsque le besoin le justifie.
  • Le refus par défaut et l’isolation des tenants sont testés explicitement.
  • Les tests montrent à la fois les accès attendus et les tentatives qui doivent échouer.

Matrice de tests : autoriser et refuser explicitement

Les exemples précédents supposent que l’utilisateur, ses rôles, ses permissions et les attributs de tenant sont construits par le serveur après authentification. Ne passe pas un objet envoyé par le navigateur directement à ces fonctions. La matrice suivante doit être traduite en tests d’API : chaque refus doit être vérifié en appelant l’endpoint, même si l’interface masque déjà l’action.
