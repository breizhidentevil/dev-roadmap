3. Backend

Redis et cache

Mettre en cache des données et comprendre les compromis de cohérence.

Tutoriel détailléLot 12 · 2026

Objectifs d’apprentissage

  • Expliquer où et pourquoi mettre en cache.
  • Comparer cache-aside et cache HTTP.
  • Choisir clés, TTL et règles d’invalidation.
  • Anticiper les données périmées, les pannes et les pics de charge.

1. Pourquoi mettre en cache

Un cache conserve temporairement une copie d’une donnée coûteuse à récupérer ou recalculer. Redis est un magasin en mémoire utilisé pour des valeurs clé/valeur, compteurs et structures de données. Le cache peut réduire la latence et la charge, mais ajoute un deuxième état à maintenir.

Ne mets en cache que si le gain est mesuré et si l’application sait fonctionner en cas d’absence, d’expiration ou d’indisponibilité du cache. La base de données reste généralement la source de vérité.

2. Modèle cache-aside

L’application lit d’abord le cache. Si la clé est absente, elle lit la source de vérité, place le résultat dans le cache avec une durée de vie (TTL), puis renvoie la donnée. Ce modèle est simple et largement utilisé.

Distingue une clé absente d’une valeur métier vide. Définis aussi ce que fait le backend si Redis échoue : selon le cas, il peut continuer sans cache, refuser la requête ou utiliser une dégradation contrôlée.

3. Clés, TTL et invalidation

Une clé doit inclure tous les paramètres qui changent le résultat : identifiant, langue, filtres, version de schéma et contexte de tenant ou de droits si nécessaire. Des clés trop générales peuvent mélanger des réponses appartenant à des utilisateurs différents.

Le TTL limite la durée de conservation, mais ne garantit pas une fraîcheur immédiate. Après une modification, choisis entre invalidation, mise à jour du cache ou acceptation d’un délai de cohérence. Documente cette décision par type de donnée.

4. Cache HTTP et cache applicatif

Le cache HTTP s’appuie notamment sur Cache-Control, ETag et les requêtes conditionnelles ; il peut éviter du travail dans le navigateur ou un CDN. Redis est souvent piloté par le backend pour stocker résultats métier, sessions ou compteurs.

N’autorise pas un cache partagé à conserver une réponse privée. Vérifie les directives de cache, Vary, l’authentification et les règles propres au contenu renvoyé.

5. Pannes et concurrence

Un cache stampede survient lorsque de nombreuses requêtes recalculent simultanément une valeur expirée. Selon le contexte, utilise coalescence des requêtes, verrou court ou variation aléatoire des TTL.

La mémoire est limitée : surveille les évictions, le taux de succès et la latence. Si le cache tombe en panne, la charge peut basculer brutalement sur la base ; prévois timeouts, limites et capacité de dégradation.

6. Étude de cas : cache périmé après une modification

Une route GET /products/42 lit une valeur cache-aside. Une route de mise à jour modifie ensuite le produit dans la base, mais l’ancienne valeur reste en cache. Définis explicitement la garantie attendue : une cohérence immédiate stricte, une cohérence éventuelle bornée par un TTL, ou une stratégie de rafraîchissement. Le cache ne devient pas automatiquement cohérent parce qu’il expire un jour.

async function getProduct(id) {
  const key = `product:v1:${id}`;
  const cached = await redis.get(key);
  if (cached !== null) return JSON.parse(cached);

  const product = await repository.findById(id);
  if (product !== null) {
    await redis.set(key, JSON.stringify(product), { EX: 60 });
  }
  return product;
}

async function updateProduct(id, patch) {
  const product = await repository.update(id, patch);
  await redis.del(`product:v1:${id}`);
  return product;
}

Cet exemple est illustratif : vérifie la syntaxe de ton client Redis et traite les erreurs de sérialisation, les valeurs absentes et l’indisponibilité du cache. L’invalidation après écriture réduit le risque de lecture périmée, mais ne supprime pas toutes les courses : une lecture lente peut récupérer l’ancienne valeur, puis la réécrire après l’invalidation. Pour les données sensibles ou les invariants financiers, le cache ne doit pas devenir la source d’autorité.

Risques de production

  • Clé incomplète : deux langues, tenants ou niveaux d’autorisation partagent une réponse. Intègre dans la clé chaque dimension qui change le résultat.
  • Cache stampede : une clé populaire expire et toutes les requêtes interrogent la base simultanément. Selon le besoin, étale les expirations, regroupe les lectures concurrentes ou utilise un verrou court avec prudence.
  • Cache poisoning : une entrée non fiable est mise en cache puis servie à d’autres utilisateurs. Valide la donnée et cloisonne les clés.
  • Panne Redis : une stratégie fail-open peut préserver la disponibilité mais surcharger la base ; fail-closed peut être nécessaire pour certains contrôles, mais pas pour toute donnée de confort.

Mesures : taux de hit/miss, latence du cache, erreurs, évictions, mémoire consommée et charge de la base. Une optimisation n’est validée qu’en comparant les mêmes scénarios avant/après. Le TTL est un compromis entre fraîcheur, mémoire et coût de recalcul, pas une valeur magique.

Critère de réussite : tu peux expliquer la politique d’invalidation, montrer le comportement en panne et prouver qu’une réponse ne traverse pas les frontières d’utilisateurs ou de tenants.

Erreurs fréquentes

  • Ajouter un cache sans mesurer le gain.
  • Ne pas définir d’invalidation.
  • Omettre le contexte utilisateur dans une clé.
  • Choisir un TTL arbitraire.
  • Traiter Redis comme source de vérité sans stratégie de persistance.

Exercice guidé

Pour une API de produits, propose des clés et TTL distincts pour la fiche produit et le stock. Décris ce qui se passe après un changement de prix et après une vente, puis précise le comportement si Redis devient indisponible.

Critères de réussite

source de vérité identifiée ; clés, TTL et invalidation justifiés ; aucune fuite entre utilisateurs ; panne et pics de requêtes traités ; métriques de latence, hit rate et mémoire prévues.
