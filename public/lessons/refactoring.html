6. Tests, débogage et qualité

Refactoring et maintenabilité

Améliorer la structure interne d’un code sans modifier son comportement observable.

Tutoriel approfondiQualité et tests

Objectifs et prérequis

Le refactoring consiste à modifier la structure interne du code tout en conservant son comportement observable. Il vise à rendre le code plus facile à comprendre, tester et faire évoluer. Ce n’est ni une réécriture complète, ni une occasion d’ajouter en même temps de nouvelles fonctionnalités.

  • Repérer un code difficile à maintenir à partir de symptômes concrets.
  • Procéder par transformations petites et vérifiables.
  • Utiliser les tests, la revue et le contrôle de version pour réduire le risque.

1. Quand refactorer ?

Des signes fréquents sont la duplication de règles métier, une fonction qui fait plusieurs choses, des noms vagues, des conditions imbriquées, des modules trop couplés ou des changements qui obligent à modifier de nombreux fichiers sans raison fonctionnelle claire. La présence d’un motif inhabituel ne suffit pas : le coût de compréhension et de modification doit être réel.

Le bon moment est souvent juste avant ou après une modification fonctionnelle, lorsque la zone est déjà comprise. Si le code est stable, peu modifié et bien isolé, une refonte esthétique peut coûter plus qu’elle ne rapporte. Le refactoring doit servir un besoin de maintenance, pas la recherche abstraite d’une architecture parfaite.

2. Séparer comportement et structure

Avant de commencer, définis le comportement à préserver. Ajoute ou vérifie des tests qui couvrent les cas importants. Ensuite, fais une petite transformation, lance les tests et inspecte le diff. Cette boucle courte permet d’identifier rapidement la modification responsable d’une régression.

Exemple : si une fonction calcule un prix, vérifie d’abord les remises, les montants nuls et les entrées invalides. Extraire une partie du calcul dans une fonction nommée peut améliorer la lisibilité, mais la nouvelle fonction doit conserver les mêmes règles d’arrondi et de validation.

// Avant : une expression métier noyée dans le traitement
const finalPrice = price - price * discount;

// Après : une règle nommée, testable séparément
function applyDiscount(price: number, discount: number) {
  return price - price * discount;
}
const finalPrice = applyDiscount(price, discount);

Cet exemple n’est volontairement qu’une extraction minimale : en code réel, documente les contraintes, notamment les bornes de remise et la représentation des montants. Un simple déplacement de code n’améliore pas automatiquement la conception si le nom ou la responsabilité reste flou.

3. Techniques courantes

  • Extraire une fonction : donner un nom à un bloc cohérent et réduire la complexité locale.
  • Renommer : exprimer l’intention métier plutôt que le mécanisme d’implémentation.
  • Remplacer un nombre magique par une constante nommée : clarifier une règle et éviter les incohérences.
  • Réduire la duplication : centraliser une règle réellement commune, sans créer une abstraction prématurée.
  • Déplacer une responsabilité : rapprocher une règle des données ou du module qui en est responsable.
  • Remplacer des conditions complexes par des fonctions explicites : rendre les décisions métier lisibles et testables.

Choisis la transformation la plus petite qui améliore la compréhension. Un refactoring ne nécessite pas toujours un nouveau patron de conception ou une couche supplémentaire.

4. Maîtriser le risque et la portée

Les changements de structure peuvent casser des contrats implicites : ordre des effets secondaires, gestion des exceptions, transactions, timing asynchrone ou compatibilité des données sérialisées. Les tests ne couvrent pas nécessairement tout ; la revue de code et la vérification des appels externes restent nécessaires.

Évite de mélanger dans un même diff un renommage massif, un changement d’architecture, une mise à jour de dépendances et une nouvelle fonctionnalité. Des changements petits, cohérents et réversibles sont plus faciles à relire. Si une modification doit changer le comportement, sépare-la clairement du refactoring pur.

Pour une API publique, un changement de nom interne peut être sans conséquence, alors qu’un changement de signature, de format ou de sémantique est une évolution du contrat. Dans ce cas, documente la compatibilité et prévois une migration plutôt que de présenter le changement comme un simple nettoyage.

5. Refactoring guidé par les symptômes

Une fonction trop longue n’est pas toujours mauvaise si elle décrit un processus linéaire et clair. À l’inverse, une fonction courte peut être difficile à comprendre si elle déclenche des effets cachés. Évalue la cohésion, le nommage, la duplication réelle, la stabilité des règles et la facilité des tests.

Une bonne abstraction capture une règle qui a du sens pour le domaine. Une mauvaise abstraction rassemble des éléments qui se ressemblent aujourd’hui mais évolueront différemment. Si deux morceaux de code ne changent pas pour les mêmes raisons, les forcer dans une seule fonction générique peut rendre les futurs changements plus complexes.

Mesure également les compromis : une abstraction peut améliorer les tests mais ajouter une indirection ; un module peut réduire le couplage mais introduire une interface trop générale ; une optimisation peut accélérer un chemin mais diminuer la lisibilité. La maintenabilité est un équilibre, pas une quantité directement mesurable par le nombre de lignes.

6. Utiliser des étapes petites et réversibles

Un refactoring sûr forme une séquence de transformations dont chacune conserve le comportement observable. Avant de commencer, identifie les entrées, sorties, effets secondaires et invariants de la zone. Lance les tests de référence, puis effectue une seule transformation et relance les tests ciblés. Termine par la suite complète, le lint et le contrôle de types quand ils existent.

  1. Ajouter ou préciser un test pour le comportement qui doit rester stable.
  2. Extraire une fonction sans changer son contrat.
  3. Renommer les concepts pour refléter leur responsabilité.
  4. Éliminer la duplication uniquement si les règles métier sont réellement identiques.
  5. Comparer le diff et vérifier les appels externes, les permissions et les transactions.

Si une étape échoue, annule-la ou corrige-la avant d’empiler d’autres changements. Un refactoring n’est pas une occasion de modifier en même temps la règle métier, le format d’API, les dépendances et le style. Si le changement de comportement est nécessaire, formule-le explicitement et couvre-le par des tests distincts.

Signaux à mesurer

Le nombre de lignes n’est pas un indicateur de qualité suffisant. Observe plutôt la facilité à nommer les responsabilités, le nombre de chemins conditionnels, le couplage, la duplication des règles métier et la capacité des tests à isoler un échec. Ne crée pas d’abstraction générique pour une seule occurrence hypothétique.

Erreurs fréquentes

  • Réécrire un module entier sans tests ni étapes intermédiaires.
  • Changer le comportement et la structure dans le même diff sans les distinguer.
  • Créer une abstraction générique avant d’avoir plusieurs cas réellement similaires.
  • Extraire des fonctions dont les noms n’expriment pas une intention claire.
  • Supprimer une duplication qui correspond en réalité à deux règles différentes.
  • Considérer une suite de tests verte comme une preuve absolue d’absence de régression.

Exercice guidé

Choisis une fonction de ton projet qui combine validation, calcul et formatage. Écris d’abord quelques tests sur son comportement actuel. Puis effectue une seule transformation : extraire la validation ou renommer une règle ambiguë. Lance les tests et examine le diff avant de poursuivre.

Explique en quelques lignes quel coût de maintenance cette transformation réduit et quel coût elle introduit éventuellement. Si tu ne peux pas nommer le bénéfice, annule la modification.

Exercice autonome et critères de réussite

Identifie une zone du code qui évolue souvent ou génère des bugs. Prépare un plan de refactoring en étapes petites, avec les tests qui sécurisent chacune d’elles. Sépare les modifications structurelles des changements fonctionnels.

Réussite : le comportement attendu est documenté par des tests ; chaque étape reste petite et réversible ; les responsabilités et les noms deviennent plus explicites ; le diff est relisible ; les compromis sont identifiés ; les tests et la revue sont réalisés avant fusion.
