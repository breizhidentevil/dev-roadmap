0. Informatique générale et fonctionnement des systèmes

Réseaux : TCP/IP, ports et pare-feu

Comprendre les échanges réseau et les principaux mécanismes de transport.

Tutoriel complet · Niveau intermédiaireDurée indicative : 2 h

Objectifs pédagogiques

  • Distinguer adressage IP, ports et protocoles de transport.
  • Décrire l’établissement d’une connexion TCP et la résolution de noms.
  • Diagnostiquer les problèmes réseau avec des outils adaptés.

1. Les couches réseau

Une application s’appuie sur plusieurs couches. IP permet d’acheminer des paquets entre réseaux ; TCP fournit un flux d’octets fiable et ordonné ; UDP transporte des datagrammes sans garantir la livraison ou l’ordre. Au-dessus, des protocoles comme HTTP définissent les échanges applicatifs.

Les couches sont un modèle utile pour localiser une panne. Une erreur HTTP 500 est différente d’un échec DNS, d’un refus de connexion TCP ou d’une absence de route IP.

2. Adresses IP et ports

Une adresse IP identifie une interface réseau dans un contexte d’acheminement. Un port identifie un point d’extrémité de transport sur une machine. Une connexion TCP est habituellement identifiée par le protocole et les deux couples adresse/port source et destination. Le port 443 est conventionnellement associé à HTTPS, mais le numéro seul ne prouve pas que le service parle réellement ce protocole.

Les adresses privées IPv4 ne sont pas directement routées sur l’Internet public. Les routeurs domestiques utilisent souvent le NAT pour permettre à plusieurs appareils de partager une adresse publique.

3. Ce que TCP garantit

TCP établit une connexion, numérote les octets, retransmet les segments perdus et remet les données dans l’ordre au destinataire. Le « three-way handshake » synchronise les deux extrémités avant le transfert. TCP ne garantit pas que l’application distante traitera la demande, ni que l’opération métier sera exécutée une seule fois : ces garanties appartiennent à d’autres couches.

Une coupure après l’envoi d’une requête peut laisser le client incertain du résultat. Pour les opérations sensibles, prévoyez une stratégie d’idempotence et de reprise au niveau applicatif.

4. DNS et diagnostic

DNS associe des noms de domaine à des informations, notamment des adresses IP. Une résolution peut échouer même si le serveur est en ligne. Les caches DNS, le TTL et les différents résolveurs expliquent pourquoi un changement ne se propage pas instantanément partout.

getent hosts example.com
nslookup example.com
curl -v https://example.com
ss -lnt
ip route

Ces outils ne répondent pas tous à la même question : la résolution vérifie le nom, curl -v détaille la requête HTTP/TLS, ss liste les sockets et ip route affiche les routes connues. La disponibilité de certaines commandes dépend de la distribution.

5. Pare-feu, proxy et TLS

Un pare-feu peut filtrer les connexions selon les adresses, ports ou états. Un proxy relaie les requêtes et peut appliquer des règles, mettre en cache ou terminer TLS. HTTPS utilise TLS pour protéger la confidentialité et l’intégrité du transport et authentifier le serveur selon la validation du certificat.

Un certificat valide ne prouve pas que l’application est exempte de vulnérabilités. Il faut aussi contrôler les autorisations, les entrées, les dépendances et la configuration du service.

6. Exercice

Diagnostiquez une API inaccessible à partir de quatre hypothèses : nom non résolu, port fermé, négociation TLS échouée ou réponse HTTP d’erreur. Pour chacune, choisissez une commande et indiquez ce que son résultat permet de conclure — et ce qu’il ne permet pas de conclure.

Critères de réussite

  • Vous distinguez DNS, transport et protocole applicatif.
  • Vous comprenez les garanties et limites de TCP.
  • Vous choisissez des outils qui isolent les couches du problème.
  • Vous ne confondez pas HTTPS avec la sécurité complète de l’application.

7. Arbre de diagnostic réseau

Un diagnostic efficace teste une couche à la fois. Si le nom ne se résout pas, examine DNS avant de chercher un problème HTTP. Si l’adresse est connue mais que la connexion échoue, vérifie la route, le pare-feu, le port d’écoute et l’accessibilité depuis le bon réseau. Si la connexion aboutit mais que le serveur renvoie une erreur HTTP, le transport fonctionne au moins suffisamment pour échanger une réponse : inspecte alors le protocole applicatif, les logs et le comportement du service.

# Résolution de nom
getent hosts example.com

# Connectivité IP (les ICMP peuvent être filtrés)
ping -c 4 example.com

# Tester la négociation HTTPS et la réponse HTTP
curl -I --connect-timeout 5 https://example.com

Ces commandes ont des limites. Un ping qui échoue ne prouve pas que le site est indisponible, car ICMP peut être bloqué. Une résolution réussie ne garantit pas que le port est joignable. Une requête curl -I envoie une requête HEAD ; certains serveurs la traitent différemment d’un GET. Utilise plusieurs indices et note précisément depuis quelle machine et quel réseau le test est lancé.

TCP garantit un flux d’octets fiable et ordonné tant que la connexion reste utilisable ; il ne préserve pas les frontières des messages applicatifs. Une lecture peut recevoir une partie d’un message ou plusieurs messages selon le protocole utilisé. L’application doit donc définir le cadrage des messages. TCP ne garantit pas non plus que le serveur a terminé une opération métier quand le client perd la connexion.

Enfin, le chiffrement TLS protège le canal mais ne corrige pas les autorisations, les validations d’entrée ou les défauts métier. Une API accessible en HTTPS peut toujours exposer des données si ses contrôles d’accès sont incorrects.
