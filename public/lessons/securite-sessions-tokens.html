5. Sécurité applicative

Sécurisation des sessions et tokens

Réduire les risques de vol, fuite et réutilisation de credentials.

Tutoriel approfondiSécurité applicative

Objectifs d’apprentissage

À la fin de cette leçon, tu dois pouvoir comparer une session côté serveur et un token autonome, configurer des cookies de session sûrs, gérer expiration et révocation, et identifier les fuites de jetons les plus courantes.

  • Comprendre qu’un identifiant de session est un secret porteur d’autorité.
  • Choisir un emplacement de stockage cohérent avec le modèle de menace.
  • Définir les règles de durée de vie, rotation, invalidation et renouvellement.

1. Session et token : deux modèles différents

Dans un modèle à session, le navigateur détient un identifiant opaque ; le serveur conserve l’état de la session et peut généralement l’invalider immédiatement. Dans un modèle JWT, le token transporte des claims signés que le destinataire vérifie. La signature garantit l’intégrité, pas la confidentialité : le contenu d’un JWT classique est lisible par celui qui le possède.

Un JWT n’est pas automatiquement plus sûr ni plus simple. La révocation anticipée demande une stratégie supplémentaire (durée courte, liste de révocation, version de session ou rotation de clés). Pour une application Web classique, une session serveur avec cookie bien configuré est souvent une solution simple et contrôlable.

2. Cookies de session

Un cookie de session sensible devrait généralement être marqué Secure pour ne circuler qu’en HTTPS, HttpOnly pour empêcher sa lecture directe par JavaScript, et SameSite selon le besoin d’usage cross-site. L’attribut Path limite l’envoi sur certains chemins, mais ne constitue pas une frontière de sécurité forte. Évite l’attribut Domain s’il n’est pas nécessaire, afin de réduire les sous-domaines qui reçoivent le cookie.

Set-Cookie: session=VALEUR_OPAQUE; Path=/; Secure; HttpOnly; SameSite=Lax

La valeur affichée est illustrative. Le serveur doit générer un identifiant imprévisible, suffisamment robuste, et ne jamais le construire à partir d’informations personnelles prévisibles.

3. Cycle de vie et invalidation

  1. Créer une nouvelle session après une authentification réussie.
  2. Renouveler l’identifiant après une élévation de privilèges ou une connexion, pour prévenir la fixation de session.
  3. Définir une expiration d’inactivité et une durée de vie absolue adaptées au risque.
  4. Invalider côté serveur lors de la déconnexion, du changement de mot de passe ou d’un événement de sécurité pertinent.
  5. Protéger les opérations sensibles avec une nouvelle vérification ou une authentification renforcée si nécessaire.

Effacer le cookie côté navigateur ne suffit pas si le serveur accepte encore l’identifiant. L’invalidation doit être effective dans le stockage de sessions.

4. Stockage des tokens et risques de fuite

Un token volé peut être utilisé comme un mot de passe temporaire. Les sources de fuite incluent les journaux, les URL, les captures d’écran, les erreurs de télémétrie, les dépôts Git et le stockage accessible au JavaScript compromis. Évite de placer des tokens dans les paramètres d’URL : ils peuvent se retrouver dans l’historique, les logs de serveurs ou l’en-tête Referer.

localStorage est accessible au JavaScript de la page ; une faille XSS peut donc exposer les tokens qui y sont stockés. Un cookie HttpOnly réduit ce risque d’exfiltration directe, mais n’empêche pas un script malveillant d’émettre des requêtes au nom de l’utilisateur. Il faut donc aussi traiter XSS, CSRF et les permissions serveur.

5. JWT : validation rigoureuse

Lorsqu’un JWT est utilisé, le serveur doit valider la signature avec une liste d’algorithmes autorisés, ainsi que les claims nécessaires au contexte : émetteur (iss), audience (aud), expiration (exp) et éventuellement sujet (sub). Ne fais jamais confiance aux claims avant validation cryptographique. Ne choisis pas l’algorithme uniquement à partir de l’en-tête non fiable du token.

Utilise une bibliothèque reconnue, garde les clés hors du code, prévois leur rotation et limite la durée de vie des access tokens. Les refresh tokens méritent une protection accrue, une rotation contrôlée et une détection de réutilisation lorsque le système le permet.

Vérifier le cycle de vie complet

La sécurité d’une session se joue sur toute sa durée : création après authentification, renouvellement après changement de privilège, expiration, déconnexion et révocation après incident. Régénère l’identifiant de session après connexion ou élévation de privilège afin de réduire le risque de fixation. La déconnexion doit invalider la session côté serveur lorsque le modèle repose sur une session serveur.

Pour un JWT, vérifier uniquement la signature ne suffit pas. Le serveur doit imposer l’algorithme attendu et valider au minimum l’émetteur, l’audience, l’expiration et les claims nécessaires au contexte. Ne fais pas confiance à des claims de rôle obsolètes si le besoin métier exige une révocation rapide. Les tokens de renouvellement devraient être protégés, rotés et détecter les réutilisations selon le modèle choisi.

  • Tester cookie absent, expiré, altéré, mal signé et audience incorrecte.
  • Vérifier les attributs Secure, HttpOnly et SameSite sur les cookies concernés.
  • Documenter la durée de vie, la révocation, la rotation et la réponse à un token compromis.

Le stockage dans localStorage expose les tokens aux scripts exécutés dans l’origine ; un cookie HttpOnly réduit l’accès direct depuis JavaScript mais nécessite d’analyser le risque CSRF.

6. Renouvellement et protection CSRF

Si le système utilise des refresh tokens, traite-les comme des secrets à usage contrôlé. Un modèle courant conserve côté serveur une empreinte du token, associe les renouvellements à une même famille et remplace le token à chaque utilisation réussie. Le remplacement doit être atomique : deux demandes concurrentes ne doivent pas pouvoir consommer le même token sans détection. Si un ancien token réapparaît après rotation, considère cela comme un possible rejeu et révoque la famille concernée selon la politique documentée.

  1. Valider le token, son expiration et son association au compte/session.
  2. Marquer l’ancien token comme consommé et enregistrer le nouveau de façon atomique.
  3. Ne jamais journaliser les valeurs des tokens ; journaliser seulement un identifiant technique non secret et le résultat.
  4. Définir une réponse au vol ou à la réutilisation : révocation, nouvelle authentification et notification adaptée au risque.

Si l’authentification repose sur un cookie automatiquement envoyé par le navigateur, SameSite est une défense en profondeur, pas une justification pour ignorer CSRF. Pour les opérations qui modifient l’état, évalue un jeton CSRF et la vérification de l’en-tête Origin (ou une stratégie équivalente adaptée à l’application). Avec un bearer token explicitement ajouté à l’en-tête Authorization, le risque CSRF classique est différent, mais le risque XSS et le vol du token restent présents.

Exercice : simule deux renouvellements avec le même refresh token. Le premier doit réussir ; le second doit déclencher le comportement anti-rejeu défini, sans créer deux sessions actives. Vérifie aussi qu’une requête de modification cross-site sans preuve CSRF est refusée lorsque le modèle cookie l’exige.

Erreurs fréquentes

  • Considérer un JWT signé comme chiffré.
  • Oublier la rotation de session après la connexion.
  • Confondre expiration du cookie et invalidation côté serveur.
  • Stocker un token dans une URL ou le journaliser.
  • Accepter un JWT sans vérifier audience, expiration et algorithme.
  • Penser que HttpOnly suffit contre toutes les conséquences d’une XSS.

Exercice guidé

Sur une application de test, inspecte le cookie de session dans les outils développeur. Vérifie ses attributs, sa rotation à la connexion, sa disparition après déconnexion et le refus de réutilisation de l’ancien identifiant. N’utilise jamais un compte ou token de production pour cet exercice.

Si l’application utilise des JWT, écris une liste de vérifications serveur et teste un token expiré, une audience incorrecte et une signature invalide.

Exercice autonome et critères de réussite

Rédige une courte politique de sessions pour une application contenant des données privées : modèle choisi, attributs cookie, durée d’inactivité, durée absolue, événements d’invalidation et traitement du renouvellement.

Réussite : le choix session/JWT est justifié ; les secrets ne sont pas placés dans les URL ni dans les logs ; les identifiants sont imprévisibles et renouvelés au bon moment ; la déconnexion invalide réellement la session ; les tokens sont validés strictement ; les risques CSRF et XSS sont traités séparément.
