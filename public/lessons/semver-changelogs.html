Versionnement sémantique et changelogs

Le versionnement sémantique et le changelog aident les utilisateurs d’une bibliothèque ou d’un service à comprendre le risque associé à une mise à jour. Le numéro de version ne remplace pas des tests de compatibilité, mais il fournit un contrat de communication. Une version doit refléter les changements réellement livrés ; un changelog doit permettre de repérer les nouveautés, corrections, suppressions et migrations nécessaires sans parcourir chaque commit.

Objectifs pédagogiques

  • Appliquer les règles MAJOR, MINOR et PATCH dans un contexte de versions stables.
  • Identifier les changements incompatibles, compatibles et correctifs.
  • Maintenir un changelog lisible, orienté utilisateur et lié aux versions publiées.
  • Comprendre les limites de SemVer pour les versions initiales et les dépendances.

Prérequis

Connaître les bases du HTML, du CSS et du JavaScript, savoir inspecter une page dans les outils de développement du navigateur et pouvoir modifier un exemple simple. Les notions propres à ce sujet sont introduites progressivement. Il n’est pas nécessaire de maîtriser tous les outils cités avant de commencer.

1. Lire MAJOR.MINOR.PATCH

SemVer représente une version stable sous la forme `MAJOR.MINOR.PATCH`, par exemple `3.4.2`. PATCH augmente pour une correction compatible avec l’API publique. MINOR augmente lorsqu’une fonctionnalité compatible est ajoutée ; PATCH revient alors à zéro. MAJOR augmente lorsqu’un changement incompatible est introduit ; MINOR et PATCH reviennent à zéro. Cette logique suppose que le projet définit clairement son API publique et respecte la compatibilité annoncée.

Une correction n’est pas automatiquement un PATCH si elle change un comportement sur lequel les utilisateurs s’appuyaient, même si ce comportement était considéré comme un bug. La compatibilité dépend du contrat public, des usages réels et parfois des comportements documentés. Les changements de schéma, signatures, types exportés, formats de configuration et effets secondaires peuvent être incompatibles sans modifier une simple fonction exportée.

2. Définir ce qui est public

Avant d’appliquer SemVer, déterminez ce qui constitue l’API publique : fonctions exportées, commandes CLI, variables de configuration, événements, formats de données, schémas, interfaces TypeScript ou comportements documentés. Un détail interne peut devenir de facto public s’il est utilisé et observé par les consommateurs ; c’est une raison de garder une frontière explicite entre API stable et implémentation privée.

L’ajout d’une fonction facultative est souvent compatible, mais pas toujours : il peut créer une ambiguïté dans une surcharge, changer l’inférence de types ou introduire un conflit de nom. Un changement de valeur par défaut peut être incompatible même si aucune signature ne change. Analysez le contrat de bout en bout et testez des exemples de consommateurs existants, pas seulement les tests internes de la bibliothèque.

3. Préversions et dépendances

Les suffixes de préversion, comme `-alpha.1`, `-beta.2` ou `-rc.1`, signalent un état qui ne doit pas être interprété comme une version stable ordinaire. Leur comparaison suit des règles précises ; les scripts ne devraient pas trier les versions en comparant simplement des chaînes. Les plages SemVer des gestionnaires de paquets expriment une politique de sélection, mais elles ne garantissent pas que chaque publication respecte réellement la compatibilité annoncée.

Pour une application, verrouillez les dépendances de façon reproductible et testez les mises à jour dans une intégration continue. Pour une bibliothèque, vérifiez le comportement attendu avec les versions prises en charge et documentez les changements de dépendances. Les versions `0.y.z` sont généralement considérées comme initiales et peuvent évoluer plus librement selon la spécification ; ne promettez pas le même niveau de stabilité qu’une API mature sans l’avoir défini.

4. Écrire un changelog utile

Un changelog est destiné aux personnes qui doivent comprendre ce qui change entre deux versions. Regroupez les entrées par version et par catégorie : nouveautés, modifications, corrections, dépréciations et changements incompatibles. Une entrée utile décrit l’effet observable, pas uniquement le nom du fichier modifié. « Corrige l’erreur lors d’une réponse 204 sans corps » aide davantage qu’un message de commit comme « fix response handler ».

Mentionnez les migrations, les changements de configuration, les versions minimales requises et les comportements supprimés. Si une entrée concerne une correction de sécurité, suivez la politique de divulgation du projet et ne publiez pas prématurément des détails exploitables. Un changelog n’a pas besoin de contenir tous les détails de développement : reliez les discussions techniques, commits ou notes de publication lorsqu’ils sont utiles.

5. Automatiser la publication sans perdre le contrôle

Un processus de release fiable vérifie les tests, construit les artefacts, confirme la version et publie des notes cohérentes. Automatisez les tâches répétitives, mais protégez les secrets de publication et vérifiez le contenu réellement envoyé au registre. Un tag Git, une version dans `package.json`, un changelog et une release doivent correspondre. Toute divergence rend le diagnostic et la reproduction plus difficiles.

Avant une version majeure, fournissez un guide de migration avec les remplacements recommandés et les changements de comportement. Avant une version mineure, vérifiez que l’ajout est réellement compatible avec les consommateurs pris en charge. Après publication, surveillez les erreurs et préparez une stratégie de correction ou de retrait. Le numéro de version est une promesse de communication ; il n’est fiable que si le processus et les tests soutiennent cette promesse.

Exemple pratique

Le fragment suivant illustre une décision de conception à tester dans le contexte complet du produit.

{
  "name": "@exemple/format-date",
  "version": "2.3.1"
}

Changelog
## [2.3.1] - 2026-10-09
### Corrigé
- Gère les dates invalides sans lever d'exception non documentée.

## [2.3.0] - 2026-10-01
### Ajouté
- Ajoute l'option `locale` compatible avec les appels existants.

La version 2.3.1 décrit une correction compatible ; la version 2.3.0 ajoute une option sans casser les appels existants. Dans un vrai package, validez que les dates invalides suivent bien le contrat documenté et que l’option possède une valeur par défaut compatible. Les dates de publication doivent correspondre à l’historique réel de la release.

Pièges fréquents et compromis

  • Augmenter PATCH pour un changement qui casse un contrat public.
  • Considérer tout ajout comme compatible sans tester les consommateurs.
  • Rédiger un changelog composé uniquement de messages de commit internes.
  • Oublier les étapes de migration d’une version majeure.
  • Publier des artefacts dont la version diffère du tag ou du changelog.

Une recommandation générale est un point de départ, pas une preuve de qualité. Vérifiez le parcours complet, les états moins fréquents et les contraintes du produit avant de conclure qu’une solution est appropriée.

Exercice pratique

Prenez cinq changements fictifs : correction d’une exception, ajout d’une option facultative, suppression d’un paramètre, modification d’une valeur par défaut et dépréciation d’une fonction. Classez chacun en PATCH, MINOR ou MAJOR selon le contrat défini, justifiez chaque choix puis rédigez un changelog compréhensible par un utilisateur de la bibliothèque.

Critères de réussite

  • La règle de version est justifiée par le contrat public.
  • Les préversions ne sont pas traitées comme des versions stables.
  • Le changelog décrit les effets observables.
  • Les incompatibilités et migrations sont clairement signalées.
  • La release, le tag et les métadonnées du package restent cohérents.

Considérez l’exercice terminé lorsque chaque critère peut être démontré avec un exemple reproductible. Expliquez vos choix, les tests réalisés et les limites restantes ; l’absence d’erreur visible ne suffit pas à prouver qu’une interface est accessible, compréhensible ou rapide.

Atelier approfondi — seconde passe

Objectifs opérationnels

  • Classer une modification publique en MAJOR, MINOR ou PATCH selon le contrat annoncé.
  • Rédiger un changelog orienté vers les utilisateurs et les migrations nécessaires.
  • Distinguer une version stable d’une préversion et contrôler ce qui sera effectivement publié.

Explications et méthode

SemVer s’applique à une API publique déclarée. PATCH corrige sans casser la compatibilité, MINOR ajoute une capacité compatible et MAJOR indique une rupture incompatible. Cette règle n’évalue pas automatiquement le risque : elle dépend de la définition explicite du contrat public et des comportements garantis.

Un changelog doit expliquer les changements visibles, leurs effets et les actions nécessaires. Il ne devrait pas être une simple liste de messages de commits. Les modifications internes sans effet utilisateur peuvent rester dans les notes de développement, tandis qu’une dépréciation doit annoncer le calendrier et l’alternative.

Les préversions comme 2.0.0-beta.1 servent à tester un changement avant la version stable. L’automatisation peut proposer une version, mais la décision doit être cohérente avec les changements réels, les tests de compatibilité et la politique de support.

Exemple commenté

## [2.4.0] - 2026-10-10
### Added
- Ajout de `searchProducts({ cursor })` pour parcourir les résultats.
### Fixed
- Correction du traitement des réponses vides.
### Migration
- Aucun changement requis pour les appels existants.

# Exemple de règle de décision
# Nouvelle fonction compatible -> MINOR
# Correction compatible -> PATCH
# Suppression/changement incompatible d’une API stable -> MAJOR

Pièges à éviter

  • Incrémenter automatiquement PATCH pour une modification qui change en réalité un contrat public.
  • Présenter un ajout comme compatible sans tester les comportements existants ou les types exportés.
  • Publier un changelog qui ne dit ni qui est affecté ni comment migrer.

Exercice d’application

À partir de cinq changements proposés sur une bibliothèque TypeScript, classe chaque changement, justifie la version attendue et rédige les sections Added, Changed, Fixed, Deprecated ou Removed pertinentes. Ajoute une note de migration pour tout changement incompatible.

Critères de réussite

  • Chaque numéro de version est justifié par rapport à l’API publique et à la compatibilité.
  • Le changelog décrit les effets observables plutôt que de recopier uniquement les commits.
  • Les préversions, dépréciations et instructions de migration sont explicites quand elles s’appliquent.
