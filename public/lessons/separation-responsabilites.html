Séparation des responsabilités

Séparer les responsabilités consiste à donner à chaque module une raison claire de changer. L’objectif n’est pas de multiplier les fichiers, mais de rendre les règles compréhensibles, testables et modifiables sans effets de bord inutiles.

Objectifs et prérequis

Une application web doit recevoir une requête, vérifier les entrées, appliquer les règles du domaine, lire ou écrire des données et produire une réponse. Si toute cette logique est concentrée dans un seul contrôleur, chaque évolution devient risquée. À l’inverse, une architecture fragmentée en dizaines de classes minuscules peut compliquer la navigation sans améliorer la conception.

  • Identifier les responsabilités de l’interface, de l’application, du domaine et de l’infrastructure.
  • Réduire le couplage entre règles métier et détails techniques.
  • Utiliser des interfaces lorsqu’elles apportent une frontière utile.
  • Tester les règles métier sans démarrer un serveur ni une base de données.

1. Une responsabilité est une raison de changer

Considérez un endpoint qui crée une commande. Il parse le JSON, vérifie les champs, calcule les remises, vérifie le stock, écrit plusieurs lignes SQL, envoie un courriel et construit la réponse HTTP. Il rassemble des décisions qui évoluent pour des raisons différentes : contrat d’API, politique commerciale, schéma de données et fournisseur de messagerie.

La séparation consiste à placer chaque décision à l’endroit où elle est la plus compréhensible. Le contrôleur adapte HTTP à l’application ; le service applicatif orchestre le cas d’usage ; le domaine exprime les invariants métier ; les adaptateurs techniques réalisent les accès à la base et aux services externes.

Ces couches sont un moyen, pas une loi universelle. Pour un petit CRUD, une structure simple avec peu de fichiers peut être préférable. La question utile est : « cette modification métier peut-elle être comprise et testée sans modifier des détails techniques sans rapport ? »

2. Une répartition concrète

  1. Transport / contrôleur : lit la requête, applique les contrôles de format, appelle le cas d’usage et traduit le résultat en code HTTP.
  2. Application : coordonne le scénario, définit les frontières de transaction et appelle les ports nécessaires.
  3. Domaine : contient les règles et invariants indépendants du framework, par exemple interdire une commande vide ou calculer une remise autorisée.
  4. Infrastructure : implémente les accès SQL, l’envoi d’e-mails, le cache ou les appels externes.

Exemple de flux : POST /orders → contrôleur → CreateOrder → règle métier de commande → interface OrderRepository → implémentation PostgreSQL → résultat → réponse HTTP. Le domaine n’a pas besoin de connaître Express, Spring, HTTP ou le pilote SQL.

La validation se fait à plusieurs niveaux : validation de forme à l’entrée, puis vérification des invariants au niveau métier. Un champ numérique valide peut malgré tout être illégal dans le domaine : une quantité doit être positive, une commande clôturée ne doit pas être modifiée, etc.

3. Dépendances orientées vers les règles

Un module de règles métier ne devrait généralement pas dépendre directement d’un framework web ou d’un pilote de base de données. Il peut définir une interface minimale dont l’implémentation se trouve dans l’infrastructure. L’application reçoit cette dépendance par construction ou par injection.

interface OrderRepository {
  save(order: Order): Promise;
}

class CreateOrder {
  constructor(private orders: OrderRepository) {}

  async execute(input: CreateOrderInput): Promise {
    const order = Order.create(input.items);
    await this.orders.save(order);
    return order.id;
  }
}

Exemple pédagogique en TypeScript : les types Order, OrderId et CreateOrderInput sont ici supposés définis. Le code illustre la frontière, pas une implémentation complète : une vraie commande doit traiter la concurrence, les transactions et les erreurs métier appropriées.

Une interface est utile lorsqu’elle exprime un contrat stable ou permet de remplacer un adaptateur. Créer une interface pour chaque classe sans besoin réel peut ajouter du bruit. Il n’est pas nécessaire d’abstraire chaque fonction pure.

4. Tester au bon niveau

Les tests unitaires du domaine vérifient les règles avec des données en mémoire et sans infrastructure. Les tests d’application vérifient l’orchestration à l’aide de dépendances contrôlées. Les tests d’intégration valident que l’adaptateur SQL respecte le contrat du dépôt, que les transactions fonctionnent et que les contraintes de base sont effectives. Les tests HTTP vérifient le contrat exposé au client.

Ne simulez pas tout : un test avec un faux dépôt ne prouve pas qu’une requête SQL fonctionne. À l’inverse, il n’est pas nécessaire de lancer une base de données pour vérifier qu’une remise de 10 % est calculée correctement.

Les erreurs doivent aussi franchir les frontières de manière explicite. Le domaine peut produire une erreur métier ; le contrôleur la traduit en réponse appropriée sans exposer la pile technique au client. Les journaux internes doivent conserver suffisamment de contexte pour diagnostiquer le problème sans enregistrer de secrets.

5. Signes de mauvaise séparation

  • Contrôleur obèse : règles métier, SQL et appels externes s’accumulent dans la même méthode.
  • Modèle anémique : les objets ne portent aucune règle et toute la logique est dispersée dans des services sans cohésion.
  • Abstraction prématurée : plusieurs couches ou interfaces sont créées avant d’avoir un besoin de variation ou de test identifiable.
  • Fuite du framework : des objets de requête HTTP ou des annotations ORM envahissent le cœur métier sans nécessité.
  • Transaction mal placée : plusieurs écritures doivent être atomiques, mais sont exécutées dans des fonctions indépendantes sans coordination.
  • Duplication de validation : la même règle est copiée dans le front-end, le contrôleur et plusieurs services ; les contrôles d’interface améliorent l’expérience, mais le serveur reste l’autorité.

La qualité se mesure à la facilité de raisonner sur une modification, au caractère local des tests et à la clarté des dépendances, pas au nombre de couches.

Exercice guidé

Refactorisez mentalement un endpoint POST /users qui vérifie le format d’un e-mail, refuse les doublons, enregistre l’utilisateur et envoie un message de bienvenue.

  1. Quelles vérifications relèvent du format d’entrée et lesquelles relèvent du domaine ?
  2. Quel module orchestre l’enregistrement et l’envoi ?
  3. Comment empêcher qu’un échec d’e-mail crée un état incohérent ?
  4. Quels tests peuvent rester unitaires et lesquels nécessitent une base réelle ?
  5. Quelles informations ne doivent jamais apparaître dans une réponse d’erreur publique ?

Critères de réussite : vous proposez des frontières cohérentes, évitez la dépendance directe du domaine au framework, distinguez tests unitaires et d’intégration et identifiez les questions de transaction et d’effets secondaires.

Atelier de validation : séparer sans disperser

La séparation des responsabilités doit réduire les raisons de changer et rendre les tests plus précis. Elle ne signifie pas qu’il faut créer une classe ou une interface pour chaque fonction.

Exemple : appliquer une remise

type Ligne = { prixUnitaire: number; quantite: number };
function calculerTotal(lignes: Ligne[], remise: number): number {
  if (!Number.isFinite(remise) || remise < 0 || remise > 1) {
    throw new Error("Remise invalide");
  }
  return lignes.reduce((somme, ligne) => {
    if (ligne.quantite < 0 || ligne.prixUnitaire < 0) {
      throw new Error("Ligne invalide");
    }
    return somme + ligne.prixUnitaire * ligne.quantite;
  }, 0) * (1 - remise);
}

Cette règle pure peut être testée sans base de données ni framework web. Le cas d’usage orchestre ensuite chargement, calcul, sauvegarde et publication d’événement ; le contrôleur traduit la requête HTTP en entrée de cas d’usage. La transaction doit couvrir les écritures qui partagent un invariant.

Diagnostic des responsabilités

  • Une fonction qui lit HTTP, calcule un prix, écrit en base et envoie un courriel mélange plusieurs raisons de changer.
  • Une interface n’est utile que si elle définit une frontière, un contrat substituable ou un point de test pertinent.
  • Évitez d’extraire une abstraction tant que ses variations et ses invariants ne sont pas compris.

Exercice

Refactorisez un contrôleur « créer commande » en quatre étapes : caractériser le comportement existant par des tests, extraire la règle pure, déplacer l’orchestration dans un cas d’usage, puis isoler les adaptateurs. À chaque étape, lancez les tests et inspectez le diff.

Critères de réussite : les règles métier se testent sans infrastructure ; les effets secondaires sont explicites ; les erreurs et transactions ont un propriétaire clair ; le refactoring ne change pas silencieusement le comportement.
