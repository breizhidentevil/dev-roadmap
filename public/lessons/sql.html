4. Bases de données et modélisation

SQL

Lire et écrire des requêtes pour interroger et modifier des données.

Tutoriel détailléLot 13 · 2026

Objectifs d’apprentissage

  • Lire une requête SELECT et comprendre son ordre logique.
  • Filtrer, trier, joindre et agréger des données.
  • Modifier les données avec INSERT, UPDATE et DELETE.
  • Utiliser des paramètres plutôt que concaténer des valeurs dans le SQL.

1. SQL et modèle relationnel

SQL est un langage déclaratif : tu décris les résultats attendus, et le moteur choisit un plan d’exécution. Une base relationnelle organise les données en tables, colonnes et lignes, avec des types et des contraintes. Une clé identifie une ligne ; les relations relient les tables.

Une requête lisible explicite les colonnes, les conditions et les relations. Évite SELECT * dans les traitements applicatifs durables : l’ajout d’une colonne peut modifier le volume de données transférées et surprendre le code consommateur.

2. SELECT, WHERE et ORDER BY

SELECT id, title, priority
FROM tasks
WHERE done = false
  AND priority IN ('high', 'normal')
ORDER BY priority, id
LIMIT 20;

WHERE filtre les lignes avant l’agrégation. ORDER BY définit l’ordre de présentation ; sans tri explicite, l’ordre n’est pas garanti. Une pagination stable doit employer un ordre déterministe, idéalement avec une clé unique comme dernier critère.

Attention à NULL : il signifie une valeur absente ou inconnue. On utilise IS NULL et IS NOT NULL, pas = NULL.

3. Jointures et agrégations

SELECT u.id, u.email, COUNT(t.id) AS task_count
FROM users AS u
LEFT JOIN tasks AS t ON t.user_id = u.id
GROUP BY u.id, u.email
HAVING COUNT(t.id) >= 3;

Une jointure combine les lignes selon une condition. LEFT JOIN conserve aussi les utilisateurs sans tâche, contrairement à INNER JOIN. GROUP BY forme des groupes et les fonctions comme COUNT, SUM ou AVG les résument ; HAVING filtre les groupes après agrégation.

Une jointure plusieurs-à-plusieurs peut multiplier les lignes. Vérifie la cardinalité avant de calculer des totaux afin de ne pas compter deux fois une même valeur.

4. Écrire et modifier des données

INSERT INTO tasks (title, done)
VALUES ('Réviser SQL', false);

UPDATE tasks
SET done = true
WHERE id = 42;

DELETE FROM tasks
WHERE id = 42;

Avant un UPDATE ou un DELETE, vérifie la condition WHERE et estime le nombre de lignes touchées. Sans condition, toutes les lignes peuvent être modifiées ou supprimées. Pour une opération critique, utilise une transaction et contrôle le résultat avant validation.

5. Sécurité et performances

Ne construis pas une requête en concaténant une entrée utilisateur. Les requêtes paramétrées séparent le code SQL des valeurs et constituent la défense de base contre l’injection SQL. Les noms de colonnes ou mots-clés dynamiques ne peuvent pas toujours être passés comme paramètres : utilise alors une liste blanche de choix autorisés.

Mesure avant d’optimiser. Consulte le plan avec les outils du moteur, observe le nombre de lignes lues et renvoyées, puis évalue les index, les filtres et les jointures. Un index accélère certaines lectures mais consomme de l’espace et rend les écritures plus coûteuses.

6. Étude de cas : une requête correcte, sûre et déterministe

Considérons une liste paginée de tâches appartenant à un utilisateur. La requête doit filtrer par propriétaire, trier de manière stable et limiter le nombre de lignes. Les valeurs venant du client sont des paramètres ; les noms de colonnes ou le sens de tri ne peuvent généralement pas être liés comme de simples valeurs et doivent provenir d’une liste blanche.

SELECT id, title, priority, created_at
FROM tasks
WHERE owner_id = $1
  AND done = false
ORDER BY created_at DESC, id DESC
LIMIT $2;

Les marqueurs de paramètres dépendent du pilote : $1 est courant avec PostgreSQL, tandis que d’autres drivers utilisent ? ou une syntaxe nommée. L’idée essentielle est que le moteur reçoit les valeurs séparément de la structure SQL. Ne construis pas la clause WHERE par concaténation de texte utilisateur.

Raisonner sur le résultat

  • Filtrage : la condition de propriétaire doit venir de l’identité authentifiée côté serveur, pas d’un owner_id librement choisi par le client.
  • Ordre stable : trier uniquement par une date non unique peut produire des doublons ou des omissions entre pages ; ajouter une clé unique comme dernier critère rend l’ordre déterministe.
  • NULL : les valeurs inconnues ne se comparent pas comme les valeurs ordinaires. Utilise IS NULL et comprends la position des valeurs nulles dans le tri du moteur.
  • Jointure : un LEFT JOIN conserve les lignes de gauche sans correspondance ; déplacer une condition de la table jointe de ON vers WHERE peut éliminer ces lignes et changer le résultat.
  • Agrégation : distingue les filtres de lignes (WHERE) des filtres appliqués aux groupes (HAVING).

Transactions : lorsque plusieurs écritures forment une seule opération métier, utilise une transaction et définis ce qui doit être annulé si une étape échoue. Une transaction ne rend pas automatiquement toutes les courses impossibles : selon le niveau d’isolation et les contraintes, il peut rester nécessaire de verrouiller, de vérifier un état ou de gérer une violation de contrainte.

Diagnostic de performance : commence par mesurer la durée et le volume, puis examine le plan d’exécution avec les outils du moteur. Un index peut accélérer certaines lectures mais ralentir les écritures et consommer de l’espace. N’ajoute pas d’index uniquement parce qu’une colonne figure dans une requête ; vérifie la sélectivité, l’ordre des colonnes d’un index composite et les plans réels sur des données représentatives.

Exercice : écris une requête de pagination, teste les identifiants en double dans le tri, vérifie que les données d’un autre propriétaire ne sortent jamais, puis transforme une requête vulnérable par concaténation en requête paramétrée. Compare le résultat et le plan avant/après un index candidat.

Critère de réussite : la requête retourne les bonnes lignes dans un ordre reproductible, protège les frontières d’accès, traite correctement NULL et agrégations, et les choix de performance reposent sur une mesure.

Erreurs fréquentes

  • Oublier une condition dans UPDATE ou DELETE.
  • Supposer que les résultats arrivent dans un ordre naturel.
  • Comparer à NULL avec l’opérateur égal.
  • Concaténer des entrées utilisateur dans une requête.
  • Ajouter des index sans mesurer leur utilité ni leur coût.

Exercice guidé

Avec deux tables users(id, email) et tasks(id, user_id, title, done), écris une requête qui liste les utilisateurs et le nombre de tâches terminées, y compris ceux qui n’en ont aucune. Ensuite, ajoute une tâche avec des paramètres et explique pourquoi le paramétrage protège la requête.

Critères de réussite

  • La jointure conserve les utilisateurs sans tâche.
  • L’agrégation compte uniquement les tâches terminées.
  • La requête ne dépend pas d’un ordre implicite.
  • Les valeurs externes sont paramétrées.
  • Les modifications de données sont contrôlées.
