16. Architecture frontend approfondie

SSR, CSR et hydratation

Comprendre les stratégies de rendu côté serveur et côté client, ainsi que leurs conséquences.

Tutoriel approfondiLecture et mise en pratique

Objectifs et prérequis

Tu sauras distinguer CSR, SSR, génération statique et rendu hybride, expliquer l’hydratation, diagnostiquer les écarts entre HTML serveur et rendu client, et choisir une stratégie selon le contenu, la personnalisation et les contraintes de performance.

Prérequis : HTML, JavaScript, React et notions HTTP. Les détails d’implémentation varient selon les frameworks ; ne transpose pas mécaniquement une règle d’un framework à un autre.

1. Les stratégies de rendu

En rendu côté client (CSR), le serveur fournit souvent une page initiale légère et du JavaScript qui construit l’interface dans le navigateur. Cette approche permet des transitions riches, mais l’utilisateur peut attendre le téléchargement, l’analyse et l’exécution du JavaScript avant de voir le contenu principal. Les moteurs de recherche et les technologies d’assistance peuvent aussi rencontrer une expérience initiale moins robuste si le contenu dépend entièrement du script.

En rendu côté serveur (SSR), le serveur génère le HTML pour une requête. Le navigateur peut afficher du contenu avant que toute l’interactivité soit disponible. Le serveur doit cependant exécuter le code nécessaire à la génération, et la page peut nécessiter ensuite une hydratation. La personnalisation, le cache et la charge serveur deviennent des sujets importants.

La génération statique préconstruit des pages à l’avance, ce qui permet de les servir depuis un cache ou un CDN. Elle convient aux contenus qui changent peu ou qui peuvent être régénérés. Le rendu hybride combine ces stratégies selon la route ou le composant. Aucun mode n’est universellement meilleur : le choix dépend du contenu, de la fraîcheur, de la personnalisation, du coût serveur et du budget JavaScript.

2. Ce que fait l’hydratation

L’hydratation relie le HTML déjà présent dans le document aux composants JavaScript qui gèrent les interactions. Le navigateur peut afficher le contenu initial, puis React attache la logique interactive en s’attendant à ce que le rendu client corresponde au HTML du serveur. Si les arbres diffèrent, le framework peut signaler un avertissement, remplacer une partie du rendu ou produire un comportement incorrect.

Les différences proviennent souvent de valeurs non déterministes : date et heure calculées séparément, nombres aléatoires, dépendance à `window`, langue ou fuseau horaire différents, ou données qui ont changé entre le rendu serveur et l’hydratation. Un composant ne devrait pas produire un HTML différent uniquement parce qu’il s’exécute dans deux environnements distincts, sauf si le framework fournit un mécanisme explicite pour cela.

Évite de masquer les avertissements d’hydratation sans comprendre leur cause. Un rendu initial incohérent peut créer un saut visuel, un mauvais contenu ou des contrôles qui ne fonctionnent pas comme attendu. Si une donnée n’est disponible que côté client, prévois un état initial stable puis une mise à jour après montage, ou choisis un composant explicitement client lorsque le framework le permet.

3. Données, cache et personnalisation

Le SSR peut fournir des données initiales dans le HTML, mais il faut déterminer leur fraîcheur et leur cacheabilité. Une page publique identique pour tous les visiteurs peut être mise en cache agressivement. Une page contenant des données personnelles doit être isolée selon l’utilisateur et ne doit pas être mise en cache publiquement par erreur. Une configuration incorrecte peut divulguer des informations entre sessions.

Le rendu serveur ajoute des contraintes de latence et de disponibilité : la réponse dépend du temps de calcul et des services interrogés. Évite de bloquer la génération sur des appels indépendants qui pourraient être parallélisés. Définis des timeouts et des états de repli. Si un service externe est lent, il peut retarder le HTML initial.

La génération statique demande une stratégie de mise à jour : reconstruction au déploiement, régénération planifiée ou revalidation selon le framework. Les données affichées peuvent être volontairement légèrement anciennes. Documente cette contrainte lorsque l’utilisateur dépend de la fraîcheur, par exemple pour un inventaire ou un tarif. Le cache est un choix de cohérence autant qu’un choix de performance.

4. Mesurer les compromis

Le SSR peut améliorer le temps d’affichage du contenu, mais ne garantit pas à lui seul une bonne interactivité. Une page qui envoie un gros bundle JavaScript peut afficher du HTML rapidement et rester lente au clic. Le CSR peut être adapté à un outil interne très interactif derrière authentification, tandis qu’un site de contenu public peut bénéficier du HTML pré-rendu.

Mesure le temps de réponse serveur, le LCP, l’INP, le poids JavaScript, les requêtes et le coût d’exploitation. Compare les mêmes parcours sur des appareils et réseaux représentatifs. N’optimise pas uniquement le score d’une page d’accueil si les pages de détail ou les parcours de conversion restent lents.

Les composants serveur et client ont des responsabilités différentes dans les frameworks qui les proposent. Un composant serveur peut accéder à certaines ressources privées sans exposer tout le code au navigateur, mais ses sorties peuvent toujours inclure des données rendues. Un composant client peut gérer les interactions, mais tout secret livré dans son bundle est exposé. Le rendu serveur n’est pas une protection automatique contre les fuites de données.

5. Diagnostic des erreurs d’hydratation

Reproduis le problème avec les mêmes données et la même locale. Inspecte le HTML reçu, les erreurs console et les composants qui utilisent des valeurs variables. Vérifie les dates, les formats locaux, les identifiants générés et les conditions d’exécution. Une différence qui n’apparaît qu’en production peut provenir de la configuration, du cache ou de données différentes.

Corrige la source de l’écart plutôt que de forcer le navigateur à remplacer silencieusement le contenu. Lorsque le framework offre une stratégie spécifique pour un contenu volontairement variable, utilise-la avec parcimonie et documente pourquoi l’écart est acceptable. Les suppressions d’avertissement sont des exceptions, pas une méthode de conception.

Teste une route directement, recharge-la, navigue vers elle depuis l’application et vérifie le comportement sans JavaScript lorsque cela fait partie des objectifs du produit. Observe aussi les états d’erreur serveur, la session expirée et les différences de cache entre visiteurs anonymes et connectés.

Atelier approfondi — garantir un rendu initial déterministe

Objectifs ciblés

Tu sauras choisir une stratégie de rendu en fonction du contenu et de l’interactivité, expliquer le rôle de l’hydratation et diagnostiquer un désaccord entre le HTML produit par le serveur et le premier rendu client.

Le choix n’est pas uniquement une question de score de performance. Il dépend de la personnalisation, de la fraîcheur, de l’indexation, de la sécurité des données et du coût d’exploitation. Le rendu côté serveur n’autorise pas à envoyer au navigateur des données privées qui ne lui sont pas destinées.

L’hydratation exige le même premier rendu

Le serveur livre du HTML ; le client exécute le code pour attacher les comportements interactifs à ce HTML. Le premier rendu client doit correspondre à la structure et aux valeurs déjà présentes. Une date formatée selon le fuseau du serveur puis celui du navigateur, une valeur issue de localStorage, un nombre aléatoire ou un horodatage calculé indépendamment peuvent provoquer un avertissement d’hydratation.

// À éviter dans le rendu initial partagé :
function Greeting() {
  return <p>Bonjour, il est {new Date().toLocaleTimeString()}</p>;
}

// Préférer une valeur initiale produite une fois et transmise :
function Greeting({ initialLabel }: { initialLabel: string }) {
  return <p>{initialLabel}</p>;
}

Le serveur et le premier rendu client utilisent ici exactement la même valeur sérialisée par le framework. Si une valeur ne peut être connue qu’après le démarrage du navigateur, affiche un état initial déterministe, puis lis cette valeur après montage. N’ignore pas un avertissement d’hydratation pour le faire disparaître : cherche la différence et corrige sa cause.

Données et frontières serveur/client

Charge autant que possible les données nécessaires au rendu initial dans la couche prévue par le framework et passe au client uniquement ce dont il a besoin. Les données transmises doivent être sérialisables et filtrées. N’inclus ni secret, ni données d’un autre utilisateur, ni objet serveur interne. Évite aussi de lancer la même requête une fois côté serveur puis une seconde fois côté client sans politique explicite de réutilisation ou de revalidation.

Pièges spécifiques

  • Utiliser typeof window pour produire deux structures initiales différentes peut déplacer le problème plutôt que le résoudre.
  • Une page SSR peut être lente si elle attend des appels externes séquentiels non nécessaires.
  • Un HTML initial visible ne signifie pas que les contrôles sont déjà interactifs : mesure aussi le délai d’hydratation.
  • Un composant client ne doit pas recevoir de secrets sous prétexte qu’il est rendu initialement sur le serveur.

Exercice et critères de réussite

Choisis une page d’article, une page de tableau de bord et une page interactive. Justifie pour chacune la stratégie de rendu. Reproduis ensuite un désaccord d’hydratation avec une date ou une préférence locale, inspecte le HTML initial et corrige-le sans masquer l’avertissement.

  • La stratégie choisie est justifiée par fraîcheur, interactivité, personnalisation et coût.
  • Le premier rendu client correspond au HTML initial.
  • Les données sérialisées sont limitées au strict nécessaire et ne contiennent aucun secret.
  • Les mesures distinguent affichage du contenu, interactivité et charge serveur.
  • Les erreurs d’hydratation sont corrigées à leur source.

Pièges, limites et compromis

  • SSR ne garantit ni faible INP ni faible poids JavaScript.
  • Une page rendue sur serveur peut divulguer des données si le cache ou la sélection des champs est incorrect.
  • L’hydratation suppose une cohérence du rendu initial ; les valeurs non déterministes sont une cause fréquente d’écart.
  • Le rendu statique exige une stratégie explicite de fraîcheur.
  • Le SSR ajoute du coût serveur et peut augmenter la latence si les appels sont séquentiels.
  • Les API de navigateur ne sont pas disponibles dans tous les environnements serveur.
  • Ne masque pas les avertissements d’hydratation sans identifier la cause.

Exercice

Prends une petite page React et compare une version rendue côté client à une version pré-rendue par un framework. Mesure le contenu visible, le poids JavaScript et la réactivité après chargement. Introduis volontairement une date locale ou une valeur aléatoire dans le rendu, observe l’écart puis corrige-le. Vérifie également que les données privées ne sont pas incluses dans un cache public.

Critères de réussite

  • Je peux expliquer CSR, SSR et génération statique.
  • Je sais pourquoi l’hydratation exige un rendu initial cohérent.
  • Les données privées ne sont pas partagées par un cache public.
  • La stratégie de fraîcheur des pages pré-générées est documentée.
  • Les mesures couvrent affichage, interactivité et coût d’exécution.
  • Les erreurs d’hydratation sont corrigées à la source.
