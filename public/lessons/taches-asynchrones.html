3. Backend

Tâches asynchrones et files d’attente

Découpler les traitements longs avec des jobs et des files comme BullMQ.

Tutoriel détailléLot 11 · 2026

Objectifs d’apprentissage

  • Identifier les opérations à déporter hors du cycle HTTP.
  • Comprendre producteur, file, worker, retries et file d’échec.
  • Concevoir des jobs idempotents et observables.
  • Gérer délais, échecs et cohérence entre base de données et file.

1. Quand utiliser une file

Une requête HTTP devrait généralement terminer rapidement. L’envoi d’un courriel, la génération d’un rapport, le traitement d’une image ou l’import d’un gros fichier peut durer longtemps, échouer à cause d’une dépendance ou consommer beaucoup de ressources. Une file permet d’accepter la demande puis de traiter le travail indépendamment du cycle de la requête.

Le serveur peut répondre 202 Accepted avec un identifiant de job et une URL de suivi. Cela signifie que le traitement est accepté, pas qu’il est déjà terminé. Pour une opération courte et nécessaire à la réponse immédiate, ajouter une file augmente inutilement la complexité.

2. Les composants d’une architecture

  • Producteur : valide la demande et publie un message décrivant le travail.
  • File : conserve les jobs en attente et organise leur livraison.
  • Worker : consomme un job et exécute le traitement.
  • Stockage d’état : permet de suivre attente, exécution, réussite ou échec.
  • Supervision : mesure profondeur de file, âge des jobs, échecs et durée de traitement.

La file absorbe des pointes, mais ne crée pas une capacité infinie. Si les producteurs génèrent plus de travail que les workers ne peuvent en traiter, le retard augmente : il faut limiter le débit, augmenter la capacité ou réduire le coût des jobs.

3. Exemple de lancement d’un job

// Pseudo-code : l’API de la file et la fonction hash dépendent du projet.
const idempotencyKey = requireIdempotencyKey(request);
const stableJobId = hash(`${user.id}:generate-report:${idempotencyKey}`);

const job = await queue.add("generate-report", {
  reportId,
  requestedBy: user.id,
  idempotencyKey
}, {
  jobId: stableJobId
});

return response.status(202).json({
  jobId: job.id,
  statusUrl: `/api/jobs/${job.id}`
});

La même intention doit réutiliser la même clé lors d’un retry HTTP ; une nouvelle demande reçoit une nouvelle clé. L’identifiant stable de job peut réduire les doublons, mais sa portée, le comportement en cas de doublon et la durée de conservation varient selon la bibliothèque. Ne considérez pas la déduplication de la file comme un registre métier permanent, surtout si les jobs terminés sont supprimés. Pour une création critique, persistez aussi la clé et le résultat dans la base.

Le message contient des identifiants et les informations minimales nécessaires, pas un objet gigantesque ou des secrets. Le worker relit les données nécessaires depuis la source de vérité, vérifie que le job est encore pertinent, effectue le travail puis enregistre le résultat et son état. L’endpoint statusUrl doit authentifier l’appelant et vérifier qu’il est autorisé à consulter ce job : un identifiant difficile à deviner n’est pas un contrôle d’accès.

4. Retries, doublons et idempotence

Un worker peut terminer une action externe puis tomber en panne avant de confirmer la réussite. Le système peut alors relivrer le job. Dans de nombreux systèmes, une livraison « au moins une fois » implique de tolérer les doublons.

Un job idempotent peut être rejoué sans reproduire un effet indésirable. Utilise une clé d’idempotence, un état métier vérifiable ou une contrainte unique lorsque cela convient. Configure des tentatives limitées, un délai progressif et une politique distinguant erreurs temporaires et permanentes. Après épuisement des tentatives, place le job dans un état consultable ou une file d’échec dédiée.

5. Cohérence, sécurité et exploitation

Publier un message et valider une transaction SQL sont deux opérations distinctes. Si l’une réussit et l’autre échoue, le système peut perdre un événement ou créer un job sans données correspondantes. Pour les cas critiques, étudie le pattern transactional outbox, qui écrit l’événement dans la même transaction que les données puis le publie de manière fiable. Le dispatcher peut republier après un crash : le worker doit donc dédupliquer à partir d’un identifiant stable et enregistrer l’effet métier de manière atomique lorsque c’est possible.

Ne place pas de mots de passe ou de tokens dans les messages. Protège l’accès à la file, définis des limites de taille et de durée, et rends les jobs observables avec un identifiant de corrélation. Prévois la fermeture propre des workers, la reprise après redémarrage et des alertes sur les files qui vieillissent.

6. Ordonnancement et concurrence

Un job qui met à jour la même ressource qu’un autre peut créer une course. Définis si l’ordre est important, si plusieurs jobs peuvent s’exécuter simultanément et comment éviter les mises à jour concurrentes. La concurrence améliore le débit mais augmente la charge sur les bases et les services externes.

Les tâches planifiées doivent aussi gérer les exécutions en double, les fuseaux horaires et les changements d’heure. Une exécution prévue à 02:30 n’a pas le même comportement lors d’un passage à l’heure d’été selon le système utilisé.

7. Étude de cas : rendre un job reprenable sans doublon

Un client demande la génération d’un rapport. Le serveur enregistre une demande et publie un job ; le worker commence le traitement, puis tombe avant d’accuser réception. La file peut livrer le même message une nouvelle fois. Il faut donc concevoir en supposant des livraisons au moins une fois, sauf garantie plus forte documentée par le système choisi.

  1. Attribuer un identifiant stable au job et enregistrer un état consultable : queued, running, succeeded ou failed.
  2. Rendre l’effet métier idempotent : avant de créer le rapport ou de déclencher un paiement, vérifier une clé d’idempotence unique ou utiliser une contrainte transactionnelle.
  3. Configurer un nombre maximal de tentatives, un délai progressif avec jitter et une liste de jobs définitivement échoués. Les erreurs permanentes (par exemple un fichier au format interdit) ne doivent pas être retentées sans limite.
  4. Rendre le worker observable : durée, nombre de tentatives, âge du plus ancien job, profondeur de file et raison d’échec, sans exposer le contenu sensible des messages.

Le piège de la double écriture : écrire dans une base puis publier dans une file n’est généralement pas atomique. Si la base réussit et que la publication échoue, le job manque ; si le message est publié puis la transaction échoue, le worker peut traiter une opération inexistante. Le pattern outbox consiste à écrire l’événement dans la même transaction que les données métier, puis à le publier depuis un processus dédié. Il ajoute de l’exploitation, mais réduit cette fenêtre d’incohérence.

Une réponse HTTP 202 Accepted signifie que la demande a été acceptée pour traitement, non que le résultat est garanti. Fournis un identifiant de suivi, une politique de conservation et un état terminal explicite. Prévois aussi ce qui se passe si le client réessaie la requête de création après un timeout : sans clé d’idempotence, il peut créer deux jobs.

Exercice de diagnostic : simule un worker qui échoue après l’écriture du résultat mais avant l’accusé de réception. Montre que la seconde livraison ne duplique pas l’effet. Ajoute ensuite une erreur permanente et vérifie qu’elle termine dans la file d’échec après la politique prévue.

Critère de réussite : le job peut être livré à nouveau, suivi et diagnostiqué sans produire d’effet métier en double ni disparaître silencieusement.

Erreurs fréquentes

  • Répondre « terminé » alors que seul le job a été mis en file.
  • Ne pas prévoir les doublons ou les retries.
  • Relancer indéfiniment une erreur permanente.
  • Ignorer la profondeur et l’âge de la file.
  • Supposer que base de données et file sont mises à jour atomiquement.

Exercice guidé

Conçois le traitement asynchrone de génération d’un rapport PDF. Décris l’endpoint de lancement, le message, les états du job, les règles de retry, la stratégie contre les doublons et l’endpoint de consultation. Ajoute les métriques et alertes nécessaires.

Critères de réussite

  • La réponse HTTP distingue acceptation et achèvement.
  • Les jobs ont des états et un identifiant de suivi.
  • Les doublons et les échecs définitifs sont gérés.
  • La capacité et le retard de la file sont observables.
  • La cohérence entre base et file est explicitement traitée.
