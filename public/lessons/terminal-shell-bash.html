0. Informatique générale et fonctionnement des systèmes

Terminal, shell et Bash

Utiliser efficacement la ligne de commande et automatiser des tâches simples.

Tutoriel complet · Niveau intermédiaireDurée indicative : 2 h

Objectifs pédagogiques

  • Distinguer terminal, shell et commande.
  • Composer des commandes avec redirections et pipelines.
  • Écrire un script Bash robuste qui gère les erreurs et les arguments.

1. Terminal, shell et processus

Le terminal fournit une interface d’entrée et de sortie. Le shell interprète les commandes, développe les variables et motifs, puis lance des programmes. Bash est un shell courant sous Linux. Une commande peut être un builtin du shell, un exécutable trouvé dans PATH ou une fonction définie par l’utilisateur.

pwd
printf '%s\n' "$SHELL"
command -v bash
type cd
echo "$PATH"

Comprendre cette distinction aide à diagnostiquer les commandes introuvables, les différences d’environnement et les scripts qui fonctionnent dans un terminal mais pas dans un service automatisé.

2. Fichiers, motifs et citations

Les espaces et caractères spéciaux ont une signification pour le shell. Les guillemets doubles permettent généralement l’expansion des variables, tandis que les guillemets simples préservent leur contenu littéral. Les chemins contenant des espaces doivent être cités.

name="rapport final.txt"
printf '%s\n' "$name"
ls -l -- "$name"
find . -type f -name '*.html'

Dans le dernier exemple, les apostrophes empêchent le shell de développer le motif avant que find le reçoive. Utilisez -- lorsque la commande le prend en charge pour séparer les options des arguments qui pourraient commencer par un tiret.

3. Redirections et pipelines

La sortie standard (stdout) et la sortie d’erreur (stderr) sont deux flux distincts. Les redirections permettent de les envoyer vers un fichier ; un pipeline transmet la sortie d’une commande à l’entrée de la suivante.

grep -n "ERROR" app.log > erreurs.txt
command-that-may-fail 2> erreurs.log
cat app.log | grep "WARN" | sort | uniq -c

Évitez les pipelines inutiles si une commande peut lire directement le fichier. Dans un script, l’option set -o pipefail permet qu’un échec au milieu d’un pipeline ne soit pas masqué par la réussite de la dernière commande.

4. Écrire un script plus robuste

Un script doit rendre ses hypothèses visibles, vérifier les arguments et échouer proprement.

#!/usr/bin/env bash
set -Eeuo pipefail

if [[ $# -ne 1 ]]; then
  printf 'Usage : %s fichier\n' "$0" >&2
  exit 2
fi

file=$1
if [[ ! -r "$file" ]]; then
  printf 'Fichier absent ou illisible : %s\n' "$file" >&2
  exit 1
fi

wc -l -- "$file"

set -e a des règles de comportement nuancées dans certaines constructions ; il ne remplace pas une gestion explicite des erreurs importantes. Le quoting, la validation des arguments et les codes de sortie restent essentiels.

5. Sécurité et débogage

Ne construisez pas une commande shell en concaténant directement des données fournies par un utilisateur. Une chaîne contenant des métacaractères peut être interprétée comme du code. Dans un programme, préférez lancer un exécutable avec une liste d’arguments plutôt que de passer une commande assemblée à un shell.

Pour diagnostiquer un script, utilisez des messages sur stderr, inspectez les codes de sortie et activez temporairement une trace avec bash -x script.sh. Attention : la trace peut révéler des secrets présents dans les arguments ou les variables. N’utilisez pas sudo comme solution générale à un problème de permissions.

6. Exercice

Écrivez un script qui reçoit un répertoire et un chemin de rapport, vérifie que le répertoire est accessible, compte les fichiers HTML et crée le rapport sans écraser un fichier existant. Testez un chemin avec des espaces, un répertoire absent, un rapport déjà présent et un répertoire non lisible lorsque vous pouvez effectuer le test avec un compte non privilégié.

Exemple de solution

#!/usr/bin/env bash
set -Eeuo pipefail

if [[ $# -ne 2 ]]; then
  printf 'Usage : %s repertoire rapport\n' "$0" >&2
  exit 2
fi
repertoire=$1
rapport=$2

if [[ ! -d "$repertoire" || ! -r "$repertoire" || ! -x "$repertoire" ]]; then
  printf 'Répertoire absent ou inaccessible : %s\n' "$repertoire" >&2
  exit 1
fi
if [[ -e "$rapport" ]]; then
  printf 'Le rapport existe déjà : %s\n' "$rapport" >&2
  exit 1
fi

liste=$(mktemp)
trap 'rm -f -- "$liste"' EXIT
if ! find "$repertoire" -type f -name '*.html' -print0 > "$liste"; then
  printf 'Échec du parcours du répertoire : %s\n' "$repertoire" >&2
  exit 1
fi

compte=0
while IFS= read -r -d '' fichier; do
  ((compte += 1))
done < "$liste"

if ! (set -o noclobber; printf 'Répertoire : %s\nFichiers HTML : %d\n' "$repertoire" "$compte" > "$rapport"); then
  printf 'Impossible de créer le rapport sans écrasement : %s\n' "$rapport" >&2
  exit 1
fi
printf 'Rapport créé : %s\n' "$rapport"

La liste intermédiaire permet de vérifier le code de sortie de find avant de compter. Les chemins sont séparés par NUL afin de préserver les noms contenant des espaces ou des retours à la ligne. Le mode noclobber évite de remplacer un rapport créé entre le contrôle initial et l’écriture ; il ne remplace pas les permissions du système de fichiers.

Critères de réussite

  • Le script vérifie ses arguments et ses entrées.
  • Les variables et chemins sont correctement cités.
  • Les erreurs sont envoyées sur stderr avec un code de sortie adapté.
  • Un échec de find n’est pas présenté comme un comptage complet.
  • Le rapport existant n’est pas écrasé et les noms avec espaces sont préservés.
  • Le script ne transforme pas des données non fiables en commandes shell.

Approfondissement — préserver les noms de fichiers et comprendre les flux

Un nom de fichier peut contenir des espaces, des tabulations ou même un retour à la ligne. Une ligne de sortie n’est donc pas toujours une frontière fiable entre deux noms. Pour transmettre des chemins à une autre commande, utilise un séparateur qui ne peut pas apparaître dans un nom Unix : l’octet NUL. C’est le rôle de -print0 de find et de read -d '' en Bash.

#!/usr/bin/env bash
set -u

repertoire=${1:?Usage : $0 repertoire}
[[ -d "$repertoire" ]] || {
  printf 'Répertoire introuvable : %s\n' "$repertoire" >&2
  exit 1
}

compte=0
while IFS= read -r -d '' fichier; do
  printf 'HTML : %s\n' "$fichier"
  ((compte += 1))
done < <(find "$repertoire" -type f -name '*.html' -print0)
printf 'Total : %d fichier(s)\n' "$compte"

IFS= empêche la suppression des espaces de début et de fin, -r évite que les antislashs soient interprétés, et le délimiteur NUL préserve le nom entier. La substitution de processus < <(…) est une fonctionnalité de Bash, pas une syntaxe POSIX universelle. Autre nuance : le code de sortie de find lancé dans cette substitution n’est pas automatiquement celui de la boucle ; si la détection d’une erreur de parcours est critique, traite explicitement ce statut.

Les redirections sont traitées de gauche à droite. Ainsi, commande >sortie.log 2>&1 envoie stdout et stderr vers le fichier, tandis que commande 2>&1 >sortie.log duplique d’abord stderr vers la sortie courante : les deux formes ne sont pas équivalentes. De même, > rapport.txt remplace le fichier, alors que >> rapport.txt ajoute à la fin. Vérifie toujours si l’écrasement est voulu.

Diagnostic reproductible

  1. Reproduis la commande avec un petit fichier de test.
  2. Observe séparément stdout, stderr et le code de sortie avec printf '%s\n' "$?" juste après la commande concernée.
  3. Ajoute une redirection seulement après avoir identifié le flux à conserver.
  4. Teste les chemins contenant des espaces et les cas d’échec, pas uniquement le chemin nominal.

Exercice de vérification

Crée dans un répertoire de test deux fichiers HTML, dont un nommé page avec espaces.html. Modifie le script pour écrire la liste dans un rapport et le total dans stderr. Provoque aussi un échec de lecture et explique ce que le script peut détecter ou non.

Critères de réussite

  • Les noms de fichiers sont préservés sans découpage sur les espaces.
  • Le rapport n’est écrasé que si ce comportement est explicite.
  • La différence entre stdout, stderr et code de sortie est démontrée.
  • Les limites de la substitution de processus sont documentées si elle est utilisée.
