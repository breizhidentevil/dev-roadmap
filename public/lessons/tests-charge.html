Tests de charge

Évaluer le comportement d’un système sous trafic représentatif, détecter les limites de capacité et interpréter les résultats sans conclusions hâtives.

Leçon approfondieThéorie · pratique · validation

Objectifs d’apprentissage

À la fin de cette leçon, tu dois pouvoir expliquer les concepts avec tes propres mots, choisir une approche adaptée à un besoin réel, et justifier tes choix à partir de contraintes observables.

  • Définir le vocabulaire essentiel et le problème que la compétence résout.
  • Appliquer les principes dans un exemple pratique et identifier les limites.
  • Vérifier le résultat avec des critères explicites plutôt qu’une impression subjective.

1. Définir ce que le test doit apprendre

Un test de charge mesure comment une application se comporte lorsque plusieurs utilisateurs ou requêtes sollicitent le système. Il peut servir à vérifier une capacité cible, comparer deux versions, identifier un point de saturation ou observer la stabilité pendant une durée prolongée. Il ne suffit pas de lancer un grand nombre de requêtes et de noter le débit : il faut définir le scénario métier, les conditions de réussite et les limites de sécurité avant de commencer.

Choisis des objectifs quantifiables : par exemple, maintenir un certain nombre de requêtes par seconde avec un p95 inférieur à une cible et un taux d’erreur sous un seuil. Les objectifs doivent venir des besoins de service et du comportement attendu, pas d’une valeur choisie parce qu’elle paraît ambitieuse. Mesure les réponses fonctionnelles, pas seulement les codes HTTP : une API qui renvoie rapidement une erreur métier ne constitue pas un succès.

Précise aussi l’environnement : version de l’application, taille des instances, configuration de base, cache froid ou chaud, jeu de données, emplacement du générateur de charge et dépendances utilisées. Une expérience ne permet de conclure que sur les conditions qu’elle représente. Ne lance pas un test intensif sur un service tiers ou une production sans autorisation et sans plan de réduction du trafic.

2. Comprendre les profils de charge

Les termes décrivent des questions différentes. Un test de charge observe le système au niveau de trafic attendu. Un test de stress augmente la pression au-delà de la capacité nominale pour comprendre le mode de dégradation. Un test d’endurance ou soak maintient une charge pendant longtemps afin de détecter les fuites mémoire, les connexions non libérées ou les dégradations progressives. Un test de pic vérifie la réaction à une montée soudaine. Un test de capacité cherche le volume maximal qui respecte les objectifs.

La charge peut être définie par un nombre d’utilisateurs virtuels ou par un débit cible. Les utilisateurs virtuels reproduisent souvent des parcours avec des temps de réflexion et des durées variables ; le débit cible permet de maintenir une pression définie. Ces modèles ne sont pas interchangeables. Si le système ralentit, un modèle où chaque utilisateur attend la réponse avant d’envoyer la requête suivante peut naturellement réduire le débit généré, ce qui masque parfois la saturation. Choisis le modèle selon la question à tester.

Un scénario réaliste comprend plusieurs parcours, des proportions de lecture et d’écriture, des identifiants valides, des erreurs plausibles et des pauses. Répéter une seule requête extrêmement cacheable peut mesurer le CDN plutôt que le parcours réel d’un utilisateur. À l’inverse, utiliser des données aléatoires sans contrôle peut créer un coût artificiel en base de données.

3. Mesurer les bonnes métriques

Le débit indique combien d’opérations réussissent par unité de temps. La latence doit être examinée par percentiles : p50 décrit le milieu de la distribution, p95 et p99 exposent une partie des expériences lentes. Le taux d’erreur doit distinguer erreurs serveur, timeouts, erreurs réseau et réponses métier attendues. Surveille simultanément CPU, mémoire, garbage collection, connexions de base, files d’attente, temps SQL, bande passante et limites du générateur de charge.

La loi de Little donne un lien utile entre le nombre moyen de requêtes en cours, le débit et le temps de séjour : L = λ × W, lorsque les conditions sont suffisamment stables. Si la latence augmente alors que le débit reste plafonné, la file d’attente peut grossir. Une forte utilisation CPU n’est pas nécessairement un défaut si le service respecte ses objectifs ; une faible utilisation peut masquer une attente sur la base ou le réseau.

Les percentiles deviennent instables lorsque le nombre d’échantillons est faible. Exécute suffisamment longtemps pour observer un comportement stable et plusieurs périodes de trafic. Note la période de chauffe, les erreurs de préparation et la façon dont les résultats sont agrégés. Ne supprime pas silencieusement les timeouts : ils font partie de l’expérience utilisateur.

4. Construire et exécuter un scénario

Avec un outil comme k6, le script décrit les requêtes et les seuils de validation. Exemple simplifié :

import http from 'k6/http';
import { check, sleep } from 'k6';

export const options = {
  vus: 10,
  duration: '2m',
  thresholds: {
    http_req_failed: ['rate<0.01'],
    http_req_duration: ['p(95)<500'],
  },
};

export default function () {
  const res = http.get('https://test.example.invalid/api/items');
  let body = null;
  try {
    body = res.json();
  } catch (_) {
    // Une réponse non JSON doit faire échouer le contrôle de contrat.
  }

  check(res, {
    'statut 200': (r) => r.status === 200,
    'type de contenu JSON': (r) => String(
      r.headers['Content-Type'] || r.headers['content-type'] || ''
    ).toLowerCase().includes('application/json'),
    'corps conforme au contrat': () => body !== null && Array.isArray(body.data),
  });
  sleep(1);
}

Ce fragment suppose que l’API renvoie un objet JSON contenant un tableau data ; adapte ce contrôle au contrat réel. L’adresse est fictive et doit être remplacée par un environnement que tu es autorisé à tester. Les seuils sont des exemples, pas des objectifs universels. Un script de test doit gérer l’authentification de test, éviter les secrets dans le dépôt, créer ou nettoyer ses données et vérifier les réponses métier.

Commence par une charge faible afin de valider le script et d’établir une référence. Augmente ensuite la pression par paliers et laisse le système se stabiliser à chaque palier. Arrête le test si les erreurs ou la charge sur une dépendance dépassent les limites convenues. Le générateur lui-même peut devenir le goulot ; surveille ses ressources et, si nécessaire, distribue la charge.

5. Lire les résultats et choisir la suite

Quand la latence se dégrade, compare sa chronologie à celle des métriques système. Si le CPU est saturé et que les profils montrent une fonction dominante, le travail peut porter sur le calcul ou le parallélisme. Si les connexions SQL sont épuisées, examine les durées de requêtes, la taille du pool et les transactions longues. Si le service dépend d’une API externe, vérifie ses délais et les limites de débit. Ne conclus pas à un manque de serveurs avant d’avoir identifié la ressource limitante.

Répète le test après un changement avec le même scénario et les mêmes conditions. Compare débit, percentiles, erreurs et consommation des ressources. Une hausse du débit accompagnée d’un p99 beaucoup plus élevé peut ne pas être acceptable. Documente les limites connues, les écarts entre test et production et les hypothèses non vérifiées.

  • Ne confonds pas utilisateurs virtuels et requêtes par seconde.
  • Ne tire pas de conclusion d’un seul lancement non reproductible.
  • Ne teste pas une production sans autorisation et coordination.
  • Ne mesure pas uniquement le temps moyen ou le taux de réussite HTTP.
  • Ne néglige pas le générateur, le réseau ou les systèmes tiers.

6. Exercice pratique

Crée un scénario de lecture sur un environnement de test, avec un palier de chauffe puis trois paliers de charge. Fixe un objectif de p95 et de taux d’erreur. Enregistre les métriques applicatives et système, identifie le premier signe de saturation, puis propose une seule hypothèse d’amélioration. Après correction, rejoue le même test et rédige une conclusion chiffrée. Si aucun goulot n’apparaît, indique jusqu’à quelle charge les objectifs restent respectés au lieu d’inventer une limite.

Critères de réussite

  • Je sais formuler une hypothèse et un objectif mesurable avant le test.
  • Je distingue charge nominale, stress, endurance, pic et capacité.
  • Je surveille latence par percentiles, débit, erreurs et ressources.
  • Je contrôle la sécurité et l’autorisation de l’environnement testé.
  • Je compare les versions avec des scénarios reproductibles et des conclusions nuancées.

Atelier approfondi — concevoir un test de charge exploitable

Objectifs pédagogiques

  • Définir un profil de trafic réaliste plutôt qu’un simple nombre de requêtes.
  • Distinguer montée en charge, palier stable, pic, endurance et test de capacité.
  • Relier latence, débit, taux d’erreur et saturation à un objectif de service.

Profil de test

Décrire les parcours, proportions de requêtes, authentification, données et think time. Utiliser un environnement isolé et des données représentatives.

Protocole

Établir une ligne de base, échauffer le système, augmenter progressivement la charge, tenir un palier, puis revenir à la normale.

Mesures

Enregistrer p50/p95/p99, débit, erreurs, CPU, mémoire, pool de connexions et latence SQL. Une moyenne seule masque les queues de distribution.

Interprétation

Le générateur ne doit pas être le goulot. Vérifier ses ressources, la concurrence réellement atteinte et les limites du réseau.

Décision

Définir à l’avance les seuils d’arrêt et les critères de réussite; documenter la version, la configuration et les données du test.

Exercice pratique

Exécuter un test sur une API de catalogue : 20 utilisateurs virtuels au départ, puis paliers progressifs. Produire un rapport reproductible et expliquer pourquoi le p99 se dégrade.

Critères de réussite

  • Le profil reflète des parcours métier et pas seulement une boucle uniforme.
  • Le rapport contient p50/p95/p99, débit et erreurs.
  • La capacité du générateur est contrôlée.
  • Les seuils d’arrêt et la conclusion sont explicites.
