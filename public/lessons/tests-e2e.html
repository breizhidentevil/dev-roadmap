6. Tests, débogage et qualité

Tests end-to-end

Valider les parcours utilisateur essentiels dans une application complète.

Tutoriel approfondiQualité et tests

Objectifs et prérequis

À la fin, tu dois pouvoir sélectionner les parcours critiques, écrire un scénario de navigateur stable, préparer les données et diagnostiquer les échecs sans transformer la suite en collection de tests lents et fragiles.

  • Distinguer test E2E, test d’intégration et test unitaire.
  • Choisir des sélecteurs robustes et attendre les conditions utiles.
  • Organiser l’environnement, les comptes et les traces de diagnostic.

1. Ce que valide un test E2E

Un test end-to-end exerce le système depuis une interface proche de celle de l’utilisateur : navigateur, frontend, API et dépendances nécessaires. Il vérifie qu’un parcours complet fonctionne, par exemple se connecter, créer une commande et voir la confirmation.

Cette portée est précieuse, mais un échec peut avoir plusieurs causes et le test est plus coûteux à exécuter. Il ne faut donc pas reproduire chaque combinaison de règles métier en E2E : teste les règles en unité, les contrats entre composants en intégration, et réserve les tests E2E aux parcours qui justifient ce coût.

2. Écrire un scénario lisible

Exemple avec Playwright :

import { test, expect } from "@playwright/test";

test("un utilisateur crée une tâche", async ({ page }) => {
  await page.goto("/tasks");

  await page.getByRole("button", { name: "Nouvelle tâche" }).click();
  await page.getByLabel("Titre").fill("Préparer la release");
  await page.getByRole("button", { name: "Enregistrer" }).click();

  await expect(
    page.getByRole("heading", { name: "Préparer la release" })
  ).toBeVisible();
});

Les libellés doivent correspondre à l’interface de l’application. Les sélecteurs accessibles par rôle et nom reflètent mieux l’expérience utilisateur que des classes CSS internes. Si un composant ne peut pas être identifié de manière accessible, cela peut aussi révéler un problème d’accessibilité.

Un scénario utile décrit une intention et un résultat observable : « créer une tâche et la retrouver dans la liste », plutôt que « cliquer sur le troisième bouton ». Évite aussi de vérifier seulement le toast de succès : si la confirmation s’affiche avant l’enregistrement ou si la liste n’est pas rafraîchie, le parcours peut sembler réussir alors que la ressource est perdue. Pour les opérations critiques, vérifie l’état final par l’interface ou par une préparation/inspection contrôlée hors du parcours utilisateur.

3. Éviter les attentes fragiles

N’utilise pas des pauses fixes comme waitForTimeout(3000) pour espérer que la page soit prête. Elles ralentissent les tests rapides et restent insuffisantes sur les environnements lents. Préfère les assertions qui attendent automatiquement l’état attendu, par exemple visibilité d’un élément, réponse d’une action ou navigation.

Ne dépends pas des coordonnées de souris, des classes CSS générées ou du texte ambigu si un rôle accessible et un libellé précis sont disponibles. Un test doit échouer quand le comportement change, pas parce qu’un détail de mise en page a été renommé sans effet utilisateur.

4. Données et authentification

Chaque test doit commencer dans un état connu. Utilise des comptes de test dédiés, crée les données via une API de préparation lorsque c’est approprié et supprime-les après usage. Évite que plusieurs tests modifient simultanément le même compte ou la même ressource.

Pour accélérer une suite, certains outils permettent de réutiliser un état authentifié. Protège le fichier de session et ne le partage pas avec des utilisateurs ou environnements de production. Il reste important de tester au moins un parcours réel de connexion lorsque l’authentification fait partie des risques fonctionnels à couvrir.

Attribue à chaque test une ressource unique, par exemple un titre avec un suffixe propre à l’exécution, ou prépare une base isolée. Si plusieurs tests utilisent le même compte, évite qu’ils modifient la même ressource ; sinon, un test peut supprimer ce que l’autre attend. Pour les scénarios d’autorisation, prépare un compte réellement limité et vérifie qu’il ne peut ni lire ni modifier la ressource protégée, sans te contenter de masquer le bouton dans l’interface.

5. Fiabilité en CI et diagnostic

Les tests E2E doivent être exécutables de façon reproductible dans la CI : versions d’outils maîtrisées, application démarrée et prête, variables d’environnement explicites, base de test isolée et dépendances externes contrôlées. Active captures d’écran, vidéo ou traces au premier échec selon les capacités du runner, en veillant à ne pas capturer des secrets ou données réelles.

Les nouvelles tentatives automatiques peuvent aider à diagnostiquer un test intermittent, mais ne doivent pas servir à masquer durablement l’instabilité. Suis les tests qui échouent de façon aléatoire et traite la cause : données partagées, attente incorrecte, réseau externe ou état non nettoyé.

Au premier échec, conserve une trace utile : étape échouée, URL, capture ou trace du navigateur, console et requêtes réseau pertinentes. Avant de publier ces artefacts, retire les cookies, jetons, données personnelles et informations métier confidentielles. Une trace trop complète peut devenir une fuite de données ; une trace trop pauvre oblige à reproduire l’incident à l’aveugle.

Erreurs fréquentes

  • Tester toute la logique métier uniquement dans le navigateur.
  • Employer des pauses fixes au lieu d’attendre un état précis.
  • Utiliser des sélecteurs dépendants du style interne.
  • Partager des données ou comptes entre tests parallèles.
  • Rendre les tests dépendants d’un service tiers réel.
  • Ignorer les tests intermittents parce qu’une relance finit par réussir.

Exercice guidé

Écris un test E2E qui ouvre la page de connexion d’une application de test, se connecte avec un compte dédié, crée une ressource et vérifie qu’elle apparaît dans la liste. Ajoute un scénario qui tente une action interdite avec un compte de droits limités.

Exécute les tests plusieurs fois et en parallèle si ton runner le permet. Vérifie que les données ne se chevauchent pas et qu’un échec produit des éléments utiles au diagnostic.

Exercice autonome et critères de réussite

Choisis trois parcours utilisateur essentiels de ton projet et justifie pourquoi ils méritent un test E2E plutôt qu’un test plus bas dans la pyramide.

Réussite : les tests couvrent un parcours de bout en bout ; les sélecteurs sont robustes et accessibles ; les attentes portent sur des états observables ; les données sont isolées ; les secrets et données personnelles sont exclus des artefacts ; les tests s’exécutent en CI et les échecs sont diagnostiquables. Exécute chaque scénario plusieurs fois et en parallèle si le runner le permet ; aucun test ne doit dépendre d’une ressource créée par un autre test.
