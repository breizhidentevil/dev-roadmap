2. Frontend

Tests frontend

Construire une stratégie de tests frontend fondée sur le risque : vérifier la logique, les interactions accessibles et les parcours réels sans rendre la suite fragile.

Tutoriel détailléLot 9 · 2026

Objectifs d’apprentissage

  • Choisir le niveau de test adapté au risque.
  • Tester le comportement plutôt que les détails internes.
  • Écrire des tests déterministes et lisibles.
  • Automatiser les parcours critiques sans rendre la suite fragile.

Fil conducteur

Partir du risque produit, choisir le niveau de test le moins coûteux qui le couvre, puis ajouter quelques parcours intégrés pour vérifier que les couches fonctionnent ensemble.

1. Choisir le bon niveau de test

Un test unitaire vérifie une petite unité de logique ; un test de composant vérifie l’interaction d’une partie de l’interface avec son environnement ; un test end-to-end (E2E) vérifie un parcours utilisateur à travers l’application en fonctionnement. Ces niveaux sont complémentaires et n’ont pas le même coût d’exécution ni de maintenance.

Teste en priorité les règles métier, les états d’erreur, les formulaires et les parcours dont la régression aurait un impact important. Une grande quantité de tests ne garantit pas une bonne couverture des risques : choisis des scénarios représentatifs.

2. Tester comme un utilisateur

Testing Library encourage à retrouver les éléments comme le ferait un utilisateur : par rôle accessible, nom, libellé ou texte visible. Ce choix favorise des tests qui détectent aussi certains problèmes d’accessibilité.

import { expect, test, vi } from "vitest";
import { render, screen } from "@testing-library/react";
import userEvent from "@testing-library/user-event";
import { LoginForm } from "./LoginForm";

test("soumet l’adresse saisie", async () => {
  const user = userEvent.setup();
  const onSubmit = vi.fn();
  render(<LoginForm onSubmit={onSubmit} />);
  await user.type(
    screen.getByRole("textbox", { name: /e-mail/i }),
    "personne@example.test"
  );
  await user.click(screen.getByRole("button", { name: /connexion/i }));
  expect(onSubmit).toHaveBeenCalled();
});

Le code suppose que `LoginForm` expose une prop `onSubmit`, que ses champs portent les libellés indiqués et que Vitest, Testing Library et `user-event` sont installés. Crée une instance de `userEvent` avec `userEvent.setup()` dans chaque test qui simule des interactions. Évite de sélectionner un élément uniquement par une classe CSS ou un détail de structure DOM si ce n’est pas le contrat fonctionnel visé.

3. Gérer l’asynchronisme

Les interfaces mettent souvent à jour leur contenu après une requête ou une interaction asynchrone. Utilise les mécanismes d’attente de la bibliothèque de test plutôt que des délais fixes. Les attentes doivent porter sur un résultat observable, par exemple un message de succès qui apparaît.

Les tests deviennent fragiles lorsqu’ils dépendent de l’heure, d’un réseau externe ou d’un ordre d’exécution implicite. Remplace les services externes par des réponses contrôlées lorsque le but est de tester l’interface, et réserve les tests intégrés aux environnements appropriés.

4. Tests E2E avec Playwright ou Cypress

Un test E2E ouvre l’application dans un navigateur et suit un parcours proche de l’usage réel : connexion, recherche, création d’un élément ou achat simulé. Ces tests couvrent les interactions entre le frontend, les routes et les services configurés, mais ils sont plus lents et demandent un environnement reproductible.

test("la recherche affiche un résultat", async ({ page }) => {
      await page.goto("/products");
      await page.getByRole("searchbox").fill("clavier");
      await expect(page.getByText("Clavier mécanique")).toBeVisible();
    });

Le chemin relatif de `page.goto` est résolu par rapport à `use.baseURL` dans `playwright.config.ts`. Si `baseURL` n’est pas défini, passe une URL absolue ; démarre le serveur de test avant la suite. Utilise des sélecteurs robustes, des données de test isolées et des attentes sur l’état de la page. Évite de dépendre de services publics instables ou de données de production.

5. Fiabilité et intégration continue

Un test doit échouer quand le comportement est incorrect et réussir de manière répétable quand il est correct. Les tests aléatoires ou dépendants de l’ordre rendent la CI peu fiable et incitent l’équipe à ignorer les échecs.

Structure la suite pour obtenir un retour rapide : tests unitaires et composants d’abord, puis E2E ciblés sur les parcours critiques. En CI, exécute les tests sur une installation reproductible, collecte les rapports et captures utiles, et ne masque pas les échecs par des relances répétées sans diagnostic.

Exercice guidé

Écris des tests pour un formulaire de recherche : rendu initial, résultat trouvé, absence de résultat, erreur de service et soumission au clavier. Ajoute un test E2E qui suit le parcours depuis l’ouverture de la page jusqu’à l’affichage du résultat.

Critères de réussite

  • Les tests utilisent des rôles et libellés accessibles.
  • Les cas nominal, vide et erreur sont couverts.
  • Les attentes sont basées sur des résultats observables.
  • Les données de test sont isolées et reproductibles.
  • La suite s’exécute en CI et ses échecs sont diagnostiquables.

Erreurs fréquentes

  • Tester les détails d’implémentation plutôt que le comportement.
  • Utiliser des temporisations arbitraires pour attendre un rendu.
  • Faire dépendre les tests de données externes instables.
  • Ne tester que le cas nominal.
  • Multiplier les E2E lents pour des règles qui peuvent être testées plus simplement.

Évite de vérifier trois fois le même détail à des niveaux différents ; réserve les tests les plus lents aux risques qu’ils sont seuls à couvrir.

Repère pratique. Quand un test échoue de façon intermittente, distingue un vrai défaut d’une course temporelle : identifie l’événement attendu, attends cet état précis, et assure-toi que les données et le réseau sont contrôlés. Un délai fixe ne prouve pas que l’application a terminé son travail.

Repère pratique. Pour diagnostiquer un échec, conserve le message d’assertion, les logs et, pour un E2E, la capture ou la trace. Ne transforme pas automatiquement tout échec en nouvelle tentative : cela peut cacher une instabilité qui doit être corrigée.
