6. Tests, débogage et qualité

Tests d’intégration

Vérifier que plusieurs composants collaborent correctement à travers leurs interfaces.

Tutoriel approfondiQualité et tests

Objectifs et prérequis

Tu dois savoir écrire quelques tests unitaires et comprendre les interfaces entre modules. À la fin, tu pourras choisir les dépendances réelles à inclure, préparer un environnement isolé et tester des scénarios tels qu’une requête HTTP avec accès à une base de données de test.

  • Distinguer un test unitaire d’un test d’intégration.
  • Tester les contrats entre couches plutôt que toutes les combinaisons possibles.
  • Rendre l’environnement et les données reproductibles.

1. Ce que l’intégration permet de détecter

Des unités peuvent passer leurs tests isolés tout en échouant ensemble : configuration de connexion incorrecte, requête SQL incompatible avec le schéma, sérialisation inattendue, middleware absent ou transaction mal gérée. Les tests d’intégration exercent plusieurs composants réels à travers leurs interfaces.

Un test d’intégration peut démarrer un serveur HTTP et une base de données jetable, appeler un endpoint, puis vérifier le statut, le corps et l’effet en base. Il est généralement plus lent qu’un test unitaire, mais donne une preuve plus forte que les composants s’accordent réellement.

2. Définir la frontière du test

Décide ce qui sera réel et ce qui sera simulé. Pour un test d’API avec base de données, conserve souvent le routeur, la validation, la logique métier et la base réelle de test ; remplace éventuellement un service tiers coûteux par un faux serveur ou un stub contrôlé.

Évite de remplacer précisément le composant dont tu veux vérifier l’intégration. Si la question est « le dépôt enregistre-t-il correctement la commande dans PostgreSQL ? », mocker le dépôt rend le test incapable de répondre. À l’inverse, appeler un service de paiement réel n’est généralement ni nécessaire ni souhaitable.

3. Préparer des données isolées

Chaque test doit disposer d’un état connu. Les stratégies courantes sont une base éphémère, un schéma par exécution, des transactions annulées après le test ou un nettoyage explicite. Choisis une stratégie compatible avec le comportement testé : une transaction externe peut masquer un problème de commit ou ne pas isoler correctement plusieurs connexions.

Utilise des données synthétiques et déterministes. Évite les bases de production et les comptes personnels. Les tests ne doivent pas dépendre d’un ordre particulier, d’un identifiant déjà présent ou d’un état laissé par la suite précédente.

4. Exemple de test HTTP + persistance

Exemple conceptuel avec un endpoint de création de tâche :

it("crée une tâche persistée", async () => {
  const response = await request(app)
    .post("/api/tasks")
    .send({ title: "Préparer la release" });

  expect(response.status).toBe(201);
  expect(response.body.title).toBe("Préparer la release");

  const stored = await db.task.findUnique({
    where: { id: response.body.id }
  });
  expect(stored?.title).toBe("Préparer la release");
});

Les fonctions request et db représentent les outils de ton projet, pas une API universelle. Le test doit initialiser une base de test et nettoyer les données. Vérifie aussi le comportement invalide, par exemple un titre manquant, et assure-toi qu’aucune ligne n’est créée lorsque la validation échoue.

Ne te limite pas au statut HTTP : vérifie les invariants persistants. Pour une création qui écrit dans plusieurs tables, teste qu’une erreur au milieu de l’opération n’en laisse pas une partie enregistrée. Par exemple, si la commande est créée mais qu’une ligne de commande échoue, le résultat attendu peut être un rollback complet. Le test doit observer la base après la réponse, pas seulement inspecter un objet en mémoire.

Pour rendre l’assertion fiable, distingue les données créées par le test de celles déjà présentes : utilise un identifiant connu ou une requête filtrée sur une clé unique. Une assertion sur le nombre total de lignes est fragile dès que les tests peuvent s’exécuter en parallèle.

Isoler et nettoyer sans masquer un échec

Prépare le schéma et applique les migrations avant la suite ; ferme les connexions et arrête les services après les tests. Pour un exemple simple exécuté de façon séquentielle, une liste d’identifiants créés permet un nettoyage ciblé :

const createdTaskIds: string[] = [];

afterEach(async () => {
  if (createdTaskIds.length > 0) {
    await db.task.deleteMany({
      where: { id: { in: createdTaskIds } }
    });
  }
  createdTaskIds.length = 0;
});

Cette syntaxe de nettoyage illustre une API de type ORM et doit être adaptée au projet. Ajoute l’identifiant à la liste dès que la création réussit. Pour les suites parallèles ou les tests qui peuvent échouer avant de récupérer l’identifiant, préfère une base ou un schéma isolé par worker, des noms de ressources propres au test ou une base éphémère détruite en fin de suite. N’utilise jamais un nettoyage global sur une base partagée.

Ajoute aussi un cas de validation invalide : envoie un titre absent ou vide, vérifie le statut d’erreur contractuel (souvent 400 ou 422) et confirme qu’aucune ressource n’a été créée. Une comparaison du nombre de lignes avant/après n’est fiable que dans une base isolée et sans écritures concurrentes ; sinon, recherche par identifiant unique ou isole davantage le test.

5. Temps, dépendances et diagnostic

Les tests d’intégration peuvent échouer à cause d’un port occupé, d’un service non démarré ou d’une course sur les migrations. Réduis ces aléas en démarrant explicitement les dépendances, en attendant leur état prêt, en fixant les versions des images et en affichant les logs utiles lors d’un échec.

Les tests qui touchent le réseau externe doivent éviter de dépendre de la disponibilité de tiers. Utilise des environnements sandbox contrôlés ou des doubles de service. Si un test échoue, le rapport doit aider à distinguer un bug applicatif d’un environnement de test défaillant.

La correction doit viser la cause identifiée : une temporisation plus longue n’est pas une solution si le service n’est jamais prêt, et un nettoyage global n’est pas acceptable s’il peut supprimer les données d’un autre test.

Erreurs fréquentes

  • Appeler le test « intégration » alors que toutes les dépendances sont mockées.
  • Partager une base persistante entre développeurs ou CI sans isolation.
  • Ne pas tester l’effet en base après une réponse HTTP réussie.
  • Nettoyer les données de manière incomplète et créer des tests dépendants de l’ordre.
  • Utiliser un service externe réel pour un scénario qui n’en a pas besoin.
  • Ignorer les migrations et la configuration de la base de test.

Exercice guidé

Ajoute un test d’intégration à un endpoint de création de ressource. Le test doit démarrer l’application, utiliser une base isolée, envoyer une requête valide, vérifier le code de statut et relire l’enregistrement en base. Ajoute ensuite un test de validation invalide et vérifie qu’aucune donnée n’a été créée.

Exécute la suite deux fois de suite et dans un ordre différent. Le résultat ne doit pas dépendre de données laissées par la première exécution.

Exercice autonome et critères de réussite

Définis un petit plan de tests d’intégration pour un endpoint qui crée une commande avec plusieurs lignes et vérifie le stock.

Réussite : la frontière de test est explicite ; les dépendances critiques sont réelles ; les données sont isolées ; les migrations sont exécutées ; le test vérifie la réponse et l’état persistant ; les échecs sont diagnostiquables ; aucun service de production n’est utilisé. Lance la suite deux fois et en parallèle si possible, puis démontre qu’une erreur simulée pendant une écriture multiple ne laisse pas de données partielles lorsque la règle exige l’atomicité.
