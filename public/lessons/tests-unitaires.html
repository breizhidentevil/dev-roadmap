6. Tests, débogage et qualité

Tests unitaires

Vérifier une unité de comportement isolée avec des tests rapides et ciblés.

Tutoriel approfondiQualité et tests

Objectifs et prérequis

À la fin, tu dois pouvoir identifier une unité testable, écrire un test lisible qui vérifie un comportement, choisir des cas nominaux et limites, et comprendre quand un mock aide ou masque un problème.

  • Distinguer test unitaire et test d’intégration.
  • Structurer un test avec préparation, action et assertions.
  • Éviter les tests fragiles liés aux détails d’implémentation.

1. Tester un comportement, pas une ligne de code

Un test unitaire vérifie une petite unité de comportement de façon suffisamment isolée pour localiser rapidement un échec. L’unité peut être une fonction, un objet ou une règle métier ; il n’existe pas de taille universelle, mais un test doit rester rapide, déterministe et facile à comprendre.

Un bon test exprime une règle : « une remise ne peut pas rendre le total négatif », plutôt que « la fonction appelle telle méthode privée ». Si l’implémentation change sans changer le contrat observable, le test de comportement devrait généralement continuer à passer.

2. Structure Arrange–Act–Assert

Un test lisible sépare trois étapes : préparer les données, exécuter l’action, vérifier le résultat.

import { describe, expect, it } from "vitest";

function totalAfterDiscount(price: number, discount: number) {
  if (price < 0 || discount < 0 || discount > 1) {
    throw new Error("invalid_input");
  }
  return Math.round(price * (1 - discount) * 100) / 100;
}

describe("totalAfterDiscount", () => {
  it("applique une remise de 10 %", () => {
    // Arrange
    const price = 50;
    const discount = 0.1;

    // Act
    const total = totalAfterDiscount(price, discount);

    // Assert
    expect(total).toBe(45);
  });
});

L’exemple utilise des nombres simples et une règle de validation explicite. Pour des montants financiers réels, préfère généralement une représentation entière en centimes ou une bibliothèque décimale adaptée afin d’éviter les erreurs de flottants binaires.

3. Choisir les cas de test

Pour chaque règle, pense à :

  • cas nominal : entrée valide et résultat attendu ;
  • frontières : zéro, minimum, maximum et valeurs juste au-delà ;
  • entrées invalides : types ou valeurs interdits ;
  • règles combinées : deux conditions qui interagissent ;
  • régression : cas qui reproduit un bug corrigé.

Le but n’est pas de multiplier les tests identiques, mais de couvrir les décisions significatives. Les tests basés sur des tables de cas sont utiles lorsqu’une même fonction doit respecter plusieurs combinaisons. Dans Vitest, it.each permet de rendre ces combinaisons visibles sans copier-coller la même structure :

it.each([
  { price: -1, discount: 0 },
  { price: 50, discount: -0.1 },
  { price: 50, discount: 1.01 },
])("refuse les entrées invalides : prix=$price, remise=$discount", ({ price, discount }) => {
  expect(() => totalAfterDiscount(price, discount)).toThrow("invalid_input");
});

Chaque ligne du tableau doit correspondre à un résultat attendu distinct. Ajoute aussi les cas de prix négatif et de remise négative, car ils exercent des branches de validation différentes. Ne regroupe pas des cas dont l’échec demanderait des diagnostics différents.

4. Doubles de test et isolation

Un mock, stub ou fake remplace une dépendance pour contrôler son comportement. Cela peut rendre un test rapide et déterministe, par exemple en simulant une horloge ou un service externe. Mais si tu mocks chaque fonction interne, tu peux finir par tester surtout la structure actuelle du code.

Garde les règles métier pures autant que possible. Injecte les dépendances externes, comme le stockage ou l’horloge, pour pouvoir les remplacer facilement. Ne mocke pas un composant si le vrai composant est simple, stable et nécessaire pour prouver le comportement recherché.

5. Fiabilité et lisibilité

Un test doit être déterministe : il ne devrait pas dépendre de l’ordre d’exécution, d’un réseau instable ou de l’heure réelle. Nettoie les mocks entre les tests, contrôle l’horloge lorsque c’est nécessaire et évite de partager un état mutable entre plusieurs cas.

Un échec doit indiquer rapidement ce qui est attendu et ce qui s’est produit. Donne des noms descriptifs aux tests et évite les assertions multiples sans rapport dans un même cas. La couverture de lignes peut signaler des zones peu exercées, mais elle ne mesure pas à elle seule la qualité des assertions.

Une vérification complémentaire consiste à modifier temporairement une condition ou une valeur de retour pour simuler un défaut (par exemple, remplacer la remise appliquée par zéro). Si tous les tests passent encore, ils n’observent probablement pas le comportement important. Cette démarche manuelle reprend l’idée des tests de mutation : évaluer si la suite détecte des changements incorrects, et pas seulement si elle exécute le code.

Quand un test échoue, classe d’abord le problème : résultat métier incorrect, donnée de préparation invalide, mock non configuré ou état partagé. Réduis le test à la plus petite entrée qui reproduit le défaut avant de changer les assertions.

Erreurs fréquentes

  • Tester uniquement le cas nominal et oublier les frontières.
  • Écrire des tests qui vérifient des détails privés plutôt que le contrat.
  • Faire des appels réseau réels dans un test supposé unitaire.
  • Utiliser des mocks si nombreux que le test ne reflète plus le comportement réel.
  • Accepter un test intermittent sans chercher la cause.
  • Prendre le pourcentage de couverture pour une preuve de correction.

Exercice guidé

Écris des tests unitaires pour une fonction qui calcule le prix d’un panier avec une remise comprise entre 0 et 1. Couvre le panier vide, le prix nul, la remise nulle, la remise maximale autorisée, une remise invalide et un montant négatif.

Fais ensuite évoluer l’implémentation sans modifier le contrat. Si les tests cassent à cause d’un renommage interne alors que le comportement reste correct, révise les assertions.

Exercice autonome et critères de réussite

Choisis une règle métier de ton projet et écris une suite de tests indépendants, rapides et reproductibles. Ajoute au moins un test de frontière et un test d’entrée invalide.

Réussite : chaque test possède un nom qui décrit le comportement ; les données sont contrôlées ; les assertions échouent si la règle est violée ; aucun réseau ni service réel n’est requis ; les tests peuvent être lancés plusieurs fois avec le même résultat ; les mocks restent limités aux dépendances nécessaires. Pour le prouver, exécute la suite deux fois, puis introduis volontairement une petite erreur dans la règle et confirme qu’au moins un test échoue avant de restaurer le code.
