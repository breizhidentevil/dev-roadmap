Timeouts, retries et annulation

Maîtriser les délais d’attente, les tentatives répétées et l’annulation pour rendre les appels réseau robustes sans amplifier les pannes.

1. Objectifs et prérequis

Un appel réseau peut être lent, échouer temporairement ou continuer à travailler alors que son résultat n’intéresse plus l’appelant. Une stratégie robuste combine des délais d’attente, des tentatives répétées contrôlées et une annulation qui se propage aux opérations concernées. À la fin, vous saurez distinguer ces mécanismes, choisir des valeurs cohérentes et éviter qu’une politique de reprise transforme une panne ponctuelle en surcharge. Il faut connaître les promesses JavaScript, fetch, HTTP et la gestion des erreurs.

2. Le timeout : limiter le temps d’attente

Un timeout définit une limite au temps pendant lequel un appelant accepte d’attendre. Il ne prouve pas que le serveur a cessé de travailler : il signifie que le client ne souhaite plus attendre le résultat. La requête a pu atteindre le serveur et produire un effet, même si le client n’a pas reçu la réponse. Cette distinction est cruciale pour les opérations qui créent une commande, un paiement ou une réservation.

Il n’existe pas de délai universel. Le choix dépend du budget de latence de l’application, du comportement du service appelé, des délais de connexion et de réponse, et de l’expérience utilisateur attendue. Un timeout trop court provoque des échecs inutiles ; un timeout trop long immobilise des ressources et dégrade la réactivité. Mesurez les latences réelles et définissez un budget explicite par type d’opération.

3. Annuler un appel avec AbortController

Dans les environnements qui le prennent en charge, AbortController permet d’annuler un fetch en transmettant son signal. Un délai peut être géré avec AbortSignal.timeout() dans les environnements compatibles, ou avec un contrôleur et un timer. L’annulation doit être distinguée d’une erreur serveur et d’un timeout selon les conventions du runtime.

async function loadProfile(
  url: string,
  callerSignal?: AbortSignal
): Promise<unknown> {
  const timeoutSignal = AbortSignal.timeout(4_000);
  const signal = callerSignal
    ? AbortSignal.any([callerSignal, timeoutSignal])
    : timeoutSignal;

  try {
    const response = await fetch(url, { signal });
    if (!response.ok) {
      throw new Error(`HTTP ${response.status}`);
    }
    return await response.json();
  } catch (error) {
    if (signal.aborted && signal.reason?.name === "TimeoutError") {
      throw new Error("Délai maximal de lecture du profil dépassé.");
    }
    throw error; // conserver notamment l’annulation demandée par l’appelant
  }
}

Cette variante utilise AbortSignal.timeout() et AbortSignal.any(), disponibles dans les runtimes modernes ; vérifiez leur compatibilité avant de l’adopter. Sur un runtime plus ancien, relayez explicitement le signal de l’appelant vers un contrôleur et nettoyez le timer dans finally. Un timeout et une annulation utilisateur ne doivent pas être présentés comme la même erreur : l’interface peut ignorer une annulation volontaire, mais doit généralement signaler un délai dépassé.

4. Propager l’annulation

Créer un contrôleur n’est utile que si son signal atteint l’opération qu’on veut arrêter. Dans une chaîne de fonctions, transmettez le signal explicitement plutôt que de le garder caché dans un état global. Une fonction qui ignore le signal peut continuer son travail, même si le composant qui l’a appelée s’est démonté.

L’annulation n’est pas une garantie d’annulation transactionnelle. Interrompre la lecture de la réponse ne restaure pas automatiquement l’état distant. Pour une opération qui modifie des données, le serveur doit lui-même vérifier les conditions d’annulation et garantir une sémantique cohérente, lorsque c’est possible. À défaut, concevez la reprise en supposant que le résultat peut être incertain.

5. Quand réessayer ?

Un retry répète une opération après un échec considéré comme temporaire. Il convient parfois aux erreurs réseau, aux limites de débit ou à certains statuts de service indisponible. Il est rarement pertinent de répéter aveuglément une requête mal formée ou une erreur d’autorisation. La décision dépend du type d’opération, de la cause probable et du contrat de l’API.

Avant de réessayer, posez trois questions : l’échec est-il probablement temporaire ? La requête peut-elle être répétée sans effet indésirable ? Le budget de temps permet-il une nouvelle tentative ? Si le client a perdu la connexion après l’envoi d’une requête de création, il ne sait pas nécessairement si le serveur l’a exécutée. Sans mécanisme d’idempotence, un retry peut créer un doublon.

  • À examiner selon le contrat : erreurs réseau, 408, 429, 502, 503 et 504. Respectez Retry-After lorsqu’il est fourni et compatible avec l’échéance globale.
  • Pas de retry automatique par défaut : erreurs de validation (400/422) et d’autorisation (401/403). Un 500 n’est relançable que si le contrat et la sûreté de l’opération le justifient.
  • Définissez si « trois tentatives » signifie trois essais au total ou trois retries après l’essai initial ; consignez cette convention dans les tests.

6. Backoff exponentiel et jitter

Des retries immédiats peuvent synchroniser de nombreux clients qui réessaient ensemble, augmentant la charge sur un service déjà dégradé. Le backoff exponentiel augmente progressivement le délai entre les tentatives. Le jitter ajoute une variation aléatoire afin que les clients ne se réveillent pas tous au même instant.

function retryDelayMs(attempt: number): number {
  const base = 250;
  const cap = 8_000;
  const ceiling = Math.min(cap, base * 2 ** attempt);
  return Math.random() * ceiling; // full jitter
}

Ce fragment illustre un délai possible ; il ne constitue pas à lui seul une politique de retry. Fixez un nombre maximal de tentatives, un délai maximal, un budget total et des erreurs admissibles. Si le serveur renvoie un en-tête de limitation tel que Retry-After, tenez compte du contrat et évitez de réessayer avant le délai demandé.

7. Le budget global et les retries en cascade

Un timeout de quatre secondes appliqué à chaque tentative ne signifie pas que l’opération complète durera quatre secondes. Trois tentatives et leurs pauses peuvent dépasser largement ce budget. Définissez donc une échéance globale et n’autorisez une nouvelle tentative que si elle peut raisonnablement finir avant cette échéance.

Les retries à plusieurs niveaux peuvent se multiplier. Si un navigateur réessaie trois fois, un service intermédiaire trois fois et une bibliothèque interne trois fois, la dépendance finale peut recevoir beaucoup plus d’appels que prévu. Décidez quel niveau possède la politique de reprise, documentez-la et limitez le nombre total d’essais. Les mécanismes de circuit breaker ou de limitation de concurrence peuvent compléter cette stratégie, mais ne remplacent pas le bon choix des délais.

8. Erreurs fréquentes et compromis

  • Réessayer toutes les erreurs, y compris celles qui ne peuvent pas être corrigées par une nouvelle tentative.
  • Répéter une mutation sans garantie d’idempotence et créer des doublons.
  • Ne pas nettoyer les timers ou ne pas transmettre le signal d’annulation.
  • Choisir un timeout par intuition sans mesurer la latence.
  • Multiplier les retries dans plusieurs couches et amplifier la charge.
  • Traiter l’annulation côté client comme une preuve que le serveur n’a rien exécuté.

9. Exercice

Écrivez une fonction qui appelle un endpoint de lecture avec un timeout, puis ajoutez une politique de trois tentatives maximum pour les erreurs que vous jugez transitoires. Insérez un délai croissant avec jitter et un budget total. Simulez successivement une réponse réussie, une erreur HTTP permanente, une erreur temporaire et une requête annulée. Notez pourquoi la même politique ne doit pas être copiée sans adaptation sur un endpoint de création.

10. Critères de réussite

  • Je distingue timeout, annulation et erreur de réponse.
  • Je transmets le signal d’annulation à l’opération concernée.
  • Je limite les retries aux cas justifiés et aux opérations sûres à répéter.
  • Je sais expliquer le backoff, le jitter et le budget global.
  • Je tiens compte des effets possibles côté serveur après une coupure client.

Explications et exemple guidé

Un timeout limite le temps qu’un appel peut occuper ; un retry répète une opération après un échec jugé temporaire ; l’annulation indique que le résultat n’est plus nécessaire. Ces mécanismes doivent être conçus ensemble avec un budget de temps total et une politique de répétition bornée.

const controller = new AbortController();
const timeout = setTimeout(() => controller.abort(), 2500);
try {
  const response = await fetch(url, { signal: controller.signal });
  if (!response.ok) throw new Error(`HTTP ${response.status}`);
  return await response.json();
} finally {
  clearTimeout(timeout);
}

Ne relancez pas automatiquement toutes les erreurs : une erreur de validation ne devient pas temporaire au second essai. Respectez Retry-After lorsqu’il est applicable, utilisez un délai exponentiel avec jitter et limitez le nombre de tentatives. Les retries de mutations exigent une sémantique sûre ou une clé d’idempotence.

Pièges et limites

  • Piège : additionner plusieurs retries indépendants dans les couches réseau, service et client et multiplier la charge.
  • Piège : choisir un timeout plus long que le budget de la requête appelante.
  • Piège : oublier de propager le signal d’annulation ou de libérer les ressources.
  • Piège : relancer une mutation après un timeout alors que le serveur a peut-être déjà traité la demande.

Exercice

Définissez une politique pour une lecture GET : timeout par tentative, nombre maximal de tentatives, erreurs relançables, délai exponentiel avec jitter et budget total. Puis expliquez pourquoi cette politique ne doit pas être copiée telle quelle pour un paiement.

Critères de réussite

  • Le timeout et le budget global sont explicites.
  • Les retries sont bornés et réservés aux échecs transitoires.
  • L’annulation est propagée et les temporisateurs sont nettoyés.
  • Les mutations ne sont répétées que si leur sûreté est démontrée.
