Traces distribuées

Suivre le parcours d’une requête à travers plusieurs composants et comprendre où se produisent les délais ou les erreurs.

Leçon approfondieThéorie · pratique · validation

Objectifs d’apprentissage

À la fin de cette leçon, tu dois pouvoir expliquer les concepts avec tes propres mots, choisir une approche adaptée à un besoin réel et justifier tes choix à partir de contraintes observables.

  • Définir le vocabulaire essentiel et le problème que la compétence résout.
  • Appliquer les principes dans un exemple pratique et identifier les limites.
  • Vérifier le résultat avec des critères explicites plutôt qu’une impression subjective.

1. Pourquoi une trace ?

Dans un système composé de plusieurs services, une requête utilisateur peut traverser une passerelle, un backend, une base de données et plusieurs API externes. Les logs de chaque composant donnent des fragments de l’histoire, mais ils ne montrent pas toujours l’ordre des appels ni le temps consommé à chaque étape. Une trace distribuée représente ce parcours sous la forme d’un ensemble de spans reliés.

Une trace possède généralement un identifiant partagé. Chaque span décrit une opération, avec son nom, son début, sa durée, son statut et des attributs utiles. Les spans peuvent être imbriqués : un span parent représente le traitement HTTP global, tandis que des spans enfants décrivent une requête SQL et un appel réseau. Cette structure aide à repérer les attentes et les erreurs qui se propagent entre services.

La trace ne remplace ni les métriques ni les logs. Les métriques indiquent une tendance agrégée, par exemple un p95 qui augmente ; les traces aident à comprendre un échantillon de requêtes ; les logs décrivent des événements et des détails. Les trois signaux sont complémentaires, à condition de pouvoir les relier avec des identifiants cohérents.

2. Comprendre trace, span et propagation

Le trace ID identifie le parcours global. Le span ID identifie une opération particulière, et le lien parent-enfant représente la causalité ou la hiérarchie de traitement. Un span peut contenir des attributs comme la méthode HTTP, le nom de route ou le type d’opération, mais évite les données personnelles et les valeurs à cardinalité élevée qui ne sont pas nécessaires au diagnostic.

Pour continuer la trace au-delà d’une frontière réseau, le service appelant transmet un contexte de trace selon un format partagé, couramment le standard W3C Trace Context avec des en-têtes comme traceparent. Le service destinataire extrait ce contexte puis crée un nouveau span lié au même parcours. Si la propagation est interrompue, l’outil peut afficher plusieurs traces indépendantes et perdre la relation entre l’appel entrant et l’appel sortant.

La propagation de contexte doit être configurée et testée pour chaque protocole et chaque client. Ne suppose pas que toute bibliothèque instrumente automatiquement tous les appels. Les files de messages et les traitements asynchrones nécessitent aussi une propagation explicite ou un lien entre spans, selon la sémantique du flux.

3. Lire une trace de bout en bout

Commence par le span racine et regarde la durée totale. Identifie ensuite les spans enfants qui occupent le plus de temps. Attention : des spans imbriqués peuvent se chevaucher ; il ne faut donc pas additionner naïvement toutes les durées pour reconstituer le temps total. Une longue période sans span enfant peut représenter du travail non instrumenté, une attente ou une instrumentation incomplète.

Les erreurs doivent être interprétées dans leur contexte. Un span enfant en erreur peut entraîner l’échec du parent, mais certaines erreurs sont gérées et le traitement global réussit. Examine le statut, les attributs et les logs associés. Un code HTTP 500 peut être la conséquence d’un timeout en aval ; le span révèle parfois la première défaillance plutôt que le symptôme final.

Les traces peuvent aussi montrer un fan-out : un service lance plusieurs appels parallèles et attend leur résultat. Un seul appel lent peut dominer la latence totale même si la plupart des dépendances répondent vite. À l’inverse, de nombreux appels séquentiels courts peuvent s’additionner et devenir coûteux.

4. Instrumenter avec OpenTelemetry

OpenTelemetry fournit des API, des SDK et des conventions pour générer et exporter des traces. Dans une application, commence par l’instrumentation automatique supportée pour le serveur HTTP, le client HTTP et le pilote de base de données. Ajoute des spans manuels aux étapes métier où ils apportent un contexte absent des instrumentations standard.

// Exemple conceptuel : le nom de l'API varie selon le SDK.
const span = tracer.startSpan("commande.calculer-total");
try {
  const total = calculerTotal(lignes);
  span.setAttribute("commande.nb_lignes", lignes.length);
  return total;
} catch (error) {
  span.recordException(error);
  span.setStatus({ code: SpanStatusCode.ERROR });
  throw error;
} finally {
  span.end();
}

Ce code illustre les opérations, pas un fichier directement exécutable : les imports et les noms exacts dépendent du SDK et du langage. Termine toujours un span, y compris en cas d’exception. Les attributs doivent être stables, utiles et conformes à la politique de confidentialité. Évite de nommer chaque span avec un identifiant de commande unique ; conserve le nom d’opération et place seulement les attributs nécessaires.

5. Échantillonnage, coûts et sécurité

En production, enregistrer toutes les traces peut coûter cher et augmenter le volume de données. L’échantillonnage décide quelles traces sont conservées. Un échantillonnage en tête prend la décision tôt, avant de connaître le résultat complet ; il est efficace mais peut manquer des erreurs rares. Un échantillonnage en queue peut prendre en compte le statut ou la durée après collecte, au prix d’une architecture et d’une mémoire supplémentaires.

La propagation d’un contexte de trace entrant ne doit pas être considérée comme une preuve d’identité ou d’autorisation. Un client peut envoyer des en-têtes arbitraires. Valide et borne les attributs, limite les données sensibles, contrôle l’accès à l’interface de traces et définis une durée de conservation. Une trace peut exposer des URL, des identifiants ou des paramètres qui n’auraient pas dû être enregistrés.

Un taux d’échantillonnage trop faible peut masquer les problèmes rares ; un taux trop élevé peut dégrader le coût et la disponibilité du système d’observabilité. Adapte-le au trafic, au budget et à la criticité, puis vérifie que les parcours importants restent visibles.

6. Exercice pratique

Dessine le parcours d’une requête « créer une commande » à travers API, service de commandes, base et service de paiement. Pour chaque étape, définis le span, son parent, deux attributs non sensibles et les erreurs possibles. Décris ensuite comment le trace ID traverse l’appel HTTP et comment une erreur du prestataire serait repérée. Enfin, propose une règle d’échantillonnage qui conserve davantage les traces lentes ou en échec.

Critères de réussite

  • Je distingue trace ID, span ID et relation parent-enfant.
  • Je sais expliquer la propagation du contexte entre services.
  • Je repère les délais dominants sans additionner abusivement les spans imbriqués.
  • Je connais le rôle d’OpenTelemetry et les limites de l’échantillonnage.
  • Je n’ajoute pas de secrets ni de données personnelles inutiles aux traces.

Atelier approfondi — lire une trace distribuée de bout en bout

Objectifs pédagogiques

  • Comprendre spans, traces, parenté et propagation de contexte.
  • Utiliser les durées et événements pour identifier une dépendance lente.
  • Instrumenter sans créer de données sensibles ni une cardinalité incontrôlée.

Modèle mental

Une trace représente une opération distribuée; chaque span décrit une unité de travail et porte durée, attributs et relation parent-enfant.

Propagation

Transmettre le contexte via les mécanismes standard entre services; vérifier que les appels asynchrones ne perdent pas le contexte.

Diagnostic

Comparer durée totale et spans enfants. Les écarts peuvent provenir du travail local, de l’attente, des files ou d’un contexte manquant.

Échantillonnage

Choisir une stratégie compatible avec le coût et le diagnostic; les traces rares d’erreurs critiques peuvent nécessiter une politique adaptée.

Confidentialité

Ne pas mettre jetons, mots de passe, corps complets ou données personnelles dans les attributs; borner les valeurs et la cardinalité.

Exercice pratique

Dessiner une trace navigateur → API → service de paiement simulé → base de données. Marquer les spans, propager le contexte et diagnostiquer une latence de 800 ms dans une dépendance.

Critères de réussite

  • Les spans sont reliés par un contexte propagé.
  • La somme des durées n’est pas interprétée naïvement en présence de parallélisme.
  • Les attributs restent bornés et non sensibles.
  • Le diagnostic s’appuie sur une trace concrète.
