Transactions et cohérence métier

Garantir qu’une opération métier composée de plusieurs écritures respecte les invariants, même en cas d’erreur ou de concurrence.

Leçon approfondieThéorie · pratique · validation

Objectifs d’apprentissage

À la fin de cette leçon, tu dois pouvoir concevoir une opération métier dont plusieurs écritures doivent réussir ensemble, expliquer ce qui se passe en cas de concurrence et distinguer une transaction locale d’un workflow distribué.

  • Formuler les invariants métier avant de choisir le mécanisme de persistance.
  • Encadrer les écritures dans une transaction et vérifier le résultat de chaque étape.
  • Choisir entre contrainte, écriture conditionnelle, verrou et isolation renforcée selon le risque.
  • Prévoir les répétitions de requêtes et les effets externes sans supposer qu’un rollback les annule.

Prérequis : savoir lire une requête SQL, une contrainte et le cycle requête/réponse d’une API.

1. Comprendre l’invariant métier

Une transaction métier est une opération cohérente du point de vue de l’utilisateur : réserver un article, transférer de l’argent, confirmer une commande ou attribuer une place. Elle peut nécessiter plusieurs lectures et écritures en base. L’enjeu n’est pas seulement de réussir chaque requête séparément ; il faut préserver des règles qui doivent toujours rester vraies. On appelle ces règles des invariants.

Pour un transfert, l’invariant peut être « le montant débité d’un compte est égal au montant crédité sur l’autre ». Pour une réservation, « une place ne peut pas être attribuée à deux personnes ». Pour une commande, « une commande confirmée possède une ligne de commande et une quantité valide ». Énonce les invariants avant de choisir l’implémentation : ils déterminent quelles opérations doivent réussir ou échouer ensemble.

Une transaction de base de données fournit généralement les propriétés ACID : atomicité (tout ou rien), cohérence (les contraintes restent respectées), isolation (les opérations concurrentes sont contrôlées) et durabilité (un commit validé persiste selon les garanties du système). ACID ne remplace toutefois pas la conception métier : la base ne peut protéger que les règles que tu lui exprimes.

2. Encadrer les écritures atomiquement

Une transaction fournit une frontière de validation : avant le COMMIT, les écritures restent provisoires ; si une étape échoue, l’application annule l’ensemble avec ROLLBACK. Une transaction ne rend pas automatiquement correcte une règle métier : il faut vérifier que les conditions attendues sont satisfaites et que les contraintes de la base expriment les invariants critiques.

BEGIN;

-- Validation préalable côté application : montant_cents > 0,
-- comptes source/cible distincts et même devise.
-- Verrouiller les comptes dans un ordre stable pour limiter les deadlocks.
SELECT id
FROM accounts
WHERE id IN (10, 20)
ORDER BY id
FOR UPDATE;

-- L'application exige exactement deux comptes existants.
UPDATE accounts
SET balance_cents = balance_cents - 2500
WHERE id = 10 AND balance_cents >= 2500;
-- rowCount doit valoir 1 ; sinon ROLLBACK.

UPDATE accounts
SET balance_cents = balance_cents + 2500
WHERE id = 20;
-- rowCount doit valoir 1 ; sinon ROLLBACK.

INSERT INTO transfers (from_id, to_id, amount_cents)
VALUES (10, 20, 2500);

COMMIT;

Ce fragment illustre le flux PostgreSQL avec des montants en unités mineures entières (ici 2 500 centimes) ; il suppose que la table utilise balance_cents et amount_cents. La logique applicative doit vérifier le nombre de lignes renvoyées par le verrouillage, puis rowCount après chaque écriture ; si un contrôle échoue, elle exécute ROLLBACK et ne poursuit pas. Une contrainte CHECK (balance_cents >= 0), des clés étrangères et une contrainte d’unicité adaptée renforcent la protection côté base. Si le système gère plusieurs devises, l’égalité des devises doit être garantie ou le change traité comme une opération distincte.

Avec un pilote Node.js, garde toutes les requêtes sur la même connexion transactionnelle, puis libère cette connexion dans un bloc de nettoyage, y compris en cas d’erreur. N’ouvre pas une transaction sur une connexion et n’exécute pas une partie du travail sur une autre connexion du pool : elle ne ferait pas partie de la même transaction.

La transaction doit couvrir l’unité de cohérence métier, pas toute la durée de la requête HTTP. Évite les appels réseau, l’envoi d’e-mails et les attentes utilisateur à l’intérieur : ils allongent la durée des verrous et ne deviennent pas atomiques pour autant.

3. La concurrence change le raisonnement

Deux requêtes peuvent lire la même valeur, décider toutes les deux qu’une action est possible, puis écrire un résultat qui viole l’invariant. Le contrôle « vérifier puis agir » en deux étapes applicatives n’est donc pas suffisant si un autre processus peut intervenir entre les deux.

Choisis le mécanisme selon l’invariant et les garanties du moteur :

MécanismeÀ privilégier lorsqueLimite à connaître
Contrainte UNIQUE ou CHECKLa règle peut être exprimée directement sur les données.Il faut traduire proprement la violation en erreur métier.
Mise à jour conditionnelleLa décision peut être liée à l’état courant dans une seule instruction.Le nombre de lignes modifiées devient une partie du contrat.
Verrou de ligneUn scénario doit lire puis modifier un enregistrement de façon coordonnée.Les verrous peuvent provoquer attente, interblocage et baisse de débit.
Isolation plus strictePlusieurs lectures doivent respecter une vue cohérente de données liées.Le moteur peut annuler une transaction concurrente ; il faut traiter l’erreur.

Pour une dernière unité en stock, une décrémentation conditionnelle est souvent plus simple qu’une lecture suivie d’une écriture séparée :

UPDATE inventory
SET available = available - 1
WHERE product_id = 42 AND available > 0;

-- 1 ligne modifiée : réservation obtenue.
-- 0 ligne modifiée : stock absent ou épuisé.

Une transaction peut encore être nécessaire pour créer la commande et enregistrer la réservation ensemble. Les niveaux d’isolation ont des sémantiques propres au moteur : une transaction sérialisable peut échouer volontairement pour préserver la cohérence. Dans ce cas, ne réessaie que l’unité transactionnelle complète, avec un nombre de tentatives borné et un délai adapté.

4. Définir les frontières et les effets externes

Un COMMIT local ne peut pas annuler un paiement déjà accepté par un prestataire ni retirer un e-mail déjà envoyé. Pour un workflow qui traverse plusieurs systèmes, définis les états intermédiaires et les règles de reprise au lieu de prétendre qu’une transaction distribuée existe automatiquement.

Une approche fréquente consiste à écrire l’état métier et un événement à publier dans la même transaction :

BEGIN;
UPDATE orders SET status = 'confirmed' WHERE id = 501;
-- event_id doit être stable et protégé par une contrainte UNIQUE.
INSERT INTO outbox(event_id, event_type, aggregate_id, payload)
VALUES ('evt-501', 'OrderConfirmed', '501', jsonb_build_object('orderId', 501));
COMMIT;

Un worker lit ensuite l’outbox, publie l’événement et marque sa livraison. Comme le worker peut s’arrêter après la publication mais avant l’enregistrement du succès, le même événement peut être publié plus d’une fois. Le consommateur doit donc dédupliquer ou rendre l’effet idempotent. L’outbox réduit le risque de perdre un événement entre la validation métier et sa publication ; elle ne garantit pas une livraison « exactement une fois » de bout en bout.

Pour un paiement externe, utilise l’identifiant de commande comme clé d’idempotence si le prestataire le permet, conserve l’état du workflow et prévois une réconciliation des opérations dont le résultat est inconnu après un timeout. Une saga peut coordonner plusieurs étapes avec des actions compensatoires, mais une compensation est une nouvelle action métier, pas un rollback magique.

5. Erreurs fréquentes et arbitrages

  • Validation sans protection concurrente : une vérification en JavaScript ne remplace pas une contrainte ou une écriture atomique.
  • Résultat non contrôlé : une requête SQL peut réussir techniquement tout en modifiant zéro ligne.
  • Transaction trop longue : les appels réseau et les traitements coûteux gardent inutilement des ressources verrouillées.
  • Retry aveugle : une erreur de validation ou une contrainte métier ne se corrige pas en répétant la même requête.
  • Effet externe non idempotent : après un timeout, le client ignore parfois si l’opération a réussi ; une répétition peut créer un doublon.

Pour diagnostiquer une transaction qui échoue, consigne un identifiant de corrélation, la catégorie d’erreur, le nombre de tentatives et la durée, sans enregistrer les secrets ou données sensibles. Distingue conflit de concurrence, contrainte violée, indisponibilité du moteur et erreur de programmation. Le message envoyé au client doit rester stable et ne pas exposer les détails SQL.

Le bon niveau de protection dépend du coût d’une incohérence. Commence par les contraintes simples et les écritures conditionnelles, puis ajoute verrous ou isolation plus stricte lorsque l’invariant l’exige. Une stratégie plus complexe doit être justifiée par un scénario concret et testée sous concurrence.

6. Exercice guidé

Construis une réservation de la dernière unité d’un produit. Écris le schéma minimal, une contrainte empêchant un stock négatif et une transaction qui crée la commande puis réserve l’unité. Prévois le cas où le stock est épuisé entre l’affichage du panier et la confirmation.

  1. Formule au moins deux invariants, par exemple « le stock ne devient jamais négatif » et « une commande confirmée possède une réservation ».
  2. Exécute deux tentatives concurrentes et vérifie qu’une seule peut obtenir la dernière unité.
  3. Ajoute un événement OrderConfirmed via une outbox transactionnelle plutôt qu’un appel direct au broker dans la transaction.
  4. Simule un timeout HTTP après le commit et explique comment une clé d’idempotence permet de retrouver le résultat existant.
  5. Documente les erreurs qui sont réessayables et celles qui doivent produire un refus métier.

Critères de réussite

  • Les invariants métier sont écrits avant le choix de l’implémentation.
  • Un échec à n’importe quelle étape empêche une validation partielle de l’opération locale.
  • Les écritures conditionnelles et contraintes empêchent le stock négatif sous concurrence.
  • Le code contrôle les lignes affectées et distingue conflit, refus métier et erreur technique.
  • L’événement externe peut être repris sans perdre la cohérence locale, et le consommateur tolère les doublons.
  • Le scénario de timeout ne crée pas une seconde commande lors d’une répétition.
