4. Bases de données et modélisation

Transactions et cohérence

Regrouper des opérations atomiques et choisir le niveau d’isolation adapté aux risques.

Seconde passe pédagogiqueBase de données

Objectifs d’apprentissage

  • Expliquer les propriétés ACID.
  • Utiliser BEGIN, COMMIT et ROLLBACK.
  • Reconnaître les risques liés aux opérations concurrentes.

1. Une transaction, une unité cohérente

Une transaction regroupe des opérations qui doivent réussir ou échouer ensemble. ACID signifie atomicité (tout ou rien), cohérence (les contraintes restent respectées), isolation (les accès concurrents sont contrôlés) et durabilité (un commit confirmé résiste aux défaillances selon les garanties du système).

BEGIN;
UPDATE comptes SET solde = solde - 50 WHERE id = 10;
UPDATE comptes SET solde = solde + 50 WHERE id = 20;
COMMIT;

Un transfert doit aussi vérifier que le compte source existe et que le solde est suffisant. Si une étape échoue, l’application annule la transaction. Les contraintes de base et les mises à jour conditionnelles protègent mieux les invariants qu’un contrôle réalisé uniquement avant l’écriture.

2. Frontière transactionnelle, commit et rollback

Une transaction n’est utile que si toutes les écritures nécessaires au même invariant se trouvent dans la même frontière. En cas d’exception, il faut annuler la transaction ; en cas de succès, la valider. Les appels réseau externes ne participent pas automatiquement à la transaction SQL : pour un paiement ou un message, prévois une outbox transactionnelle et un traitement idempotent.

Exemple pédagogique avec PostgreSQL et node-postgres. Les identifiants ont déjà été validés, sourceId et targetId sont différents, et amount est un montant décimal positif validé sans conversion flottante imprécise.

const client = await pool.connect();
let discardClient = false;
try {
  await client.query("BEGIN");

  // Verrouiller les deux comptes dans un ordre stable limite
  // les interblocages lors de transferts simultanés opposés.
  const accounts = await client.query(
    "SELECT id FROM comptes WHERE id = ANY($1::bigint[]) ORDER BY id FOR UPDATE",
    [[sourceId, targetId]]
  );
  if (accounts.rowCount !== 2) throw new Error("ACCOUNT_NOT_FOUND");

  const debit = await client.query(
    "UPDATE comptes SET solde = solde - $1 WHERE id = $2 AND solde >= $1 RETURNING id",
    [amount, sourceId]
  );
  if (debit.rowCount !== 1) throw new Error("INSUFFICIENT_FUNDS");

  const credit = await client.query(
    "UPDATE comptes SET solde = solde + $1 WHERE id = $2 RETURNING id",
    [amount, targetId]
  );
  if (credit.rowCount !== 1) throw new Error("TARGET_ACCOUNT_NOT_FOUND");

  await client.query("COMMIT");
} catch (error) {
  try {
    await client.query("ROLLBACK");
  } catch {
    // Ne pas rendre au pool une connexion dont l’état est incertain.
    discardClient = true;
  }
  throw error;
} finally {
  client.release(discardClient);
}

Ce fragment illustre le cycle de vie, pas une fonction bancaire prête à déployer. En production, ajoute des contraintes de schéma, un journal de transfert, des règles métier, une gestion d’erreurs typées et des tests de concurrence. Vérifie aussi le comportement de la bibliothèque et du pool lorsque la connexion est perdue pendant le commit : le résultat peut être incertain pour le client.

  • Rollback : annule les écritures SQL de la transaction, pas les effets déjà produits par un service externe.
  • Libération : rends toujours la connexion au pool dans un finally, même si le commit ou le rollback échoue.
  • Nouvel essai : après une erreur de sérialisation, recommence toute la transaction, avec un nombre de tentatives limité. Après un résultat de commit incertain, ne répète pas aveuglément une opération non idempotente.
  • Durée : ne garde pas de transaction ouverte pendant une interaction utilisateur ou un appel réseau lent.

3. Isolation et concurrence

Les niveaux d’isolation définissent quelles anomalies concurrentes sont possibles. Le niveau par défaut de PostgreSQL, READ COMMITTED, fournit un nouvel instantané par instruction ; il ne suffit pas à rendre atomique une séquence « lire puis modifier » si aucune protection n’est ajoutée. Selon la règle, utilise une mise à jour conditionnelle, une contrainte, SELECT ... FOR UPDATE ou une isolation plus forte.

Avec SERIALIZABLE, la base peut interrompre une transaction pour préserver un résultat équivalent à une exécution sérielle. L’application doit être capable de réessayer la transaction entière en cas d’erreur de sérialisation, avec un nombre limité de tentatives et une logique idempotente. Teste les opérations concurrentes, pas uniquement leur exécution séquentielle.

Erreurs fréquentes

  • Supposer que deux requêtes séparées sont atomiques.
  • Oublier le rollback en cas d’exception.
  • Garder une transaction ouverte pendant une interaction utilisateur.
  • Croire que le rollback annule les actions d’un service externe.

Exercice

Conçois la réservation de la dernière place disponible d’un événement. Deux requêtes concurrentes ne doivent pas réserver la même place. Propose une solution avec contrainte, verrou ou mise à jour conditionnelle, puis explique comment l’application traite un conflit.

Critères de réussite

  • L’invariant est protégé par la base ou par une stratégie transactionnelle solide.
  • Le succès est déterminé par le résultat de l’écriture.
  • Les transactions restent courtes et les erreurs sont traitées.
  • La reprise ne duplique pas les effets externes.
