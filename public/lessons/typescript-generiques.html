TypeScript : types génériques

Comprendre comment les génériques préservent la relation entre les types d’entrée et de sortie sans recourir à any.

1. Objectifs et prérequis

Les génériques permettent d’écrire des fonctions, types et classes qui fonctionnent avec plusieurs types tout en conservant l’information de type. À la fin, vous saurez lire un paramètre de type, en créer un, contraindre un générique avec extends, comprendre l’inférence et reconnaître les cas où un générique rend l’API plus compliquée qu’elle ne devrait l’être. Il faut connaître les types primitifs, les tableaux, les objets, les fonctions et les unions TypeScript.

2. Le problème que résout un générique

Imaginons une fonction qui renvoie la valeur reçue. Si son paramètre est de type unknown, le retour est sûr mais l’appelant perd l’information précise. Si elle utilise any, cette information est contournée et les erreurs peuvent passer silencieusement. Un générique nomme le type capturé à l’entrée et le réutilise dans le résultat.

function identity<T>(value: T): T {
  return value;
}

const name = identity("Ada"); // string
const count = identity(42);   // number

T est un paramètre de type, pas une variable JavaScript. Le compilateur infère ici string et number à partir des arguments. Le nom est conventionnel : T, Item ou Value fonctionnent ; un nom descriptif devient préférable quand il existe plusieurs paramètres.

3. Préserver la relation entre entrée et sortie

Un générique est particulièrement utile quand le type de sortie dépend du type fourni. Considérez une fonction qui renvoie le premier élément d’un tableau :

function first<T>(items: T[]): T | undefined {
  return items[0];
}

const maybeNumber = first([10, 20]); // number | undefined
const maybeName = first(["Ada", "Lin"]); // string | undefined

Le retour inclut undefined, car un tableau vide n’a pas de premier élément. Le générique n’élimine pas les cas limites : il permet de les représenter correctement. Si la fonction devait toujours renvoyer un élément, il faudrait soit valider l’entrée et lancer une erreur, soit modifier le contrat.

4. Plusieurs paramètres de type

Les génériques peuvent représenter une relation entre plusieurs valeurs. Un exemple courant associe une clé à une valeur :

function pair<A, B>(left: A, right: B): [A, B] {
  return [left, right];
}

const result = pair("user", 12);
// type : [string, number]

Chaque paramètre de type doit apporter une information utile. Ajouter des paramètres uniquement pour donner une impression de flexibilité rend l’API plus difficile à comprendre. Si le type ne dépend pas d’une relation entre les entrées et sorties, une signature simple suffit souvent.

5. Contraindre avec extends

Un générique ne garantit pas que la valeur possède une propriété arbitraire. Pour lire une propriété, il faut exprimer la contrainte minimale requise :

function getLength<T extends { length: number }>(value: T): number {
  return value.length;
}

getLength("bonjour");       // accepté
getLength([1, 2, 3]);       // accepté
// getLength(123);           // erreur de type

extends signifie ici que T doit satisfaire cette forme. La fonction conserve le type précis de T tout en pouvant utiliser length. Ne remplacez pas la contrainte par any : cela supprimerait précisément la vérification recherchée.

6. Clés liées à un objet : keyof

Pour obtenir la valeur d’une propriété, le type de la clé doit correspondre à une clé réelle de l’objet. Le couple keyof T et T[K] exprime cette dépendance :

function getProperty<T, K extends keyof T>(obj: T, key: K): T[K] {
  return obj[key];
}

const user = { id: 7, name: "Mina" };
const id = getProperty(user, "id");       // number
const name = getProperty(user, "name");   // string
// getProperty(user, "email");            // erreur

K est limité aux clés de T, et le résultat T[K] correspond au type de la propriété choisie. C’est plus précis qu’une fonction qui accepte n’importe quelle chaîne et renvoie une union générale de toutes les valeurs.

7. Génériques et tableaux d’objets

On peut écrire une fonction qui transforme une collection tout en préservant le type de ses éléments. Toutefois, il est souvent préférable d’utiliser les méthodes standard déjà bien typées :

function toArray<T>(value: T): T[] {
  return [value];
}

const one = toArray({ id: 1 }); // { id: number }[]

Les types génériques servent aussi à définir des enveloppes réutilisables, par exemple ApiResponse<T> pour associer des données à des métadonnées. Attention : le type statique ne valide pas une réponse HTTP à l’exécution. Les données externes doivent être vérifiées à la frontière du système.

type ApiResponse<T> = {
  data: T;
  requestId: string;
};

type User = { id: string; name: string };
type UserResponse = ApiResponse<User>;

8. Inférence, annotations et erreurs fréquentes

Laissez TypeScript inférer les types lorsque la relation est évidente. Une annotation explicite peut être utile pour documenter une API publique, lever une ambiguïté ou garantir un contrat. Forcer un paramètre de type à chaque appel est rarement nécessaire : identity<string>("Ada") est valide, mais identity("Ada") suffit généralement.

  • Ne choisissez pas un générique quand un type concret décrit réellement le contrat.
  • N’utilisez pas any pour contourner un problème d’inférence sans le comprendre.
  • Ne confondez pas contrainte statique et validation à l’exécution.
  • Évitez les paramètres de type qui ne relient aucune entrée à une sortie.
  • Vérifiez les types inférés dans l’éditeur ou le TypeScript Playground.

Atelier guidé — concevoir une fonction réutilisable sans perdre les types

On veut indexer des objets par identifiant. Une première version peut sembler pratique, mais elle cache une perte d’information :

function firstItem(items: object[]): object | undefined {
  return items[0];
}

const user = firstItem([{ id: 7, name: "Ada" }]);
// user est object | undefined : user.name n'est pas autorisé.

La bonne question n’est pas « comment faire accepter n’importe quoi ? », mais « quelle relation entre l’entrée et la sortie faut-il conserver ? ». Le type générique répond à cette question :

function firstItem<T>(items: readonly T[]): T | undefined {
  return items[0];
}

const user = firstItem([{ id: 7, name: "Ada" }]);
if (user) console.log(user.name); // string

readonly T[] annonce que la fonction n’a pas besoin de modifier le tableau. T | undefined rend explicite le cas du tableau vide. Pour vérifier le contrat, testez au minimum un tableau de chaînes, un tableau d’objets et un tableau vide. Si vous devez ajouter une assertion as T pour faire compiler le corps, demandez-vous si la relation de type est réellement garantie par l’implémentation.

Piège de conception : un générique n’est pas automatiquement meilleur qu’un type concret. Pour une fonction qui ne traite que des identifiants numériques, (id: number) => string est plus clair qu’une signature générique artificielle.

9. Exercice

Écrivez une fonction pluck qui reçoit un objet et une clé valide de cet objet, puis renvoie la valeur correspondante avec le type exact. Testez-la sur un objet contenant une chaîne, un nombre et un booléen. Vérifiez qu’une clé inexistante est refusée par le compilateur. Ensuite, écrivez wrap, qui renvoie une valeur sous la forme { value: ... } tout en préservant son type.

10. Critères de réussite

  • Je peux expliquer le rôle de T et l’inférence des types.
  • Je préserve une relation précise entre entrée et sortie.
  • Je sais écrire une contrainte avec extends.
  • Je sais utiliser keyof et T[K] pour typer un accès par clé.
  • Je distingue la sûreté de compilation de la validation des données réelles.
