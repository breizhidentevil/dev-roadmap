TypeScript : modules, déclarations et tsconfig

Comprendre les imports et exports, les fichiers de déclaration, les options de compilation et les différences entre vérification des types et exécution.

1. Objectifs et prérequis

Ce module explique comment organiser un projet TypeScript en modules, ce que contiennent les fichiers de déclaration et comment lire un tsconfig.json. À la fin, vous saurez distinguer les modules source des types de déclaration, comprendre la résolution des imports et diagnostiquer des erreurs fréquentes liées aux options de compilation. Vous devez connaître les fonctions, les imports JavaScript et les bases de la ligne de commande.

2. Modules : définir une interface entre fichiers

Un module expose explicitement les éléments qu’un autre fichier peut importer. Un export nommé rend disponible un symbole avec son nom ; un export par défaut définit une valeur principale. Dans une base de code, les exports nommés facilitent souvent la recherche et la refactorisation, mais l’essentiel est de suivre une convention cohérente.

// src/math.ts
export function add(a: number, b: number): number {
  return a + b;
}

// src/app.ts
import { add } from "./math.js";
console.log(add(2, 3));

Dans cet exemple, les fichiers sont placés sous src/ pour correspondre au include du tsconfig.json présenté ensuite. Pour exécuter cet exemple comme ESM avec Node.js, le package.json du projet doit déclarer "type": "module". Avec module/moduleResolution réglés sur NodeNext, l’import source utilise ici l’extension d’exécution .js : TypeScript la résout vers math.ts pendant la vérification, puis le chemin reste valide dans le JavaScript émis. La forme exacte dépend de l’outillage, du format de module et de la résolution utilisée ; vérifiez le runtime réel, pas seulement l’absence d’erreur de type.

3. Modules TypeScript et formats d’exécution

TypeScript vérifie les types puis, selon la configuration, émet du JavaScript. Les mots-clés import et export participent au système de modules ; ils ne garantissent pas que le runtime choisira automatiquement le même format. L’écosystème JavaScript distingue notamment ECMAScript Modules (ESM) et CommonJS.

Le projet doit aligner la configuration TypeScript, les champs de package.json, l’environnement d’exécution et l’outil de build. Les options module et moduleResolution influencent l’interprétation des imports et la manière dont le compilateur cherche les fichiers. Il n’existe pas une combinaison universelle : utilisez le modèle recommandé pour votre version de Node.js, votre bundler ou votre plateforme cible.

4. Le rôle de tsconfig.json

Le fichier de configuration fixe les règles de compilation et les fichiers inclus. Il doit être compris comme un contrat de projet : une option peut changer le niveau de vérification, les fichiers produits ou la manière dont les modules sont résolus.

{
  "compilerOptions": {
    "target": "ES2022",
    "module": "NodeNext",
    "moduleResolution": "NodeNext",
    "strict": true,
    "noEmit": true
  },
  "include": ["src/**/*.ts"]
}

Cet exemple illustre des options, pas une configuration à copier pour tous les projets. noEmit demande au compilateur de ne pas générer de fichiers ; un bundler ou un autre outil doit alors prendre en charge la production du JavaScript. Si vous exécutez directement le code avec un outil spécialisé, sa configuration doit être compatible avec celle du compilateur.

5. Comprendre quelques options importantes

  • target : version de JavaScript visée pour le code émis.
  • module : format de modules attendu pour la sortie ou l’analyse.
  • moduleResolution : règles de recherche des modules et de leurs entrées.
  • strict : active un ensemble de vérifications plus strictes.
  • noEmit : vérifie sans produire les fichiers JavaScript.
  • outDir et rootDir : contrôlent l’organisation des fichiers sources et générés.
  • include, exclude et files : déterminent l’ensemble de fichiers du projet, selon leurs règles de priorité.

Quand le compilateur semble ignorer une option, vérifiez quel fichier de configuration est effectivement chargé, si un autre outil utilise sa propre configuration et si le fichier source appartient au projet. La commande tsc --showConfig peut aider à examiner la configuration effective.

6. Fichiers de déclaration : décrire des types qui existent ailleurs

Les fichiers .d.ts décrivent des types sans fournir l’implémentation JavaScript correspondante. Ils permettent à TypeScript de comprendre une bibliothèque JavaScript, un environnement global ou un module dont les types ne sont pas inclus. Ils peuvent déclarer des fonctions, classes, interfaces, types et modules.

// legacy-library.d.ts
declare module "legacy-library" {
  export function transform(input: string): string;
}

Cette déclaration indique au compilateur comment utiliser le module ; elle ne crée pas le module et ne prouve pas que l’implémentation respecte la signature. Si la fonction réelle renvoie parfois un nombre, le fichier de déclaration peut masquer le problème au lieu de le résoudre. Les déclarations doivent correspondre au comportement observé et être maintenues quand la dépendance change.

7. Types d’une dépendance et résolution des imports

De nombreuses bibliothèques publient leurs types avec le package ; d’autres s’appuient sur des packages de déclarations séparés. Si un import est introuvable, vérifiez d’abord que la dépendance est installée, que sa version est compatible, que son package expose bien le point d’entrée utilisé et que la configuration correspond au runtime. Évitez d’ajouter un fichier de déclaration global permissif juste pour faire disparaître l’erreur.

Les chemins d’alias comme @/utils nécessitent souvent une configuration cohérente entre TypeScript, le bundler, les tests et le runtime. L’option paths aide le compilateur à résoudre certains imports, mais ne réécrit pas nécessairement les chemins dans le JavaScript émis. Il faut donc configurer également l’outil qui exécute ou regroupe le code.

8. Erreurs fréquentes et diagnostic

  • Confondre une vérification de types réussie avec une application exécutable.
  • Mélanger ESM et CommonJS sans comprendre les règles du runtime.
  • Supposer que paths réécrit automatiquement les imports dans le code final.
  • Écrire des déclarations .d.ts qui ne reflètent pas l’implémentation.
  • Modifier plusieurs options à la fois et perdre la cause de l’erreur.

Pour diagnostiquer, réduisez le problème à un import, inspectez la configuration effective, vérifiez le package installé et exécutez la commande de build ou de lancement réelle. Consultez la documentation de la version utilisée : la résolution des modules a évolué avec TypeScript, Node.js et les bundlers.

9. Exercice

Créez deux fichiers, l’un qui exporte une fonction typée et l’autre qui l’importe. Ajoutez un tsconfig.json strict et une commande de vérification. Puis choisissez une dépendance JavaScript sans types intégrés et rédigez une petite déclaration qui reflète son API réelle. Testez à la fois la compilation et l’exécution : notez si les deux étapes utilisent les mêmes règles de résolution.

Explications et exemple guidé

Le système de modules TypeScript dépend de trois éléments distincts : la syntaxe d’import/export, la résolution de modules du compilateur et le runtime qui exécutera le JavaScript. Une compilation réussie ne garantit donc pas qu’un import fonctionnera en production.

  1. Identifier le runtime cible (Node.js, navigateur ou bundler).
  2. Choisir module et moduleResolution compatibles avec ce runtime, plutôt que copier une configuration générique.
  3. Vérifier les chemins relatifs, les extensions attendues par le runtime et les fichiers de déclaration des dépendances.
  4. Tester le résultat compilé dans le même environnement que la production.
// src/domain/money.ts
export type Money = { amountCents: number; currency: 'EUR' };
export function formatMoney(value: Money): string {
  return `${(value.amountCents / 100).toFixed(2)} ${value.currency}`;
}

// src/main.ts
import { formatMoney, type Money } from './domain/money.js';
const total: Money = { amountCents: 1299, currency: 'EUR' };
console.log(formatMoney(total));

Dans un projet Node en ESM, l’extension présente dans l’import TypeScript peut devoir correspondre au fichier JavaScript généré. Le réglage exact dépend de la version de TypeScript et du mode d’exécution.

Pièges et limites

  • Piège : confondre target (syntaxe JavaScript émise) et module (format des modules).
  • Piège : installer des types externes sans vérifier qu’ils correspondent à la version de la bibliothèque.
  • Piège : utiliser des chemins d’alias connus du compilateur mais inconnus du runtime.

Exercice

Créez un module price.ts exportant un type et deux fonctions, puis importez-les depuis main.ts. Configurez le projet pour son runtime, compilez-le et exécutez réellement le JavaScript produit. Ajoutez une dépendance sans types natifs et documentez comment ses déclarations sont résolues.

Critères de réussite

  • La configuration cible explicitement le runtime et sa résolution de modules.
  • Le projet compile depuis un répertoire propre avec la commande documentée.
  • Le JavaScript compilé s’exécute sans erreur d’import.
  • Les types externes et les alias sont expliqués sans masquer les erreurs par any.
