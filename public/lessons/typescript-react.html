2. Frontend

TypeScript avec React

Typer les props, événements et états React pour détecter les erreurs à la compilation sans alourdir inutilement le code.

Tutoriel détailléLot 8 · 2026

Objectifs d’apprentissage

  • Définir les types des props.
  • Typer événements et état React.
  • Modéliser props optionnelles et unions discriminées.
  • Éviter les assertions forcées et les types trop larges.

Fil directeur

Le typage d’une interface React doit rendre explicites les contrats entre composants et les états possibles de l’application. Il améliore l’autocomplétion et détecte des incohérences à la compilation, mais ne valide pas les données reçues à l’exécution.

1. Définir le contrat des props

Déclare les propriétés attendues avec un type ou une interface. Distingue les champs obligatoires, optionnels et les callbacks. Un type doit exprimer ce que le composant exige réellement, sans rendre chaque prop optionnelle « par commodité ».

type Product = { id: string; name: string; price: number };
type ProductCardProps = {
  product: Product;
  onSelect: (id: string) => void;
};

Les props sont en lecture seule par convention et par conception : le composant signale une intention au parent via un callback plutôt que de muter la donnée reçue.

2. Typer les événements et les contrôles

Utilise les types d’événements React appropriés plutôt que `any`. Pour un champ texte, `React.ChangeEvent<HTMLInputElement>` donne accès à la cible typée ; pour un formulaire, `React.FormEvent<HTMLFormElement>` convient à la soumission.

function handleChange(event: React.ChangeEvent<HTMLInputElement>) {
  setQuery(event.currentTarget.value);
}

Lorsque le contexte JSX suffit à inférer le type du gestionnaire, une annotation explicite peut être inutile. Privilégie le type le plus simple qui conserve la sécurité.

3. Représenter correctement l’état

Type l’état à partir de ses valeurs réelles. Si une valeur commence à `null` puis reçoit un résultat, exprime ce cas dans le type. Pour les états de chargement, utilise une union discriminée plutôt que des booléens indépendants qui peuvent se contredire.

type LoadState<T> =
  | { status: "loading" }
  | { status: "success"; data: T }
  | { status: "error"; message: string };

Le champ `status` permet à TypeScript de réduire le type : les données n’existent que dans la branche `success`, ce qui force le code à traiter les autres cas.

4. Valider les données externes à l’exécution

TypeScript n’inspecte pas la réponse JSON à l’exécution. Une annotation comme `response.json() as Product[]` ne vérifie pas que la réponse contient effectivement des produits. Traite les données réseau comme inconnues, vérifie leur structure ou utilise un schéma runtime, puis convertis-les en type applicatif.

Le typage aide à garantir la cohérence du code après validation ; il ne remplace ni la validation des entrées ni les contrôles d’autorisation du serveur.

Erreurs fréquentes et diagnostic

  • Utiliser `any` pour faire disparaître une erreur de type.
  • Forcer un type avec `as` sans validation de la donnée.
  • Oublier le cas `null` ou l’état de chargement.
  • Modéliser le même état par plusieurs booléens contradictoires.
  • Annoter des callbacks alors que l’inférence fournit déjà le bon type.

Exercice guidé

Crée un composant `ProductCard` avec des props strictes et un callback de sélection. Ajoute un chargement typé avec une union discriminée, puis écris une fonction de validation des données inconnues reçues d’une API avant de les transmettre au composant.

Critères de réussite

  • Les props obligatoires et optionnelles sont explicites.
  • Les événements utilisent des types React adaptés.
  • Les états de succès, chargement et erreur sont exhaustifs.
  • Aucune assertion de type ne remplace la validation des données externes.
  • La compilation stricte passe sans recourir à `any` injustifié.
