TypeScript : types conditionnels et types mappés

Créer des types dérivés en fonction d’autres types, transformer les propriétés d’un objet et reconnaître quand une abstraction devient trop complexe.

1. Objectifs et prérequis

Les types conditionnels et mappés servent à construire un type à partir d’un autre. Ils sont à la base de nombreux utilitaires TypeScript, mais peuvent aussi produire des signatures difficiles à lire. À la fin du module, vous saurez écrire un type conditionnel simple, transformer les propriétés d’un objet, comprendre le comportement distributif sur les unions et choisir une solution plus simple quand elle suffit. Il faut déjà maîtriser les génériques, keyof, les unions et les types indexés.

2. Types conditionnels : choisir un type à partir d’une relation

Un type conditionnel utilise la forme T extends U ? X : Y. Il pose une question de compatibilité de types : si T est assignable à U, le résultat est X, sinon Y. Il s’agit d’une opération au niveau du système de types, pas d’un if exécuté en JavaScript.

type IsString<T> = T extends string ? true : false;

type A = IsString<"bonjour">; // true
type B = IsString<42>;        // false

Le résultat est un type, pas une valeur booléenne disponible à l’exécution. Un type conditionnel est pertinent lorsque la forme du résultat dépend réellement du type d’entrée. Pour une fonction métier ordinaire, une condition JavaScript reste nécessaire si le programme doit agir sur une valeur réelle.

3. Extraire une information d’un type

Le mot-clé infer permet de nommer un type à l’intérieur de la condition lorsque TypeScript peut l’inférer à partir d’une structure. Un exemple conceptuel est l’extraction du type de retour d’une fonction :

type ReturnOf<T> = T extends (...args: never[]) => infer R
  ? R
  : never;

type Result = ReturnOf<() => Promise<number>>;
// Promise<number>

Dans cette définition, R est capturé à partir de la signature de fonction. En pratique, le type utilitaire intégré ReturnType<T> remplit déjà ce rôle et doit être préféré sauf si vous apprenez ou avez une exigence spécifique. Évitez de réinventer un utilitaire standard sans raison claire.

4. Distribution sur les unions

Lorsqu’un type conditionnel agit sur un paramètre générique nu, il se distribue sur les membres d’une union. Par exemple, une condition qui transforme les chaînes en tableaux s’applique séparément à chaque membre d’une union :

type ToArray<T> = T extends unknown ? T[] : never;
type Values = ToArray<string | number>;
// string[] | number[]

Le résultat est une union de tableaux, pas un tableau qui mélange librement chaînes et nombres. Si vous voulez tester l’union entière sans distribution, enveloppez les deux côtés dans un tuple :

type ToArrayWhole<T> = [T] extends [unknown] ? T[] : never;
type Whole = ToArrayWhole<string | number>;
// (string | number)[]

Cette différence est subtile mais importante. Avant d’ajouter une condition à un type générique, testez-la sur un type concret, une union et parfois never. Le TypeScript Playground aide à inspecter le résultat réellement calculé.

5. Types mappés : transformer chaque propriété

Un type mappé parcourt les clés d’un type existant. La forme générale { [K in keyof T]: ... } produit un nouvel objet dont les propriétés sont dérivées de celles de T.

type ReadonlyLike<T> = {
  readonly [K in keyof T]: T[K];
};

type User = {
  id: string;
  name: string;
};

type ReadonlyUser = ReadonlyLike<User>;

TypeScript fournit déjà Readonly<T>, équivalent pour ce besoin courant. L’intérêt pédagogique est de comprendre que le compilateur parcourt les clés et réutilise le type de chaque propriété grâce à T[K]. Les modificateurs comme readonly et ? peuvent être ajoutés ou retirés dans un type mappé.

6. Transformer les propriétés sélectionnées

Les types mappés deviennent puissants lorsqu’ils combinent une sélection de clés avec une transformation. Voici une version simple d’un type qui rend toutes les propriétés facultatives :

type OptionalFields<T> = {
  [K in keyof T]?: T[K];
};

type Profile = { id: string; displayName: string };
type ProfilePatch = OptionalFields<Profile>;
// { id?: string; displayName?: string }

En code applicatif, utilisez généralement Partial<Profile>. Gardez en tête que rendre toutes les propriétés facultatives peut être trop permissif : un objet vide devient acceptable. Pour une commande de mise à jour, vous devrez peut-être exiger au moins une propriété ou définir un type dédié à l’opération.

Les clés peuvent aussi être filtrées par un type conditionnel. Cette technique permet d’identifier les propriétés dont les valeurs satisfont une condition, mais elle augmente rapidement la complexité. Préférez une définition explicite si le type calculé devient difficile à expliquer à un collègue.

7. Remappage des clés

Avec la clause as dans un type mappé, il est possible de transformer les noms de propriétés ou d’écarter certaines clés en les remappant vers never. Par exemple, on peut retirer les propriétés qui ne sont pas des chaînes :

type StringKeys<T> = {
  [K in keyof T as T[K] extends string ? K : never]: T[K];
};

type Settings = {
  theme: string;
  retries: number;
  locale: string;
};

type TextSettings = StringKeys<Settings>;
// { theme: string; locale: string }

Ce mécanisme est utile pour construire des vues dérivées, mais il ne valide pas les données à l’exécution et ne change pas l’objet JavaScript. Le type n’est qu’une description statique. Si une valeur vient d’un formulaire ou d’un serveur, sa forme réelle doit être contrôlée séparément.

8. Erreurs fréquentes et limites

  • Confondre une transformation de type et une transformation de valeur au runtime.
  • Oublier la distribution des types conditionnels sur une union.
  • Construire un utilitaire compliqué alors qu’un type intégré existe déjà.
  • Créer des types qui donnent une illusion de validation pour des données externes.
  • Empiler trop de conditions, ce qui ralentit parfois le compilateur et nuit à la lisibilité.

La meilleure abstraction est celle que l’équipe peut comprendre et modifier. Les types sophistiqués sont justifiés quand ils évitent des erreurs récurrentes ou améliorent clairement l’expérience d’utilisation d’une API ; ils ne constituent pas un objectif en soi.

Atelier guidé — dériver un type sans masquer son comportement

Les types conditionnels et mappés sont des outils de métaprogrammation au niveau des types. Ils sont utiles pour supprimer les duplications, mais rendent les erreurs plus difficiles à lire si leur résultat n’est pas vérifiable simplement.

type ApiResult<T> = T extends { error: unknown }
  ? { ok: false; error: T["error"] }
  : { ok: true; data: T };

type ApiUser = { id: number; name: string };
type ApiUserResult = ApiResult<ApiUser>;
// { ok: true; data: ApiUser }

type ApiError = { error: { message: string } };
type ErrorResult = ApiResult<ApiError>;
// { ok: false; error: { message: string } }

Pour comprendre le résultat, évaluez d’abord la condition T extends ..., puis la branche choisie. Si T est un paramètre générique nu qui reçoit une union, le type conditionnel peut se distribuer sur chaque membre. Pour éviter cette distribution dans certains cas, on peut encadrer les côtés du test avec des tuples, par exemple [T] extends [U].

Avant de publier un utilitaire de type, ajoutez des exemples de types d’entrée simples, unions, types limites et propriétés optionnelles. Survolez le type résultant dans l’éditeur ou utilisez des tests de types. Si l’équipe ne peut pas expliquer le résultat sans plusieurs minutes de navigation, préférez plusieurs alias nommés et une transformation plus simple.

9. Exercice

Définissez un type Config avec des propriétés chaîne, nombre et booléenne. Créez un type mappé qui conserve seulement les propriétés de type chaîne. Puis écrivez un type conditionnel qui enveloppe un type dans un tableau. Testez le résultat sur string | number et comparez la version distributive à la version qui enveloppe l’union entière. Utilisez le Playground pour vérifier les résultats.

10. Critères de réussite

  • Je sais lire et écrire T extends U ? X : Y.
  • Je comprends le rôle de infer dans une condition.
  • Je peux expliquer la distribution sur les unions.
  • Je sais transformer les propriétés avec keyof et un type mappé.
  • Je préfère les utilitaires standards lorsque leur contrat suffit.
