TypeScript : unions, intersections et narrowing

Modéliser plusieurs formes de données et réduire un type union de manière sûre à partir de contrôles explicites.

1. Objectifs et prérequis

Les unions et intersections permettent de décrire des données qui peuvent prendre plusieurs formes ou combiner plusieurs ensembles de propriétés. Le narrowing consiste à réduire un type large à un type plus précis grâce à des tests que TypeScript sait analyser. À la fin, vous saurez modéliser des états métier, utiliser des discriminants, traiter tous les cas d’une union et éviter les assertions de type inutiles.

2. Union : une valeur parmi plusieurs possibilités

Le type A | B signifie qu’une valeur peut être de type A ou de type B. Le code doit donc rester valide pour toutes les possibilités tant qu’il n’a pas établi laquelle est présente.

function formatId(id: string | number): string {
  return String(id);
}

formatId("abc");
formatId(42);

Dans le corps de la fonction, vous ne pouvez pas appeler directement une méthode propre aux chaînes sans vérifier le type. Une union n’est pas une promesse que la valeur est simultanément de chaque type : elle représente un ensemble de possibilités.

3. Réduire le type avec des contrôles

TypeScript comprend plusieurs formes de contrôle de flux. Le test typeof permet de distinguer des types primitifs ; in permet de vérifier la présence d’une propriété ; instanceof est utile pour certaines instances de classes. Après le test, le compilateur peut réduire le type possible dans chaque branche.

function describe(value: string | string[]) {
  if (typeof value === "string") {
    return value.toUpperCase();
  }
  return value.join(", ");
}

Le narrowing n’est pas une conversion magique à l’exécution : il s’appuie sur une condition réellement exécutée. Un cast tel que value as string ne vérifie pas que la valeur est une chaîne. Il demande au compilateur de faire confiance au programmeur, ce qui peut masquer un bug.

4. Unions discriminées : représenter des états métier

Pour des objets ayant plusieurs formes, un champ commun contenant une valeur littérale permet de distinguer les variantes. Ce champ est appelé discriminant. Cette approche est souvent plus robuste que de tester une série de propriétés facultatives.

type Result =
  | { status: "success"; data: string }
  | { status: "error"; message: string }
  | { status: "loading" };

function renderResult(result: Result): string {
  switch (result.status) {
    case "success":
      return result.data;
    case "error":
      return `Erreur : ${result.message}`;
    case "loading":
      return "Chargement…";
  }
}

Chaque branche donne accès aux propriétés qui appartiennent à la variante concernée. Ce modèle empêche par exemple de lire message sur un succès si ce champ n’existe pas dans son type. Il décrit aussi explicitement les états possibles de l’interface ou d’une opération asynchrone.

5. Vérifier l’exhaustivité

Lorsqu’une union représente un ensemble fini d’états, chaque cas doit être traité. Une fonction d’aide avec un paramètre de type never peut faire échouer la compilation si une nouvelle variante est ajoutée et oubliée :

function assertNever(value: never): never {
  throw new Error(`État non traité : ${String(value)}`);
}

function render(result: Result): string {
  switch (result.status) {
    case "success": return result.data;
    case "error": return result.message;
    case "loading": return "Chargement";
    default: return assertNever(result);
  }
}

Si une nouvelle variante est ajoutée à Result, le paramètre du cas par défaut ne sera plus nécessairement assignable à never, ce qui signale qu’il manque un traitement. L’exhaustivité est particulièrement utile pour les actions, statuts, événements et protocoles internes.

6. Intersection : combiner des contraintes

Le type A & B représente une valeur qui satisfait à la fois A et B. Il est utile pour composer des capacités ou décrire un objet qui possède plusieurs groupes de propriétés.

type HasId = { id: string };
type HasTimestamps = { createdAt: Date; updatedAt: Date };
type RecordBase = HasId & HasTimestamps;

const record: RecordBase = {
  id: "r-17",
  createdAt: new Date(),
  updatedAt: new Date()
};

Une intersection n’est pas une fusion qui résout automatiquement tous les conflits. Si deux types imposent des types incompatibles pour une même propriété, le résultat peut devenir impossible à satisfaire. Vérifiez les clés communes avant de composer des types complexes.

7. Unions et intersections ne sont pas interchangeables

Si ShapeA | ShapeB est une union, la valeur satisfait l’une des formes ; seules les propriétés communes sont accessibles avant narrowing. Avec ShapeA & ShapeB, la valeur doit satisfaire les deux formes. Utilisez l’union pour les alternatives, et l’intersection pour les exigences cumulatives.

Évitez aussi les objets dont toutes les propriétés sont facultatives pour représenter des états incompatibles. Par exemple, un objet pouvant avoir simultanément data? et error? autorise des combinaisons ambiguës. Une union discriminée rend les états valides explicites et les états impossibles plus difficiles à représenter.

8. Pièges fréquents

  • Accéder à une propriété spécifique avant d’avoir réduit l’union.
  • Utiliser un cast pour faire taire le compilateur sans contrôle d’exécution.
  • Oublier un cas lorsqu’une union évolue.
  • Confondre | et &.
  • Composer des intersections avec des propriétés homonymes incompatibles.
  • Supposer que TypeScript valide automatiquement un JSON reçu d’un serveur.

Le typage protège le code que vous compilez, mais les données externes restent à vérifier. Une réponse HTTP, un fichier JSON ou une valeur stockée dans le navigateur doit être considérée comme inconnue tant que sa forme n’a pas été validée.

Atelier guidé — rendre un traitement exhaustif

Une union discriminée représente les états possibles d’un processus. Le champ littéral status permet à TypeScript de réduire le type dans chaque branche :

type WorkflowResult =
  | { status: "success"; data: string }
  | { status: "failure"; message: string }
  | { status: "loading" };

function assertNeverWorkflow(value: never): never {
  throw new Error(`État non traité : ${JSON.stringify(value)}`);
}

function renderWorkflowResult(result: WorkflowResult): string {
  switch (result.status) {
    case "success": return result.data;
    case "failure": return `Erreur : ${result.message}`;
    case "loading": return "Chargement…";
    default: return assertNeverWorkflow(result);
  }
}

Ajoutez ensuite un état { status: "empty" } à WorkflowResult. Le compilateur doit signaler que le switch n’est plus exhaustif au niveau de assertNeverWorkflow(result). C’est une protection utile lorsque le modèle métier évolue : elle oblige à décider comment afficher le nouvel état au lieu de laisser passer un cas oublié.

Union ou intersection : utilisez une union lorsque la valeur peut respecter l’un de plusieurs contrats alternatifs ; utilisez une intersection lorsque la même valeur doit satisfaire simultanément plusieurs contrats compatibles. Une intersection de propriétés homonymes incompatibles peut produire un type impossible ou peu exploitable : ne l’utilisez pas comme stratégie automatique pour fusionner des objets.

9. Exercice

Définissez un type PaymentState avec les variantes pending, paid et failed. Ajoutez uniquement les propriétés pertinentes à chaque état : par exemple, une date de paiement pour paid et un code d’erreur pour failed. Écrivez une fonction qui renvoie un libellé pour chaque variante, activez le contrôle d’exhaustivité, puis ajoutez une quatrième variante et vérifiez que le compilateur vous aide à trouver le cas manquant.

10. Critères de réussite

  • Je distingue une union d’une intersection.
  • Je sais réduire une union avec typeof, un discriminant ou un contrôle adapté.
  • Je modélise des états métier sans combinaisons ambiguës.
  • Je détecte les variantes oubliées grâce à l’exhaustivité.
  • Je n’utilise pas un cast comme substitut à une validation.
