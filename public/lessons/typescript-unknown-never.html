TypeScript : inférence, unknown et never

Laisser le compilateur déduire les types, manipuler les valeurs inconnues sans perdre la sûreté et utiliser never pour représenter l’impossible.

1. Objectifs et prérequis

La qualité d’un programme TypeScript dépend autant des types que vous écrivez que de ceux que le compilateur peut inférer. Ce module explique quand laisser l’inférence agir, pourquoi unknown est préférable à any pour une donnée non vérifiée et comment never représente une impossibilité logique ou un chemin de code qui ne peut pas se terminer normalement. Il faut connaître les fonctions, les unions et le narrowing.

2. L’inférence : ne pas annoter pour annoter

TypeScript déduit souvent le type à partir de la valeur initiale, du contexte ou du retour d’une fonction. Cela évite les annotations redondantes et maintient le code lisible :

const retryCount = 3;       // type littéral 3 dans certains contextes
let attempts = 0;           // number
const names = ["Ada", "Lin"]; // string[]

function double(value: number) {
  return value * 2;         // retour inféré : number
}

Une annotation est utile lorsque le contrat doit être explicite, lorsqu’elle empêche une inférence trop étroite ou lorsqu’elle documente une frontière publique. Pour une fonction exportée ou une API réutilisée, un type de retour explicite peut améliorer la lisibilité et stabiliser le contrat. À l’inverse, annoter chaque variable locale avec un type évident ajoute du bruit.

3. any et unknown ne signifient pas la même chose

any désactive de nombreuses vérifications : vous pouvez accéder à des propriétés ou appeler la valeur sans preuve suffisante. unknown signifie que la valeur existe, mais que son type n’est pas encore établi. Vous devez effectuer un contrôle avant de l’utiliser comme un type plus précis.

function logLength(value: unknown) {
  if (typeof value === "string" || Array.isArray(value)) {
    console.log(value.length);
  }
}

Cette fonction ne suppose pas que toute donnée inconnue possède une propriété length. Elle vérifie les cas qu’elle sait traiter. Pour une donnée reçue d’un serveur, d’un fichier JSON ou d’un stockage local, utilisez souvent unknown à la frontière, puis validez et transformez la valeur en un type de domaine.

4. Valider une donnée inconnue

Un contrôle typeof ne suffit pas pour vérifier un objet complexe. Une fonction de garde peut inspecter les champs requis et annoncer un prédicat de type :

type User = { id: string; active: boolean };

function isUser(value: unknown): value is User {
  if (typeof value !== "object" || value === null) return false;
  if (!("id" in value) || !("active" in value)) return false;
  return typeof value.id === "string"
    && typeof value.active === "boolean";
}

Le prédicat value is User indique au compilateur que la fonction garantit le contrat si elle renvoie true. Il faut donc l’implémenter honnêtement : un prédicat incorrect peut tromper le système de types. Pour des structures profondes, des unions complexes ou des données provenant de sources peu fiables, une bibliothèque de validation peut être préférable à des contrôles manuels.

5. never : aucune valeur possible

never représente un type auquel aucune valeur normale ne peut appartenir. Il apparaît notamment lorsqu’une fonction lance toujours une exception ou lorsqu’une branche d’une union a été éliminée par narrowing. Il peut aussi servir à détecter les variantes non traitées.

function fail(message: string): never {
  throw new Error(message);
}

type Status = "queued" | "running" | "done";

function label(status: Status): string {
  switch (status) {
    case "queued": return "En attente";
    case "running": return "En cours";
    case "done": return "Terminé";
    default: {
      const exhaustive: never = status;
      return exhaustive;
    }
  }
}

Si une variante, par exemple "failed", est ajoutée à Status sans être traitée, l’affectation à never provoque une erreur de compilation. Cela transforme une omission silencieuse en problème détectable. Le même principe est utile pour les événements, actions, statuts et protocoles à ensemble fini.

6. Inférence et valeurs de retour

Une fonction qui n’a pas de retour explicite peut être inférée comme retournant void ou un type issu des branches. Si les branches renvoient des types différents, TypeScript peut inférer une union. Cela peut être exact, mais il est utile de se demander si cette union reflète vraiment le contrat voulu.

function parseCount(input: string) {
  const value = Number(input);
  if (!Number.isFinite(value)) return null;
  return value;
}
// retour : number | null

Le type number | null oblige les appelants à traiter l’échec représenté par null. Une autre conception pourrait renvoyer un objet discriminé ou lancer une erreur ; choisissez selon la convention du projet. Ne changez pas le contrat simplement pour rendre le type plus court.

7. Options de compilation qui renforcent la sûreté

Des options comme strict, noImplicitAny et strictNullChecks rendent plusieurs erreurs plus visibles. noUncheckedIndexedAccess peut également rappeler qu’un accès par index peut ne pas trouver de valeur. Ces options peuvent révéler des problèmes dans du code existant ; activez-les avec une stratégie de correction progressive plutôt qu’en masquant toutes les erreurs avec des assertions.

Une compilation sans erreur ne prouve pas que le programme respecte toutes les règles métier. Les types ne remplacent ni les tests, ni la validation runtime, ni l’observation du comportement en production. Ils réduisent toutefois la classe d’erreurs que le compilateur peut détecter avant l’exécution.

8. Erreurs fréquentes

  • Utiliser any pour faire disparaître une erreur sans comprendre son origine.
  • Faire confiance à un prédicat de type dont l’implémentation ne vérifie pas réellement le contrat.
  • Confondre void et never : une fonction void peut se terminer normalement sans valeur utile ; never n’a pas de retour normal.
  • Multiplier les annotations locales évidentes au lieu de laisser l’inférence fonctionner.
  • Supposer que les types compilés valident les données reçues au runtime.

Atelier guidé — sécuriser une frontière non typée

Une réponse HTTP, une valeur lue dans le stockage local ou une exception interceptée doit être considérée comme une donnée à vérifier. Le type déclaré par votre code ne garantit pas que le producteur respecte le contrat.

type ParsedUser = { id: number; name: string };

function isParsedUser(value: unknown): value is ParsedUser {
  if (typeof value !== "object" || value === null) return false;
  if (!("id" in value) || !("name" in value)) return false;
  return typeof value.id === "number" && typeof value.name === "string";
}

function parseUser(payload: unknown): ParsedUser {
  if (!isParsedUser(payload)) throw new Error("Réponse utilisateur invalide");
  return payload;
}

Ce prédicat vérifie les deux propriétés requises et leurs types primitifs. Pour des objets plus profonds, il faudrait valider chaque niveau pertinent ; dans une application réelle, une bibliothèque de validation de schéma peut réduire le risque d’oublier un cas. Ne convertissez pas une valeur en User par simple assertion si elle n’a pas été contrôlée. L’atelier utilise le nom distinct ParsedUser pour pouvoir être copié dans le même fichier que l’exemple précédent sans redéclarer User ni isUser.

Pour comprendre never, utilisez-le pour les branches qui ne devraient pas exister après un contrôle exhaustif. À l’inverse, unknown décrit une valeur présente mais pas encore comprise. Cette distinction est essentielle : une donnée externe commence souvent comme unknown, puis devient un type plus précis après validation ; never sert à prouver qu’aucune possibilité ne reste dans une branche.

9. Exercice

Écrivez une fonction qui accepte une valeur unknown et renvoie un nombre si la valeur est une chaîne représentant un nombre fini, sinon null. Ajoutez des tests pour une chaîne valide, une chaîne vide, une valeur non numérique et un nombre déjà fourni. Ensuite, définissez une union de quatre statuts et utilisez never pour détecter l’oubli d’une branche.

10. Critères de réussite

  • Je sais quand laisser TypeScript inférer un type et quand expliciter un contrat.
  • Je distingue clairement any et unknown.
  • Je valide les données inconnues avant de les traiter comme un type métier.
  • Je comprends l’usage de never et l’exhaustivité des unions.
  • Je peux expliquer les limites des garanties statiques de TypeScript.
