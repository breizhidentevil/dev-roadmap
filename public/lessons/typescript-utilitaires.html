TypeScript : types utilitaires — Pick, Omit, Partial et Record

Composer des types existants avec les utilitaires intégrés de TypeScript et comprendre les garanties, limites et usages de chacun.

1. Objectifs et prérequis

Les types utilitaires sont des transformations génériques fournies par TypeScript. Ils permettent de dériver un type d’un autre sans recopier les propriétés manuellement. À la fin, vous saurez utiliser Pick, Omit, Partial et Record, choisir entre eux selon l’intention et repérer les cas où ils rendent le contrat trop permissif. Il faut connaître les objets, les unions, keyof et les types génériques.

2. Pourquoi dériver un type ?

Un même modèle métier peut être utilisé dans plusieurs contextes. Un utilisateur complet peut contenir un identifiant, un nom, un courriel, un statut et des champs internes. Une fiche publique ne doit peut-être exposer que le nom et le statut ; un formulaire de mise à jour ne reçoit qu’une partie des propriétés. Copier la définition dans plusieurs types provoque des divergences quand le modèle évolue.

Les utilitaires expriment une intention à partir du type source. Ils ne créent pas un nouvel objet JavaScript et ne suppriment pas réellement des propriétés à l’exécution. Ils ne remplacent donc ni une projection de données, ni une validation de requête, ni une règle d’autorisation.

3. Pick<T, K> : ne garder que certaines clés

type User = {
  id: string;
  name: string;
  email: string;
  isAdmin: boolean;
};

type PublicUser = Pick<User, "id" | "name">;
// { id: string; name: string }

Pick est utile quand vous voulez définir précisément les champs nécessaires à une vue ou à une fonction. Les clés doivent appartenir au type source, ce qui aide à détecter une faute de frappe. Si le modèle évolue, le type dérivé continue à suivre les types des propriétés sélectionnées.

Attention : Pick n’efface pas les champs de l’objet à l’exécution. Si vous renvoyez directement un objet complet depuis une API, les propriétés supplémentaires peuvent toujours être présentes. Construisez explicitement la réponse ou utilisez une couche de sérialisation adaptée pour contrôler les données exposées.

4. Omit<T, K> : retirer certaines clés du type

type UserWithoutEmail = Omit<User, "email">;
// { id: string; name: string; isAdmin: boolean }

Omit est pratique lorsqu’un type reprend presque tout le modèle sauf quelques champs. Mais une liste d’exclusions peut devenir dangereuse si le modèle gagne plus tard une nouvelle propriété sensible : celle-ci sera incluse par défaut. Pour une réponse publique ou une frontière de sécurité, une liste positive avec Pick est souvent plus sûre parce qu’elle n’expose que les champs explicitement autorisés.

5. Partial<T> : rendre les propriétés facultatives

type Profile = {
  displayName: string;
  biography: string;
};

type ProfilePatch = Partial<Profile>;
// { displayName?: string; biography?: string }

Partial est souvent utilisé pour des mises à jour partielles. Il autorise toutefois l’objet vide et n’exprime pas automatiquement la différence entre « champ absent » et « champ fourni avec une valeur vide ». Ces distinctions peuvent être importantes dans une API. Il faut définir la sémantique de la mise à jour : une propriété absente signifie-t-elle « ne rien changer », et une chaîne vide signifie-t-elle « effacer le contenu » ?

Pour une opération métier qui exige au moins un champ, ajoutez une validation ou définissez un type plus précis. Le type statique peut empêcher certaines erreurs, mais la requête reçue d’un client doit être validée à l’exécution.

6. Record<K, V> : associer des clés à un type de valeur

type Role = "reader" | "editor" | "admin";
type RolePermissions = Record<Role, boolean>;

const permissions: RolePermissions = {
  reader: true,
  editor: true,
  admin: false
};

Lorsque les clés forment une union finie, Record impose une entrée pour chaque membre et signale les clés manquantes ou inattendues dans un littéral d’objet. Il est adapté aux tables de configuration, dictionnaires et correspondances entre états et fonctions.

Si K est simplement string, Record<string, V> décrit un objet indexé par des chaînes ; cela ne signifie pas que toutes les chaînes possibles existent réellement à l’exécution. Pour une clé arbitraire, vérifiez la présence de l’entrée avant de l’utiliser, et considérez noUncheckedIndexedAccess dans la configuration TypeScript.

7. Combiner les utilitaires avec intention

type UserPatch = Partial<Pick<User, "name" | "email">>;
type UserSummary = Pick<User, "id" | "name">;
type UserCreation = Pick<User, "name" | "email">;

Ces combinaisons peuvent réduire la duplication, mais chaque alias devrait exprimer un concept du domaine. Pour une entrée contrôlée par un client, Pick établit une liste positive des champs acceptés ; Omit<User, "id"> laisserait ici isAdmin dans le type de création. La liste positive réduit le risque d’autoriser involontairement un champ ajouté plus tard. Les types sont une interface pour les personnes qui lisent le code autant qu’une contrainte pour le compilateur.

8. Ce que les utilitaires ne font pas

  • Ils ne valident pas le JSON reçu sur le réseau.
  • Ils ne retirent pas les propriétés d’un objet à l’exécution.
  • Ils ne garantissent pas l’autorisation d’un utilisateur à consulter un champ.
  • Ils ne définissent pas à eux seuls la sémantique métier d’une mise à jour.
  • Ils n’empêchent pas toutes les valeurs incorrectes si le code contourne le système de types.

Un type comme PublicUser documente ce que votre code prévoit d’exposer ; la couche qui construit la réponse doit respecter ce contrat réellement. Une autorisation doit être contrôlée côté serveur, même si le frontend ne possède pas le champ sensible dans ses types.

Atelier guidé — distinguer forme TypeScript et sécurité métier

Considérons un modèle interne et une requête de modification :

type InternalUser = {
  id: string;
  email: string;
  displayName: string;
  isAdmin: boolean;
};

type InternalUserSummary = Pick<InternalUser, "id" | "displayName">;
type InternalUserPatch = Partial<Pick<InternalUser, "email" | "displayName">>;
type RoleByUserId = Record<string, "reader" | "editor">;

Ces types précisent la forme attendue au moment de la compilation. Ils ne filtrent pas automatiquement le JSON reçu sur le réseau. Si un client envoie { "isAdmin": true }, une annotation InternalUserPatch ne constitue pas une validation à l’exécution. Il faut analyser les données entrantes, rejeter les propriétés non autorisées selon le contrat de l’API, puis appliquer une autorisation côté serveur.

Décision de conception : Partial<T> rend toutes les propriétés facultatives ; il ne signifie pas que toutes les combinaisons partielles sont valides métier. Un patch peut aussi avoir des règles différentes pour une valeur absente, null et une chaîne vide. Documentez ces distinctions et testez-les explicitement.

9. Exercice

À partir d’un type Product contenant id, name, price, stock et internalCost, créez un type pour l’affichage public, un type de mise à jour partielle et un dictionnaire de produits indexé par une union de catégories. Expliquez pourquoi le type d’affichage ne suffit pas à filtrer les champs de la réponse HTTP et écrivez une fonction qui construit explicitement la projection publique.

10. Critères de réussite

  • Je sais distinguer les usages de Pick et Omit.
  • Je comprends que Partial autorise des champs absents et peut être trop permissif.
  • Je sais utiliser Record pour une table de correspondance.
  • Je sépare types statiques, validation runtime et autorisation serveur.
  • Je peux justifier chaque type dérivé par un besoin identifiable.
