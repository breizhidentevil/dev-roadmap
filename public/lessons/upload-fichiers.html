5. Sécurité applicative

Sécurité des fichiers téléversés

Valider, isoler et servir les fichiers envoyés par les utilisateurs.

Tutoriel approfondiQualité et tests

Objectifs et prérequis

Tu dois savoir concevoir un endpoint de téléversement sans faire confiance au nom, à l’extension ou au type MIME déclarés par le navigateur. Tu apprendras à limiter la taille, vérifier le contenu, stocker hors du répertoire exécutable et contrôler l’accès au téléchargement.

  • Définir une liste blanche de formats et des limites de taille.
  • Comprendre pourquoi une extension ou un en-tête MIME ne suffit pas.
  • Protéger le système de fichiers et le parcours de traitement asynchrone.

1. Pourquoi un upload est une frontière de confiance

Un fichier envoyé par un utilisateur est une entrée non fiable. Il peut être trop volumineux, malformé, conçu pour exploiter un parseur, porter un contenu actif ou avoir une extension trompeuse. Le nom de fichier peut aussi contenir des chemins ou des caractères inhabituels. La sécurité doit couvrir l’acceptation, le stockage, le traitement et la restitution.

Commence par définir précisément les usages permis. Un avatar JPEG n’a pas les mêmes besoins qu’un import CSV ou un document PDF. Une liste blanche de formats et des limites par usage sont plus faciles à vérifier qu’une règle générique « tout type de fichier est accepté ».

2. Valider plusieurs propriétés

Ne considère jamais un seul signal comme preuve. Vérifie au minimum :

  • la taille maximale du fichier et, si nécessaire, le nombre de fichiers par requête ;
  • l’extension normalisée selon la liste autorisée ;
  • le type déclaré, sans lui faire confiance seul ;
  • la signature ou la structure réelle du contenu avec une bibliothèque appropriée ;
  • les dimensions, pages ou limites de décompression pour les formats concernés.

Un fichier peut annoncer image/png tout en contenant autre chose. Inversement, une détection de signature n’élimine pas les fichiers malveillants. Pour des formats complexes, maintiens les bibliothèques à jour et envisage une analyse antivirus ou une mise en quarantaine selon le risque.

Ces contrôles se cumulent : la signature du fichier, le MIME et l’extension sont des indices différents, pas trois preuves équivalentes. Si tu convertis une image, effectue la conversion avec une bibliothèque maintenue et limite les ressources consommées ; ne traite pas cette conversion comme une garantie absolue.

3. Noms et emplacement de stockage

Ne construis pas un chemin de destination directement depuis le nom fourni par l’utilisateur. Génère un identifiant aléatoire côté serveur, conserve éventuellement le nom original comme métadonnée nettoyée, et stocke les fichiers dans un emplacement dédié qui n’est pas servi comme code exécutable.

// Schéma de principe
const id = crypto.randomUUID();
const destination = join(UPLOAD_ROOT, id);
// Vérifier que UPLOAD_ROOT est fixe et que le traitement
// n'utilise jamais le nom fourni comme chemin.

Le code est illustratif : en production, utilise une API de stockage adaptée et vérifie les permissions du répertoire. Pour le stockage objet, sépare les buckets ou préfixes selon les besoins, protège les credentials et évite de rendre les objets publics par défaut.

La normalisation de chemin seule n’est pas une garantie si des liens symboliques ou des courses entre vérification et ouverture sont possibles. La conception la plus sûre évite de laisser l’utilisateur choisir le chemin.

4. Télécharger un fichier en sécurité

Le téléchargement doit vérifier l’autorisation sur la ressource : connaître un identifiant de fichier ne doit pas suffire à récupérer le fichier d’un autre utilisateur. Le serveur devrait définir un type de contenu maîtrisé et, pour les fichiers non destinés à être affichés en ligne, utiliser souvent Content-Disposition: attachment. Une politique X-Content-Type-Options: nosniff peut compléter les protections côté navigateur.

Si tu utilises des URL signées vers un stockage objet, limite leur durée de vie et leur périmètre. Une URL signée est un bearer token : toute personne qui la possède peut agir selon ses permissions jusqu’à expiration.

Traite les formats actifs séparément des images raster. SVG, HTML et certains documents peuvent contenir du contenu interprétable ; ne les affiche pas automatiquement en ligne sur la même origine que l’application authentifiée. Si le besoin métier ne l’exige pas, refuse ces formats. Pour des images, un ré-encodage avec un décodeur maintenu peut réduire les métadonnées et contenus inattendus, sans remplacer les limites de ressources ni les autres contrôles. Pour les fichiers téléchargés, définis un type contrôlé, utilise Content-Disposition: attachment lorsque l’affichage n’est pas nécessaire, et envisage une origine dédiée sans cookies applicatifs pour les contenus utilisateur.

5. Traitement et disponibilité

Ne traite pas immédiatement des fichiers coûteux dans le thread de la requête si cela risque de bloquer le serveur. Une chaîne robuste peut stocker d’abord le fichier en quarantaine, créer un travail asynchrone, analyser le contenu puis marquer le fichier comme disponible seulement après validation.

Limite aussi le temps CPU, la mémoire, le nombre de pages, les dimensions d’image et les taux de décompression. Les archives et documents compressés peuvent être très petits avant extraction et énormes après extraction. Définis des plafonds et traite les erreurs sans laisser des fichiers temporaires orphelins.

Modélise le traitement avec un état explicite, par exemple RECEIVED → QUARANTINED → SCANNING → AVAILABLE, avec une sortie REJECTED en cas d’échec. Seuls les fichiers AVAILABLE sont téléchargeables. Le worker doit tolérer une relance sans publier deux fois le même fichier ; un travail interrompu ne doit pas laisser un objet publiquement accessible. Prévois également une tâche de nettoyage des fichiers temporaires et des éléments en quarantaine trop anciens.

Erreurs fréquentes

  • Faire confiance à l’extension ou au MIME envoyé par le client.
  • Utiliser le nom du fichier comme chemin sur le serveur.
  • Stocker les fichiers dans un répertoire où le serveur peut exécuter du code.
  • Accepter des fichiers sans limite de taille ou de quantité.
  • Servir des fichiers privés sans revérifier les droits à chaque téléchargement.
  • Extraire des archives sans limiter la taille totale décompressée.

Exercice guidé

Construis un endpoint de démonstration qui accepte uniquement des images PNG et JPEG de moins de 2 Mo. Génère un identifiant serveur, place le fichier dans un répertoire dédié, puis crée un endpoint de lecture qui vérifie que l’utilisateur a le droit d’accéder au fichier.

Teste une extension falsifiée, un MIME incorrect, un fichier trop volumineux, un nom contenant ../, un SVG avec contenu actif et un identifiant appartenant à un autre utilisateur. Chaque cas doit être rejeté ou traité selon une règle documentée. Vérifie qu’un fichier en quarantaine ou rejeté n’est jamais servi, même si son URL ou son identifiant est connu, et que les réponses de téléchargement ne révèlent pas le chemin interne ni le nom temporaire. Ajoute un test qui simule l’échec du scanner et vérifie que le fichier reste indisponible, puis un test de reprise du worker pour vérifier qu’il ne crée pas de publication en double. Vérifie enfin que les fichiers temporaires sont supprimés après un échec.

Exercice autonome et critères de réussite

Décris le pipeline d’upload d’un document PDF : validation, stockage temporaire, analyse, publication, accès et suppression.

Réussite : les formats acceptés sont explicitement listés ; taille et traitement sont bornés ; le nom client ne contrôle pas le chemin ; le stockage n’exécute pas les fichiers ; l’accès est vérifié au téléchargement ; les erreurs nettoient les fichiers temporaires ; les tests couvrent les entrées falsifiées et les limites de ressources.
