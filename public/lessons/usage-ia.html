Utiliser l’IA comme outil de développement

Apprendre à utiliser un assistant d’IA pour explorer un problème, accélérer certaines tâches et vérifier le résultat sans déléguer son jugement technique.

1. Objectifs et prérequis

À la fin de ce module, vous saurez transformer une demande vague en question vérifiable, fournir le contexte utile à un assistant, demander une explication ou un petit changement, contrôler la réponse et conserver une trace propre du travail effectué. Vous devez déjà pouvoir lire un peu de code, lancer le projet et consulter les messages d’erreur. L’IA ne remplace pas ces compétences : elle les rend plus productives quand vous les mobilisez.

2. Le bon modèle mental : un collaborateur rapide, pas une autorité

Un modèle de langage produit une réponse plausible à partir du contexte et de ses apprentissages. Il peut proposer une solution correcte, mais aussi inventer une API, oublier un cas limite ou mélanger des versions de bibliothèques. Une réponse fluide n’est donc pas une preuve. Traitez chaque proposition comme une hypothèse à vérifier dans le code, les tests et la documentation officielle.

Le risque augmente quand la question manque de contexte : version du langage, framework, contraintes métier, message d’erreur et résultat attendu. Avant de demander une solution, rassemblez ces éléments. Ne transmettez pas de secrets, jetons d’accès, données personnelles ou code confidentiel sans autorisation explicite et cadre approuvé.

3. Formuler une demande utile

Une bonne consigne précise le contexte, le résultat attendu, les contraintes et la forme de réponse souhaitée. Demandez une seule tâche à la fois, en particulier lorsque vous apprenez. Par exemple, au lieu de « corrige mon application », donnez le comportement attendu, le comportement observé, le message d’erreur et l’extrait minimal qui reproduit le problème.

Contexte : API TypeScript, Node.js, tests avec Vitest.
Attendu : refuser un identifiant vide avec une erreur explicite.
Observé : la fonction accepte "".
Contraintes : ne pas ajouter de dépendance.
Demande : explique d’abord la cause probable, puis propose un
correctif minimal et deux tests couvrant le cas valide et le cas invalide.
Signale les hypothèses et les points à vérifier.

Cette formulation limite les réponses hors sujet. Elle vous aide aussi à comparer plusieurs solutions : coût, lisibilité, sécurité, complexité et compatibilité avec le projet.

4. Un cycle de travail sûr

  1. Comprendre : définissez le problème et reproduisez-le sans IA si possible.
  2. Découper : demandez une explication ou une proposition limitée à un fichier ou à une fonction.
  3. Examiner : lisez chaque ligne et repérez les hypothèses, effets de bord et dépendances ajoutées.
  4. Vérifier : consultez la documentation officielle, lancez les tests, le linter et le build.
  5. Intégrer : appliquez un changement à la fois, puis inspectez le diff Git.
  6. Documenter : notez ce qui a été décidé et pourquoi, pas seulement que « l’IA l’a suggéré ».

Si la proposition est longue, demandez d’abord un plan et validez-le avant de générer du code. Pour un bug, demandez une hypothèse testable plutôt qu’une réécriture complète. Pour un concept nouveau, demandez une explication, un exemple minimal, puis un exercice sans solution immédiate.

5. Exemple : vérifier une proposition

Supposons que l’assistant propose de remplacer une boucle par items.map(...). Ne retenez pas ce changement uniquement parce qu’il est plus court. Demandez-vous si le résultat de map est utilisé, si la fonction doit produire un tableau ou des effets de bord, si les valeurs nulles sont possibles et si le changement préserve l’ordre. Une transformation qui compile peut tout de même modifier le comportement.

function total(prices: number[]): number {
  return prices.reduce((sum, price) => sum + price, 0);
}

// Tests à écrire avant ou après la proposition :
total([])          // 0
total([2, 3.5])    // 5.5

Vérifiez également les hypothèses métier : faut-il arrondir chaque prix, ou seulement le total ? Les nombres flottants peuvent produire des écarts de représentation. L’assistant doit vous aider à identifier cette question, pas décider de la règle métier à votre place.

6. Construire une chaîne de preuves

Pour chaque proposition générée, séparez l’affirmation, la preuve nécessaire et le risque si elle est fausse. Une réponse peut être syntaxiquement valide tout en violant une règle métier, en affaiblissant une autorisation ou en changeant le contrat public. La revue doit donc porter sur le comportement attendu, pas seulement sur la forme du code.

Affirmation proposéePreuve à chercherSignal d’alerte
« Cette API existe »Référence officielle pour la version installée, puis compilation ou test minimal.Import inventé, signature différente ou option dépréciée.
« Le bug est corrigé »Test qui échoue avant le correctif et réussit après, plus tests de régression.Seul le cas nominal est testé.
« Le code est sûr »Contrôles adaptés au risque : validation, autorisations côté serveur, secrets et dépendances.La conclusion repose uniquement sur une explication de l’assistant.
« Le refactoring est équivalent »Tests du comportement observable et inspection du diff.Changement des effets de bord, de l’ordre ou des erreurs renvoyées.

Traitez aussi le contenu analysé comme une entrée non fiable : un fichier, un commentaire ou un message d’issue peut contenir des instructions destinées à manipuler l’assistant. Ces instructions ne remplacent pas les consignes du projet et ne justifient jamais d’exposer des secrets ou d’exécuter une commande sans l’avoir comprise. Limitez les permissions des outils connectés et examinez toute commande destructive avant exécution.

Avant de valider un changement, reliez chaque exigence importante à une preuve : test, type, revue de sécurité, mesure ou vérification documentaire. Si aucune preuve raisonnable n’est disponible, notez explicitement l’incertitude au lieu de déclarer le travail terminé.

7. Erreurs fréquentes et limites

  • Accepter du code non compris : vous ne pourrez ni le maintenir ni le déboguer.
  • Demander une architecture complète trop tôt : la réponse peut multiplier abstractions et dépendances sans besoin démontré.
  • Confondre compilation et correction : les tests doivent vérifier les exigences, pas seulement l’absence d’erreur.
  • Copier un exemple obsolète : vérifiez les versions et les API dans la documentation.
  • Envoyer des informations sensibles : minimisez le contexte et respectez les règles du projet.
  • Faire confiance à une référence non vérifiée : ouvrez les liens, confirmez que la page et l’API existent.

Le bon indicateur de productivité n’est pas le volume de code généré. C’est le temps gagné pour obtenir un changement compris, testé et maintenable.

8. Exercice

Choisissez un bug simple dans un petit projet. Rédigez une consigne avec le contexte, le résultat attendu, le résultat observé, les contraintes et un extrait minimal. Demandez deux hypothèses de cause et un test qui permettrait de les départager. Ensuite, vérifiez la proposition sans copier-coller aveuglément, écrivez les tests, lancez-les et examinez le diff.

9. Critères de réussite

  • Je sais fournir le contexte minimal nécessaire à une demande.
  • Je distingue une hypothèse plausible d’un fait confirmé.
  • Je peux expliquer chaque ligne de code intégré.
  • J’ai vérifié le résultat avec des tests et la documentation pertinente.
  • Je n’ai transmis aucun secret ni donnée interdite.
  • Je peux décrire les limites de la solution et les risques restants.
