3. Backend

Validation avec Zod, Joi ou Yup

Définir et vérifier des schémas de données.

Tutoriel détailléLot 11 · 2026

Objectifs d’apprentissage

  • Décrire les données attendues avec un schéma exécutable.
  • Distinguer validation syntaxique, validation métier et autorisation.
  • Comprendre la différence entre validation et conversion des types.
  • Produire des erreurs utiles sans exposer d’informations sensibles.

1. Pourquoi valider à la frontière

Les données reçues d’un navigateur, d’un webhook, d’un fichier ou d’un autre service doivent être considérées comme non fiables. Les types TypeScript disparaissent à l’exécution : déclarer req.body comme un objet typé ne vérifie pas le JSON reçu. Un schéma d’exécution permet de contrôler réellement la structure, les types et certaines contraintes.

Valide tôt, à la frontière du système, puis transmets au reste du code une représentation dont les invariants sont connus. Les contraintes importantes doivent aussi être garanties par la base de données lorsqu’elles concernent l’intégrité des données.

2. Définir un schéma avec Zod

import { z } from "zod";

const CreateTaskSchema = z.object({
  title: z.string().trim().min(1).max(120),
  dueDate: z.string().date().optional(),
  priority: z.enum(["low", "normal", "high"]).default("normal")
});

type CreateTaskInput = z.infer<typeof CreateTaskSchema>;

const result = CreateTaskSchema.safeParse(input);
if (!result.success) {
  // Convertir les erreurs en réponse HTTP documentée.
} else {
  const data: CreateTaskInput = result.data;
}

Exemple avec Zod : safeParse renvoie un résultat discriminé et évite d’utiliser une exception pour un échec de validation attendu. result.data est la valeur validée et éventuellement transformée, pas simplement la donnée brute d’origine.

3. Valider n’est pas seulement typer

Un schéma peut vérifier la forme, les longueurs, les formats, les valeurs permises et parfois transformer les données. Mais une date syntaxiquement valide peut être dans le passé ; un identifiant peut exister sans appartenir à l’utilisateur ; une adresse électronique peut être bien formée sans être vérifiée.

  • Structure : l’objet possède les champs attendus et des types acceptés.
  • Règles métier : la date limite est cohérente avec l’état de la tâche.
  • Autorisation : l’utilisateur a le droit de modifier cette tâche.
  • Intégrité : la base garantit unicité, clés étrangères et contraintes atomiques.

4. Corps, paramètres et erreurs

Valide séparément le corps JSON, les paramètres de chemin et les paramètres de requête. Les paramètres d’URL arrivent souvent sous forme de chaînes : convertir "25" en nombre doit être une décision explicite et contrôlée, avec une plage autorisée.

Renvoie une erreur stable qui identifie les champs invalides et la nature du problème. Ne renvoie pas l’objet complet reçu ni des détails internes du validateur si ceux-ci risquent de révéler des informations inutiles. La validation côté client améliore l’expérience, mais le serveur reste la frontière de confiance.

5. Schémas partagés et évolution

Partage les schémas lorsqu’ils représentent réellement le même contrat. Un schéma de création, de mise à jour et de réponse ne sont pas nécessairement identiques : une réponse peut inclure un identifiant généré, tandis qu’une mise à jour autorise certains champs absents. Réutiliser un schéma trop général peut rendre accidentellement modifiables des champs réservés au serveur.

Ajoute des tests pour les cas valides, les champs manquants, les types incorrects, les limites, les valeurs inattendues et les tentatives d’injecter des propriétés sensibles comme role ou ownerId.

6. Étude de cas : de l’entrée non fiable à la commande métier

Une requête de création de tâche peut contenir title, dueDate et priority. Le schéma d’entrée vérifie la forme des données ; il ne garantit pas à lui seul que la date soit compatible avec la règle métier, que l’utilisateur possède le projet ciblé ou que l’écriture concurrente reste valide.

const CreateTaskSchema = z.object({
  title: z.string().trim().min(1).max(120),
  dueDate: z.string().date().optional(),
  priority: z.enum(["low", "normal", "high"]).default("normal")
}).strict();

const parsed = CreateTaskSchema.safeParse(request.body);
if (!parsed.success) {
  const details = parsed.error.issues.slice(0, 20).map(issue => ({
    field: issue.path.join("."),
    code: issue.code
  }));
  return reply.code(400).send({ error: "INVALID_INPUT", details });
}
const input = parsed.data; // valeur validée et normalisée
// Ensuite : authentifier, autoriser, vérifier les règles métier,
// puis persister avec les contraintes de la base de données.

.strict() est un choix de contrat : il refuse les propriétés inconnues. Selon l’API, tu peux préférer les retirer ou les conserver explicitement, mais ne laisse pas le comportement par défaut décider sans réflexion. Les valeurs par défaut et transformations doivent également être documentées, car elles modifient la donnée transmise à la logique métier.

Trois niveaux à ne pas confondre

  • Syntaxe/forme : la chaîne ressemble-t-elle à une date valide et le champ est-il du bon type ?
  • Règle métier : la date d’échéance est-elle autorisée pour ce statut ou ce projet ?
  • Autorisation : cet utilisateur a-t-il le droit de créer une tâche dans ce projet ?

Ne renvoie pas automatiquement tous les détails internes du validateur : les chemins de champs peuvent être utiles au client, mais les valeurs reçues peuvent contenir des données personnelles. Normalise le format d’erreur, limite le nombre d’erreurs et évite d’inclure une pile d’appel.

Tests à écrire : champ manquant, corps qui n’est pas un objet, chaîne vide après trim, chaîne trop longue, priorité inconnue, date mal formée, propriété inattendue et valeur valide. Vérifie aussi que le défaut normal est appliqué comme prévu. Puis teste séparément une règle métier refusée et un accès interdit : ces cas ne sont pas des erreurs de schéma. Vérifie enfin que la réponse d’erreur contient seulement des chemins de champs et des codes contrôlés, jamais les valeurs reçues ni une pile d’appel.

Critère de réussite : une entrée invalide n’atteint pas la logique métier, une entrée valide fournit un type inféré fiable, et les erreurs de validation ne sont pas confondues avec les refus métier ou d’autorisation.

Erreurs fréquentes

  • Penser que TypeScript valide automatiquement les requêtes à l’exécution.
  • Valider uniquement dans le navigateur.
  • Confondre validation de forme et autorisation.
  • Accepter des propriétés supplémentaires sensibles par défaut.
  • Utiliser le même schéma indistinctement pour création, modification et réponse.

Exercice guidé

Écris un schéma de création d’utilisateur avec un nom de 2 à 60 caractères, un courriel au format accepté et un mot de passe d’au moins 12 caractères. Refuse les propriétés non prévues ou définis explicitement leur traitement. Ajoute ensuite les contrôles métier et d’autorisation nécessaires à une modification de profil.

Critères de réussite

  • Les règles sont exécutées côté serveur.
  • Les conversions et valeurs par défaut sont explicites.
  • Les erreurs identifient les champs sans exposer de secrets.
  • Validation, règles métier et autorisation restent distinctes.
  • Les cas limites sont testés automatiquement.
