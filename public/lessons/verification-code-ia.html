Vérification du code généré

Contrôler exactitude, sécurité, tests, licences et maintenabilité du code produit avec une IA.

Leçon approfondieThéorie · pratique · validation

Objectifs d’apprentissage

À la fin de cette leçon, tu dois pouvoir expliquer les concepts avec tes propres mots, choisir une approche adaptée à un contexte réel et justifier tes décisions en fonction des contraintes et des risques.

  • Comprendre les notions essentielles et le problème qu’elles permettent de résoudre.
  • Appliquer une méthode concrète et vérifier son résultat.
  • Identifier les limites, les compromis et les erreurs fréquentes.

1. Traiter la génération comme une proposition, pas comme une preuve

Un assistant de code peut produire rapidement une fonction plausible, un test ou une migration. La forme convaincante du résultat ne garantit ni sa correction ni sa sécurité. Le code doit respecter le besoin, les contrats existants, les contraintes de performance et les conventions du projet. La responsabilité de l’intégration reste celle de la personne qui livre le changement.

Commence par reformuler ce que le code doit garantir. Par exemple, « valider un e-mail » est trop vague : faut-il vérifier une syntaxe minimale, accepter les adresses internationales, confirmer l’existence de la boîte ou empêcher les doublons ? Une implémentation ne peut être évaluée sans contrat clair. Identifie les entrées, sorties, effets de bord, erreurs attendues et invariants métier avant de lire le code généré.

Examine ensuite la différence introduite plutôt que de relire uniquement les lignes nouvelles. Une fonction apparemment locale peut modifier un type partagé, un comportement public, une dépendance ou une requête SQL. Le contexte révèle souvent les hypothèses que le générateur n’a pas pu connaître.

2. Une procédure de vérification reproductible

  1. Relire le besoin : écris les comportements attendus et les cas qui doivent être refusés.
  2. Inspecter chaque ligne : vérifie les types, les conditions, les conversions, la gestion des erreurs et les effets de bord.
  3. Exécuter les contrôles : formatage, lint, compilation, tests unitaires, intégration et tests pertinents du projet.
  4. Ajouter des tests indépendants : ne te limite pas aux tests proposés par l’IA, qui peuvent reproduire les mêmes hypothèses erronées que l’implémentation.
  5. Examiner la sécurité : authentification, autorisation, validation des entrées, secrets, dépendances et exposition des données.
  6. Vérifier la maintenabilité : cohérence avec l’architecture, complexité, duplication, noms et documentation.

Les tests prouvent seulement que le code satisfait les cas couverts. Ils ne prouvent pas que le comportement est complet. Il faut donc associer tests automatisés, revue humaine et, pour les changements risqués, vérifications ciblées comme l’analyse statique ou un test de charge.

// Exemple TypeScript : contrat explicite et testable
// Nécessite une cible JavaScript/TypeScript ES2020 ou plus récente.
type Discount = {
  priceCents: number;
  percentageBps: number; // 100 points de base = 1 %
};

const BASIS_POINTS = 10_000n;

export function discountedPrice(input: Discount): number {
  if (!Number.isSafeInteger(input.priceCents) || input.priceCents < 0) {
    throw new RangeError("priceCents doit être un entier sûr positif ou nul");
  }
  if (!Number.isInteger(input.percentageBps) ||
      input.percentageBps < 0 || input.percentageBps > 10_000) {
    throw new RangeError("percentageBps doit être un entier entre 0 et 10000");
  }

  const price = BigInt(input.priceCents);
  const factor = BASIS_POINTS - BigInt(input.percentageBps);
  // Arrondi commercial explicite : les demi-centimes sont arrondis vers le haut.
  const discountedCents = (price * factor + BASIS_POINTS / 2n) / BASIS_POINTS;
  return Number(discountedCents);
}

Le contrat choisit ici des centimes entiers, une remise entière en points de base et un arrondi des demi-centimes vers le haut. BigInt évite de multiplier directement les montants par des nombres flottants. Cette règle d’arrondi est un choix métier illustratif : elle doit être confirmée, documentée et partagée avec les autres systèmes avant utilisation réelle. Le code nécessite une cible ES2020 ou plus récente.

3. Tester les frontières et les hypothèses

Pour une fonction numérique, vérifie zéro, les valeurs négatives, les limites, les valeurs extrêmes et les entrées non finies. Pour une API, teste l’absence de champs, les types incorrects, les permissions, les erreurs du service tiers et les requêtes répétées. Pour une migration, teste les données historiques et la possibilité de reprendre après une interruption.

Les tests générés automatiquement peuvent être utiles pour obtenir un premier squelette. Évalue leur pertinence : un test qui ne contient que des assertions triviales ou qui copie exactement l’algorithme de la fonction apporte peu de confiance. Les tests devraient exprimer le comportement attendu indépendamment de l’implémentation.

Lorsque la logique a beaucoup de cas, ajoute des tests fondés sur des propriétés ou des invariants. Par exemple, une pagination ne doit pas retourner deux fois le même élément dans des pages successives, et une opération idempotente doit conserver le même effet lorsqu’elle est répétée avec la même clé. Ces propriétés peuvent détecter des défauts que quelques exemples heureux ne révèlent pas.

4. Sécurité, dépendances et provenance

Inspecte les appels système, les requêtes construites à partir de chaînes, la désérialisation, les permissions et les données journalisées. Un code généré peut contenir une injection SQL, un contrôle d’accès manquant ou un secret fictif ressemblant à une vraie valeur. Utilise des requêtes paramétrées, les mécanismes d’autorisation du projet et un gestionnaire de secrets adapté.

Si la proposition ajoute une bibliothèque, vérifie sa maintenance, sa licence, sa réputation, ses vulnérabilités connues, sa taille et la nécessité réelle de la dépendance. N’installe pas un paquet simplement parce que le nom proposé semble plausible. Vérifie aussi la provenance et les règles de licence applicables au code utilisé dans ton organisation. Les outils et politiques varient ; l’assistant ne remplace pas cette vérification.

Ne colle pas des clés d’API, des données clients ou des fragments propriétaires dans un service externe sans autorisation. Même un prompt utilisé pour demander une revue peut contenir des informations sensibles. Réduis le contexte envoyé au strict nécessaire et utilise les environnements approuvés.

5. Limites et erreurs fréquentes

  • Faire confiance à la syntaxe : une fonction bien formatée peut être logiquement fausse.
  • Accepter des tests superficiels : les tests passent, mais ne couvrent pas les règles métier ou les cas négatifs.
  • Ignorer le contexte : le code ne respecte pas les contrats, les conventions ou les versions du projet.
  • Ajouter une dépendance inutile : maintenance, surface d’attaque et complexité augmentent sans valeur suffisante.
  • Confondre outil et validation : un résultat d’analyse automatisée doit être interprété, et un contrôle absent ne prouve pas l’absence de risque.

Adapte l’intensité de la revue à l’impact du changement. Une fonction d’affichage simple n’exige pas la même démarche qu’un traitement de paiement, une permission d’accès ou une migration destructive. Mais aucun code généré ne doit être fusionné sans comprendre ce qu’il fait.

6. Exercice pratique

Demande à un assistant de générer une fonction qui calcule une remise en centimes avec un pourcentage exprimé en points de base. Écris indépendamment des tests pour 0 %, 100 %, un demi-centime, prix négatif, entier non sûr, remise négative, remise supérieure à 100 % et valeur fractionnaire. Vérifie la règle d’arrondi et explique pourquoi une sortie plausible ou des tests générés par le même assistant ne suffisent pas.

Critères de réussite

  • Je peux expliquer chaque ligne du code que j’intègre.
  • Je définis le contrat avant de juger l’implémentation.
  • Je teste les cas limites et les erreurs indépendamment du code généré.
  • Je vérifie sécurité, dépendances, licences et données sensibles.
  • Je sais adapter la profondeur de revue au risque sans supprimer la revue humaine.

163 — Atelier de clôture : vérifier le code généré

Objectif : Établis une chaîne de vérification reproductible avant d’intégrer du code généré.

Modèle mental et méthode

La vérification combine revue du diff, compilation, tests unitaires et d’intégration, analyse statique, audit des dépendances et tests des cas limites. Un test qui passe prouve seulement le comportement couvert ; il ne garantit pas l’absence de défaut.

Exemple guidé

Exemple : pour un parseur de date, teste chaîne vide, date invalide, fuseau, changement d’année et format inattendu. Vérifie aussi les exceptions et les effets de bord.

Pièges à éviter

Pièges : faire écrire les tests par le même prompt sans les relire, réduire les assertions pour faire passer la suite, ignorer licences et provenance.

Exercice de synthèse

Exercice : audite un extrait généré, ajoute au moins cinq cas limites et explique ce que chaque contrôle détecte.

Critères de réussite

Réussite : tests pertinents, erreurs reproduites, sécurité et dépendances contrôlées, limites connues.

Exemple de tests indépendants

Ces tests Vitest illustrent les frontières du contrat. Ils supposent que la fonction discountedPrice est importée depuis le module testé ; ils ne sont pas exécutés par la page statique.

import { describe, expect, it } from "vitest";
import { discountedPrice } from "./discounted-price";

describe("discountedPrice", () => {
  it("conserve le prix sans remise", () => {
    expect(discountedPrice({ priceCents: 101, percentageBps: 0 })).toBe(101);
  });

  it("retourne zéro à 100 %", () => {
    expect(discountedPrice({ priceCents: 999, percentageBps: 10_000 })).toBe(0);
  });

  it("arrondit un demi-centime vers le haut", () => {
    expect(discountedPrice({ priceCents: 1, percentageBps: 5_000 })).toBe(1);
  });

  it("préserve un entier sûr sans remise", () => {
    expect(discountedPrice({
      priceCents: Number.MAX_SAFE_INTEGER,
      percentageBps: 0
    })).toBe(Number.MAX_SAFE_INTEGER);
  });

  it("rejette une remise hors limites", () => {
    expect(() => discountedPrice({ priceCents: 100, percentageBps: 10_001 }))
      .toThrow(RangeError);
  });

  it("rejette un prix négatif", () => {
    expect(() => discountedPrice({ priceCents: -1, percentageBps: 0 }))
      .toThrow(RangeError);
  });
});

Complète la suite avec un prix non entier, un entier supérieur à Number.MAX_SAFE_INTEGER, une remise fractionnaire et NaN. Chaque test doit exprimer une règle du contrat, pas reproduire simplement la formule de l’implémentation.
