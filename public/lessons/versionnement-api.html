3. Backend

Versionnement d’API

Faire évoluer une API en protégeant les consommateurs existants grâce à des changements compatibles, une dépréciation mesurée et des contrats vérifiés.

Tutoriel détailléLot 11 · 2026

Objectifs d’apprentissage

  • Distinguer évolution compatible et changement cassant.
  • Choisir une stratégie de versionnement adaptée au contexte.
  • Organiser la dépréciation et le retrait d’une version.
  • Tester la compatibilité des clients et des contrats.

Fil conducteur

Avant de créer une nouvelle version, détermine si le changement est réellement incompatible. Prépare ensuite la migration des consommateurs, l’observation de l’usage et une procédure de retrait explicite.

1. Ce que signifie versionner une API

Une API est un contrat : chemins, méthodes, paramètres, formats, statuts et sémantique métier. Versionner ne consiste pas seulement à modifier une URL. Il faut gérer les changements du contrat dans le temps et préserver les clients qui n’ont pas encore migré.

Une évolution est généralement compatible lorsqu’un client existant continue de fonctionner sans modification. Ajouter un champ facultatif à une réponse est souvent compatible ; rendre un champ obligatoire, supprimer une propriété ou changer la signification d’un champ peut casser les intégrations.

2. Les stratégies courantes

  • Version dans le chemin : /api/v1/orders, puis /api/v2/orders. Facile à repérer, router et documenter.
  • En-tête de version : la version est transmise dans un en-tête dédié. L’URL reste stable, mais les outils et caches doivent gérer ce choix correctement.
  • Version par média type : la représentation demandée précise la version. C’est flexible mais moins visible dans une URL.

Aucune stratégie n’est universellement supérieure. Pour une API publique, la lisibilité opérationnelle et la facilité de migration comptent autant que l’élégance théorique.

3. Évoluer sans nouvelle version majeure

Privilégie les ajouts facultatifs et les changements qui ne modifient pas le sens des données existantes. Évite de supposer que tous les clients ignorent les champs inconnus : certains désérialiseurs stricts peuvent échouer. Pour les énumérations, l’ajout d’une nouvelle valeur peut aussi casser un client qui ne prévoit que les valeurs connues.

// Réponse existante
{ "id": "ord_123", "status": "paid" }

// Évolution additive
{ "id": "ord_123", "status": "paid", "createdAt": "2026-10-10T10:00:00Z" }

Documente les champs, leur nullabilité, les valeurs possibles et les garanties de stabilité. Teste la sérialisation et les clients représentatifs avant la mise en production.

4. Dépréciation et retrait

  1. Identifier les consommateurs et les usages réels de l’ancienne version.
  2. Publier une date de dépréciation et une date de fin de support compréhensibles.
  3. Fournir une documentation de migration avec exemples avant/après.
  4. Mesurer les appels encore effectués sur l’ancienne version.
  5. Prévenir les consommateurs connus et vérifier les dépendances critiques avant retrait.

Une annonce seule ne suffit pas : sans visibilité sur les usages, une version obsolète peut continuer d’être appelée par un service oublié.

5. Contrats, tests et gouvernance

Maintiens une spécification par version supportée et automatise les tests de contrat. Une comparaison OpenAPI peut signaler la suppression d’une propriété, le changement de type ou l’ajout d’un paramètre obligatoire. Les tests ne remplacent pas la discussion de compatibilité sémantique : une réponse peut respecter le schéma tout en changeant de sens.

Définis une politique claire : durée de support, délai de préavis, critères de changement majeur, responsable de validation et procédure d’urgence. Les exceptions doivent être explicites.

Exercice guidé

Une API de commandes expose GET /api/v1/orders avec les champs id, status et total. On souhaite ajouter la devise, renommer total en amount, puis supprimer une valeur de statut. Classe chaque changement en compatible, potentiellement risqué ou cassant et propose un plan de migration.

Critères de réussite

  • Chaque changement est évalué du point de vue du client.
  • Les changements cassants ont une stratégie de transition.
  • La dépréciation s’appuie sur des métriques et une communication.
  • Les contrats et tests sont versionnés et exécutés en CI.

Erreurs fréquentes

  • Créer une nouvelle version pour chaque petit ajout.
  • Modifier le sens d’un champ sans changer le contrat.
  • Supprimer une version sans mesurer son usage.
  • Confondre version de l’API et version de l’application serveur.
  • Publier une migration sans expliquer les changements concrets.
