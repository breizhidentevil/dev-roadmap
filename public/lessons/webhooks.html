Webhooks et intégrations tierces

Recevoir des événements externes de manière sécurisée, tolérer les doublons et retards, puis traiter les événements de façon observable et fiable.

1. Objectifs et prérequis

Un webhook permet à un service externe de notifier votre application lorsqu’un événement survient, au lieu de vous obliger à interroger régulièrement son API. Cette simplicité apparente cache des questions de sécurité et de fiabilité : l’émetteur peut réessayer, envoyer les événements dans le désordre, ou ne pas recevoir votre accusé de réception. À la fin, vous saurez concevoir un endpoint de réception, vérifier l’authenticité des messages, dédupliquer les événements et séparer l’acquittement du traitement métier.

2. Fonctionnement général

Le consommateur enregistre une URL auprès du fournisseur. Lorsqu’un événement se produit, le fournisseur envoie une requête HTTP, souvent un POST contenant un corps JSON, un identifiant d’événement, un type et des métadonnées. Votre endpoint vérifie la requête, enregistre l’événement et répond rapidement avec un statut convenu. Le traitement métier peut ensuite se faire en arrière-plan.

Un webhook n’est pas une source de vérité absolue. Un événement peut être livré plusieurs fois, être retardé ou arriver après un événement plus récent. Selon le fournisseur, il peut aussi exister une durée maximale de retry et une procédure de rejeu. Consultez les garanties et limites documentées par chaque intégration.

3. Sécuriser la réception

Ne faites pas confiance à un webhook uniquement parce qu’il arrive à une URL difficile à deviner. Utilisez le mécanisme d’authentification recommandé par le fournisseur, souvent une signature HMAC calculée sur le corps brut avec un secret partagé. La vérification doit être effectuée avant de traiter les données, avec une comparaison résistante aux attaques temporelles lorsque le langage ou la bibliothèque le permet.

// Pseudocode : utilisez la bibliothèque cryptographique adaptée.
const rawBody = await readRawRequestBody(request);
const suppliedSignature = request.headers.get("provider-signature");

if (!verifySignature(rawBody, suppliedSignature, webhookSecret)) {
  return new Response("Signature invalide", { status: 400 });
}

Le pseudo-code souligne un détail important : certains fournisseurs signent les octets exacts du corps reçu. Si votre framework parse puis sérialise le JSON, l’espace ou l’ordre des propriétés peut changer et invalider la signature. Suivez la documentation du fournisseur. Ne loguez pas le secret ni le corps complet s’il contient des données personnelles ou des jetons.

Vérifiez également les limites de taille, les délais de traitement, le type de contenu et les protections réseau adaptées à votre environnement. Une liste d’adresses IP peut être une défense complémentaire si le fournisseur la publie, mais elle ne remplace pas la vérification cryptographique. Gardez les secrets hors du dépôt et prévoyez leur rotation.

4. Accuser réception rapidement

Les fournisseurs attendent généralement une réponse dans un délai limité. Effectuer plusieurs appels lents à des services tiers avant de répondre peut provoquer un timeout côté fournisseur, qui renverra alors le même événement. Une approche robuste consiste à vérifier la signature, à enregistrer durablement l’événement dans une file ou une table d’inbox, puis à acquitter la réception.

Cette séquence exige une vraie persistance : répondre « reçu » avant que l’événement soit durablement enregistré risque de le perdre si le processus s’arrête. À l’inverse, si l’écriture réussit mais que la réponse réseau se perd, le fournisseur peut envoyer un doublon. Le système doit être capable de reconnaître ce doublon.

5. Déduplication et traitement au moins une fois

Utilisez l’identifiant stable fourni par l’émetteur, combiné au contexte nécessaire pour éviter les collisions entre comptes ou fournisseurs. Stockez cet identifiant avec un état de traitement et une contrainte d’unicité. Ne vous fiez pas à l’heure d’arrivée ou à l’égalité approximative des corps : deux événements légitimes peuvent avoir un contenu identique.

type IncomingEvent = {
  provider: string;
  eventId: string;
  eventType: string;
  receivedAt: string;
  payload: unknown;
};

// À la réception :
// 1. vérifier la signature ;
// 2. insérer l'événement avec une contrainte unique ;
// 3. mettre le traitement en file ;
// 4. acquitter seulement après persistance durable.

Attention à la double écriture : enregistrer l’inbox puis publier séparément dans une file laisse une fenêtre où le processus peut tomber entre les deux. Si la file n’est pas elle-même le stockage durable de réception, écrivez l’inbox et une ligne d’outbox dans la même transaction, puis laissez un dispatcher publier l’outbox. Exemple SQL schématique (les tables et colonnes doivent être adaptées au schéma réel) :

BEGIN;

WITH accepted AS (
  INSERT INTO webhook_inbox
    (provider, account_id, event_id, event_type, payload, status)
  VALUES
    (:provider, :account_id, :event_id, :event_type, :payload, 'pending')
  ON CONFLICT (provider, account_id, event_id) DO NOTHING
  RETURNING id
)
INSERT INTO outbox (topic, aggregate_id, payload)
SELECT
  'webhook.received',
  id,
  jsonb_build_object('inboxId', id)
FROM accepted;

COMMIT;

La contrainte unique doit porter sur le véritable périmètre d’unicité du fournisseur (ici fournisseur, compte et identifiant d’événement). Si aucun événement n’est inséré parce qu’il s’agit d’un doublon, aucune nouvelle ligne d’outbox n’est créée. Répondez positivement seulement après le commit durable, selon le contrat du fournisseur ; le dispatcher et le worker doivent eux aussi tolérer une publication ou une livraison répétée.

Le traitement doit lui aussi être idempotent. Il peut être exécuté, puis le worker peut s’arrêter avant de marquer l’événement comme terminé. À la reprise, l’événement sera traité une nouvelle fois. Les mutations métier doivent donc utiliser une transaction, une clé de déduplication ou une opération qui tolère la répétition.

6. Ordre, versions et événements périmés

Ne supposez pas que les événements arrivent dans l’ordre où ils se sont produits. Si un client reçoit « paiement confirmé » puis « paiement en attente » avec retard, appliquer naïvement le dernier message reçu peut faire régresser l’état. Utilisez si possible une version, un numéro de séquence ou l’état courant consulté auprès de l’API du fournisseur. Définissez les transitions métier autorisées plutôt que de copier chaque payload sans contrôle.

Un événement peut n’être qu’une notification indiquant qu’une ressource a changé. Dans ce cas, il peut être préférable de récupérer la ressource actuelle via l’API du fournisseur au lieu de considérer le contenu de l’événement comme exhaustif. Cette stratégie ajoute un appel réseau et nécessite elle aussi des délais, retries et règles de limitation.

7. Retries, erreurs et file de quarantaine

Un échec temporaire de traitement doit être réessayé selon une politique bornée. Les erreurs permanentes, les messages invalides ou les événements qui échouent toujours ne doivent pas être remis en boucle sans fin. Après un nombre déterminé d’essais, placez-les dans une file de quarantaine ou un état nécessitant une investigation, avec une procédure de rejeu contrôlée.

Les réponses HTTP du endpoint doivent suivre les règles du fournisseur : un statut de succès peut arrêter ses retries, tandis qu’un statut d’erreur peut les déclencher. Il ne faut pas renvoyer un échec au fournisseur pour un problème métier déjà enregistré si le contrat indique que l’événement est pris en charge et que le traitement sera repris en interne. Documentez cette frontière clairement.

8. Observabilité et données sensibles

Chaque événement devrait pouvoir être retrouvé par son identifiant, le fournisseur, le type, l’heure de réception, le nombre de tentatives et l’état de traitement. Mesurez les retards, les erreurs de signature, les doublons et la taille de la file. Une alerte sur un événement bloqué peut être plus utile qu’un simple compteur d’erreurs HTTP.

Conservez le minimum de données nécessaire, limitez les accès et définissez une durée de rétention. Les payloads peuvent contenir des informations personnelles, des adresses ou des identifiants internes. Préférez les logs structurés avec des champs expurgés aux journaux qui enregistrent systématiquement l’intégralité du corps.

9. Erreurs fréquentes

  • Accepter un webhook sans vérifier la signature ou le mécanisme d’authentification.
  • Parser le corps avant la vérification alors que la signature porte sur les octets bruts.
  • Faire tout le traitement métier avant l’accusé de réception et dépasser le délai du fournisseur.
  • Répondre avec succès avant d’avoir persisté l’événement.
  • Supposer une livraison unique ou un ordre strict.
  • Oublier les retries bornés, la quarantaine et la procédure de rejeu.

10. Exercice et critères de réussite

Concevez un webhook fictif de confirmation de paiement. Définissez les contrôles de signature, la table d’inbox, la clé unique de déduplication et les statuts du worker. Simulez deux livraisons du même événement, un retard d’ordre et une panne du worker après l’écriture métier mais avant l’accusé de traitement. Décrivez comment le système évite une double confirmation et comment l’équipe retrouve un événement bloqué.

  • Je vérifie l’authenticité du message avant son traitement.
  • Je persiste durablement l’événement avant de l’acquitter.
  • Je supporte les doublons, les retards et les traitements rejoués.
  • Je borne les retries et prévois une file de quarantaine.
  • Je trace les événements sans exposer inutilement les données sensibles.

Explications et exemple guidé

Un webhook est une notification HTTP envoyée par un système externe. Il peut être dupliqué, retardé, désordonné ou rejoué. Le endpoint doit authentifier la provenance, valider le format, enregistrer l’événement de façon durable et répondre rapidement ; le traitement métier peut ensuite être délégué à une file.

  1. Lire le corps brut si la signature du fournisseur est calculée sur ses octets exacts.
  2. Vérifier la signature avec une comparaison sûre et appliquer une fenêtre temporelle lorsque le protocole le prévoit.
  3. Enregistrer un identifiant d’événement unique avec une contrainte d’unicité.
  4. Répondre après acceptation durable, puis traiter de manière idempotente.

Une signature valide prouve l’origine du message selon le protocole, mais ne remplace pas la validation du schéma, l’autorisation métier ni la protection contre le rejeu.

Pièges et limites

  • Piège : parser puis re-sérialiser le JSON avant de vérifier une signature attendue sur le corps brut.
  • Piège : répondre succès avant toute persistance et perdre l’événement lors d’un crash.
  • Piège : supposer que chaque événement arrive une seule fois ou dans l’ordre.
  • Piège : exposer le secret de signature dans les logs.

Exercice

Élaborez un endpoint de webhook de commande avec vérification de signature, table d’événements reçus, déduplication et file de traitement. Décrivez la stratégie en cas d’indisponibilité de la base ou d’échec du worker.

Critères de réussite

  • La signature est vérifiée selon la documentation du fournisseur.
  • L’événement est persisté avant l’accusé de réception positif.
  • Les doublons ne produisent pas de double effet métier.
  • Les retries, échecs permanents et mécanismes de rejeu sont documentés et observables.
