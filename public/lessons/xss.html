5. Sécurité applicative

Prévention des failles XSS

Afficher le contenu non fiable sans permettre son interprétation comme code dans le navigateur.

Tutoriel approfondiBackend et données

Objectifs d’apprentissage

  • Définir une faille XSS et distinguer ses principales formes.
  • Choisir une méthode d’affichage qui traite les données comme du texte plutôt que comme du code.
  • Comprendre l’encodage contextuel, l’assainissement HTML et les protections complémentaires.

1. Comment fonctionne une XSS ?

Une faille Cross-Site Scripting (XSS) permet à un contenu non fiable d’être interprété comme du code dans le navigateur d’une victime, dans le contexte du site vulnérable. Une XSS peut être stockée (contenu malveillant enregistré puis affiché), réfléchie (retournée dans une réponse) ou basée sur le DOM (le code côté client manipule une entrée de façon dangereuse).

Le risque ne se limite pas à une fenêtre d’alerte : un script exécuté dans le contexte du site peut agir avec les droits de la session de l’utilisateur, lire des données accessibles à la page ou déclencher des actions. Les cookies marqués HttpOnly ne sont pas directement lisibles par JavaScript, mais cela ne rend pas une XSS inoffensive.

2. Traiter les données comme des données

Pour afficher du texte fourni par un utilisateur, privilégie les API qui créent du texte, par exemple textContent, plutôt que d’interpréter une chaîne comme HTML.

// Sûr pour afficher un texte brut
messageElement.textContent = userProvidedMessage;

// Dangereux si la chaîne contient du HTML contrôlé
messageElement.innerHTML = userProvidedMessage;

Les frameworks modernes échappent généralement les interpolations textuelles ordinaires, mais des API de HTML brut ou des bibliothèques tierces peuvent contourner cette protection. Si du HTML est réellement nécessaire, utilise un assainisseur reconnu, configuré pour le contexte et maintenu à jour.

L’encodage doit correspondre au contexte de sortie : texte HTML, attribut, URL, CSS et JavaScript ne suivent pas les mêmes règles. Évite d’insérer des données non fiables dans du code JavaScript inline, des gestionnaires d’événements ou des contextes difficiles à encoder correctement.

3. Défense en profondeur

La politique de sécurité du contenu (CSP) peut limiter les scripts autorisés et réduire certaines conséquences, mais elle ne remplace pas le traitement sûr des données. Évite les scripts inline non nécessaires et privilégie une politique CSP restrictive avec des nonces ou des hachages lorsque l’architecture le permet.

Teste les chemins où du contenu utilisateur est enregistré, affiché, rendu côté client ou inséré dans le DOM. Une bibliothèque de composants, un aperçu Markdown ou un éditeur riche peuvent créer des contextes de sortie spécifiques. Vérifie également que les URL utilisées comme liens ne permettent pas des schémas dangereux.

Choisir la défense selon le contexte de rendu

Il n’existe pas un encodage universel pour toutes les sorties. Commence par identifier le contexte exact où la donnée sera interprétée, puis privilégie une API qui évite l’interprétation de code. Les données injectées dans une URL, un attribut HTML ou un bloc JavaScript demandent des protections différentes ; le plus sûr est généralement de ne pas placer de données non fiables dans du code exécutable.

// Texte ordinaire : aucune interprétation HTML
statusNode.textContent = profile.displayName;

// Lien : contrôler le schéma et la destination avant affectation
const target = new URL(profile.website, window.location.origin);
if (target.protocol === 'https:' || target.origin === window.location.origin) {
  link.href = target.href;
}

La validation d’URL de l’exemple est illustrative : adapte la politique aux liens réellement permis. Une URL analysable n’est pas automatiquement sûre. Pour du HTML riche, configure un assainisseur maintenu et teste les éléments, attributs et schémas autorisés après assainissement.

  • Ajouter des tests pour texte brut, guillemets, balises, attributs événementiels et URL de schéma inattendu.
  • Tester le rendu initial côté serveur et les mises à jour DOM côté client.
  • Rechercher les API de HTML brut et les composants tiers qui contournent l’échappement normal.

Tests de non-régression

Un test doit vérifier le résultat du rendu, pas seulement l’absence d’une exception. Utilise des marqueurs inoffensifs dans les tests automatisés et inspecte le DOM final.

  • Texte brut : la chaîne <b>marqueur</b> apparaît littéralement ; aucun élément b n’est créé.
  • Attributs et événements : une chaîne contenant un attribut événementiel reste du texte ou est supprimée par l’assainisseur ; aucun gestionnaire n’est actif.
  • URL : les liens javascript: et data: sont refusés selon la politique du produit ; les liens HTTPS autorisés restent fonctionnels.
  • HTML riche : les balises permises sont conservées, tandis que les scripts, attributs événementiels et schémas d’URL non autorisés sont retirés.
  • Chemins de rendu : couvre le rendu serveur et les mises à jour DOM, et recherche les sinks tels que innerHTML, outerHTML, insertAdjacentHTML, document.write et les API de HTML brut des frameworks.

Ne valide pas l’exercice en te contentant d’un test CSP : la défense principale reste le traitement adapté au contexte de sortie et l’assainissement du HTML riche.

Erreurs fréquentes

  • Utiliser innerHTML pour afficher un simple message utilisateur.
  • Considérer une validation de longueur ou de caractères comme une protection XSS complète.
  • Réutiliser un encodage conçu pour le texte HTML dans un attribut ou une URL.
  • Penser que React ou un autre framework protège les API de HTML brut.
  • Traiter CSP comme une solution qui permet de conserver du rendu dangereux.

Exercice

Une application affiche le commentaire saisi par un utilisateur et propose ensuite un aperçu HTML enrichi. Réécris l’affichage du commentaire en texte brut, puis décris comment traiter l’aperçu riche avec un assainisseur maintenu. Indique les tests nécessaires pour les vues serveur et client.

Critères de réussite

  • Le commentaire ordinaire est affiché avec textContent ou l’équivalent sûr du framework.
  • Le HTML riche est assaini avec une politique explicite, pas par une expression régulière maison.
  • Le contexte d’insertion est pris en compte.
  • La CSP est considérée comme une couche supplémentaire, non comme la défense principale.
